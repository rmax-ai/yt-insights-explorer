Overview

  • Speaker: Michael Cohen, Member of Technical Staff, Anthropic
  • Channel: Claude
  • Main topic: Building and scaling production-ready autonomous agents using Claude Managed Agents
  • Purpose: To provide developers with a comprehensive technical guide and hands-on walkthrough for building, configuring, orchestrating, and observing production-ready autonomous agents using Claude Managed Agents. In this technical workshop, Michael Cohen from Anthropic walks through building and deploying production-ready autonomous agents using Claude Managed Agents. He covers the core primitives—agent definitions, environments, sessions, and events—and demonstrates implementing a multi-agent M&A research application called Deal Desk using the Anthropic SDK and Claude Code.

[A]Architecturehigh noveltymoderate evidence

Session events are a single unified stream carrying control-plane signals (user events, agent actions, session state) and telemetry (span data) on the same channel, rather than telemetry being a separate observability sidecar.

Why it matters

If the runtime event protocol is also the observability protocol, then tracing, debugging, and replay come from the same durable artifact the application already consumes to drive state — removing the need to instrument a parallel tracing pipeline and making agent execution auditable by default.

Generalization

Agent runtimes should treat the event log as the primary append-only source of truth for both application state transitions and telemetry, rather than bolting observability onto a runtime after the fact.

[A]Architecturemedium noveltymoderate evidence

The execution environment is decoupled from the managed control plane: developers can substitute the Anthropic sandbox with their own (Cloudflare, Vercel, Modal) while keeping the agent/session/event primitives.

Why it matters

This draws an explicit boundary between orchestration/state (managed) and compute/isolation (swappable), which is the split enterprise buyers need for data residency, egress control, and reuse of existing cloud commitments.

Generalization

Agent platforms should expose the sandbox as a pluggable execution interface behind a managed control plane, so isolation guarantees and cloud placement become deployment-time choices rather than platform lock-in.

[M]Mechanismhigh noveltymoderate evidence

MCP tunnels invert the usual network model: the agent reaches private MCP servers inside a corporate perimeter without those servers being exposed to the public internet.

Why it matters

Most agent security guidance focuses on the agent's outbound egress and secret handling; this addresses the opposite risk — exposing internal tool servers (e.g., private databases) to reach them from a hosted agent. An outbound tunnel broker changes the trust boundary from network ingress to a brokered, authenticated channel.

Generalization

Tool access to internal systems should be modeled as an outbound, brokered connection from the resource side rather than inbound exposure of the resource — the same pattern as reverse tunnels or private service connect.

Source video ↗
[M]Mechanismmedium noveltymoderate evidence

Memory is externalized as persistent, human-editable store artifacts (markdown files) that agents read and write across sessions, rather than being implicit context window state or opaque embedding retrieval.

Why it matters

Making memory a first-class, inspectable artifact allows operators to diff, audit, correct, and version what an agent 'knows' between sessions — closing a common production gap where memory errors are invisible and unrepairable.

Generalization

Long-lived agent memory should be a versioned, human-readable store with explicit read/write semantics per session, so memory correctness becomes a reviewable engineering artifact rather than a retrieval side effect.

Source video ↗
[P]Practicemedium noveltymoderate evidence

Tool authorization is expressed as a per-tool execution policy (auto-execute vs. require approval) rather than a global autonomy setting or a single global kill switch.

Why it matters

Autonomy level is a per-capability dial, so agents can run read-only tools unattended while gating destructive or external-effect tools behind human approval — a practical middle ground between 'fully autonomous' and 'confirmation on every step'.

Generalization

Agent permission models should be scoped per tool/capability with explicit execution policies, since autonomy is not a single axis but a per-action risk decision.

Source video ↗
[~]Tradeoffmedium noveltymoderate evidence

Adopting the managed primitives removes session and state plumbing from application code, with the live demo implementing session lifecycle through thin beta SDK calls (client.beta.sessions.list/create) and an event stream.

Why it matters

The abstraction boundary moves: what used to be custom durable-state, retry, and sandbox orchestration code becomes platform surface area, so team effort shifts to agent definition and environment configuration — while the beta namespace signals an unstable contract and a migration burden.

Generalization

As agent platforms absorb session/state infrastructure, the differentiating engineering work shifts upward to prompt/skill/tool/environment design, and the risk profile shifts from build complexity to platform dependency and API churn.

Unified event stream as control plane and telemetry substrate

Research question

Can a single append-only session event stream faithfully serve as both the control plane for agent state transitions and the primary telemetry substrate for tracing, debugging, and replay, or does this coupling constrain observability depth?

Why

If true, agent runtimes can eliminate separate tracing pipelines and make every run auditable by default; if false, teams may need sidecar observability despite the unified stream.

Trust boundary and failure domain of outbound MCP tunnels

Research question

Why

Enterprise adoption depends on knowing whether tunnel brokering adds a new critical path and blast radius versus simply preserving the perimeter.

Feature parity across managed and self-hosted sandboxes

Research question

Why

Approval policy propagation in delegated multi-agent topologies

Why

Delegation multiplies tool invocations; if approval policy does not compose, per-tool permissions give false assurance in exactly the topologies they are meant to make safe.

Sandbox Parity Diff Harness

gatehouse

For the same agent definition and environment, self-hosted sandboxes (Cloudflare, Vercel, Modal) do not emit identical event/span telemetry or enforce identical network/package controls as the managed sandbox; differences are observable and measurable.

Proof of concept

Define one agent and environment, run identical sessions against managed and self-hosted sandboxes, capture event streams and telemetry, and diff event types, ordering, metadata, and sandbox controls.

Measurement

Event type coverage, missing span rate, ordering divergence, p95 latency delta, and network/package policy mismatches.

MCP Tunnel Fault Injector

gatehouse

Proof of concept

Run an agent that depends on a private database MCP server through a tunnel; inject latency, disconnects, and auth failures; capture session events and agent outputs.

Measurement

Delegated Approval Propagation Tester

gatehouse

Proof of concept

Architectural implications

4

The primitives are split into agent definition (template: system prompt, skills, tools), environment (container template, network controls, packages), session (conversation instance), and events (stream).

Before

A team builds one monolithic agent service that conflates prompt config, container setup, conversation state, and logging in application code.

After

Configuration is decomposed into a reusable agent template plus a deployment environment plus instantiated sessions, with events as the interaction interface.

Consequence

Agent configuration becomes declarative and reusable across deployments, but teams must now manage lifecycle and versioning across three separate abstractions instead of one codebase.

Source video ↗

Private MCP servers are reached via secure tunnels rather than internet exposure.

Before

Internal tool servers must be exposed through ingress, VPN, or public endpoints to be callable by a hosted agent.

After

An outbound tunnel lets the hosted agent reach private MCP servers while they stay inside the corporate perimeter.

Consequence

Enterprise adoption of hosted agents no longer requires opening internal services to the internet, but it introduces a new brokered component that must be authenticated, monitored, and made highly available.

Source video ↗

Observability is delivered through the Claude Console session view, including parallel sub-agent execution timelines and debug logs.

Before

Debugging a multi-agent run requires correlating scattered application logs across concurrently executing sub-agents.

After

Parallel sub-agent execution is rendered as a single timeline within the session view.

Consequence

Concurrency in multi-agent orchestration becomes legible for operations, but visibility depth is bounded by what the platform chooses to expose.

Source video ↗

Multi-agent coordination is implemented by a coordinator agent delegating to four research sub-agents running in parallel.

Before

A single agent sequentially performs all research subtasks within one context.

After

A coordinator decomposes the task and fans out to specialized sub-agents executing concurrently.

Consequence

Task specialization and wall-clock efficiency improve, but cost, concurrency limits, and per-sub-agent failure handling become new coordination concerns with less obvious attribution.

Tradeoffs and failure modes

5

Platform absorption of session/state infrastructure

Benefit

Eliminates custom boilerplate for session and state management and inherits sandboxing, retries, and context management.

Cost or risk

Depends on a beta SDK surface (client.beta.sessions), implying API churn and migration work, plus lock-in to a specific platform's primitive model.

Source video ↗

Bring-your-own sandbox

Benefit

Meets enterprise data-residency and cloud-standardization requirements by running execution on Cloudflare, Vercel, or Modal.

Cost or risk

Self-hosting the execution layer reintroduces operational responsibility for isolation, patching, scaling, and feature parity with the managed sandbox.

Source video ↗

Per-tool approval policies

Benefit

Allows unattended execution for low-risk tools while gating high-risk tools, avoiding a binary autonomy choice.

Cost or risk

Approval-gated tools introduce human latency and blocking into otherwise asynchronous agent runs, and approval logic must be maintained per tool.

Source video ↗

Persistent cross-session memory

Benefit

Agents retain context between sessions instead of relearning it each run.

Cost or risk

Persisted memory outlives the reasoning that produced it, so stale or incorrect entries propagate across future sessions unless explicitly curated — which the console supports but does not automate.

Source video ↗

Parallel sub-agent fan-out

Benefit

Improves efficiency and specialization for complex research or workflow tasks.

Cost or risk

Multiple concurrent agents multiply token cost and run-surface, and failures or loops in one sub-agent must be detected and recovered without a single linear transcript.

Source video ↗
