Summary

Overview

  • Speaker: Justin Schroeder
  • Channel: AI Engineer
  • Main topic: Domain-Specific AI Agents and Multi-Agent Orchestration
  • Purpose: To explain why domain-specific agents are the future of AI engineering, detail the agent tech stack (from models to MCP and skills), contrast inheritance with composition in agent design, and predict the rise of multi-agent orchestration by 2027. Justin Schroeder argues that the future of AI building and usage lies in domain-specific agents rather than monolithic general-purpose models. He defines agents as deterministic software harnessing non-deterministic model results, explains the challenges of current agent engineering, and introduces a stack based on composition, Model Context Protocol (MCP), agent skills, and multi-agent coordination mimicking historical engineering milestones like the Apollo program.

Key Points

Agents are deterministic software wrapped around non-deterministic models

  • Explanation: The orchestration logic, loop control, and safety guardrails are code-driven, while the reasoning steps rely on probabilistic AI models.
  • Evidence: Justin Schroeder's formal definition slide.
  • Practical implication: Developers must focus on robust software engineering around the model rather than treating the model as the entire application.

Token costs are rising, not falling, when accounting for intelligence needs

  • Explanation: Even though raw token prices drop, the token count required per task is increasing rapidly due to context bloat and lack of efficiency.
  • Evidence: Standard Agents tracking data showing token costs up 29% to 76% in 2026.
  • Practical implication: Domain-specific agents are required to restrict context windows and drastically improve token efficiency.

Composition beats inheritance in agent scaling

  • Explanation: Overloading a single agent with every tool and skill causes context degradation and high token costs. Orchestrating small, specialized agents via natural language coordination is far more effective.
  • Evidence: Analogy to software engineering principles (composition over inheritance) and multi-agent workflow diagrams.
  • Practical implication: Build modular sub-agents for specific tasks (e.g., Figma, Gmail, legal compliance) rather than one giant monolithic assistant.

Core insights

[O]Mental Modelmedium noveltystrong evidence

Agents should be defined as deterministic software that harnesses non-deterministic model output — orchestration logic, loop control, and guardrails are code, while only reasoning steps are probabilistic. This makes the 'harness' a first-class engineering artifact separate from the model.

Why it matters

It relocates engineering effort from prompt/model tuning to the software layer (control flow, guardrails, safety) that most teams underinvest in, and gives a concrete boundary for what is and is not an 'agent'.

Generalization

Any system embedding a probabilistic component should treat the probabilistic part as a bounded service inside deterministic code, not as the application itself.

[A]Architecturemedium noveltymoderate evidence

Scaling a single agent by stacking MCP servers and skills exhibits diminishing returns on context; the composition pattern — a coordinator dispatching to narrow sub-agents (e.g., Figma, Gmail, Kayak, Navan) — is claimed to be the superior architecture. This is inheritance-vs-composition from OO design re-applied to agent capability accumulation.

Why it matters

It defines where capability boundaries belong: not inside one context window, but between agents. This changes how teams decompose tools, prompts, and permissions.

Generalization

Capability growth via accumulated context scales sublinearly; capability growth via decomposition into independently-scoped components scales better wherever context is a scarce resource.

Why it matters

It inverts the common cost-model assumption that model price declines automatically improve unit economics, and makes context discipline (not model choice) the primary cost lever.

Generalization

When a resource gets cheaper per unit but consumption per unit of work rises faster, total cost rises; optimizations must target consumption, not unit price.

Sub-agent granularity: measuring composition over inheritance

Research question

For a fixed multi-tool task, what sub-agent granularity minimizes tokens per successful task, and how does task-failure attribution change as tools move from one shared context window into independently-scoped sub-agents?

Why

The composition claim is asserted with an analogy (Figma, Gmail, Kayak, Navan) but no boundary rule or benchmark. Without a measured granularity curve, teams decomposing agents are guessing, and coordination cost may silently eat the context savings.

Source video ↗

Skill-count degradation mechanism and the routing fix

Research question

Is agent performance degradation with skill count monotonic, and is the cause context dilution, tool-selection ambiguity, or conflicting instructions — and does retrieval/routing over the skill registry remove the degradation?

Why

Skill degradation is treated as context pollution but the mechanism is unstated, so teams cannot decide whether to cap skills, summarize them, or retrieve them. This determines whether an agent skill library can scale at all.

Source video ↗

Separating scope restriction from model choice in the token-savings claim

Research question

How much of the reported 80%+ token savings from domain-specific agents is attributable to narrowed scope versus model choice, when model and scope are independently ablated on the same task set?

Why

The savings figure and the SLM practicality claim are stated together, so teams cannot tell whether narrowing scope makes small models viable or whether a small model was doing the saving. This determines the order of operations for cost work.

Source video ↗

Cost model for recursive sub-agency at increasing depth

Research question

In a coordinator/sub-agent topology, how do token consumption, latency, and error propagation scale from depth 1 to depth 3, and at what depth does marginal task success stop justifying marginal cost?

Why

Sub-agents represented as tools make recursion the default scaling mechanism, but nesting adds overhead and makes it ambiguous where hooks, rules, and context limits apply. A depth ceiling or budget rule is needed before this becomes a production default.

Interface checklist for the missing agent standard

Research question

Which concrete interfaces (loop control, provider abstraction, durable execution, telemetry, composability) must a framework define for agents to be portable, and how do current candidates score against that checklist on the same agent?

Why

High friction in telemetry, portability, and composability is named as the core pain, and 'eve' is cited as an emerging standard without defined interfaces. Turning this into a checklist converts an opinion into a testable portability target.

Project ideas

4

Granularity Bench

beyond-evals

For a fixed multi-tool task set, a coordinator dispatching to 3–4 narrow sub-agents achieves at least 50% fewer tokens per successful task than a single agent with every tool loaded into one context, at equal or better task success.

Proof of concept

Implement both topologies against the same task suite with the same tool set (Figma, Gmail, Kayak, Navan), a shared model, and identical prompts-per-tool; run N trials per task and instrument token accounting per agent boundary.

Measurement

Tokens per successful task, task success rate, latency, and per-failure attribution (which agent boundary failed) for monolithic vs. composed topologies.

Source video ↗

Skill Degradation Curve

beyond-evals

Tool-selection accuracy degrades monotonically past a measurable skill count, and replacing unconditional skill loading with retrieval-based skill routing removes the degradation at equal task success.

Proof of concept

Incrementally inject 1 to 100 skill definitions into a fixed agent, probing tool-selection accuracy and instruction-following at each step; then swap in a retrieval router over the same registry and repeat the sweep.

Measurement

Tool-selection accuracy and instruction-following score as a function of injected skill count, with and without retrieval routing; identify the degradation knee.

Source video ↗

Context Cost Attribution Gateway

gatehouse

Most per-task token growth is context payload (tool schemas, skill documentation, accumulated history) rather than reasoning tokens, so enforcing a per-request context budget at the gateway cuts cost per task by 30%+ at parity task success.

Proof of concept

Instrument an agent's outbound calls to segment every request into tool-schema tokens, skill-documentation tokens, history tokens, and reasoning tokens; add a gateway policy that caps and summarizes the injectable segments only.

Measurement

Token breakdown by segment per task and cost per task before and after the gateway policy, plus task success rate to confirm parity.

Source video ↗

Sub-Agent Depth Meter

new

Coordinator/sub-agent nesting beyond depth 2 yields sublinear task-success gains while producing superlinear token and latency cost, and error propagation across boundaries amplifies with each added level.

Proof of concept

Build one coordinator with specialized sub-agents callable as tools, then run the same task set at nesting depths 1, 2, and 3 with identical sub-agent implementations and injected failures at each boundary.

Measurement

Tokens, latency, task success, and error-propagation rate (failures traceable to a nested boundary) as a function of nesting depth.

Architectural implications

3

The unit of capability becomes the sub-agent boundary rather than the tool/skill slot on a single agent.

Before

One general-purpose agent accumulating MCP servers and skills in a shared context window.

After

A coordinator agent routing to narrow sub-agents (Figma, Gmail, Kayak, Navan, Salesforce, Google Workspace, Asset Generation).

Consequence

Context per agent shrinks; permissions and capability limits become enforceable per sub-agent; tool registries must be scoped rather than global.

Source video ↗

The model, harness, and agent are separated as distinct artifacts.

Before

The model is treated as the application, with orchestration implicit in prompts.

After

Deterministic orchestration code (loop control, guardrails, hooks, rules) wraps non-deterministic model calls.

Consequence

Portability, telemetry, and durable execution become harness concerns with their own design surface, and provider abstraction can live below the agent.

Source video ↗

Sub-agents are represented as a tool type in the stack, alongside functions and prompts.

Before

Tools are external functions; agents are top-level constructs.

After

Sub-agents callable as tools, enabling recursion under a coordinator.

Consequence

Uniform call interface simplifies orchestration but raises questions about depth limits, cost accounting, and failure propagation across nested agents.

Source video ↗
