Summary

Overview

  • Speaker: Jan Čurn
  • Channel: AI Engineer
  • Main topic: Evaluating and improving Model Context Protocol (MCP) usage with agents by combining MCP with CLI approaches (MCPC).
  • Purpose: Explain why agents struggle with MCP, analyze existing solutions, and introduce mcpc as a universal CLI client combining MCP and CLI strengths. Jan Čurn, founder and CEO of Apify, addresses the hate and criticism directed at the Model Context Protocol (MCP) over the past year. He argues that the protocol itself is not flawed; rather, the naive harness implementations used by most AI agents are to blame. Agents frequently load all available MCP tools and their results directly into the context window, causing token bloat, loss of accuracy, and high costs. To solve this, Čurn introduces three solutions: sub-agents, progressive tool discovery, and code mode, and presents 'mcpc', a universal CLI client for MCP developed by Apify that implements progressive tool discovery, asynchronous tasks, JSON output, and x402 payments.

Topic Map

The State of MCP and Backlash

  • Explanation: MCP became immensely popular last year as a standard for agent-to-tool interaction, but quickly faced heavy criticism and complaints from developers claiming MCP is the wrong abstraction or dead in the water.
  • Key claims:
    • MCP became the darling of the AI world with thousands of servers built.
    • A wave of criticism emerged claiming MCP eats too much context and CLIs are better.
  • Examples:
    • Tweets from developers stating 'MCP is a mistake. Long live CLIs' and 'MCPs are mostly useless'.
  • Terminology:
    • Model Context Protocol (MCP)
    • MCP Registry
  • Why it matters: Highlights the industry tension between protocol-based tool access and traditional CLI/API usage.

The Core Problem: Harness Inefficiency

  • Explanation: The primary issue with MCP is not the protocol specification, but how agent harnesses load tools and context.
  • Key claims:
    • Most agents load all MCP tools and their results directly into the context window right away.
    • Uncontrolled context growth leads to reduced accuracy and higher costs.
  • Examples:
    • Loading 10 MCP servers with 10 tools each consumes a massive fraction of the context window before any work is done.
  • Terminology:
    • Harness
    • Context window
    • Token bloat
  • Why it matters: Clarifies that blaming the MCP protocol is misguided; harness architecture needs improvement.

Solutions to Context Bloat

  • Explanation: Three main solutions have emerged to combat context consumption: sub-agents, progressive tool discovery, and code mode.
  • Key claims:
    • Solution 1: Splitting context into sub-agents helps isolate tasks, but still incurs token costs and retains sensitive data in context.
    • Solution 2: Progressive tool discovery (like tool search tool) loads tools only when needed, saving massive amounts of context.
    • Solution 3: Code mode treats tools as code rather than functions, leveraging LLMs' strong code generation and navigation capabilities.
  • Examples:
    • Anthropic and Cursor introducing tool search tool and code mode.
  • Terminology:
    • Sub-agents
    • Progressive tool discovery
    • Code mode
  • Why it matters: Provides architectural patterns for developers building agent harnesses.

Why CLIs Outperform Naive MCP Clients

  • Explanation: CLIs naturally handle context efficiently because agents never load a full CLI and its docs into context at once; instead, they use progressive tool discovery via help commands and execute shell commands.
  • Key claims:
    • Agents never load full CLIs into context; they load them progressively.
    • Models know the Unix shell and CLI patterns deeply from extensive training data.
    • CLIs remain a local black box lacking standard auth and transport protocols.
  • Examples:
    • Using bash help commands or basic Linux shell utilities.
  • Terminology:
    • CLI
    • Shell
    • Sandbox
  • Why it matters: Demonstrates why developers lean towards CLIs and how MCP can adopt CLI advantages.

Introducing MCPC: The Universal CLI Client for MCP

  • Explanation: Apify built 'mcpc' as a universal CLI client for MCP that encapsulates full MCP complexity behind standard bash tool calls.
  • Key claims:
    • mcpc provides full MCP support and compatibility (tasks, resources, prompts, logging).
    • It is lightweight with minimal dependencies and no LLM built-in.
    • It supports code mode with --json flags and agentic payments via x402.
  • Examples:
    • Running npx @apify/mcpc or bun install -g @apify/mcpc, logging in via OAuth, and connecting to filesystem or Apify MCP servers.
  • Terminology:
    • mcpc
    • x402
    • Asynchronous tasks
    • OAuth profiles
  • Why it matters: Bridges the gap between MCP's remote capabilities and CLI's interface simplicity.

Connector Evaluations and Benchmarks

  • Explanation: Apify built a new benchmarking framework called connector-evals to compare raw MCP, mcpc, and native CLIs across various tasks.
  • Key claims:
    • mcpc and CLI performance are very comparable in cost and time benchmarks.
    • Raw MCP sometimes finishes tasks faster but consumes more tokens.
  • Examples:
    • Cross-actor-meta-and-repo-test benchmarks comparing cumulative cost vs time.
  • Terminology:
    • connector-evals

  • Why it matters: Provides empirical data on the trade-offs between different agent tool-calling wrappers.

Key Points

MCP doesn't suck; agent harnesses do

  • Explanation: The protocol specification is robust, but naive client implementations overload the context window with all available tools.
  • Evidence: Analysis of context window consumption showing over 60-95% free space differences when using progressive tool search.
  • Practical implication: Developers must implement progressive tool loading in their agent harnesses rather than dumping all tool schemas into system prompts.

CLIs succeed because of progressive discovery and shell familiarity

  • Explanation: Models are trained extensively on shell commands and explore command-line tools incrementally via help documentation.
  • Evidence: Linux shell history dating back to 1969 optimized characters and documentation for concise human and AI interaction.
  • Practical implication: Agent interfaces should mimic shell behavior and progressive execution.

MCPC bridges remote MCP power with CLI simplicity

  • Explanation: By wrapping MCP servers in a CLI client (mcpc), agents can interact with remote MCP capabilities using a single familiar tool call (bash).
  • Evidence: Live terminal demonstrations showing session persistence, grep search, async task execution, and OAuth login.
  • Practical implication: Agents can use MCP servers without managing complex sessions, authorization, or transport protocols directly.

Frameworks, Models & Processes

mcpc (Model Context Protocol Client)

  • How it works: Acts as a lightweight CLI wrapper over the MCP protocol, exposing commands like connect, session, grep, tools-call, tasks, and resources with full JSON output formatting.
  • Components:
    • Session management
    • Progressive tool discovery (grep)
    • Code mode (--json flag)
    • Agentic payments (x402)
    • MCP proxy for sandboxing
  • When to use: When building AI agents that need secure, standardized remote tool access via simple shell commands.

Connector Evals

  • How it works: A benchmarking framework to evaluate the performance and token costs of different agent connectors (raw MCP, mcpc, CLI).
  • Components:
    • Test scenarios (cross-actor-meta, repo tests)
    • Time tracking
    • Cumulative cost calculation in USD
  • When to use: When comparing the efficiency and cost-effectiveness of various agent tool integration strategies.

[O]Mental Modelmedium noveltystrong evidence

The MCP backlash is misattributed: the protocol spec is not the problem, the harness is. Naive harnesses eagerly load every tool schema and result into the context window before any work happens, so context exhaustion is an architectural defect of the client, not the wire protocol.

Why it matters

Shifts the fix from 'abandon MCP for CLIs' to 'fix tool-loading architecture', which is a much cheaper and more general intervention for anyone maintaining an agent harness or MCP client.

Generalization

When a tooling standard is perceived as bad, check whether the failure is in the protocol or in the eager-loading behavior of its default consumer.

[E]Empirical Resultmedium noveltymoderate evidence

Progressive tool discovery (a tool-search tool that loads tools only on demand) reclaims a large fraction of the context window — the summary cites 60–95% free-space differences versus eager loading.

Why it matters

Quantifies the payoff of on-demand tool schema retrieval, making it a concrete lever for cost and accuracy rather than a vague best practice.

Generalization

Tool schemas and capability docs should be retrieved lazily like a search index, not inlined into the system prompt.

[M]Mechanismhigh noveltymoderate evidence

Code mode reframes tools as code rather than as callable functions, exploiting LLMs' strong code generation and navigation ability instead of relying on structured function-calling schemas.

Why it matters

Changes the abstraction boundary between agent and tool: the model writes/reads code against tools, which can collapse many function-call round-trips into a single code artifact.

Generalization

Where the model is strongest (code), express the tool interface in that medium rather than in a schema format optimized for the host language.

[O]Mental Modelmedium noveltymoderate evidence

CLIs already behave like a progressive-discovery agent interface: agents never load a whole CLI or its docs at once, they explore incrementally via help/search, and models have deep prior training on Unix shell patterns and 1969-era conventions designed for terse input.

Why it matters

Explains the CLI advantage as a structural property (lazy discovery + training prior), not aesthetics, so MCP/agent tooling can deliberately adopt those properties.

Generalization

Interface designs that match a model's pretraining distribution and support incremental discovery will outperform richer but eagerly-loaded alternatives.

Source video ↗
[A]Architecturehigh noveltymoderate evidence

Wrapping MCP servers in a CLI client (mcpc) reduces the agent-facing surface to a single familiar bash tool call, while the client absorbs MCP complexity — sessions, OAuth profiles, resource/prompt/logging support, async tasks — behind standard commands with JSON output.

Why it matters

Moves session management, authorization, and transport handling out of the agent's reasoning context into a deterministic client, which should reduce context cost and tool-call error surface.

Generalization

Put protocol complexity in a thin deterministic adapter and expose one already-known interface (shell) to the model, rather than teaching the model the protocol.

Source video ↗
[~]Tradeoffmedium noveltymoderate evidence

Benchmark evidence from connector-evals shows three wrappers trading off differently: mcpc and native CLI are comparable on cost and time, while raw MCP sometimes finishes faster but at higher token consumption.

Why it matters

Suggests there is no single dominating tool-access strategy — latency-sensitive workloads may prefer raw MCP, cost-sensitive ones the CLI/mcpc path — so wrapper choice should be workload-driven and measured.

Generalization

Token cost and wall-clock latency are separable axes for tool interfaces; optimize and benchmark them independently.

Source video ↗
[!]Failure Modemedium noveltymoderate evidence

Sub-agent decomposition isolates task context but does not eliminate the underlying costs: it still incurs token spend and can retain sensitive data inside context.

Why it matters

Cautions against treating sub-agents as a clean fix for context bloat; they mitigate interference but not token economy or data-exposure risk.

Generalization

Context isolation and context minimization are distinct goals; an isolation strategy is not automatically a minimization or privacy strategy.

Architectural implications

4

Tool schema delivery to the model

Before

All MCP tool schemas are inlined into the system prompt/context at agent start.

After

Tools are discoverable on demand via search/grep and loaded only when relevant.

Consequence

Large context savings (cited 60–95% free-space differences) and fewer distractors, at the cost of an extra discovery step per task.

Source video ↗

Where protocol concerns live

Before

The agent directly manages MCP sessions, transport, and authorization.

After

A thin CLI client (mcpc) owns sessions, OAuth profiles, resources, and transport; the agent only issues bash calls.

Consequence

Smaller agent-facing interface and fewer context tokens spent on protocol mechanics, but adds a dependency between agent and adapter.

Source video ↗

Tool invocation medium

Before

Structured function-call schema per tool invocation.

After

Code mode: the model writes/reads code that uses tools, with JSON output flags.

Consequence

Fewer round-trips and better use of code-generation strength; requires the harness to safely execute generated code.

Source video ↗

Task decomposition boundary

Before

Single agent context accumulates all intermediate state.

After

Sub-agents isolate sub-task context.

Consequence
