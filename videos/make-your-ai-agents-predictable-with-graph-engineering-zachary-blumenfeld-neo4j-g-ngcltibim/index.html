Overview

  • Purpose: To introduce graph engineering concepts, frameworks, and tools that enable predictable, governed, and portable AI agent workflows. Zachary Blumenfeld from Neo4j discusses graph engineering as a new discipline for AI agents, covering execution graphs, context graphs, and procedure graphs. He presents how graph-based memory and distillation improve predictability, governance, and portability of AI agent systems, supported by real-world use cases from customers like Arhasi and Uber.

Introduction to Graph Engineering

  • Explanation: Defining graph engineering as designing agent work as an explicit graph where nodes do work and edges route state between them.
  • Key claims:
    • Graph engineering is an evolution from prompt and context engineering.
    • Mechanisms like state machines and workflow graphs are old, but their application to AI agents is new.
    • Graph engineering can be categorized into execution graphs, context graphs, and procedure graphs.

    • Workflow graphs with routers and agents as nodes within agent harnesses.

Frameworks, Models & Processes

Graph Engineering Framework

  • How it works: Designs agent work as an explicit graph where nodes perform tasks and edges handle state routing, governance, and memory.
  • Components:
    • Execution graph
    • Context graph
    • Procedure graph
  • When to use: When building complex, multi-step, enterprise-grade AI agent workflows requiring auditability.

Agent Instruction Protocol (AIP)

  • How it works: Compiles human-written procedural knowledge into deterministic graph structures that agents execute.
  • Components:
    • Human written skill
    • Draft AIP skill
    • Validate
    • Functional tests
  • When to use: When translating compliance policies or multi-step standard operating procedures into reliable agent routines.

[A]Architecturemedium noveltymoderate evidence

Governance is implemented as graph structure and code constraints on edges/paths rather than as instructions inside prompts, which makes agent judgment auditable and policy enforceable.

Why it matters

Moves safety/compliance from a probabilistic, unauditable surface (the prompt) to a deterministic, inspectable one (the graph), which is the difference between 'we told it not to' and 'it cannot'.

Generalization

Any regulated or high-blast-radius agent should have its policy constraints expressed in the control structure, with the prompt used only for content, not for compliance.

[A]Architecturemedium noveltymoderate evidence

Agent skills/procedures belong in a knowledge layer (graph store) separate from the execution runtime, so the same skill artifacts can be executed by different orchestration frameworks.

Why it matters

Creates a portability boundary: the runtime becomes swappable infrastructure while the durable asset — accumulated procedural knowledge — stays in the graph.

Generalization

Treat agent procedures as data, not code, to decouple the durable asset from the volatile runtime/framework churn.

[O]Mental Modelmedium noveltymoderate evidence

Graph engineering decomposes into three distinct graph roles — execution (routing/state), context (grounding/memory), and procedure (skills) — rather than one undifferentiated 'agent graph'.

Why it matters

Gives separable abstraction boundaries with different lifecycles: execution graphs change per task, context graphs change per data refresh, procedure graphs change per policy revision.

Generalization

Separating control flow, grounding data, and procedural knowledge into distinct artifacts simplifies versioning, testing, and ownership of each.

[M]Mechanismmedium noveltyweak evidence

Why it matters

Makes agent behavior regression-testable at the procedure level instead of only end-to-end, and inserts an explicit validation gate before a skill is trusted in production.

Generalization

Procedural knowledge should be versioned and tested like code, with the compile + validate + functional-test loop as the CI analogue for agent skills.

Deep dives

4

Constraint calibration for graph-routed agents

Research question

How does increasing path constraint in an execution graph affect task success, off-script coverage, and loop incidence?

Why

The core promise of graph engineering is predictability through constrained paths, but the same constraint that prevents runaway loops can make the agent unable to handle cases outside the authored procedure. Teams need a measured tradeoff curve, not a binary choice between free-form agents and rigid workflows.

Source video ↗

Scaffolding decay: procedure graphs versus model scale

Research question

At matched inference cost, does a small model executing a compiled procedure graph retain its advantage over an unscaffolded frontier model as base model capability increases?

Why

If explicit graph scaffolding substitutes for model capability, model selection becomes a joint decision with procedure structure. But if the advantage decays quickly across model generations, teams should treat graph engineering as a temporary bridge rather than a durable architecture.

Source video ↗

Structural governance and auditable execution

Research question

Does encoding policy as graph path constraints and code-level rules reduce policy violations and produce more complete audit trails than prompt-embedded policy under ambiguous or adversarial inputs?

Why

Moving compliance from prompt text to graph structure changes the enforcement surface from probabilistic instruction-following to deterministic path constraint. The engineering consequence is that the execution trace itself can become the compliance record, but only if the constraint model is actually complete.

Source video ↗

Automatic skill graph extraction from unstructured documentation

Research question

Can LLM-extracted AIP graphs from unstructured policy or procedure documents match human-authored graphs on functional-test pass rate and downstream task reward?

Why

The AIP pipeline shown starts from a human-written skill. If extraction can be automated reliably with a validation gate, skill graph creation scales; if not, graph engineering remains bottlenecked on manual authoring and validation effort.

Article ideas

Your Agent Doesn't Need a Bigger Model; It Needs a Better Graph

For stable, documentable procedures, compiling procedural knowledge into an explicit execution graph is a cheaper reliability lever than upgrading the model, but the gain is real only when the graph is validated and functionally tested before production use.

Angle

Frame model selection as a joint decision with procedure structure; show where graph scaffolding substitutes for model scale and where it merely shifts cost into authoring and validation.

Source video ↗

Stop Putting Compliance in the Prompt

Policy enforcement belongs in the control structure, not in prompt text; graph path constraints and code-level rules make agent judgment auditable and turn the execution trace into a structural compliance record.

Angle

Contrast prompt-embedded policy, which is probabilistic and post-hoc auditable, with graph-constrained execution, where forbidden paths are structurally unavailable and audit data is generated as a byproduct of routing.

Source video ↗

Three Graphs, Not One: Separating Execution, Context, and Procedure

Treating execution routing, grounding memory, and procedural skills as one undifferentiated agent graph creates versioning and ownership problems; separating them gives each artifact its own lifecycle, test strategy, and change cadence.

Angle

Use the three graph roles to explain why context refresh, policy revision, and task routing should not be coupled in a single graph artifact.

Constraint Ablation Harness

movement-lab

Increasing graph path constraint improves task success up to a point, after which off-script handling degrades and overall failure rate rises.

Proof of concept

Build a fixed task suite with a graph-routed agent, generate variants with progressively tighter edge constraints, and record task success, off-script recovery rate, and loop incidence for each variant.

Measurement

Plot task success, off-script handling rate, and loop count against constraint tightness; identify the point where success stops improving or begins to fall.

Architectural implications

3

Where agent procedure logic lives

Before

Skills, routing, and policies live inside prompt text and framework-specific orchestration code

After

Procedure and skill logic lives as graph data in a knowledge layer; the runtime loads and executes it

Consequence

Multiple runtimes can execute the same skill; framework migration no longer means rewriting agent logic, but introduces synchronization between graph store and runtime

Source video ↗

Where policy enforcement happens

Before

Compliance rules expressed as prompt instructions with post-hoc log review

After

Policy constraints expressed as constrained graph paths plus code-level rules, producing built-in audit trails

Consequence

Auditability becomes structural rather than forensic; compliance reporting can be generated from the execution record itself

Source video ↗

How reliability is bought

Before

Upgrade to a larger model or add more retries/harness complexity

After

Compile procedure into an explicit graph and let a smaller model execute it stepwise

Consequence

Cost and latency budgets shift from inference tokens to graph authoring/validation effort, changing the team's core skill requirement

Constraint vs autonomy

Benefit

Cost or risk

Extra knowledge-layer system
