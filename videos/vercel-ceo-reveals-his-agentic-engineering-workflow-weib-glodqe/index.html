Overview

  • Speaker: Guillermo Rauch
  • Channel: David Ondrej
  • Main topic: Agentic Engineering Workflow and AI Software Development
  • Purpose: To explore how AI agents are transforming software engineering workflows, infrastructure, security, and developer productivity. Guillermo Rauch discusses the evolution of software engineering in the post-AGI era, highlighting the security debt of human-written code, the shift toward sandboxes, and the importance of human control in creative and cybersecurity risk management. He shares insights on Supabase, Vercel's internal AI tools like Fx and Cloudroom, and the economic tradeoffs of running software agents at scale.

Key Points

The Analogy of Farming vs. Software

  • Explanation: Farming was once done by 90% of the population, but automation reduced it to under 1%. Similarly, filling out forms and writing boilerplate code will be automated by AI agents.
  • Evidence: Percentage of human population in food production over time chart.
  • Practical implication: Engineers will transition from manual coding to managing fleets of AI agents and setting high-level architectures.

Iteration Velocity vs. Iteration Speed

  • Explanation: Iteration speed is how fast you output code, but iteration velocity measures speed combined with correct direction and goal alignment.
  • Evidence: Discussion on token maxing and PR landing rates.
  • Practical implication: Moving fast without proper direction leads to building the wrong product efficiently.

Secure Code by Construction

  • Explanation: Relying solely on unit tests after writing insecure code is insufficient. Infrastructure must be secure by construction.
  • Evidence: Discussion on moving C libraries into memory-safe languages like Rust.
  • Practical implication: Enterprises must adopt secure cloud environments and automated vulnerability scanners like Deepsec.

[A]Architecturehigh noveltymoderate evidence

Rather than relying on post-hoc testing of code that is already insecure, security must be a property of the execution environment: running development cycles inside sandboxed containers whose app kernel is isolated from the host kernel, with the claim that this can eradicate supply chain attacks.

Why it matters

Moves the security boundary from the code artifact (unit tests, reviews, scanners) to the runtime substrate, which changes where an agent harness must execute and what the host must expose to it.

Generalization

Any agentic coding system that executes model-generated code should treat the execution sandbox, not the generated artifact, as the primary trust boundary; 'secure by construction' becomes a property of the runtime, not of the review process.

Research question

Why

Why

If security-scanning skill does not track general coding benchmarks, security workflows need their own model-selection axis; if it does, the scanner is redundant with coding evaluation.

Research question

Why

Generated code is the least trustworthy component in an agent-first stack, so the security floor must be inherited from the platform rather than written by the agent.

Post-hoc unit tests applied to already-insecure generated code cannot remove the vulnerability; assurance has to be an environmental property of the runtime, so agent harness teams should spend on isolation and construction-time guarantees instead of test volume.

Angle

Project ideas

4

Sandbox Escape Range

gatehouse

A per-agent sandbox that isolates the app kernel from the host kernel bounds supply chain attack impact but does not eradicate it; at least one non-kernel vector — credential access through build inputs, package resolution, or persistence across sandbox lifetimes — still escapes.

Proof of concept

Build a red-team range that runs instrumented coding agents in per-agent sandboxes and systematically attempts host-kernel reach, credential exfiltration, and cross-sandbox persistence; record every successful escape and its class.

Measurement

Number and class of successful escapes per attempt type, aggregated across N sandbox lifetimes, plus the specific vectors that remain outside the isolation boundary.

Source video ↗

Direction-Correctness Instrument

beyond-evals

A velocity metric combining landed-change rate with a direction-correctness signal (rework rate, reverted changes, spec-match evaluation) diverges from token throughput and PR landing rates on real repositories, and predicts accepted outcomes better than those throughput proxies.

Proof of concept

Instrument an agentic delivery pipeline to log tokens, landed PRs, revert rate, rework, and a spec-match score per task; compare the composite metric against the throughput-only metrics across delivered changes.

Measurement

Divergence between composite velocity and token/PR metrics, and relative predictive power of each metric for post-hoc accepted changes.

Source video ↗

Vuln-Bench Validity Check

beyond-evals

Model score on a vulnerability-detection benchmark correlates poorly with real-world confirmed-finding yield and precision on a mature codebase, and precision rather than recall dominates developer cost per confirmed finding.

Proof of concept

Run the scanner over a known-vulnerable corpus and a clean corpus, measuring precision, recall, false-positive ratio, and developer minutes per confirmed finding.

Measurement

Precision/recall on both corpora, false-positive ratio per thousand lines scanned, and developer minutes per confirmed finding versus benchmark rank.

Source video ↗

Generation-Proof Auth Floor

gatehouse

Agent-generated applications built against a platform-layer authorization policy maintain access-control invariants at a higher rate than applications whose authorization lives in generated server code, particularly in the wrong-but-compiling case.

Proof of concept

Generate the same application specification N times with platform-layer policy enforcement and N times with authorization in generated server code; run an automated authorization test suite against all artifacts.

Measurement

Authorization violation rate per generated app, share of violations in apps that compile successfully, and variance across generations for each configuration.

Source video ↗

Architectural implications

4

Development execution is relocated from the developer's host machine into per-agent sandboxed containers with the app kernel isolated from the host kernel.

Before

Code runs on a developer or CI host with host-kernel access, and supply chain compromise can reach the host.

After

Each development cycle runs in an isolated sandbox where the app kernel cannot touch the host kernel.

Consequence

Supply chain and prompt-injection blast radius is bounded by the sandbox, but the harness must be redesigned to operate entirely inside that boundary.

Source video ↗

Agent compute, harness, and model are separated into independently selectable layers on an open platform.

Before

Cloud agents are consumed as a closed stack where the vendor controls compute, harness, and model together.

After

Each agent gets its own cloud computer and the developer chooses the model and harness on top of it.

Consequence

Evaluation and cost routing become harness-relative instead of vendor-relative, and switching costs shift from migration projects to configuration.

Source video ↗

Authorization and data protection move into the backend platform layer (Row Level Security) that is directly reachable by the model runtime.

Before

The application server owns credentials and enforces authorization in hand-written server code.

After

The agent builds the backend against a database whose policies enforce access control, reachable from inside ChatGPT/Claude.

Consequence

Agent-generated apps inherit a security floor that does not depend on the quality of generated server code.

Source video ↗

Security assurance shifts from post-write unit tests to construction-time infrastructure guarantees plus automated deep scanning.

Before

Insecure code is written first, then unit tests and reviews are applied as a downstream gate.

After

Secure cloud environments and automated scanners such as Deepsec are part of how the code is produced and verified.

Consequence

Verification tooling becomes part of the agent harness rather than a separate CI stage.

Tradeoffs and failure modes

5

Iteration speed versus direction

Benefit

High token throughput and PR landing rates maximize apparent progress and agent utilization.

Cost or risk

Without goal alignment the pipeline efficiently produces the wrong product, with no metric that reveals it.

Source video ↗

Expanded attack surface from AI systems

Benefit

Agents write and ship large volumes of code and operate across many systems, increasing capability and throughput.

Cost or risk

The surface of attack expands with new vectors such as prompt injections and training attacks, plus latent vulnerabilities in existing human-written code.

Source video ↗

Automation versus human control

Benefit

Fleets of agents and software factories automate implementation and can operate largely autonomously.

Cost or risk

Creative control and risk management remain human domains, making human oversight the bottleneck even as execution scales.

Source video ↗

Open agent platforms and paid inference

Benefit

Developers can run their favorite models and harnesses on per-agent cloud computers.

Cost or risk

Users pay for inference directly, so cost control and model selection become the operator's responsibility rather than the platform's.

Source video ↗

Test-based assurance for generated code

Benefit

Unit tests are cheap to generate and give fast feedback on behavior.

Cost or risk

Tests written after insecure code do not remove the vulnerability; assurance must come from the environment and construction rather than the test suite alone.
