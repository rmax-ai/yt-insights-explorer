Overview

  • Speaker: Mike Chambers
  • Channel: AI Engineer
  • Main topic: Harness engineering and building production-ready AI agents on AWS
  • Purpose: To educate AI engineers on harness engineering, explaining the difference between using agents and building production agents at scale using AWS infrastructure, Strands Agents SDK, and AgentCore. Mike Chambers, Senior AI Specialist Developer Advocate at AWS, discusses harness engineering—the code, configuration, and execution logic that surrounds an AI model to make it production-ready. He contrasts agents we use (like coding assistants) with agents we build, introduces the Agentic AI Foundation, and demonstrates building and deploying agents using Strands Agents SDK and AgentCore.

Key Points

Agent = Model + Harness

  • Explanation: The core formula defining an AI agent, where the model provides intelligence and the harness provides execution logic, tools, memory, and guardrails.
  • Evidence: Referenced articles by Birgitta Böckeler and Martin Fowler.

No more slop ops

  • Explanation: Moving away from ad-hoc manual console clicking (clickops) toward infrastructure-as-code managed by agents.
  • Evidence: Chambers' advocacy for infrastructure-as-code agent deployments.
  • Practical implication: Production agents must build and manage their own cloud infrastructure safely.

Observability and evaluations first

  • Explanation: Tracking traces, logging, and evaluation metrics should be foundational elements in agent harness design.
  • Evidence: Placement of observability and evaluations at the top of the AgentCore architecture diagram.
  • Practical implication: Without robust observability, debugging complex multi-turn agent loops at scale is impossible.

[O]Mental Modelmedium noveltystrong evidence

An agent decomposes cleanly into model plus harness, where the harness is defined by subtraction: everything in the system that is not the model (code, configuration, execution logic, tools, memory, guardrails). This makes 'harness engineering' the primary lever for production readiness rather than model capability.

Why it matters

Gives engineers a partitioning rule for where to invest: if a production problem is not a model-weight problem, it is a harness problem, and most enterprise work belongs on the harness side.

Generalization

For any LLM-backed system, define the boundary by subtraction — the non-model remainder is the maintainable, testable engineering surface.

Design patterns from single-tenant interactive tools do not transfer to multi-user production services; the cost, isolation, and concurrency models are inverted.

Project ideas

4

Minimum Viable Agent Trace Schema (MVATS)

beyond-evals

A minimal multi-turn trace and eval schema (span types, tool-call outcomes, state transitions, cost attribution) enables root-causing injected failures in agent loops, whereas logs alone produce significantly longer time-to-diagnosis or failure to diagnose.

Proof of concept

Instrument a multi-turn agent (e.g., using Strands/AgentCore) with the proposed schema; inject a controlled set of failures (tool timeout, context loss, hallucinated tool call, wrong tool selection); compare root-cause time and success rate against a logs-only baseline.

Measurement

Time-to-diagnosis (median and 90th percentile), percentage of injected failures successfully root-caused, and number of additional diagnostic queries required per incident.

Source video ↗

Agent IaC Plan Gate

gatehouse

Agent-generated infrastructure-as-code plans can be safely bounded by policy-as-code plus plan-diff approval gates, reducing blast radius from malformed or adversarial plans without eliminating legitimate provisioning.

Proof of concept

Build an agent that generates infrastructure-as-code plans; enforce policy checks (deny public buckets, wildcard IAM, destructive replacement) and require human approval on plan diffs; run adversarial and benign plans through the pipeline.

Measurement

Number of unsafe plans blocked, false-positive rate on benign plans, reduction in simulated blast radius (resources affected), and added approval latency per plan.

Source video ↗

Identity-Bound Wallet Scoping

gatehouse

Scoping an agent's identity to a spend-limited wallet with per-transaction and aggregate limits, enforced at runtime, prevents runaway spend while allowing legitimate microtransactions, and does so with acceptable false-positive rates.

Proof of concept

Implement an agent with a scoped wallet, policy engine (limits, merchant allowlist, velocity checks), and audit log; simulate a mix of legitimate purchases and adversarial attempts (limit evasion, replay, spoofed identity).

Measurement

Prevented unauthorized spend (absolute and percentage), false-positive rate for legitimate transactions, audit completeness (every transaction traceable to identity and policy decision), and policy decision latency.

Source video ↗

Cross-Tenant Leakage Test Suite for Scaffolded Agents

gatehouse

Multi-tenant isolation provided by CLI scaffolding (e.g., AgentCore) is enforced at a specific boundary (process, container, memory store, API) and can be verified by adversarial cross-tenant probes; leakage is possible when isolation relies on application code rather than runtime enforcement.

Proof of concept

Deploy two tenants using the same scaffolded agent framework with shared infrastructure (e.g., common memory store, vector DB, tool registry); attempt to read or mutate other tenant's memory, secrets, or tool outputs via prompt injection, API parameter tampering, and direct store access.

Measurement

Number of successful cross-tenant accesses (leakage incidents), isolation boundary failure rate, and time-to-detect leakage across probe types.

Architectural implications

4

Observability and evaluations are positioned at the top of the AgentCore architecture rather than as a peripheral tooling layer.

Before

Traces, logging, and evals added after launch in response to incidents.

After

Instrumentation and eval metrics designed as a first-class harness component before the agent loop ships.

Consequence

Debugging and cost attribution for multi-turn loops become tractable, but harness scope expands and eval coverage becomes a launch-blocking dependency.

Source video ↗

Deployment moves from human clickops to infrastructure-as-code generated and managed by agents.

Before

Humans provision cloud resources through consoles; agents only invoke APIs at runtime.

After

Agents own provisioning via IaC, with policy and identity bounding what they can create.

Consequence

Authorization and plan-review mechanisms become the critical safety surface; the object under review shifts from runtime calls to generated infrastructure plans.

Source video ↗

Payments and identity are modeled as harness components rather than application-level concerns.

Before

Billing and auth treated as external plumbing outside the agent's own architecture.

After

Settlement and authentication live beside memory, runtime, and tools in the harness.

Consequence

Agents can autonomously transact, but require policy enforcement and identity scoping inside the runtime to bound spend and abuse.

Source video ↗

Multi-tenant isolation and secure memory are handled by CLI scaffolding rather than application code.

Before

Prototype agents with a single user, local state, and no isolation boundary.

After

Framework-provided per-tenant isolation and secure memory on deployment.

Consequence

The framework/CLI layer becomes the enforcement point for tenant boundaries, so framework version and config correctness carry security weight.

Tradeoffs and failure modes

5

Observability-first harness design

Benefit

Multi-turn agent loops at scale become debuggable and evaluable via traces and metrics.

Cost or risk

Upfront instrumentation and eval-suite investment before any agent behavior ships; observability becomes a gate on iteration speed.

Agent-managed infrastructure provisioners

Benefit

Cost or risk

Local prototype-to-production continuity

Benefit

Cost or risk

Consumer-agent design assumptions in production

Cost or risk
