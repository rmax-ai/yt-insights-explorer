Summary

Overview

  • Speaker: Vasant Kearney
  • Channel: AI Engineer
  • Main topic: Using X12 healthcare transaction standards as a deterministic harness and execution layer for AI agents in healthcare claims and insurance workflows.
  • Purpose: To educate AI engineers on how to build reliable, cost-effective, and safe agentic workflows in healthcare by grounding LLMs in standardized transaction protocols like X12. Vasant Kearney, co-founder and CEO of Onlay AI, discusses the challenges and architecture of building agentic AI systems in healthcare insurance workflows. He argues that while large language models (LLMs) bring flexibility and general reasoning, healthcare requires strict determinism, guardrails, and cost management. By treating X12 electronic data interchange standards as the agent's bytecode and harness, developers can constrain agent capabilities into bounded tasks, handle multi-step payer journeys reliably, and avoid unmanageable system complexity.

Key Points

LLMs reason about ambiguity, but healthcare needs determinism

  • Explanation: LLMs are probabilistic and flexible, but healthcare transactions require strict rule-based grounding to prevent costly errors.
  • Evidence: X12 transaction standards give agents deterministic targets.
  • Practical implication: Do not rely solely on raw LLMs for financial transactions; wrap them in structured harnesses.

The ledger is the durable object

  • Explanation: Long-running agent workflows need persistent state recording at every action rather than relying solely on the LLM's active context window.
  • Evidence: 50-step jobs accumulate context bloat and error propagation.
  • Practical implication: Implement explicit check-pointing, replay mechanisms, and memory ledgers.

Treat every source as evidence, not gospel

  • Explanation: Payers, portals, and X12 documents can contain conflicting or incorrect information.
  • Evidence: An eligibility check returning active status can still result in a claim denial.
  • Practical implication: Build validation layers that aggregate multiple signals before reaching a final verdict.

Long-Running Agent Memory Ledger

  • How it works: Tracks state across multi-step workflows to ensure auditability and error recovery.
  • Components:
    • Checkpoint (persist state after actions)
    • Replay (reconstruct agent execution history)
    • Idempotency (prevent duplicate execution)
    • Summaries (feed relevant history forward)
  • When to use: For complex, multi-step agent tasks spanning hours or days.

[A]Architecturehigh noveltymoderate evidence

Use a pre-existing, externally-specified interchange standard (X12) as the agent's compilation target: rather than letting the LLM emit free-form actions, its output is constrained to a schema whose validity is machine-checkable, making the standard function as 'bytecode' for the agent.

Why it matters

It relocates the reliability boundary from prompt engineering to a formal contract: correctness becomes a parser/validator problem instead of a probabilistic-judgment problem, which is what makes financial and clinical actions auditable and regression-testable.

Generalization

Any regulated domain with a mature interchange format (SWIFT/ISO 20022, EDI, FHIR, tax filings, telecom provisioning) can be used as the agent's typed target language, giving determinism without hand-building a bespoke DSL.

[M]Mechanismmedium noveltymoderate evidence

Long-horizon jobs (≈50 steps) should be modeled as durable state machines whose authoritative state lives in a memory ledger external to the context window, with checkpoint, replay, idempotency, and summaries as four distinct primitives rather than one 'memory' feature.

Why it matters

It separates three different problems usually conflated under 'memory': crash recovery (checkpoint), debugging/audit (replay), duplicate-side-effect prevention (idempotency), and context budgeting (summaries). Each has a different failure mode and needs its own implementation.

Generalization

Applies to any agent taking real-world side effects across hours or days — procurement, DevOps remediation, travel booking, billing — where re-running a step must not re-charge or re-submit.

[!]Failure Modehigh noveltymoderate evidence

Schema-valid data is not ground truth: structurally correct envelopes routinely carry semantically wrong content, so the agent must treat every source (payer portal, phone tree, 271 eligibility file, 835 EOB) as one piece of evidence and reach verdicts only by aggregating and cross-checking multiple signals.

Why it matters

Most integration stacks validate at the transport/schema layer and stop there; an agent that reports 'eligibility active' from a valid 271 and then acts on it can cause denials and downstream rework. This is a correctness bug invisible to schema-level monitoring.

Generalization

Generalizes to any agent reading authoritative-looking APIs or documents (CRM records, logs, KYC files): validation must include semantic reconciliation across independent sources, not just parse success.

Your Agent's Output Schema Is Not a Correctness Guarantee

Schema validation is a transport-tier property that says nothing about whether the content is true; any agent acting on a single authoritative-looking response needs a second semantic tier that reconciles independent sources before it moves money or touches care.

Angle

Walk through the failure class — bad data inside good envelopes — and show why schema-level monitoring is structurally blind to it, then specify the reconciliation tier as an engineering artifact rather than a prompt instruction.

Source video ↗

Pick a Standard You Didn't Invent: Bytecode as the Agent Reliability Boundary

Reliability gains come from constraining agent output to an externally-specified interchange grammar rather than from better prompting, because it converts correctness into a parser-and-validator problem with unit-testable surfaces.

Angle

Reframe the design question from 'how do we get the model to behave' to 'what is the compilation target', using the X12-as-bytecode framing and generalizing to other mature interchange standards.

Source video ↗

Memory Is Four Features, Not One

Checkpoint, replay, idempotency, and summarization solve four different problems with four different failure modes — crash recovery, audit/debug, duplicate side effects, and context budgeting — and collapsing them into a single 'memory' feature means at least two of them are missing in production.

Angle

Take the six-slot harness checklist and drill into the memory slot, arguing that each primitive needs its own implementation and its own test.

Source video ↗

Human Handoff Is a Runtime Node, Not an Error Path

Treating escalation as an exception handler hides the most important policy artifact in the system; declaring handoffs as gates with states, SLAs, and ledger records makes human-in-the-loop measurable and forces explicit definition of which actions require approval.

Angle

Contrast the bolted-on escalation pattern with handoffs expressed as permissions and gates, and show what becomes observable once the ledger records which gate was crossed.

Step-Curve Ablation Bench

beyond-evals

Adding summary-only context control recovers less than half of the reliability gain obtained from full checkpoint+replay+idempotency, and the gap widens monotonically with step count beyond roughly 25 steps.

Proof of concept

A synthetic multi-step claim-journey generator (submit, check eligibility, resubmit, correct, follow up) with injectable tool failures and schema-valid-but-wrong responses; run each journey under five harness configurations (baseline, +summaries, +checkpoint, +replay, +idempotency, all) at 10/25/50/100 steps.

Measurement

Task success rate and cost-per-success as a function of step count per configuration; marginal contribution of each primitive to flattening the curve.

Evidence Arbitration Gate

gatehouse

An explicit precedence-plus-confidence arbitration layer routed to a declared human gate reduces false-accept decisions (acting on a wrong-but-valid signal) by a measurable margin versus majority voting or single-source acceptance, with an escalation-rate increase bounded to a set threshold.

Proof of concept

A reconciliation component that ingests N labeled evidence items per decision, applies ordered precedence rules and a calibrated confidence score, and emits accept / reject / escalate; wire escalation to a ledger-recorded gate event.

Measurement

False-accept rate, false-reject rate, escalation rate, and cost per correctly resolved decision versus single-source and majority-vote baselines on a held-out labeled evidence set.

Adapter Swap Coverage Matrix

movement-lab

With the deterministic core and validators frozen, per-channel task success is explained primarily by adapter coverage rather than by model capability, and handoff rate on off-standard channels remains above the conformant-channel rate regardless of model upgrades.

Proof of concept

One fixed X12-constrained core plus three pluggable adapters (conformant API, portal-scraping, phone-tree/IVR) over the same task set; upgrade the underlying model in a second run to test whether the gap persists.

Measurement

Per-channel success rate, handoff rate, and steps-to-completion, reported as a matrix of adapter × model tier.

Validator Break-Even Profiler

new

Deterministic validator passes cost less per avoided-rework event than LLM self-assessment once average journey length exceeds a measurable step threshold; below it, self-assessment is cheaper.

Measurement

Architectural implications

4

Authoritative task state moves out of the prompt and into an external ledger.

Before

Agent state is implicit in the accumulated conversation/context window; recovery means restarting or re-prompting.

After

State is an append-only ledger of checkpoints that the runtime can replay and diff, with summaries generated from it for context injection.

Consequence

Enables deterministic debugging and audit, but requires idempotent tool implementations and a summarization policy that does not silently drop load-bearing facts.

Source video ↗

Validation relocates from the LLM's self-assessment to an external deterministic validator over the contract.

Before

The model is asked to check its own output for correctness before acting.

After

Output is parsed and validated against the X12 structure and payer rules by a non-LLM component; failures block execution or trigger handoff.

Consequence

Turns correctness into a unit-testable surface and removes a whole class of silent model errors, at the cost of maintaining validators per transaction type and payer.

Source video ↗

Human review becomes a runtime node rather than an error handler.

Before

Escalation to a human is an exception path bolted on after an agent fails or gets stuck.

After

Handoffs are declared in the harness as permissions/gates with defined states and SLAs, and the ledger records which gate was crossed.

Consequence

Makes human-in-the-loop measurable and schedulable, and forces explicit definition of which actions require approval — a policy artifact rather than prompt text.

Source video ↗

A channel adapter layer is required between messy payer interfaces and the deterministic contract.

Before

The agent is assumed to talk to conformant X12 endpoints.

After

Portals, phone trees, and missing/incorrect response files are mediated by adapters that normalize into the canonical transaction shape.

Consequence

Prevents source-specific quirks from contaminating core agent logic, and lets targets be tested against synthetic conformant data.

Tradeoffs and failure modes

4

Constraining LLM output to a rigid standard

Benefit

Machine-checkable outputs, bounded blast radius, reproducible and auditable transactions.

Cost or risk

Reduced flexibility and higher upfront modeling cost; anything outside the standard grammar must be forced through adapters or human handoff, and the constraint may not cover non-standard payer behaviors.

Source video ↗

Aggregating multiple signals before verdict

Benefit

Avoids acting on a single authoritative-looking but wrong data point.

Cost or risk

Higher latency and more tool calls per decision; introduces a new problem — how to arbitrate when signals conflict — that the summary does not resolve.

Source video ↗

Summarization for context control in long jobs

Benefit

Keeps the active context within budget across dozens of steps.

Cost or risk

Summaries are lossy; a dropped detail can silently change a later decision, and the loss is invisible unless the ledger is replayed against it.

Source video ↗

Idempotent replay of agent actions

Benefit

Safe retries and reconstructable execution history.

Cost or risk

Requires every side-effecting tool (claims submission, calls, portal actions) to support deduplication keys, which is often not under the developer's control.
