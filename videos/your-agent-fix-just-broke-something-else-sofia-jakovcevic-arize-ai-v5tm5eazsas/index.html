Overview

  • Speaker: Sofia Jakovcevic
  • Channel: AI Engineer
  • Main topic: Agent observability and regression testing loops
  • Purpose: To explain the methodology and tooling required for building robust regression loops in AI agent development using production traces and LLM-as-a-judge evaluators. Sofia Jakovcevic, forward deployed engineer at Arize AI, discusses how to turn agent observability into a regression loop that tests every agent change before it ships in production. She covers why agent regressions are different from traditional software bugs (failing at runtime rather than compile time), how to build a 5-step regression loop using datasets, evaluators, baselines, and CI/CD integration, and how moving from human triage to agentic evaluation closes the loop at agent speed.

Why Agent Regressions Are Different

  • Explanation: Contrasting traditional software bugs with agent regressions, highlighting why code diffs alone are insufficient for agents.
  • Key claims:
    • Code changes are local, but behavioral effects are non-local.
    • In traditional software, every path is written down and exact paths are known before runtime.
    • In AI agents, logic only exists at runtime, making traces the new source of truth.
    • The diff tells you what changed, but the trace tells you what it actually did.
  • Examples:
    • A one-line prompt change in system_prompt.md appears simple during code review, but at runtime it fundamentally alters the agent's trajectory, tool calling, and sub-agent interactions.
  • Terminology:

Building the Regression Loop: 5-Step Process

  • Explanation: Detailed breakdown of the 5-step process to build a regression loop: selecting a dataset, adding evaluators, running the baseline experiment, making changes and rerunning, and putting the experiment in CI/CD.
  • Key claims:
    • Step 1: Select a dataset pulled from production traces, including representative workflows, known failures, edge cases, and successful workflows to protect.
    • Step 2: Add evaluators to turn subjective metrics into numeric scores using LLM-as-a-judge or code-based/ML-based evaluators.
    • Step 3: Run baseline experiments by running the agent against the dataset with no changes.
    • Step 4: Make one change (prompt, tool, policy, model) and rerun the experiment against the same dataset.
    • Step 5: Put the experiment in CI/CD so every pull request runs through the evaluation gates automatically before merging.
  • Examples:
    • Using LLM-as-a-judge to evaluate task completion on a scale with labels like complete or incomplete.
    • Setting GitHub Actions YAML to run regression python scripts on every pull request.
  • Terminology:

    • Baseline experiment
    • CI/CD gate

Key Points

Code changes are local, but behavioral effects are systemic

  • Explanation: A minor one-line edit to a prompt can drastically alter downstream tool calls, planning, and execution paths in non-deterministic ways.
  • Evidence: A single line change in system_prompt.md caused unintended degradation in task completion rates despite improving action safety.
  • Practical implication: Never ship prompt or policy changes based solely on intuition or code diffs; always validate against a production test dataset.

Traces are the new source of truth

  • Explanation: Unlike traditional software where logic is explicitly written in source code, agent behavior only materializes at runtime through stochastic LLM interactions.
  • Evidence: Thousands of possible trajectories exist only in runtime traces, not in static code files.
  • Practical implication: Build test suites directly from production traces rather than synthetic test data alone.

Every failure should become a test

  • Explanation: When an agent fails in production or during evaluation, that exact trace and failure case must be ingested back into the regression test suite.
  • Evidence: Failed production runs become new regression test cases, preventing the same bug from recurring.
  • Practical implication: Establish an automated pipeline from production observability failures to regression test datasets.

Frameworks, Models & Processes

The 5-Step Agent Regression Loop

  • How it works: A continuous engineering workflow to test agent changes against production data before deployment.
  • Components:
    • Observe: Trace every agent run in production
    • Evaluate: Score live traces with standardized evaluators
    • Change: Edit prompt, model, tool, skill, or policy
    • Test: Run regression experiments in CI/CD against evaluation gates
    • Improve: Ship what passes and feed new failures back into test datasets
  • When to use: Whenever making modifications to LLM prompts, agent policies, tool definitions, or underlying models in production applications.

Examples & Case Studies

A security engineer added a one-line policy requiring the support agent to confirm before taking any action.

  • Illustrates: Unintended side effects of localized prompt changes on multi-step workflows.
  • Lesson: Action safety improved by 17% (+0.17), but task completion dropped by 17% (-0.17), resulting in a net-zero overall average improvement.

Actionable Takeaways

  • Immediate:
    • Pull real production traces including normal workflows, known failures, edge cases, and successful workflows into evaluation datasets.
    • Combine code-based evaluators for deterministic checks with LLM-as-a-judge evaluators for semantic metrics.
    • Integrate agent evaluation suites into GitHub Actions or CI/CD pipelines as merge gates.
  • Strategic:
    • Treat production traces as the authoritative source of truth for agent behavior.
    • Shift from human manual triage to automated agent-driven self-correction and testing.
    • Ensure every production failure automatically updates and strengthens the regression test suite.
  • Questions to investigate:
    • How can agents autonomously propose and test prompt or policy fixes based on trace failures?
    • What is the optimal balance between LLM-as-a-judge evaluation cost and accuracy in CI pipelines?

[E]Empirical Resulthigh noveltystrong evidence

Agent changes produce metric tradeoffs, not uniform improvements: adding confirmation steps before actions raised action safety 0.81→0.98 while dropping task completion 0.89→0.72 because sessions were abandoned mid-flow. Any single-metric gate is therefore unsafe — regression suites must gate on a vector of behavioral metrics, including a 'successful workflows to protect' set.

Why it matters

It quantifies the failure mode that motivates the whole talk: a locally correct, safety-improving change silently degrades the primary user outcome. Engineers who track one headline metric will ship this regression.

Generalization

In agentic systems, safety/guardrail interventions have an intrinsic cost in task completion. Treat safety and completion as a coupled tradeoff surface that must be measured jointly per change, not optimized sequentially.

Any stochastic system needs a control run against an unchanged configuration before an intervention can be attributed; and a test set must contain protected exemplars of current success, not only known failures.

Deep dives

Statistical power of trace-derived regression gates

Research question

How large and how stratified must a trace-derived dataset be before a CI gate's pass/fail decision reliably distinguishes a real agent regression from run-to-run noise on an unchanged agent?

Why

The five-stage loop prescribes a baseline run and a gate, but without variance characterization the gate either blocks on noise or passes regressions. This determines the minimum viable dataset size, the per-slice coverage required, and the delta threshold a change must exceed — the three numbers every team implementing this loop needs and none of the sources give.

Metric-vector gating and the safety/completion tradeoff surface

Research question

Can safety interventions and task completion be modeled as a coupled tradeoff surface that lets a regression gate flag any change improving one dimension while degrading another, and how stable is that surface across model versions?

Why

The concrete 0.81→0.98 / 0.89→0.72 inversion is the talk's load-bearing evidence that single-metric gates ship regressions. Turning that anecdote into a gating primitive — a protected-success slice plus cross-metric delta rules — is what converts the story into enforceable policy.

LLM-as-a-judge reliability as merge-gate infrastructure

Research question

What is the false-pass and false-fail rate of an LLM-as-a-judge evaluator used as a merge gate, and how much does judge agreement with human labels drift across judge model versions?

Why

Once an evaluator blocks merges it becomes a dependency with correctness requirements, not a scoring convenience. Judge drift is an unquantified risk injected directly into the release path, and the source treats evaluators as given rather than as a calibrated instrument.

The Diff Tells You What Changed; The Trace Tells You What It Did

For model-mediated systems, code review certifies nothing about behavior and should be demoted to a syntax check; the reviewable artifact must become the trace diff — trajectory, tool-call sequence, and sub-agent interaction deltas — generated per pull request.

Angle

Argue that the one-line system_prompt.md edit is the canonical false-negative of static review, and that teams should invest in trace-diff tooling before they invest in more prompt review discipline.

Source video ↗

Your Safety Fix Is a Completion Regression

Guardrail interventions have an intrinsic and measurable cost in task completion, so safety and completion must be gated jointly as a tradeoff vector; any release process that optimizes them sequentially will silently ship user-facing regressions that look like wins on the dashboard.

Angle

Use the 0.81→0.98 safety gain against the 0.89→0.72 completion collapse as a worked case, then generalize to a gating rule: no change merges unless it holds the protected-success slice and reports all metric deltas together.

Source video ↗

The Ratchet: Turning Production Failures into Permanent Test Coverage

Test suites built from imagined cases decay with team velocity, while suites built from observed failures compound; the pipeline from failed trace to versioned test case must be automated because manual promotion of incidents into tests does not survive shipping pressure.

Angle

Frame coverage as a function of real incident volume rather than authoring effort, and describe the data-plane coupling required between observability and test infrastructure for the ratchet to actually turn.

The Dashboard Is the Bottleneck

Observability interfaces designed for human visual scanning become the throughput ceiling once agents are the loop's rate limiter; instrumentation must be redesigned as structured, queryable context that an agent can act on directly.

Angle

Project ideas

4

Variance-Calibrated Merge Gate

gatehouse

Running an unchanged baseline N times on a trace-derived dataset yields a run-to-run noise envelope wide enough that a fixed absolute threshold gate produces measurable false blocks, and calibrating the gate threshold to that envelope reduces false blocks without increasing missed regressions.

Proof of concept

Take a small support-style agent with a trace-derived dataset split into representative workflows, known failures, edge cases, and a protected-success slice. Run the unchanged agent 20 times to estimate per-metric variance, then inject a set of known synthetic regressions (prompt edits, tool removal, policy change) and measure gate decisions at both a fixed threshold and a variance-derived threshold.

Measurement

False-block rate on no-change runs and missed-regression rate on injected regressions, at fixed vs variance-calibrated thresholds; also the minimum dataset size at which the miss rate falls below a stated bound.

Source video ↗

Judge Drift Sentinel

beyond-evals

An LLM-as-a-judge evaluator used as a merge gate loses agreement with a human-labeled holdout when the judge model version changes, and that disagreement is large enough to flip gate decisions on a nontrivial fraction of a trace-derived dataset.

Proof of concept

Hold out a human-labeled subset of task-completion judgments from production traces. Score it with three judge model versions, recompute agreement per version, and replay a set of real change experiments through each judge to see whether the gate verdict changes.

Measurement

Per-version judge–human agreement, count and rate of flipped pass/fail verdicts across judge versions on the same experiment results, and detection latency of the drift alarm.

Source video ↗

Agent-Triage Benchmark

new

A coding agent given structured trace access to failing runs detects and correctly patches agent regressions at lower latency and lower recurrence rate than human triage on the same incident queue.

Proof of concept

Build a fixed queue of failing traces from a controlled agent, expose them through a structured query interface (not a dashboard), and run two arms: a coding agent that reads traces and proposes patches, and a human engineer doing the same. Apply both patch sets and rerun the regression suite.

Measurement

Time-to-diagnosis, patch correctness against a held-out acceptance suite, and recurrence rate on the next regression run; plus the ratio of agent-proposed patches that pass the gate unmodified.

Source video ↗

Failure-to-Test Ratchet Pipeline

movement-lab

Automating promotion of failed production traces into versioned test cases increases regression-suite coverage of real failure distribution faster than manual test authoring, and the resulting suite catches a materially higher share of seeded regressions at equal suite size.

Proof of concept

Instrument a small deployed agent, capture failing traces, and auto-promote each into a dataset entry with an attached evaluator expectation. Run the ratchet for a fixed period alongside a manually authored suite of matched size, then seed known regressions into both.

Measurement

Seeded-regression detection rate of ratchet-built vs hand-built suites at equal case count, plus case-promotion latency from incident to test and the stale-case fraction over time.

Architectural implications

3

Evaluation moves from an ad-hoc notebook activity to a merge-blocking gate in the pull request pipeline.

Before

Prompt, tool, and policy changes are validated by code review and informal manual spot checks.

After

Every pull request automatically runs a regression experiment script (e.g., via GitHub Actions) against a production-derived dataset and blocks on evaluator thresholds.

Consequence

The observability/eval backend becomes a hard build-time dependency with its own availability, latency, and versioning requirements inside CI.

Source video ↗

The tracing system is promoted from a debugging tool to the source of truth and the feedstock for the test corpus.

Before

Traces exist for post-hoc human investigation of incidents.

After

Traces are parsed into datasets, converted into permanent test cases, and replayed as the behavioral specification of the agent.

Consequence

Trace schema, retention, and sampling policy become load-bearing product decisions, since dataset quality is bounded by trace fidelity.

Source video ↗

Observability surfaces are exposed as an agent-consumable interface rather than a human dashboard.

Before

An engineer reads dashboards and files fixes.

After

Coding agents connect to the observability backend (agent playgrounds, remote agent connections, agent skills) and read traces to self-correct.

Consequence

Tool APIs must return structured, compact, actionable context; dashboards optimized for human visual scanning do not satisfy this contract.

Tradeoffs and failure modes

4

Safety guardrails vs task completion

Benefit

Confirmation steps before actions meaningfully improve action safety (0.81 to 0.98).

Cost or risk

The same change degrades task completion (0.89 to 0.72) because users abandon incomplete sessions — a regression invisible to a single-metric safety gate.

Static code review for model-mediated behavior

Benefit

Code review is cheap, fast, and catches syntactic and structural defects.

Cost or risk

A one-line prompt edit reveals nothing about trajectory, tool-call, or sub-agent changes at review time; behavioral failures are silent until runtime.

Human-in-the-loop triage vs throughput

Cost or risk
