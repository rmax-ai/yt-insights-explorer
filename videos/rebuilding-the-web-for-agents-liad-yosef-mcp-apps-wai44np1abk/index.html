  • Purpose: To explain the architectural shift toward the Agentic Web, introduce MCP Apps as the standard for rich UI inside chats, and present frameworks for evaluating agent readiness of websites. Liad Yosef discusses the emergence of the Agentic Web and how Model Context Protocol (MCP) Apps and agent-ready standards are bridging the last mile of human-agent interaction, arguing that websites and traditional browsers will become obsolete in favor of personal AI assistants.

Key Points

MCP Apps Solved the Last Mile

  • Explanation: MCP Apps allow servers to send rich UI components directly into conversational interfaces, preserving brand identity and user trust.
  • Evidence: Integration examples with Booking.com, AllTrails, and Spotify inside chat agents.
  • Practical implication: Developers should build MCP-compatible interfaces rather than relying solely on raw text outputs.

Websites are Going Headless

  • Explanation: As agents take over interactions, human-centric visual interfaces on websites become secondary to robust APIs and agent-readable protocols.
  • Evidence: Major platforms like Salesforce, Cloudflare, and Sentry shifting toward headless/API-first architectures.
  • Practical implication: Product teams must prioritize API-first design and agent readiness scorecards.

Discovery Layer for the Agentic Web

  • Explanation: Just as web had search engines and mobile had app stores, the agentic web requires standardized discovery layers like ai-catalog.json and ARD.
  • Evidence: Ora.directory benchmarking thousands of domains for agent compatibility.
  • Practical implication: Websites must implement open standards like .well-known/ai-catalog.json to remain discoverable by AI agents.

[A]Architecturehigh noveltymoderate evidence

MCP Apps resolve the 'last mile' by splitting responsibility: the agent performs the headless task via APIs, then the server pushes a self-contained rich UI chunk back into the chat for the human to complete the interaction. The server, not the client, owns the human-facing surface.

Why it matters

It defines a concrete boundary for where human-facing UI lives in an agentic system: the tool/server vendor renders and controls the interface, while the agent harness only hosts and displays it. This changes who owns rendering, branding, and interaction state, and removes the need for the human to leave the chat.

Generalization

Any tool exposed to an agent can carry its own presentation layer as a payload rather than relying on the harness to compose UI — the analog of server-driven UI inside a conversational runtime.

[O]Mental Modelmedium noveltymoderate evidence

The 'nearly headless' model introduces two distinct consumers of the same service that must be designed for separately: Agent Experience (AX) — machine traversal, auth, and API integration — and User Agent Experience (UAX) — the last-mile human interaction rendered inside the chat.

Deep dives

4

Harness-relative agent readiness: decomposing site-side vs harness-side variance

Research question

How much of a domain's measured 'agent readiness' score is attributable to site-side substrate (stable schemas, docs structure, auth flows) versus harness-side traversal and tool-use policy, and does any substrate dominate across harnesses?

Why

If a meaningful fraction of readiness variance is harness-side, then single-harness scores are non-transferable and readiness must be reported as a matrix (site x harness) rather than a scalar. That changes what an evaluation product even is: a benchmark suite with the harness as an explicit independent variable, analogous to cross-browser testing, rather than a checklist audit.

Source video ↗

Trust and isolation model for server-supplied UI chunks rendered inside a third-party chat host

Research question

What threat model applies when a tool server injects self-contained UI into a host chat surface, and can the host enforce isolation, permission scoping, and unambiguous user consent without breaking the server's brand and interaction ownership?

Why

MCP Apps moves the human-facing surface into the server's payload, which creates a new attack surface inside the host: data exfiltration through rendered components, spoofing of host chrome to manufacture false consent, and ambiguous delegation of permissions between the agent and the injected UI. Any team shipping UI-as-payload needs a rendering/sandbox contract before they need a design system, and harnesses need to define that contract for vendors to target.

Source video ↗

The discovery-artifact consumption gap: from declared manifests to observed fetch behavior

Research question

Do agent harnesses actually fetch proposed discovery artifacts (.well-known/ai-catalog.json, ARD indexes, llms.txt), and does the presence of any of them change tool selection, navigation path, or task success holding API quality constant?

Why

The llms.txt evidence suggests adoption and consumption are decoupled: half the tested sites published the artifact, yet agents reportedly navigated docs and homepages directly. If that pattern repeats for ai-catalog.json, early adopters will have paid a schema and versioning tax for signaling value only. The engineering consequence is that discovery artifacts should be validated against real harness fetch logs before a roadmap commits to them.

Source video ↗

Re-architecting auth, rate limiting, caching, and cost attribution for a non-human dominant client class

Research question

Which systems break first when agent-originated requests outnumber human sessions, and what does a request-shape-aware auth and quota model look like for clients that issue many more calls per 'session' at machine pace?

Why

Session-based auth, human-paced rate limits, JS-rendered caching assumptions, and per-seat cost attribution all encode a human client model. If the traffic inversion is even directionally true, those are the systems that fail first and the ones that must be redesigned, with bot-vs-human classification becoming a first-class observability concern rather than a security afterthought.

Your llms.txt Is Not Working: Agent Readiness Must Be Measured, Not Declared

Publishing a machine-readable manifest is signaling, not discovery; the only defensible definition of agent readiness is behavior observed from real harnesses, and teams that ship llms.txt instead of machine-consumable docs and schemas are optimizing a checklist that no agent reads.

Angle

Contrast the near-50% adoption of llms.txt against the reported behavior of agents navigating straight to documentation and homepages, then generalize: adoption of a standard is not evidence of consumption, so validate discovery mechanisms against real harnesses before standardizing on them.

The Server Owns the Last Mile

MCP Apps inverts client-side composition: the tool vendor, not the chat host, renders the human-facing interaction, which means every agent-integrated service now owns a UI-as-payload contract with versioning, sizing, and trust obligations, plus a thin API-first core behind it.

Angle

Decompose the 'nearly headless' model into the machine contract (AX: schemas, auth, traversal) and the delegated presentation contract (UAX: server-rendered chunks in chat), and argue that teams still optimizing only the browser surface are optimizing the wrong layer for the traffic that matters.

Project ideas

4

HarnessMatrix

beyond-evals

A substantial share of measured agent-readiness variance across domains is attributable to harness-side traversal and tool-use policy rather than site-side substrate, so single-harness scores will not predict task success on a different harness for the same domain.

Proof of concept

Build a factorial benchmark: N domains x M harnesses (at least three distinct agent runtimes) x a fixed task suite (find docs, authenticate, complete a transaction-shaped task). Instrument every run with fetch logs, tool calls, and transcripts; score task success and steps-to-completion; then fit a variance decomposition of score into site, harness, and interaction terms.

Measurement

Percentage of total score variance explained by harness vs site factors; rank correlation (Spearman) of per-domain scores between harness pairs; rate at which the top-quartile domain under harness A falls out of the top quartile under harness B.

Source video ↗

UIChunkGatehouse

gatehouse

Server-supplied UI chunks rendered inside a chat host can be made safe by a host-enforced sandbox contract (capability-scoped data access, host-chrome provenance markers, explicit consent surfaces), and without such a contract injected UI permits data exfiltration and consent spoofing.

Proof of concept

Implement a minimal MCP-Apps-style host that renders a deliberately hostile server-supplied chunk (attempts to read adjacent chat context, exfiltrate via image URLs, and draw a fake host consent button). Then implement a candidate isolation contract and re-run the same adversarial chunk suite against it, with a permission-delegation model tying each UI-initiated action to an agent-scoped grant.

Measurement

Attack success rate per adversarial case (context read, exfiltration, consent spoofing) with and without the isolation contract; false-consent rate in a user study of the rendered consent surface; number of permission grants required per completed flow.

Source video ↗

CatalogConsumptionProbe

movement-lab

Publishing .well-known/ai-catalog.json does not measurably change agent discovery, tool selection, or task success relative to the same site without it, mirroring the observed llms.txt pattern where agents navigate docs and homepages directly.

Proof of concept

Stand up two mirrored domains with identical API quality and documentation, identical except for the presence of ai-catalog.json and an ARD index entry. Point multiple real agent harnesses at both with discovery-shaped tasks; log every fetch at the HTTP layer to detect whether the catalog path is ever requested, and compare resulting tool selection and task completion.

Measurement

Fraction of runs in which the catalog path is fetched at all; task success rate delta (with vs without catalog) with confidence intervals; delta in number of navigation steps to first successful API call; effect size on tool selection distribution.

Source video ↗

AgentTrafficLedger

new

Agent-originated request streams have a structurally different shape than human sessions (many more calls per intent, different burst and retry patterns, distinct auth failure modes), so human-derived rate limits and per-session cost attribution misprice and mis-throttle the dominant client class.

Proof of concept

Instrument an edge layer on a representative service to classify requests into agentic vs human using behavioral signals (request burstiness, tool-call fan-out, header and traversal signatures) rather than user-agent strings alone, then replay both classes against the existing quota and auth stack to find where policies break.

Measurement

Estimated agentic share of traffic and its confidence interval against the classification method; ratio of calls-per-intent for agentic vs human; percent of agentic requests hitting human-paced rate limits; misattributed cost per month under session-based accounting.

Architectural implications

3

Human-facing UI for an agent-integrated service is produced by the service and injected into the agent's chat rather than composed by the client.

Before

The service exposes data; the browser or client application owns layout, branding, and interaction rendering.

After

The service returns self-contained UI chunks that the agent harness renders, so the server retains brand identity and interaction control inside a third-party chat surface.

Consequence

Server teams must own UI-as-payload contracts (versioning, sizing, trust boundaries, security of injected UI), and harnesses must define a rendering/sandbox contract.

Source video ↗

Discovery moves from human-oriented SEO/sitemaps toward well-known machine-readable catalogs.

Before

Sites optimize for crawlers and human search results; documentation is written for people.

After

Sites publish structured catalogs at well-known paths and expose schemas agents can traverse directly.

Consequence

Discoverability becomes a build artifact with schema/versioning obligations, and search-engine ranking experience partially loses relevance.

Source video ↗

Agent-readiness evaluation requires running real agents against the site rather than auditing against a fixed checklist.

Before

Readiness assessed by human-authored best-practice criteria (presence of llms.txt, meta tags, docs structure).

After

Readiness scored from agent-observed behavior across multiple harnesses and task transcripts.

Consequence

Evaluation infrastructure (agent harnesses, task suites, scoring rubrics) becomes part of the product toolchain; scores must be reported per-harness to avoid over-fitting.

Tradeoffs and failure modes

4

Server-injected UI chunks in chat

Benefit

Preserves brand identity and enables rich, interactive last-mile flows without leaving the conversation.

Cost or risk

Injected UI creates a new trust and security surface inside the chat host, and couples the service to each harness's rendering capabilities; brand presence now depends on an intermediary's rendering contract.

Source video ↗

Standard adoption vs. actual consumption (llms.txt)

Benefit

Publishing llms.txt is cheap and widely adopted (nearly 50% of tested sites), signaling agent-friendliness.

Cost or risk

Agents reportedly bypass it and navigate docs/homepages directly, so the investment yields little and can create false confidence that discovery is solved.

Source video ↗

Harness-relative readiness scores

Benefit

Agent-defined evaluation reflects real behavior rather than human assumptions.

Cost or risk

Scores measured on one harness may not generalize; optimizing to a benchmark can over-fit to current traversal policies of specific agents.

Source video ↗

Intermediary-only gateway

Benefit

A single personal assistant as the gateway yields unified multi-service experiences without switching tabs.

Cost or risk

Removes the direct site relationship, leaving brand discovery and monetization unresolved when users never visit the service directly.
