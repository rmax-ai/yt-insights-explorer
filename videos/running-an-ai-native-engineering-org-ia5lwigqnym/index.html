Summary

Overview

  • Speaker: Fiona Fung
  • Channel: Claude
  • Main topic: Running an AI-native engineering organization and adapting team norms around Claude Code and Co-work
  • Purpose: To share lessons and tactical insights on how engineering organizations must adapt their processes, norms, and team structures when AI makes coding significantly faster and shifts bottlenecks away from writing code. Fiona Fung, manager of the Claude Code and Cowork team at Anthropic, discusses how engineering bottlenecks have shifted from coding and writing bandwidth to verification, review, and cross-functional collaboration. She outlines five major team norms that had to be rewritten—code review, onboarding, planning, hiring, and org shape—arguing that code is now the source of truth, building is cheap while arguing is expensive, and leaders should maintain individual contributor work.

Topic Map

The Shift in Bottlenecks

  • Explanation: Engineering bandwidth used to be the expensive limiting factor, driving heavy planning, scoping, and review processes to protect that resource. With AI coding tools like Claude Code, coding is rarely the slow part anymore, causing bottlenecks to shift from writing code to verification, review, cross-functional alignment, and security.
  • Key claims:
    • For years, engineering bandwidth was the expensive thing.
    • On the Claude Code team, coding is rarely the slow part anymore.
    • The bottleneck moved from coding to everything around coding: Verification, Review, XFN, Security.
  • Examples:
    • Comparing early 2000s software development where visual studio required one server room and on-call rotations to current continuous build and cloud paradigms.
  • Terminology:
    • engineering bandwidth
    • bottlenecks
    • verification
    • cross-functional (XFN)
  • Why it matters: Understanding where bottlenecks have moved prevents engineering teams from over-optimizing around obsolete constraints like manual test writing order or restrictive code merge queues.

Norms We Had to Rewrite

  • Explanation: Five core systems assuming engineering time was scarce had to change: Code review, onboarding, planning, hiring, and org shape.
  • Key claims:
    • Human judgment on what actually needs code review.
    • Cost of asking a dumb question went to zero during onboarding.
    • Planning requires less upfront design docs and more prototyping.
    • Hiring shifts toward creativity and judgment over raw output.
    • Org shape becomes flatter with every manager acting as an IC first.
  • Examples:
    • Replacing upfront design docs with prototypes and pull requests.
    • Using Claude as a design and content partner during bug fixes.
  • Terminology:
    • planning norms
    • code ownership
    • code review
    • team make-up
    • knowledge sharing
  • Why it matters: Old processes quietly stop working when AI changes throughput velocity; teams must explicitly audit and retire redundant rituals.

How We Rolled It Out

Key Points

In technical debates, code wins

  • Explanation: When teammates disagree on a design, having Claude prototype both approaches and examining the actual artifact is faster and cheaper than lengthy arguments.
  • Evidence: Generating multiple PR versions with Claude to compare technical approaches and human impact.
  • Practical implication: Reduces meeting time and opinion-driven stalemates by leaning on rapid prototyping.

Code is the new source of truth

  • Explanation: Documentation and design docs quickly go out of date, whereas keeping specs and source of truth directly inside the codebase leverages AI updating loops.
  • Evidence: Claude code commits and repository-embedded specs act as the primary knowledge base for onboarding.
  • Practical implication: Eliminates out-of-sync wikis and ensures engineering documentation stays current.

Every manager starts as an IC

  • Explanation: Managers must stay hands-on with coding and dogfooding to coach scrappiness effectively and understand team velocity.
  • Evidence: Managers on the Claude Code team actively write code, review PRs, and use the tooling daily.
  • Practical implication: Builds authentic product sense and empathy for developer friction points.

[O]Mental Modelhigh noveltymoderate evidence

When code generation becomes fast, the constraint migrates to verification, review, cross-functional alignment, and security — i.e., the harness around the code, not the code production itself. The Claude Code team reports coding 'is rarely the slow part anymore.'

Why it matters

It inverts where investment should go in agentic engineering systems: throughput, latency, and headcount planning should target verification and review capacity (test synthesis, diff triage, review routing, security scanning), not generation speed. Teams that keep optimizing generation will see diminishing returns and growing review queues.

Generalization

Any pipeline where one stage becomes near-free will shift the system bottleneck downstream; measure the new constraint before optimizing the old one.

[M]Mechanismmedium noveltymoderate evidence

Technical disagreements are resolved by generating multiple competing prototypes/PR versions with the model and comparing the artifacts, rather than by argument or deliberation. This is a concrete decision mechanism: candidate generation plus empirical comparison replaces opinion-driven debate.

Why it matters

It is a cheap, repeatable selection procedure that can be applied to architecture choices, API designs, and human-impact tradeoffs. For agent systems it suggests building explicit 'generate N variants, then compare against criteria' loops rather than single-shot generation followed by review meetings.

Generalization

Where the cost of producing a candidate artifact approaches zero, selection should be based on produced artifacts rather than on pre-hoc argument; the comparison criteria become the scarce, valuable asset.

[A]Architecturemedium noveltymoderate evidence

The source of truth is relocated into the codebase: specs, docs, and knowledge live next to the code so that the model's update loop keeps them current, and they serve as the primary onboarding knowledge base. External wikis/design docs are treated as inherently decayed.

Why it matters

This is a context-placement decision: colocating durable knowledge with the artifact it governs gives the agent a maintainable retrieval surface and eliminates a synchronization problem between two stores. It implies a design principle — put machine-maintained context where the machine already writes, instead of in a separate doc system that drifts.

Generalization

For any AI-maintained knowledge store, choose the storage location that a reliable automated write loop already touches; otherwise the store decays.

[P]Practicemedium noveltymoderate evidence

Rollout uses 'forcing functions': non-negotiable top-down mandates paired with explicit bottom-up permission to delete processes and adapt local rituals. The key operational lever is that leaders must name which processes can die, because people do not delete processes on their own.

Why it matters

Adoption of transformative tooling fails not from lack of capability but from unpriced legacy process. Naming and authorizing removal of specific processes is the mechanism that converts a new tool into a new default; without it, old rituals persist and consume the freed capacity.

Generalization

To change an engineering system's operating point, pair a hard constraint (mandate) with an explicit depreciation permission; otherwise the system retains its old invariants.

[A]Architecturemedium noveltyweak evidence

Code review is reframed as selective: humans apply judgment about what actually needs review rather than uniformly gating all changes. This turns review into a routing/classification problem rather than a blanket stage.

Why it matters

If generation volume rises, uniform human review becomes the throughput ceiling. Treating review as risk-based routing (which diffs, which reviewers, which checks) is the concrete way to keep the pipeline from stalling, and it implies an explicit classifier or policy layer between generation and merge.

Generalization

Project ideas

4

Review Router with Calibrated False-Negative Budget

gatehouse

A risk-scoring router between generation and merge can cut human-reviewed change volume by at least 50 percent while holding the rate of risky changes auto-passed to human review at or below the team's current post-merge incident rate.

Proof of concept

Instrument a change stream (diff size, touched subsystems, test coverage delta, security-relevant paths, author history) and route each change to auto-merge, single reviewer, or deep review; run shadow mode against existing uniform review and compare routing decisions with what human reviewers actually flagged.

Measurement

Change volume routed to human review, review queue depth per day, time-to-verified, and the false-negative rate of risky changes let through in shadow mode versus the uniform-review baseline.

Source video ↗

Verification Throughput Telemetry

beyond-evals

Time-to-verified per change predicts end-to-end delivery time better than assisted-commit share or coded volume once generation is no longer the constraint.

Proof of concept

Emit per-change telemetry from first commit to verified merge, decompose it into generation, review wait, review active, and CI/verification segments, and regress delivery time against each segment across several repositories.

Measurement

Explained variance of delivery time by verification-segment latency versus generation-segment latency; correlation of review queue depth with delivery time.

Source video ↗

Spec Drift Benchmark: In-Repo versus External Store

new

Repository-embedded specs are corrected faster and drift less than an external doc store under equal maintenance effort, but agent retrieval accuracy for intent and rejected-alternative questions is lower from in-repo specs alone.

Proof of concept

Take a non-code question set (why a decision was made, what alternatives were rejected, cross-cutting constraints), answer it from in-repo specs and from curated external docs, and separately measure staleness by timestamping claims against the commits that invalidate them.

Measurement

Retrieval answer accuracy per question class, median staleness age of contradicted claims, and correction latency after an invalidating commit.

Source video ↗

Prototype Bake-Off Loop

movement-lab

Generating N competing variants and scoring them against pre-declared criteria reduces decision latency and post-decision rework compared with single-variant generation followed by review discussion.

Proof of concept

Wrap a change request in a loop that produces two or three implementation variants in parallel plus an explicit comparison rubric, then log decision latency, number of review rounds, and whether the losing variant's approach reappears as rework.

Measurement

Median time from disagreement to decision, review rounds per decision, revert/rework rate within two weeks for single-variant versus multi-variant decisions.
