Summary

Overview

  • Speaker: Tom Moor
  • Channel: AI Engineer
  • Main topic: Context problems in AI coding agents and how to solve them through workflow integration
  • Purpose: To explain why current AI coding agents fail due to lack of context beyond the codebase, and to propose a structured context-carrying workflow from issue intake to code review and distillation. Tom Moor from Linear discusses the context problem facing modern AI coding agents. While code generation is becoming cheaper and more abundant, agents often produce locally correct code that fails to maintain global product coherence. To solve this, Moor introduces Linear's workflow model—Intake, Implement, Review, and Distill—which carries organizational, product, and historical context throughout the software development lifecycle, thereby improving agent reliability and reducing rework.

Core insights

[!]Failure Modemedium noveltymoderate evidence

The dominant failure mode of coding agents is no longer code-level incorrectness but loss of global product coherence: agents emit many locally correct changes that individually pass review yet collectively produce an incoherent product because intent, conventions, tradeoffs, and history are not in the repo.

Why it matters

Shifts the engineering target from 'make the agent write correct code' to 'make the agent aware of the constraints that make a change appropriate' — a different retrieval, data-modeling, and evaluation problem than code generation quality.

Generalization

As generation cost collapses, the binding constraint in any code-producing agent system moves from per-artifact correctness to cross-artifact consistency, which requires context that lives outside the artifact itself.

[M]Mechanismhigh noveltymoderate evidence

Rationale is not recoverable from code: when a decision's justification is absent from the files, agents re-propose previously rejected work (e.g., re-adding a UI component). This makes 'why not' knowledge — rejections and dismissed alternatives — a first-class context artifact rather than documentation nice-to-have.

Why it matters

Points to a concrete context store requirement: negative decisions and their reasons must be captured and retrievable at generation time, since standard repo contents structurally cannot contain them.

Generalization

Any agent system acting on a long-lived shared artifact needs an external record of rejected proposals, not just accepted state, or it will loop on settled decisions.

[A]Architecturemedium noveltymoderate evidence

Context should be treated as a pipeline state carried across four workflow stages (Intake, Implement, Review, Distill), with each stage enriching and passing context downstream rather than each agent re-deriving context from the repo alone.

Why it matters

Relocates context assembly from a per-agent prompt concern to a workflow-level data model, so enrichment done at triage (customer importance, MCP context, bug reproduction) is reused by implementation and review instead of being re-computed or lost.

Generalization

For multi-step agent systems, context should be a persisted, progressively enriched record attached to the work item — not a prompt assembled independently at each step.

Source video ↗
[M]Mechanismhigh noveltymoderate evidence

The Distill stage converts human review decisions on merged PRs into durable agent memory (system prompts, documentation, codebase conventions), creating a compounding loop where each human judgment reduces future repeated mistakes.

Why it matters

A concrete, implementable memory-write path: instead of generic memory or RAG over code, the write signal is human review verdicts on accepted changes — high-precision labels about what the org actually wants.

Generalization

In human-in-the-loop agent systems, the highest-value memory writes come from the correction and approval events produced by reviewers, because they encode policy that was never otherwise written down.

[E]Empirical Resulthigh noveltymoderate evidence

Historical PR and incident context lets review agents flag risks that diff-only review cannot see — e.g., holding a DB transaction open during slow network I/O — meaning review quality depends on retrieval over organizational history, not on larger models or bigger diffs.

Why it matters

Gives a concrete class of defect (latency-coupled resource holding, regression patterns) that becomes detectable only with cross-PR retrieval; useful as a benchmark target for review agents.

Generalization

Review/verification agents should be evaluated on recall of historically-documented risk patterns, which requires an index over past changes and ownership, not just the current changeset.

[>]Predictionmedium noveltyweak evidence

As inference cost falls and task horizons lengthen from interactive loops to hours-long autonomous runs, the required context model changes qualitatively: longer horizons mean more independent decisions made without human correction, so the cost of missing organizational context compounds per step.

Why it matters

Implies context architecture should be designed for horizon length: short-loop agents can be re-steered by humans, long-horizon or multi-agent 'factory' runs must front-load intent and constraints because mid-run correction is unavailable.

Generalization

Context and guardrail investment should scale with agent autonomy horizon, not with task complexity alone.

Source video ↗
[P]Practicelow noveltyweak evidence

Agent reliability requires closing the loop with verification signals — CI failures and explicit verification skills — as part of the harness, so that a context-rich but wrong change is caught mechanically rather than by more context.

Why it matters

Separates two distinct reliability levers: better context (reduces wrong-problem solutions) and mechanical verification (catches wrong implementations). Systems need both, and they fail differently.

Generalization

Context enrichment and executable verification are complementary, non-substitutable reliability mechanisms; track their failure contributions separately.

Project ideas

CoherenceBench

beyond-evals

A benchmark that scores sequences of agent changes on cross-change coherence proxies will rank coding models differently from diff-level correctness benchmarks, and its scores will correlate with human product-coherence judgments.

Proof of concept

Assemble multi-PR change sequences from open-source repositories; define coherence proxies such as duplicate or re-added components, convention violations against written policy, and settings-surface growth; collect human coherence ratings; compare model rankings on CoherenceBench versus diff-level benchmarks.

Measurement

Spearman correlation between benchmark scores and human ratings; rank divergence from diff-level benchmarks; inter-rater agreement on coherence judgments.

Source video ↗

RejectionMemory

new

Recording rejected proposals with rationale and retrieving them at generation time reduces the rate at which agents re-propose previously rejected changes, without increasing review time or prompt size beyond a bounded overhead.

Proof of concept

Instrument a repository with a rejection log containing proposal, rationale, scope, and date; build retrieval over that log; run an agent on tasks that include opportunities to re-add rejected components; A/B test with and without rejection-memory retrieval.

Measurement

Re-proposal rate of rejected changes; human review rejection rate; prompt token overhead; review time delta.

Source video ↗

ContextCarrier

movement-lab

Persisting and progressively enriching a work-item context record across Intake, Implement, Review, and Distill reduces context re-derivation and wrong-problem fixes compared with per-agent repo prompting.

Proof of concept

Build a lightweight work-item schema with fields for intent, customer importance, constraints, decisions, rejections, and provenance; connect intake enrichment and agent harnesses; run the same tasks with ContextCarrier versus repo-only prompts.

Measurement

Time to first correct plan; wrong-problem fix rate; human rework rate; frequency of context re-derivation across stages.

Source video ↗

DistillGuard

gatehouse

A review-derived memory store with conflict detection, scoping, and expiry reduces recurrence of the same review findings over successive PRs without increasing prompt size beyond a set threshold.

Proof of concept

Ingest PR review comments, extract candidate rules, deduplicate and conflict-check them, inject them into agent instructions with scope and expiry metadata, then run over a sequence of PRs in a test repository.

Measurement

Recurrence rate of identical review findings across PRs; prompt token growth per PR; number of conflicting-rule incidents; stale-rule expiry rate.

Architectural implications

4

Context assembly is moved out of the individual agent prompt and into a staged workflow record.

Before

Each coding agent is given repo files plus a task prompt and re-derives intent, conventions, and history on its own.

After

Intake, Implement, Review, and Distill each read and append to a shared, persisted context record attached to the work item.

Consequence

Context becomes a data-modeling and schema problem (what fields, what provenance) rather than prompt engineering, and enrichment work becomes reusable across agents.

Source video ↗

Review is repositioned from diff inspection to history-aware judgment.

Before

Review agents and tools examine the changeset against codebase conventions and tests.

After

Review agents additionally retrieve past PRs, team ownership, and incident history to assess fit and risk.

Consequence

Requires an index over organizational change history with ownership metadata; review latency and cost increase in exchange for catching regression classes invisible to diff review.

Source video ↗

Human output is reallocated from code production to context production.

Before

Engineer value is primarily in writing and fixing implementation code.

After

Engineer value concentrates in review verdicts and tradeoff decisions, which are captured and fed back as agent instructions and documentation.

Consequence

Human review becomes a training/memory signal with pipeline requirements (capture format, dedup, attribution); unreviewed or unrecorded decisions produce no compounding benefit.

Source video ↗

Verification is owned by the harness, not the agent's context.

Before

Reliability is pursued by giving the agent more information and better prompts.

After

Reliability combines context enrichment with verification skills and CI failure feedback loops the agent must consume.

Consequence

Harness needs structured access to CI results as tool output; otherwise long-horizon runs cannot self-correct and errors surface only at review.

Source video ↗

Tradeoffs and failure modes

5

Context volume vs. prompt effectiveness

Benefit

Richer context (history, ownership, intent, customer importance) reduces wrong-problem solutions and rework.

Cost or risk

There is an unidentified saturation point where additional context degrades agent performance; no selection or ranking policy is specified.

Source video ↗

Throughput vs. product coherence

Benefit

Cheap, abundant generation plus autonomous multi-agent execution increases change velocity substantially.

Cost or risk

Without carried context the output is thousands of locally correct changes that jointly degrade the product; the system 'manages chaos' rather than preventing it.

Source video ↗

Autonomy vs. human oversight

Benefit

Longer autonomous horizons and software-factory orchestration remove interactive bottlenecks.

Cost or risk

The correct balance between human oversight and autonomous multi-agent execution is unresolved; over-automation removes the judgment that produces distillable context.

Source video ↗

Distillation into agent instructions

Benefit

Learnings from merged PR reviews compound so the same mistakes are not repeated.

Cost or risk

Feeding review feedback back into system prompts and documentation risks bloat, conflicting rules, and stale policy; the summary specifies no selection, dedup, or expiry mechanism for distilled learnings.

Source video ↗

Trusting historical-context signals in review

Benefit

Historical PR and incident data surface risk classes (e.g., transaction held open across slow I/O) that diff-only review misses.

Cost or risk

Retrieval of 'similar past PRs' can surface irrelevant precedent and anchor the reviewer; the summary gives no recall or precision evidence for this mechanism.
