Summary

Overview

  • Speaker: Doug Guthrie and Carlos Esteban
  • Channel: AI Engineer
  • Main topic: AI System Evaluation and Observability with Braintrust
  • Purpose: To educate AI engineers on how to build robust testing, evaluation, and observability frameworks for LLM applications using Braintrust. This hands-on workshop led by solutions engineers from Braintrust covers the comprehensive lifecycle of evaluating AI and LLM systems. It introduces core concepts like prompt engineering, offline and online evaluations, datasets, scorers (code-based and LLM-as-a-judge), and human-in-the-loop workflows. Through practical activities, attendees learn how to use Braintrust's UI and TypeScript SDK to run evaluations, track performance regressions, set up online logging and scoring, and close the feedback loop for continuous improvement.

Ingredients of an Eval

  • Explanation: Breaks down an evaluation into three core components: Task, Dataset, and Scorer.
  • Key claims:
    • A task is the code or prompt being evaluated, requiring an input and output.
    • A dataset is a collection of real-world or synthetic test cases.
    • A scorer is the logic (LLM-as-a-judge or code function) that grades output on a 0-1 scale.
  • Examples:
    • Using code-based exact match functions alongside GPT-4 as an LLM judge.
  • Terminology:
    • task

    • scorer
    • LLM-as-a-judge
    • code function
  • Why it matters: Provides a clear modular framework for structuring any AI evaluation.

Offline vs Online Evals

  • Explanation: Contrasts offline evals (done in development via playgrounds and SDKs to catch issues early) with online evals (monitoring real production traffic and user feedback).
  • Key claims:
    • Offline evals proactively identify issues before deployment using predefined datasets.
    • Online evals provide real-time monitoring, tracing, and user feedback capture in production.
  • Examples:
    • Running experiments in the Braintrust UI versus streaming production logs via proxy or SDK.
  • Terminology:
    • offline evals
    • online evals

Key Points

Evals cut dev time and reduce costs

  • Explanation: Automating test reviews replaces manual QA, allowing faster iteration and safer releases.
  • Evidence: Customer examples like Zapier and Coda saw 5x to 20x increases in feature delivery and productivity.
  • Practical implication: Teams can iterate on prompts and models with high confidence without manual bottlenecking.

Two mental models for evals: Offline and Online

  • Explanation: Offline evals test changes during development; online evals monitor production traffic and capture real user feedback.
  • Evidence: Braintrust supports both playground experiments and SDK/proxy-based production tracing.
  • Practical implication: Engineers must test rigorously before shipping and continuously monitor after deployment.

Combine code-based and LLM-as-a-judge scorers

  • Explanation: Code scorers handle deterministic binary checks, while LLM judges evaluate subjective criteria like tone, style, and completeness.
  • Evidence: Workshops demonstrated setting up both accuracy scorers (LLM) and formatting scorers (TypeScript).
  • Practical implication: Using both types provides a balanced evaluation of both strict constraints and nuanced quality.

Core insights

[!]Failure Modemedium noveltyweak evidence

Because model behavior is a function of a mutable third-party dependency, a production LLM system can regress with zero code changes; therefore evals must be a repeated/scheduled discipline (re-run on provider updates) rather than a one-time pre-launch test.

Why it matters

It reframes evals from a launch gate to a continuous monitoring loop owned by engineering, and makes model/prompt version pinning and re-validation a release requirement.

Generalization

Any system whose behavior depends on externally mutated services (hosted models, third-party APIs, managed retrievers) needs scheduled re-validation against frozen test suites, not just pre-merge tests.

[A]Architecturelow noveltystrong evidence

An eval is factored into a three-part contract — Task (the prompt/code under test with input and output), Dataset (real or synthetic cases), and Scorer (0-1 grading logic) — which decouples the artifact under test from the test corpus and the grading function.

Why it matters

This factorization is what allows swapping a model or prompt while holding the test fixed, making model/prompt changes diffable and comparable across runs.

Generalization

Separating 'system under test', 'fixture corpus', and 'assertion/grading logic' is the same interface discipline as unit testing, and it is what makes evaluation composable and CI-able.

Source video ↗
[O]Mental Modellow noveltystrong evidence

Evaluation splits into two distinct systems with different feedback latencies: offline evals on predefined datasets during development, and online evals over live production traffic with tracing and user feedback capture.

Why it matters

They have different data sources, cost profiles, and consumers (engineers pre-merge vs. operators post-deploy), so treating them as one pipeline leads to either untested releases or unmonitored production.

Generalization

Mirrors the classic offline-training/online-serving split; any adaptive AI system likely needs both a controlled replay harness and a live telemetry loop.

Source video ↗
[M]Mechanismmedium noveltymoderate evidence

Production traces are not just diagnostics — they are fed back into evaluation datasets, so the test corpus is a continuously growing artifact derived from real usage rather than a static fixture set.

Why it matters

It converts observability telemetry into test coverage, closing the loop between field failures and regression suites, and implies the eval set needs curation, sampling, and privacy handling rather than write-once authoring.

Generalization

This is a data flywheel pattern: production telemetry becomes the training/eval corpus, requiring a defined path from log to curated fixture.

Source video ↗
[P]Practicelow noveltystrong evidence

Scoring is deliberately hybrid: deterministic code scorers enforce binary/format constraints while LLM-as-a-judge scorers grade subjective dimensions like tone, style, and completeness, and the two are treated as complementary rather than substitutable.

Why it matters

Single-scorer designs systematically blind-spot either hard constraints (a judge will pass malformed output) or nuanced quality (an exact-match check rejects acceptable paraphrases).

Generalization

Layered verification — deterministic guardrails plus probabilistic quality graders — is the general pattern for evaluating open-ended generative output.

Source video ↗
[M]Mechanismmedium noveltymoderate evidence

Observability is attached at the LLM client boundary (SDK wrapper or proxy) rather than instrumented inside application logic, so traces are captured without application code changes.

Why it matters

It reduces the marginal cost of adding tracing to existing services and keeps instrumentation orthogonal to business logic, which matters for adoption and for not coupling the app to a vendor.

Generalization

Interposition at the transport/client layer is a reusable strategy for cross-cutting concerns (tracing, cost accounting, rate limiting, caching) across heterogeneous LLM call sites.

Project ideas

4

Provider Regression Sentinel

beyond-evals

Scheduled eval runs against pinned model versions will detect provider-side behavioral regressions within 24 hours, while pre-merge-only evals will miss them entirely.

Proof of concept

Frozen dataset and hybrid scorers run on a cron; alert on score drop beyond threshold; log model/prompt versions per run.

Measurement

Time-to-detection, false-positive rate, cost per detected regression.

Judge Calibration Harness

beyond-evals

A labeled holdout set can measure LLM-judge agreement with human labels and detect judge drift before it corrupts eval comparisons.

Proof of concept

Run judge versions against human-labeled fixtures; track agreement rate and calibration curve over time.

Measurement

Judge-human agreement rate, drift detection latency, score stability across judge versions.

Trace-to-Eval Promotion Pipeline

beyond-evals

Prioritizing thumbs-down and low-scored production traces for promotion yields higher regression-detection power per curated example than random trace sampling.

Proof of concept

Ingest production traces, filter by feedback/score, sample into dataset, run evals against baseline.

Measurement

Regression detection power per curation hour, coverage delta, false-positive promotion rate.

Architectural implications

3

Eval assets become portable, versioned artifacts instead of ad-hoc playground sessions.

Before

Prompts prototyped in a playground and validated by manual eyeballing.

After

Task + dataset + scorer defined as a reusable unit runnable programmatically or via UI.

Consequence

Model swaps and prompt edits become diffable experiments and can be gated in CI, shifting eval ownership into the engineering workflow.

Tracing responsibility moves from application code to the LLM client wrapper.

Before

Manual logging calls scattered through application logic.

After

LLM API clients wrapped with an observability SDK/proxy that emits traces automatically.

Consequence

Tracing becomes vendor-adjacent infrastructure rather than app concern; lowers adoption cost but introduces a client-layer dependency and a data-egress surface.

The evaluation dataset becomes a downstream consumer of the production logging pipeline.

Before

Static, hand-authored test set created before launch.

After

Production traces sampled, human-labeled, and promoted into the dataset.

Consequence

Requires new plumbing (sampling, PII scrubbing, labeling queues) and turns eval-set growth into an ongoing operational process rather than a one-time task.

Tradeoffs and failure modes

4

LLM-as-a-judge scoring

Benefit

Can grade subjective criteria such as tone, style, and completeness that code scorers cannot express.

Cost or risk

Probabilistic and non-deterministic, so scores need calibration and are weaker evidence than deterministic checks for hard constraints.

Source video ↗

Human-in-the-loop review

Benefit

Establishes ground truth and aligns model behavior with business compliance and user expectations.

Cost or risk

Introduces human latency and cost into the iteration loop, so it cannot be the primary gate for high-frequency prompt/model changes.

Source video ↗

Synthetic-first dataset bootstrapping

Benefit

Lets teams start evaluating immediately without waiting for production traffic.

Cost or risk

Synthetic cases may not match the real input distribution, producing optimistic scores that do not transfer to production behavior.

Source video ↗

Continuous production logging

Benefit

Cuts debugging of field issues from hours to minutes by retaining trace context.

Cost or risk

Persisting every LLM call creates storage cost and stores potentially sensitive prompt/output content, requiring retention and redaction policy.
