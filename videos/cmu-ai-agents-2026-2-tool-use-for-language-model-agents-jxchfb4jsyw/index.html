Summary

Overview

  • Speaker: Graham Neubig
  • Channel: Graham Neubig
  • Main topic: Tool Use and API integration for Language Model Agents
  • Purpose: To educate students and researchers on how language model agents interface with external programs, APIs, and tools, detailing the mechanics, execution, constraints, and evaluation methods. This lecture covers the fundamentals of tool use for language model agents, exploring how models turn token predictions into actions. Graham Neubig discusses tool definitions, benefits of tools (extending capabilities and facilitating computation), scenarios for tool use, programmatic tool calling (CodeAct), mechanics of providing tools (tokens, chat templates, tool definitions), constrained decoding (JSON schema and push-down automata), REST API calling, Model Context Protocol (MCP), orchestration of multiple calls (serial vs. parallel), and evaluation methodologies like the Berkeley Function Calling Leaderboard.

Topic Map

Basic Idea and Definition of Tools

  • Explanation: Defines what a tool is for a language model agent and why they are necessary to bridge the gap between token-predicting language models and external computer programs.
  • Key claims:
    • A tool is an interface through which a language model can invoke an external computer program.
    • Language models cannot perform tool invocation on their own because they are fundamentally token-predicting machines.
  • Examples:
    • Search, calculator, browser, Python, arbitrary APIs.
  • Terminology:
    • Tool
    • Language Model Agent
    • Token-predicting machine
  • Why it matters: Establishes the foundational distinction between static language models and active agents.

Benefits of Tools

  • Explanation: Outlines the core benefits of giving language models access to tools: extending capabilities beyond model parameters and facilitating operations that models could do but less efficiently.
  • Key claims:
    • Extending allows access to information or actions unavailable in model parameters (e.g., getting current time).
    • Facilitating allows delegating external operations that the model can do in text but much more slowly or unreliably (e.g., multi-digit multiplication).
  • Examples:
    • Getting current time via API; using a calculator for arithmetic.
  • Terminology:
    • Extend
    • Facilitate
    • Action space
  • Why it matters: Explains why tool use is necessary for real-world agent utility.

Tool-Use Scenarios

  • Explanation: Categorizes the practical needs for tool use into current information, exact computation, private state, and external action.
  • Key claims:
    • Call tools only when their benefit outweighs latency, cost, failure, and risk.
  • Examples:
    • Search for current information; calculator for exact computation; account API for private state; browser for external action.
  • Terminology:
    • Current information
    • Exact computation
    • Private state
    • External action
  • Why it matters: Helps developers determine when and what tools to integrate.

Examples of Tools

  • Key claims:

  • Examples:
    • Textual responses (finish), information retrieval (search_web), code execution (execute_code), image generation (generate_image), custom functions (create_grocery_cart).
  • Terminology:
    • Textual response

  • Why it matters: Provides concrete architectural patterns for tool implementations.

Programmatic Tool Calling and CodeAct

  • Explanation: Discusses using code as a meta-tool, enabling control flow, variables, and libraries in one action.
  • Key claims:
    • Code acts as a meta-tool that improves success rates and reduces interaction turns.
    • Code is expressive but introduces challenges with broader action spaces, harder constraints, and higher impact/security risks.
  • Examples:
    • Using Python and pandas for data analysis tasks.
  • Terminology:
    • CodeAct

    • Programmatic tool calling

  • Why it matters: Demonstrates how code execution significantly enhances agent capability and efficiency over rigid single-function calls.

Mechanics of Providing Tools

  • Explanation: Explains how tool calls are structured as tokens, serialized into prompt inputs, and dispatched by execution harnesses.
  • Key claims:
    • Tool calls are expressed as tokens within model outputs.
    • Different models use different tool call protocols and serialization formats.
  • Examples:
    • Qwen (function + parameter tags), Mistral Small 4 (control token + call ID), DeepSeek V3 (DSML invocation block).
  • Terminology:
    • Tool call tokens
    • Chat template
    • Tool definition
    • Call ID
  • Why it matters: Crucial for understanding how different LLM providers handle tool calling under the hood.

Constrained Decoding

  • Explanation: Covers how to ensure language models generate valid tool calls using JSON schema, context-free grammars, push-down automata, and token masking.
  • Key claims:
    • Language models are not guaranteed to generate well-formed tool calls without constraints.
    • Token masking based on grammars ensures 100% syntactic and schema validity during decoding.
  • Examples:
    • Using JSON schema to validate types, required fields, and enum values; XGrammar and push-down automata for token masking.
  • Terminology:
    • Constrained decoding
    • JSON schema
    • Context-free grammar
    • Push-down automaton
    • Token masking
  • Why it matters: Prevents malformed outputs and runtime parsing errors in production agent systems.

REST API Calling and Model Context Protocol (MCP)

  • Explanation: Examines how to expose functions over HTTP using FastAPI, publish OpenAPI descriptions, and connect hosts to servers via the Model Context Protocol (MCP).
  • Key claims:
    • REST APIs use OpenAPI descriptions for schema sharing.
    • MCP provides a standardized protocol for connecting AI hosts to local and remote client servers with separate credentials.
  • Examples:
    • FastAPI weather endpoint with API key authentication; FastMCP server wrapping OpenAPI.
  • Terminology:
    • REST API
    • OpenAPI
    • FastAPI
    • Model Context Protocol (MCP)
    • FastMCP
  • Why it matters: Provides industry standards for securely exposing external capabilities to agents.

Orchestrating Multiple Calls: Serial vs. Parallel

  • Explanation: Compares serial tool execution with parallel execution using asyncio.gather, highlighting dependencies and efficiency.
  • Key claims:
    • Parallel tool calls can significantly reduce task latency when calls are independent.
    • Calls with data dependencies must be sequenced.
  • Examples:
    • Executing weather, calendar, and flight lookups in parallel versus finding a customer ID before fetching orders.
  • Terminology:
    • Serial tool calling
    • Parallel tool calling
    • Asyncio.gather
    • Dependency
  • Why it matters: Directly impacts agent speed and cost efficiency.

Key Points

Tools Extend and Facilitate LLM Capabilities

  • Explanation: Tools allow agents to access external data/actions and perform complex computations more reliably and quickly.
  • Evidence: Distinction between fetching live time/weather vs. performing multi-digit multiplication.
  • Practical implication: Developers should use tools for real-time data retrieval and precise computation tasks rather than relying purely on model weights.

Code as a Meta-Tool (CodeAct)

  • Explanation: Allowing agents to write and execute code provides control flow, variables, and library access in a single unified action.
  • Evidence: CodeAct research shows higher success rates and fewer interaction turns.
  • Practical implication: Code execution interfaces make powerful general-purpose agent environments but require strict sandboxing for security.

Constrained Decoding Guarantees Syntax

  • Explanation: Using JSON schemas and grammar-based token masking prevents models from generating malformed tool calls.
  • Evidence: Push-down automata and XGrammar mask invalid logits during inference.
  • Practical implication: Always implement constrained decoding to eliminate parsing failures in production applications.

Model Context Protocol (MCP) Secures Agent Tool Integration

  • Explanation: MCP standardizes discovery and invocation while maintaining separate credentials between agent hosts and upstream servers.
  • Evidence: FastMCP and static token verifiers in FastAPI integration.
  • Practical implication: Use MCP to safely connect AI applications to external data sources without exposing master API keys to the model.

Parallel Tool Execution Reduces Latency

  • Explanation: Independent tool calls can be executed concurrently using asynchronous gathering to dramatically speed up agent workflows.
  • Evidence: Comparing serial round-trip costs (~6.4 seconds) with parallel execution (~2.8 seconds).
  • Practical implication: Design agent execution harnesses to batch independent tool calls whenever possible.

Frameworks, Models & Processes

CodeAct

  • How it works: Treats executable code (e.g., Python) as the primary action space, allowing the model to compose functions, control loops, and use external libraries.
  • Components:
    • Built-in functions
    • External libraries (pandas)
    • Utility functions
  • When to use: When agents need to perform complex multi-step data manipulation, calculations, or programmatic workflows.

Model Context Protocol (MCP)

  • How it works: Connects an AI application host to client servers (local or remote) using a standardized protocol for discovering tools at runtime and handling secure authentication.
  • Components:
    • MCP Host
    • Clients
    • Local/Remote servers
  • When to use: When building secure, modular enterprise agent architectures that integrate multiple third-party services.

Grammar-Based Constrained Decoding (XGrammar)

  • How it works: Maps a JSON schema to a context-free grammar parsed by a push-down automaton, masking model output logits at each step to allow only valid tokens.
  • Components:
    • Finite control
    • Stack memory
    • Token mask cache
  • When to use: In production inference engines where 100% valid schema compliance is mandatory.

Actionable Takeaways

  • Immediate:
    • Implement constrained decoding (JSON schema / grammar masking) for all production tool-use agents.
    • Use asynchronous execution (asyncio.gather) for independent tool calls to reduce latency.
    • Leverage FastAPI and FastMCP to expose safe, credential-separated tools to language models.
  • Strategic:
    • View code as a meta-tool (CodeAct) to maximize agent expressiveness and efficiency.
    • Evaluate agents across the full stack: selection, arguments, trajectory, and operational metrics (latency, cost, reliability, safety).
    • Be aware that provider-level quantization and decoding differences dramatically impact tool-call error rates.
  • Questions to investigate:
    • How do different LLM quantization levels (FP8 vs FP4) affect tool-calling robustness?
    • What are the best sandboxing practices for executing arbitrary code generated by language model agents?
    • How can we effectively measure semantic correctness beyond syntactic schema validation?

Article ideas

4

The Decoder Is the Contract: Why Tool-Call Correctness Belongs in the Inference Stack

Prompt engineering and retry loops are the wrong place to guarantee tool-call structure; grammar-constrained decoding collapses schema validity into the serving layer, but it also couples deployment to schema versioning and shifts the remaining failure surface to semantic mismatches between valid arguments and intended actions.

Angle

Argue that schema enforcement is an inference-layer concern, then map the resulting organizational consequences: schema-as-decoding-artifact, version coupling between serving and tools, and a reduced but altered error budget.

Source video ↗

Code as a Meta-Tool Is a Security Architecture Decision

Adopting CodeAct is not merely a capability upgrade; it replaces schema-bounded safety with sandbox containment as the primary control, forcing teams to design filesystem, network, resource, and credential boundaries before they can responsibly ship expressive code execution.

Angle

Frame the CodeAct vs. typed-function choice as a trade of verification burden from static schema check to dynamic sandbox and resource containment, with concrete containment dimensions as the real design surface.

Source video ↗

Your Agent Harness Has a Wire Protocol Problem

Tool-call formats are vendor-specific token dialects, not a uniform API, so multi-model agents require protocol adapters and protocol-level test suites; treating tool calls as portable leads to brittle parsing and silent failures that only appear after model swaps.

Angle

Reframe tool-call serialization as a wire protocol with dialects, then derive the adapter layer and test strategy needed to keep harnesses model-agnostic.

Source video ↗

Parallel Tool Calls Are a Scheduling Problem, Not a Prompt Trick

Latency wins from concurrent tool execution require dependency-aware scheduling, not just a prompt asking for parallel calls; without an explicit call graph, parallelism is unsafe, and with one, the agent loop becomes a workflow engine with partial-failure semantics.

Angle

Show that the serial/parallel decision is a data-dependency scheduling problem, then outline how static argument-reference analysis can derive call graphs and what correctness and failure-handling constraints follow.

Architectural implications

4

Schema validity is enforced during decoding via token masking from grammars and push-down automata rather than by prompting and post-hoc JSON validation.

Before

Prompt instructions plus output parsing, validation, and retry loops to repair malformed tool calls.

After

Grammar/schema-constrained decoding integrated into the serving stack, with schemas as a decoding-time artifact.

Consequence

Retry logic and error-handling code shrink, but the inference/serving layer becomes coupled to tool schemas and must be versioned with them.

Source video ↗

Code execution acts as a single meta-tool replacing many narrow function tools.

Before

A large catalog of typed single-purpose tools, each individually described and schema-constrained.

After

A sandboxed code interpreter as one tool, with expressive multi-step programs executed in a single turn.

Consequence

The critical engineering boundary moves from tool-schema design to sandboxing, resource limits, and auditability, since the action space is no longer bounded by a fixed schema.

Source video ↗

Tool-call formats are model-family specific and expressed as tokens within the output stream.

Before

A portable, provider-agnostic tool-calling interface assumed interchangeable across models.

After

A per-model protocol adapter (chat template plus parser for tags, control tokens, or invocation blocks) sitting between the model and the execution harness.

Consequence

Model swaps become integration projects; teams need protocol-level test suites and model-specific harness code.

Source video ↗

Multiple tool calls are scheduled as an orchestration problem with dependencies rather than a strictly sequential loop.

Before

Turn-by-turn serial execution, waiting for each tool result before deciding the next call.

After

Dependency-aware scheduling that dispatches independent calls concurrently (asyncio.gather) and sequences only dependent ones.

Consequence

Agent latency drops substantially for read-heavy workflows, but the harness must model call graphs and handle partial failures of concurrent calls.
