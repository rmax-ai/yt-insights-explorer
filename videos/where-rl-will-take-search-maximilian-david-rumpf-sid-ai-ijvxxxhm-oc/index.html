Summary

Overview

  • Speaker: Maximilian-David Rumpf
  • Channel: AI Engineer
  • Main topic: Applying reinforcement learning to search and retrieval systems using agentic subagents
  • Purpose: To demonstrate how reinforcement learning can replace human-engineered search pipelines with specialized, compute-scalable agentic search models. Maximilian-David Rumpf, founder and CEO of SID.ai, discusses how reinforcement learning (RL) is transforming search and retrieval. Traditional search pipelines use fixed, human-designed architectures with chained models that suffer from compounding errors and high costs when run via agentic workflows. Rumpf presents SID-1, a specialized RL model that acts as a subagent for search, making all decisions on the fly and enabling 20x faster and over 100x cheaper retrieval compared to frontier models while outperforming vector and reranker baselines.

Topic Map

The Problem with Agents in Search

  • Explanation: Agents provide high-quality results in search and retrieval (twice as likely to find the right document), but they are extremely expensive ($0.1–$1 per question) and slow (taking minutes instead of milliseconds). Agents spend 30-50% of their tokens searching.
  • Key claims:
    • Agents are a new paradigm for search yielding much higher quality results
    • Agents are currently incredibly expensive and slow (minutes vs. milliseconds)
    • Agents spend 30% to 50% of their tokens on searching
  • Examples:
    • TurboPuffer as a fast retrieval baseline vs. slow agentic search
  • Terminology:
    • subagent
    • retrieval
    • token cost
  • Why it matters: High cost and latency limit the practical adoption of agentic search systems.

Classical Search vs. RL Search

  • Explanation: Classical search pipelines use chained, locally-optimized models with decisions baked in at design time and fixed compute per question. In contrast, RL-driven search uses a single model that adapts on the fly, dynamically allocating compute based on question difficulty.
  • Key claims:
    • Classical search pipelines accrue a long tail of failures due to fixed design-time decisions
    • Machine design outperforms human design in search algorithms, mirroring history in computer vision and chess (Stockfish to AlphaZero)
    • RL for search uses a single model that can search, read results, iterate, and adjust metadata filters on the fly
  • Examples:
    • IBM DeepBlue (human rules) vs. AlphaZero (pure RL)
    • Canny edge detection vs. VLM computer vision
  • Terminology:
    • BM25
    • PageRank
    • AlphaZero
    • reranker
  • Why it matters: Moving from human-designed pipelines to RL allows models to discover optimal retrieval strategies without manual edge cases.

Why Search is an Ideal Target for RL

  • Explanation: RL requires verifiable and grindable rewards. Search is verifiable ('Did you find the correct documents?') and grindable (models can attempt questions thousands of times per second). Furthermore, specialized smaller models can outperform general LLMs for search tasks.
  • Key claims:
    • Search needs rewards that are verifiable and grindable
    • Most parts of a general language model are not needed for specialized search tasks
    • Search quality increases predictably with compute without hitting a ceiling
  • Examples:
    • CPU vs GPU analogy: a CPU can do anything a GPU can, but you wouldn't use one for LLM inference
  • Terminology:
    • verifiable rewards
    • grindable
    • compute scaling
  • Why it matters: Verifiability and grindability enable reinforcement learning to scale search quality predictably.

SID-1 Results and Production Architecture

  • Explanation: SID-1 achieves superior retrieval recall while being 20x faster and 100x cheaper than frontier models like GPT-5.1 or Gemini. In production, routing search to a subagent prevents context pollution in the main agent's context window.
  • Key claims:
    • SID-1 achieves 0.84 recall in 5.5 seconds at $0.0004 per question
    • Search subagents prevent context pollution by keeping failed search traces out of the main agent's context window
    • Scaling RL will give arbitrarily good search in any domain
  • Examples:
    • SID-1 vs GPT-5.1, Gemini 3 Pro, Sonnet 4.5 benchmarks
  • Terminology:
    • SID-1
    • context pollution
    • subagent execution trace
  • Why it matters: Demonstrates practical production readiness with massive speedups and cost reductions.

Key Points

Agents as a New Paradigm for Search

  • Explanation: Using agents for search improves document discovery significantly but introduces high latency and high token consumption.
  • Evidence: Agents spend 30-50% of tokens on searching and cost $0.1 to $1 per question.
  • Practical implication: Requires delegation to specialized subagents to maintain efficiency.

Machine Design Beats Human Design

  • Explanation: Just as AlphaZero surpassed Stockfish in chess through pure RL rather than hand-crafted rules, RL models outperform manual search pipelines.
  • Evidence: Historical evolution from BM25 and PageRank through vector search and rerankers to pure RL.
  • Practical implication: Stop engineering complex multi-step search heuristics by hand and let RL discover them.

Search is Verifiable and Grindable

  • Explanation: Reinforcement learning thrives when outcomes can be automatically verified and trained against thousands of iterations per second.
  • Evidence: Verification of whether correct documents were retrieved for a given question.
  • Practical implication: Makes search an ideal candidate for large-scale RL training.

Context Pollution Prevention in Production

  • Explanation: Passing raw search iterations and failed queries to a main agent pollutes its context window. Subagents handle iterations locally and return clean results.
  • Evidence: Agent execution traces comparing raw multi-step search vs. delegated subagent execution.
  • Practical implication: Saves 30-50% tokens and increases accuracy in production LLM systems.

Core insights

[A]Architecturehigh noveltymoderate evidence

Delegating search to a dedicated subagent functions as a context firewall: the subagent absorbs all failed queries, dead-end iterations, and raw result traces locally and returns only a ranked list to the main agent, preventing the main agent's context window from being polluted by the search process itself.

Why it matters

It reframes subagents as a context-budget instrument rather than just a modularity convenience; the primary benefit is measurable token savings (30-50%) plus accuracy, not code organization.

Generalization

Any high-iteration, high-fan-out subtask (search, code execution, browsing, data cleaning) should be wrapped behind a narrow return contract so its internal loop stays out of the parent's context.

Deep dives

5

Subagent return contracts as context-budget engineering

Research question

What should a search subagent return to its parent — a bare ranked list, or a ranked list plus calibrated confidence, failure reason, and query provenance — and how much downstream answer accuracy does each contract buy relative to its token cost?

Why

The context-firewall argument is only half-specified: isolating the loop saves 30-50% of tokens, but discarding the failure trace destroys the signal the orchestrator needs to escalate, reformulate, or change strategy. This is the concrete design decision any team building an agent with a search tool must make, and there is currently no measured guidance on where the compression boundary should sit.

Source video ↗

The verifiable-and-grindable screen for RL candidacy

Research question

Given an agent subtask, can verifiability (programmatic pass/fail) and grindability (rollout throughput) be operationalized into a decision rule that predicts whether an RL policy will beat a hand-engineered pipeline — and where does the rule fail?

Why

This is the most transferable idea in the talk: it converts 'should we RL this?' from taste into a checklist. But the conjunction is asserted, not tested. The interesting failure case is a task that is verifiable but low-throughput, or high-throughput but only weakly verifiable — exactly where most real engineering subtasks live (code execution, data cleaning, tool routing).

Source video ↗

Label construction for retrieval rewards and reward hacking risk

Research question

When retrieval rewards are built from binary 'correct document' labels, do trained policies learn user-perceived retrieval quality or the labeling convention — and how does recall@k choice and graded versus binary relevance change the learned search behavior?

Why

The entire RL-for-search thesis rests on the claim that search is verifiable, but 'did you find the correct document' hides every hard question in IR evaluation: multi-relevant queries, partially relevant documents, k selection, and corpus-dependent ground truth. If the reward is a proxy, the policy optimizes the proxy. This is the highest-probability way the whole approach quietly fails.

Source video ↗

Variable per-question compute versus budgetable SLOs

Research question

Does dynamic compute allocation per question actually lower the tail of retrieval failures without making per-question cost and latency unbudgetable, and which query classes still require a fixed-compute millisecond fallback path?

Why

Adaptive compute is presented as a pure win, but it trades a predictable fixed budget for a heavy-tailed one. For anyone running retrieval in an interactive product, a variable 5.5-second call is a different engineering object than a fixed 5-millisecond one — routing and fallback policy, not model quality, becomes the binding constraint.

Source video ↗

Cross-domain transfer cost of specialized retrieval policies

Research question

What is the marginal training cost per new domain for an RL retrieval policy, and how far does a policy trained on one corpus family transfer to structurally different corpora before it degrades to baseline?

Why

The 'arbitrarily good search in any domain' claim is the load-bearing prediction for anyone considering building rather than buying. If each domain needs a fresh environment and reward pipeline, specialization becomes a per-domain capital expense and the generalist model remains the rational default for long-tail domains.

Article ideas

4

Your Agent's Search Loop Is Eating Your Context Window

The subagent boundary in agentic search should be justified as a context-budget instrument rather than a modularity pattern: the subagent exists to absorb an unbounded iterative loop so the parent's context stays clean, and the design question that actually matters is what the return contract compresses and what it must preserve.

Angle

Take the 30-50% token figure at face value and work backwards: if search is the dominant token line item, then the subagent's interface — not its retrieval algorithm — is the highest-leverage design surface. Argue that 'returns a ranked list' is an underspecified contract and that confidence and failure reasons are part of the API.

Source video ↗

Stop Reaching for the Frontier Model on Every Tool Call

For narrow, high-volume, verifiable subtasks, a specialized small model dominates the cost/latency/quality frontier, which means the right architecture is a cost-tiered one — expensive generalist orchestrating cheap specialists — and the default 'biggest model everywhere' habit is a straight budget leak.

Angle

Use the CPU/GPU framing as an architectural argument about composition rather than a hardware analogy, and press on the vendor-benchmark caveat: the headline 100x/20x numbers demand scrutiny of corpus, k, and baseline parity, but the structural argument survives even a heavily discounted version of them.

Source video ↗

Verifiable and Grindable: A Screen for When RL Beats Your Pipeline

Before investing in RL for a subsystem, demand two properties — a programmatically checkable reward and enough rollout throughput that sample cost is negligible; if either is missing, engineering the pipeline remains the correct answer, and the industry's enthusiasm for RL is over-applied to tasks that fail this screen.

Angle

Turn an asserted conjunction into an actionable pre-flight checklist, then attack the seductive part: the AlphaZero-over-Stockfish narrative is a precedent about games and perception, and citing it for a domain with fuzzy ground truth is an unearned analogy.

Source video ↗

The Long Tail Is a Design-Time Artifact

Retrieval failures on unusual queries are structural, not incremental — no prompt tuning fixes a pipeline whose compute budget was fixed before the question arrived; the fix is to demote BM25, ANN, and rerankers from architecture to tools and learn the orchestration policy on top of them.

Angle

Keep the primitives, move the value: argue that the durable engineering artifact becomes the training environment and reward function, and that teams accumulating RAG pipeline heuristics are accumulating technical debt against a learned policy.

Project ideas

4

Contract A/B: ranked list versus ranked list plus confidence

gatehouse

A search subagent that returns a ranked list plus calibrated confidence, a failure reason, and query provenance yields higher end-to-end answer accuracy per token spent than one returning a bare ranked list, because the orchestrator can escalate or reformulate instead of accepting a bad retrieval silently.

Proof of concept

Implement two search subagents over one identical backend with two return contracts; wire both behind the same orchestrator on a fixed question set; sweep a token budget and record accuracy, token spend, and escalation rate for each contract.

Measurement

End-to-end answer accuracy at matched total token spend, plus the rate of correct escalations on adversarial queries where the correct document is absent from the corpus.

Source video ↗

Reward-proxy divergence probe

beyond-evals

Retrieval policies trained on binary correct-document labels overfit the labeling convention rather than user-perceived quality, producing measurably different search behavior under graded relevance than binary relevance at matched training compute.

Proof of concept

Build one eval set with graded relevance and derive a binary version from it; train otherwise identical retrieval policies against each reward; evaluate both against a held-out graded judgment and a small human preference sample.

Measurement

Divergence between policy-ranked and human-preferred orderings on multi-relevant and partially-relevant queries, plus recall@k on each reward's own convention versus the other's.

Source video ↗

RL-candidacy screen benchmark

new

Across a set of agent subtasks, the conjunction of reward verifiability and rollout throughput predicts which subtasks benefit from a trained policy over a hand-engineered pipeline, and subtasks failing either condition show no improvement from RL at any practical compute budget.

Proof of concept

Select four subtasks spanning the 2x2 of verifiable/unverifiable and grindable/low-throughput (retrieval, code execution, tool routing, open-ended browsing); implement a strong scripted pipeline and a policy trained with RL for each; compare at matched spend.

Measurement

Delta in task success between the trained policy and the strongest scripted baseline, plotted against rollout throughput and reward-label noise for each subtask.

Source video ↗

Adaptive-compute retrieval router with a millisecond floor

movement-lab

Routing queries by predicted difficulty to either a dynamic-compute search policy or a fixed-compute ANN fallback lowers tail latency and cost per question versus running the adaptive policy for every query, while preserving its accuracy gains on hard queries.

Proof of concept

Train a lightweight difficulty predictor from query features; route the easy quantile to a fixed ANN path and the rest to the iterate-and-adjust policy; measure per-query cost, p95 latency, and recall against an all-adaptive and an all-fixed baseline.

Measurement

p95 latency and mean cost per question at matched recall, plus the share of correct results that would have been lost by the fixed path alone.

Architectural implications

3

The main agent should not own the search loop; it should call a subagent that owns iteration and returns a ranked list.

Before

Main agent issues queries, reads raw results, retries on failure, and accumulates every attempt in its own context window.

After

Main agent calls a search subagent with a question; the subagent iterates against the backend and returns a ranked list plus a clean result.

Consequence

Lower token cost per question and less context pollution, at the cost of the main agent losing visibility into why a search failed.

Source video ↗

Retrieval primitives are demoted from architecture to tools; the orchestration policy becomes a trained artifact.

Before

LLM query rewrite -> search backend -> reranker, wired as a fixed multi-step chain with a fixed compute budget per query.

After

A single RL model that calls BM25/ANN/tool-call primitives, reads results, applies metadata filters, and iterates, with compute allocated per question.

Consequence

The same BM25/ANN infrastructure is retained but the value migrates to the training environment and reward function, which become the code that must be maintained.

Source video ↗

Model selection becomes a per-subtask routing decision rather than a global choice.

Before

One frontier model performs reasoning, retrieval, and synthesis, with retrieval as one more tool call.

After

Frontier model orchestrates; a specialized model (e.g., SID-1) handles retrieval at roughly 100x lower cost and 20x lower latency.

Consequence

System design gains a cost-tier abstraction: cheap specialists for high-volume narrow subtasks, expensive generalists for open-ended reasoning.
