Summary

Overview

  • Speaker: Giselle van Dongen
  • Channel: AI Engineer
  • Main topic: Running AI agents reliably in production using durable execution infrastructure (Restate)
  • Purpose: To introduce Restate as a flexible, durable foundation and runtime for building reliable, long-running, stateful AI agent workflows. Giselle van Dongen discusses how to run AI agents reliably in production, focusing on the infrastructure layer rather than e-files. She traces the evolution of LLM usage through three waves (websites, app downloads, and persistent/asynchronous long-running entities with org-wide tools). She introduces Restate, an open-source framework inspired by Apache Flink and Meta's core event infra, designed to turn normal functions into durable, stateful entities. The talk includes a demo of a Slack research agent built using Restate, showing durable execution, retry logic, concurrency control, human-in-the-loop suspension, and steering/cancellation.

Topic Map

The Evolution of LLM and Agent UX

  • Explanation: Andrej Karpathy's three waves of LLM interaction: (1) LLM as a website you go to, (2) LLM as an app you download with tools, (3) persistent, asynchronous entities with org-wide tools and context.
  • Key claims:
    • Interaction with LLMs is shifting toward self-contained, persistent, asynchronous entities.
    • Infrastructure layer must evolve to support long-running, stateful agent processes.
  • Examples:
    • Chatbots (wave 1), standalone apps (wave 2), long-running enterprise agents (wave 3).
  • Terminology:
    • LLM UX waves
    • persistent asynchronous entity

The Infrastructure Requirements for Complex Agents

  • Explanation: Agent SDKs and memory are great for POCs, but complex multi-agent systems require retry logic, checkpoints, cron jobs, session locking, queues, and KV stores.
  • Key claims:
    • Agent SDKs do not solve distributed coordination and resilience across an organization.
    • Deploying extra infrastructure for retry and recovery logic is complex and error-prone.
  • Examples:
    • Queues, KV stores, retries, checkpoints, cron jobs, session locks.
  • Terminology:

Introduction to Restate

  • Explanation: Restate is an open-source framework by Apache Flink creators and Meta event infra ex-architects providing a durable runtime for agents.
  • Key claims:
    • Restate turns normal functions into long-running, durable, stateful entities.
    • Provides durable execution, state and session coordination, communication and flow control, and observability.
  • Examples:
    • Restate server sitting in front of agent service as a proxy/message broker.
  • Terminology:
    • Restate

  • Why it matters: Provides a unified developer experience for handling retries, state, and concurrency without custom infrastructure code.

Key Points

Shift toward persistent, asynchronous agents

  • Explanation: Agents are no longer just request-response query tools; they run as long-lived distributed processes interacting with organizational tools.
  • Evidence: Karpathy's tweet on LLM UX evolution.
  • Practical implication: Backends must support long-running, stateful processes with robust error handling.

Durable execution eliminates boilerplate recovery logic

  • Explanation: Instead of manually writing retry, checkpointing, and recovery state machines, durable runtimes record a journal of execution steps.
  • Evidence: Restate journal tracking tool calls and LLM requests.
  • Practical implication: Developers can write standard sequential code that automatically recovers from failures at the exact point of interruption.

Human-in-the-loop via durable promises/suspension

  • Explanation: Long-running tasks requiring human approval can suspend execution without consuming server compute resources.
  • Evidence: Waiting for Slack button click in Python handler.
  • Practical implication: Enables robust workflows spanning days or weeks without state loss or resource drain.

Push model and event-driven distributed logs

  • Explanation: Inspired by Meta's event infra, Restate uses a push model with a distributed log, achieving low latency (p99 ~45ms for 10 steps).
  • Evidence: Architecture slide showing ingress, event loop, and processor.
  • Practical implication: Provides high availability and low latency with simple binary operations and no external dependencies.

[M]Mechanismmedium noveltymoderate evidence

Durable execution replaces hand-built recovery machinery: the runtime records a journal of execution steps so developers write plain sequential code and recover at the exact interruption point, rather than authoring retry/checkpoint state machines.

Why it matters

The recovery state machine is the most error-prone and least differentiated part of a production agent backend; moving it into the runtime changes what code an agent engineer has to write and test.

Generalization

Any multi-step orchestration involving non-idempotent external calls (LLM APIs, tool/API calls) can externalize recovery to a journaling runtime instead of encoding it in application logic.

Deep dives

4

Journal contents and replay-safe side effects for non-deterministic agent steps

Research question

What exactly is journaled for an LLM call and a tool call, and does replay suppress or duplicate non-idempotent side effects when failure occurs mid-step?

Why

If journals only replay control flow, agent code must still isolate side effects; if they capture responses, recovery can skip re-invoking non-deterministic LLMs and tools. This determines whether durable execution is a drop-in reliability layer or a programming discipline.

Source video ↗

Session-keyed virtual objects as concurrency control for per-conversation agent state

Research question

Do virtual-object handlers serialize all invocations for a session ID, including queued turns during replay and recovery, and what happens to concurrent requests when an entity is recovering?

Why

Session locking and per-session KV are usually bolted on with databases and locks; if the runtime guarantees serialization by key, agent teams can delete a class of coordination code, but only if queued invocations survive recovery without interleaving.

Cost and signal semantics of durable suspension for human approval

Research question

What is the sustained runtime-side cost per suspended workflow, and what delivery semantics does an external approval signal get when it arrives during replay or after a timeout?

Why

Approval-gated agents are only economical if idle wall-clock time is genuinely free. The answer changes whether teams can park workflows for days without holding workers, and whether they must still build signal deduplication and timeout handling themselves.

Article ideas

4

The Agent SDK Is Not the Orchestrator

Production reliability is not a prompting or tool-abstraction problem; agent SDKs leave retry, checkpoints, cron, session locking, queues, and KV to the application, so teams should treat coordination as a separate runtime layer rather than rebuilding it per project.

Angle

Audit the boundary between agent SDK responsibilities and distributed-systems primitives, using the concrete checklist of missing coordination features.

Source video ↗

Durable Suspension Makes Human-in-the-Loop Economical

Approval-gated agents should park as durable promises, not held workers or polling loops; this turns wall-clock duration into a non-cost and makes days-long workflows practical, at the price of needing reliable signal delivery.

Angle

Compare held-worker, polling, and durable-suspension designs for approval workflows and argue that the real design constraint shifts to signal recording and replay.

Source video ↗

The Journal Is the Contract: What Replay Forces You to Design

Durable execution does not eliminate failure handling; it relocates it into a journal contract. Agent steps must be written so that replay can distinguish control-flow recovery from external side effects, or recovery will duplicate or diverge.

Angle

Treat journaling as an API contract for agent steps and show which design choices become explicit once replay is the recovery model.

Source video ↗

Durability Without the Latency Tax Is a Benchmark Claim, Not a Property

A p99 figure for a 10-step workload does not establish that durable orchestration is cheap for interactive agents; the claim must be tested under fan-out, long journals, and recovery before it changes architecture decisions.

Angle

Interrogate the latency claim by scoping what the benchmark does and does not cover, then propose the stress conditions that matter for agent runtimes.

Architectural implications

3

A durable runtime sits in front of the agent service as a proxy/message broker, handling ingress, invocation dispatch, and event streaming.

Before

Agent service owns its own request handling, retry loops, queues, and state store, each wired per project.

After

Runtime owns ingress, journaling, retries, flow control, and state; agent code is a set of plain functions invoked by the runtime.

Consequence

The runtime becomes a critical-path dependency and the source of truth for execution history; agent code must be written to be replayable.

Source video ↗

Coordination and resilience move out of the application and into infrastructure primitives (virtual objects, journals, durable promises).

Before

Session locks, cron jobs, and KV stores are provisioned and glued together by the application team.

After

These become first-class runtime abstractions keyed by session/entity ID.

Consequence

Fewer bespoke moving parts, but tighter coupling to a specific runtime's programming model and migration cost if it is replaced.

Source video ↗

Human approval gates become suspension points instead of held-open processes or polling loops.

Before

Workflow holds a worker or polls a database waiting for a human response.

After

Execution suspends at zero compute and resumes on signal delivery.

Consequence

Approval-gated agents become economically viable over long horizons; the design constraint shifts to reliably delivering and durably recording the external signal.

Tradeoffs and failure modes

4

Durable runtime as proxy in the critical path

Benefit

Retries, recovery, flow control, and state coordination are handled without application code.

Cost or risk

An additional hop and an additional stateful system must be operated and kept available; the agent service's availability becomes coupled to the runtime.

Source video ↗

Journal replay as recovery mechanism

Benefit

Resume from the exact point of interruption rather than restarting the workflow.

Cost or risk

Correctness depends on replaying recorded steps faithfully, so side effects outside the journal can be duplicated or diverge on recovery.

Source video ↗

Latency claims for durable orchestration

Benefit

Reported p99 ~45ms for 10 steps, positioned as low-latency and dependency-free.

Cost or risk

The figure is scoped to a 10-step workload; behavior under parallel sub-agent fan-out, long-running sessions, or large journals is not characterized.

Source video ↗

Leaving stateless serverless behind

Benefit

Enables long-running, stateful, org-tool-connected agents.

Cost or risk

Lost elasticity and simple failure semantics of stateless functions; requires operating long-lived, state-bearing entities.
