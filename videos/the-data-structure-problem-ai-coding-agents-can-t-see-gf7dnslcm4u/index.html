Summary

Overview

  • Speaker: Avery Townsend, Dexter Horthy, Vaibhav Gupta, Kyle Mistele
  • Channel: Boundary
  • Main topic: How bad data structures compound failure rates in AI-generated code and agent-driven development.
  • Purpose: To demonstrate that AI coding agents struggle with data structure design, how poor data representations compound failures over multiple development steps, and why reviewing and designing clean data structures is critical for preventing code slop in agentic systems. The speakers discuss an experiment testing how frontier AI coding models (like GPT-5.6-sol on high reasoning effort) handle building a simple application (Ticketmaster box office) feature-by-feature when each agent starts from scratch without prior agent context. The results demonstrate that bad data structures exponentially increase error rates and compounding complexity for AI agents, whereas well-chosen data structures (e.g., using enums and BTreeMaps to make illegal states unrepresentable) lead to self-evident, robust code.

Key Points

All slop starts as bad data structures

  • Explanation: When data structures are poorly designed, program logic, error handling, and state validations multiply exponentially, leading to brittle code.
  • Evidence: Experiment data showing 12.5% to 42.5% invalid state representations produced by frontier AI models.
  • Practical implication: Developers and reviewers must focus heavily on data structure design during code review rather than just control flow.

Agents lack historical context across iterative builds

  • Explanation: When AI agents build software iteratively from scratch without seeing prior agent evolution, they fall back on convenient but non-optimal data structures.
  • Evidence: The 200-run experiment on Ticketmaster features where codebases were passed forward without git history.
  • Practical implication: Prompting or guiding agents toward robust type systems is necessary to maintain codebase health.

Compounding failure rates in software factories

  • Explanation: A small 10-12% failure rate per feature compounds rapidly over dozens or hundreds of shipped features, eventually destroying the codebase.
  • Evidence: Dexter Horthy's mathematical explanation of compounding error rates across software factories.
  • Practical implication: Automated guardrails and strict data structure reviews are vital for AI-assisted engineering pipelines.

Frameworks, Models & Processes

Enum-Based State Representation

  • How it works: Using algebraic data types (enums) instead of multiple boolean flags to represent state, ensuring mutually exclusive states and preventing invalid combinations at the type level.
  • Components:
    • Enum definition (e.g., Open, Held, Sold)
    • State transition matcher (match state, event)
    • Exclusive payload binding
  • When to use: When managing business objects or entities that transition between distinct, mutually exclusive operational states.

Sync Engine Architecture

  • How it works: Placing a sync engine in front of a relational database (like Postgres) to handle optimistic mutations, streaming state updates, and caching for multiple clients.
  • Components:
    • Postgres database with write-ahead log
    • Sync Engine / Cache Layer
    • Authorization Proxy
    • Durable Streams Server
    • Client sync bindings
  • When to use: When building real-time collaborative applications with multiple disconnected clients requiring fast reads and resilient state sync.

Core insights

[E]Empirical Resulthigh noveltymoderate evidence

Per-feature failure rates that look tolerable in isolation (10-12.5%) compound exponentially across a long feature sequence, so an agent pipeline can be mathematically doomed even when each individual agent run is 'mostly right'. The argument is that unrecoverability comes from accumulation, not from any single bad generation.

Why it matters

Sets the reliability bar for agentic software factories: per-step success rate is the wrong metric; the metric that matters is error rate vs. the number of steps before the codebase degrades past repair. It implies hard gates (data structure review) must sit inside the pipeline, not after it.

Generalization

Any multi-step generative pipeline (code, config, migrations, schemas, infra) with a non-trivial per-step defect rate will degrade super-linearly with step count, so step-level evals must be converted into sequence-level survival curves.

[M]Mechanismmedium noveltystrong evidence

The highest-leverage control point for agent-written code is the data representation, not the control flow: substituting an enum (Open/Held/Sold) for multiple boolean flags (held, sold) removes illegal states at the type level and collapses the number of code sites touched when a new state is introduced. Representational choice determines how many places an agent must edit correctly per feature.

Why it matters

Gives a concrete, reviewable intervention: when reviewing agent output, inspect the state model first. A representation that admits invalid combinations forces every downstream feature and every future agent to add validation and error handling, multiplying edit surface and defect probability.

Generalization

Blast radius of a change is a function of representation: types that make illegal states unrepresentable convert N-site edits into a single exhaustive-match change, which is disproportionately valuable when the editor is a stateless agent.

[O]Mental Modelmedium noveltymoderate evidence

'Fold knowledge into data, so program logic can be stupid and robust' reframes design effort as relocating complexity out of procedural logic and into the type/schema layer — a mental model that maps directly onto agents, which are more reliable at writing simple logic over a strong representation than at maintaining implicit invariants across many branches.

Why it matters

Explains why prompting agents toward 'cleaner code' is less effective than changing the data model they must code against; the agent's error budget is spent on branch and invariant bookkeeping.

Generalization

In any generation-or-handoff setting, push invariants into declarative artifacts (types, schemas, constraints) that are cheap to check mechanically, rather than into procedural code that must be reasoned about each time.

[A]Architecturemedium noveltymoderate evidence

Sync engine design decouples storage from streaming: a sync layer sits in front of Postgres, behaves as a read replica with optimistic mutations, and fans state out to clients via a durable streams server behind an authorization proxy, with local SQLite on clients and WAL-based replication as the change source.

Why it matters

Illustrates why data-representation discipline scales into distributed systems: separating the authoritative log from the streaming/projection layer is what makes high write volume plus many syncing clients tractable, and the authorization proxy keeps per-client visibility out of the storage layer.

Generalization

For real-time multi-client state, split the durable authority (WAL/append-only log) from the fan-out path (streams/WebSockets) and place policy (authorization) at the boundary between them rather than inside the store.

[P]Practicemedium noveltymoderate evidence

Because agents cannot see a codebase's evolution, reviewing their output with the same lens as human code (behavior and control flow) misses the failure that actually compounds; the review gate should be aimed at data structure and state model design first.

Why it matters

Changes where human or automated review budget is spent in agentic pipelines, and suggests a checkable pre-merge criterion (e.g., forbid multi-boolean state encodings, require exhaustive matching over enums).

Generalization

Review effort should be allocated to the artifacts with the largest downstream blast radius; in agent-generated code that is the schema/type layer, not individual functions.

4

Per-Step Success Rate Is the Wrong Metric for Agentic Pipelines

A pipeline whose individual agent runs are 'mostly right' can still be mathematically doomed, because the metric that governs whether a codebase survives is the error rate relative to the number of steps before degradation passes repair — not the per-step pass rate. Teams shipping agent-generated features must convert step-level evals into sequence-level survival curves before scaling iteration count.

Angle

Reframe reliability reporting: replace per-run benchmarks with survival curves and break-even feature counts, and show why a 12.5% step success gap is not a 12.5% problem.

Source video ↗

Stop Reviewing the Diff, Start Reviewing the State Model

Because a fresh agent cannot see how the codebase evolved, reviewing its output the way we review human code — behavior and control flow — inspects the wrong artifact. The failure that compounds lives one level up in the data representation, so review budget should be reallocated to the schema and state model first, with checkable pre-merge criteria such as forbidding multi-boolean state encodings and requiring exhaustive matching.

Angle

Operational: propose concrete review-gate rules and explain why they are cheap to check and high in downstream blast radius.

Source video ↗

Fold Knowledge Into Data: Why Prompting Agents for Cleaner Code Fails

Instructing agents to write cleaner code spends their error budget on branch and invariant bookkeeping; changing the representation they code against spends almost none. Pushing invariants into declarative artifacts that are cheap to check mechanically — types, schemas, constraints — makes program logic stupid and robust, which is exactly the property a stateless generator needs.

Angle

Mechanism-first argument connecting representation choice to blast radius, with the boolean-flag vs enum example as the minimal demonstration.

Source video ↗

The Handoff Artifact Is an Architecture Decision

What one agent passes to the next is not plumbing but design: code-only handoff optimizes for reproducibility and context hygiene while discarding design intent, and that trade has a measurable downstream cost. Treating the handoff artifact — code, code plus history, or code plus design contracts — as a first-class architectural component is the precondition for making per-feature defect rates roughly constant instead of compounding.

Representation Gate

gatehouse

Inserting an automated representation gate (rejecting multi-boolean state encodings, requiring exhaustive state matching) before feature generation or merge keeps per-feature invalid-state rate roughly constant instead of letting it compound across a long feature sequence.

Proof of concept

Wrap a fresh-agent feature pipeline with a pre-merge checker that parses the state model, flags mutually non-exclusive boolean state fields, and requires exhaustive handling when a new variant is added; A/B the same feature sequence with the gate off and on.

Measurement

Invalid-state representations per feature and edit sites touched per new state, with and without the gate, plus the fitted slope of defect accumulation versus feature index.

Architectural implications

3

Data structure design becomes an explicit enforcement point rather than an emergent outcome of code review.

Before

Agents generate features end-to-end; quality is judged by whether the feature works, and state representation is an implicit artifact of each generation.

After

A representation/schema gate precedes feature generation (or blocks merge): state models must use exhaustive, mutually exclusive encodings, and boolean-flag state encodings are rejected.

Consequence

Shifts the bottleneck from reviewing generated code volume to reviewing a small, high-leverage type/schema surface, and makes defect rate per feature roughly constant rather than compounding.

Source video ↗

The agent handoff artifact is a design decision with measurable downstream effects.

Before

Only the raw code base is passed between agents; prior reasoning, design intent, and history are discarded.

After

Code plus persistent design contracts (state models, invariants, ADRs) travel with the repository as the handoff unit.

Consequence

Reduces the chance that each fresh agent re-derives a convenient-but-wrong representation, at the cost of maintaining a contract artifact that must itself stay in sync with the code.

Source video ↗

In sync backends, the storage engine is no longer the client-facing surface.

Before

Clients talk to the database (or to an API that directly proxies the database) and consistency/broadcast concerns mix with persistence.

After

A sync engine in front of Postgres acts as read replica with optimistic mutations, with a durable streams server and authorization proxy mediating client sync.

Consequence

Storage and streaming can be scaled and failed independently, but conflict resolution and per-client authorization become first-class components that need their own correctness arguments.

Tradeoffs and failure modes

3

Boolean-flag state encoding vs. enum/tagged-union state

Benefit

Boolean flags are the locally convenient choice and are easy to generate incrementally as new attributes appear.

Cost or risk

They admit illegal states (both flags true) and multiply the number of code sites touched when a state is added or changed, raising the per-feature failure rate for every subsequent agent.

Source video ↗

Stateless fresh-agent iteration (code-only handoff)

Benefit

Avoids context rot and stale assumptions; simulates real team handoffs and keeps each run reproducible across 200 iterations.

Cost or risk

Without visibility into prior design evolution, agents fall back on convenient designs and produce invalid state representations at 12.5% to 42.5%, letting defects compound.

Source video ↗

Optimistic mutations in a sync engine

Benefit

Clients can apply writes immediately, keeping real-time UI responsive without waiting for round trips.

Cost or risk

Managing high write volume and many syncing clients forces careful decoupling of storage and streaming, and makes reconciliation/conflict handling an ongoing correctness burden.
