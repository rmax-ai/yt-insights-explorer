Summary

Overview

  • Speaker: Ankit Jain
  • Channel: AI Engineer
  • Main topic: Re-engineering code review processes in the era of AI-generated code by moving alignment upstream and automating semantic verification.
  • Purpose: To propose a new paradigm for code review and verification where AI handles generation and initial testing, humans review intent and architecture rather than line-by-line diffs, and recurring feedback is codified into automated guards. Ankit Jain, co-founder of Aviator, explores why traditional line-by-line human code reviews are failing as code volume increases exponentially due to AI agents. Presenting a four-part thesis, he argues that code reviews are fundamentally about alignment and knowledge sharing rather than just diff verification. He introduces 'Spec-Driven' and 'Intent-Driven' development frameworks, the AI Slop Register concept to codify recurring review comments into automated checks, and a verification system combining deterministic checks with runtime LLM judges to ensure high semantic accuracy without manual bottlenecking.

Topic Map

The Problem with Code Review Today

  • Explanation: With code volume increasing rapidly due to AI, traditional line-by-line code reviews have become a major bottleneck. Metrics show massive code churn, increased incident-to-PR ratios, and longer median review times, leading teams to bypass reviews or merge code without proper scrutiny.
  • Key claims:
    • Code volume and code churn are increasing exponentially, causing severe bottlenecks in code review.
    • Traditional line-by-line reviews are no longer effective, with incident-to-PR ratios and median review times increasing.
    • Over 30 percent of code changes are being merged today without any review at all.
  • Examples:
    • Metrics cited from Accelerate/Atlassian reports showing +861% code churn, +243% incidents-to-PR ratio, and +441% median time in review.
  • Terminology:
    • Code churn
    • Incidents-to-PR ratio
    • Medium time in review
  • Why it matters: It proves that human-driven line-by-line code review does not scale in the AI era and creates a massive bottleneck for engineering velocity.

Alignment vs. Semantic Accuracy

  • Explanation: Code review is historically about two things: semantic accuracy (catching bugs, conventions, security issues) and alignment (knowledge sharing, mentorship, architectural feedback, onboarding). AI can assist with semantic accuracy, but human alignment must survive upstream.
  • Key claims:
    • Code review is not just about code review; a large part of it is alignment, knowledge sharing, mentorship, and architectural feedback.
    • Semantic accuracy needs better tooling, but human alignment must survive.
  • Examples:
    • Contrasting solo coding projects where zero alignment is needed against team-based collaborative coding where knowledge sharing is vital.
  • Terminology:
    • Semantic accuracy
    • Alignment
    • Knowledge sharing
  • Why it matters: Recognizing that reviews serve an alignment and cultural purpose prevents teams from blindly trusting AI-generated code without team consensus.

Flaws in Spec-Driven Development

  • Explanation: Spec-driven development resembles waterfall methodology from the 1970s because it lacks a feedback loop: specs are written before the work teaches the author anything, leading to spec drift when implementation surfaces decisions the spec never anticipated.
  • Key claims:
    • Spec-driven development is waterfall in new clothes because there is no feedback loop.
    • LLMs are non-deterministic, so static specs fail to capture everything during implementation.
  • Examples:
    • Comparing 1970s waterfall models (Requirements -> Design -> Implementation -> Verification) with modern spec-driven AI development.
  • Terminology:
    • Spec-driven development
    • Waterfall
    • Specs drift
  • Why it matters: Highlighting why pure spec-driven AI generation falls short when encountering non-deterministic AI decisions.

Intent-Driven Development and the AI Slop Register

  • Explanation: Intent lives in Jira tickets, PRDs, and most importantly, interactive prompts where real decisions are made. The AI Slop Register captures recurring review comments and codifies them into automated guards so developers do not have to repeat the same review feedback manually.
  • Key claims:
    • Intent does not only live in a spec; it lives in Jira tickets, design docs, and prompts.
    • The AI Slop Register automatically compiles recurring code review comments into automated checks that run on every pull request.
  • Examples:
    • Using Aviator verify platform to codify reviewer comments into invariants like 'Use the Money type for currency amounts, not float'.
  • Terminology:
    • Intent-driven development
    • AI Slop Register
    • Invariants
  • Why it matters: It turns tribal knowledge and repetitive code review feedback into reusable, automated guardrails.

The New Verification System: Two Halves, One Loop

  • Explanation: Combining intent capture and semantic verification into a single loop. Sessions become acceptance criteria, criteria plus invariants create test plans, and preview environments run automated checks so reviewers review intent and evidence rather than raw diffs.
  • Key claims:
    • The session becomes the criteria, converting user responses into acceptance criteria and test plans.
    • Reviewers no longer review diffs line-by-line; they review intent, architecture, and verification evidence.
  • Examples:
    • A workflow showing Capture (Session -> Acceptance criteria), Build (AI Slop Register -> Test plan), Run (Preview env -> Results), and Review (Reviewer checks intent, not diff).
  • Terminology:
    • Acceptance criteria
    • Test plan
    • Preview environment
    • Deterministic check
    • LLM judge
  • Why it matters: It shifts the human reviewer's role from reading raw code lines to evaluating test evidence against stated intent.

Key Points

Traditional code review is broken at scale

  • Explanation: With 861% higher code churn and increasing incident rates, manual line-by-line review is a bottleneck that fails to keep up with AI-generated code productivity.
  • Evidence: Data from Accelerate and Atlassian reports showing surging PR volumes and review times.
  • Practical implication: Engineering teams must stop relying solely on manual line-by-line code reviews for AI-generated code.

Code review is primarily about alignment, not just inspection

  • Explanation: Reviews serve as knowledge sharing, architectural guidance, mentorship, and team alignment rather than just catching syntax errors.
  • Evidence: Comparison of solo coding versus team collaboration workflows.
  • Practical implication: New AI review tools must preserve human collaboration and architectural alignment.

Spec-driven development lacks feedback loops

  • Explanation: Writing specs upfront without iterative feedback leads to spec drift because LLM implementations encounter unforeseen edge cases.
  • Evidence: Parallels drawn with 1970s waterfall methodology.
  • Practical implication: Intent must be captured dynamically from prompts and interactive sessions during development.

The AI Slop Register automates recurring feedback

  • Explanation: Codifying repeated review comments into automated rules ensures the same mistakes are never manually reviewed twice.
  • Evidence: Aviator's verify platform feature demo showing automated invariant checks.
  • Practical implication: Engineers should mine past review comments to build automated guardrails.

Balance deterministic checks with LLM judges

  • Explanation: Use deterministic checks where possible (assertions, status codes) and LLM runtime judges where necessary (screenshots, fuzzy semantics).
  • Evidence: Framework distinguishing between deterministic code verification and AI-powered runtime evaluation.
  • Practical implication: The AI model acts as a tool inside the harness, never as the sole judge of record.

The 'AI Slop Register' closes the loop from human review to automation: recurring code review comments are compiled into durable, machine-checkable invariants that execute on every pull request, so the same feedback is never given twice.

Why it matters

Generalization

Any recurrent human judgment applied to agent output (style rules, schema constraints, domain invariants) should be promoted from a comment into a versioned, executable guard that runs automatically thereafter.

Why

Article ideas

4

Your Review Comments Are Bugs in Your CI Config

Every recurring human review comment is an unencoded invariant, and the correct response to repeated feedback is not a firmer comment but a compiled, versioned, executable guard; teams that treat review feedback as ephemeral attention will watch review cost scale linearly with AI-generated PR volume while teams that treat it as a rule artifact do not.

Angle

Argue for review feedback as a compilable engineering deliverable, then confront the uncomfortable part: an invariant registry needs ownership, conflict detection, and deprecation, and an unowned registry becomes a false-positive generator that developers route around.

Source video ↗

Kill the Diff, Not the Reviewer

Code review is two functions wearing one name, and only semantic accuracy is a legitimate automation target; the alignment function must be deliberately re-sited upstream rather than assumed to survive, because the summary's claim that alignment 'must survive' specifies no mechanism for it.

Angle

Decompose review into verification versus socialization, show what each automation strategy deletes, and specify the human checkpoint that replaces the diff rather than promising AI review wholesale.

Source video ↗

Spec-Driven Development Is Waterfall in New Clothes

Front-loading a static spec onto a non-deterministic generator reproduces the waterfall failure mode because the work itself is the primary source of new information; intent must be captured continuously from the session, making the spec a derived output rather than an authoritative input.

Angle

Take the counter-position against the dominant write-a-spec-then-generate pattern and demand measurement: how much drift is observable, and do iteratively revised specs still drift?

The 30 Percent No-Review Merge Is the Baseline, Not the Risk

Review bypass is already the de facto behavior at current volumes, not a hypothetical hazard of AI-generated code, so exhorting teams to review more carefully is a failing strategy; the gate must be redesigned rather than enforced harder, because human review gates degrade silently into rubber-stamping once submission volume exceeds processing capacity.

Angle

Use the churn, incident-to-PR, and time-in-review figures to frame automation as remediation of an existing collapse rather than a speculative bet, while flagging that the underlying data window and causal attribution remain unverified.

Project ideas

4

Invariant Registry with Conflict Detection

gatehouse

Enough natural-language review comments can be compiled into correct, non-flaky automated invariants that the compiled rule set catches recurring violations without human curation, and the registry's false-positive rate stays bounded as rules accumulate across many pull requests because automated conflict and overlap detection prunes contradictory rules.

Proof of concept

Build a registry that ingests reviewer comments, compiles candidates into executable checks (e.g., 'Use the Money type for currency amounts, not float'), runs them on a shadow corpus of historical PRs, and flags contradictory or overlapping rules for deprecation.

Measurement

Percentage of comments converted into invariants that fire correctly without hand-editing; false-positive rate as a function of registry size; number of conflicting rule pairs detected; developer override rate per PR over successive weeks.

Source video ↗

Deterministic-vs-Judge Verification Benchmark

beyond-evals

A hybrid gate of deterministic checks plus runtime LLM judges reaches precision and recall on labeled PR defects that are not materially worse than human line-by-line review, at a lower latency and cost per PR than the manual baseline, and the deterministic layer alone accounts for the majority of caught defects.

Proof of concept

Assemble a labeled corpus of historical PRs with known defects, run three configurations (deterministic only, LLM judge only, hybrid) in a preview environment, and score each on precision, recall, latency, and cost.

Measurement

Precision/recall versus human review on the same changes; verdict variance across repeated LLM-judge runs on identical inputs; marginal defects caught by the judge layer that deterministic checks miss; seconds and dollars per PR.

Source video ↗

Session-to-Criteria Extractor

movement-lab

Acceptance criteria and test plans extracted from interactive session transcripts cover edge cases as well as human-written criteria on the same task, and the residual intent loss is concentrated in a small, identifiable class of under-specified interactions rather than spread uniformly.

Proof of concept

Capture development sessions, extract structured acceptance criteria and test plans, and compare them head-to-head against criteria written by a human for the same task using defect-escape and coverage metrics.

Measurement

Defect escape rate for session-derived versus human-written criteria; coverage delta on edge cases; fraction of criteria traceable to an explicit session utterance; human-flagged mis-extractions per task.

Source video ↗

Alignment Proxy Instrumentation

new

Alignment value lost when line-by-line diff review is removed is recoverable through upstream intent review sessions, and this recovery is detectable through proxies such as onboarding time to first independent contribution and architectural drift measured against declared intent, rather than being an unmeasurable cultural good.

Proof of concept

Instrument two comparable teams, one keeping diff review and one running upstream intent review plus automated verification, and track onboarding time, architectural drift against acceptance criteria, and knowledge-distribution metrics over a quarter.

Measurement

Time-to-first-independent-contribution for new joiners; rate of architectural changes that contradict prior acceptance criteria; concentration of authorship/decision knowledge across team members; self-reported mentorship touchpoints.

Benefit

Cost or risk

Invariants abstracted from individual past comments can be over-broad, conflicting, or stale as the codebase evolves, requiring ongoing curation of the rule set.

Cost or risk
