Summary

Overview

  • Speaker: Jakub Hojsan
  • Channel: AI Engineer
  • Main topic: Building semantic search and retrieval systems for coding and review agents using Exa
  • Purpose: Explain how Exa's semantic search infrastructure solves the knowledge cutoff and context overload problems for coding and review agents. Jakub Hojsan discusses the core limitations of large language models in coding and review agents, specifically focusing on the knowledge cutoff problem where models lag behind upstream repository updates. He introduces Exa's semantic search engine designed to give agents context-rich highlights, enabling agents to handle breaking dependency and version changes accurately. The presentation covers Exa's architecture, token-efficient highlights, cost efficiency, model standardization, and practical agent integration via MCP.

Topic Map

The Problem: Knowledge Cutoff in Coding Agents

  • Explanation: LLMs used in coding and review agents typically have a knowledge cutoff of several months, causing a gap between model training and repository release dates where breaking changes occur.
  • Key claims:
    • Models typically lag around six months from knowledge cutoff date to release date.
    • Real-world repositories experience upstream changes post-cutoff that models cannot natively review or understand.
  • Examples:
    • A cuVS Kmeans migration PR where the inertia check parameter was removed after model cutoff.
  • Terminology:
    • Knowledge cutoff
    • Launch lag
    • Model blind spot
  • Why it matters: Coding agents fail to correctly review PRs or handle dependency bumps because they are unaware of recent upstream API changes.

Why Search Is Not Enough for Agents

  • Explanation: Simply providing a web search tool or 10 blue links to an LLM does not work because models need context-aware instructions on when and how to use search.
  • Key claims:
    • LLMs do not know out-of-the-box when a version or dependency change requires checking upstream sources.
    • Agents need explicit rules and triggers to invoke web search for breaking changes.
  • Examples:
    • Claude Code having access to a web search tool but failing to use it because it doesn't know a newer version exists.
  • Terminology:
    • Agantic search
    • Two-step process
    • Model rules
  • Why it matters: Giving an agent a search tool without instruction or proper API design results in the model ignoring the tool or hallucinating.

Exa Features for Models

  • Explanation: Exa provides four key benefits to models: transparency, token-efficient highlights, cost efficiency, and standardization.
  • Key claims:
    • Exa returns exact sources and queries instead of a black-box synthesis.
    • Highlights distill pages down to ~700 characters per result, saving tokens and reducing latency.
    • Pricing is significantly more effective for large workloads compared to native search providers.
    • Provides a single standardized API across any model provider.
  • Examples:
    • Exa Search API returning specific lines from documentation without dumping whole web pages into context.
  • Terminology:
    • Transparency
    • Token-efficient highlights
    • Standardization
    • Exa Search API
  • Why it matters: Reduces token usage, lowers latency, and avoids black-box retrieval limitations of standard LLM provider web search tools.

Exa Agent and Exa Connect

  • Explanation: Exa Agent and Exa Connect expand search capabilities from the open web to private and specialized data providers like Similarweb, Particle, and Crunchbase.
  • Key claims:
    • Exa Connect reaches private data providers used by financial firms and hedge funds.
    • Can orchestrate complex searches across web analytics, media intelligence, and private markets.
  • Examples:
    • Querying all attendees at the AI Engineer Conference or finding high-compute AI startup founders.
  • Terminology:
    • Exa Agent
    • Exa Connect
    • Similarweb
    • Crunchbase
    • Particle
  • Why it matters: Allows agents to retrieve structured proprietary data and real-time private market information beyond public web pages.

Key Points

Models lag behind real-world repositories

  • Explanation: Because of training cutoffs, LLMs miss recent dependency bumps and breaking API changes.
  • Evidence: Timeline comparison showing GPT-5.5, Sonnet 4.5, and Claude Opus 3 with ~6 months launch lag.
  • Practical implication: Engineers must supply external search grounding to agents reviewing pull requests.

Token-efficient search is essential

  • Explanation: Feeding entire web pages or repositories into an LLM wastes context and increases costs.
  • Evidence: Exa highlights return ~700 characters per result with zero loss in evaluation quality.
  • Practical implication: Lower latency and reduced token costs for agentic workflows.

Frameworks, Models & Processes

Exa Multi-Stage Search Architecture

  • How it works: Processes natural language queries into embeddings, applies keyword filtering and semantic search, and runs re-ranking steps to drop irrelevant results.
  • Components:
    • Query embedding
    • Keyword filtering
    • Semantic search
    • Re-ranker
    • Content retrieval
  • When to use: When indexing and querying billions of web and private documents with high precision.

Giving an agent a web-search tool is insufficient; the agent must be given explicit rules/triggers that tell it when a version or dependency change warrants consulting upstream sources, otherwise it silently ignores the tool.

Why it matters

Agents fail quietly rather than erroring: Claude Code had access to web search but did not call it because it did not know a newer version existed, producing a confident but wrong review. Tool availability is not the same as tool invocation policy.

Generalization

Any agent that must conditionally call an external service needs an explicit invocation policy (triggers, preconditions, defaults) layered on top of raw tool access, or it will not call the tool at the moments that matter.

Generalization

Architectural implications

3

Search is being pulled out of the model provider's built-in web tool and into a separate, standardized retrieval service.

Before

Rely on the LLM provider's native browsing/search tool, accepting its black-box synthesis.

After

Route agent retrieval through an independent API that returns sources, queries, and token-bounded highlights.

Consequence

Retrieval becomes a swappable, provider-agnostic infrastructure component, decoupling agent design from model vendor lock-in.

Before

Register a search tool and assume the agent will call it when needed.

After

Encode prompts/rules that trigger search on dependency and version diffs.

Consequence

Agent harnesses gain a policy layer that governs when external calls fire, becoming as important as the tools themselves.

Benefit

Cost or risk

Benefit

Cost or risk
