Summary

Overview

  • Speaker: Kamil Potrec
  • Channel: AI Engineer
  • Main topic: Agent authentication and authorization requirements, challenges, and solutions in AI engineering
  • Purpose: To educate AI engineers on the security pitfalls of agentic workflows and provide architectural patterns and solutions for robust agent authentication, delegation, and auditing. Kamil Potrec from Keycard discusses the critical challenges of agent authentication and authorization in modern AI systems. As AI agents increasingly interact with remote MCP servers, APIs, and enterprise systems, traditional software auth patterns fall short due to non-deterministic behavior, long-lived secrets, over-privileged service accounts, and complex multi-hop delegation chains. The talk explores architectural solutions such as gateways, runtime authorization, dynamic scoping, and short-lived credentials to secure agent interactions at scale.

Topic Map

Introduction and the Agentic Auth Problem

  • Explanation: Introduction of Kamil Potrec from Keycard and the core premise: how agents and users communicate, authorize, and make requests across MCP servers and APIs.
  • Key claims:
    • People discuss agents and MCP servers, but often overlook how agents and users communicate and make requests.
    • Users pass opaque credentials (PAT tokens) to agents, letting agents decide whether to perform actions.
  • Examples:
    • Alice asks her team's LangChain agent for her latest invoice.
  • Terminology:
    • Agent authentication
    • MCP server
    • PAT tokens
    • LangChain
  • Why it matters: Understanding who is making a request is fundamental to securing autonomous AI systems.

What's Wrong with the Current Picture (The Legacy Approach)

  • Explanation: Analysis of the security flaws in typical naive agent setups, including long-lived secrets, shared secrets/passthrough, and over-privileged service accounts.
  • Key claims:
    • Long-lived secrets stored in .env files sit on laptops, can be rotated manually, and lack easy revocation.
    • Shared secrets or token passthrough means the MCP server or API cannot distinguish between the user and the agent.
    • Service accounts aggregate permissions across multiple users, leading to over-privileged access.
    • Agents are non-deterministic software; when requests bounce back through the model, attribution is lost.
  • Examples:
    • Alice puts her access token on her laptop and corporate infrastructure security is lost.
    • An agent decides to send an invoice directly to a user; neither the user nor the agent can be uniquely attributed.
  • Terminology:
    • Long-lived secrets
    • Token passthrough
    • Over-privileged service accounts
    • Non-deterministic software
  • Why it matters: Relying on legacy software security assumptions for non-deterministic agents introduces massive security vulnerabilities.

The Right Way: Every Hop Knows User and Agent

  • Explanation: Introducing the correct architectural pattern where runtime auth issues scoped, short-lived tokens on every hop, maintaining verifiable identity and audit trails.
  • Key claims:
    • Every hop must know both the user and the agent.
    • Instead of Alice fetching long-lived tokens, agents advertise how to get access and runtime auth issues short-lived user tokens.
    • OAuth-based token exchange allows token scoping limited to the specific tool being used.
    • Workload identity federation, private key auth, certificates, or URL-based auth can be used.
  • Examples:
    • OAuth token exchange where the MCP server exchanges tokens again for a scope limited to Alice's invoices without storing a secret.
  • Terminology:
    • Runtime Auth
    • Workload identity federation
    • Short-lived user token
    • Token exchange
    • OAuth
  • Why it matters: Proper agent auth requires separating agent identity, delegation semantics, scoped credentials, and audit logging.

The Problem at Scale: Hundreds of APIs and Agents

  • Explanation: Examining how complexity explodes when scaling agentic applications across hundreds of resources, auth servers, and agent types.
  • Key claims:
    • It is never one API; there are hundreds of APIs with distinct auth models.
    • Every resource sits behind its own authorization server, most of which do not support dynamic registration.
    • Every team builds its own agents and nobody manages their auth.
    • MCP servers and A2A hops introduce multi-hop delegation flows where every hop is a new client and new resource.
  • Examples:
    • 100+ authorization servers, 100+ resources, and 100+ agents built by different teams.
  • Terminology:
    • Mixed auth
    • Authorization servers
    • A2A hops
    • Delegation flow
  • Why it matters: At enterprise scale, ad-hoc authentication breaks down completely.

What an Agent Auth System Needs to Deliver

  • Explanation: A comprehensive checklist of capabilities required for a robust agent authentication and authorization system.
  • Key claims:
      1. Agent identity: A distinct identity per agent or session, separate from the launcher.
      1. Delegation: Verifiable record that user X authorized agent Y to do Z.
      1. Scoped, short-lived credentials: Limited to tools, resources, and time windows with no master key.
      1. Federation: Trust identities across authorization servers without new clients at each integration point.
      1. Brokering: Hold credentials, cache them, and hand out scoped access instead of legacy tokens.
      1. Policy and approval: Define what runs automatically vs what needs human approval.
      1. Audit: Track what the agent did, under whose authority, and why.
  • Examples:
    • Writing policies defining which actions require human approval and which run automatically.
  • Terminology:
    • Agent identity
    • Delegation semantics
    • Federation
    • Brokering
    • Policy and approval
    • Audit trail
  • Why it matters: Defines the exact architectural requirements engineers must fulfill to build secure agent systems.

One Hop, Up Close: The Mechanics of a Secure Call

  • Explanation: Step-by-step walkthrough of a secure interaction between a client, agent, MCP server, runtime auth, and downstream API.
  • Key claims:
    • Step 1: Agent calls, gets 401, discovers AS.
    • Step 2: Registers as client and signs Alice with PKCE.
    • Step 3: Proves own identity with workload identity, gets token for audience.
    • Step 4: Calls MCP server with token; server validates signature, issuer, expiry, and token binding.
    • Step 5: Server SDK enforces local policy and authenticates locally.
    • Step 6: For invoices API, exchanges for scoped downstream token instead of stored secret.
  • Examples:
    • Using PKCE, workload identity, and token binding across client-server interactions.
  • Terminology:
    • PKCE
    • Token binding
    • Runtime Auth
    • Policy enforcement point
  • Why it matters: Demonstrates the rigorous cryptographic and protocol steps required for a single secure tool call.

SDKs at Scale vs Gateways

  • Explanation: Comparing the challenges of relying solely on SDKs versus utilizing runtime authorization gateways for agents.
  • Key claims:
    • SDK challenges: every team must adopt them, every language needs a port, off-the-shelf agents cannot be embedded everywhere, patches become migrations, and credentials stay in agent memory.
    • Gateways (Runtime Auth + Vault): move keys outside the agent's reach, provide instant revocation, attenuate on every request, and maintain a single audit trail without changing downstream services.
  • Examples:
    • Using a gateway to intercept agent requests and inject ephemeral credentials on the way out.
  • Terminology:
    • SDKs
    • Gateways
    • Runtime Auth
    • Vault
    • Attenuation
    • Revocation
  • Why it matters: Gateways solve the credential leakage and scale problem much more effectively than scattering auth logic across SDKs.

Key Points

Agents are non-deterministic software

  • Explanation: Unlike traditional software that follows rigid code paths, LLM-based agents make autonomous choices about tool calls, making deterministic auth tracking difficult.
  • Evidence: When requests loop back through models and agents decide to send data, traditional static permission models fail to attribute intent.
  • Practical implication: Security controls cannot rely on the agent to police itself; runtime authorization and gateways are required.

Every hop must know the user and the agent

  • Explanation: In multi-hop agent architectures (User -> Agent -> MCP Server -> Downstream API), identity and context must be preserved at every layer.
  • Evidence: Passing long-lived user PAT tokens directly to agents results in loss of corporate infrastructure boundaries.
  • Practical implication: Implement token exchange and workload identity federation so each hop validates both parties.

Move keys outside the agent's reach

  • Explanation: Storing API keys or long-lived credentials inside agent execution environments allows compromised agents or malicious prompts to exfiltrate secrets.
  • Evidence: If an agent has direct access to .env files or static keys, it can abuse them across its full execution scope.
  • Practical implication: Use gateways and runtime auth servers to store keys and inject short-lived, scoped credentials dynamically on outgoing requests.

Frameworks, Models & Processes

Keycard Agent Auth Architecture

  • How it works: Combines client SDKs, runtime authorization servers, gateways, and policy engines to manage identity, delegation, brokering, and auditing for AI agents.
  • Components:
    • Client SDK (discovery, PKCE sign-in, workload identity)
    • Runtime Auth / Vault (issuing scoped short-lived tokens, policy enforcement)
    • Gateway (intercepting calls, injecting ephemeral credentials, attenuation)
    • Audit Trail (logging every request with user and agent identity)
  • When to use: When deploying multi-agent or LLM tool-calling systems that interact with external corporate APIs and require enterprise-grade security.

Actionable Takeaways

  • Immediate:

    • Evaluate your agent architectures for multi-hop identity and delegation gaps.
  • Strategic:

    • Implement centralized gateways and runtime authorization rather than relying on disparate SDK patches.
  • Questions to investigate:

    • Can we instantly revoke credentials issued to autonomous agents in our environment?

Compressed Summary

  • AI agents introduce unique security challenges due to non-deterministic execution and long-lived secrets.
  • Naive credential passthrough and over-privileged service accounts break traditional access control boundaries.
  • Secure agent architectures require explicit agent identity, verifiable delegation, scoped credentials, and audit trails.
  • Gateways and runtime authorization servers keep master keys out of agent reach and enable instant revocation and request attenuation.
  • Keywords: agent auth, authorization, mcp, oauth, gateways, security
  • Core insight: Securing AI agents requires moving away from static client-side API keys toward runtime authorization gateways that enforce scoped, short-lived credentials and maintain strict user-to-agent attribution on every hop.

Core insights

[A]Architecturemedium noveltymoderate evidence

Credential passthrough collapses the distinction between the human principal and the agent principal at the enforcement point, so no downstream system can attribute an action to either one. The fix is structural, not credential-hygiene: every hop must carry and verify both identities rather than forwarding one opaque token.

Why it matters

Attribution is the precondition for audit, least privilege, and incident response; if the resource server cannot tell user from agent, none of those are recoverable after the fact. This changes where identity is asserted (per hop, not per session) and forces token design to carry dual identity.

Generalization

Any multi-actor system that forwards a single credential (agents, service meshes, RPC proxies, batch jobs acting 'on behalf of') loses accountability and should instead propagate verifiable delegated identity per hop.

[M]Mechanismmedium noveltystrong evidence

Replacing stored long-lived secrets with runtime OAuth token exchange lets the intermediary mint a credential scoped to exactly the tool/resource being invoked, so there is no master key at rest to leak or rotate. The security property comes from re-exchanging per call rather than from where the secret is stored.

Why it matters

Secret storage (.env files on laptops, shared service accounts) was the dominant failure mode in naive setups; removing the standing credential eliminates a whole class of compromise and makes scope a runtime decision instead of a provisioning decision.

Generalization

Push privilege acquisition to request time (short-lived, narrowly scoped, audience-bound) instead of provisioning time (broad, standing, stored) wherever an autonomous component acts for a user.

Dual-identity token design and enforcement of token binding

Research question

What token claim structure and binding mechanism lets every hop independently verify both the user principal and the agent principal on a single request, and does that binding survive agent restarts, multi-hop exchange, and off-the-shelf agent runtimes that cannot be instrumented?

Why

The talk's central prescription — every hop knows user and agent — is only actionable if there is a concrete, verifiable binding. Pass 1 flags this as unresolved: the summary lists 'token binding' as a validation step without stating what it is bound to (client instance, session, key) or how it is enforced when the agent process itself is untrusted and can be induced to call unintended tools.

Representation and composition of the delegation record across multi-hop A2A flows

Research question

Where must the delegation record live (token claim, authorization-server state, or ledger) so that 'under whose authority did this happen' is answerable at a leaf resource without contacting every prior hop in the chain?

Why

Audit is listed as a required capability, but audit queries are unanswerable unless the delegation record composes across hops that each introduce a new client and a new resource. This determines whether audit is a post-hoc join problem or a per-request verifiable artifact — a concrete engineering choice with different failure modes.

Broker/federation as the fallback when authorization servers lack dynamic client registration

Research question

Can a single credential broker front heterogeneous authorization servers that do not support dynamic client registration, using pre-registered clients or workload identity, without creating a per-integration client for each resource?

Why

Pass 1 identifies the real scale ceiling as the identity-provider integration surface (N authorization servers × M resources), not agent logic. If the fallback pattern requires per-integration registration anyway, federation does not remove the ceiling — it relocates it. This is the highest-novelty insight in pass 1 and the least evidenced.

Your Agent Is Not a Service Account

The dominant agent security failure is a principal-model failure, not a secrets-hygiene failure: teams keep a service-account mental model while deploying a non-deterministic executor, so permission aggregation and post-hoc attribution break simultaneously. Moving scope from provisioning time to request time is the only fix that addresses both at once.

Angle

Contrast the legacy deployment-identity model with per-session, per-action scoping; show that rotating secrets or moving them to a vault leaves the aggregation problem fully intact.

Source video ↗

Every Hop Must Carry Two Names

Token passthrough is not a bad practice to be cleaned up — it is an architectural dead end, because once a single opaque credential is forwarded, no downstream hop can recover the distinction between user and agent. Correct designs assert identity per hop, and that requirement, not the credential, is what has to be designed.

Angle

Walk a request from user to agent to MCP server to downstream API and mark exactly where attribution is destroyed and what claim must appear at each enforcement point to restore it.

Source video ↗

The Hidden Cost of Correct Delegation

A single correctly authorized tool call is a multi-round-trip protocol, and systems that appear to make agent auth free are either caching credentials — reintroducing the standing secret — or skipping verification steps. Latency and hop count are therefore legitimate audit evidence, not just performance metrics.

Angle

Treat round-trip count per call as a falsifiable indicator of whether an agent-auth implementation is actually verifying anything, and use it to triage vendor claims.

Two-Name Hop Harness

gatehouse

Propagating distinct user and agent claims per hop preserves per-action attribution across a multi-hop chain for the large majority of tool calls, while single-token passthrough yields attribution on essentially none — and the gap is measurable independently of credential storage.

Proof of concept

Instrument a user → agent → MCP server → downstream API chain in two configurations (passthrough vs dual-identity per-hop exchange) and replay a fixed scenario set including model-injected unintended tool calls; log the identity pair observed at each enforcement point.

Measurement

Attribution rate (fraction of tool calls where the leaf resource can name both user and agent), plus per-call latency and round-trip count in each configuration.

Non-Registering IdP Broker

new

A single broker holding pre-registered client credentials can front a set of heterogeneous authorization servers that lack dynamic client registration, serving multiple resources without creating a new client per integration point.

Proof of concept

Stand up three mock authorization servers with no dynamic registration and distinct auth models, place one broker in front, and drive tool calls to each resource through runtime scope exchange instead of configured per-integration clients.

Measurement

Number of clients that must be created and maintained per new resource integration (target: O(1) at the broker, not O(N) per resource) and failure rate per authorization-server variant.

Exchange Cost and Cache Sweep

movement-lab

Per-call auth overhead grows superlinearly with hop count, and any broker cache TTL long enough to recover most of that latency also recreates a standing credential whose blast radius exceeds the short-lived guarantee it was meant to provide.

Proof of concept

Benchmark the six-step flow at 1, 3, and 5 hops, then sweep broker cache TTL across a range and record both latency savings and the window during which a leaked cached credential remains usable.

Measurement

Added latency per tool call by hop count; cached-token exposure window (seconds of usable life after revocation) as a function of TTL.

Architectural implications

3

Auth enforcement migrates from the agent's application code into a runtime authorization layer on the request path.

Before

Each agent/SDK implements its own token handling, often by reading long-lived secrets from the environment.

After

A runtime auth component (gateway or server SDK) brokers credentials, issues scoped short-lived tokens, and enforces local policy at the policy enforcement point.

Consequence

Auth becomes centrally observable and language-agnostic, but introduces a new critical-path dependency and a high-value credential store to protect.

Source video ↗

Policy is enforced at each hop's local enforcement point rather than at a single perimeter.

Before

A trusted caller passing the perimeter was assumed to be safe.

After

Every server validates signature, issuer, expiry, token binding, and applies its own local policy.

Consequence

Defense-in-depth across multi-hop flows, at the cost of duplicated policy logic and configuration drift risk between hops.

Source video ↗

The identity unit shifts from 'service account per deployment' to 'identity per agent or per session'.

Before

One over-privileged service account serves all users of an agent.

After

Distinct agent identity plus a per-user delegation record, with credentials scoped to tool, resource, and time window.

Consequence

Audit queries become answerable ('which agent did what under whose authority'), but credential lifecycle management volume grows by orders of magnitude.

Tradeoffs and failure modes

4

SDK-based enforcement vs centralized gateway

Benefit

SDKs keep enforcement co-located with the code and avoid a network hop.

Cost or risk

SDK challenges: every team must adopt them, every language needs a port, off-the-shelf agents cannot be embedded — so coverage is never complete.

Source video ↗

Short-lived scoped tokens vs operational simplicity

Benefit

No master key at rest; scope limited to the specific tool and a time window; revocation is implicit via expiry.

Cost or risk

Every call path requires exchange and validation steps, adding round trips and failure modes that a static secret never had.

Source video ↗

Human approval policy vs autonomy

Benefit

Policies define which actions need human approval, containing damage from non-deterministic agent decisions.

Cost or risk

Approval gates reintroduce latency and human attention cost into flows that were designed to run unattended, and the boundary must be maintained as tools change.

Source video ↗

Federation/brokering vs per-integration client registration

Benefit

Trust can be established across authorization servers without creating a new client at each integration point.

Cost or risk

Requires a broker that holds and caches credentials — a concentrated compromise target, and a dependency that the source authorization servers (many lacking dynamic registration) may not support.
