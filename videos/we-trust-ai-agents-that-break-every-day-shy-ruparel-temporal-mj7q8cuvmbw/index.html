Summary

Overview

  • Speaker: Shy Ruparel
  • Channel: AI Engineer
  • Main topic: AI agent reliability, observability, and workflow orchestration using Temporal
  • Purpose: To analyze the state of AI agent adoption in enterprises, expose the reliability and observability gaps, and demonstrate how durable execution platforms like Temporal solve state management, crash recovery, and cost management. Shy Ruparel from Temporal presents findings from the 2026 State of Development survey of 554 engineering leaders using AI agents. The talk examines four major gaps between agent usage and enterprise production: Usage vs. Production, Trust vs. Reality, Prototype vs. Enterprise, and Seeing vs. Recovering. The presentation highlights that while 80.8% of users utilize agents daily, 41.1% hit issues daily or worse, and 62% of teams lose time or revenue to reliability issues. To solve these enterprise reliability and state management blockers, the speaker demonstrates durable execution through a payout workflow demo where state survives worker crashes without rerunning LLM calls or losing audit trails.

Core insights

6
[M]Mechanismhigh noveltystrong evidence

Durable execution separates deterministic workflow orchestration from side-effecting activities, so on worker crash the runtime replays the event history and resumes without re-executing already-completed LLM calls or activities. The workflow's state is the event log itself, not an app-managed database table.

Why it matters

It removes the entire class of bugs where a restart re-triggers paid LLM calls or duplicate external side effects (e.g., double payouts), which today forces teams to hand-write retry logic, state tables, and reconciliation jobs. Recovery becomes a runtime property rather than application code.

Generalization

Any long-running agent loop that mixes orchestration with irreversible external effects (payments, emails, ticket creation, tool calls) should put effects behind an idempotent activity boundary and make orchestration logic replayable.

[O]Mental Modelhigh noveltystrong evidence

High trust in agent output coexists with very high failure frequency, and the teams that self-report success hit issues more often (1.7x). The right reliability target is therefore costless failure, not zero failure.

Why it matters

It changes the engineering objective from model-quality improvement (reduce error rate) to recovery engineering (make each failure cheap, observable, and self-healing). Teams optimizing for zero failures will under-invest in exactly the mechanism that matters in production.

Generalization

For any autonomous system with non-deterministic components, measure mean cost of recovery per failure and time-to-automatic-recovery rather than only success rate; a higher observed incident count may indicate better detection, not worse system quality.

Deep dives

Determinism boundaries in LLM-driven workflow orchestration

Research question

Which parts of an agent loop must be deterministic for replay to be safe when the branching decisions come from a non-deterministic LLM, and what recording/versioning patterns keep histories compatible across prompt and code changes?

Why

Replay is only correct if the orchestration code reconstructs the same decision path. The demo replays completed LLM calls as activities, but it does not show how in-workflow branching on model output avoids replay divergence. Without an answer, teams adopting durable execution hit non-determinism errors precisely when they iterate on prompts — the activity they do most.

Source video ↗

A taxonomy of failures that replay actually makes costless

Research question

Which agent incident classes (worker crash, tool/API failure, poisoned context, wrong model decision) are automatically recovered by event-history replay, and which ones resurface identically after resume?

Why

The talk asserts failures should be made costless, but replay only guarantees resumption of recorded steps. If the dominant failure mode is a bad reasoning decision, replay faithfully re-executes a workflow that was already wrong. Without a taxonomy, teams will over-attribute reliability to infrastructure and under-invest in detection and rollback at the reasoning layer.

State ownership versus telemetry as the primary reliability investment

Research question

Does shifting spend from tracing/dashboards to durable, resumable state ownership reduce manual incident-repair time more than equivalent spend on observability, given that state tracking outranks debugging as a blocker?

Why

The default response to agent unreliability is more traces. The survey says the #1 blocker is tracking state across services, ahead of isolating and debugging issues. If that ordering holds under experiment, most observability roadmaps are aimed at the second-largest problem, and the architectural decision (where authoritative agent state lives) should be made before the telemetry decision.

Reliability engineering for agents has the wrong objective. Chasing zero failures under-invests in the failure path, and the fact that self-described successful teams report 1.7x more continuous issues suggests incident counts measure detection and automation depth rather than quality. The defensible target is costless failure: every crash observable, resumable, and free of duplicate side effects.

Angle

Reframe the reliability KPI from error rate to cost-per-incident and time-to-automatic-resume, using the trust-versus-failure survey split as the diagnostic that the current frame is broken.

Detection and recovery are separate capabilities with separate architectures. If authoritative agent state lives in the execution history rather than an app-managed table, recovery becomes a runtime property and telemetry becomes the trigger for automatic resume instead of a manual repair session.

Project ideas

4

CrashLoop

beyond-evals

A replay-based runtime keeps duplicate irreversible effects at zero and preserves resumed progress under randomized worker kills, while a naive in-process agent loop with application-managed state produces duplicate effects on a measurable fraction of kills.

Proof of concept

Implement the same multi-stage payout workflow twice — once as a durable workflow with side effects behind idempotent activities, once as a single process with a state table and retry logic. Inject SIGKILL at randomized points mid-workflow, restart, and diff the number of executed LLM calls, payouts issued, and workflow completions.

Measurement

Duplicate-effect rate per 100 injected kills, duplicate LLM-call spend, time-to-resume after restart, and fraction of runs that reach completion without manual repair.

Source video ↗

SignalGate

gatehouse

Modeling human approval as a durable asynchronous signal instead of an in-process await or DB-polling loop drives idle compute during approval wait to zero and reduces approval-wait incident count, at equal or lower total workflow latency.

Proof of concept

Build a 9-stage approval-gated workflow where the gate is a durable signal. Run trials where approval arrives after 1 hour and after 24 hours, with zero workers alive during the wait. Compare against a poller variant and an always-on container variant.

Measurement

Idle compute cost during the approval window, wall-clock time from signal to resumed execution, missed-approval rate, and completeness of the audit record of who approved what and when.

Source video ↗

Replay Divergence Fuzzer

new

Only workflow mutations that change control flow conditional on model output break replay; recording the LLM decision in history rather than re-deriving it eliminates non-determinism failures across prompt and code changes.

Proof of concept

Take a bug-free durable agent workflow, then systematically mutate it along two axes: (a) prompt/model changes with recorded decisions, (b) control-flow changes that branch on model output. Replay mid-history snapshots after each mutation and record which mutations fail to reconstruct state.

Measurement

Replay failure rate per mutation class, percentage of failures attributable to non-recorded decisions, and whether recording decisions restores replay to 100% across the prompt-change axis.

Source video ↗

Durable Bake-off

movement-lab

Durable execution reduces total cost of ownership versus a hand-rolled state table plus reconciliation jobs once workflows include at least one human-latency gate and one irreversible external effect; below that threshold the reverse holds.

Proof of concept

Build the payout agent both ways, operate both under a synthetic incident load of worker kills, tool timeouts, and delayed approvals, and log engineering hours, remediation minutes, and infrastructure spend per workflow execution across two volume tiers.

Measurement

Engineering hours to first working version, on-call minutes per incident, duplicate-effect incidents per 1,000 runs, and infrastructure cost per 1,000 workflow executions at each volume tier.

Architectural implications

4

Orchestration logic and side-effecting tool/LLM calls are currently written as one in-process agent loop.

Before

A single process holds conversation/agent state in memory; crashes lose progress or re-trigger paid calls and irreversible tool effects.

After

Deterministic workflow code owns control flow; every LLM call, tool call, and external effect is an activity recorded in event history.

Consequence

Replay resumes at the last completed activity; idempotency requirements concentrate at a single, explicit boundary instead of being spread across retry code.

Source video ↗

Agent state is conventionally persisted in application-managed tables plus reconciliation jobs.

Before

Engineers design schema for agent state, write retry/reconciliation jobs, and debug divergence between DB state and actual executed effects.

After

The execution event history is the source of truth for state and progress.

Consequence

Custom state tables and reconciliation jobs disappear, and the same history doubles as an audit trail for regulated review.

Source video ↗

Human approval is conventionally an in-process await or a polling loop against a DB flag.

Before

A worker or container must stay alive (or a cron must poll) for an approval that may arrive hours later.

After

Approval is delivered as a signal to a durable workflow instance; execution continues when any worker is available.

Consequence

Human latency stops costing compute, and approvals become recorded, replayable events rather than ephemeral application state.

Source video ↗

Observability is treated as the answer to agent unreliability.

Before

Add tracing and dashboards; on failure, an engineer reads traces and manually repairs state.

After

Recovery is a runtime primitive; observability is the detection layer feeding an automatic resume path.

Consequence

On-call work shifts from manual state repair to monitoring recovery metrics and root-causing recurring activity failures.
