Summary

Overview

  • Speaker: Jesse Hall
  • Channel: AI Engineer
  • Main topic: Real-time voice AI infrastructure, latency management, turn-taking, and humanlike agent design.
  • Purpose: To educate AI engineers on how to build responsive, humanlike real-time voice agents using LiveKit infrastructure and conversation-level benchmarking. Jesse Hall from LiveKit discusses the limitations of traditional component-based evaluations for real-time voice agents. He explains why component leaderboards lead engineers astray, how latency is a budget rather than just raw speed, and why asynchronous tool execution and audio-based turn detection are necessary to achieve humanlike voice agent behavior.

Topic Map

The Limitations of Component Leaderboards

  • Explanation: Why picking top-ranked components (STT, LLM, TTS) independently fails to deliver a functional real-time conversation pipeline.
  • Key claims:
    • Errors flow downhill in component cascades.
    • Component leaderboards score models in clean lab conditions, not real-world mobile traffic.
    • The leaderboard is a trap: measuring the model is not the same as shipping a conversation.
  • Examples:
    • STT hears 'Tuesday the 30th' instead of 'Tuesday the 3rd', causing downstream LLM to book the wrong date.
  • Terminology:
    • Component Leaderboard
    • Speech-to-Text (STT)
    • Large Language Model (LLM)
    • Text-to-Speech (TTS)
  • Why it matters: Engineers build brittle pipelines by optimizing individual components instead of the end-to-end user conversation experience.

Latency as a Budget vs. Humanlike Goal

  • Explanation: Distinguishing between raw component latency (like time to first byte) and the perceived latency experienced by callers.
  • Key claims:
    • Latency is a budget; humanlike behavior is the goal.
    • Dashboard metrics report time-to-first-byte, but bytes are not sound.
    • Front-loaded silence in TTS models can create up to 750ms of dead air.
  • Examples:
    • A dashboard says 210ms time-to-first-byte, but the user hears silence for 750ms.
  • Terminology:
    • Time to First Byte (TTFB)
    • Time to First Audio
    • Front-loaded silence
  • Why it matters: Optimizing purely for raw speed metrics without considering audio delivery creates unnatural, robotic pauses.

Token Metrics vs. Sentence Metrics

  • Explanation: Why text generation metrics like time-to-first-token fail to capture voice generation realities.
  • Key claims:
    • Tokens aren't sentences; words aren't equal.
    • TTS cannot start speaking on a single token; it needs an entire sentence.
    • Models that stream tokens the fastest do not finish sentences first.
  • Examples:
    • Streaming individual tokens vs complete sentences.
  • Terminology:
    • First Token
    • First Sentence
    • Token streaming
  • Why it matters: Voice agents require sentence-level pacing to sound natural rather than rushed or disjointed.

Async Tools and Conversational Pacing

  • Explanation: How humanlike agents handle long-running tool calls without freezing the conversation.
  • Key claims:
    • Real agents do things, and tools take time (2s, 10s, 40s).
    • Humans don't freeze while booking systems load; they buy time and keep listening.
    • Asynchronous tool execution allows agents to speak interim status updates while working in the background.
  • Examples:
    • Agent saying 'Searching flights. This will take a minute.' while executing async search.
  • Terminology:
    • Async Tool
    • Interim update
    • Conversational thread
  • Why it matters: Enables agents to maintain conversational flow during high-latency backend operations.

Turn-Taking and Audio-Based Detection

  • Explanation: Replacing transcript-based turn detectors with audio-based turn detection to eliminate false cutoffs.
  • Key claims:
    • Humans negotiate turn-taking in hundreds of milliseconds using tone, pitch, and intonation.
    • Pipelines that wait for the entire transcript are too slow.
    • LiveKit turn detection reduces false cutoffs from 9.9% to 4.5% at the same latency budget.
  • Examples:
    • LiveKit audio-based turn detection firing before transcript lands.
  • Terminology:
    • Turn Detector
    • Audio turn detection
    • Last syllable
    • First audible byte
  • Why it matters: Crucial for preventing awkward pauses or premature interruptions in live voice conversations.

Conversation-Level Benchmarking

  • Explanation: A new open-source benchmarking approach that tests complete working agents against simulated callers and outcomes.
  • Key claims:
    • There are as many benchmarks as there are agents.
    • Test the conversation, not the component.
    • Score outcomes (database bookings, correct names/dates) against human-equivalent behaviors.
  • Examples:
    • Running hundreds of simulated callers with mumbling, interruptions, and changing minds against hotel concierge agents.
  • Terminology:
    • Conversation benchmark
    • Outcome scoring
    • Simulated callers
  • Why it matters: Provides a realistic evaluation framework that reflects actual production performance.

Key Points

Errors flow downhill

  • Explanation: An error in the speech-to-text stage propagates through the LLM and TTS without downstream models knowing the input was flawed.
  • Evidence: STT mishearing '3rd' as '30th' causes LLM to plan the wrong date.
  • Practical implication: Component isolation hides systemic conversational failures.

Measured latency vs. Perceived latency

  • Explanation: Dashboards show fast time-to-first-byte numbers, but front-loaded silence leads to slow perceived latency for users.
  • Evidence: Up to 750ms of silence before caller hears audio despite 210ms TTFB.
  • Practical implication: Measure what the user hears, not just what the server outputs.

Async tool execution

  • Explanation: Tools take time; agents must buy time conversationally rather than freezing.
  • Evidence: Using async context updates to say 'Searching flights' while API calls run in the background.
  • Practical implication: Eliminates awkward silence during database lookups.

Frameworks, Models & Processes

Tone-Home Checklist for Voice Agents

  • How it works: A practical checklist for engineering humanlike real-time voice applications.
  • Components:
    • Set the latency budget first
    • Measure first audio and first sentence
    • Spend leftover budget on quality
    • Anything over a second goes async
    • Test conversations, then keep testing
  • When to use: When designing and deploying production-grade voice AI agents.

Examples & Case Studies

Caller books a hotel room for October 10-12, changes guests, asks for ocean view, names Jesse Hall, and later changes dates to December 20-24.

  • Illustrates: A complete real-time hotel concierge agent handling multi-turn updates, interruptions, and async tool execution.
  • Lesson: Agents must handle mid-conversation changes smoothly without awkward pauses.

Actionable Takeaways

  • Immediate:
    • Set a strict latency budget based on human perception windows.
    • Implement async tool execution to keep conversations alive during long API calls.
    • Use audio-based turn detection instead of transcript-based waiting.
  • Strategic:
    • Stop testing components in isolation; test end-to-end conversations.
    • Build or adopt neutral benchmarks that evaluate outcome success against human equivalents.
    • Treat voice agents as real-time sensory systems rather than chatbots with speakers.
  • Questions to investigate:
    • How does your current STT-LLM-TTS pipeline handle front-loaded silence?
    • What percentage of user call interruptions result in false cutoffs in your current agent?

Compressed Summary

  • Component leaderboards fail because errors flow downhill and ignore real-world audio conditions.
  • Latency is a budget bounded by human conversational expectations (~1.5s hold, ~600ms feel human).
  • Async tool execution allows voice agents to speak interim status updates while background work runs.
  • Audio-based turn detection reduces false cutoffs compared to transcript-based waiting.
  • Benchmarking must test complete working conversations and outcomes, not isolated components.
  • Keywords: latency, voice-agent, turn-detection, livekit, benchmarking
  • Core insight: Voice agents require real-time infrastructure optimized for humanlike conversational pacing and async tool handling rather than isolated component speed metrics.

Core insights

6
[O]Mental Modelhigh noveltystrong evidence

Latency must be treated as a budget allocated across the whole conversation, not as a per-component speed metric: server-side time-to-first-byte can read 210ms while the caller experiences up to 750ms of dead air because TTS models front-load silence. The unit of measurement should shift from bytes emitted to audio the caller actually hears (time-to-first-audio).

Why it matters

Engineers who optimize TTFB dashboards will ship agents that feel slow while reporting fast, so the instrumentation itself is misleading. Perceived latency is the only metric a caller can observe, and it requires a different measurement point (first audible byte, not first byte).

Generalization

In any streaming pipeline with a rendering/consumption stage, instrument at the consumer boundary rather than at the producer boundary; intermediate bytes are not the delivered experience (applies to token streaming UIs, video, and audio alike).

[E]Empirical Resulthigh noveltystrong evidence

Audio-based turn detection can replace transcript-based turn detection: because humans negotiate turn-taking in hundreds of milliseconds using tone, pitch, and intonation, waiting for a complete transcript is structurally too slow. LiveKit's audio detector fires before the transcript lands and reportedly cuts false cutoffs from 9.9% to 4.5% at the same latency budget.

Why it matters

Turn-taking is a separate, prosody-driven subsystem that should not be coupled to the ASR/transcript path; treating 'end of turn' as a transcript-completion event forces a latency floor and causes premature interruptions or awkward pauses.

Generalization

Control/scheduling decisions in real-time interactive systems should be driven by cheap, low-latency signals (prosody, partial features) rather than by waiting for the full semantic pipeline to complete.

Source video ↗
[M]Mechanismhigh noveltystrong evidence

Token-level generation metrics do not transfer to voice: TTS cannot begin speaking on a single token, it needs an entire sentence, so the fastest token-streaming model does not necessarily produce the first audible sentence soonest. The meaningful scheduling unit is the sentence, not the token.

Why it matters

Model and pipeline selection based on time-to-first-token will pick the wrong components for voice, and generation logic (buffering to sentence boundaries, chunking policy) becomes an architectural responsibility rather than an implementation detail.

Generalization

When a downstream consumer has a different natural unit than the upstream producer (tokens vs sentences, frames vs batches), optimize and measure at the consumer's unit; streaming granularity is a design parameter, not a constant.

Source video ↗
[A]Architecturemedium noveltymoderate evidence

Long-running tool calls should be executed asynchronously while the agent speaks interim status updates, rather than blocking the conversation. Humans do not freeze while booking systems load; they buy time and keep listening, so the agent must be able to hold the conversational thread during 2s/10s/40s operations.

Why it matters

It decouples tool-execution latency from conversational latency, which removes the hard requirement that every backend operation fit inside the response budget and enables a heuristic like 'anything over a second goes async'.

Generalization

Separate the agent's conversational/response clock from its task-execution clock; long-running work belongs in a background channel with explicit progress narration, mirroring how humans handle slow processes.

Source video ↗
[!]Failure Modemedium noveltymoderate evidence

Errors flow downhill in component cascades: an STT misrecognition is silently consumed by the LLM, which plans an action on corrupted input with no downstream model able to detect that the input was wrong (e.g. '3rd' heard as '30th' causes the wrong booking date). Component leaderboards score models in clean lab conditions, not real-world mobile traffic, so independently top-ranked components do not compose into a working conversation.

Why it matters

It invalidates leaderboard-driven component selection as a design method and argues that validation, confidence propagation, and outcome checks must sit at the conversation level rather than at each component boundary.

Generalization

In composed pipelines, per-stage accuracy is not composable into end-to-end reliability; without cross-stage error signaling, an upstream defect is laundered into a confident downstream action.

Source video ↗
[P]Practicehigh noveltymoderate evidence

Evaluation should be conversation-level and outcome-scored: run hundreds of simulated callers who mumble, interrupt, and change their minds against a complete working agent, then score end-state effects (database bookings, correct names and dates) rather than component metrics. The hotel concierge case (October 10-12 booking, guest change, ocean view, name, then a change to December 20-24) is the unit of test, not the ASR or LLM.

Why it matters

It provides a testable harness design: the observable is the side effect in the system of record, the workload is adversarial-but-humanlike caller behavior, and it explicitly rejects the 'one benchmark per component' trap.

Generalization

For agents that act on external systems, benchmark by scoring verified side effects under adversarial input variation, not by scoring intermediate model outputs.

Architectural implications

4

The latency budget is set at the conversation level and then allocated downward, implying an end-to-end scheduler/controller rather than independently tuned components.

Before

Pick the top-ranked STT, LLM, and TTS from component leaderboards and wire them into a cascade.

After

Define a conversational latency budget from human perception windows, measure first audio and first sentence, and spend the leftover budget on quality.

Consequence

Model selection becomes a constrained allocation problem against a shared budget, and per-component optimization loses authority over the design.

Turn detection moves off the transcript path onto the audio/prosody path.

Before

Wait for the full transcript to decide the user has finished their turn.

After

Fire turn decisions on audio signals (tone, pitch, intonation, last syllable) before the transcript lands.

Consequence

Turn-taking becomes an independent low-latency subsystem, decoupling responsiveness from ASR completion time and reducing false cutoffs.

Tradeoffs and failure modes

4

Asynchronous tool execution

Benefit

Keeps the conversational thread alive during 2s/10s/40s backend operations, eliminating awkward silence during database lookups.

Cost or risk

In-flight operations can be invalidated by the caller changing their mind mid-flight (as in the hotel example where dates change from October 10-12 to December 20-24), requiring cancellation/reconciliation of stale results.

Source video ↗

Audio-based turn detection

Benefit

Reduces false cutoffs from 9.9% to 4.5% at the same latency budget.

Cost or risk

Residual 4.5% false-cutoff rate remains, and detection fires before the transcript is available, so semantic content cannot be used to confirm the decision.

Source video ↗

Sentence-level TTS buffering

Benefit

Enables natural pacing and the first audible sentence sooner.

Cost or risk

Requires aggregating tokens to sentence boundaries, which constrains chunking policy and can delay output when generation is slow to complete a sentence.

Source video ↗

Component-level optimization / leaderboards

Benefit

Cheap, standardized comparison of individual models in controlled conditions.

Cost or risk

Lab-condition scores do not reflect real-world mobile traffic, and errors flow downhill silently, so top-ranked components can compose into a conversation that fails.
