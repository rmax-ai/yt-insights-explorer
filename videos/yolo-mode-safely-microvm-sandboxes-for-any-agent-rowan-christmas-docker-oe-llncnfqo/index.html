Summary

Overview

  • Speaker: Rowan Christmas
  • Channel: AI Engineer
  • Main topic: Using MicroVM sandboxes to run AI agents securely
  • Purpose: To demonstrate the security risks of AI coding agents running with broad system access and to introduce Docker's SBX microVM sandbox solution for runtime AI governance and isolation. Rowan Christmas from Docker presents an exploration of how AI coding agents (such as Claude Code) can be safely executed inside MicroVM sandboxes (SBX) to prevent credential harvesting, accidental file destruction, and network exfiltration. He demonstrates how easy it is for an agent to access local browser history, bank accounts, and sensitive data when trusted blindly, and explains why sandbox isolation at the kernel level is essential rather than relying on agent prompts or harness-level guardrails.

Topic Map

The Security Risks of Autonomous AI Agents

  • Explanation: Rowan recounts testing Claude Code on his Mac desktop to see what happens when an agent has unrestricted local access, showing how easily it retrieves browser history and bank login sqlite databases.
  • Key claims:
    • Coding harnesses do not protect against all bad agent actions.
    • AI agents can successfully locate and extract sensitive local credentials and PII within just a few prompts.
    • Asking an agent nicely in prompts ('please don't do bad things') is insufficient security.
  • Examples:
    • Claude Code searching local Mac directories (/Library/Application Support/Google/Chrome/Default/Login Data) to find bank credentials.
    • Extracting checking account numbers and Zelle payment patterns in 5 prompts.
  • Terminology:
    • credential harvesting
    • prompt injection
    • PII
    • egress
  • Why it matters: Demonstrates that developers deploying autonomous coding agents face severe risks of identity theft and data exfiltration if the agent runs directly on the host machine.

Docker SBX: MicroVM Sandboxes for Agents

  • Explanation: Introduction of SBX, Docker's new microVM binary designed specifically to sandbox AI agents, running them in an isolated environment with separate kernels and virtualized file systems.
  • Key claims:
    • The harness is the wrong place to enforce security policy because agents bypass it.
    • MicroVM sandboxes run their own kernel, isolate file systems, and intercept network requests.
    • Running Claude Code inside SBX prevents it from discovering host browser history or unauthorized network endpoints.
  • Examples:
    • Running sbx run claude instead of claude.
    • SBX reporting 0 browser histories found because the sandbox has no host browser installed.
  • Terminology:
    • microVM
    • SBX
    • kernel isolation
    • network egress
  • Why it matters: Provides a robust, design-level security boundary that stops unauthorized agent actions regardless of what prompts the agent receives.

AI Governance and Policy Enforcement

  • Explanation: How organizations can define network and filesystem access policies once and enforce them where the agent runs.
  • Key claims:
    • Define policy once and enforce it where the agent actually runs.
    • Network and filesystem allow/deny rules can be configured per sandbox instance.
    • MCP (Model Context Protocol) servers can also be run inside sandboxes to maintain compliance.
  • Examples:
    • Allowing github.com and denying internal production endpoints.
    • Mounting specific read-only repositories for context.
  • Terminology:
    • MCP catalog
    • identity tracking
    • delegation chains
    • audit trail
  • Why it matters: Enables CISO teams to satisfy both the CEO's demand to 'ship it' and the board's demand to 'control it' without blocking AI adoption.

Key Points

'Please' is not security

  • Explanation: Asking an LLM or agent not to do malicious things via prompt instructions provides zero real security guarantees.
  • Evidence: Claude Code readily extracted sensitive local data when asked via standard research prompts.
  • Practical implication: Do not rely on prompt-level restrictions for sensitive environment execution.

The lethal trifecta of AI agents

  • Explanation: Every useful agent requires access to private data, exposure to untrusted content, and the ability to act externally.
  • Evidence: Useful coding agents need repo access, web/prompt input, and API/network execution.
  • Practical implication: Because useful agents inherently possess the lethal trifecta, runtime enforcement layers are mandatory.

MicroVM sandboxing as the ultimate boundary

  • Explanation: Isolating agents in MicroVMs ensures that even if compromised or tricked by prompt injection, the agent cannot access the host machine's secrets or unauthorized network ports.
  • Evidence: SBX blocks unauthorized DNS lookups and web requests (e.g., to pirated sites or telemetry dumps).
  • Practical implication: Adopt microVM-based sandboxing for all local and server-side agentic workflows.

Frameworks, Models & Processes

The Lethal Trifecta for AI Agents

  • How it works: Describes the three inherent risk capabilities present in any functional AI agent.
  • Components:
    • Access to private data (internal, sensitive, regulated)
    • Exposure to untrusted content (prompt injection, poisoned input)
    • Ability to act externally (exfiltration, unbounded egress)
  • When to use: When evaluating the security posture of any autonomous AI agent deployment.

[A]Architecturemedium noveltystrong evidence

Security policy for autonomous agents must be enforced at a boundary below the agent (kernel/microVM), because harness-level guardrails and prompts are bypassable by the agent itself.

Why it matters

It relocates the trust boundary from a component the agent controls (the harness/prompt) to one it cannot escape (a separate kernel), which is the difference between a suggestion and an enforcement guarantee.

Generalization

For any untrusted-code execution system, policy enforcement must live in the substrate, not in the code being governed — same reason browsers and containers don't rely on app-level permissions.

Why it matters

Gives a concrete, testable design lever: capability can be reduced by shrinking the namespace (files, binaries, endpoints) rather than by adding behavioral instructions, making the security property deterministic instead of probabilistic.

Generalization

Treat filesystem and network visibility as the capability surface of an agent; auditing and limiting that surface is equivalent to limiting what the agent can do.

Harness Bypass Benchmark

beyond-evals

Popular agent harnesses' built-in permission and deny rules can be bypassed by an ordinary agent using shell, file, or network primitives in a measurable fraction of trials.

Proof of concept

Build a test suite that places decoy credential files on a host, configures harness-level deny rules, and runs coding-agent tasks that attempt to read or encode those files; record bypasses.

Measurement

Bypass rate per harness, time-to-bypass, percentage of deny categories defeated, and whether bypass required adversarial prompts versus ordinary research prompts.

Namespace Minimality for Coding Agents

movement-lab

Agent task success is preserved when filesystem and network visibility are reduced to task-specific read-only mounts and allow-listed endpoints, while credential exposure drops to zero.

Proof of concept

Run a coding task suite in a microVM with tiered mount policies (full host, repository read-only, scoped subtree) and network allow-lists; measure task success and attempted sensitive access.

Measurement

Task success rate, sensitive-file access attempts, exfiltration attempts, and policy-violation events per tier.

gatehouse

Architectural implications

3

Policy enforcement relocates from the agent harness to a kernel-level microVM boundary.

Before

Guardrails, prompt instructions, and harness permissions inside the agent process.

After

MicroVM with its own kernel, virtualized filesystem, and intercepted network requests.

Consequence

Agent misbehavior becomes contained by construction; compromised agents cannot reach host secrets or unauthorized endpoints regardless of prompt content.

Source video ↗

Governance authoring is separated from enforcement location.

Before

Security rules expressed per-harness, per-developer, or in prompts.

After

Policy declared once and enforced where the agent runs, per sandbox instance.

Consequence

CISO/security teams get a single control point while developers keep using arbitrary harnesses, resolving the 'ship it vs control it' tension.

Source video ↗

Context supply becomes an explicit, restricted mount operation rather than ambient host access.

Before

Agent inherits full host filesystem and network reach.

After

Specific read-only repositories and allow-listed endpoints are mounted into the sandbox.

Consequence

Context engineering gains a security surface: what you mount is exactly what the agent can read, making blast radius auditable.

Tradeoffs and failure modes

3

Isolation vs developer experience and execution latency

Benefit

Kernel-level microVM isolation prevents credential harvesting and unauthorized egress even under prompt injection.

Cost or risk

Summary leaves unresolved how SBX affects agent execution speed and developer experience; added virtualization and policy friction may slow the inner loop.

Narrowing visibility trades capability for safety

Benefit

Mounting only specific read-only repositories limits what data an agent can reach.

Cost or risk

Under-provisioned sandboxes reduce agent usefulness and may push users to request broad mounts, re-expanding the attack surface.

Reliance on prompt-level prohibition

Benefit
