Summary

Overview

  • Speaker: Justin Schroeder
  • Channel: AI Engineer
  • Main topic: Standardizing AI Agents via the Standard Agent Specification
  • Purpose: To introduce and open-source the Standard Agent Specification and Standard Agent Builder, establishing an open ecosystem of interoperable, domain-specific agents. Justin Schroeder introduces the Standard Agent Specification, an open-source, engineering-first approach to building, packaging, and running domain-specific AI agents. He highlights why prevailing approaches—such as combining MCP servers and markdown files with general models—fail because businesses require control, reliability, repeatability, and non-generic tone. The talk details the three primary factors for agent adoption (Integration, Trust, Efficacy) and outlines the core specification principles: agents must be vendor-agnostic, domain-specific, coupled to a model, composable, and portable, implemented in TypeScript via file-based definitions, threads, hooks, effects, and runtimes.

The Standard Agent Specification

  • Explanation: Introduces the Standard Agent Specification (standardagentspec.org) as an open-source, engineering-first approach where agents are deterministic software harnessing non-deterministic models.

    • Five core principles: vendor-agnostic, domain-specific, coupled to a model, composable, and portable.

Key Points

A business is its processes

  • Explanation: All business value—relationships, network effects, and proprietary data—derives from the underlying operational processes.
  • Evidence: Business processes in HVAC repair, universities, and cloud providers dictate organizational success.
  • Practical implication: AI agents must integrate directly into existing business processes rather than acting as generic standalone chatbots.

An agent that can do anything is a liability

  • Explanation: Unconstrained general agents with access to broad toolsets introduce unacceptable risks of unintended actions.
  • Evidence: Grok or Claude with full tool access might check emails or read news instead of completing a warranty claim.
  • Practical implication: Domain-specific agents must have strictly restricted, fine-tuned scopes and workflows.

A Gmail agent beats a Gmail skill

  • Explanation: Specialized single-task agents running on smaller, cheaper models outperform massive general models equipped with dozens of skills.
  • Evidence: DeepSeek V4.1 Flash configured as a dedicated Gmail agent is cheaper, more evaluable, and easier to compose than Claude Opus with 41 skills.
  • Practical implication: Decompose complex systems into hierarchies of small, domain-specific agents.

Everything in the specification is code

  • Explanation: To enable packaging, distribution on npm, and portability, every aspect of an agent must be defined in code.
  • Evidence: TypeScript definitions for models, prompts, tools, handlers, hooks, and effects.
  • Practical implication: Eliminates hand-written prompts and proprietary UI configurations, allowing agents to be shipped on USB sticks or package registries.

Core insights

6
[A]Architecturehigh noveltymoderate evidence

The harness — the orchestration layer that turns a model into an agent — is the one layer of the agent stack with no standard, while tool access (MCP), prompt/skill packaging (Skills, Agents.md), and inter-agent communication (A2A, ACP, payments) are all already standardized. This makes the harness the highest-leverage place for a new specification.

Why it matters

It tells engineers exactly where the interoperability gap lives and where to invest abstraction effort: not in tools, prompts, or transport, but in the orchestration contract that binds model, prompt, tools, state, and runtime together.

Generalization

Standards emerge bottom-up by layer; whichever layer is left unstandardized becomes the source of fragmentation and vendor lock-in for everything above it.

Decompose at the job boundary, not the skill boundary: a dedicated single-job agent on a small cheap model is claimed to be cheaper, easier to evaluate, and composable into larger systems, versus one frontier model loaded with dozens of tools and skills.

Why it matters

It is a concrete architectural rule for where to cut agent boundaries, and it flips the default instinct of adding capabilities to one general agent. It also implies evaluation surfaces are per-agent, which changes how CI, benchmarks, and cost accounting are structured.

Generalization

Capability should be allocated at the smallest independently evaluable unit; composition replaces configuration breadth.

[O]Mental Modelmedium noveltymoderate evidence

The spec's framing is that an agent is deterministic software that harnesses non-deterministic model output — which relocates control flow, tool invocation, hooks, and effects into ordinary code, leaving the model as a constrained component rather than the system itself.

Why it matters

This framing determines where reliability engineering happens: in typed, testable code paths around the model rather than in prompt engineering. It also makes the agent testable like software (deterministic shell, stubbed model) rather than only evaluable end-to-end.

Generalization

Treat the model as an unreliable dependency behind a deterministic boundary; push every decision that can be decided in code out of the model.

[P]Practicemedium noveltymoderate evidence

Capability breadth is a liability: an agent with unrestricted tool access may take unintended actions, so trust is achieved by strictly scoping tools and workflow rather than by instructing a general model to stay on task.

Why it matters

It converts a vague 'safety' concern into a concrete design constraint — the tool surface and workflow graph are the enforcement boundary, not the system prompt. This directly affects permission models, allowlists, and blast-radius design.

Generalization

Least-privilege applies to agent tool surfaces exactly as it does to service credentials; instruction-level constraints are not an enforcement mechanism.

[M]Mechanismhigh noveltymoderate evidence

A file-based, TypeScript-typed agent definition (models, prompts, agents, threads, HTTP endpoints) becomes a build artifact that a coding agent can generate from a process document — turning agent construction into a compile target rather than hand-written glue.

Why it matters

If the agent package is a declarative artifact, generation, review, diffing, and deployment all become standard software supply-chain operations. It implies agent definition files should be treated like source code with review gates, not like prompts stored in a database.

Generalization

Any domain artifact that becomes a typed, file-based spec immediately becomes automatable by coding agents and reviewable by normal engineering process.

Source video ↗
[~]Tradeoffmedium noveltymoderate evidence

The spec deliberately holds two opposing positions at once: agents are vendor-agnostic and portable at the runtime layer, but each agent is coupled to a specific model. Portability lives in the definition format; repeatability lives in the pinned model.

Why it matters

This resolves a common confusion in agent architecture — teams conflate 'model agnosticism' with 'deterministic behavior'. Pinning the model per agent while keeping the runtime swappable is what makes evaluation meaningful without sacrificing deployment flexibility.

Generalization

Vary what must be portable (packaging, runtime contract) and pin what must be reproducible (model version, weights, temperature); the two are different axes, not a single 'agnostic vs locked' choice.

Deep dives

Cross-runtime conformance of harness specifications

Research question

Does a spec-defined harness produce equivalent tool-call traces and outcomes across independent runtimes, or do hooks, effects, and thread semantics leak runtime-specific behavior?

Why

If portability is only nominal, the specification's core promise fails and teams inherit a new abstraction without escaping lock-in. Conformance criteria determine whether agents are truly portable packages or just portable-looking files.

Source video ↗

Trust enforcement boundary: declarative scope versus runtime sandbox

Research question

Are agent trust constraints enforced by spec-declared tool allowlists and workflow boundaries, by runtime sandboxing, or only by prompt instructions—and which layer actually blocks unauthorized actions?

Why

Trust is named as an adoption gate, but if enforcement is only prompt-level, the liability claim is unaddressed. The answer determines whether the agent definition is a security artifact or merely documentation.

Source video ↗

Job-boundary decomposition versus frontier-model breadth

Research question

Can a composed hierarchy of small single-job agents match the end-to-end success rate of one frontier model with many skills, or does it only win on cost and evaluability?

Why

This separates a general architecture rule from a cost optimization with a quality ceiling. If composition loses accuracy, teams need explicit orchestration quality budgets; if it matches, capability breadth in a single agent is mostly technical debt.

Source video ↗

Model deprecation in composed agent graphs

Research question

How should a composed graph of agents pinned to different model versions handle model deprecation, upgrade, and rollback without invalidating whole-system evaluations?

Why

Per-agent model pinning improves repeatability but creates version debt. Without a registry and dependency graph, a single deprecation can force fleet-wide re-evaluation and erode the cost advantage of narrow agents.

Process-document-to-agent-package generation fidelity

Research question

What fraction of a real business process can a coding agent capture in a generated agent package before human decomposition into multiple agents becomes necessary, and what error classes dominate?

Why

The demo suggests minutes-to-agent, but review of generated tool scope and prompts becomes the bottleneck. Measuring fidelity tells us whether this is a throughput win or a safety risk that merely moves engineering effort into review.

Harness Conformance Diff Lab

new

Two independent runtimes executing the same spec-conformant agent package will produce identical tool-call traces for deterministic test cases, with divergence confined to explicitly declared runtime hooks and effects.

Proof of concept

Implement a small agent package with one job, three tools, one hook, and one effect; run it on a reference runtime and an independent stub runtime; capture normalized tool-call and state traces for a fixed test suite; diff the traces.

Measurement

Percentage of test cases with identical traces; divergence categorized by hook, effect, and thread semantics; count of runtime-specific leaks.

Agent Scope Red-Team Gate

gatehouse

Definition-level tool allowlists and workflow boundaries block out-of-scope tool invocations at 95% or more, while prompt-only instructions block less than 50% under adversarial prompts.

Proof of concept

Generate a narrow warranty-claim agent package, then create three variants: spec allowlist, runtime sandbox only, and prompt-only. Run a prompt-injection suite attempting unauthorized billing and scheduling tool calls, and log the enforcement point and outcome.

Measurement

Out-of-scope attempt success rate per variant; enforcement layer that blocked each attempt; false-positive rate on legitimate tasks.

Small-Agent Composition Benchmark

beyond-evals

A composed set of single-job small-model agents achieves at least 90% of a frontier model's end-to-end task success rate at 40% or less cost per successful task on a multi-step business workflow.

Proof of concept

Implement a four-step workflow—intake, lookup, decision, response—in two configurations: one frontier model with all skills and tools, and four single-job agents on small pinned models orchestrated by code. Use synthetic and replayed cases.

Measurement

Task success rate, cost per success, p95 latency, and failure taxonomy; identify steps where composition loses accuracy.

Pinned-Model Deprecation Registry

movement-lab

A dependency-aware agent registry that records per-agent pinned model versions and composition edges reduces the re-evaluation set for a single model deprecation from all agents to only direct and transitive dependents, cutting re-evaluations by 60% or more in a 20-agent graph.

Proof of concept

Build a registry manifest for 20 agents across five pinned models with composition edges; simulate deprecating one model; compute naive re-evaluation versus graph-scoped re-evaluation; prototype rollback and upgrade propagation.

Measurement

Number of agents re-evaluated; false negatives where affected agents are not flagged; time to produce an upgrade plan.

Architectural implications

4

The harness stops being bespoke per-company code and becomes a spec-conformant package executed by a runtime.

Before

Every team hand-builds its own orchestration loop, retry logic, tool dispatch, and state handling, producing agents that cannot be shared or composed.

After

Agents are portable packages defined in code and executed by any conforming runtime, with runtime responsibilities separated from agent responsibilities.

Consequence

Distribution and composition become possible, but the spec and runtime contract become a new critical dependency that must be versioned and governed.

Source video ↗

Model selection moves from a platform-wide decision to a per-agent property.

Before

An organization picks one frontier model for all AI features and layers skills/tools on top of it.

After

Each narrow agent pins its own model, potentially a smaller cheaper one, chosen for that job.

Consequence

Cost and latency can drop sharply, but fleet management now involves many pinned models with different upgrade and deprecation timelines.

Source video ↗

Agent construction becomes a code-generation pipeline fed by business process documents.

Before

A process document is read by humans who then hand-write prompts, tool schemas, and glue code.

After

A coding agent reads the process PDF and emits a complete agent package with tools, prompts, threads, and endpoints in minutes.

Consequence

Throughput of agent creation rises, but review of generated definitions (tool scope, prompt correctness) becomes the new bottleneck and the main safety control.

Source video ↗

Observability is treated as a runtime contract property rather than something each agent implements.

Before

Each custom harness logs whatever it happens to log; cost and cache behavior are invisible or inconsistent.

After

The runtime surfaces tool calls, token usage, cost, and cache rate uniformly for any conforming agent.

Consequence

Cross-agent cost and reliability comparisons become feasible, enabling portfolio-level decisions about which agents to keep, downgrade, or retune.

Tradeoffs and failure modes

4

Vendor-agnostic portability vs pinned-model repeatability

Benefit

A portable runtime contract lets the same agent definition run on different infrastructure, while pinning the model keeps behavior reproducible and evaluable.

Cost or risk

Any model upgrade is a per-agent change requiring re-validation, and a fleet of pinned agents accumulates version debt and heterogeneous behavior.

Source video ↗

Restricted scope vs capability

Benefit

Tightly scoped tools and workflows make the agent trustworthy and reduce the space of harmful actions.

Cost or risk

Narrow agents cannot handle off-nominal cases that fall outside their scope and require a composition layer and orchestration overhead to cover the full business process.

Source video ↗

Fast agent generation from process documents

Benefit

A complete agent package for a warranty process can be produced in minutes instead of days.

Cost or risk

Correctness of the generated tool scope and prompts is asserted by the generator, not verified; a plausible-looking package can encode the wrong process semantics.

Source video ↗

Custom harnesses vs standardized harness

Benefit

A standard lets agents be distributed, shared, and composed instead of rebuilt per organization.

Cost or risk

Ad-hoc harnesses already work for their owners; a spec adds conformance overhead and may lag behind novel orchestration patterns that do not fit the abstraction.
