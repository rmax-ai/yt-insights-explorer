Summary

Overview

  • Speaker: Philipp Schmid
  • Channel: AI Engineer
  • Main topic: How markdown files, YAML, and filesystems replace traditional Python code in building LLM agents
  • Purpose: To demonstrate the shift in agent engineering from hardcoded Python orchestration loops to file-driven, framework-managed, and cloud-sandboxed managed agents. Philipp Schmid from Google DeepMind explores the evolution of building LLM agents, demonstrating how raw Python code loops, JSON schema definitions, and custom tooling are being replaced by declarative configuration, filesystem-based agent definitions (AGENTS.md, SKILL.md), and managed remote sandboxes via the Interactions API.

Frameworks, Models & Processes

Interactions API

  • How it works: Provides server-side state management, native tool use, multimodal input/image generation, and background execution via a unified client interface.
  • Components:
    • Unified interface for models and agents
    • Server-side state management
    • Background execution for long-running workflows
  • When to use: When building scalable agent applications without managing custom state loops.

Managed Agents Architecture

  • How it works: Decouples execution sandboxes configured dynamically or saved by ID, utilizing markdown files for instructions and skills.
  • Components:
    • AGENTS.md
    • SKILL.md
    • Remote Linux Sandbox
    • Network Proxy Credential Injection
  • When to use: When deploying general-purpose agents into secure cloud environments.

Generalization

Article ideas

4

Your Agent Harness Is Technical Debt: Build to Delete It

Hardcoded agent orchestration should be treated as a depreciating asset. As foundation models improve, teams should measure harness code by how little of it remains and design for deletion rather than accumulation.

Angle

Reframe agent engineering as continual subtraction: identify orchestration code that model capability can absorb, and replace it with declarative files while instrumenting reliability to prove nothing important was lost.

Source video ↗

Agents Are Just Files—And That's the Problem

File-driven agent definitions improve reviewability and portability, but they sacrifice determinism, type safety, testability, and failure diagnosis. Teams should use markdown for instructions and capabilities while keeping code for enforcing critical constraints.

Angle

Argue against the totalizing version of the 'agents are just files' claim by cataloging what markdown and YAML cannot express, and propose a hybrid model where files define intent and code enforces invariants.

Source video ↗

The Abstraction Boundary: What Agent Frameworks Don't Remove

Agent development kits remove schema generation, tool loops, dispatching, and retries, but they leave per-tool implementation and runtime hosting with the developer. Adoption plans must budget for this residual ownership instead of assuming framework use eliminates infrastructure.

Angle

Compare raw SDK, ADK-style framework, and managed file-based agent implementations to expose the exact categories of code each tier does and does not remove.

Source video ↗

Server-Side State Is Not Free: Turn-Based vs Steps Data Models

Offloading agent state and execution to a hosted API removes client-side serialization, retry, and loop control, but introduces platform-specific data models that determine resumption granularity, observability, and long-running workflow design.

Angle

Argue that teams should select a hosted agent runtime based on the data model's fit with their durability and debugging needs, not only on boilerplate reduction.

Architectural implications

3

Agent state and execution loop move from application code to a hosted API with server-side state and background execution.

Before

Client-side Python loop tracks turns, serializes state, retries failures, and ties agent lifetime to the process.

After

Server holds state and runs long-lived workflows; client issues interactions and receives results.

Consequence

Reliability, retry semantics, and observability become platform concerns; applications gain durability but lose fine-grained control and gain a dependency on runtime semantics like turn-based vs steps data models.

Source video ↗

Agent definitions become filesystem artifacts (AGENTS.md, SKILL.md) rather than application source.

Before

Agent behavior encoded in Python modules, JSON schemas, and bespoke tool code.

After

Behavior and capabilities declared in markdown files loaded by a managed runtime.

Consequence

Agents become reviewable, diffable, and portable artifacts; authorship shifts toward prompt/instruction engineering and away from programming, and tooling must support file-based agent lifecycle management.

Source video ↗

Code execution and credential access are separated into an isolated sandbox plus an injecting network proxy.

Before

Agent process runs with ambient credentials or receives secrets directly.

After

Agent runs in an isolated remote Linux sandbox; the proxy injects credentials so the agent never holds secrets.

Consequence

Enables safer autonomous tool use and third-party access without secret exposure, but introduces a proxy as a critical path component that must itself be secured and audited.

Tradeoffs and failure modes

3

Framework abstraction vs residual ownership

Benefit

Frameworks like ADK remove boilerplate: automatic JSON schema generation from docstrings, managed tool loops, dispatching, and retries.

Cost or risk

Developers still must own Python plumbing for every tool and the runtime hosting environment, so adopting a framework does not remove infrastructure burden.

Source video ↗

Minimizing harness code as models improve

Benefit

Deleting orchestration code (e.g., 12,000-15,000 lines of TypeScript replaced by a 200-line markdown skill) reduces maintenance and lets model capability drive behavior.

Cost or risk

Reducing hardcoded control flow may sacrifice determinism and explicit guardrails, making behavior depend on model reasoning quality.

Remote sandbox with proxy credential injection

Benefit

Provides isolated execution and lets agents use authenticated services without being given secrets.

Cost or risk

The mechanism for keeping secrets away from the agent while still authenticating its requests is not explained, leaving an unresolved security question.
