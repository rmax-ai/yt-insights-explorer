Summary

Overview

  • Speaker: Jacqui Read
  • Channel: GOTO Conferences
  • Main topic: Disambiguating event-driven architecture terminology, patterns, and concepts
  • Purpose: To clear up confusion around event-driven terminology and provide software architects and developers with clear patterns and definitions for designing event-driven systems. Jacqui Read presents a comprehensive guide to understanding and disambiguating event-driven architecture terminology and patterns. The talk walks through what an event is, differentiates events from commands and messages, explores event listeners, handlers, event streaming, message logs, message queues, event sourcing, tombstone events, and event-driven architecture versus command-driven architecture. She concludes with guidelines on event granularity and designing events like APIs.

Topic Map

What is an Event?

  • Explanation: Explores dictionary and computing definitions of events, emphasizing that a computing event represents something that has already happened with a definitive outcome.
  • Key claims:
    • A computing event is something that has already happened.
    • Events are immutable facts that cannot be changed once published.
  • Examples:
    • Java EventObject from JDK 1.1
    • PreferenceChangeEvent and PropertyChangeEvent
  • Terminology:
    • Event
    • EventObject
    • Computing Event
  • Why it matters: Understanding the fundamental definition of an event prevents confusion with commands or calendar events.

Event vs. Command

  • Explanation: Compares commands and events as two types of messages, highlighting that commands express intention and expect something to happen, whereas events represent published facts with no expectation of a response.
  • Key claims:
    • Commands represent intent and are sent to a specific target expecting an action.
    • Events are published facts that state what happened without expecting anything in return.
  • Examples:
    • Batman intent vs. cat-on-head result (fact)
  • Terminology:
    • Command
    • Message
    • Intent
    • Result
    • Fact
  • Why it matters: Distinguishing between intent and fact is crucial for designing loose coupling in distributed systems.

Event Listeners, Handlers, Streaming, Logs, and Queues

  • Explanation: Clarifies the components of message delivery, contrasting event listeners and handlers, message logs with offsets, and message queues with competing consumers.
  • Key claims:
    • Event listeners trigger asynchronous callback code when an event occurs.
    • Message logs maintain ordered offsets where multiple consumers can read independently.
    • Message queues use competing consumers where processed items are removed from the queue.
  • Examples:
    • Star Trek captains log and intercepted/docked messages
  • Terminology:
    • Event Listener
    • Event Handler
    • Event Streaming
    • Message Log
    • Message Queue
    • Offset
    • Idempotency
  • Why it matters: Choosing the right messaging infrastructure depends on whether you need pub-sub streaming or point-to-point queuing.

Event-Driven Architecture (EDA) vs. Command-Driven

  • Explanation: Compares command-driven architectures (high coupling, direct service calls) with event-driven architectures (low coupling via brokers and pub-sub).
  • Key claims:
    • Command-driven architectures lead to complex networks of high coupling between services.
    • Event-driven architectures decouple producers and consumers through brokers using publish-subscribe.
  • Examples:
    • Service-to-service webs vs. broker-mediated event meshes
  • Terminology:
    • Event-Driven Architecture
    • EDA
    • Broker
    • Publish-Subscribe
    • Coupling
  • Why it matters: EDA reduces system coupling and improves scalability in distributed microservice environments.

EventStorming and Bounded Contexts

  • Explanation: Explores EventStorming as a collaborative modeling method to break down silos and identify pivotal events and bounded contexts.
  • Key claims:
    • EventStorming extracts knowledge from peoples' heads to break down organizational and technical silos.
    • Pivotal events mark the boundaries where information shifts across contexts.
  • Examples:
    • Ship docked, resupply started, resupply finished
  • Terminology:
    • EventStorming
    • Pivotal Event
    • Bounded Context
    • Hotspot
    • Opportunity
  • Why it matters: EventStorming helps teams align business language and discover domain models collaboratively.

Event Sourcing and Tombstones

  • Explanation: Defines event sourcing as storing state changes as a sequence of events rather than current state, and explains tombstone events for marking data deletion or non-existence.
  • Key claims:
    • Event sourcing stores history of state changes, allowing state reconstruction at any point in time.
    • Tombstone events indicate that data is no longer present or valid in a stream.
  • Examples:
    • USS Enterprise state updates vs. event logs
    • Kafka tombstone error handling pattern 4
  • Terminology:
    • Event Sourcing
    • Stateful Entity
    • Sourced Entity
    • Tombstone Event
    • Versioning
  • Why it matters: Event sourcing provides robust auditing, debugging, and temporal querying capabilities.

Event Granularity and Domain Events

  • Explanation: Discusses the continuum of event payload sizes from notifications to event-carried state transfer, and argues that events should be designed like APIs.
  • Key claims:
    • Event granularity ranges from minimal notifications to full event-carried state transfer.
    • Events should be designed as small as possible and as large as necessary.
    • Domain events are integration events that domain experts care about and should be designed like public APIs.
  • Examples:
    • Clickbait notifications vs. kitchen-sink events
  • Terminology:
    • Event Granularity
    • Notification
    • Event-Carried State Transfer
    • Domain Event
    • Integration Event
  • Why it matters: Proper event granularity balances network overhead with consumer coupling risks.

Key Points

Events represent past facts, not future intentions

  • Explanation: Confusing commands (intent) with events (facts) leads to architectural tightly-coupled anti-patterns.
  • Evidence: Comparison of command request-response vs event publish-subscribe models.
  • Practical implication: Always name events in the past tense (e.g., PreferenceChanged).

Event sourcing mirrors version control systems like Git

  • Explanation: Instead of storing current state in a table row, event sourcing stores every state change event in order.
  • Evidence: Comparison of stateful database tables versus event stream history logs.
  • Practical implication: Enables complete audit trails and time-travel debugging.

Events need careful granularity design

  • Explanation: Too little data requires costly callbacks; too much data increases coupling and privacy risks.
  • Evidence: The event granularity continuum from notifications to event-carried state transfer.
  • Practical implication: Design events to be as small as possible and as large as necessary.

Examples & Case Studies

Java EventObject and PreferenceChangeEvent introduced in JDK 1.1 in 1997

  • Illustrates: Early computing usage of event-driven patterns for UI preference updates.
  • Lesson: Event-driven programming has deep roots in standard libraries long before modern microservices.

Star Trek Captains Logs in message queues

  • Illustrates: How message logs with offsets allow multiple consumers to track state at their own pace.
  • Lesson: Message logs retain history allowing consumers to replay or recover from failures easily.

Actionable Takeaways

  • Immediate:
    • Name events in the past tense to reflect immutable facts.
    • Avoid chatty back-and-forth callbacks by choosing appropriate event payload sizes.
  • Strategic:
    • Treat events like public APIs with clear versioning and domain boundaries.
    • Use EventStorming to break down organizational silos and discover bounded contexts.
  • Questions to investigate:
    • How do our current event schemas handle versioning and backward compatibility?
    • Are we misusing commands as events in our microservice communication?

Idempotency under competing consumers vs. ordered log offsets

Research question

Under what delivery semantics do competing-consumer queues versus offset-based message logs produce duplicated or lost side effects, and what minimal consumer contract (idempotency key, dedupe window, offset checkpoint) makes each equivalent in observable effect?

Why

The infrastructure choice is usually made on vendor convenience rather than on which failure mode the team can actually tolerate; a formal contract per topology turns an architectural debate into a testable property.

The event/command boundary as a mechanically enforceable invariant

Research question

Can a small set of syntactic rules on message names, payloads, and addressing (no target, no imperative verb, past tense, no response channel) predict measured coupling between producers and consumers better than team self-classification as 'event-driven'?

Why

If intent-versus-fact is detectable in the schema, teams can lint architecture decisions at the artifact level instead of relitigating terminology in design reviews.

Event granularity metrics and schema-evolution cost

Research question

Do measurable granularity properties of an event catalog (fields per event, state-carrying versus delta-carrying payloads, fan-out per event type) predict the rate and breakingness of schema changes over a release cycle?

Why

Granularity is currently an intuition handed out as a guideline; if it has proxies, it becomes a design metric that can be budgeted and regression-tested like latency.

Correcting immutable published facts: tombstones, compaction, and compensating events

Research question

What correction protocol — tombstone event, compaction rule, schema-versioned superseding event, or compensating event — keeps a log immutable in spirit while allowing erroneous or legally-retracted data to be neutralized, and how does each behave for replaying consumers?

Why

Immutability is the property teams cite when adopting event sourcing, yet every real system eventually needs to retract or repair a fact; the correction mechanism is what determines whether replay is still trustworthy.

Article ideas

Your Event-Driven Architecture Is a Command Bus With Extra Steps

Most systems labeled event-driven are command-driven with a broker inserted; the tell is not the topology but the naming and payload, and applying event/command disambiguation rules typically reveals that consumers are coupled to producer intent rather than to facts.

Angle

Audit an existing 'event-driven' system by rewriting its message catalog into past-tense facts and counting how many require a target or an expected response — each one is a hidden command.

Source video ↗

Immutability Is a Promise You Can't Keep Without a Retraction Protocol

Declaring events immutable is only defensible when the design also specifies how a wrong, superseded, or legally-retracted fact is neutralized — tombstones, compaction, superseding versions, or compensating events — otherwise teams quietly mutate history and destroy replay's value.

Angle

Walk through each correction mechanism against the question 'what does a consumer replaying from offset zero see?' and show where immutability claims break.

Source video ↗

Queues and Logs Are Not Interchangeable, and the Difference Is Your Idempotency Bill

Choosing pub-sub streaming over point-to-point queuing is a decision about replay and independent consumption, not throughput; teams that pick by familiarity pay for it in duplicate side effects and missing replay, and the cost is quantifiable before migration.

Angle

Compare competing-consumer removal semantics against offset-based independent reads and derive the idempotency contract each topology forces on the consumer.

Project ideas

3

Event Lint

new

A static checker over message names, schemas, and addressing headers can classify messages as intent or fact with high agreement against human review, and the share of intent-shaped messages in a catalog correlates with measured producer-consumer coupling.

Proof of concept

CLI that parses a message catalog (topic names, JSON schemas, addressing fields) and flags imperative verbs, explicit target fields, and response/reply channels; run it over several real catalogs and compare its classification with two reviewers' labels.

Measurement

Inter-rater agreement (Cohen's kappa) between lint verdicts and expert labels, plus correlation between intent-message share and number of consumer code paths that must change when a producer changes its schema.

Source video ↗

Topology Replay-Diff Harness

beyond-evals

The same consumer logic deployed against a queue with competing consumers and against an offset-based log will diverge in observable side effects under injected duplicate and out-of-order delivery, and the divergence is fully predicted by whether the consumer is idempotent.

Proof of concept

Test harness that runs one consumer implementation under both topologies, injects redelivery, reordering, and consumer restart, and diffs the resulting external side-effect ledger.

Measurement

Count and kind of duplicate or missing side effects per topology per injected fault, and the fraction of failures eliminated by adding a dedupe key or offset checkpoint.

Source video ↗

Retention & Retraction Gate

gatehouse

A deploy-time gate that requires every published event stream to declare retention, tombstone/compaction, and correction semantics will reduce the number of streams whose full replay cannot reconstruct a consistent state.

Proof of concept

Policy check integrated into a schema registry or CI: each event stream must carry a machine-readable retention and retraction declaration; a replay audit job reconstructs state from offset zero for conforming and non-conforming streams.

Measurement

Percentage of streams passing replay reconstruction before and after the gate is enforced, and number of deploys blocked or remediated in the first quarter.
