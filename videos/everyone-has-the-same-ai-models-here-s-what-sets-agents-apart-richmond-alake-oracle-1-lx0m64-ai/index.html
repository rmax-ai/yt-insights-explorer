Summary

Overview

  • Speaker: Richmond Alake
  • Channel: AI Engineer
  • Main topic: Agent architecture, memory, control planes, and intelligence planes using Oracle AI Database
  • Purpose: Educate AI engineers on moving beyond basic prompting and control planes toward the intelligence plane (knowledge, memory, and learning) to build superior, secure, and production-ready AI agents. Richmond Alake discusses how as foundational AI models commoditize and everyone has access to the same LLMs, differentiation in AI agents comes down to architecture: specifically the introduction of the Intelligence Plane alongside the Control Plane and Data Plane. He explores agent memory taxonomy, continuous learning, deep data security, and how Oracle AI Database tools enable building production-grade agents.

Topic Map

Agent Memory Taxonomy

  • Explanation: Defining agent memory across short-term (working memory, semantic cache) and long-term (semantic, episodic, procedural) structures, governed by the four R's: retain, reuse, recall, and refine.
  • Key claims:
    • Agent memory is how an agent retains, reuses, refines, and recalls what it learns across turns, sessions, and agents.
    • Memory management is critical for structuring agent workflows and reducing token costs.
  • Examples:
    • Short-term working memory vs long-term episodic or procedural memory.
  • Terminology:
    • agent memory
    • working memory
    • semantic cache
    • episodic memory
    • procedural memory
    • four R's
  • Why it matters: Without structured memory, agents cannot retain context or improve across user sessions.

Control Plane vs Intelligence Plane

  • Explanation: Differentiating between the control plane (governance, identity, tool permissions, and guardrails) and the intelligence plane (knowledge, memory, and continuous learning).
  • Key claims:
    • The control plane governs what an agent may do: who it is, what it may call, spending limits, and auditing.
    • Information does not equal intelligence; having the same models and data does not grant competitive advantage without the intelligence plane.
    • The intelligence plane decides what an agent knows, what it remembers, what it is allowed to see, and how it gets better over time.
  • Examples:
    • The historical parallel of Washington OP-20-G (control) vs Pearl Harbor Station HYPO (intelligence) decoding 'AF' as Midway during WWII.
  • Terminology:
    • control plane
    • intelligence plane
    • identity and access
    • policy and guardrails
    • continuous learning
  • Why it matters: Engineers need to build beyond orchestration and control to incorporate knowledge, memory, and learning into agent architectures.

Software Factory and Agent Workflows

  • Explanation: Applying Bob Bemer's 1968 software factory concept to AI agent production lines where specialized agents handle planning, building, and testing under human review gates.
  • Key claims:
    • A software factory is a production line where AI agents build software with specific tools, memory, and checks.
    • Humans decide the work and sign off on what ships to production.
  • Examples:
    • Plan agent, build agent, and test agent working in parallel with review gates.
  • Terminology:
    • software factory
    • production line
    • review gate
    • work queue
  • Why it matters: Enables reliable, repeatable software generation by chaining specialized agent roles.

Oracle AI Database & Deep Data Security

  • Explanation: Leveraging Oracle AI Database features for deep data security, private inference containers, ontology, semantic layers, and continual learning.
  • Key claims:
    • Oracle Deep Data Security propagates user permissions and row/column security policies into agent memory and vector searches.
    • Private AI Services Containers allow hosting LLMs, embeddings, and rerankers securely on-prem or in-cloud within organizational data boundaries.
  • Examples:
    • Governed analyst vs naive analyst querying financial data with and without ontology and semantic layers.
  • Terminology:
    • Oracle AI Database
    • deep data security
    • private AI services container
    • ontology
    • semantic layer
    • tokenomics
  • Why it matters: Ensures enterprise-grade security, compliance, and accurate data interpretation for mission-critical workflows.

Key Points

Agent = Model + Harness

  • Explanation: The model provides core intelligence, while the harness (tools, memory, checks) turns it into an operational agent.
  • Evidence: Equation presented in speaker slides outlining agent architecture components.
  • Practical implication: Engineers must focus heavily on building robust harnesses around foundation models.

Information != Intelligence

  • Explanation: Having access to the same data and models does not mean agents arrive at correct, secure, and optimal conclusions without structured intelligence layers.
  • Evidence: Historical WWII Station HYPO vs Washington example and financial analyst demo showing 97% vs 33% accuracy.
  • Practical implication: Invest in ontologies, semantic layers, and memory engineering rather than relying solely on base LLM capabilities.

Memory Traces as Training Data

  • Explanation: Capturing agent memory traces, corrections, and feedback provides the exact fine-tuning data needed to improve models over time.
  • Evidence: Demonstration of fine-tuning routing and decision models using recorded conversation memory and classifications.
  • Practical implication: Teams should log and convert agent memory and interactions into fine-tuning datasets.

[A]Architecturehigh noveltymoderate evidence

The intelligence plane is a distinct architectural layer from the control plane: the control plane governs what an agent may do (identity, tool permissions, spending limits, audit), while the intelligence plane governs what the agent knows, remembers, is permitted to see, and how it improves over time.

Why it matters

It separates two concerns that are commonly collapsed into 'orchestration' plus 'a vector store', giving memory, ontology, and learning a first-class boundary with its own responsibilities and its own security surface.

Generalization

Any production agent stack can be evaluated by asking which plane a given capability lives in; capabilities that mix governance and knowledge semantics tend to be where permissions bugs and accuracy regressions originate.

[M]Mechanismhigh noveltymoderate evidence

Authorization should be enforced inside the data/memory layer so that agent memory retrieval and vector search inherit the invoking user's row/column entitlements, rather than relying on prompt-level or orchestration-level filtering.

Why it matters

Retrieval is where most enterprise data leakage in agent systems would occur; enforcing entitlements at the storage/query layer means a compromised or confused agent cannot retrieve documents the user was never allowed to read.

Generalization

Treat memory as governed enterprise data with the same access policies as primary records, so that any agent, tool, or sub-agent reading memory is constrained identically to a human analyst.

[M]Mechanismhigh noveltymoderate evidence

Recorded agent memory traces, corrections, and user feedback are directly usable as fine-tuning data for routing and decision models, making the memory store a training-data pipeline rather than a passive cache.

Why it matters

It converts runtime telemetry into a closed improvement loop and reframes memory schema design as a data-labeling decision: what you log determines what you can ever learn from.

Generalization

Instrument the harness so every decision point (routing, classification, tool selection) emits a labeled trace with an eventual correction signal; the same logs then serve observability and continual learning.

Article ideas

3

Your Vector Store Is Not a Memory System

Treating agent memory as an application-side vector cache outside enterprise governance is the largest latent data-leakage path in agent systems; memory is governed enterprise data that must inherit row/column entitlements for every memory type — working memory, semantic cache, and long-term semantic, episodic, and procedural stores — during recall, not a cache to be filtered in the prompt.

Angle

Take the four R's (retain, reuse, recall, refine) and show that each one has a permission question attached, then argue that the correct enforcement point is the data layer rather than orchestration code.

Source video ↗

Information Is Not Intelligence: Budget for the Semantic Layer, Not the Model Swap

As foundation models commoditize, the reported 97% vs 33% accuracy gap on the same model and data shows the dominant lever is domain ontology and semantic definition, and because the same change cuts token consumption, semantic modeling is the rare investment that improves correctness and unit cost simultaneously.

Angle

Reframe the buy-vs-build conversation: a model-selection review is mispriced compared with a domain-modeling review, and the pass/fail test is accuracy and tokens per query before and after adding defined concepts.

Two Planes, One Interface: How to Split Control from Intelligence Without Creating an Authorization Gap

The control-plane/intelligence-plane split only works if the boundary specifies how a knowledge request still passes control-plane authorization; collapsing the two into a single orchestration layer hides the seam, but splitting them without a delegation interface moves permissions bugs to the seam instead of removing them.

Angle

Use the OP-20-G versus Station HYPO parallel to argue that separate missions require explicit handoff protocols, then specify the handoff as authorization delegation, memory schema contract, and semantic layer API.

Ontology A/B Rig

beyond-evals

On a fixed financial query set with a frozen base model and identical raw data, adding an ontology/semantic layer increases answer accuracy by a large margin and reduces tokens per query versus an agent querying raw tables; the effect is attributable to the semantic layer and not to prompt or model changes.

Proof of concept

Build two agents over the same open financial dataset: a naive agent that writes raw table queries and a governed agent that queries defined entities and metric definitions from a hand-built ontology. Run both against an identical query set with logging of accuracy, tokens, and error taxonomy per query.

Measurement

Accuracy per query with a fixed rubric, tokens in/out per query, and a per-error-category breakdown, reported as before/after distributions over the same query set.

Entitlement Leak Harness

gatehouse

Even with row/column policies enforced at the data layer, restricted documents that are semantically near permitted queries can be inferred from retrieval scores, reranker outputs, or cached memory summaries, producing a measurable leakage rate above zero.

Proof of concept

Seed a governed corpus with restricted documents placed as near neighbors of permitted queries. Issue permitted queries as a low-entitlement principal and probe whether ranking position, score deltas, reranker output, and cached summaries reveal restricted content. Compare against a no-policy baseline to confirm the harness can detect the leak at all.

Measurement

Leakage rate per channel (score, reranker output, cache summary) across the adversarial query set, plus false-positive rate on the no-policy baseline as a harness sanity check.

Trace-to-Dataset Loop

movement-lab

Fine-tuning a routing/decision model on filtered memory traces and user corrections improves routing accuracy over a frozen prompt-only baseline, and the improvement persists only above a minimum trace volume and only with deduplication and label-provenance filtering applied.

Proof of concept

Instrument a harness so every routing and tool-selection decision emits a labeled trace with an eventual correction signal. Build a trace-to-dataset pipeline with configurable dedup and provenance filters, fine-tune a small routing model at several data volumes, and evaluate against the frozen baseline.

Measurement

Routing/decision accuracy versus the frozen baseline at each trace volume, with and without filtering, plus a regression check for degradation of out-of-distribution routing cases.

Plane Boundary Portability Kit

new

The control-plane/intelligence-plane split can be implemented on an open-source vector store plus a policy engine with a specified authorization-delegation interface, reproducing the governance properties claimed for a single-vendor stack without vendor-specific features.

Architectural implications

4

Memory is currently often implemented as an application-side vector store outside enterprise governance.

Before

Agent memory lives in a separate vector database, with access control enforced in application code or prompts.

After

Memory lives in the enterprise database alongside records, inheriting row/column entitlements and policy for retrieval and vector search.

Consequence

Fewer leakage paths and one governance model, but the memory layer must now be schema-managed and migrated like primary data rather than treated as an ephemeral cache.

Source video ↗

Control and intelligence concerns are typically tangled in a single orchestration layer.

Before

Orchestration code handles tool permissions, identity, memory, retrieval, and learning heuristics together.

After

A control plane owns identity, tool permissions, spend limits, and audit; an intelligence plane owns ontology, memory, semantic layer, and the learning loop.

Consequence

Clearer ownership and testability per plane; requires defining the interface where a knowledge request must still pass control-plane authorization.

Source video ↗

Fine-tuning data is usually sourced from curated datasets rather than production telemetry.

Before

Improvement requires assembling labeled datasets separately from the running system.

After

Memory traces and corrections emitted by the harness become the training set for routing and decision models.

Consequence

Faster improvement loops, but memory retention policy, PII handling, and label quality become upstream dependencies of model training.

Source video ↗

Inference and embedding/reranker serving are usually outsourced to third-party APIs.

Before

LLMs, embeddings, and rerankers are called from external providers across organizational data boundaries.

After

Private AI services containers host models on-prem or in-cloud within organizational boundaries.

Consequence

Stronger compliance and data-residency guarantees, at the cost of owning capacity planning, upgrades, and serving reliability.

Tradeoffs and failure modes

4

Ontology and semantic layer investment

Benefit

Large accuracy gains and sharply reduced token consumption on the same model and data.

Cost or risk

Requires upfront domain modeling (entities and definitions) before agents can query, and the model must be maintained as the domain changes.

Source video ↗

Data-layer security propagation

Benefit

Agents inherit existing row/column policies, so retrieval and vector search cannot exceed the user's entitlements.

Cost or risk

Couples agent memory design to database security policy; policy changes in the data layer now silently alter agent behavior and recall.

Source video ↗

Human review gates in agent software factories

Benefit

Humans decide the work and sign off on what ships, keeping autonomous generation auditable.

Cost or risk

The gate becomes the throughput bottleneck of the production line, capping how much parallelism the plan/build/test agents can exploit.

Source video ↗

Owning memory and inference infrastructure

Benefit

Maintaining security and compliance by keeping memory and inference inside organizational boundaries.

Cost or risk

Shifts operational burden (serving, scaling, model rollout) onto the team, reducing the ability to swap in newer hosted models quickly.
