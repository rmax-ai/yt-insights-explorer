Overview

  • Speaker: Eduardo Simon & Javier Casal
  • Channel: AI Engineer
  • Main topic: Building practical, structured, and compliant AI agent workflows in-house at Flywire
  • Purpose: To share Flywire's engineering journey and technical architecture for building practical, compliant, and reliable AI agent workflows rather than open-ended LLM loops. Eduardo Simon and Javier Casal from Flywire discuss their AI platform 'Orbit', which transitions AI agents from open-ended autonomous 'autopilot' loops into structured, workflow-driven tools. Operating in the heavily regulated global payments space (PCI DSS, SOC II), Flywire requires strict security, data privacy, and deterministic control. Orbit uses YAML-defined workflows, reuses the Claude Agent SDK with strict network, tool, and skill restrictions, and implements isolated evaluations and YAML-first developer tooling.

[A]Architecturehigh noveltymoderate evidence

Agent capability should be bounded per workflow step, not per agent: each LLM step declares its own allowed network access, tools, skills, and MCP servers in the YAML definition, so the same harness can be read-only in one step and write-capable in another.

Why it matters

Least-privilege at step granularity shrinks the blast radius of a single bad model decision without requiring a separate agent per permission set, and makes permission review a plain code-review activity.

Generalization

Treat tool/network permissions as a per-node property of the workflow graph rather than a global config of the agent runtime; this composes with any harness that supports tool allowlists.

Deep dives

4

Enforcement layer for per-step capability grants

Research question

When a workflow node is granted a read-only tool set, at which layer (harness allowlist, sandbox syscall/filesystem boundary, or orchestrator) must the restriction be enforced so that tool chaining, MCP servers, or prompt injection cannot escalate to file writes or network egress?

Why

Per-step least privilege is only worth the YAML complexity if the restriction is adversarially sound; if the boundary lives in the prompt or the harness's cooperative tool filter, a compliant-looking workflow file is a false sense of security in a PCI/SOC-scoped environment.

Source video ↗

Correlation between step-level replay evals and end-to-end workflow outcomes

Research question

Do regressions detected by replaying historical state into individual LLM steps predict actual end-to-end workflow failures in production, and what is the false-negative rate of a step-only eval suite relative to end-to-end scenario testing?

Why

The whole economic argument for step-level evaluation rests on an unmeasured assumption of agreement; if step replay systematically misses cross-step interaction failures, teams will ship regressions that their tests declare green.

Source video ↗

Schema violations as a first-class failure mode with a recovery budget

Research question

What is the observed schema-validation failure rate per LLM step in production, and how should the retry/fallback split be budgeted so that a failing step degrades deterministically instead of converting into retry storms or silent semantic drift?

Why

Schemas are described as the bridge that makes probabilistic output safe to branch on, but the operational cost of that bridge (retry latency, token spend, fallback quality) determines whether the boundary is a control or just a tax.

Source video ↗

Expressivity ceiling of a single-file declarative agent spec

Research question

At what workflow complexity (loop depth, dynamic fan-out, conditional branching over structured state) do authors of YAML-defined agents start needing escape hatches into general-purpose code, and how much reviewability is lost when they do?

Why

The governance benefit of YAML-reviewed agents is bounded by the schema's expressiveness; knowing where that ceiling sits tells teams when to split a workflow versus when to reach for code, and prevents the schema from becoming a leaky abstraction with hidden scripts.

Article ideas

4

Least Privilege Belongs on the Workflow Node, Not the Agent

Granularity of the permission boundary, not the strength of the model, determines the blast radius of an agent failure; declaring tools, network, and MCP access per step lets one harness be read-only in one node and write-capable in another, which is strictly better than either a globally-permissioned agent or a fleet of single-purpose agents each with its own deploy surface.

Angle

Reframe agent permissions as a property of a node in a workflow graph rather than a property of the runtime, and show why that composes with code review, rollback, and audit in a way that global allowlists cannot.

Source video ↗

Your Agent Evals Are Integration Tests When They Should Be Unit Tests

Teams building agent workflows default to synthetic end-to-end scenarios because that is the only test shape they know, then abandon evals as too expensive and too noisy; capturing per-step inputs from real production runs and replaying them turns each node into a regression unit test, and the residual risk of missed cross-step interactions is a measurable quantity rather than an article of faith.

Angle

Argue for a record-and-replay eval pyramid over agent workflow graphs, and specify what must be captured per node to make replay faithful (state, context, tool observations, not just the prompt).

Source video ↗

Adopt the Loop, Own the Control Plane

The build-versus-adopt question for an agent harness is usually answered wrong: teams reimplement a reasoning loop they cannot maintain and then have no budget left for the control layers that actually determine whether the system is safe. Reusing a mature harness and constraining it externally with per-step permissions, strict schemas, and step boundaries moves engineering effort to the only part that is genuinely yours.

Angle

Frame the architecture as an adopted, untrusted reasoning core surrounded by an owned control plane, and enumerate what must be built on the outside to make that posture defensible.

Source video ↗

YAML Is a Governance Surface, Not a Config Format

Declarative agent specs are worth their constraints because they co-opt Git as the audit, review, and rollback mechanism for AI behavior; the win is not readability but the fact that a behavior change becomes a diffable merge request, and the cost is a hard expressivity ceiling that teams should plan for instead of discovering mid-migration.

Angle

Position agent specification files as infrastructure-as-code and derive the concrete review practices (blast-radius review, permission diffs, rollback) that follow for free.

Source video ↗

Project ideas

3

StepBoundary

gatehouse

A workflow node granted only read tools can be driven to perform a file write or outbound network call via tool chaining, MCP server invocation, or injected instructions when the restriction is enforced at the harness allowlist layer, but cannot when the same grant is enforced at the sandbox boundary — so the escape rate is a function of enforcement layer, not of the permission declaration.

Proof of concept

Build a minimal 3-step YAML workflow (read-only code search node, reasoning node, write node) running on a containerized agent harness, implement the per-step restriction twice — harness tool-allowlist only, and harness allowlist plus a syscall/egress-denying microVM sandbox — and run a fixed red-team suite of escalation attempts (MCP shim, prompt injection in retrieved file content, tool-argument confusion) against both configurations.

Measurement

Successful escapes per 100 attempts per enforcement layer, broken down by attack vector; a nonzero harness-only rate with a zero sandbox rate confirms the hypothesis, while any sandbox escape falsifies it.

Source video ↗

Replay Agreement Study

beyond-evals

Step-level replay evaluations rank a set of candidate prompt/model changes in the same order as end-to-end workflow evaluations with high agreement, but under-report failures whose cause is inter-step interaction — giving a measurable false-negative rate rather than an assumed one.

Proof of concept

Instrument a 4-5 step internal workflow to persist per-node inputs and outputs from production, build a replay harness that injects historical state into single nodes, then take 20 candidate changes (prompt edits, model swaps) and evaluate each both by step-level replay and by end-to-end runs on a held-out set of real trigger events.

Measurement

Spearman rank correlation between step-level and end-to-end pass rates across the 20 changes, plus the count of changes that pass all step replays but fail end-to-end; report the false-negative rate and per-evaluation cost delta.

Source video ↗

Schema Recovery Budget

new

Schema-validation failures cluster in a small number of steps and failure classes, so a per-step recovery policy tuned to the observed failure taxonomy (bounded retry for malformed output, fallback for semantic mismatch) reduces failed workflow runs more than a uniform retry-everything policy at lower token cost.

Proof of concept

Instrument a schema-validated workflow to log every validation failure with the offending payload and the resolved recovery path, classify failures into malformed-JSON, missing-field, enum-mismatch, and semantically-wrong-but-valid, then A/B a uniform 3x retry policy against a class-specific retry/fallback policy.

Measurement

Validation failure rate per step, recovery success rate and additional tokens consumed per failure class, and end-to-end workflow completion rate under each policy; the hypothesis holds if class-specific recovery improves completion rate at lower mean token cost per successful run.

Architectural implications

3

Responsibility for control flow is moved out of the LLM and into deterministic code that invokes small, bounded LLM steps.

Before

An autonomous agent loop decides its own next action, tool, and termination condition.

After

A workflow skeleton of deterministic steps owns sequencing; the LLM is called only at nodes where reasoning is required, with typed input and schema-validated output.

Consequence

Cost and token usage drop, behavior becomes reproducible and debuggable, and failures localize to a single node—at the cost of losing open-ended exploration capability.

Source video ↗

Session state is externalized from the runtime, separating orchestration, agent runtime, and session state.

Before

A single ECS Fargate container holds both the harness and the runtime, so a run's lifespan is tied to one container.

After

Orchestration schedules work; execution happens in isolated, resumable microVMs; session state is addressable independently.

Consequence

Parallel agent executions can be sandboxed and resumed, but the platform now needs explicit state serialization and lifecycle management.

Source video ↗

The agent specification file becomes the unit of review and governance.

Before

Agent behavior is defined in prompts or UI configuration, outside normal code review and change management.

After

Each agent is a single YAML file in the repository, reviewed through merge requests like any other code.

Consequence

Audit trails, rollback, and blast-radius review come for free from the Git workflow—but expressiveness is capped by what the YAML schema can represent.

Source video ↗

Tradeoffs and failure modes

4

Workflow rigidity versus agent autonomy

Benefit

Deterministic control, safety, lower token cost, and reviewable behavior in a regulated domain.

Cost or risk

Workflows that hit an unanticipated situation have no path forward unless the YAML author anticipated it; open-ended discovery tasks are out of scope by construction.

Source video ↗

Isolated step evaluation versus end-to-end validity

Benefit

Cheaper, more reproducible, and faster regression detection on prompt and model changes.

Cost or risk

Step-level replay with historical state can miss failures that only emerge from interaction between steps, and the historical corpus encodes past distributions rather than new inputs.

Source video ↗

Adopting a third-party harness

Benefit

Mature, well-tested agent loop without building one; engineering effort goes to workflow definition.

Cost or risk

Security guarantees depend on externally applied control layers (network, tool, skill, MCP restrictions), and the team inherits the vendor's abstraction and release cadence.

Source video ↗

Platform substrate choice (Fargate vs Lambda microVMs)

Benefit

MicroVMs restore missing package-manager capability and provide resumable, isolated execution.

Cost or risk

Introducing a second compute substrate alongside Fargate increases operational surface area and adds state-handoff complexity between runtime and session store.
