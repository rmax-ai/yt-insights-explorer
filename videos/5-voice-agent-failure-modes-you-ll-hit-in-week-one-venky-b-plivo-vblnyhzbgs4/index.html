Overview

  • Speaker: Venky B

  • Main topic: Voice Agent Failure Modes and Solutions
  • Purpose: To educate AI engineers on the practical production hurdles of building real-time voice AI agents and provide architectural strategies to mitigate latency, transcription errors, structured data collection issues, text-to-speech input formatting, and turn-taking failures. Venky B, founder and COO of Plivo, discusses five critical failure modes encountered when deploying voice AI agents from proof of concept to production. Drawing on Plivo's 14 years in telephony and handling over a billion voice calls monthly, Venky breaks down latency, brittle transcription, data collection challenges, input normalization to TTS, and turn detection/barge-in handling, offering concrete engineering strategies for each.

Failure Mode 1: Latency

  • Explanation: Examines the latency budget of the typical voice AI pipeline (Telephony -> STT -> Turn Detection -> LLM -> TTS), noting the time-to-first-audio (TTFA) threshold and tradeoffs between cost, intelligence, and latency.
  • Key claims:
    • TTFA under 550ms feels natural/good; 750ms-1.2s causes conversation drag; over 1.2s causes users to hang up.
    • Frontier models (OpenAI, Claude, Gemini) have high TTFA (450-500ms) unless using dedicated capacity (Cerebras, Groq).
    • Open-source models like Qwen 3.5 and Gemma 4 offer good speed-intelligence tradeoffs, while mixture-of-experts (MoE) models need careful sizing.
  • Examples:
    • Using frontier models vs. specialized high-speed inference accelerators like Cerebras and Groq.
  • Terminology:
    • TTFA (Time to First Audio)
    • STT
    • TTS
    • turn detection
    • mixture of experts
    • frontier models
  • Why it matters: Latency is the primary reason users abandon voice agents in production.

Failure Mode 2: Brittle Transcription

  • Explanation: Discusses why speech-to-text (STT) engines fail on real-world audio with accents, background noise, domain vocabulary, proper nouns, phone numbers, addresses, and code-switched languages.
  • Key claims:
    • Best STTs achieve 4-6% Word Error Rate (WER) on clean eval sets, but real-world calls perform much worse due to accent and noise.
    • Proper nouns, jargons, phone numbers, and code-switching break downstream LLM understanding.
    • Dynamic keyword/phrase boosting and post-processing via LLM domain context are essential.
  • Examples:
    • Hindi spoken in Devanagari script vs. Roman script leading to transcription and translation errors.
    • Phone number digit transcription errors like '415 e 6942 won 0'.
  • Terminology:
    • WER (Word Error Rate)
    • STT transcription
    • code-switching
    • dynamic keyword boosting
    • transliteration
    • post-processing
  • Why it matters: If transcription is wrong, the entire downstream agent response fails.

Failure Mode 3: Collecting Data

  • Explanation: Explores structured data extraction from unstructured voice conversations, drawing parallels to frontend form fields, Pydantic, Zod, and data classes.
  • Key claims:
    • Treat voice data collection like a typed schema UX problem rather than hoping an LLM parses transcripts correctly.
    • Constrained capture (defining required fields, types, validation rules, allowed values) increases extraction accuracy from 30% to 95%.
    • Relative date values (e.g., 'next week Wednesday at 8') require normalization and confirmation mechanisms.
  • Examples:
    • Capturing complex names like 'Aleksandr Szymonowicz' or relative date-time values.
    • Using unit tests at a field level to ensure extraction reliability.
  • Terminology:
    • structured data extraction
    • Pydantic
    • Zod
    • dataclass
    • constrained capture
    • unit testing
  • Why it matters: Open-ended prompt engineering for data collection results in hallucinated or malformed data.

Failure Mode 4: Input to TTS

  • Explanation: Examines issues when sending raw LLM output directly to Text-to-Speech (TTS) engines without a normalization layer.
  • Key claims:
    • LLM output should never go to TTS directly; a separate normalization layer is required.
    • Emojis and markdown must be stripped before synthesis.
    • Custom pronunciation dictionaries and speed control (e.g., slowing down to 0.8x or 0.7x for names and numbers) prevent pronunciation failures.
  • Examples:
    • An agent failing to pronounce difficult names like 'Balasubramanian' or company names like 'Plivo' correctly.
    • Normalizing messy stuff like emails, currencies, dates, and numbers.
  • Terminology:
    • TTS synthesis
    • normalization layer
    • pronunciation dictionary
    • prosody
    • speed scaling
  • Why it matters: Poor pronunciation ruins user trust immediately ('if your agent can't pronounce your name, you've already dropped the ball').

Failure Mode 5: Turn Detection and Barge-in

  • Explanation: Covers end-of-turn detection challenges (VAD vs semantic vs acoustic models) and handling interruptions/backchannels without breaking conversational flow.
  • Key claims:
    • VAD/silence-based turn detection fires on any pause, cutting users off mid-thought.
    • Semantic and acoustic models predict end-of-turn from words said and prosody (intonation, pitch, rhythm).
    • Backchanneling ('uh-huh', 'mhm') requires classifying interruptions to know whether to stop or keep going.
  • Examples:
    • VAD treating brief pauses or backchannels ('uh-huh', 'okay') as complete interruptions.
    • Managing walkie-talkie-style vs conversational backchanneling.
  • Terminology:
    • turn detection
    • VAD (Voice Activity Detection)
    • semantic turn detection
    • backchanneling
    • barge-in
    • prosody
  • Why it matters: Natural conversation pacing depends on accurate turn-taking and backchannel management.

Key Points

Latency Budget Management

  • Explanation: Time-to-first-audio (TTFA) must remain under 550ms for natural conversation; anything over 1.2s causes hang-ups.
  • Evidence: Customer telemetry across over a billion calls on Plivo's platform.
  • Practical implication: Engineers must carefully choose between frontier model intelligence and high-speed inference options like Groq, Cerebras, or smaller open-source models.

Transcription is Brittle

  • Explanation: Even the best STT engines have 4-6% WER on clean data, which degrades significantly with noise, accents, and code-switching.
  • Evidence: Real-world calls involve proper nouns, domain jargon, phone numbers, and multilingual code-switching.
  • Practical implication: Implement dynamic keyword boosting and intelligent LLM-based post-processing layers.

Constrained Data Collection

  • Explanation: Treating voice data collection like a typed schema UX problem drastically improves accuracy.
  • Evidence: Accuracy increases from 30% to 95% when moving from open-ended extraction to typed schema validation (Pydantic, Zod).
  • Practical implication: Define schemas, required fields, and allowed values before asking data from users.

TTS Normalization Layer

  • Explanation: LLM text output cannot be piped directly into TTS without normalization.
  • Evidence: Unfiltered output contains emojis, markdown, unformatted numbers, and mispronounced names.
  • Practical implication: Add a normalization layer to strip markdown/emojis, apply pronunciation dictionaries, and adjust speech rates for names and numbers.

Advanced Turn Detection

  • Explanation: Basic VAD fails by interrupting users on pauses or missing backchannels.
  • Evidence: Semantic and acoustic models are required to analyze prosody and distinguish backchannels from true interruptions.
  • Practical implication: Classify user interruptions to determine whether to stop speaking or continue with backchannels.

Actionable Takeaways

  • Immediate:
    • Never pipe raw LLM output directly into a TTS engine; always use a normalization layer.
    • Strip emojis and markdown from text before TTS synthesis.
    • Implement dynamic keyword boosting in your STT engine for domain-specific vocabulary.
  • Strategic:
    • Treat voice data collection like a typed form schema (Pydantic, Zod) rather than relying on unconstrained prompts.
    • Balance the LLM trilemma (latency, cost, intelligence) by choosing appropriate model sizes or specialized hardware.
    • Move beyond basic VAD by incorporating semantic and acoustic prosody analysis for turn detection.
  • Questions to investigate:
    • How does your current voice agent pipeline handle TTFA latency under load?
    • Are you using typed schemas for data extraction in your voice conversations?
    • How does your system distinguish between a backchannel and a true barge-in interruption?

  • Keep TTFA latency under 550ms for natural conversation flow.
  • Mitigate brittle STT transcription with dynamic keyword boosting and LLM post-processing.
  • Use typed schemas (Pydantic/Zod) for reliable structured data collection from voice.
  • Always normalize LLM text output (strip markdown/emojis, apply pronunciation dictionaries) before TTS.
  • Upgrade from basic VAD to semantic and acoustic turn detection to handle barge-ins and backchannels.

Core insights

6
[A]Architecturehigh noveltymoderate evidence

Voice data collection should be architected as a typed-schema UX problem rather than an open-ended prompting problem: define required fields, types, validation rules, and allowed values (Pydantic/Zod/dataclass-style), which reportedly lifts extraction accuracy from 30% to 95%.

Why it matters

Shifts responsibility for reliable capture from the LLM's free-form reasoning to an explicit schema contract, making extraction testable, predictable, and less prone to hallucinated or malformed fields.

Generalization

Applies to any agentic system extracting structured entities from unstructured input: constrain the output space and validate at field level rather than trusting the model to infer the schema.

Why it matters

TTFA Stage Budget Analyzer

new

By instrumenting each pipeline stage (telephony, STT, turn detection, LLM, TTS) and swapping inference backends, teams can predict and reduce end-to-end TTFA below 550ms without changing model intelligence.

Proof of concept

Build a reference voice agent pipeline with per-stage timers; run the same conversation scripts across frontier model (OpenAI/Claude/Gemini), dedicated accelerators (Cerebras/Groq), and open-source MoE (Qwen/Gemma); report per-stage latency contributions and total TTFA.

Measurement

Per-stage latency distributions and total TTFA across configurations; correlation between stage reductions and simulated user hang-up rates (e.g., timeout logs).

Schema-Forge: Field-Level Extraction Test Harness

beyond-evals

Defining a typed schema with validation rules and running field-level unit tests on transcribed conversations will achieve >90% field extraction accuracy and localize failures to specific fields, outperforming end-to-end conversation-level evaluation.

Proof of concept

For appointment scheduling, define a Pydantic/Zod schema for required fields (name, date, time, phone); create a test set of 100 transcripts with ground truth; compare open-ended prompt extraction vs. schema-constrained extraction with field-level validation.

Measurement

Per-field precision/recall/F1, overall extraction accuracy, and number of fields requiring manual fallback.

Source video ↗

Turn-Taking Classifier Playground

new

A classifier using prosodic features plus partial transcript tokens can distinguish backchannels from true barge-ins with >85% accuracy, and using it to gate agent stopping behavior reduces perceived interruptions in simulated conversations.

Proof of concept

Collect or simulate call audio with labeled interruptions (backchannel vs barge-in); extract prosody (pitch, energy, rhythm) and lexical features; train a classifier; integrate into a turn-detection module and measure stop/continue decisions against human labels.

Measurement

Classification accuracy, F1, and false-positive/negative rates; user-perceived interruption score in a Wizard-of-Oz study or simulated user hang-up rate.

Proof of concept

Architectural implications

3

LLM output has different formatting requirements than TTS input.

Before

Raw LLM text streams directly into the TTS synthesis call.

After

A dedicated normalization layer sits between the LLM and TTS, handling emoji/markdown stripping, pronunciation dictionaries, and speed scaling.

Consequence

Formatting and prosody concerns are removed from the model; failures become localized and the normalization logic becomes independently testable.

After

Consequence
