Summary

Overview

  • Speaker: Diogo Almeida
  • Channel: AI Engineer
  • Main topic: The state of AI, LLM alignment limitations, and the future of software engineering and agent design
  • Purpose: To challenge current industry assumptions about LLMs, RLHF, and agent design, and to advocate for software engineering practices that prioritize reliability and machine-native optimization over vibe coding. Diogo Almeida, co-founder of TypeSafe AI, presents a provocative critique of current AI trends. He argues that 100% of LLMs are optimized for assistance (RLHF) rather than automation, creating a cognitive dissonance where models are 'too good to be true' at reasoning benchmarks yet 'too bad to be useful' at real-world automation tasks. He compares the current LLM revolution to the discovery of the blue LED—an unexpected primitive that unlocked entirely new capabilities—and outlines a vision for machine-native AI, real software engineering (decomposition, encapsulation, state management), and reliable intelligence.

Key Points

LLMs are optimized for assistance, not automation

  • Explanation: Current training pipelines like RLHF optimize models to be helpful assistants, which makes them unreliable for autonomous execution.
  • Evidence: Infamous failures of AI automation in simple workflows like drive-thrus.
  • Practical implication: Engineers must build systems that integrate code with AI decision-making rather than expecting end-to-end autonomy without verification.

Reliable intelligence vs. general intelligence

  • Explanation: The industry suffers from LLM Stockholm syndrome, focusing on broad capabilities instead of narrow, hyper-reliable intelligence.
  • Evidence: Getting 95% accuracy on general tasks is useless if reliability is needed 100% of the time.
  • Practical implication: Focus engineering efforts on narrow, highly verifiable agent workflows.

Core insights

6
[M]Mechanismhigh noveltymoderate evidence

The post-training objective, not raw model capability, determines whether a model is deployable in an autonomous loop. RLHF trains for *assistance* (helpful, human-in-the-loop, conversational), which produces models that score well on reasoning benchmarks but are structurally unsuited to unverified *automation*.

Why it matters

It reframes agent reliability as a training-objective problem rather than a prompting or scaffolding problem: no amount of harness engineering fully converts an assistance-tuned policy into a reliable automation policy, so harness design must assume and compensate for that mismatch.

Generalization

Whenever a system is optimized against a proxy objective (human preference, helpfulness ratings), downstream autonomous use inherits the proxy's blind spots; the harness must supply the verification the training objective omitted.

Source video ↗
[A]Architecturehigh noveltymoderate evidence

The KV cache is the binding architectural constraint on agents: it is the only memory a model actually has, and it provides neither shared state nor memory management. Agent state therefore has to be an explicit, externally managed artifact rather than something left implicit in context.

Why it matters

It locates the correct architectural boundary: state management, memory lifecycle, and inter-agent sharing belong in the runtime/software layer, not inside the model context. This directly determines where you build persistence, invalidation, and encapsulation.

Generalization

In any system whose long-term memory is a bounded, non-shareable cache, correctness requires an external state authority; treating the cache as the state store produces silent, non-reproducible failures at scale.

Source video ↗
[~]Tradeoffmedium noveltymoderate evidence

Reliability requirements are binary, not average-case: ~95% general-task accuracy is worthless when the workflow demands 100% correctness. This inverts the usual scaling instinct — narrow, hyper-verifiable workflows beat broad, general capability in production automation.

Why it matters

It justifies deliberately constraining agent scope and inserting verification gates, and it explains why benchmark gains do not translate into automation gains for real users.

Generalization

For long-horizon or chained tasks, per-step accuracy compounds multiplicatively; the optimal architecture minimizes chain depth and maximizes per-step verifiability rather than maximizing per-step generality.

Source video ↗
[P]Practicemedium noveltyweak evidence

Task decomposition should be driven by verifiability, not by logical or semantic decomposition: break work into stages whose outputs can be checked, so that each stage boundary is a place where a deterministic or programmatic check can halt or correct the pipeline.

Why it matters

It gives a concrete design rule for agent workflows — the decomposition boundary is chosen for its testability, which is what makes the compound system reliable despite unreliable components.

Generalization

Any composition of probabilistic components should be partitioned at boundaries where outputs are machine-checkable; this is the same principle as designing for testability in classical software.

Source video ↗
[O]Mental Modelmedium noveltyweak evidence

The 'bitterer lesson': task selection and data dominate compute and algorithm choice. The pre-training task (next-token prediction) versus the alignment task (RLHF) is presented as the decisive variable in what capability emerges.

Why it matters

It shifts engineering leverage away from scale and toward task formulation — i.e., what you ask the model to do and what data you show it — which is an actionable, low-cost lever for teams that cannot train models.

Generalization

When a capability is missing, the first hypothesis should be 'we are training/asking for the wrong task', not 'we need more compute'.

Source video ↗
[>]Predictionhigh noveltyweak evidence

The proposed frontier primitive is semantic dependent typing: types whose validity depends on semantic content and on prior values, applied to LLM inputs/outputs so that a program can statically constrain what a model is allowed to emit at each interface.

Why it matters

If realized, it moves LLM I/O contracts from natural-language prompt instructions (soft, unenforced) to checked interfaces (hard, enforceable), which changes where safety and correctness guarantees live in an agent codebase.

Generalization

Natural-language specifications should be compiled into enforceable interface constraints; anything left in prose is an unverified assumption.

Deep dives

5

Harness-level substitution for task-aligned training

Research question

How much of the assistance-to-automation reliability gap can be closed purely through harness design (verification density, decomposition granularity, external state) versus requiring a differently-tuned policy?

Why

If harness design closes most of the gap, teams that cannot retrain models have a viable path to unattended automation; if it closes little, the entire 'agent framework' investment thesis is misallocated and the bottleneck is post-training objective.

Source video ↗

Verifiability-driven decomposition as the unit of agent design

Research question

Does partitioning a workflow at machine-checkable boundaries (rather than at logically natural boundaries) measurably raise end-to-end success on chained tasks, and how does that gain trade against latency and token cost from extra model calls?

Why

This turns 'agent architecture' from taste into a measurable design variable, and gives a rule a practitioner can apply before writing any code: the stage boundary is chosen for its test, not its semantics.

Source video ↗

External state authority over KV-cache-as-memory

Research question

What lifecycle, serialization, and context-assembly policy for an external state store maximizes multi-turn agent task success while minimizing context tokens, compared against long-context baselines that treat the window as memory?

Why

The KV cache is bounded and non-shareable, so any multi-agent or long-horizon system that leaves state implicit will fail silently and non-reproducibly; making state explicit is the precondition for replay, rollback, and sharing.

Source video ↗

Semantic dependent typing for LLM I/O contracts

Research question

What fraction of LLM input/output can be statically rejected by validity predicates that depend on semantic content and prior runtime values, and how much residual error survives to post-hoc checks?

Why

It relocates safety and correctness guarantees from prose prompt instructions (unenforced) to checked interfaces (enforced), which is the difference between an assumption and a guarantee in an agent codebase.

Source video ↗

Isolating the jagged frontier from benchmark framing

Research question

When the same underlying operation is presented once as a benchmark-style reasoning problem and once as an operational automation step, what is the accuracy gap and how sensitive is it to task framing?

Why

If the frontier's shape changes with framing alone, benchmark scores are not a valid proxy for production readiness and model-selection decisions are being made on a contaminated signal.

Project ideas

4

Verification-Density Ablation Harness

beyond-evals

At fixed model and fixed task, increasing decomposition granularity and verification density raises end-to-end task success on a chained workflow, but with diminishing returns that plateau well below 100% — quantifying exactly how much harness design can substitute for task-aligned training.

Proof of concept

Take one multi-step operational workflow. Run the same model under four configurations: single end-to-end call chain; stage decomposition with no checks; stage decomposition with machine-checkable post-conditions and code-level gating; and stage decomposition plus an external state store. Same model, same task, only harness varied.

Measurement

End-to-end success rate per configuration, per-stage failure localization rate, tokens per successful task, and the residual failure rate at maximum verification density (the plateau that harness design cannot cross).

Source video ↗

Context-Assembly Gateway

gatehouse

An explicit external state store with a defined lifecycle and a context-assembly policy that materializes only what a stage needs will match or beat a long-context baseline on multi-turn agent task success while substantially reducing tokens consumed — and will additionally enable replay and cross-agent state sharing that the baseline cannot express at all.

Proof of concept

Wrap a multi-turn agent workload behind a state service exposing explicit read/write APIs plus an encapsulation boundary per agent role. Context is derived per stage from the store rather than accumulated. Run identical task suites against the same model with a long-context accumulated-window baseline.

Measurement

Task success rate, prompt tokens per turn and per task, degradation curve as task length approaches context limits, and replayability (whether a run can be deterministically reconstructed from stored state).

Source video ↗

Value-Dependent Interface Checker

new

A meaningful fraction of invalid LLM outputs can be rejected statically at the interface — via validity predicates that depend on semantic content and on prior stage values — before any post-hoc evaluation runs, shrinking the error surface that a downstream verifier must handle.

Proof of concept

Implement a constrained-decoding plus schema layer whose type predicates reference runtime values from earlier pipeline stages (e.g., an emitted amount must reconcile against a previously emitted subtotal). Apply it to one narrow, hyper-verifiable workflow and count rejections by category.

Measurement

Share of invalid outputs rejected pre-execution versus only caught post-hoc, false-rejection rate on valid outputs, and end-to-end task success with the checker versus schema-only validation.

Source video ↗

Framing-Paired Frontier Probe

beyond-evals

The same underlying operation presented as a benchmark-style reasoning problem and as an operational automation step yields a significant accuracy gap, which means benchmark scores are a contaminated proxy for production automation readiness.

Proof of concept

Construct paired task sets where each pair is one operation expressed two ways: a benchmark-framed version and an operational-automation-framed version embedded in a realistic workflow. Run many models across both framings.

Measurement

Per-pair accuracy delta between framings, correlation between benchmark-framed score and operational-framed score, and whether models ranked by benchmark score retain that ranking under operational framing.

Architectural implications

3

Agent state currently lives implicitly in the KV cache, which is bounded and not shareable across agents.

Before

Context window treated as the agent's memory; conversation history is the state store.

After

Explicit external state store with defined lifecycle, sharing semantics, and encapsulation boundaries; the model context becomes a derived, disposable view over that state.

Consequence

Enables multi-agent shared state and reproducible replay, but forces engineers to design serialization, invalidation, and context-assembly logic — the new core of agent runtime work.

Source video ↗

End-to-end autonomy is unreliable, but individually verifiable stages are not.

Before

One agent call chain executed end-to-end, with a human reviewing the final output.

After

Pipeline decomposed into stages, each with a machine-checkable post-condition, with code-level decision logic interleaved between model calls.

Consequence

Reliability becomes a property of the harness rather than the model; failures localize to a stage, and rollback/repair is possible without re-running the whole chain.

Source video ↗

RLHF-optimized models are mismatched to autonomous execution.

Before

Assume the best benchmark model is the best automation engine; invest in prompting to close the gap.

After

Treat the model as one unreliable component inside a software system that supplies the verification, state, and control flow the model lacks.

Consequence

Architecture investment shifts from prompt engineering to decomposition, encapsulation, and state management — and model selection becomes a component-selection decision, not a capability-selection decision.

Source video ↗

Tradeoffs and failure modes

4

RLHF / assistance alignment

Benefit

Helpful, steerable, conversational models that are pleasant and safe to interact with.

Cost or risk

Models become optimized for the assistance objective, so they are 'too good to be true' on reasoning benchmarks and 'too bad to be useful' for unattended automation, permanently requiring a human in the loop.

Source video ↗

Optimizing against proxy objectives

Benefit

RLHF provides a tractable, scalable training signal where ground truth is unavailable.

Cost or risk

You inherit the proxy: the model maximizes the measured objective and remains weak on the unmeasured one (autonomous task completion), often without any visible signal until production.

Source video ↗

Vibe coding vs. software engineering discipline

Benefit

Fast iteration and low ceremony when building prototypes and exploring agent behavior.

Cost or risk

Without decomposition, encapsulation, and state management, systems are unverifiable and fail at the reliability levels production automation requires.

Source video ↗

Benchmark-driven evaluation

Benefit

Cheap, comparable, and scalable proxy for model capability and progress tracking.

Cost or risk

Produces cognitive dissonance: superhuman benchmark scores coexist with total failure on simple real-world workflows such as accounting or drive-through automation, so benchmark gains mislead production readiness decisions.
