Summary

Overview

  • Speaker: Andrew Qu
  • Channel: AI Engineer
  • Main topic: Agent building infrastructure and frameworks at Vercel, transitioning from primitive megamprompts to file-system agent architectures and the Next.js for agents framework (Eve).
  • Purpose: To explain the evolution of agent-building methodologies at Vercel and introduce Eve, an open-source framework for building agents using file-system conventions. Andrew Qu, Chief of Software at Vercel, shares the journey of how Vercel tackled agent building. Moving through iterations from naive megamprompts, multi-agent workflows, and specialized tool architectures, Vercel discovered that file-system-based agent runtimes (inspired by Claude Code and Opus 4.5) drastically simplify agent engineering. This realization culminated in Eve, an open-source agent framework that brings Next.js-like file-system routing conventions to agent infrastructure.

Topic Map

The Evolution of Agent Building at Vercel

  • Explanation: Andrew discusses Vercel's exploration into agent building across internal teams like marketing, sales, finance, legal, and data science, starting with the data science team.
  • Key claims:
    • Data teams spent too much time writing SQL queries instead of focusing on high-value analytics.
    • The first attempt at solving agent building involved massive megamprompts passed to LLMs.
  • Examples:
    • Passing a Snowflake schema directly into a system prompt and copying-pasting generated SQL.
  • Terminology:
    • megamprompt
    • system prompt
    • snowflake schema
  • Why it matters: Demonstrates the naive starting point of agent development and highlights the limitations of unstructured prompt engineering.

Multi-Agent Workflows and Their Limits

  • Explanation: Moving beyond single megamprompts, Vercel built chained multi-agent architectures (D0) with dedicated query, planning, execution, and reporting agents.
  • Key claims:
    • Chaining multiple specialized agents allowed for end-to-end loops from user question to answer.
    • Manual mapping of agent workflows hit architectural walls when dealing with complex, unanticipated edge cases.
  • Examples:
    • Query agent passing to planning agent, passing to execution agent, passing to reporting agent.
  • Terminology:
    • query agent
    • planning agent
    • execution agent
    • reporting agent
  • Why it matters: Illustrates why multi-agent chaining becomes brittle and unscalable without proper memory and state management.

The File System Agent Breakthrough

  • Explanation: The release of Claude Code and Opus 4.5 introduced file-system agent architecture, which Vercel adopted and adapted into a file-system sandbox agent.
  • Key claims:
    • Claude Code and Opus 4.5 effectively function as AGI compared to previous hand-grown agent architectures.
    • Giving agents a file system and letting them explore local execution environments with minimal toolsets unlocks emergent behavior.
  • Examples:
    • Giving sandbox agents access to bash, grep, read file, and write file tools.
  • Terminology:
    • Claude Code
    • Opus 4.5
    • file system agent
    • sandbox
    • grep
    • bash
  • Why it matters: Proves that file-system-based agent execution significantly outperforms overly prescriptive toolsets.

Announcing Eve: Next.js for Agents

  • Explanation: Vercel built and released Eve, an open-source agent framework applying Next.js-like file system conventions to agent building.
  • Key claims:
    • Building agents should be as simple as configuring file system folders for skills, tools, and system instructions.
    • Eve combines runtime durability, model streaming, sandboxes, and multi-channel support.
  • Examples:
    • Defining skills using skills.sh, system instructions in markdown, and tools in TypeScript.
  • Terminology:
    • Eve
    • Next.js for agents
    • skills.sh
    • durable workflow
    • Vercel Sandbox
    • Vercel Connect
  • Why it matters: Provides developers with a standardized, opinionated framework to build, deploy, and scale production-ready AI agents.

Key Points

From Megamprompts to File Systems

  • Explanation: Initial agent attempts relied on giant prompts, but true agent capability emerged when agents were given file systems and local execution capabilities.
  • Evidence: Evaluating eve's performance showed evaluation scores doubled when transitioning from multi-agent chains to file-system sandbox architectures.
  • Practical implication: Developers should avoid overly prescriptive tool definitions and instead give agents file-system access and sandbox execution environments.

Company-Specific Knowledge Integration

  • Explanation: Off-the-shelf agents are useful, but maximum value comes from agents embedded with deep company knowledge, domain terminology, and internal web properties.
  • Evidence: Beta partners like Aura rebuilt their agents using Eve and saw massive success compared to off-the-shelf Claude Code.
  • Practical implication: Building proprietary agents embedded with domain-specific company data yields significantly higher productivity gains.

Framework-Defined Infrastructure

  • Explanation: Just as Next.js eliminated infrastructure complexity for web applications, Eve eliminates infrastructure complexity for agents.
  • Evidence: Developers only need to create skills, tools, and instruction folders; the framework handles runtime routing and execution.
  • Practical implication: Agent frameworks should handle durability, security sandboxing, and channel routing out of the box.

Frameworks, Models & Processes

Eve (Next.js for Agents)

  • How it works: Provides a file-system-driven agent framework where folder structures define agent instructions, skills, tools, and subagents, backed by Vercel's runtime primitives.
  • Components:
    • Runtime (Durable Workflow, AI SDK, Sandbox, Subagents)
    • Channel (Chat SDK, Web Chat, Discord, Slack, WhatsApp, API, GitHub)
    • File System Architecture (system.md, instructions.md, rules.md, tools/, skills/)
  • When to use: When building production-ready AI agents requiring secure execution, durable state, multi-channel deployment, and deep domain knowledge integration.

Article ideas

4

Your Multi-Agent Graph Is a Liability

A hand-authored control-flow graph for an LLM system has edge-case coverage bounded by the designer's imagination, so its reliability decays as task diversity grows; a single agent inside a constrained, explorable environment with a persistent file system degrades more gracefully because the model supplies control flow at inference time.

Angle

Treat orchestration diagrams as a coverage budget: enumerate the transitions a DAG cannot represent and show why each unmodeled path has no valid route, then argue for moving control flow into the model while keeping the environment constrained.

Source video ↗

Four Tools Beat Four Hundred

Tool-interface design has been optimizing the wrong variable: a small set of orthogonal primitives the model composes at inference time outperforms a large enumerated typed tool API, because the enumerated API spends context on descriptions and cannot cover paths the designer did not anticipate.

Angle

Frame it as a design inversion — from design-time capability enumeration to inference-time composition — and tie it directly to reduced tool-authoring and maintenance surface, plus the loss of static guarantees.

Source video ↗

Your Agent Framework Is Not Your Moat

If file-system conventions and runtime primitives commoditize the framework layer, the durable advantage sits in encoded organizational context — domain terminology, internal properties, proprietary data — so budget should shift from tooling breadth to context curation and review.

Angle

Follow the value from framework to instruction files, and argue that context curation deserves versioning, ownership, and evaluation rigor comparable to code.

Source video ↗

Next.js for Agents: When Folder Structure Becomes the Interface

Declarative directory conventions can serve as the stable interface for agent definition the way file-system routing did for the web, because moving topology out of imperative code makes agent changes diffable, reviewable, and owned by the framework rather than re-implemented per team.

Angle

Compare the two configuration regimes directly — imperative wiring versus folder layout defining instructions, skills, tools, and subagent boundaries — and examine what the convention hides and what it exposes.

Substrate Ablation Harness

beyond-evals

Holding model, task suite, and tool budget constant, a file-system sandbox agent with bash/grep/read/write scores measurably higher than a hand-chained query->planning->execution->reporting pipeline, and the effect size is smaller than the reported doubling once prompts are matched.

Proof of concept

Build two runtimes over one identical task suite: (a) a chained multi-agent pipeline with typed step tools, (b) a single agent in a sandboxed file system with four primitives. Report per-task scores, not a single aggregate number.

Measurement

Per-task pass rate and score delta across both runtimes, with per-task variance and a stated baseline, so the doubling claim is either reproduced, shrunk, or refuted.

Sandbox Containment Curve

gatehouse

Containment strength and agent task success are not a simple tradeoff: allowlisted file paths plus egress control preserve most task success while eliminating outbound exfiltration paths that unrestricted sandbox access permits.

Proof of concept

Run one file-system agent task suite under escalating isolation profiles — no isolation, container, microVM, plus syscall filtering, filesystem allowlists, and egress deny-by-default — and log both blocked actions and completed tasks.

Measurement

Task success rate per isolation profile, count of blocked or denied agent actions, and count of attempted outbound connections, giving a containment-versus-capability curve instead of a single sandbox claim.

Edge-Case Coverage Probe

new

A hand-built multi-agent graph has no valid path for a substantial fraction of realistic edge cases collected from production logs, while a file-system sandbox agent completes those same cases without new engineering.

Proof of concept

Harvest a set of unanticipated edge cases from real usage traces, then attempt each against a fixed multi-agent DAG and against a sandbox agent, recording whether a route exists and whether the task completes.

Measurement

Fraction of edge cases with no valid DAG path, and completion rate for those same cases under the sandbox agent, reported as a coverage gap rather than an anecdote.

Context Versus Substrate Split

movement-lab

For domain-specific agents, injecting proprietary instruction files and internal context accounts for more of the performance gap against a generic agent than swapping the file-system framework does.

Proof of concept

Ablate one agent across four conditions — generic framework with generic context, generic framework with proprietary context, file-system framework with generic context, file-system framework with proprietary context — on matched tasks.

Measurement

Condition-wise task success and quality scores, isolating the framework effect from the context effect that the partner comparison currently confounds.

Architectural implications

3

Agent definition moves from imperative orchestration code to a declarative file-system convention.

Before

Developers wired query/planning/execution/reporting agents together in code and maintained hand-mapped control flow.

After

Folder structure (system.md, instructions.md, rules.md, tools/, skills/) plus runtime primitives defines the agent, its tools, and its subagents.

Consequence

Orchestration code and its bespoke edge-case handling largely disappear; agent changes become file diffs, and composition is delegated to the framework.

Source video ↗

Execution-semantics responsibility shifts from application code to the runtime.

Before

Teams assembled their own state, retry, sandbox, and channel plumbing around the model.

After

Durable Workflow, AI SDK, Sandbox, Subagents, and a multi-channel layer (Chat SDK, Web Chat, Discord, Slack, WhatsApp, API, GitHub) ship with the framework.

Consequence

Faster time-to-first-production-agent, but increased coupling to one vendor's runtime primitives and their failure/limit characteristics.

Source video ↗

Capability surface collapses from many task-specific tools to a few general primitives plus a file system.

Before

Specialized agents with dedicated, prescriptive tools per step of the workflow.

After

One agent with bash, grep, read, write and a sandboxed file system exploring the environment.

Consequence

Lower tool-authoring and maintenance cost, but weaker static guarantees about which actions an agent can or will take.

Tradeoffs and failure modes

4

Minimal toolsets and emergent behavior versus explicit control

Benefit

Agents recombine low-level primitives and handle unanticipated cases, outperforming prescriptive tool definitions in evaluations.

Cost or risk

Emergent behavior is harder to bound, audit, and reproduce than an enumerated tool API; capability is claimed rather than fully specified.

Source video ↗

Prescriptive multi-agent chaining

Benefit

Produces end-to-end loops from user question to answer with legible, inspectable stages.

Cost or risk

Breaks down on complex, unanticipated edge cases and requires manual remapping for each new path.

Source video ↗

Sandboxed shell/file execution as an agent capability

Benefit

Unlocks local exploration and file-system-driven agent architecture with high evaluation scores.

Cost or risk

Requires security sandboxing as a first-class runtime concern; the summary asserts the need but gives no isolation mechanism or threat model.

Source video ↗

Megaprompt-as-agent

Benefit

Fastest possible starting point: inject a schema into the system prompt and copy generated SQL.

Cost or risk

Unstructured and non-extensible; represents the naive baseline that the team moved past.
