Core insights

6
[A]Architecturemedium noveltystrong evidence

The development lifecycle is driven by an ordered chain of versioned Markdown artifacts (intent.md → spec.md → plan.md) where each file has a distinct semantic role: intent.md = why, spec.md = what/expected behavior, plan.md = decomposed actionable tasks. This makes agent context an auditable repository artifact rather than ephemeral prompt text.

Why it matters

It relocates the grounding context for agents out of chat history and into reviewable, diffable files, which changes how context is versioned, reviewed, and rolled forward between agent runs.

Generalization

Any long-horizon agent workflow (not just coding) can be decomposed into chained, human-readable artifacts with separated why/what/how responsibilities, giving structured context handoff and an audit trail.

[M]Mechanismmedium noveltystrong evidence

Self-verification is treated as a hard gate: the agent must have a machine-checkable way to verify its own work (tests, builds, lints, screenshot diffs) and pass test/lint/build with zero failures before it is allowed to report completion to a human.

Why it matters

Defining 'done' as passing an automated check rather than the agent's own assertion converts self-reported completion into an objectively falsifiable signal and reduces human review load.

Generalization

Agent harnesses should terminate on externally verifiable criteria (a build/test/lint exit contract) rather than model self-assertion; the verification surface is a first-class part of the runtime design.

Staleness and invalidation in a chained artifact pipeline (intent.md → spec.md → plan.md)

Research question

When intent.md changes mid-flight, how should downstream spec.md and plan.md be invalidated, regenerated, or reconciled, and what explicit staleness metadata minimizes silent drift between artifacts?

Why

The artifact chain only works as a context contract if downstream files can be proven consistent with the intent they derive from; without an invalidation scheme, agents execute against superseded specs and the audit trail becomes misleading rather than authoritative.

Externally verifiable termination contracts for autonomous coding agents

Research question

Does enforcing a machine-checkable exit contract (test/lint/build with zero failures) before an agent may report completion measurably reduce human review defects and rework compared with agents that self-assess completion?

Why

If 'done' is defined by an automated gate rather than model assertion, completion becomes falsifiable and review load becomes a measurable dependent variable instead of an anecdote about agent quality.

Minimum viable eval-suite size and pass thresholds as a CI stage gate

Research question

What suite size and pass-rate threshold, for a given task-diversity profile, reliably detects regressions introduced by model swaps or rule changes before they reach production?

Why

A 20-50 task suite is named as the stage gate but no acceptance bar or sensitivity analysis is given, so operators cannot distinguish a meaningful gate from a formality that yields false confidence about unmodeled cases.

Bypass surface of enumerated hook guardrails

Research question

Against an agent operating under a block-list of hook-enforced actions, what fraction of unsafe behaviors are caught, and what novel or unenumerated actions escape the guardrail?

Why

Hooks convert governance from model discretion into runtime interception, but the guarantee is bounded by the enumeration itself; quantifying bypass surface determines whether hooks are a real safety boundary or only a speed bump.

Conflict arbitration among decomposed review passes (bugs, security, compliance)

Research question

When independent review passes disagree or when a REVIEW.md rubric is wrong, how should disagreements be arbitrated and how should rubric quality itself be validated?

Why

Decomposed passes with an in-repo rubric are only useful if rubric defects and inter-pass conflicts are detectable; otherwise three passes create three places for silent mis-grading.

Project ideas

4

Artifact-Chain Linter with Staleness Provenance

movement-lab

Adding explicit provenance and staleness markers to intent.md → spec.md → plan.md reduces the rate at which agents execute against superseded requirements compared with an unmarked chain.

Proof of concept

Build a CLI/CI check that hashes and records the parent-artifact revision each downstream file was generated from, flags stale descendants, and blocks plan execution when spec is stale relative to intent.

Measurement

Count of agent runs executed against stale downstream artifacts, and time-to-detect intent drift, in a seeded repository where intent is mutated mid-flight.

Source video ↗

Exit-Contract Harness: Zero-Failure Completion Gate

gatehouse

Binding agent completion to a zero-failure test/lint/build contract reduces human review defects and rework per merged change versus agents that self-report completion.

Proof of concept

Wrap an agent runner so the done signal is emitted only by the exit codes of test/lint/build commands, and A/B against a self-assessment baseline on the same task backlog.

Measurement

Human review defects per merged PR, rework minutes per task, and false-completion rate (tasks reported done that fail the contract).

Source video ↗

Eval-Suite Sensitivity Calibrator

beyond-evals

Regression-detection sensitivity scales with task diversity rather than raw task count, so suites below a diversity threshold fail to catch model-swap regressions even at 50 tasks.

Proof of concept

Inject known regressions into a fixed set of 20-50 real tasks, vary suite size and diversity coverage, and run the suite via a GitHub Actions workflow on both baseline and regressed model configurations.

Measurement

Detection rate and false-negative rate per injected regression as a function of suite size and diversity coverage; minimum viable suite configuration.

Source video ↗

Hook Bypass Red-Team Rig

gatehouse

An enumerated block-list guardrail leaves a measurable bypass surface, and red-team-derived action classes can be converted into new block rules that reduce that surface without blocking legitimate work.

Proof of concept

Red-team an agent under a hook guardrail that blocks file edits and production credential access, enumerate unsafe actions not on the list, then extend the rule set and re-run.

Measurement

Number and severity of unsafe actions executed per red-team episode before and after rule extension; false-block rate on legitimate tasks.

Architectural implications

3

Governance constraints are implemented as deterministic hooks rather than as prompt instructions.

Before

Safety rules lived as instructions in the model's system prompt or context, enforced at the model's discretion.

After

Hooks intercept and block specific actions (file edits, production credential access) at the runtime boundary.

Consequence

Policy becomes non-negotiable and testable independently of model behavior, but requires maintaining interception logic and anticipating which actions to block.

Source video ↗

Agent grounding context is externalized into chained version-controlled files (intent.md, spec.md, plan.md, REVIEW.md) rather than accumulated in conversation state.

Before

Requirements and plans lived in chat history or tribal knowledge, and were re-explained per session.

After

Each stage reads a prior stage's artifact, forming an explicit, diffable handoff chain.

Consequence

Context becomes reviewable and reproducible, and stage boundaries become contract boundaries between agents/humans.

Source video ↗

Model and rule changes are gated by a real-task eval suite in CI.

Before

Model swaps or prompt/rule changes were validated manually or not at all.

After

A fixed 20-50 task suite runs in GitHub Actions as a stage gate before accepting change.

Consequence

Shifts the operational definition of reliability from anecdote to repeatable regression evidence, at the cost of building and maintaining task datasets.

Tradeoffs and failure modes

4

Fast agent loops vs human governance

Benefit

AI-native SDLC compresses execution from weeks to hours, freeing humans to focus on intent, review, and governance.

Cost or risk

Humans directing and governing at agent speed requires review and approval capacity that may not scale to match the loop speed.

Source video ↗

Eval suite as regression gate

Benefit

Catches agent regressions after model swaps or rule changes before they reach production.

Cost or risk

A suite of only 20 to 50 real tasks may not represent production task diversity, so passing it can give false confidence about unmodeled cases.

Source video ↗

Self-verification via test/lint/build

Benefit

Agents catch and fix their own errors before human review, cutting review overhead.

Cost or risk

Correctness of the gate is bounded by the coverage and quality of the tests and checks the agent itself relies on.

Source video ↗

Hooks as approval gates

Benefit

Blocks unauthorized actions such as editing certain files or touching production credentials.

Cost or risk

Hooks can only block anticipated actions; novel or unenumerated actions may bypass the guardrail until the rule set is extended.
