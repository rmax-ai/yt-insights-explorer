Overview

  • Speaker: Jack Wotherspoon
  • Channel: AI Engineer
  • Main topic: Managed agents, cloud sandboxes, and multi-agent workflows using Google DeepMind's Gemini API and Antigravity harness.
  • Purpose: To explain the architecture, benefits, and practical implementation of cloud-hosted managed agents and multi-agent workflows using Google DeepMind tools. Jack Wotherspoon from Google DeepMind discusses the transition from running local coding agents to leveraging cloud-hosted managed agents. He introduces the new Interactions API, Antigravity harness, core primitives like secure sandboxes, stateless/stateful environments, credentials injection via egress proxies, and scheduling triggers, showcasing a live multi-agent financial research application.

Topic Map

Why Managed Agents and Cloud Sandboxes

  • Explanation: Running coding agents locally presents challenges with permission prompts, browser hijacking, and lack of scalability. Moving agents to cloud sandboxes solves verification, scalability, and security.
  • Key claims:
    • Local laptops do not scale for multi-agent workflows.
    • Sandboxes allow agents to write, execute, test, and verify code autonomously.
    • Cloud execution eliminates local permission prompt fatigue and security risks.
  • Examples:
    • Spawning cloud agents to write code, search the web, run tests, and return verified outputs.
  • Terminology:
    • managed agents
    • cloud agents
    • sandbox
    • verification
  • Why it matters: Cloud sandboxes enable scalable, automated, and secure execution of AI agents without burdening developer machines.

Gemini Managed Agents and Interactions API

  • Explanation: Google DeepMind's new Interactions API provides a single API call to spin up a Google-hosted Linux sandbox, persistent filesystem, and the Antigravity agent loop out of the box.
  • Key claims:
    • Managed agents boil down to a single API call.
    • Interactions API mirrors multi-step agent workflows.
    • Set environment=remote to activate cloud-managed execution.
  • Examples:

  • Terminology:

  • Why it matters: It drastically simplifies agent orchestration by removing infrastructure management from the developer.

Building Blocks of Managed Agents

  • Explanation: Managed agents rely on core primitives: harness (Antigravity), environment (stateful Linux container), tools (built-in and remote MCP servers), skills (AGENTS.md / .md files), credentials (egress proxy injection), and schedule/triggers.
  • Key claims:
    • Harness handles tool calls and planning loops.
    • Environments are stateful filesystems on Linux containers.
    • Credentials use egress proxy injection to keep secrets out of the sandbox.
  • Examples:
    • Mounting AGENTS.md, SKILL.md, git repos, or Cloud Storage buckets into the sandbox.
  • Terminology:
    • harness
    • environment
    • MCP servers
    • skills
    • credentials
    • triggers
  • Why it matters: These building blocks provide robust control, security, and reusability for enterprise agentic workflows.

Security and Secrets Management

  • Explanation: Secrets never enter the sandbox directly. An egress proxy sits between the sandbox and APIs, injecting dummy tokens locally and matching them with real API credentials upstream.
  • Key claims:
    • Secrets never enter the sandbox.
    • Egress proxy acts as a secure wiretap.
    • Prevents rogue agents from exfiltrating real API tokens.
  • Examples:
    • Client stores tokens with client.credentials.create; egress proxy injects bearer tokens on allowed outbound requests.
  • Terminology:
    • egress proxy
    • wiretap
    • credentials
    • zero-trust egress
  • Why it matters: Ensures enterprise-grade security when agents interact with external APIs like GitHub or financial data providers.

Multi-Agent Workflows and State Management

  • Explanation: Interactions and environments are stateful. Conversations are tracked via interaction IDs, while environments share filesystem state across different agent turns.
  • Key claims:
    • Interactions keep conversation history and reasoning turns.
    • Environments keep workspace files, data, and installed packages.
    • Multiple specialized agents can reuse the same environment while maintaining fresh context windows.
  • Examples:
    • Passing previous_interaction_id and environment_id between SEC researcher, quant modeler, and report writer agents.
  • Terminology:
    • interactions
    • environments
    • stateful
    • context window
  • Why it matters: Allows complex, multi-step division of labor among specialized agents working on the same shared workspace.

Core insights

6
[M]Mechanismhigh noveltymoderate evidence

Credentials are injected at an egress proxy that sits between the sandbox and external APIs: the sandbox holds dummy tokens, and the proxy substitutes real API credentials on approved outbound requests. The secret is never materialized inside the agent's filesystem or process memory.

Why it matters

It relocates the trust boundary for secrets from 'the agent will behave' to 'the network path is mediated.' An agent that reads its own environment variables, dumps memory, or is prompt-injected into printing its token gains nothing, because there is nothing real to print.

Generalization

Any agent runtime that executes untrusted, model-generated code should treat credentials as an outbound-proxy concern rather than a secret-store-in-the-box concern. The pattern ports to any sandbox, container, or VM-based agent runtime.

[A]Architecturehigh noveltymoderate evidence

Conversation state and workspace state are two separate, independently addressable objects: an interaction ID carries the reasoning transcript, an environment ID carries files, data, and installed packages. Multiple specialized agents can reuse one environment while each starts with a fresh context window.

Why it matters

This is context-window hygiene as a first-class primitive. Instead of one long-running agent accumulating an ever-growing transcript, you get durable shared artifacts plus disposable per-agent conversations. It also makes the unit of parallelism and the unit of memory explicit and separately managed.

Generalization

Separating 'memory of what was said' from 'state of what exists' is a reusable architectural split for multi-agent systems: the filesystem/database is the handoff channel, and each agent's context is a cache that can be dropped at will.

[A]Architecturemedium noveltymoderate evidence

Managed agents decompose into named primitives — harness (planning/tool-call loop), environment (stateful Linux container), tools including remote MCP servers, skills as mounted markdown files, credentials via egress proxy, and schedule/triggers — and the whole composition is reachable through a single API call with environment='remote'.

Why it matters

The abstraction boundary moves from 'you run the loop and own the box' to 'you declare a harness and an environment.' That is the difference between building an agent framework and consuming an agent runtime, and it determines which layer your engineering effort goes into.

Generalization

Expect the agent stack to standardize on a small set of orthogonal primitives whose composition is declarative. Teams should design so that harness, environment, tools, and identity are swappable, because vendors will keep re-bundling them.

[O]Mental Modelmedium noveltymoderate evidence

The stated justification for cloud execution is closing the verify loop, not merely avoiding prompts: the sandbox exists so the agent can write, execute, test, and verify its own output before returning it.

Why it matters

It reframes sandboxing from a safety feature to a correctness feature. If your agent cannot run the thing it produced, you are shipping unverified model output; the sandbox is the mechanism that converts generation into checked artifacts.

Generalization

Any agent whose output is executable or queryable should have a runtime it can act inside. The design question is not 'is the sandbox secure' but 'can the agent falsify its own answer in here.'

[P]Practicemedium noveltyweak evidence

Agent skills and configuration are delivered as mounted artifacts — AGENTS.md, SKILL.md, git repos, Cloud Storage buckets — rather than as prompt text assembled by the caller.

Why it matters

Bootstrap behavior becomes versioned filesystem content, which means skills are diffable, mountable per-environment, and shared across agents without re-serializing instructions into every interaction. It also creates a clean seam: changing an agent's capability becomes a filesystem-level operation.

Generalization

Treat agent instructions and skills as deployable artifacts with a lifecycle (mount, version, roll back), not as strings embedded in application code. This is the same shift as config-as-code, applied to agent behavior.

[>]Predictionmedium noveltyweak evidence

Scheduling/triggers appear as a peer primitive alongside harness and environment, implying agents as durable, recurring cloud workloads rather than interactive chat sessions.

Why it matters

If invocation can be a cron-like trigger, agents move into the same operational category as batch jobs and services — demanding the same observability, idempotency, and alerting that other unattended workloads get, which chat-shaped agent designs usually lack.

Generalization

Agent systems designed for unattended invocation must answer the questions services answer: what happens on partial failure, how is a run traced, who is paged.

Deep dives

5

Adversarial bounding of egress-proxy credential injection

Research question

Does proxy-mediated credential injection actually bound exfiltration, or only narrow it to the allowlisted destinations an agent can still encode data into?

Why

The entire security claim rests on 'secrets never enter the sandbox,' but the residual channel is any allowlisted endpoint plus headers, URLs, and request bodies. If the allowlist is coarse, the trust boundary has moved without shrinking the attack surface — and the proxy becomes a single choke point whose misconfiguration is a fleet-wide credential risk.

Source video ↗

Artifact contract fidelity when state passes through the environment instead of the transcript

Research question

How much task fidelity is lost when specialized agents hand off through filesystem artifacts with fresh context windows, versus one agent carrying a full accumulating transcript?

Why

Fresh-context-per-agent is presented as pure context hygiene, but the cost is that implicit reasoning, caveats, and negative results recorded only in the prior transcript never transfer. The file format becomes the real inter-agent API, so the design burden shifts to defining an artifact contract — and nobody has measured what that contract silently drops.

Source video ↗

Concurrency, locking, and lifetime semantics of a shared stateful environment

Research question

What happens when multiple agents write concurrently to one shared environment, and when is an environment snapshotted or reclaimed?

Why

The environment is described as a stateful filesystem reused across agents and turns, which implicitly promises a shared workspace — but parallel writers, locking, snapshotting, and garbage collection are unaddressed. Without these semantics, multi-agent parallelism on a shared environment is unsafe by default and cost of long-lived environments is unmodeled.

Source video ↗

Debuggability across a vendor-owned harness boundary

Research question

When the planning loop is selected by name and owned by the vendor, can a failing multi-step task be localized to a specific tool call or planning decision from exposed telemetry?

Why

Delegating the loop trades iteration speed on the loop itself for lost depth below the harness boundary. If step-level traces are thin, teams can only debug at the tool/skill/environment layer and will misattribute harness failures to their own configuration — a persistent tax on operating managed agents.

Source video ↗

Sandbox self-verification as a measurable correctness signal

Research question

Does an agent running and testing its own output inside a sandbox measurably reduce error rates on downstream artifacts, or does it produce confident but circular self-checks?

Why

Reframing the sandbox from safety feature to correctness feature is the strongest claim in the talk, and it is testable. If self-verification does not move downstream error rates, the sandbox's justification collapses back to convenience and isolation, which changes how teams should budget for it.

Article ideas

4

The Sandbox Is a Correctness Feature, Not a Safety Feature

Teams justify sandboxing with security language, but the actual engineering value is closing the verify loop: an agent that cannot execute what it produced is shipping unverified model output. Security is a side effect of giving the agent a runtime it can falsify itself in.

Angle

Reframe the sandbox design question from 'is it isolated' to 'can the agent disprove its own answer in here,' then derive concrete requirements for what the sandbox must expose (runnable tests, queryable data, network egress) versus what it must deny.

Source video ↗

Your Agent's Real API Is the Filesystem: Designing the Artifact Contract for Multi-Agent Handoffs

Once conversation state and workspace state are split into separately addressable objects, the file format — not the prompt — becomes the inter-agent contract. Teams that do not design it explicitly get silent fidelity loss, because everything recorded only in a prior transcript does not survive a fresh context window.

Angle

Treat handoff artifacts as a versioned schema with an explicit discipline for persisting caveats and negative results, and compare this against the single-long-transcript baseline it replaces.

Source video ↗

Prompt-Injection Is No Longer a Credential-Disclosure Bug

Moving secrets to an egress proxy changes the blast radius of prompt injection: a hijacked agent can print its token all day and get a dummy. The vulnerability class relocates to the outbound allowlist, which becomes the critical maintained artifact and a fleet-wide single point of failure — so allowlist review deserves the rigor secret rotation used to get.

Angle

Walk the trust boundary migration from 'the agent will behave' to 'the network path is mediated,' then enumerate what the proxy does not cover: allowlisted destinations, encoded payloads, and non-HTTP channels.

Source video ↗

When You Outsource the Loop, You Outsource the Debugger

Declaring a harness by name removes infrastructure management but also removes iteration speed on the planning loop and depth of failure inspection. Differentiation shifts upward to tools, skills, environment configuration, and orchestration — and teams must budget for the debugging ceiling that comes with the boundary.

Angle

Map what is still owned versus delegated under a one-call managed agent, and specify the telemetry a team needs before it can safely depend on a vendor-owned loop for unattended workloads.

Project ideas

4

Canary Leak Harness for Egress-Mediated Agent Sandboxes

gatehouse

An agent confined to a sandbox with proxy-injected dummy credentials cannot exfiltrate a planted canary secret through allowed outbound requests, even under directed prompt injection — measurable as a zero successful egress channels out of a fixed adversarial suite.

Proof of concept

Stand up a sandboxed agent holding only dummy tokens, plant a canary value in its workspace, run a scripted suite of injection prompts that attempt to encode the canary into allowed endpoint paths, headers, request bodies, and error-triggering payloads, and log every outbound request at the proxy to check for canary presence.

Measurement

Count of injection attempts that successfully place the canary in an outbound request the proxy forwards, per channel; plus false-negative rate on a deliberately permissive allowlist to confirm the harness detects leaks it should.

Source video ↗

Transcript Versus Artifact Handoff Benchmark

beyond-evals

A three-agent pipeline sharing one environment with fresh context windows matches or beats a single long-context agent on structured outputs while using fewer total tokens — but loses measurable fidelity specifically on constraints and negative results that exist only in the prior transcript unless explicitly persisted.

Proof of concept

Build the same multi-step research task two ways: one agent with the full accumulating transcript, and three specialist agents handing off via filesystem artifacts, run both against a rubric with planted mid-task constraints and dead ends, then ablate by adding an explicit 'decisions and ruled-out paths' artifact file.

Measurement

Output accuracy against a ground-truth rubric, count of planted constraints honored across the handoff, total tokens and wall-clock latency, and lift from the added decisions artifact.

Source video ↗

Shared-Environment Concurrency Probe

movement-lab

A shared stateful environment supports concurrent agent writers without silent data loss only when writers are partitioned by path or serialized by an explicit lock, and unguarded concurrent writes produce reproducible lost-update conflicts.

Proof of concept

Run N agents writing overlapping and disjoint paths in one environment simultaneously, with and without a lock discipline and with path partitioning, then diff final workspace state against a merge of all intended writes.

Measurement

Rate of lost updates and clobbered files per concurrency level, plus per-run provisioning and idle cost of a long-lived environment to quantify the lifetime tradeoff.

Source video ↗

Self-Verification Lift Meter

beyond-evals

Agents that execute and test their own output inside a sandbox produce lower downstream error rates than identical agents that generate without execution — but the lift shrinks toward zero when the agent writes its own tests, indicating circular verification rather than genuine checking.

Proof of concept

Run a code-producing task in three conditions: no execution, execution with agent-authored tests, and execution with held-out tests the agent cannot see. Score all artifacts against the same held-out suite.

Measurement

Downstream pass rate on held-out tests per condition, and the gap between agent-authored-test pass rate and held-out pass rate as a circularity index.

Architectural implications

3

Credential handling moves out of the agent process and into an egress proxy that brokers outbound calls.

Before

API keys are stored in the agent's environment variables or a secret mounted into the container, and safety depends on the model not leaking them.

After

The sandbox sees only dummy tokens; the proxy holds the real credentials and injects them on allowed outbound requests.

Consequence

Prompt-injection and code-execution vulnerabilities stop being credential-disclosure vulnerabilities, but the egress allowlist becomes a critical, maintained artifact and a single point of failure for all external integrations.

Source video ↗

Memory is split into an interaction (conversation/reasoning history) and an environment (filesystem state), addressed by separate IDs.

Before

A single long-running agent thread accumulates tool outputs and reasoning, and context grows monotonically across a multi-step task.

After

Specialized agents each get a fresh context window while sharing one workspace; state is handed off by reference, not by transcript.

Consequence

You must design an explicit artifact contract — what gets written to the filesystem, in what format, so the next agent can pick it up without the prior conversation. The file format becomes the real inter-agent API.

Source video ↗

The agent loop is delegated to a vendor-owned harness that is selected by name in the API call.

Before

The team writes and owns the planning loop, tool routing, retry logic, and context assembly.

After

The team declares a harness and an environment; iteration speed on the loop itself is no longer under their control.

Consequence

Differentiation shifts to tools, skills, environment configuration, and multi-agent orchestration above the harness — while debugging depth below the harness boundary is limited.

Tradeoffs and failure modes

4

Proxy-mediated credential injection

Benefit

Rogue or injected agents cannot exfiltrate real API tokens because they never exist inside the sandbox.

Cost or risk

Security now depends on the outbound allowlist being correct and tight; the proxy is an added hop and a central choke point, and any allowlisted destination reachable by the agent remains a potential exfiltration path.

Source video ↗

Fresh context windows per agent

Benefit

Avoids context bloat and keeps each specialist agent focused, enabling division of labor across a shared workspace.

Cost or risk

Anything not persisted to the environment is lost on handoff; implicit reasoning, caveats, and negative results recorded only in the prior transcript do not transfer unless deliberately written out.

Source video ↗

Single-API managed execution

Benefit

Infrastructure management is removed from the developer; sandbox, filesystem, and harness come up in one call.

Cost or risk

Reduced control and visibility into isolation, resource limits, environment lifetime, and debugging inside the managed container.

Source video ↗

Shared 1M-token budget across input, thinking, and output

Benefit

Large filings and lengthy financial modeling fit within one window.

Cost or risk

Extended reasoning consumes the same budget as input and output, so long decode competes with document context and final report length rather than being free.
