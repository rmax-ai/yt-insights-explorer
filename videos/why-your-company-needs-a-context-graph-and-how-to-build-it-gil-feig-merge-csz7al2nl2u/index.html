Summary

Overview

  • Speaker: Gil Feig
  • Channel: AI Engineer
  • Main topic: Enterprise AI infrastructure and the necessity of context graphs for production AI applications
  • Purpose: To explain what a context graph is, why companies need one beyond simple MCP servers or live API lookups, and how to architect and build a robust, traceable context layer for enterprise AI agents. Gil Feig, co-founder and CTO of Merge, explains why companies need a context graph to power production AI applications effectively. He breaks down the components of a company context graph, including third-party data, structured context, memories, and skills. He outlines the tiers of context—prompt/skills/memory, live API calls, cached data, and derived context—and discusses selection strategies, syncing layers, routing, and provenance requirements for reliable enterprise AI systems.

Key Points

Tools are not enough for context

  • Explanation: Connecting an agent to MCP servers or APIs is insufficient for complex enterprise reasoning; organizations need a structured context graph.
  • Evidence: Live lookup pagination and timeouts when searching thousands of tickets.
  • Practical implication: Architects must implement a syncing and caching layer alongside live tool calls.

More data is not always better

  • Explanation: Pulling massive amounts of raw context causes context window overload and timeouts. Quality and freshness matter more than volume.
  • Evidence: Pulling 5 tickets instead of full history to avoid API timeouts.
  • Practical implication: Use derived summaries and targeted caching strategies.

Traceability is mandatory for enterprise AI

  • Explanation: Models must provide provenance for every piece of data used in decision-making to enable auditing and debugging.
  • Evidence: Citations and source links in chat interfaces.
  • Practical implication: Store metadata, fetch timestamps, scope permissions, and invalidation rules with every context node.

Deep dives

4

Context-tier routing as an explicit, testable policy

Research question

Does a router that orders context sources by cost, freshness, and volatility (skills/memory → cache freshness check → live API → summarization) outperform a single-strategy retrieval baseline (vector-only or tool-loop-only) on correctness, p95 latency, and external-call volume across a mixed query workload?

Why

If context management is really a routing policy, then the router becomes a first-class, evaluable component — and teams that keep a single retrieval strategy will systematically overpay in either latency or correctness. Quantifying the cross-over points turns 'context management' from folklore into a tunable engineering surface.

Source video ↗

Where live tool-call lookups structurally break: the aggregate-query boundary

Research question

At what dataset size, page depth, or query cardinality does an MCP-style live lookup measurably exceed an acceptable latency/error budget for set-level questions ("which customers were upset last week?") relative to a synced vectorized cache?

Why

This is the falsifiable boundary that decides whether a sync layer is mandatory or optional for a given enterprise. A concrete threshold (records, pages, p95 seconds) converts an architectural argument into capacity planning and a build-vs-skip decision per data source.

Source video ↗

Minimal viable provenance schema and its overhead budget

Research question

What is the smallest provenance schema (source, requester, fetch timestamp, scope permissions, invalidation rules) that still supports tracing a derived summary back to source record IDs, and what is its measured storage and token overhead per context node?

Why

Provenance is the precondition for letting agents act on cached or summarized data, but unbounded metadata bloats both context windows and storage. Finding the knee of the utility-vs-overhead curve determines whether provenance ships in v1 or gets deferred — and deferring it makes stale data invalidatable in theory only.

Source video ↗

Deriving per-context-type freshness policies from staleness-induced error cost

Research question

Can freshness thresholds be set per context type by empirically measuring the error rate induced by staleness against refresh cost (for 15-minute account summaries versus long-lived documents), rather than by picking a fixed cadence?

Why

Every cached tier collapses into a staleness problem the moment it is written, and the only defensible threshold is one derived from the cost of acting on stale data. Without this, freshness is guessed, and invalidation rules have no calibration target.

Article ideas

3

MCP Is a Lookup Mechanism, Not a Context Layer

Tool-call access over SaaS APIs solves the single-entity question and structurally fails the set-level question; the aggregate query class is the dividing line where a first-party sync-and-index layer stops being optional and becomes core infrastructure. Teams that treat MCP as their retrieval architecture will discover this only on their first fleet-wide or historical query.

Angle

Draw the boundary precisely — one-entity lookups versus aggregate/cross-entity queries — and show what each architecture can and cannot answer, then argue that the sync layer carries its own freshness, cost, and failure surface that must be funded as infrastructure.

Source video ↗

Stop Calling It Retrieval: Context Assembly Is a Routing Policy

Context is not one store but four tiers with distinct cost, freshness, and semantic-capability profiles; the engineering work is dispatch across those tiers (skills/memory first, cache with a freshness check, live APIs as fallback, summaries for breadth), not selecting a single vector database. Committing to one retrieval strategy for all query types guarantees you overpay in latency or correctness.

Angle

Reframe context management as an ordered decision tree with short-circuits, and treat the router as a component with its own evaluation criteria rather than an implicit code path.

Source video ↗

Your Vendor Will Never Index Your Data, So Build the Sync Layer

Platform providers are structurally steered toward the cheapest integration path — pass-through API access — while vectorization and pre-indexing carry ongoing cost and maintenance they have no incentive to absorb. The durable indexing burden therefore lands on the enterprise consuming the data, which should shape build-vs-buy and team-scoping decisions before the first connector is chosen.

Angle

Argue from incentive structure rather than capability: predict where vendor roadmaps will and will not go, and what that means for owning the ingestion, embedding, and invalidation pipeline.

Tradeoffs and failure modes

4

Live API lookups vs cached/derived context

Benefit

Live API calls are cheaper and easier to build for simple, scoped lookups and always reflect current state.

Cost or risk

They cannot perform live aggregation across vast datasets and fail via pagination/timeouts on set-level queries.

Source video ↗

Cached and vectorized data

Benefit

Enables complex semantic queries and avoids timeout risk on large dataset lookups.

Cost or risk

Requires ongoing syncing and vectorization, which platforms avoid due to cost and maintenance; cache can go stale without invalidation rules.

Source video ↗

Raw context volume

Benefit

More raw context could improve recall and completeness.

Cost or risk

Overloads the context window and triggers API timeouts, degrading reliability.

Source video ↗

Derived summaries (precomputed)

Benefit

Faster retrieval and bounded payloads for broad queries.

Cost or risk

Introduces staleness and requires provenance to trace back to sources; summaries can drift from underlying truth.
