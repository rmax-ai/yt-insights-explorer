Summary

Overview

  • Speaker: Dr. Stephanie Jarmak
  • Channel: AI Engineer
  • Main topic: How AI agents are transforming developer relations, go-to-market strategies, and software development workflows.
  • Purpose: To examine the changing landscape of developer relations and go-to-market strategies in the era of AI agents, arguing that developer advocates must become agent advocates. In this talk, Dr. Stephanie Jarmak explores how the rise of AI agents changes the role of developer advocates and developer relations (DevRel). With developers now orchestrating fleets of AI agents and non-engineers building tools, the traditional paths of software evangelism have evolved into a feedback loop. Agents act as both users and recommenders of software tools, meaning product go-to-market strategies must adapt to agent consumption alongside human developers.

  • Key claims:

    • Developer advocacy became a two-way feedback loop between developers and product teams in the 2010s.
    • In 2026, developers no longer work alone, and developers stopped meaning naming one person.
  • Examples:

Key Points

Agents sit in two seats at once

  • Explanation: AI agents act as both end users executing code and recommenders suggesting libraries and tools.
  • Evidence: Analysis of agent behavior across thousands of recorded prompt sessions and benchmark evaluations.
  • Practical implication: Product teams must optimize documentation and APIs for both human and machine consumption.

The blurring of organizational roles

  • Explanation: Engineering, product, and marketing roles overlap more than ever in managing AI agents and developer experience.
  • Evidence: Cross-functional collaboration required for MCP server instrumentation, evals, and GEO.
  • Practical implication: Teams need hybrid approaches combining engineering instrumentation, product UX, and marketing reach.

The importance of symptom-first documentation

  • Explanation: Agents search for solutions based on error symptoms and developer pain points rather than category names.
  • Evidence: Benchmark data showing zero mentions when prompts focus on general category names instead of specific failure symptoms.
  • Practical implication: Write documentation that explicitly addresses specific error messages and troubleshooting scenarios.

Core insights

[O]Mental Modelhigh noveltymoderate evidence

AI agents occupy two distinct functional roles in the software supply chain simultaneously: they are tool *users* (reading docs, authenticating, calling APIs, running CLIs, recovering from errors) and tool *recommenders* (selecting libraries, scaffolding frameworks, recommending tools to humans). This means the evaluation surface for a developer product now includes machine consumption, not just human discovery.

Why it matters

It reframes a product's addressable 'user' as an agent persona with its own auth, error-recovery, and tool-use requirements. If you only optimize for a human reading a landing page, you are invisible or unusable at the point where agents actually pick and install dependencies.

Generalization

Any product or internal platform consumed programmatically by agents needs two interfaces: a machine-executable interface (API/CLI/MCP) and a machine-legible persuasion surface (docs structured for retrieval and quoting). This applies to internal platform teams, not just external GTM.

[E]Empirical Resulthigh noveltymoderate evidence

Documentation should be authored against *symptom-first* retrieval patterns, because agents search from an error state rather than a product-category state. The reported benchmark result is that prompts framed around general category names produced zero mentions, while failure-symptom framing surfaced tools.

Why it matters

This is an actionable content-architecture constraint with a measurable outcome attached: doc sections that enumerate concrete error messages and troubleshooting scenarios are agent-retrievable, category-level marketing prose is not. It also suggests eval design: test your docs with symptom-shaped prompts, not product-shaped prompts.

Generalization

Agent retrieval is anchored to failure signatures. Any knowledge artifact intended for agent consumption (docs, runbooks, tool descriptions, error catalogs) should be indexed by observable symptom, not by taxonomy or capability name.

[E]Empirical Resulthigh noveltymoderate evidence

Mention rate and recommendation rate are distinct metrics, and being present in an agent's context does not imply being selected. Presence in a prompt or training corpus is necessary but not sufficient for adoption.

Why it matters

It splits 'visibility' into two measurable stages with different interventions. Optimizing for mention (SEO/GEO presence, registry listing) is not the same work as optimizing for recommendation (evidence that the tool is the right choice for this symptom). Teams building agent-facing eval harnesses should instrument both.

Generalization

For any agent-mediated selection process — tool selection, RAG source selection, model routing — separate 'was the candidate retrieved' from 'was the candidate chosen' and measure the gap. The retrieval-to-selection conversion is the real optimization target.

[!]Failure Modemedium noveltymoderate evidence

Agents exhibit reproducible, repeatable errors driven by training-data priors about command syntax and library choice — i.e., the model expects a different API shape than the tool actually exposes, and repeats that mistake identically across sessions.

Why it matters

Repeatable (not random) failure means it is fixable at the interface layer rather than the model layer: explicit tool descriptions, error messages that name the correct invocation, and self-correction affordances let the agent recover in-loop. This is a concrete argument for investing in error-message quality as a first-class tool-design concern.

Generalization

When agent failures are deterministic given a tool interface, the tool interface is the bug surface. Design error strings to be machine-actionable (state the correct command, not just that the command was wrong), and de-bias by explicitly noting deprecated/legacy alternatives.

[P]Practicemedium noveltyweak evidence

'Drift at read time' — stale documentation and stale training priors cause agents to recommend obsolete libraries or use outdated APIs, and this must be corrected in the documentation the agent reads at inference time rather than by waiting for model retraining.

Why it matters

It locates the corrective lever outside the model lifecycle. Because you cannot retrain the model, the only controllable point is the retrieved context: keep docs fresh, add authoritative sources (LLMs.txt), and explicitly mark deprecated paths so read-time evidence overrides stale priors.

Generalization

Model priors are effectively frozen; the retrieved context is the only writable channel. Systems should treat documentation as a live override layer for model bias, with freshness and deprecation-marking as reliability requirements rather than content chores.

The organizer's guidance implies treating agent telemetry and error data as a first-class feedback channel routed into product and engineering — agent failures become product requirements, not support tickets.

Why it matters

This makes observability of agent-tool interaction a DevRel/product responsibility with an engineering-shaped output (evals, instrumentation, doc fixes). It implies a telemetry pipeline where agent error traces are systematically mined rather than handled ad hoc.

Generalization

Agent-facing products need a closed loop: instrument agent tool calls → cluster failures → emit interface/doc fixes → re-run evals. Without this loop, deterministic agent errors persist indefinitely because no human files them.

Research question

Why

If presence in agent context is necessary but not sufficient, teams can burn budget on visibility and still lose selection. Decomposing mention from recommendation turns GEO into two instrumented stages with separate owners and separate metrics, and makes the conversion gap the actual optimization target.

Research question

Why

Deterministic agent tool-use errors as interface bugs

Research question

For tools where agents repeat identical invocation errors, does remediation at the interface layer (error strings naming the correct command, alias/shim layers, description rewrites) measurably reduce repeated error rates and improve in-loop self-correction?

Why

Repeatable rather than random failure relocates the bug surface from the model to the tool interface. That converts error-message quality into a first-class tool-design concern and gives every deterministic failure a natural home as a reproducible eval case.

MentionGap

beyond-evals

For a fixed tool, the mention-to-recommendation conversion rate is dominated by symptom-first documentation coverage rather than by registry presence; adding explicit symptom sections raises recommendation rate materially while registry listing alone does not.

Proof of concept

Build an eval harness that runs a fixed set of symptom-shaped and category-shaped buyer prompts against multiple models for one real OSS tool; ablate three factors — symptom doc coverage, registry/context presence, and explicit deprecation markers — and record mention rate and recommendation rate per condition.

Measurement

Delta in recommendation rate per ablation factor, with mention rate held constant; report the conversion gap (recommendation divided by mention) per condition and per model version.

Source video ↗

SymptomIndex

movement-lab

Documentation sections indexed by concrete error signature are retrievable by agents searching from a failure state, whereas capability-taxonomy sections are not; symptom-first structure increases agent surfacing even when total content volume is unchanged.

Proof of concept

Take one tool's docs, produce two variants (taxonomy-organized versus symptom-organized with identical underlying facts and error strings), and run both through the same symptom-shaped prompt set to compare surfacing and quoting behavior.

Measurement

Count of prompts that surface the tool and quote its docs, per variant; false-zero rate (prompts yielding no mention at all) per variant.

Source video ↗

ErrorStringFixLoop

gatehouse

Rewriting error strings to name the correct invocation reduces repeated identical agent tool-use failures more than rewriting tool descriptions alone, and the effect is measurable as in-loop recovery without human intervention.

Proof of concept

Instrument an MCP server to capture every tool call with intent, invocation, error, and recovery path; identify deterministic error clusters; ship three remediations in sequence (error-string rewrite, alias/shim layer, description rewrite) and re-run the same traces against each.

Measurement

Repeated-identical-error rate per remediation, in-loop recovery rate, and whether clustered failures map to doc/interface changes that survive a re-run of the eval suite.

Source video ↗

PriorOverrideLedger

new

Explicit deprecation markers and fresh authoritative sources in retrieved context shift agent library selection away from obsolete-but-prior-favored options, but only in the fraction of cases where retrieval actually fires; the residual gap is the ceiling on read-time correction.

Proof of concept

Maintain a ledger of deprecated libraries and their current replacements with an authoritative source file; run selection prompts with and without the ledger present in context, and measure how often retrieval fails to fire and the stale prior wins anyway.

Measurement

Share of selections shifted away from deprecated options with the ledger versus without, plus the retrieval-miss rate that bounds the achievable correction.

Architectural implications

4

Agent-consumed interfaces need error strings and tool descriptions designed for machine self-correction, since agents repeat identical mistakes when docs are unclear.

Before

Error messages and tool descriptions written for a human developer who can infer intent and search externally.

After

Error messages that explicitly name the correct invocation and disambiguate against the model's prior expectation; tool descriptions that include concrete examples and reference tables for the agent to quote.

Consequence

Tool/API surface design becomes an agent-UX discipline with its own review criteria; deterministic agent failures become reproducible test cases in an eval suite.

After

Tradeoffs and failure modes

4

Optimizing documentation for agent retrieval

Benefit

Higher recommendation rate when agents search from a failure symptom; agents can quote concrete examples, tables, and snippets.

Cost or risk

Symptom-first, example-dense documentation can degrade the human reading experience and encourage over-indexing on the agent as the primary audience, risking drift toward machine-optimized content that loses human credibility.

Source video ↗

Presence in agent context vs. being chosen

Benefit

Being listed in registries, marketplaces, and tool catalogs is a prerequisite for any recommendation.

Cost or risk

Teams can achieve high mention rate and still see no adoption, misallocating effort on visibility while losing on selection posture.

Source video ↗

Relying on read-time correction of model bias

Benefit

Corrects stale priors without waiting for model retraining; a controllable lever owned by the tool vendor.

Cost or risk

The correction depends on the agent actually retrieving the fresh documentation; if retrieval misses or the prior is strong, the obsolete recommendation persists. This is not a guarantee, only a probability shift.

Source video ↗

Treating agents as a distinct user persona

Benefit

Forces explicit design for authentication, tool-use, and error recovery that also benefits programmatic human users.

Cost or risk

Adds a second persona to maintain across docs, APIs, and UX; role blurring across engineering, product, and marketing creates ambiguous ownership.
