Overview

  • Speaker: Steven Latré

  • Main topic: Benchmarking the full stack of AI systems from silicon to harness, comparing API vs. on-premise infrastructure costs and trade-offs.
  • Purpose: To quantify the cost, accuracy, concurrency, and hardware trade-offs of moving from closed APIs to self-hosted infrastructure for agentic AI tasks. Steven Latré from imec discusses the transition from API-based token consumption to owning and operating your own AI infrastructure, presenting a comprehensive benchmarking study across thousands of runs evaluating models, coding harnesses, and hardware configurations for long-horizon coding tasks.

Key Points

The API-to-Infrastructure decision is non-linear

  • Explanation: Moving from APIs to self-hosted infrastructure involves complex trade-offs between model size, hardware architecture, and token consumption.
  • Evidence: Benchmarking data across 1,000+ runs shows non-linear cost and performance curves.
  • Practical implication: Engineers cannot simply swap APIs for self-hosted models without re-evaluating their entire infrastructure stack.

Concurrency and KV cache are major bottlenecks

  • Explanation: As user concurrency increases, GPU memory must accommodate both model parameters and growing KV caches.
  • Evidence: Larger models like Kimi K3 dropped to 4 comfortable concurrent users on 8x B300 with 3x higher latency than baseline.
  • Practical implication: Concurrency limits can severely degrade the economic viability of self-hosting large models.

Harness choice impacts GPU wall-time and token consumption

  • Explanation: Different coding harnesses generate vastly different numbers of tokens for the same task performance.
  • Evidence: Codex generated half the tokens of Claude Code and Pi for GLM-5.2-Flash, halving GPU wall-time and infrastructure cost.
  • Practical implication: Choosing the wrong harness when managing your own infrastructure can double your GPU bill.

When self-hosting, concurrency capacity is bounded by GPU memory budget = model weights + per-session KV cache, so 'comfortable concurrency' collapses for large models even on top-end hardware. Kimi K3 fell to ~4 concurrent users on 8x B300 with 3x latency vs baseline.

Why it matters

Capacity planning for self-hosted inference cannot be done from throughput benchmarks or model accuracy alone; the economically relevant number is how many concurrent long-horizon agent sessions fit in HBM after weights, which determines cost per session and SLA.

Generalization

For any long-context agentic workload, memory-per-session (KV cache) rather than FLOPs is the binding constraint on serving density; model size and context length trade directly against tenant count.

Generalization

When you own the inference layer, any component that controls token generation volume (harness, prompting, tool-call verbosity, context management) is a cost-multiplier with the same leverage as hardware selection.

Harness Cost Matrix

beyond-evals

For at least two open-weight models on long-horizon coding tasks, harness token-consumption rankings are stable and explain at least 50% of the variance in GPU wall-time per resolved task.

Proof of concept

Run Codex, Pi, and Claude Code harnesses against GLM-5.2-Flash and one additional open-weight model on a SWE-bench PRO subset, logging tokens, wall-time, and resolve rate for every run.

Measurement

Token ratio, wall-time per resolved task, and rank correlation across models; reject if rankings invert or token count does not predict wall-time.

Architectural implications

3

Serving capacity for agentic workloads is bounded by KV cache growth per concurrent session, not by raw compute.

Before

Plan inference capacity from model throughput/latency benchmarks at batch size 1.

After

Plan capacity as an HBM budget: weights + context_length x concurrency x KV-per-token, and cap concurrency explicitly per node.

Consequence

Long-horizon agent sessions (long contexts, many tool turns) become the dominant cost driver; context compaction and session lifetime become architectural concerns, not prompt hygiene.

Source video ↗

Harness token efficiency becomes an infrastructure-level cost variable under ownership.

Before

Harness is a developer-tooling choice, evaluated on task success and ergonomics.

After

Harness is a cost/throughput component with an owned-infrastructure price tag, evaluated on tokens-per-resolved-task and GPU wall-time.

Consequence

Harness selection, prompt scaffolding, and tool-call verbosity move into platform/ops ownership with continuous benchmarking, and may be routed per workload like models are.

Source video ↗

Model selection and hardware topology become a joint design decision.

Before

Pick the best model, then pick hardware that can run it.

After

Pick model+hardware pairs as a unit, benchmarked on resolve rate per dollar at target concurrency.

Consequence

Requires an internal benchmarking rig and periodic re-evaluation as new open-weight models appear; the decision surface is combinatorial rather than one-dimensional.

Tradeoffs and failure modes

3

Owning/leasing infrastructure for control

Benefit

Predictable cost, regulatory and security control over the stack, and ~25% savings for GLM-class workloads.

Cost or risk

Requires ~89% GPU utilization on lower-tier hardware to be viable, which is nearly infeasible; idle capacity inverts the economics.

Source video ↗

Choosing a stronger/larger model

Benefit

Higher task success (86.4% vs ~35-39% resolve rate in the reported comparison).

Cost or risk

Concurrency collapses to a handful of sessions and latency inflates ~3x, so effective cost per concurrent user rises sharply.

Source video ↗

Token-hungry harnesses

Benefit

Equivalent application resolve rate to leaner harnesses; no measurable quality loss.

Cost or risk

Under self-hosting, doubled token consumption doubles GPU wall-time and infrastructure cost.
