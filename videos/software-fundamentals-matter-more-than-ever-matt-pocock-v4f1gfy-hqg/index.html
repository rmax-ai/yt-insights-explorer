Summary

Overview

  • Speaker: Matt Pocock
  • Channel: AI Engineer
  • Main topic: Why software engineering fundamentals and code quality are more critical than ever in the age of AI coding tools
  • Purpose: To comfort developers worried about their skillset becoming obsolete and to provide practical tips for using AI coding tools effectively by applying proven software engineering design principles. Matt Pocock argues against the notion that software fundamentals are dead in the era of AI. Through six common failure modes experienced when using AI coding assistants (such as the AI not doing what you want, verbosity, code not working, doing too much, lacking code understanding, and cognitive overload), he demonstrates that bad code is more expensive than ever. Good codebases and foundational practices like ubiquitous language, Test-Driven Development (TDD), and deep modules (grey boxes) are essential to successfully leverage AI coding capabilities.

Topic Map

The Specs-to-Code Fallacy

  • Explanation: The flawed idea that developers can just write specs, let AI write code, and if something breaks, change specs without looking at the code. This leads to compounding complexity and garbage code.
  • Key claims:
    • Running the compiler over and over on unmanaged AI output leads to garbage code
    • Code is not cheap; bad code is the most expensive it has ever been
  • Examples:
    • Specs -> Code -> Worse Code -> Even Worse Code -> Garbage
  • Terminology:
    • Specs to code
    • Software entropy
    • Complexity
  • Why it matters: Ignoring code structure and relying solely on AI generation creates unmaintainable codebases that prevent developers from harnessing AI's true benefits.

Failure Mode 1 & Tip 1: Shared Design Concept

  • Explanation: Addressing the failure where AI doesn't do what you want by borrowing concepts from Frederick P. Brooks ('The Design of Design') on establishing a shared design concept before coding.
  • Key claims:
    • No-one knows exactly what they want initially
    • Using a skill like /grill-me forces the AI to relentlessly interview the user until a shared understanding is reached
  • Examples:
    • Using the /grill-me skill to walk down each branch of the design tree before creating code
  • Terminology:
    • Design concept
    • /grill-me
    • Plan mode
  • Why it matters: Reaching a shared design concept prevents communication barriers and misaligned requirements between the human and the AI.

Failure Mode 2 & Tip 2: Ubiquitous Language

  • Explanation: Fixing AI verbosity and miscommunication by establishing a shared vocabulary derived from Domain-Driven Design (Eric Evans).
  • Key claims:
    • A ubiquitous language aligns developer, domain expert, and AI conversations
    • Creating a UBIQUITOUS_LANGUAGE.md file improves planning and implementation precision
  • Examples:
    • Creating and referencing UBIQUITOUS_LANGUAGE.md while prompting the AI
  • Terminology:
    • Ubiquitous language
    • Domain-driven design
    • Domain model
  • Why it matters: A shared vocabulary reduces ambiguity and helps the AI think and write in concise, domain-aligned terms.

Failure Mode 3, 4 & Tip 3: Feedback Loops & TDD

  • Explanation: Tackling code that doesn't work and AI doing too much by enforcing strict feedback loops, static types, browser access, automated tests, and Test-Driven Development.
  • Key claims:
    • The rate of feedback is your speed limit
    • TDD forces the LLM to take small, deliberate steps rather than generating massive blocks of untested code
  • Examples:
    • Writing a test first, making it pass, then refactoring
  • Terminology:
    • Feedback loops
    • TDD
    • Speed limit
  • Why it matters: Without proper feedback loops and small steps, AI tends to outrun headlights and produce broken code.

Failure Mode 5, 6 & Tip 4, 5: Deep Modules & Grey Boxes

  • Explanation: Solving AI misunderstanding and brain overload by structuring codebases into deep modules with simple interfaces and hidden complexity, inspired by John Ousterhout.
  • Key claims:
    • Shallow modules create tiny blobs that are hard for both humans and AI to understand and explore
    • Deep modules act as grey boxes where you design the interface and delegate implementation
  • Examples:
    • /improve-codebase-architecture skill to deepen modules and organize boundaries
  • Terminology:
    • Deep modules
    • Shallow modules
    • Grey boxes
    • Simple interface
  • Why it matters: Structuring code into deep modules saves mental energy and allows both developer and AI to interact via clean, testable boundaries.

Key Points

Code is not cheap; bad code is the most expensive it has ever been

  • Explanation: While AI makes generating lines of code cheap, bad codebases prevent you from utilizing AI effectively.
  • Evidence: Comparing software entropy and Ousterhout's definition of complexity.
  • Practical implication: Invest in codebase architecture and software fundamentals daily.

The rate of feedback is your speed limit

  • Explanation: Large AI tasks lead to failures. Small steps and fast feedback keep development on track.
  • Evidence: Pragmatic Programmer principles applied to AI code generation.
  • Practical implication: Use TDD and small prompts to avoid outrunning your headlights.

Design the interface, delegate the implementation

  • Explanation: Treat deep modules as grey boxes where boundaries and interfaces are human-designed, while implementation is delegated to AI.
  • Evidence: Contrasting flat shallow module grids with well-bounded deep module architectures.
  • Practical implication: Focus your brain on high-level system design and let AI handle tactical implementation details.

[A]Architecturehigh noveltymoderate evidence

Module depth is reframed as an agent-comprehension property, not just a human-maintainability property: shallow modules decompose into 'tiny blobs' that both humans and the AI struggle to navigate and explore, while deep modules with simple interfaces act as grey boxes where the human designs the boundary and delegates the interior. This makes codebase shape a direct input to agent performance.

Why it matters

If agent success depends on the navigability of the module graph, then architectural refactoring becomes an investment in agent throughput rather than a purely hygiene activity, and interface design becomes the human's primary artifact.

Generalization

For any agent operating over a large artifact graph (code, schemas, service catalogs, docs), abstraction granularity and interface narrowness govern how much of the system the agent must load and reason about per task.

[M]Mechanismmedium noveltymoderate evidence

TDD is used as a step-size governor for the model rather than merely a correctness ritual: writing a test first and making it pass constrains the LLM to small deliberate increments instead of emitting large untested blocks. The stated governing metric is feedback rate, framed as the speed limit of the whole system.

Generalization

Any agent loop should be bounded by the latency and fidelity of its cheapest verification signal; the loop step size should be derived from time-to-feedback, not from the apparent size of the goal.

4

Architecture Is Now an Agent Input, Not Just a Human Courtesy

Refactoring toward deep modules is no longer a maintainability chore paid for by human onboarding cost; it is a direct investment in agent throughput, which means interface design quality is the binding constraint on agent reliability and the interface itself becomes the primary review surface.

Angle

Reframe architecture work as capability work: show how shallow-module codebases turn agent tasks into wide-context navigation problems, and argue the human's job migrates from reviewing implementations to designing boundaries.

Source video ↗

Bad Code Is the Most Expensive It Has Ever Been

Cheap generation does not make code cheap: the specs-to-code loop has no read/verify step, so each regeneration cycle deposits unmanaged output that degrades the very codebase the agent must work in next, making quality a throughput variable rather than a hygiene concern.

Angle

Name the entropy loop explicitly and specify the missing step — inspection of prior artifacts — as the fix, rather than arguing for better prompts or larger models.

Source video ↗

Stop Decomposing Tasks by Logic; Decompose Them by Time-to-Feedback

If the rate of feedback is the system's speed limit, then step size should be derived from the latency of the cheapest verification signal rather than from the apparent logical shape of the goal, which reorganizes planning around test runtime, type checking, and browser access instead of task boundaries.

Angle

Turn a slogan into a scheduling rule: walk through how feedback latency sets a hard cap on step size and why easy-but-hard-to-test work is the throughput bottleneck.

Move Domain Context Out of the Prompt and Into the Repository

Treating verbosity and miscommunication as prompt defects is a category error; persisting a shared vocabulary as a versioned repo artifact makes context diffable and terminology drift observable, at the cost of a permanent synchronization obligation between glossary, code, and tests.

Argue for externalized vocabularies as first-class repo citizens, then confront the drift problem the approach creates instead of treating the glossary as a one-time artifact.

Agent Comprehension Bench

beyond-evals

At identical functionality, agent task success rate rises and tokens/steps per accepted change fall as module depth increases (fewer, wider interfaces with hidden interiors).

Proof of concept

Implement the same application at three module-granularity levels — many shallow modules, one monolith, deep modules with narrow interfaces — and run an identical task suite against each with the same coding agent, recording navigation and edit traces.

Measurement

Task success rate, tokens per accepted change, tool-call steps, and rate of edits landing in unintended modules, compared across the three granularity variants.

Source video ↗

Feedback-Latency Governor

movement-lab

Accepted-changes-per-hour in an agent loop is bounded by time-to-feedback, so cutting verification latency (test runtime, type-check time, browser round-trip) raises completed-task rate proportionally and shrinks generated step size.

Proof of concept

A harness that measures time-to-feedback per step and automatically caps the agent's step size at that bound, run over a fixed task set against a batch-generation baseline with no such cap.

Measurement

Wall-clock throughput (accepted changes per hour), rework rate per accepted change, and total tokens per accepted change, with and without the latency-derived step cap.

Glossary Drift Gate

gatehouse

Automated drift detection between persisted glossary terms, code identifiers, and test names reduces agent requirement-conformance failures relative to an unenforced glossary file.

Proof of concept

A checker that maps UBIQUITOUS_LANGUAGE.md terms to identifiers and test names, flags divergence as a blocking gate before agent runs, and injects the reconciled vocabulary into the prompt.

Measurement

Count of detected term/identifier divergences over time, requirement-conformance rate on a fixed task set, and prompt verbosity (tokens spent restating domain context).

Interrogation-Before-Generation Skill Eval

new

An adversarial pre-code interrogation phase that enumerates the design decision tree reduces requirement-conformance failures per accepted change more cheaply than repairing misaligned output after generation.

Proof of concept

A /grill-me-style skill that iteratively questions the user down each design branch until a shared design concept is recorded, benchmarked against direct generation on the same underspecified task set.

Measurement

Number of design branches resolved pre-code, rework rate, tokens per accepted change, and fraction of generated code discarded after first review.

Architectural implications

3

The human/agent responsibility split is drawn at the module interface rather than at the line of code.

Before

Humans wrote implementations and reviewed AI output line by line.

After

Humans design interfaces and boundaries; agents own implementation behind those boundaries, and an agent skill refactors the codebase toward deeper modules.

Consequence

The interface becomes the primary review surface and the primary context-passing unit, so interface design quality directly bounds agent reliability.

Domain context is externalized from prompts into repository artifacts.

Before

Domain terms and constraints were restated per conversation or held in the model's context window.

After

A UBIQUITOUS_LANGUAGE.md file lives in the repo and is referenced during planning and implementation.

Consequence

Context becomes versionable, diffable, and shareable across agents and humans, but introduces a synchronization obligation between the glossary, code, and tests.

Codebase shape becomes an input variable to agent performance.

Before

Refactoring was justified by human maintainability and onboarding cost.

After

Module depth and interface narrowness are treated as determinants of whether an agent can comprehend and explore the system.

Consequence

Architecture work can be budgeted as agent-capability work, and codebase metrics could be evaluated against agent task success rather than only human effort.

Tradeoffs and failure modes

4

Tight feedback loops (types, browser access, automated tests, TDD)

Benefit

Small verified steps keep the LLM inside a tight loop, catching breakage before it compounds and preventing large untested generations.

Cost or risk

Every step carries verification and setup overhead; all work must be decomposed to fit the feedback cadence, which caps achievable step size and may slow throughput on tasks that are easy but hard to test.

Source video ↗

Deep modules as grey boxes

Benefit

Simple interfaces over hidden complexity save mental energy and give both developer and AI a clean, testable boundary to interact through.

Cost or risk

Interfaces must be designed before the implementation is understood, and the delegated interior becomes opaque — correctness lives behind a boundary the human is no longer inspecting.

Source video ↗

Pre-code adversarial interrogation (/grill-me)

Benefit

Forces the design tree's branches to be resolved up front, producing a shared design concept before any code exists.

Cost or risk

Adds an explicit up-front phase before any output; if the interview is unfocused it consumes effort proportional to the ambiguity rather than to the value of the resulting design.

Source video ↗

Regenerating from specs without inspecting code

Benefit

Fast iteration: when output is wrong, adjust the spec and regenerate rather than reading and repairing the artifact.

Cost or risk

Compounding complexity and garbage code; the loop has no read/verify step, so each cycle adds unmanaged output that degrades the codebase the agent must later work in.
