Overview

  • Speaker: Ankur Duggal
  • Channel: AI Engineer
  • Main topic: Evaluating and improving AI agents using traces, CLIs, and structured loops
  • Purpose: To demonstrate a structured, repeatable framework for debugging and evaluating AI agents in production using observability tools and coding agent skills. Ankur Duggal from Arize AI explains how developers can move beyond debugging AI agents on vibes and establish rigorous evaluation loops using traces, datasets, root-cause analysis, and experiment management. He demonstrates setting up a coding agent skill via the Arize CLI to automatically pull traces, cluster failures, and propose code and prompt fixes.

The Problem with Vibing in Agent Development

  • Key claims:

    • Gut feeling is insufficient for production-grade AI applications.

Traces as the New Source of Truth

  • Explanation: Unlike traditional software with deterministic call graphs, AI agents rely on LLM reasoning steps that require tracing to debug.
  • Key claims:
    • Traditional software has deterministic paths that are easy to trace via APM tools.
    • LLM agents have non-linear execution paths requiring deep traces.
    • Traces capture every step, tool call, and LLM response.
  • Examples:
    • A support agent calling the wrong order status tool due to hallucination.
  • Terminology:
    • traces
    • APM monitoring
    • tool call
    • groundedness
  • Why it matters: You cannot read an agent or harness through code alone; traces provide the execution context needed to find root causes.

Key Points

Shift from vibe debugging to metric-driven evaluations

  • Explanation: Relying on intuition in production leads to undetected hallucinations and systemic failures.
  • Evidence: Audience poll showed high adoption of vibe-based checking compared to structured evaluation setups.
  • Practical implication: Teams must build eval suites tied to real production traces.

Traces reveal hidden agent execution errors

  • Explanation: Agentic workflows make multiple tool calls and reasoning steps that require step-by-step visibility.
  • Evidence: An example trace showed a support agent calling order status instead of handling a refund request.
  • Practical implication: Instrumentation is mandatory before attempting to debug complex multi-step agents.

Agents follow an engineering loop, not magic

  • Explanation: Fixing agents requires gathering evidence, forming hypotheses, writing evals, testing prompts, and verifying results.
  • Evidence: The 8-step loop framework demonstrated at Arize.
  • Practical implication: Engineering teams should treat agent debugging with the same rigor as CI/CD pipelines.

Core insights

[O]Mental Modelhigh noveltymoderate evidence

Failure detection and failure evaluation are decoupled in time: engineers observe that an agent is broken well before they can formalize what 'broken' means as a metric, so the operational bottleneck is converting a felt symptom into an executable evaluator rather than detecting the symptom.

Why it matters

Shifts effort from monitoring/dashboards toward evaluator authoring as the scarce engineering activity; teams that only instrument will still stall because they cannot regression-test the failure they just saw.

Generalization

For any non-deterministic system, the expensive step is operationalizing a quality criterion, not observing anomalies — build the path from observed failure to codified check as a first-class workflow.

[A]Architecturemedium noveltymoderate evidence

Traces occupy the architectural role that call graphs/APM occupy in deterministic software: because agent execution paths are non-linear and reasoning-mediated, the trace — not the source code — is the artifact that must be read to locate a root cause.

Why it matters

Implies tracing is a prerequisite for debugging, not a nice-to-have: without span-level capture of every tool call and LLM response, no amount of code reading localizes the fault.

Generalization

When control flow is decided at runtime by a model, the execution record becomes the primary specification of behavior; debuggers, tests, and agents must all consume traces as their input interface.

[M]Mechanismmedium noveltymoderate evidence

The debugging loop is externalized as an installable skill that a coding agent executes against production trace data via a CLI, so the agent — not the human — performs trace pulling, failure clustering, hypothesis formation, evaluator authoring, and fix proposal.

Why it matters

Moves the debugging harness outside the application codebase and into a tool-interface layer (CLI + skill), making the improvement loop scriptable, repeatable, and transferable across projects.

Generalization

Agentic tooling is most powerful when the observability backend exposes a programmatic CLI/skill surface that an agent can drive, rather than a human-only UI.

[P]Practicemedium noveltymoderate evidence

Failure clustering is the compression primitive that makes the loop tractable: instead of debugging individual bad outputs, related failures are grouped so that one root-cause hypothesis and one evaluator cover a whole class of production errors.

Why it matters

Converts unbounded per-incident debugging into a bounded number of clusters, which is the mechanism behind the claimed days-to-minutes compression.

Generalization

Any evaluation pipeline over high-volume production traffic needs a clustering/dedup stage before human or agent analysis, or cost scales with incident count rather than with distinct causes.

[P]Practicelow noveltymoderate evidence

Evaluators should be authored against real production trajectories rather than synthetic inputs, with experiments comparing a candidate against a stored baseline and runnable either locally or on the platform.

Why it matters

Makes the eval dataset a production-derived artifact that stays distributionally aligned with the failures actually occurring, and makes experiment comparison the acceptance gate for fixes.

Generalization

Evaluation suites degrade when they drift from observed traffic; the sustainable pattern is continuous harvesting of real traces into eval datasets plus baseline-vs-candidate experiment runs.

[!]Failure Modemedium noveltymoderate evidence

A representative agent failure is a silent semantic routing error — the agent invokes a plausible but wrong tool (`get_order_status` for a refund request) and then fabricates a successful-looking answer, which no exception, schema check, or output-format validator would catch.

Deep dives

5

Minimum viable trace schema for root-cause localization

Research question

Which subset of captured span fields (tool name, tool arguments, tool result, model reasoning, intermediate state, latency, token counts) is minimally sufficient for a human or coding agent to correctly localize the root cause of an agent failure?

Why

If a small set of fields carries almost all localization signal, tracing cost, storage, and PII surface can be cut dramatically; if reasoning text is load-bearing, redaction and retention policies must change. Without an ablation, teams instrument maximally and still cannot tell which fields made the debug succeed.

Source video ↗

Deterministic tool-call preconditions versus LLM-judge tool-selection evaluators

Research question

Can wrong-tool-invocation failures be detected structurally — via intent-to-tool contracts and argument preconditions — with recall comparable to an LLM judge at materially lower cost?

Why

The most dangerous failure returns HTTP 200 with a confident, well-formed, wrong answer, so exception handling and schema validators are structurally blind to it. If deterministic preconditions catch most of these, judge capacity is freed for genuinely semantic properties like groundedness; if they do not, teams must budget judge calls on every tool call, not every conversation.

Source video ↗

Memorization risk in eval suites harvested from production failures

Research question

How quickly does an eval set harvested from a fixed window of failing production traces stop discriminating on fresh traffic, and what re-baselining cadence keeps it predictive?

Why

The loop claims convergence ('fewer failures occur with each iteration pass'), but a harvested eval set is a sample of past incidents. If it saturates, the verification gate passes candidates that would fail on new traffic — the loop appears to converge while production quality plateaus. This determines whether continuous harvesting is optional hygiene or a mandatory control.

Source video ↗

Acceptance thresholds as automated merge gates for agent-proposed fixes

Research question

What experiment delta and guardrail-eval combination is sufficient to auto-accept an agent-proposed prompt or code change, and at what point must a human reviewer enter the loop?

Why

The claimed days-to-minutes compression depends entirely on the verify step, which the summary leaves unspecified. If the gate is too loose, the loop ships plausible-but-wrong fixes faster than a human team would; too tight and the compression vanishes. This is the boundary between a demo and a deployable practice.

Source video ↗

Failure-cluster size distribution as the precondition for loop tractability

Research question

In real agent traffic, how concentrated is the failure distribution across root-cause clusters — is the number of distinct causes bounded and stable, or does it grow with incident count and defeat the clustering compression?

Why

The entire days-to-minutes claim rests on one hypothesis and one evaluator covering a whole class of errors. If the distribution is heavy-tailed with mostly singleton clusters, per-incident cost is irreducible and the loop's throughput advantage disappears — a result worth knowing before teams reorganize around cluster-driven triage.

Article ideas

4

You Already Know It's Broken: The Bottleneck Is Evaluator Authoring, Not Observability

Instrumentation is a solved commodity; the binding constraint on agent quality is the latency between noticing a failure and encoding it as an executable check. Teams that buy dashboards without buying an evaluator-authoring workflow will observe their failures indefinitely without regressing them.

Angle

Reframe the tooling market and the engineering job description: measure teams by time-from-symptom-to-evaluator, not by dashboard coverage or span volume.

Source video ↗

Traces Are the Source Code of an Agent

When control flow is decided at runtime by a model, the trace — not the repository — is the artifact that specifies actual behavior. Debuggers, tests, and coding agents must therefore take traces as their primary input interface, which makes span-level capture a prerequisite for debugging rather than an observability afterthought.

Angle

Architectural argument with a concrete consequence: any debugging tool that cannot consume spans is unusable on agents, regardless of how good its code analysis is.

Source video ↗

Silent Tool Routing Is the New Outage — and Your Validators Can't See It

As agents compose tools, the dominant reliability risk migrates from crashes and schema violations to plausible-but-wrong action selection that returns a well-formed, confident, incorrect answer. Output-level validation and exception handling are structurally blind to this class, so correctness must be judged at the trajectory level.

Angle

Failure-taxonomy piece: walk a single refund/order-status misroute through every conventional check it passes, then show what a trajectory-level judge or precondition contract would have caught.

Source video ↗

Your Agent Debugger Is a Scaffold, Not a Genius

The reliability of agent-driven debugging comes from the enforced procedure — observe, cluster, hypothesize, evaluate, fix, experiment, verify — plus a verification gate, not from model capability. This is testable and consequential: swap the model and loop completion rate should hold, while removing the gate should cause regressions to ship faster.

Angle

Argue the harness is the artifact to engineer, version, and test; treat prompt-and-pray 'fix the bug' instructions as the anti-pattern.

Project ideas

4

Span Ablation Bench

beyond-evals

A minimal span set — tool name, tool arguments, tool result, and final model output, without reasoning text or intermediate state — achieves at least 80% of full-schema root-cause localization accuracy on a fixed agent failure corpus.

Proof of concept

Freeze a corpus of 60-100 labeled agent failures with known root causes. Programmatically produce five trace projections (minimal, +reasoning, +args, +intermediate state, full). Have both a coding agent and human engineers localize root causes under each projection, blind to the label.

Measurement

Per-projection localization accuracy, time-to-localize, judge/agent token cost, and storage delta versus the full schema. Falsified if minimal-schema accuracy falls below 80% of full.

Source video ↗

Tool Contract Linter

gatehouse

Deterministic intent-to-tool preconditions and argument constraints detect at least 60% of silent wrong-tool-invocation failures at under 5% of the cost of an LLM-judge tool-selection evaluator.

Proof of concept

Define declarative preconditions per tool (e.g. refund path requires a refund-intent signal and a refund-eligible order state). Run the linter and a judge evaluator over a corpus containing the refund/order-status misroute class plus clean traffic, and compare detection sets.

Measurement

Recall and precision against labeled misroutes, false-positive rate on clean traffic, cost per 1k tool calls, and latency added per call. Falsified if recall trails the judge by more than 20 points or false positives exceed 3%.

Source video ↗

Eval Decay Monitor

beyond-evals

Eval suites harvested from a single traffic window lose at least 30% of their discriminating power on traffic sampled four weeks later, even with no code changes.

Proof of concept

Harvest a failure-derived eval set from week 0 traffic. Replay baseline, week-2, and week-4 traffic windows through the same agent build and score each window with the week-0 evaluators; also track candidate-vs-baseline deltas per window to see when the gate stops separating good from bad.

Measurement

Discrimination (AUC or pass-rate gap between known-good and known-bad outputs) per window, plus the week at which the gate fails to flag a deliberately injected regression. Falsified if discrimination holds within 10% across four weeks.

Source video ↗

Cluster Compression Audit

movement-lab

Real agent failure traffic compresses into a bounded set of root-cause clusters such that the top 20 clusters cover at least 70% of incidents, making cluster-driven triage cheaper than per-incident debugging.

Proof of concept

Ingest a month of production traces for an agent, run embedding-plus-LLM clustering on failure outputs and trajectories, then have engineers label a stratified sample to measure cluster purity and how many distinct causes sit behind the top clusters.

Measurement

Cluster-size distribution (share of incidents in top 20), cluster purity from human labels, number of distinct root causes per cluster, and estimated engineer-hours saved versus incident-by-incident triage. Falsified if top-20 coverage falls below 50% or average purity drops under 0.7.

Architectural implications

3

Improvement loop runs on traces pulled out of the observability backend into a coding agent, rather than on the source repo alone.

Before

Engineer reads code and reproduces the bug locally to guess what happened.

After

Engineer or coding agent pulls production traces via CLI, clusters failures, and derives fix candidates from observed behavior.

Consequence

The observability platform's CLI/tool API becomes a load-bearing developer interface; its ergonomics and data fidelity determine debugging speed.

Source video ↗

Evaluators and datasets become derived artifacts of production traffic rather than hand-written specs.

Before

Eval sets written up front from imagined user inputs.

After

Eval cases harvested from failing production traces and versioned alongside experiment runs.

Consequence

Eval quality tracks traffic coverage; requires governance for PII handling, sampling, and re-baselining as distributions shift.

Source video ↗

The coding agent is given a bounded, repeatable procedure (the 8-step loop) plus tools, rather than open-ended license to fix.

Before

Prompt an agent to 'fix the bug' with no evidence discipline.

After

Agent must traverse observe -> cluster -> hypothesize -> evaluate -> fix -> experiment -> verify before a change is accepted.

Consequence

Reliability comes from the loop scaffold and the verification gate, not from model capability; the harness becomes the thing to engineer and test.

Tradeoffs and failure modes

4

LLM-as-a-judge evaluator cost versus accuracy

Benefit

Automated, scalable scoring of semantic properties like groundedness and tool-selection correctness on real traffic.

Cost or risk

Judge calls add inference cost and latency proportional to eval volume, and judge error rates can silently corrupt the signal used to accept or reject fixes.

Source video ↗

Automated fix generation by coding agent

Benefit

Collapses multi-day manual triage into a single scripted loop the agent executes.

Cost or risk

Agent-proposed prompt or code changes can be plausible but wrong; without a verified-improvement gate the loop can ship regressions faster than humans would.

Source video ↗

Silent tool-routing failures

Benefit

Multi-tool agents can satisfy user intent flexibly by choosing tools at runtime.

Cost or risk

Wrong-tool invocation produces a well-formed, confident, and entirely incorrect response with no exception raised, so conventional error handling and output validation miss it.

Vendor-demonstrated productivity gains

Benefit

Claimed compression of debugging from days to minutes via CLI-driven agent loops.

Cost or risk

Claim comes from a product demo on a curated scenario with no independent measurement or controlled baseline, so it may not transfer.
