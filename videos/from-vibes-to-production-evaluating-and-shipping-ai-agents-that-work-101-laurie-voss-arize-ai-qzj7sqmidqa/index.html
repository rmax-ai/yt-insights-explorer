Overview

  • Speaker: Laurie Voss
  • Channel: AI Engineer
  • Main topic: Evaluating and shipping production-ready AI agents using observability, tracing, code evaluations, LLM-as-a-judge evaluators, datasets, experiments, and meta-evaluation.
  • Purpose: To educate AI engineers on how to build, trace, evaluate, and systematically improve LLM-based AI agents using structured testing, evaluation rubrics, and observability tooling. Laurie Voss, Head of Developer Relations at Arize AI, presents a comprehensive 101 workshop on moving AI agents from casual 'vibe checks' to reliable production systems. He explains why standard software unit tests and manual reviews fail for non-deterministic AI outputs, introducing a rigorous framework of OpenTelemetry tracing (via Arize AX), code evals, LLM-as-a-judge evals, golden datasets, error analysis, and meta-evaluation to iteratively improve agent prompts and codebases.

    • Traces are logs for AI; evals are tests for AI.
    • Without evals, changing a prompt to fix one tone issue can silently hallucinate product features elsewhere.
    • Manual human review does not scale, doesn't catch regressions, and doesn't run in CI.
  • Examples:

Two Types of Evals: Code Evals vs. LLM-as-a-Judge Evals

  • Explanation: Comparison of code-based deterministic checks versus semantic LLM-as-a-judge evaluations, highlighting their pros, cons, and appropriate use cases.
  • Key claims:
    • Code evals are deterministic, free, fast, and reproducible like unit tests, but can be brittle.
    • LLM-as-a-judge evals use a second LLM to grade outputs against a rubric, handling meaning and semantics rather than just strings.
    • LLM judges cost money, are non-deterministic, and require calibration against human judgment.
  • Examples:
    • Code eval checking if output parses as JSON or contains a ticker symbol.
    • LLM judge checking faithfulness or tone.
  • Terminology:
    • code evals
    • LLM-as-a-judge
    • rubric
    • deterministic
  • Why it matters: Helps engineers choose the right evaluation mechanism depending on whether the test is syntactic or semantic.

Why Agents Make Evaluation Harder

  • Explanation: Analysis of multi-agent and multi-turn agent execution complexity, tool calls, and cascading errors.
  • Key claims:
    • Single LLM calls have simple input-output pairs, but agents make a series of tool calls and reasoning steps.
    • Errors cascade across steps: bad retrieval leads to bad reasoning, leading to confidently wrong output.
    • Multi-agent handoffs add another layer where triage and specialist routing can fail.
  • Examples:
    • Agent searching the web for Tesla, finding info on an 18th-century inventor instead, and writing a polished report about them.
  • Terminology:

    • multi-agent complexity
    • tool calls
    • hallucination
  • Why it matters: Demonstrates why monitoring intermediate agent steps (spans) is essential for debugging agent workflows.

Error Analysis and Looking at Your Data

Building and Running Code Evals

  • Explanation: Writing simple deterministic code evaluators in Python to check specific constraints like ticker symbol mentions.
  • Key claims:
    • Code evals provide instant, free, deterministic checks for format, structure, constraints, and required fields.
    • Grade the outcome, not the path; don't punish agents for taking a creative or unexpected path to the correct answer.
  • Examples:
    • Writing a Python evaluator to check if a financial report mentions the required stock ticker.

Building LLM-as-a-Judge Evals and Rubrics

  • Explanation: Implementing semantic evaluations using LLM judges, covering correctness and faithfulness, structuring rubrics with XML tags, and managing tradeoffs.
  • Key claims:
    • An LLM judge rubric should have four parts: define the judge's role, define explicit pass/fail criteria, label data with XML tags, and define output choices outside the prompt.
    • Include labeled examples of good and bad outputs in your rubric to drastically improve judge consistency.
    • Chain-of-thought prompting (asking the judge to explain its reasoning before scoring) measurably improves evaluation accuracy.
  • Examples:
    • Using Built-In Correctness and Faithfulness evaluators with Claude Sonnet 4.6 as a judge.
  • Terminology:
    • LLM-as-a-judge
    • rubric
    • faithfulness
    • correctness
    • XML tags
    • chain-of-thought
  • Why it matters: Enables evaluation of complex semantic attributes like adherence to source documents and actionability.

Meta-Evaluation: Testing Your Tests

  • Explanation: Evaluating the evaluator by comparing LLM judge predictions against human annotations to measure agreement, precision, and recall.
  • Key claims:
    • Your judge is a classifier that makes predictions (pass/fail or actionable/not actionable) that can be compared against human ground truth.
    • Human inter-rater reliability is often low (0.2–0.3 Cohen's Kappa); if your judge is more consistent than humans, that's a win.
    • When judges disagree with humans, read explanations to uncover ambiguity in your rubric.
  • Examples:
    • Calculating agreement rate between human annotations and classification evaluator scores in a pandas DataFrame.
  • Terminology:
    • meta-evaluation
    • confusion matrix
    • precision
    • recall
    • inter-rater reliability
  • Why it matters: Ensures that the evaluation suite itself is trustworthy and correctly calibrated.

The Eval-Iterate Cycle and Automated Prompt Improvement

Key Points

Treat Evals as Infrastructure

  • Explanation: Evaluations should not be an afterthought; they must be treated with the same rigor and systematic integration as unit tests in traditional software engineering.
  • Evidence: Real-world engineering teams at Descript, Bolt, and Anthropic followed the exact arc of shipping on vibes, realizing it didn't scale, and building evals.
  • Practical implication: Establish telemetry and evaluation loops early in the development process rather than trying to retrofit testing after production deployment.

Grade the Outcome, Not the Path

  • Explanation: When evaluating AI agents that perform multi-step reasoning and tool calls, grading intermediate trajectories rigidly punishes creative and valid problem-solving paths.
  • Evidence: Discussion of multi-turn customer service benchmarks where agents find valid alternative execution paths that rigid trajectory testing marks as failures.
  • Practical implication: Design evaluators to check the final output and compliance with success criteria rather than enforcing a strict sequence of tool calls.

Data Quality Fixes Have the Highest Impact

  • Explanation: When iterating to improve agent performance, fixing knowledge base and retrieval data quality yields significantly higher returns than prompt tweaks or model switching.
  • Evidence: Presented in the impact hierarchy: 1. Data quality fixes, 2. Prompting improvements, 3. Model selection, 4. Hyperparameter tuning.
  • Practical implication: Invest engineering effort into retrieval augmented generation (RAG) data hygiene and grounding sources before spending time on hyperparameter tuning.

Frameworks, Models & Processes

The Swiss Cheese Model of Quality

  • How it works: Combines multiple layers of defense to catch agent errors, recognizing that no single evaluation method catches everything.
  • Components:
    • Automated code evals (catches format and syntax issues)
    • LLM-as-a-judge reviews (catches semantic and reasoning gaps)
    • Manual transcript reviews / early access programs (catches novel failures)
    • Production monitoring, A/B testing, and user feedback (catches edge cases in production)
  • When to use: When designing an end-to-end quality assurance strategy for production AI applications.

The Eval-Iterate Cycle

  • How it works: A continuous feedback loop for AI software development that mirrors traditional CI/CD pipelines.
  • Components:
    • Find failures via tracing
    • Read explanations via error analysis
    • Fix prompts or data
    • Run experiments against test datasets
    • Repeat
  • When to use: During the development, debugging, and maintenance phases of building AI agents.

The Impact Hierarchy

  • How it works: Prioritization framework for where to invest engineering resources when optimizing AI agent performance.
  • Components:
    • Data quality fixes (highest impact)
    • Prompting improvements
    • Model selection
    • Hyperparameter tuning (lowest impact)
  • When to use: When deciding what part of an AI system to refactor or tune following evaluation failures.

Actionable Takeaways

  • Immediate:
    • Instrument your agent application with OpenTelemetry tracing using two lines of code.
    • Read at least a dozen raw traces end-to-end to understand actual failure modes before writing evals.
    • Start with simple code evals for deterministic checks and add LLM judges for semantic checks.
  • Strategic:
    • Treat evaluations as core infrastructure rather than an afterthought.
    • Build golden datasets from production failures to act as permanent regression test suites.
    • Involve domain experts (product managers, customer success) in defining success criteria and writing evaluation rubrics.
  • Questions to investigate:
    • What is the inter-rater reliability between human reviewers and our LLM judge rubrics?
    • How can we systematically sample production traffic (e.g., 10%) to minimize evaluation costs while maintaining statistical significance?
    • Which dimensions of agent performance require guardrail evals versus North Star metric evals?

Core insights

[P]Practicehigh noveltymoderate evidence

Grade the outcome, not the execution path: agent evaluators should score the final result against requirements rather than penalizing agents for taking unexpected or creative routes to a correct answer.

Why it matters

Reward-shaping on the path over-constrains agents, suppresses valid tool-use strategies, and creates brittle evals that fail agents that are actually correct. Outcome grading keeps evals aligned with real user value while leaving the agent free to explore alternative trajectories.

Generalization

Applies to any evaluated non-deterministic system where multiple valid solution paths exist (agents, planning systems, search): evaluate on terminal artifacts and constraints, not intermediate action sequences, unless the path itself is a safety or cost constraint.

Calibrating LLM-as-a-judge evaluators for CI gating

Research question

What judge-human agreement level is achievable, and what calibration investment is required before an LLM judge can serve as a trustworthy CI gate?

Why

Without calibration, judge verdicts are non-deterministic and biased, so automated gates either block valid changes or pass regressions. Calibration determines whether LLM-as-a-judge can be a production quality gate rather than a noisy signal.

Architectural implications

3

Tracing/observability must be established as a layer beneath evaluation, since evals consume trace data rather than raw application state.

Before

Evaluation treated as an ad-hoc, end-of-pipeline check on final outputs, or as manual review of sample responses.

After

An instrumentation layer (OpenTelemetry/OpenInference) captures spans, token counts, model names, and tool calls, which evals then consume as input.

Consequence

Evaluation becomes a downstream consumer of a shared trace substrate, so instrumenting the agent is a prerequisite for any quality measurement, and evals can interrogate intermediate steps.

Source video ↗

Prompt changes become cross-cutting risks that can silently break unrelated behaviors, requiring regression coverage rather than point fixes.

Before

Changing a system prompt to fix a localized issue (e.g., tone) is assumed to be a contained edit.

After

Prompt edits are treated as dependency-affecting changes that must pass a suite of evals covering unrelated behaviors.

Consequence

Prompt and agent codebases need a regression eval suite and CI gating, shifting prompt management from craft to engineering discipline.

Source video ↗

Agent failure localization moves from the final output to the span graph, because errors cascade across tool calls and reasoning steps.

Before

Debugging centered on inspecting the agent's final response and guessing where it went wrong.

After

Each intermediate span (retrieval, reasoning, tool invocation, handoff) is inspected to find the true origin of cascading failure.

Consequence

Debugging and eval tooling must be span-aware, and multi-agent handoffs introduce an additional routing/triage failure surface that requires its own evaluation.

Tradeoffs and failure modes

4

Deterministic code evals

Benefit

Deterministic, free, fast, and reproducible like unit tests, and can gate format, structure, constraints, and required fields.

Cost or risk

Brittle—they cannot judge meaning, so they may pass semantically wrong outputs or fail valid variations.

Source video ↗

LLM-as-a-judge evals

Benefit

Handle meaning and semantics (faithfulness, tone) rather than just string matching.

Cost or risk

Cost money, are non-deterministic, and require calibration against human judgment, and therefore can give unstable or biased verdicts.

Source video ↗

Path-sensitive vs outcome-sensitive grading

Benefit

Outcome grading aligns evals with user value and permits diverse valid strategies.

Cost or risk

Ignoring the path can let inefficient, expensive, or unsafe trajectories pass as long as the final answer is right.

Source video ↗

Multi-agent handoffs

Benefit

Specialist routing and triage enable decomposition of complex tasks across agents.

Cost or risk

Handoffs add another layer where triage and specialist routing can fail, compounding cascading errors.
