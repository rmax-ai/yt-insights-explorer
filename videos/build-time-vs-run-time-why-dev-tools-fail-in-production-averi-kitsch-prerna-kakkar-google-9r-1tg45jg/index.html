Overview

  • Speaker: Averi Kitsch & Prerna Kakkar
  • Channel: AI Engineer
  • Main topic: Build-Time vs. Run-Time Architecture in AI Agents and Tooling for Databases
  • Purpose: To educate AI engineers on why development tools fail in production and how to build secure, robust database tooling for agents using proper architecture, parameter controls, and guardrails. Averi Kitsch and Prerna Kakkar from Google Cloud Database discuss the differences between build-time developer assistant tools and run-time end-user application agents. They cover MCP Toolbox for Databases, common tool patterns for database access (control plane tools, Natural Language to SQL, and structured SQL tools), and security guardrails such as addressing the 'Confused Deputy' attack pattern and implementing Model-Controlled vs Application-Controlled parameter security.

Common Tool Patterns for Databases

  • Explanation: Exploration of three tool patterns used for databases: Control Plane Tools (infrastructure and admin), Natural Language to SQL (NL2SQL), and Structured SQL Tools.
  • Key claims:
    • Control plane tools automate database instance creation and lifecycle management but require human-in-the-loop oversight.
    • NL2SQL tools generate raw SQL dynamically via LLMs for analytical agents and flexible exploration.
    • Structured SQL tools pre-approve queries ahead of time for production-grade applications, preventing SQL injection.
  • Examples:
    • Creating database instances with execute_sql or create_instance.
    • Querying 'Find all customers in California who bought a winter coat in July and returned it within 14 days'.
  • Terminology:
    • Control Plane Tools
    • Natural Language to SQL (NL2SQL)
    • Structured SQL Tools
    • SQL Injection
  • Why it matters: Understanding different tool patterns helps architects choose the right balance of flexibility and safety.

Build-Time vs. Run-Time Agents

  • Explanation: Distinction between developer assistant agents used at build-time (in IDEs/CLIs with generic tools) and end-user application agents running in production workflows.
  • Key claims:
    • Build-time tools are atomic and flexible, but rely on human-in-the-loop and cannot be safely exposed to end users in production.
    • Run-time end-user application agents require composite, constrained, deterministic tools with zero-trust boundaries and low latency.
  • Examples:
    • Developer assistants using generic database execution tools vs. end-user chatbots executing specific cancel_order workflows.
  • Terminology:
    • Build-Time Agents
    • Run-Time Agents

    • Zero-Trust Boundaries
  • Why it matters: Developer tools that work in local environments fail in production because they lack production-grade security and constraints.

Security & Guardrails: The Confused Deputy & Application Control

  • Explanation: Discussion of database security vulnerabilities in agents, focusing on the 'Confused Deputy' attack and Simon Willison's 'Lethal Trifecta'.
  • Key claims:

    • The Lethal Trifecta occurs when an agent has access to private data, untrusted content, and the ability to expose that data externally.
    • Application-controlled parameters enforce strict boundaries compared to model-controlled parameters where agents handle raw credentials.
  • Examples:
    • A malicious insider injecting a prompt inside a ticket to query and leak all employee salaries.
    • Transitioning from raw access to configurable sources, custom semantic tools, and binding authenticated parameters.

Key Points

Build-Time vs. Run-Time Failure

  • Explanation: Developer tools fail in production because they assume a human-in-the-loop and broad access permissions that are unsafe for end-user runtime agents.
  • Evidence: Demonstrations showing agents executing destructive DELETE statements when prompted by untrusted user text without guardrails.
  • Practical implication: Engineers must transition from generic developer tools to constrained, production-ready runtime tools.

The Lethal Trifecta in Agents

  • Explanation: When an agent combines access to private data, untrusted inputs, and external communication channels, data breaches occur via prompt injection.
  • Evidence: Simon Willison's concept of the Confused Deputy attack where ticket-processing agents are tricked into querying salary tables.
  • Practical implication: Isolate identity and abstract connection strings using Source primitives and bound/authenticated parameters.

Best Practices for Tool Quality

  • Explanation: High-quality agent tools must focus on outcomes rather than atomic REST APIs, provide actionable errors for retries, and use simple flattened inputs.
  • Evidence: Separating read and write tools, returning descriptive retryable errors instead of generic 404s, and avoiding complex nested maps.
  • Practical implication: Improves agent reliability and reduces round trips and hallucinations.

Frameworks, Models & Processes

Evolution of a Secure Tool Architecture

  • How it works: Progresses from insecure raw database access to zero-trust architecture by abstracting connection details and binding user identity at the application layer.
  • Components:
    • Raw Access (Insecure)
    • Configurable Sources
    • Custom Semantic Tools
    • Binding & Authenticated Parameters
  • When to use: When building any database-connected AI agent for production deployment.

Examples & Case Studies

An agent tasked with cleaning up a user table takes user input literally and executes a destructive DROP or DELETE query without safeguards.

  • Illustrates: The danger of exposing raw SQL execution tools to agents without guardrails or human confirmation.
  • Lesson: Never give runtime agents raw execute_sql capabilities over sensitive databases without strict pre-defined logic and parameter binding.

Actionable Takeaways

  • Immediate:
    • Separate read and write tools to enable automatic approval for read-only actions.
    • Return actionable error messages so agents can self-correct and retry.
    • Use flat parameter structures instead of complex nested maps.
  • Strategic:
    • Treat LLM agents as untrusted privileged users requiring zero-trust boundaries.
    • Abstract database connection credentials out of agent control using Source primitives.
    • Enforce authentication at the application level and pass claims (user ID, email) via bounded or AuthN parameters.
  • Questions to investigate:
    • How can we further reduce latency when implementing multi-layer security guardrails?
    • What are the best automated evaluation frameworks for testing agent tool security?

Compressed Summary

  • Developer tools built for local build-time assistance fail when deployed to production run-time agents.
  • Prevent the Confused Deputy problem by removing raw database connection strings and credentials from agent control using Source primitives.
  • Enforce zero-trust architecture by using application-controlled bounded parameters and authenticated user claims rather than letting agents generate raw SQL.
  • Keywords: mcp, databases, security, guardrails, agents, sql
  • Core insight: Production AI agents require strict parameter binding, read/write separation, and application-controlled guardrails to prevent data breaches caused by prompt injection and the Confused Deputy vulnerability.

Why

The build-time/run-time argument hinges on structured SQL being production-grade and NL2SQL being exploration-only, but without a coverage number that boundary is a preference rather than an engineering constraint. If coverage is high, the safety pattern generalizes; if it collapses, teams will silently reintroduce raw SQL generation under production load and the architectural claim becomes aspirational.

Composition semantics for bound identity and multi-dataset agents

Research question

When a single runtime agent legitimately spans multiple tenants or datasets, how should application-bound authenticated parameters and configurable sources compose so that per-request identity cannot be widened by adversarial prompts?

Why

Application-controlled parameters remove the credential surface only if the binding is unambiguous. The moment one agent must reach several allowed datasets, the application layer reintroduces a selection problem the model may be able to influence, which is exactly the confused-deputy shape the pattern was meant to eliminate. The composition rules, not the single-tenant case, decide whether this is a real boundary.

The Boundary Is the Architecture: Dev Tooling Is a Different Artifact Class, Not a Deploy Target

Reusing a build-time developer tool in a production end-user path is a category error, not a hardening task: the human-in-the-loop assumption and broad permission scope are load-bearing parts of the tool's design, so the failure is structural and cannot be patched with prompt rules. Teams should maintain two tool classes against the same backend rather than one tool with a safety toggle.

Angle

Treat presence or absence of human oversight as the variable that classifies a component, then show why every attempt to 'productionize' a dev tool by adding guardrails is really an undeclared rewrite.

Source video ↗

Capability Removal Beats Behavioral Instruction: Why Prompt-Level Hardening Loses to Structural Constraints

Agent security arguments that rely on instructing the model to behave are unfalsifiable and fail under prompt injection, whereas pre-approved statements, application-bound identity, and outcome-shaped narrowed tool surfaces are verifiable by construction. The article argues for migrating safety properties out of the prompt and into the reachable action set, and shows that the cost is bounded expressiveness rather than lost capability.

Angle

Frame the debate as design-time action-space constraint versus post-hoc output filtering, and score each approach by what it can prove rather than what it can express.

Source video ↗

Stop Passing Identity Through the Model: The Confused Deputy Is an Interface Bug

Any tool argument that names a user, tenant, or connection is an attack primitive regardless of how well the prompt is written. The fix is to bind identity and data source in the harness and expose only business-level arguments to the model, which makes cross-tenant redirection unrepresentable rather than merely unlikely — and this is a schema decision, not a detection problem.

Angle

Walk from a hijacked-model scenario to the tool schema and show which parameters were model-controlled, then present the migration ladder from raw access to bound authenticated parameters as the concrete remedy.

Source video ↗

Tool Schemas Are Reliability Infrastructure: Outcomes, Retryable Errors, and Flattened Inputs

Tool interface design is a control loop on agent reliability and cost, not cosmetic API tidiness: atomic REST wrappers inflate round trips, generic 404s destroy the agent's recovery path, and nested maps raise argument-level hallucination. Separating read and write tools and shaping schemas around business outcomes should be treated as testable engineering with measurable success and round-trip effects.

Angle

Argue that the cheapest reliability win available to most agent teams is a schema rewrite, and that the absence of benchmarks is why teams keep tuning prompts instead.

Harness-Bound Identity Proxy for Agent Database Tools

gatehouse

If user identity and data source are resolved and bound at the harness layer before the model sees a tool call, then adversarially prompted agents will produce zero successful cross-tenant or cross-dataset redirections, even when the prompt fully controls every remaining business argument.

Proof of concept

Intercept MCP tool invocations in a thin proxy that strips model-supplied identity/source arguments, injects the authenticated principal and an allowlisted dataset, and exposes only business parameters. Run a red-team suite that attempts confused-deputy redirection, credential substitution, and dataset hopping across at least two models.

Measurement

Cross-tenant leakage rate (target zero) and business-task success rate versus a baseline where identity and source remain model-controlled parameters; also record how many legitimate multi-dataset requests are broken by the binding rule.

Paired-Schema Agent Reliability Benchmark

beyond-evals

Outcome-shaped composite tools with actionable retryable errors and flattened inputs will raise task success and cut round trips by a measurable margin over atomic REST-wrapped equivalents, independently of model choice.

Proof of concept

Build two tool surfaces over the same database backend — one atomic with generic 404 errors and nested parameter maps, one outcome-shaped with flattened inputs, separated read/write tools, and descriptive retryable errors. Run an identical task suite against both across multiple models and log the full call trace.

Task success rate, mean round trips per completed task, retry-after-error success rate, and argument-validation failure rate, reported per model to separate schema effect from model effect.

Pre-Approved Statement Coverage Analyzer

new

A curated library of pre-approved SQL statements can satisfy a majority of production end-user query traffic, and the residual uncovered requests cluster into a small, enumerable set of analytic patterns rather than a long tail.

Proof of concept

Ingest a real or synthetic end-user query workload, map each request against a pre-approved statement library, classify the failures, and route only unmapped requests to an NL2SQL exploration path. Report coverage as the library grows.

Measurement

Coverage percentage versus library size, residual query diversity (distinct patterns per uncovered request), and SQL-injection surface area measured as the count of requests reaching dynamic generation.

movement-lab

An automated conformance scorer can place any existing agent-database integration at a specific rung of the raw-access-to-bound-parameters ladder and predict its exploitability, letting teams improve trust incrementally instead of rewriting.

Architectural implications

3

Identity and data-source selection currently sit inside the model's tool arguments in typical developer-oriented tooling.

Before

The agent supplies user identifiers and connection details as model-controlled parameters and can call a raw execute_sql tool.

After

The application binds authenticated identity and a configured source, exposing only business-level, bounded parameters to the model.

Consequence

Prompt injection can no longer redirect queries to another tenant's data, and the tool surface becomes auditable per caller.

Source video ↗

Database statements are currently generated freely by the LLM for flexibility.

Before

NL2SQL generates arbitrary SQL at run time for any question.

After

Production paths route through pre-approved structured statements; NL2SQL is reserved for analytical or exploratory agents.

Consequence

The reachable query set becomes finite and reviewable, trading expressive flexibility for a much smaller injection and blast-radius surface.

Source video ↗

Control-plane lifecycle operations are being tool-ified for agents.

Before

Infrastructure changes are made by humans through consoles or scripts.

After

Agents propose instance creation/lifecycle actions via control-plane tools with human-in-the-loop oversight.

Consequence

Automation gains speed but retains a mandatory approval gate, meaning control-plane tooling cannot be an unattended run-time path.

Tradeoffs and failure modes

4

NL2SQL flexibility vs. injection safety

Benefit

Dynamic SQL generation supports flexible exploration and analytical questions that cannot be enumerated in advance.

Cost or risk

Generated raw SQL reintroduces SQL injection and unbounded query scope, so it is unsuitable as a production end-user path.

Source video ↗

Model-controlled vs. application-controlled parameters

Benefit

Model-controlled parameters give the agent maximum latitude, including handling credentials and identifiers directly.

Cost or risk

The agent then owns the identity and connection decision, enabling confused-deputy exploitation where injected content redirects privileged queries.

Source video ↗

Control-plane automation vs. oversight

Benefit

Control-plane tools automate database instance creation and lifecycle management.

Cost or risk

They require human-in-the-loop oversight, so they cannot be exposed as unattended run-time capabilities for end users.

Raw execution tools exposed to runtime agents

Benefit

A generic execute_sql tool is maximally capable and simple to implement.

Cost or risk

An agent prompted by untrusted user text can execute destructive DELETE/DROP statements with no safeguard.
