Overview

  • Speaker: SallyAnn DeLucia
  • Channel: AI Engineer
  • Main topic: How to write, build, and run AI evaluations (evals) for LLMs and AI agents
  • Purpose: To provide engineers and product builders with a practical guide and recipe for defining, writing, and executing AI evaluations, moving away from subjective vibe checks. SallyAnn DeLucia, Head of Product at Arize AI, presents a workshop on how to write effective AI evaluations (evals) for LLMs and agents. She contrasts 'vibe checks' with systematic evaluation, explains why traditional software unit testing falls short for AI agents, outlines types of evals (such as LLM-as-a-judge, code/logic, annotations, user feedback), provides a step-by-step recipe for writing concrete eval criteria, and walks through a live hands-on lab using Arize AX.

Key Points

Vibe checks do not scale

  • Explanation: Relying on subjective feel when changing prompts leads to undetected regressions and broken use cases in production.
  • Evidence: Week-later failures after prompt tweaks with no way to prove why.
  • Practical implication: Teams must adopt systematic evaluations and quality gates in CI before shipping AI agents.

Software tests differ fundamentally from AI evals

  • Explanation: Traditional unit tests check single inputs against single hardcoded outputs with visible code logic, whereas LLMs have multiple valid outputs and opaque execution traces.
  • Evidence: Comparison between assert statements and multi-criteria travel itinerary evaluations.
  • Practical implication: AI engineering requires tracing execution paths and utilizing LLM-as-a-judge for probabilistic outputs.

Judge one quality per eval

  • Explanation: LLM judges perform poorly when asked to evaluate multiple complex dimensions simultaneously; focus each evaluator on a single concrete quality.
  • Evidence: Research on LLM-as-a-judge performance when handling single vs. multi-criteria rubrics.
  • Practical implication: Start with one narrow eval (e.g., instruction-following or groundedness) and add more over time.

  • Immediate:
    • Stop relying solely on vibe checks when updating prompts.
    • Write concrete, specific success and failure criteria instead of vague labels like 'helpful'.
    • Isolate one quality per LLM judge eval.
  • Strategic:
    • Integrate evals into CI/CD pipelines as automated quality gates.
    • Involve cross-functional stakeholders (product, support, domain experts) in defining agent success.
    • Build an iterative eval loop that scales from development datasets to continuous production monitoring.

Core insights

7
[A]Architecturemedium noveltymoderate evidence

Evaluation of agents is ordered after observability: you must first capture and read multi-step traces (agent trees, tool calls, retriever spans) before you can author a meaningful evaluator. Traces are the evidence substrate from which eval criteria are derived, not a parallel concern.

Why it matters

It forces a dependency ordering in the platform stack: instrumentation/tracing → trace inspection → criteria authoring → judge execution → production monitoring. Teams that build judges before inspecting real traces will write rubrics for imagined failure modes.

Generalization

For any non-deterministic multi-step system, the debugging substrate (traces/spans) must exist and be readable before automated grading can be specified; observability is a precondition for evaluation, not a sibling capability.

Source video ↗
[!]Failure Modemedium noveltymoderate evidence

Error cascades in agent traces mean a single root-level output grade is under-diagnostic: failures originate in intermediate LLM calls, tool calls, or retriever steps and propagate. Evaluation therefore has to be able to attach to spans/sub-steps rather than only final responses.

Why it matters

A passing root-output eval can mask a broken retriever or a wrong tool call that happened to be compensated downstream; a failing root eval gives no localization. Span-level grading is what turns a score into an actionable fix.

Generalization

In composed pipelines, evaluate at the granularity where the fault can be repaired; terminal-output metrics are observability of symptoms, not of causes.

Source video ↗
[M]Mechanismmedium noveltymoderate evidence

Judge design should be atomic: one quality dimension per LLM-as-a-judge evaluator, with each criterion expressed as concrete pass/fail bullets. Vague descriptors are explicitly treated as a failure mode of the rubric itself.

Why it matters

Decomposing into single-dimension judges makes the judge prompt's decision surface narrow and auditable, and lets each dimension be tracked, regressed, and fixed independently — a modularity argument for the eval suite itself.

Generalization

Apply single-responsibility decomposition to graders as you would to functions: one judge, one decision boundary, one pass-rate metric.

Source video ↗
[M]Mechanismmedium noveltymoderate evidence

Criteria are operationalized by translating them into an eval prompt plus explicit variable mapping from dataset columns to the judge's inputs/outputs — i.e., the rubric is compiled into a prompt template plus a typed binding to the trace/dataset schema.

Why it matters

Variable mapping is the interface contract between the eval and the logged data; getting it wrong silently grades the wrong field. It also makes the evaluator portable from playground to dataset runs to production traffic.

Generalization

Treat evaluators as parameterized programs over a schema (prompt template + input bindings), not as prose rubrics; the binding layer is where most silent eval bugs live.

Source video ↗
[~]Tradeofflow noveltymoderate evidence

Eval methods form a cost/capability portfolio selected by stage and question type: decision models for cheap fast binary checks, deterministic code/logic checks for structural properties (JSON validity, regex), text-similarity metrics like Rouge/BLEU for matching, LLM-as-a-judge for semantic qualities, human annotation and user feedback for judgment calibration — with online evals continuing in production.

Why it matters

Choosing the cheapest evaluator that can answer the question avoids paying LLM-judge latency and cost on things a regex or classifier can settle, while reserving semantic judges for what only they can grade.

Generalization

Build a tiered grading stack (deterministic → small model → large model → human) and route each check to the lowest tier that is sound for it.

Source video ↗
[O]Mental Modelmedium noveltymoderate evidence

Metrics and evals answer different questions: metrics detect that something broke, evals characterize what the failure mode is. And evaluation is a cross-functional loop — annotation by non-engineers is part of the signal, not a QA afterthought.

Why it matters

It separates detection (alerting on pass-rate drop, latency, cost) from diagnosis (reading graded failure reasons), which implies two distinct instrumentation outputs and an organizational process rather than a single dashboard.

Generalization

In production ML systems, split the telemetry into anomaly detection and failure-mode characterization, and treat domain-expert labeling as a first-class signal source feeding the loop.

Source video ↗
[M]Mechanismlow noveltymoderate evidence

The argument for evals is regression economics: without an objective criterion set you cannot detect prompt regressions, compare prompts or models, or enforce CI quality gates — the failure surfaces as a use case breaking days after a prompt change with no causal trail.

Why it matters

It recasts evals as the missing change-management primitive for prompts/models, analogous to tests in software delivery, and motivates putting pass-rate thresholds in the deploy pipeline.

Generalization

Any artifact changed by natural-language edits (prompts, rubrics, system messages) needs a versioned golden set plus threshold gates, or change velocity outruns defect attribution.

Judge calibration and human-agreement gates

Research question

What calibration procedure and agreement threshold are required before an LLM-as-a-judge evaluator can be trusted as a deployment gate?

Why

An uncalibrated judge creates false confidence: a pass-rate gate is only useful if judge labels track expert judgment and remain stable after judge-prompt edits.

Source video ↗

Span-level evaluation granularity and cost

Research question

Which spans in a deep agent trace must be graded to localize failures without evaluating every span?

Why

Root-only grading under-attributes cascaded errors; full per-span grading scales with trace depth. A sampling or selection policy determines whether span-level evals are actionable and affordable.

Source video ↗

Tiered grader routing

Research question

Does routing each eval check to the lowest-cost sound grader — code/regex, small classifier, LLM judge, human — reduce cost per detected defect without reducing detection?

Why

Single-dimension judges multiply LLM calls as quality dimensions grow; a routing policy is needed to keep eval portfolios economical.

Evaluator-to-schema binding and versioning

Research question

How should evaluator definitions bind to dataset and trace columns and be versioned so schema changes surface as explicit breakages rather than silent misgrades?

Why

The variable mapping is the interface contract; a wrong binding grades the wrong field and invalidates pass rates and gates.

Project ideas

4

Judge Calibration Harness

beyond-evals

A judge calibrated against expert labels per dimension will reach at least 0.8 Cohen’s kappa and keep at least 0.75 after judge-prompt edits; an uncalibrated judge will not.

Proof of concept

Build three single-dimension judges for an agent scenario, collect expert annotations, measure agreement before and after calibration, then change each judge prompt and re-measure.

Measurement

Cohen’s kappa vs expert labels, false-pass and false-fail rates, agreement delta after prompt edits.

Source video ↗

Span-Grading Selector

movement-lab

A sampled span-grading policy can catch at least 80% of trace failures while using less than 30% of full per-span grading cost, whereas root-only grading localizes less than 50% of failures.

Proof of concept

Replay a trace set and compare root-only, sampled intermediate-span, and full per-span grading against known or injected failures.

Measurement

Failure detection rate, localization accuracy, eval cost per trace, cost per detected defect.

Source video ↗

Tiered Grader Router

gatehouse

Routing structural checks to code and binary checks to a small classifier before LLM judging cuts cost per detected defect by at least 50% with no more than 5% detection loss versus an LLM judge for every dimension.

Proof of concept

Implement a router over regex and JSON checks, a small classifier, and an LLM judge; run on a fixed eval dataset and compare against flat LLM-judge-per-dimension grading.

Measurement

Cost per detected defect, detection recall, latency, judge-call volume.

Source video ↗

Evaluator Binding Linter

new

Schema-aware binding checks catch at least 90% of silent evaluator misbindings before execution, while manual variable mapping catches fewer.

Proof of concept

Define evaluator templates with typed bindings to dataset and trace columns; mutate schemas and column mappings to test detection.

Measurement

Misbinding detection rate, false-positive rate, time-to-diagnose.

4

Trace capture must precede and constrain eval authoring, since criteria are derived from observed spans.

Before

Evaluators written speculatively against assumed outputs, with prompt strings as the only artifact.

After

An instrumentation layer emits agent/tool/retriever spans; evaluators are authored against concrete trace fields and dataset columns.

Consequence

Eval infrastructure becomes downstream of the observability schema; changing span attributes is a breaking change for evaluators.

Evaluators become parameterized artifacts (prompt template + variable bindings) that move from playground to dataset backtests to online production runs.

Before

Ad-hoc grading logic embedded per-experiment, unable to run on live traffic.

After

Consequence

Need versioning and schema-stability guarantees for evaluator definitions, similar to model or migration versioning.

Before

Tradeoffs and failure modes

5

LLM-as-a-judge cost and latency vs deterministic checks

Benefit

Semantic qualities like QA, summarization, and relevance can be graded automatically with a label plus an explanation.

Cost or risk

Requires a second model call per graded item and introduces judge nondeterminism; cheaper decision models and code checks must cover the binary/structural cases.

Source video ↗

Vague rubric criteria

Benefit

Fast to write and reads intuitively ('helpful', 'accurate').

Cost or risk

Unfalsifiable rubrics produce judge outputs that cannot be trusted, making the eval itself a source of false confidence rather than a signal.

Source video ↗

Vibe checks as the incumbent testing method

Benefit

Zero setup cost; humans can catch obvious breakage immediately.

Cost or risk

No regression detection, no objective prompt/model comparison, no CI gate — breakage appears later without causal attribution.

Source video ↗

Error cascade in multi-step agent traces

Benefit

Decomposing agent work into sub-agents and tools increases capability and modularity.

Cost or risk

An error in an upstream tool call or retriever contaminates downstream spans, so root-level evaluation both under-attributes and can mask compensating successes.

Source video ↗

Breadth-first eval authoring

Benefit

Coverage across many quality dimensions early.

Cost or risk

Attempting many judges at once delays a working evaluator; the recommended path is a single eval iterated over time.

Source video ↗
