[P]Practicemedium noveltymoderate evidence

A concrete, repeatable threshold for when to hand a workflow to an agent: perform the task manually about five times first, because that repetition yields enough pattern recognition to specify the automation. This turns 'should I automate this?' from a judgment call into a counted trigger.

Why it matters

It gives engineering teams a cheap, falsifiable decision rule for automation investment, reducing both premature automation (automating a misunderstood process) and permanent manual toil. It also implies the first five executions are a data-collection phase whose output is the spec/prompt/harness for the agent.

Generalization

Automation readiness can be gated by a counted number of observed executions of a task, not by tool availability or enthusiasm; the manual run is the requirements-gathering artifact.

[A]Architecturemedium noveltymoderate evidence

Proactive agents are described as running against cloud apps independently of the user's device — the agent continues working when the laptop is closed. This moves the agent runtime out of the client session and into a persistent, always-on execution context attached to external service accounts.

Why it matters

It changes the boundary of the agent: triggers, credentials, durable state, and completion must live server-side rather than in a chat session. That has direct consequences for auth scope, auditability, idempotency, and how results are surfaced to a user who is not watching.

Generalization

Any agent expected to act proactively requires a persistent runtime with its own identity and credentials, decoupled from the interactive client that seeded it.

Why it matters

This reframes the bottleneck in agentic development from implementation capability to problem specification and evaluation. It predicts that the highest-leverage engineering work shifts toward encoding domain judgment into review criteria, tests, and constraints rather than writing the execution path.

Generalization

As execution cost falls, the binding constraint moves to whoever can specify correctness and judge output in a domain — the evaluation function becomes the product.

Project ideas

Five-Time Automation Threshold Experiment

beyond-evals

Automating a task after five manual executions yields a higher agent success rate and lower rework than automating after three or ten executions for tasks of moderate complexity.

Proof of concept

Select a common knowledge-work task (e.g., drafting meeting follow-ups). Manually execute it 10 times, capturing traces. Build agents that automate the task after N=3, 5, and 10 executions. Evaluate each agent on 20 new instances, measuring success and rework.

Measurement

Agent success rate (human-judged), average number of corrections per output, and time-to-automation.

Source video ↗

Persistent Agent Runtime with Scoped Credentials

gatehouse

A cloud-side agent with scoped OAuth credentials, durable task state, and an audit log can reliably perform background research and calendar management without user intervention, with no unintended actions.

Proof of concept

Build a prototype agent that connects to Google Calendar and Gmail with read-only and limited write scopes. It runs on a schedule to prepare daily briefings and draft follow-ups. Log all actions. Simulate credential expiry and duplicate triggers to test durability.

Measurement

Task completion rate, number of unintended side effects, successful recovery from credential expiry, and audit log completeness.

Source video ↗

Domain Expert Review Interface for Agent-Generated Artifacts

new

A structured review interface with diff annotations and domain-specific checklists improves the acceptance rate of agent-generated CAD floor plans by contractors compared to raw output.

Proof of concept

Generate simple residential floor plans using an AI model. Have contractors review them either as raw images or through a purpose-built review tool that highlights changes and prompts for corrections. Measure acceptance and corrections.

Measurement

Acceptance rate (contractor willingness to bid/use), number of corrections requested, and time spent reviewing.

Modality-Independent Tool Layer for Personal Agents

movement-lab

Swapping a voice interface for a chat interface over the same tool layer does not significantly change task success or user effort for email and scheduling tasks.

Proof of concept

Implement a tool layer for email and calendar. Expose both voice and chat interfaces. Have users complete a set of tasks with each modality. Measure task success and time on task.

Measurement

Tradeoffs and failure modes

3

Automation threshold (five-time rule)

Benefit

Counting manual repetitions avoids both premature automation and permanent toil, and yields pattern recognition needed to specify the automation.

Cost or risk

Five is an unvalidated heuristic; complex or low-frequency tasks may need far more or far fewer observations, and a task repeated five times may still be poorly understood, producing an agent that automates the wrong process.

Source video ↗

Proactive cloud-resident agents

Benefit

Work happens in the background — research, follow-ups, calendar management — without the user present.

Cost or risk

An always-on agent with cloud-app credentials acts without a human in the loop, raising the surface for unintended side effects, credential exposure, and silent failure that the user only notices later. The summary offers no stated control, approval, or rollback mechanism.

Source video ↗

AI handles execution, humans supply judgment

Benefit

Domain experts can build products without traditional programming skills, and human effort concentrates on high-value direction.

Cost or risk

If human judgment is the remaining bottleneck, throughput becomes limited by human review capacity, and unverified agent output in credentialed domains (e.g., construction plans) may fail downstream professional acceptance.
