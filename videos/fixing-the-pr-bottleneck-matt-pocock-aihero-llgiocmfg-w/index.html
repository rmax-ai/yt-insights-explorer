Summary

Overview

  • Speaker: Matt Pocock
  • Channel: AI Engineer
  • Main topic: Fixing the PR bottleneck in software engineering using automated checks, automated review, and human review with AI agents.
  • Purpose: To educate AI engineers on how to manage the explosion of PRs caused by AI coding agents by implementing structured automated and human review processes. Matt Pocock discusses how AI agents have vastly increased the number of pull requests (PRs) being generated, exacerbating the traditional PR bottleneck. He presents a three-layered framework—Automated Checks, Automated Review, and Human Review—designed to speed up software delivery while maintaining high code quality. By leveraging cheap CPU-based automated checks as lie detectors, refining AI agent prompts via targeted coding standards (CODING_STANDARDS.md) rather than global prompts, and optimizing human review around two-way doors and clear 'why' context (via tools like /pr, /show-me, and /retro), teams can stop the slop and make code review matter.

Topic Map

The PR Bottleneck in the Age of AI

  • Explanation: Organizations have always struggled with unreviewed PRs, a problem that has scaled massively due to AI coding agents imposing new constraints and generating more code.
  • Key claims:
    • AI agents promise to scale developer output, leading to more PRs and work.
    • Without proper gating, this creates a 'software factory' slipstream of low-quality PRs.
  • Examples:
    • Massive backlogs of unreviewed PRs laying around.
  • Terminology:
    • Software factory
    • PR bottleneck
    • Accelerators
    • Brakes
  • Why it matters: Unchecked AI code generation leads to software entropy and overwhelming review burdens.

The Three-Layered Cake of PR Review

  • Explanation: A structured defense against bad code comprising Automated Checks, Automated Review, and Human Review.
  • Key claims:
    • Automated checks are cheap CPU cycles used as lie detectors for code quality.
    • Automated review uses AI agents to check code against coding standards before human review.
    • Human review is the final, most costly step and should be made as fast as possible.
  • Examples:
    • Linting and type checking at layer one; AI diff review at layer two; human sign-off at layer three.
  • Terminology:
    • Automated checks
    • Automated review
    • Human review
  • Why it matters: Layering defense mechanisms prevents bad code from ever reaching human eyes.

Automated Checks and Lie Detectors

  • Explanation: Automated checks (linting, tests, type checking) are cheap, but they can lie when tests are tautological or structure-sensitive.
  • Key claims:
    • Checks cost CPU cycles, not tokens or human effort.
    • Green CI does not mean code is ready to merge because checks can lie.
    • Tautological tests and structure-sensitive tests are common failure modes of AI-generated tests.
  • Examples:
    • Tests that re-assert the implementation (e.g., expecting 280 because the constant is 280).
  • Terminology:
    • Tautological tests
    • Structure-sensitive tests
    • Automated checks
  • Why it matters: Understanding how automated checks fail prevents false confidence in CI pipelines.

Codebase Design and Deep Modules

  • Explanation: Designing codebases with deep modules (complex behavior hidden behind simple interfaces) reduces structure-sensitive tests.
  • Key claims:
    • Deep modules improve codebase design and reduce brittle tests.
    • Using /improve-codebase-architecture restructures codebases into deep modules.
  • Examples:
    • Consolidating hand-rolled validation expressions into a single predicate module.
  • Terminology:
    • Deep modules
    • Locality
    • Leverage
    • Seam
  • Why it matters: Good codebase design makes it harder for AI agents to write bad tests and code.

Automated Review Standards

  • Explanation: How to structure automated review agents so they enforce coding standards effectively without overloading the implementation agent.
  • Key claims:
    • Do not put coding standards in your implementer agent; keep implementation and review separate.
    • Automated review should output commits, not comments.
    • Use /code-review to read CODING_STANDARDS.md and check diffs.
  • Examples:
    • Separating /implement (Make It Work) from /code-review (Make It Good).
  • Terminology:
    • Implementer agent
    • Reviewer agent
    • CODING_STANDARDS.md
    • Commits not comments
  • Why it matters: Separation of concerns prevents AI agents from getting overwhelmed and producing low-quality feedback.

Human Review and PR Optimization

  • Explanation: Optimizing human review by focusing on one-way vs. two-way doors, blast radius, pseudocode, and visual summaries.
  • Key claims:
    • Some reviews are more important than others; distinguish one-way from two-way doors.
    • Use /pr to generate human-friendly PR bodies optimized for review.
    • Use /show-me to provide visual diagrams of changes rather than walls of text.
  • Examples:
    • Mermaid sequence diagrams generated automatically to explain component interactions.
  • Terminology:
    • One-way door
    • Two-way door
    • Blast radius
    • Pseudocode
    • /show-me
    • /retro
  • Why it matters: Making understanding the 'why' as fast as possible reduces the human review bottleneck.

Key Points

Automated checks are cheap but can lie

  • Explanation: While CPU cycles are inexpensive, automated tests generated by AI can be tautological or overly sensitive to internal code structure, creating false confidence.
  • Evidence: AI agents writing tests that simply assert constant values match the implementation.
  • Practical implication: Do not rely solely on green CI; ensure tests actually verify behavior rather than structure.

Separate implementation from review

  • Explanation: Overloading a single AI agent prompt with exploration, coding, debugging, and strict style guidelines degrades its output.
  • Evidence: The /implement command handles making it work (Red/Green), while /code-review handles making it good (Refactor).
  • Practical implication: Use distinct agents with specialized context windows for implementing versus reviewing code.

Automated review should produce commits, not comments

  • Explanation: Having AI reviewers leave lengthy comments burdens human reviewers with parsing feedback and applying fixes.
  • Evidence: Reviewer agents that directly commit fixes turn PRs into polished artifacts.
  • Practical implication: Configure review agents to make direct fixes so humans review finished work.

Optimize human review for 'why', not just 'how'

  • Explanation: Human reviewers need to understand the architectural intent and blast radius quickly without reading verbose text.
  • Evidence: Using /show-me for visual sequence diagrams and /pr for structured PR descriptions.
  • Practical implication: Adopt tools that summarize changes visually and highlight whether a change is a one-way or two-way door.

Frameworks, Models & Processes

The Three-Layered PR Defense

  • How it works: Layers automated checks, automated review, and human review sequentially to catch errors and enforce quality.
  • Components:
    • Automated Checks (Linting, type checking, tests)
    • Automated Review (AI agent checking diffs against standards)
    • Human Review (Targeted human sign-off on high-risk changes)
  • When to use: Whenever deploying AI coding agents that generate high volumes of pull requests.

The Refactor / Red-Green Workflow for AI

  • How it works: Splits the AI coding workflow into distinct phases executed by separate agent commands.
  • Components:
    • /implement (Make It Work / Red-Green)
    • /code-review (Make It Good / Refactor / Coding Standards)
    • /retro (Suggests automated checks and standards updates)
  • When to use: When setting up custom CLI tools or workflows for AI engineer teams.

Examples & Case Studies

An AI agent generated a test for a character limit constant by asserting that the constant equals its own value.

  • Illustrates: Tautological tests (tests that only re-assert implementation).
  • Lesson: Automated checks can lie when tests are poorly structured.

Refactoring three call sites with duplicated visibility expressions into a single predicate module.

  • Illustrates: Deep modules and codebase design (locality and leverage).
  • Lesson: Good architecture makes code easier for both AI agents and humans to maintain.

Actionable Takeaways

  • Immediate:
    • Stop putting coding standards in global prompt files like AGENTS.md; put them in CODING_STANDARDS.md.
    • Ensure automated review agents commit fixes rather than leaving verbose comments.
    • Use /show-me to generate visual diagrams for PR reviews.
  • Strategic:
    • Treat the AI coding process (exploration, implementation, debugging) as equally important as the code itself.
    • Design codebases with deep modules to minimize structure-sensitive tests.
    • Adopt a compounding review loop using /retro to update coding standards based on human review insights.
  • Questions to investigate:
    • How many of our automated tests are tautological or structure-sensitive?
    • Can we decouple our implementation agent from our review agent?
    • How can we integrate visual sequence diagrams into our standard PR template?
