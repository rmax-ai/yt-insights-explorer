Overview

  • Speaker: Katelyn Lesse, Willie Williams, Dan Shipper
  • Channel: Claude
  • Main topic: Building secure and effective AI agents for knowledge work using Claude and Every's AI co-worker platform
  • Purpose: To explore how AI agents can transform knowledge work, the importance of security and isolation, the challenges of team-wide AI adoption, and how platform-level primitives enable better human-AI collaboration. A discussion between Anthropic's Head of Platform Engineering Katelyn Lesse, Every's Head of Platform Willie Williams, and Every's Co-Founder & CEO Dan Shipper on building secure AI agents for knowledge work, utilizing platform capabilities, and bridging the gap between generic AI benchmarks and practical, customized knowledge work workflows.

Key Points

Company-wide AI adoption requires structured agents

  • Explanation: Individual experimentation with open-source LLMs fades when maintenance is high; centralized agents standardize workflows.
  • Evidence: Transition from individual open-claw tool usage to centralized Every Agent company-wide deployment.
  • Practical implication: Companies should build standardized agent wrappers rather than relying on unstructured employee prompt engineering.

Codifying human taste into agent skills

  • Explanation: By turning historical personal work output into agent skills, teams can automate complex qualitative tasks like editing.
  • Evidence: Turning 30,000 historical editorial edits into Google Doc suggestion skills in Every Agent.
  • Practical implication: Capture expert workflows by converting past work samples into evaluation rubrics and agent prompts.

Infrastructure-first agent development

  • Explanation: Using cloud-managed agent primitives accelerates feature delivery and ensures proper security sandboxing.
  • Evidence: Using Cloud Managed Agents for sandboxes, memory, and session control.
  • Practical implication: Leverage existing managed infrastructure to avoid spending engineering bandwidth on custom sandbox orchestration.

Frameworks, Models & Processes

Kate Bench Framework

    • Vibe checks

    • Human acceptance/rejection tracking
  • When to use: When evaluating whether an AI model can replicate qualitative knowledge work tasks like writing and editing.

[M]Mechanismhigh noveltystrong evidence

Historical expert output can be converted directly into agent capability: Every turned 30,000 historical editorial edits into a 'skill' inside their agent so it can make Google Docs suggestions matching editorial taste. The mechanism is treating an archive of prior human work as both the training signal and the acceptance criterion for a skill, rather than writing prompts from scratch.

Why it matters

This is a concrete recipe for automating qualitative knowledge work: mine a person's or team's past work samples, encode them as skills plus evaluation rubrics, and measure model output against the historical pattern. It shifts skill authoring from prompt engineering to corpus-derived behavior.

Generalization

Any domain with a large archive of reviewed professional output (legal redlines, code review comments, design critiques) can be compressed into a domain skill whose quality is judged against the archive itself.

[P]Practicehigh noveltymoderate evidence

Kate Bench is a personalized benchmark built around a single human expert's historical editing patterns and style preferences, combining 'vibe checks' with automated suggestion generation and human acceptance/rejection tracking, rather than a generic capability benchmark.

Why it matters

It implies that for knowledge work the meaningful eval unit is a named individual's taste, not an aggregate benchmark. This suggests building per-expert or per-team eval harnesses with accept/reject telemetry as the primary quality signal.

Generalization

Personal/org-specific eval suites (n=1 or n=org benchmarks) may be more predictive of production value than public leaderboards for subjective tasks.

[A]Architecturemedium noveltymoderate evidence

When an agent acts inside shared surfaces like Slack, the boundary problem is not just sandboxing but identity and session scoping: the agent must act on behalf of a specific user with that user's permissions and keep internal vs external data separated.

Why it matters

It relocates authorization responsibility to the agent runtime layer: session management must carry user identity and permission context so tool calls inherit the right authority, and data classification boundaries must be enforced per interaction.

Generalization

Any agent operating in a multi-tenant chat or collaboration surface needs session-scoped identity propagation, not just process isolation, to avoid confused-deputy and data-leak failures.

ExpertBench Harness

beyond-evals

A per-expert eval harness built from a corpus of historical accepted/rejected edits predicts production accept rate on new editing tasks better than generic capability benchmarks.

Proof of concept

Ingest 30,000 historical Google Docs edits from one expert, split into train/holdout, generate agent suggestions, and track human accept/reject; compare harness score to public benchmark score.

Measurement

Spearman correlation between harness score and production accept rate across 5 experts; false-positive suggestion rate.

SessionIdentity Proxy for Slack Agents

gatehouse

A session-scoped identity propagation layer that binds each agent action to the requesting user's OAuth token and data-classification context prevents confused-deputy and cross-tenant leakage without breaking task success.

Proof of concept

Wrap a Slack agent runtime; for each message, mint a session with user identity, permissions, and internal/external data labels; enforce at every tool call; run red-team scenarios.

Measurement

Red-team success rate (privilege escalation and data leakage) and task completion rate versus an ambient-identity baseline.

Cost or risk
