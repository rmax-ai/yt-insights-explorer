In this candid and technical fireside chat at the AI Engineer World's Fair, Gergely Orosz interviews Simon Eskildsen, founder and CEO of Turbopuffer. They discuss Simon's early programming journey, his eight-year tenure scaling infrastructure at Shopify through massive growth phases, the engineering challenges of managing database state and caching, building Turbopuffer, navigating venture capital, and the realities of running a high-performance vector database company in the AI era.

  • Explanation: Simple architectures that leverage commodity object storage (S3) combined with smart caching often outperform complex distributed database topologies.

A vector database can be built as a thin query/clustering layer over commodity object storage (S3) plus an aggressive reverse-proxy cache (Nginx) in front of it, rather than as a purpose-built distributed storage engine — with claimed ~95% customer cost reduction.

Why it matters

It relocates the hard engineering from storage replication/consensus into cache design and latency hiding, a very different set of failure modes and responsibilities than a classic distributed database.

Generalization

For read-heavy AI workloads, the storage tier can be commoditized and the value-add moved into a caching/coordination tier above it; the same pattern applies to embedding stores, feature stores, and artifact caches for model weights.

Deep dives

5

Cache coherence and invalidation over object storage as the durable source of truth

Research question

When the durable tier is S3 and the serving tier is a reverse-proxy cache, what invalidation protocol bounds staleness, and how is that staleness observed and alerted on under index updates and cold starts?

Why

The claimed 95% cost reduction is purchased with a cache layer whose correctness semantics are unspecified; if staleness is unbounded or unobservable, the architecture trades a known storage cost for an unknown correctness risk, which is the worst kind of trade for retrieval systems where index freshness affects answer quality.

Workload envelope where object-storage-plus-cache loses to a distributed database

Research question

Along which axes — write ratio, working-set-to-cache ratio, and query locality skew — does the S3-plus-cache topology stop outperforming a distributed database, and is the crossover sharp enough to serve as a decision rule?

Why

The simplicity claim is stated as 'often outperform' with no boundary condition, which is exactly the kind of unbounded generalization that leads teams to adopt an architecture outside its valid regime; locating the crossover converts a slogan into an engineering constraint.

Calibration of napkin-math predictions against measured latency and cost

Research question

Do napkin-math estimates for memory bandwidth, S3 round trips, and NVMe/EBS throughput predict measured P50 and P99 latency and per-query cost within an acceptable factor, or do they systematically diverge in one direction?

Why

Napkin math is only useful as a gate if its error is bounded and known; if predictions are consistently optimistic on tail-sensitive axes, teams will approve architectures the hardware cannot actually serve, and the failure will surface during a traffic event rather than at design time.

Tail-latency control when the durable tier is inherently slow

Research question

Which combination of prefetching, speculative fetch, and cache warming reduces cold-cache P99 in an object-store-backed retrieval system most effectively per unit of memory, without simply provisioning the entire working set in RAM?

Why

Cache memory is the obvious lever and the expensive one; if a prefetch or warming strategy can reduce P99 at lower memory cost, it changes the unit economics that made the architecture attractive in the first place, and it addresses the tail that determines perceived quality.

Cache state observability as the concrete face of state management

Research question

What minimum instrumentation — key-space census, hit-rate by shard, eviction and TTL distributions, dependency graph of what populates each key — is needed so that no production cache can become an undocumented 128GB liability?

Why

State management is identified as the recurring core difficulty, and the Redis anecdote is its most concrete manifestation; making cache contents a first-class observable turns failover, scaling, and debugging from archaeology into routine operations.

Project ideas

3

Cachefront Vector Store

gatehouse

An Nginx reverse-proxy cache in front of an S3-resident vector index sustains P99 under 50ms at at least 10x lower cost per million queries than a provisioned vector database for read-heavy workloads with a stable working set, and degrades predictably rather than catastrophically when the index is invalidated.

Proof of concept

Build an S3-backed HNSW/IVF index with an Nginx caching reverse proxy in front, load a fixed query set with a skewed distribution, then measure latency, hit ratio, and cost while injecting index updates to force cache invalidation.

Measurement

P50/P99 latency, cache hit ratio, dollars per 1M queries, and staleness window after an index update, compared against an in-memory vector database baseline.

Source video ↗

Napkin Divergence Harness

movement-lab

Napkin-math estimates for memory bandwidth, S3 round-trip latency, and NVMe/EBS throughput diverge from measured values by more than 2x on at least one axis for a realistic vector workload, making them usable only as order-of-magnitude filters rather than as precise design gates.

Proof of concept

Record predicted values from a written napkin-math checklist before building, then instrument the built system to capture observed memory-bandwidth utilization, object-store round trips, and storage throughput, and diff the two per axis.

Measurement

Predicted-to-observed ratio per hardware axis, with variance across workload shapes and percentile levels (P50 vs P99).

Crossover Point Sweep

movement-lab

The object-storage-plus-cache topology ceases to outperform a distributed database beyond a definable write-ratio threshold and working-set-to-cache-capacity ratio, and the crossover is sharp enough to be encoded as a deployment decision rule.

Proof of concept

Parameter-sweep a single retrieval workload across write ratio (1 to 100 percent), working-set-to-cache-capacity ratio, and query locality skew, running each configuration against both the S3-plus-cache design and a distributed database baseline.

Measurement

Crossover thresholds for P99 latency and cost parity, and the steepness of degradation on either side of each threshold.

Architectural implications

2

The durability/latency split between object storage and query serving is addressed by inserting a caching tier rather than by changing the storage engine.

Before

Assume a vector database must own its storage layer to meet latency targets on cloud infrastructure.

After

Treat S3 as the durable source of truth and put reverse proxies (Nginx) plus caching in front of it to absorb latency.

Consequence

Cache invalidation, warm-up, and P99 tail behavior become the primary operational risks, and cost scales with object-storage economics rather than provisioned DB capacity.

Source video ↗

Napkin math is used as a pre-design filter on hardware limits.

Before

Default to a distributed architecture when data or query volume is expected to be large.

After

First compute memory bandwidth, S3 round trips, and NVMe/EBS throughput to see whether a simpler design already clears the bar.

Consequence

Architecture reviews become quantitative and reject complexity that hardware numbers don't justify.

Tradeoffs and failure modes

4

Object storage as the substrate for vector search

Benefit

High durability and dramatically lower cost, with a claimed 95% reduction in customer cost via a caching layer over S3.

Cost or risk

S3 round trips are slow (hundreds of milliseconds), so correctness and latency now depend on a clever caching/reverse-proxy layer that must be right.

Undocumented cached state in production

Benefit

Large in-memory caches (e.g., a 128GB Redis server) can absorb load cheaply.

Cost or risk

When nobody knows what the cache contains, the system carries an unobservable dependency that complicates scaling, failover, and debugging.
