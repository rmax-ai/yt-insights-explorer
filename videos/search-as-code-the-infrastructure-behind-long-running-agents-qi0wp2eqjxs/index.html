Summary

Overview

  • Speaker: Aleksandr Nikolenko
  • Channel: PyData
  • Main topic: Infrastructure and architecture for long-running AI agents using Search-as-Code and durable infrastructure
  • Purpose: To explain how to build reliable, scalable infrastructure (sandboxes, event sourcing, delegation) for long-running AI agents that need to execute complex multi-step workflows over hours rather than milliseconds. Aleksandr Nikolenko, a member of the technical staff at Perplexity AI, discusses the infrastructure and architecture required behind long-running AI agents. He compares agent autonomy levels to self-driving cars (L0 to L5) and argues that code-based execution and a structured harness (SDK, Skills, Sandbox) are vastly superior to traditional tool-calling menus for complex, long-running agent tasks.

Topic Map

Levels of Agent Autonomy

  • Explanation: Drawing an analogy from self-driving cars, the speaker categorizes agent autonomy into levels ranging from manual execution (L0) to full autonomous organization (L5).
  • Key claims:
    • L0 is manual human execution.
    • L1 is text generation (Copilot).
    • L2 is Copilot with accept/decline loops.
    • L3 is delegated agents with goal-based loops.
    • L4 is autonomous operators observing logs and fixing errors.
    • L5 is autonomous organization (acting like a CEO).
  • Examples:
    • Cursor or Copilot for code suggestions.
    • Autonomous debugging and pull request deployment.
  • Terminology:
    • agent autonomy
    • driver assistance
    • copilot
    • delegated agent
    • autonomous operator
    • autonomous organization
  • Why it matters: Understanding current agent autonomy levels helps engineers design the right infrastructure for the level of independence required.

Vocabulary for an Agent: Tools vs. Language

  • Explanation: Comparing the tool-calling approach with the code/language approach, highlighting why giving an LLM a massive menu of tools creates token waste and noise.
  • Key claims:
    • Tool calling is a contract on tokens (JSON schemas).
    • Giving an LLM 20+ tools creates noise and wastes tokens when only 1 tool is needed.
    • Giving an LLM a language (like Python or bash) and an SDK is far more flexible and robust than a large menu of tools.
  • Examples:
    • Vercel, Anthropic, Cloudflare, and Microsoft benchmarks showing token reduction and accuracy improvements with tool search or code execution.
  • Terminology:
    • tool calling
    • JSON contract
    • token cost
    • SDK
    • Skill
    • Sandbox
  • Why it matters: Transitioning from tool menus to code-based interfaces drastically reduces token consumption and improves agent accuracy.

A Home for an Agent: The Sandbox

  • Explanation: Discussing the requirements for an agent's execution environment, including virtual machines, controlled network access, and filesystem persistence.
  • Key claims:
    • Agents need a real working environment like a VM or Docker container.
    • Filesystem acts as the agent's extended context, reducing payload size in the context window.
    • Network access must be strictly controlled with allowlisted domains and proxies for secrets.
  • Examples:
    • Codex CLI, Claude Code, and OpenCode CLI utilizing shell, read, write, and edit primitives.
  • Terminology:
    • sandbox
    • virtual machine
    • filesystem context
    • allowlisted domains
    • proxy secrets
  • Why it matters: Providing a secure, controlled sandbox allows agents to execute shell commands and write files safely without risking infrastructure.

An Agent That Works for Hours: Durable Infrastructure

  • Explanation: Addressing the challenges of long-running agent execution (context growth, durability, and control planes) using event sourcing.
  • Key claims:
    • Context grows every step, making re-sending the full context increasingly expensive.
    • Processes die due to worker evictions, rollouts, or client disconnects.
    • Event sourcing (queue, worker, event store) enables crash recovery, time-travel debugging, audit trails, and deterministic replay.
  • Examples:
    • Replaying an event log from a checkpoint when a worker crashes.
  • Terminology:
    • context growth
    • durability
    • control plane
    • event sourcing
    • event log
    • deterministic replay
    • checkpointing
  • Why it matters: Long-running agents require robust backend infrastructure to survive failures, manage context costs, and maintain auditability.

Key Points

Code is better than a menu of tools

  • Explanation: Giving models code execution primitives (Python/bash) instead of dozens of specific tool APIs reduces token usage and avoids classifier bottlenecks.
  • Evidence: Benchmarks from Vercel, Anthropic, Cloudflare, and Microsoft showing token reduction up to 99.9% and accuracy increases.
  • Practical implication: Build SDKs and skills in Python/bash rather than registering bloated tool definitions for every possible action.

The filesystem is the agent's context

  • Explanation: Instead of storing huge intermediate payloads in the LLM context window, write intermediate results to disk and reference file paths.
  • Evidence: Saves tokens and prevents context pollution with garbage data.
  • Practical implication: Instruct agents via AGENTS.md to write intermediate results to files and re-read on demand.

Event sourcing solves durability

  • Explanation: Treating agent execution steps as an append-only event log allows for resuming, replaying, time-travel debugging, and fault tolerance.
  • Evidence: Standard backend engineering patterns applied to AI agent loops.
  • Practical implication: Implement queue-worker-eventstore architectures for any agent run lasting longer than a few minutes.

Frameworks, Models & Processes

The Agent Harness (SDK, Skill, Sandbox)

  • How it works: Combines a model-execution loop with limited tool primitives in an isolated sandbox environment backed by a template.
  • Components:
    • Model + Loop
    • Limited tools (files, bash, python)
    • Isolated sandbox (file system, execution, outbound network)
    • Sandbox template
  • When to use: When building long-running, autonomous developer or research agents.

Decomposed Agent Architecture (Queue, Worker, Event Store)

  • How it works: Decouples task scheduling and step execution using an append-only event log for durability and replayability.
  • Components:
    • Queue (what to do next)
    • Worker (executes the step)
    • Event Store (append-only events)
  • When to use: For production agent systems that must survive worker crashes, deployments, and network drops.

Core insights

[M]Mechanismmedium noveltymoderate evidence

Replacing a large tool menu with a general code-execution interface (Python/bash plus an SDK) collapses the per-turn token cost of tool schemas and removes the classifier/selection bottleneck, because the model expresses intent in code rather than choosing among 20+ JSON contracts.

Why it matters

Tool definitions are a fixed tax paid on every model call; at 20+ tools the schema payload dominates the prompt and creates selection noise. Moving the interface to a language plus SDK turns an N-tool selection problem into a code-writing problem, which changes both cost structure and accuracy ceiling for long-running agents.

Generalization

Any agent surface where the action space is wide and sparse (few actions used per turn) should be exposed as a programmable API rather than enumerated as discrete tools; the wider and sparser the action space, the larger the win.

[A]Architecturemedium noveltymoderate evidence

The sandbox filesystem is treated as the agent's extended context: intermediate payloads are written to disk and referenced by path instead of being carried in the context window.

Why it matters

It moves state out of the most expensive and least controllable storage (the prompt) into a persistent, addressable store, which simultaneously cuts token spend, avoids polluting context with garbage intermediate data, and gives the run durable state that survives process death.

Generalization

Treat the context window as a register file, not a database: any artifact larger than the reasoning needs should be spilled to an addressable store and re-read on demand. This applies to any long-horizon agent, not just coding agents.

[A]Architecturemedium noveltymoderate evidence

Agent step execution is decomposed into queue / worker / append-only event store, applying classical event sourcing to the agent loop so runs survive worker evictions, rollouts, and client disconnects and can be replayed from a checkpoint.

Why it matters

It relocates durability responsibility from the model loop (which cannot be trusted to survive) to the backend, and unlocks capabilities the in-process loop cannot offer: crash recovery, deterministic replay, time-travel debugging, and audit trails.

Generalization

Any agent run measured in minutes-to-hours should be modeled as a durable workflow whose steps are events, not as a single long-lived process; the longer the run, the more the value shifts from prompt engineering to control-plane engineering.

[A]Architecturemedium noveltymoderate evidence

The harness is defined as a four-part boundary — model+loop, a deliberately small set of primitives (files, bash, python), an isolated sandbox (filesystem, execution, outbound network), and a sandbox template — rather than an unbounded tool registry.

Why it matters

It gives a concrete decomposition for where responsibilities live: capability comes from the sandbox and primitives, not from enumerating integrations. This makes the system reproducible (template) and the capability set stable while the reachable action space stays effectively unbounded via code.

Generalization

Design agent capability as (small primitive set) x (general-purpose runtime) x (reproducible environment template) rather than as a growing integration list; the template becomes the unit of versioning and reproducibility.

[P]Practicemedium noveltyweak evidence

Sandbox egress is a first-class security boundary: network access is limited to allowlisted domains and secrets are injected via proxy rather than placed in the sandbox.

Why it matters

Code-executing agents have arbitrary outbound capability, so the blast radius is determined by network policy and credential handling, not by tool permissions. Proxying secrets keeps credentials out of the filesystem that the agent (and anything it downloads) can read.

Generalization

When the agent can run arbitrary code, permissioning must move from the action layer to the network and credential layer; assume anything inside the sandbox is readable by an adversary-influenced process.

[!]Failure Modemedium noveltymoderate evidence

Monotonically growing context is framed as an economic failure mode of long runs: every step re-sends the accumulated context, so cost grows superlinearly with run length unless state is externalized and checkpointed.

Why it matters

It explains why long-running agents fail economically before they fail technically, and it makes context management a cost-engineering discipline (externalize, checkpoint, re-read) rather than a prompt-tuning one.

Generalization

For any agent with step count N, total token cost scales with the integral of context size; the design goal is to make context size roughly constant in N by spilling state to external stores.

Deep dives

5

Token economics of tool-schema surfaces vs. code interfaces

Research question

Holding model and task fixed, how do per-turn prompt tokens, total episode tokens, and task success scale with enumerated tool count (1, 5, 20, 50) versus an equivalent SDK-plus-code-execution interface — and at what tool count does the code interface's crossover point occur?

Why

The talk asserts a large win from code interfaces but the mechanism is a fixed per-call schema tax plus a selection bottleneck. Without a measured crossover curve, teams cannot decide when migrating from a tool registry to an SDK is worth the sandbox, egress, and error-surface costs it introduces.

Source video ↗

Replay determinism for event-sourced agent runs

Research question

What fraction of agent steps replay identically when model outputs and external call results are memoized as events, and what is the minimum memoization set needed to reach step-level determinism without recording full network payloads?

Why

Crash recovery and time-travel debugging are the payoff of moving the loop into a queue/worker/event store, but sampling and side-effecting external calls break naive replay. If replay diverges quickly, the audit-trail and debugging value is limited to log inspection rather than true re-execution.

Source video ↗

Checkpoint and context-externalization granularity as a cost function of run length

Research question

Given steps N, context size per step, checkpoint interval, and re-read frequency, what checkpoint/spill policy minimizes total cost while keeping failure-recovery loss bounded, and how does the optimum shift between a 10-minute and a 6-hour run?

Why

The claim that context cost grows every step is the economic failure mode that decides whether long runs are feasible at all. Without a parameterized model, 'spill to filesystem' and 'checkpoint often' are heuristics that can add I/O and re-read overhead faster than they save prompt tokens.

Source video ↗

Credential-injecting egress proxy compatibility with unmodified third-party SDKs

Research question

How many real-world vendor SDKs and CLI clients authenticate successfully through a transparent secret-injecting proxy from inside a network-restricted sandbox without sandbox-specific shims, and where do they break?

Why

Pushing secrets out of the sandbox is only useful if general-purpose code still works inside it. Each SDK requiring a shim is a hidden integration tax and a silent runtime capability failure when an allowlisted domain is missing, so the breakage taxonomy determines whether the security boundary is deployable.

Source video ↗

Mapping the L0-L5 autonomy taxonomy onto concrete infrastructure requirements

Research question

Does each autonomy level require a distinct, minimally sufficient infrastructure set (sandbox, egress proxy, event store, observability), and do lower-level systems that skip a level's components exhibit the predicted failure modes under sustained load?

Why

The taxonomy is offered as an analogy, not a specification. If the level-to-component mapping is real, it becomes a scoping tool that prevents both over-building an L2 copilot and under-building an L4 operator that must read logs and repair itself.

Article ideas

3

Your Tool Menu Is a Token Tax: Why Wide, Sparse Action Spaces Should Be Programs, Not Schemas

Enumerating integrations as JSON tools charges a fixed schema tax on every model call and converts a composition problem into a selection problem; when the action space is wide and sparse, exposing an SDK plus a language raises both the cost ceiling and the accuracy ceiling, at the price of moving safety from the tool permission layer to the sandbox and network layer.

Angle

Frame tool calling as a per-turn contract paid in tokens, quantify what that contract buys and costs as N grows, then show that the migration is not a free win — it trades a bounded tool list for arbitrary execution capability that must be constrained elsewhere.

Source video ↗

Long-Running Agents Fail Economically Before They Fail Technically

The binding constraint on multi-hour agent runs is not model capability but the cost curve of monotonically re-sent context; making context size roughly constant in step count by spilling state to an addressable filesystem is the design change that makes long runs viable, and it must be instructed explicitly rather than assumed.

Angle

Treat the context window as a register file rather than a database, derive the superlinear cost of naive accumulation, then present externalize/checkpoint/re-read as cost engineering with its own failure mode (stale or misreferenced files) instead of prompt tuning.

Source video ↗

Move the Loop Out of the Request: Agent Durability Is a Control-Plane Problem

A single long-lived process holding the agent loop is the wrong durability boundary; modelling each step as an event in a queue/worker/append-only store makes runs resumable and auditable, but the reward is bounded by how deterministic replay actually is once model sampling and external side effects are in the log.

Angle

Recount the failure causes (worker evictions, rollouts, client disconnects) that in-process loops cannot survive, describe the control-plane decomposition, then stress-test the deterministic-replay claim rather than accepting it.

Project ideas

4

Schema Tax Meter

beyond-evals

For a fixed task suite, total episode tokens for a code-execution-plus-SDK harness are strictly lower than for an enumerated tool menu once the tool count exceeds a measurable crossover N*, with no loss in task success.

Proof of concept

Build the same five-task suite twice against one model: once with an enumerated tool registry parameterized at 1/5/20/50 tools, once with a small primitive set (shell, read, write, edit) plus an SDK callable from Python; log per-turn prompt tokens, total tokens, success, and failure-recovery attempts.

Measurement

Tokens per successful task, success rate, and retry count as a function of tool count; report the crossover N* and the slope of schema-token growth per added tool.

Source video ↗

Replay Divergence Recorder

new

Recording model completions and external call results as events is sufficient to replay at least 95% of agent steps identically, and the residual divergence localizes to a small identifiable set of step types.

Proof of concept

Instrument a durable agent loop that writes every step (prompt hash, model output, tool/shell invocation, network response) to an append-only log; implement a replay mode that serves recorded outputs from the log and flags any step whose post-execution state differs from the recorded state; run 20 multi-hour-style runs and rerun each log twice.

Measurement

Percentage of steps replaying to identical state, per-step-type divergence rate, and recovery overhead measured as time from last checkpoint to resume.

Source video ↗

Egress Conformance Suite

gatehouse

A transparent credential-injecting proxy with a domain allowlist lets the majority of common third-party SDKs run unmodified inside a sandbox, and the remaining failures cluster into a small number of predictable patterns.

Proof of concept

Stand up a sandbox with no direct egress plus a proxy that injects secrets per allowlisted host; run a battery of real SDK clients (HTTP API clients, package managers, cloud CLIs) unmodified and catalogue each failure as missing allowlist entry, host-header/auth-header rewriting need, certificate trust issue, or non-HTTP transport.

Measurement

Fraction of tested SDKs working unmodified versus requiring a shim, plus the per-failure-category counts and number of allowlist entries needed to reach that fraction.

Source video ↗

Context Spill Cost Model

movement-lab

There exists an optimal checkpoint interval and spill policy for a given run length, and beyond a threshold run length the filesystem-externalized policy beats naive accumulation in total tokens net of re-read calls.

Proof of concept

Instrument a long-horizon task with tunable parameters (checkpoint interval, artifact size threshold for spilling, re-read strategy) and measure actual token spend and success for naive accumulation versus spill-to-file policies across a sweep of run lengths from minutes to hours.

Measurement

Total tokens and cost per completed run versus step count N for each policy; verified break-even step count where spilled state beats in-context accumulation including re-reads.

Architectural implications

4

The action interface moves from an enumerated tool registry to a programmatic SDK executed in a sandbox.

Before

Integrations are registered as individual tools with JSON schemas and dispatched by the model's tool-choice.

After

The model writes Python/bash against an SDK; capability is composed at execution time inside the sandbox.

Consequence

Tool-schema token overhead disappears and the action space becomes composable, but the system now needs code sandboxing, egress control, and error surfaces that were previously handled by tool handlers.

Source video ↗

Agent state migrates from the context window to the filesystem.

Before

Intermediate results are accumulated in the message history and re-sent each turn.

After

Intermediate results are written to files and referenced by path, re-read on demand.

Consequence

Per-step token cost becomes roughly flat in run length; the new cost is I/O and the need for agents to manage their own working set, which must be instructed explicitly (e.g., via AGENTS.md).

Source video ↗

The agent loop is extracted from the request lifecycle into a durable control plane.

Before

A single long-lived process holds the loop; a crash, rollout, or client disconnect destroys the run.

After

Queue schedules steps, workers execute them, an append-only event store records them and enables replay from checkpoint.

Consequence

Runs become resumable and auditable, and time-travel debugging becomes possible, at the cost of operating a stateful backend and defining an event schema that must stay replay-compatible.

Source video ↗

Credential handling is pushed out of the execution environment.

Before

Secrets are available to the process (environment variables or config) that performs the action.

After

A proxy holds secrets; the sandbox only reaches allowlisted domains.

Consequence

Compromise of the sandbox no longer implies credential compromise, but every external dependency must be reached through the proxy and allowlist, adding an integration and configuration surface.

Tradeoffs and failure modes

5

Code execution vs. tool menus

Benefit

Fewer tokens spent on schemas and higher accuracy, since the model writes one script instead of choosing among many contracts.

Cost or risk

The agent gains arbitrary execution capability, so safety depends on sandbox isolation and egress policy rather than on a bounded tool list.

Source video ↗

Filesystem offload of intermediate state

Benefit

Saves tokens and prevents context pollution with garbage intermediate data.

Cost or risk

State becomes external and path-addressed; the agent must write and correctly re-read files, adding steps and a failure mode if files are stale or misreferenced.

Source video ↗

Durable event-sourced execution

Benefit

Crash recovery, deterministic replay, time-travel debugging, and audit trails for runs lasting hours.

Cost or risk

Introduces a stateful queue/worker/event-store control plane that must be operated and whose event semantics must remain replayable across code changes.

Source video ↗

Sandbox network restriction

Benefit

Limits blast radius of arbitrary code execution and keeps secrets out of the agent's reachable filesystem.

Cost or risk

Allowlists and proxies must be maintained per dependency; an unlisted domain becomes a silent capability failure for the agent at runtime.

Source video ↗

Context growth in long runs

Benefit

Keeping full history maximizes recall and avoids information loss across steps.

Cost or risk

Re-sending the accumulated context each step makes cost grow with run length, making long runs economically infeasible before they become technically infeasible.
