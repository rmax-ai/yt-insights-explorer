Why your agent should manage it's context through SQL

Summary

Overview

  • Speaker: Lewis Ellis
  • Channel: The SF Database Meetup
  • Main topic: Using SQL databases as context and memory backends for AI agents
  • Purpose: To convince developers that handing agents SQL and a database is an extremely powerful, effective, and simple way to handle agentic context, memory, and search. Lewis Ellis discusses the unreasonable effectiveness of giving AI agents a SQL tool to query databases for context and memory management, instead of relying on complex MCP servers, vector search, or file systems. He explores how schemas serve as the ultimate prompt engineering and tool design, how to do it safely with read replicas and role-based access, and why brute-forcing via SQL outperforms specialized multi-tool setups.

Topic Map

The Premise: Just Give Agents SQL

  • Explanation: Giving AI agents a single SQL query tool over a database containing all necessary application state, logs, and third-party data.
  • Key claims:
    • Agents do not need 20 different tools like markdown browsers, MCP servers, and grep tools.
    • A single SQL query tool can handle almost everything an agent needs.
    • Sql is universal, functioning like bash and grep.
  • Examples:
    • PostHog agent querying data
    • Conductor and YC DB giving agents SQL access
  • Terminology:
    • SQL tool
    • MCP server
    • Context window
    • PostHog
  • Why it matters: Simplifies agent architecture by replacing multiple custom tools with one universal querying interface.

Safety and Guardrails for Agent SQL

  • Explanation: Addressing the common fear that letting agents run arbitrary SQL is dangerous by implementing robust safety measures.
  • Key claims:
    • You can make agent SQL safe using read-only roles and read replicas.
    • Implement query limits such as row count limits and result set limits.
    • Use local config scoping and rolled-back transactions to restrict what tenants or tables an agent can query.
  • Examples:
    • Pointing Metabase at a read replica with timeouts turned down for data science teams
    • Postgres config scoping tables down to the specific querying tenant
  • Terminology:
    • Read replica
    • Read-only role
    • Audit logs
    • Transaction rollback
    • View scope
  • Why it matters: Mitigates security and performance risks associated with autonomous LLM-generated queries against production systems.

Why SQL Works So Well for Agents

  • Explanation: Explaining why LLMs excel at SQL generation and brute-forcing data retrieval compared to humans.
  • Key claims:
    • Agents know schemas better than any human developer.
    • Agents do not get tired of brute-forcing queries, joining tables, or reading hundreds of rows.
    • Model code files and schema definitions provide all necessary semantic context.
  • Examples:
    • Agents chaining 12 keywords together in a WHERE clause or reading through foreign keys across tables
  • Terminology:
    • Schema design
    • Brute-forcing
    • Semantic intent
  • Why it matters: Shifts the perspective on agent limitations: LLMs possess the grit and capacity to explore relational data in ways humans find tedious.

Tips, Tricks, and Context Assembly

  • Explanation: Practical techniques to optimize SQL usage for LLM agents, reduce token usage, and improve retrieval over time.
  • Key claims:
    • Have SQL tools return CSV instead of JSON to reduce token counts by half.
    • Schema design is tool design, prompt engineering, and context assembly all in one.
    • Define targeted curated views to shortcut complex multi-table joins for agents.
    • Audit log queries, metaprompt where it misses, and add successful queries to system prompts.
  • Examples:
    • Using DuckDB in between to connect agents to any data source
    • Streaming Slack messages into a database so agents never hit API rate limits
  • Terminology:
    • CSV serialization
    • Curated views
    • Metaprompting
    • DuckDB
    • System prompt
  • Why it matters: Provides actionable methods to make database-backed agent architectures efficient, scaleable, and self-improving.

Key Points

One tool beats twenty tools

  • Explanation: Providing agents with a single, universal tool like SQL is vastly superior to equipping them with numerous specialized tools and APIs.
  • Evidence: Similar to how code search shifted from complex vector tools back to grep, SQL acts as a universal code/data interface for agents.
  • Practical implication: Reduce tool bloat in agent frameworks by consolidating data access into a SQL interface.

Agents are exceptional at brute-forcing SQL

  • Explanation: Unlike humans who get frustrated by complex joins or large datasets, LLMs patiently iterate through queries, keywords, and foreign keys.
  • Evidence: Jeff Huber's quote: many gains of AI boil down to AI being better at brute forcing than humans.
  • Practical implication: Design schemas with rich context so agents can leverage their brute-force querying capabilities effectively.

Schema design is prompt engineering

  • Explanation: Investing time in clean database schemas, model files, and views directly improves agent performance without needing complex prompt hacks.
  • Evidence: Feeding database schemas and model files gives agents superior domain understanding.
  • Practical implication: Treat database schema design as a core component of your AI agent prompt engineering strategy.

Frameworks, Models & Processes

Agent SQL Context Pattern

  • How it works: Store all application data, logs, and third-party mirrors in a relational database, give the agent a read-only SQL tool with safety limits, and refine performance iteratively through audit logs and curated views.
  • Components:
    • Read-only database replica
    • SQL execution tool
    • Tenant view scoping
    • CSV result formatting
    • Audit logging and metaprompting loop
  • When to use: When building AI agents that need to search large corpuses of logs, transcripts, business data, or application state.

Examples & Case Studies

Replacing vector search with direct SQL queries over database tables in YC and Conductor applications.

  • Illustrates: Agents frequently reach for vector search when it fails to yield results, but perform much better when forced to write raw SQL queries.
  • Lesson: You probably don't need vector search; structured SQL queries often yield more precise retrieval outcomes for agents.

Streaming all Slack messages into a local database table instead of querying the Slack API.

  • Illustrates: Bypassing third-party API rate limits by mirroring external service data into a database.
  • Lesson: Keep mirrors of third-party APIs in your database so agents can query them locally via SQL without hitting rate limits.

Actionable Takeaways

  • Immediate:
    • Configure your agent SQL tools to return CSV instead of JSON to save token context.
    • Use read replicas and read-only roles to safely expose databases to agents.
    • Feed complete database schemas and model definition files to your agent.
  • Strategic:
    • Consolidate multiple specialized retrieval tools into a single SQL query interface.
    • Treat database schema design as prompt engineering and context assembly.
    • Mirror third-party API data into your database to avoid rate limits and unify agent context.
  • Questions to investigate:
    • How do schema size limits impact agent context windows on large enterprise databases?

Result serialization is a cheap, global lever on context budget that applies to every query an agent issues, with no loss of retrieval logic.

Generalization

Tool output encodings should be chosen to minimize tokens per unit of semantic content, not for machine-parseability, since LLMs read results as text.

Guardrail Red-Team for Autonomous SQL Agents

gatehouse

A minimal database-native guardrail set (read-only role, read replica, row limit, tenant-scoped rollback) blocks unsafe or resource-exhausting agent-generated SQL with less than 5% task-capability loss compared to an unguarded baseline.

Proof of concept

Build an agent SQL harness over a Postgres read replica with configurable guardrails; run a red-team suite of write, cross-tenant, expensive, and prompt-injected queries alongside a task benchmark; toggle individual guardrails to measure coverage and capability impact.

Measurement

Unsafe query block rate, cross-tenant leakage incidents, query runtime and row-count enforcement rate, and task success rate versus unguarded baseline.

Architectural implications

4

Retrieval logic is pushed from an application tool layer into database views and schema.

Before

Engineers build bespoke retrieval tools, MCP servers, and vector indices to serve the agent.

After

Engineers define curated views and rich schemas in the database; the agent queries them directly.

Consequence

Retrieval behavior becomes a data-migration/versioning concern rather than an application-code concern, and knowledge of what to retrieve is expressed declaratively.

Source video ↗

Context assembly moves from prompt-construction code into the database and result formatting.

Before

Application code assembles context by fetching and formatting data before the model call.

After

The agent decides what to fetch and receives CSV rendered directly from query results.

Consequence

Context window composition becomes a runtime, agent-directed process, making token budget a function of query design and serialization format.

Source video ↗

Third-party integrations shift from live API calls at query time to periodic mirrors in the database.

Before

Agent calls external APIs (Slack, etc.) at inference time, subject to rate limits and latency.

After

External services stream into local tables the agent queries with SQL.

Consequence

Rate limits and API availability are decoupled from agent execution, and external data becomes joinable with internal state.

Source video ↗

Safety enforcement moves from agent-harness restrictions to database role and resource primitives.

Before

Guardrails implemented as custom validation/allow-listing inside the agent tool wrapper.

After

Read-only roles, read replicas, and rolled-back, tenant-scoped transactions enforce limits.

Consequence

Safety policy is centralized in the data platform and reused across agents and human users alike.
