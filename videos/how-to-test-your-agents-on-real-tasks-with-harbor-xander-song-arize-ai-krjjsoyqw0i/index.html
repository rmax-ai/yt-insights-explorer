Xander Song from Arize AI introduces Harbor, an open-source framework for evaluating AI agents on real tasks with real data in isolated sandboxed environments. The talk emphasizes shipping based on evidence rather than vibes, breaking down Harbor's architecture (Tasks, Agents, Verifiers, and Rewards) and demonstrating how it integrates with Phoenix for observability and tracking via ATIF and OpenTelemetry.

Key Points

Ship on evidence, not vibes

  • Explanation: Agent development should rely on rigorous evaluation pipelines rather than subjective impressions.
  • Evidence: Harbor provides automated tasks, verifiers, and reward metrics to score agent runs.
  • Practical implication: Teams can make code or prompt changes and instantly measure whether success rates improved or regressed.

Isolated sandboxing prevents cheating

  • Explanation: Verifiers and solutions are mounted after the agent finishes execution inside a fresh Docker container.
  • Evidence: Docker container isolation ensures the agent cannot read solution files or verifiers during execution.
  • Practical implication: Test results remain trustworthy and unbiased.

Verifiers are environment-agnostic scripts

  • Explanation: Verifiers check what is left behind in the environment rather than inspecting agent internals directly.
  • Evidence: A verifier script can run unit tests, check database tables, or verify file modifications.
  • Practical implication: Verifiers decouple agent implementation details from correctness checks, mirroring integration and unit testing.

Core insights

[M]Mechanismmedium noveltystrong evidence

Anti-cheating is enforced by mount timing, not by prompt-level instructions: solutions and verifiers are mounted into the container only after the agent finishes, so the agent cannot read the answer or the grading script during execution.

Why it matters

Reward hacking is typically addressed with prompt admonitions or output filters, which are probabilistic. Moving the grading artifacts out of the agent's addressable environment entirely converts an alignment problem into a container-orchestration problem, which is deterministic and cheap.

Generalization

Any agent evaluated against a known-ground-truth artifact should have that artifact physically absent from the sandbox at execution time and injected afterward; treat harness secrets like production secrets, not like instructions.

[A]Architecturemedium noveltystrong evidence

Verifiers inspect the post-execution state of the environment (tests run, DB tables, file diffs) rather than inspecting the agent's reasoning trace or tool calls, which decouples correctness checking from any particular agent implementation.

Why it matters

Trace-based graders couple the eval to a specific harness, model, and transcript schema; the moment you swap the agent framework the eval breaks. State-based verifiers survive agent rewrites and mirror how integration tests actually establish correctness in normal software.

Generalization

Where a system has observable side effects, define success as a predicate over the resulting world state; reserve trajectory inspection for diagnosis, not for scoring.

[M]Mechanismmedium noveltystrong evidence

Non-determinism is handled structurally by making the trial — one task instance in one brand-new sandbox — the atomic unit of work, so a single task is run many times as independent containerized executions rather than as one repeated call.

Why it matters

Averaging across repeated samples is common advice, but the architectural choice of a fresh environment per sample is what prevents cross-trial contamination (leftover files, warmed caches, mutated DB) from silently inflating or deflating pass rates. It also makes Pass@k and pass^k computable without special-casing.

Generalization

For any stochastic system under test, define the smallest independently-reproducible execution unit and instantiate clean state per unit; make the unit boundary the same as the parallelism boundary.

[A]Architecturemedium noveltymoderate evidence

Because each trial is an isolated container and tasks are independent, the whole evaluation pipeline is horizontally scalable and the sandbox provider becomes a swappable backend (Daytona, Modal, E2B) rather than an architectural commitment.

Why it matters

Eval throughput is usually the binding constraint on iteration speed. If isolation is per-trial, then scaling out is just adding workers to a queue, and you avoid locking your eval suite to one vendor's sandbox API. This is the difference between an eval harness that runs in minutes and one that runs overnight.

Generalization

Design evaluation and test infrastructure with a provider-agnostic sandbox interface, so compute backends are a configuration detail and benchmark suite size is limited only by spend.

Deep dives

5

Verifier false-pass rate under state-based grading

Research question

For a given task, how often does an agent produce environment state that satisfies the verifier while violating the task's intent — and can a per-task false-pass rate be measured and reported as a first-class metric?

Why

Grading on observable side effects buys harness-independence, but the verifier becomes the specification, and any under-specified predicate is a scoring hole. If false-pass rates are unknown, a green eval board is not evidence of anything; teams will ship on a number that is measuring the verifier's blind spots rather than the agent.

Source video ↗

Mount-order isolation as an adversarial attack surface, not a guarantee

Research question

Given a fresh container where solutions and verifiers are mounted only after the agent exits, what residual channels (image layers, cached build artifacts, shared volumes, network endpoints, environment variables, process leftovers) still let an agent discover or reconstruct the oracle?

Why

The architectural claim is deterministic only if the agent-visible environment is genuinely disjoint from the grading artifacts. If the base image, build context, or a networked service leaks the solution, the isolation story is a convention dressed as a guarantee — and every downstream pass rate inherits the leak.

Source video ↗

Trial allocation policy under a fixed eval compute budget

Research question

At equal total spend, does uniform k trials per task or variance-adaptive sequential allocation produce tighter, less biased estimates of suite-level success rate across heterogeneous tasks?

Why

Once trials × tasks is the cost model, sampling policy becomes an experimental design decision with real consequences: uniform k overspends on deterministic tasks and undersamples the flaky ones whose variance actually moves the decision. Without an allocation policy, Pass@k aggregates silently weight tasks by their noise rather than their importance.

Source video ↗

Curated-task to production-distribution transfer

Research question

How strongly does an agent's rank on hand-authored Harbor tasks correlate with its success on the under-specified, ambiguous requests real users submit?

Why

Every eval suite is a proxy, and this one is built from tasks with explicit natural-language instructions and hand-written verifiers. If the correlation is weak, iteration speed on the curated set is optimizing a target that does not predict deployment behavior — which is exactly the vibe-versus-evidence gap the framework claims to close.

Source video ↗

Fidelity of ATIF→OpenInference trajectory mapping

Research question

What agent-specific structure (tool-call argument schemas, sub-agent nesting, retries, context-window evictions) survives a round-trip through ATIF to OpenTelemetry/OpenInference, and is the loss material to real debugging?

Why

If the mapping flattens away the structures engineers actually need when a run fails, then the trace plane is good for dashboards and cost accounting but not for diagnosis — and diagnosis is the main reason to capture trajectories at all.

Article ideas

4

Reward Hacking Is a Mount-Order Problem

Prompt-level defenses against reward hacking are probabilistic and therefore untrustworthy; the only durable fix is to make the grading artifact physically absent from the agent's addressable environment during execution and inject it afterward — treating harness secrets like production secrets rather than like instructions.

Angle

Reframe an alignment/specification-gaming concern as a container-orchestration and secrets-management problem, then derive the concrete engineering consequences: two-phase container lifecycle, separable environment definitions for execution vs. verification, and auditing for residual oracle channels.

Source video ↗

Grade the World, Not the Transcript

Verifiers that parse the agent's message or tool-call sequence couple the eval to one harness and break on the next agent rewrite; verifiers that assert predicates over post-execution environment state inherit the durability of integration tests and let the same suite grade Claude Code, Codex, or a custom agent unchanged.

Angle

Argue from software-testing history: trace-based grading is assertion-on-logs, state-based grading is assertion-on-effects. Then state the price explicitly — destructive-but-successful trajectories score identically to clean ones, so trajectory data must be retained for diagnosis while being kept out of the reward path.

Source video ↗

The Trial, Not the Task, Is the Unit of Eval Work

Averaging over repeated samples is common advice, but the architectural choice that makes it honest is a brand-new isolated environment per sample; without it, leftover files, warm caches, and mutated state contaminate results and silently distort pass rates, and only with it do Pass@k and budget allocation become computable design decisions.

Angle

Take the isolation boundary as the design primitive and show how it forces three downstream decisions to become explicit: cost as trials × tasks, sampling policy as experimental design, and the sandbox provider as a swappable backend.

Source video ↗

Your Agent Trace Schema Is an Architecture Decision You Keep Deferring

Instrumentation choices made per agent project become unfixable once traces accumulate; standardizing the runtime's trajectory schema on an open semantic convention early is what lets evals, debugging, and production monitoring share a single data plane instead of three bespoke log pipelines.

Angle

Make the case for a neutral interchange format as platform-layer infrastructure — and name what to verify before trusting it, namely whether the translation preserves tool-call arguments, sub-agent nesting, and retries with enough fidelity to diagnose a real failure.

Project ideas

4

Verifier False-Pass Harness

beyond-evals

For tasks graded by post-execution state predicates, a non-trivial fraction of passing runs satisfy the verifier without solving the stated task, and this false-pass rate is stable enough per task to be reported as a calibration metric.

Proof of concept

Build a task corpus with verifiers that assert on environment state. For each task, generate candidate solutions that reach the checked conditions via unintended routes (hardcoded outputs, stubbed dependencies, deleted failing tests, restored-but-unmigrated schemas). Run each against the verifier and record whether it is accepted.

Measurement

False-pass rate per task and per suite; correlation between verifier assertion count/breadth and false-pass rate; delta in suite success rate after verifier hardening.

Source video ↗

Oracle Leak Prober

gatehouse

A container-per-trial harness with post-execution mounting still exposes solution or verifier artifacts through at least one residual channel in the base image, build context, or reachable network services for a measurable fraction of tasks.

Proof of concept

Run a filesystem-and-network-enumerating agent inside the execution-phase sandbox of a set of real tasks, with the agent's only goal being to locate answer or grading artifacts. Catalog every artifact whose content or hash-matches the solution or verifier, and trace its provenance back to image layers, volumes, env vars, or endpoints.

Measurement

Count of task environments with at least one exploitable oracle channel; time-to-first-leak per environment; number of channels that survive a hardened image build.

Source video ↗

Adaptive Trial Allocator

beyond-evals

At a fixed total trial budget across a heterogeneous task suite, variance-adaptive sequential allocation yields a tighter confidence interval on suite-level success rate than uniform k trials per task, and changes the ship/no-ship decision on a measurable share of agent revisions.

Proof of concept

Instrument a task runner to record per-task pass/fail across trials. Compare uniform-k against a sequential policy that allocates additional trials to tasks whose estimated pass rate sits near 0.5 or whose variance is highest, at matched total spend, replaying real before/after agent revisions.

Measurement

CI width on suite success rate at equal spend; fraction of agent revisions where the two policies disagree on ship/no-ship; trials saved to reach a target CI width.

Source video ↗

Trajectory Round-Trip Fidelity Bench

new

Mapping agent trajectories through a neutral interchange format into OpenTelemetry/OpenInference loses structural fidelity — specifically tool-call argument schemas, sub-agent nesting, and retry chains — at a rate high enough to block diagnosis of a meaningful share of real failures.

Proof of concept

Collect a diverse set of agent runs, serialize to the interchange format, translate to OpenInference, then round-trip back and diff. In parallel, have engineers diagnose a sample of failures using only the translated traces and record which structures they needed and could not find.

Measurement

Field-level round-trip loss rate by structure type; percentage of diagnosed failures where the needed structure was present post-translation; median time-to-diagnosis with native vs. translated traces.

Architectural implications

4

Grading logic is injected into the environment after the agent's run rather than shipped alongside it.

Before

Verifier scripts and expected outputs live in the same repo/filesystem the agent operates in, or are described in the prompt, and safety depends on the agent not looking.

After

A two-phase container lifecycle: an execution phase with agent-visible state only, then a verification phase that mounts solutions/tests and runs them.

Consequence

The eval harness owns container lifecycle orchestration, and the agent's environment definition must be cleanly separable from the grading environment definition.

Source video ↗

Correctness is defined as a predicate over environment state after execution, not over the agent's message/tool-call transcript.

Before

Graders parse the agent's final answer or tool call sequence, tying the eval to a specific agent framework and output schema.

After

Verifiers are ordinary test scripts (unit tests, DB assertions, file checks) that run inside the sandbox post-hoc.

Consequence

Agent implementations become replaceable behind a stable interface; eval suites survive harness rewrites, and the same verifier can grade Claude Code, Codex, or a custom agent.

Source video ↗

Trials, not tasks, are the unit of scheduling and isolation.

Before

One environment per task, retried or sampled in-place.

After

One fresh container per trial; a task fans out into N independent executions that are aggregated into Pass@k and success rates.

Consequence

Cost scales with trials × tasks, so eval budget becomes an explicit knob, and sampling policy (how many trials per task) becomes an experimental design decision.

Source video ↗

Agent trajectories are emitted in a neutral interchange format that maps to OTel/OpenInference.

Before

Traces are whatever the agent framework happens to log, analyzed with bespoke scripts.

After

A single trace pipeline feeds both eval comparison UIs and production observability.

Consequence

Instrumentation decisions move out of individual agent projects and into the runtime/platform layer.

Tradeoffs and failure modes

3

State-based verification instead of trace inspection

Benefit

Verifiers are environment-agnostic and decoupled from agent implementation details, so evals stay valid across agent rewrites.

Cost or risk

Grading only what is left behind can miss process-level pathologies — an agent that reaches the right end state through destructive or unsafe intermediate actions scores identically to a clean one; trajectory data is retained for debugging rather than scoring, so it does not gate the reward.

Source video ↗

Multiple trials for stochastic behavior

Benefit

Trials handle stochastic LLM and agent behavior and enable Pass@k style aggregate metrics rather than single-sample luck.

Cost or risk

Cost and wall-clock scale linearly with trial count per task, and more trials only tighten the estimate of a rate — they do not fix a mis-specified verifier or a leaky environment.

Source video ↗

Container-per-trial isolation

Benefit

Enables full horizontal scalability and pluggable sandbox providers, plus trustworthy results.

Cost or risk

Container start-up and image footprint dominate eval latency for short agent tasks, and heavy real-data environments may be impractical to spin up thousands of times.
