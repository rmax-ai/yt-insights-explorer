Overview

  • Purpose: To share engineering strategies, architectural patterns, and practical techniques for building fast, intelligent real-time conversational voice agents at scale. Bohan Li from EliseAI discusses the architecture of real-time voice agents that combine low-latency streaming models with frontier-level intelligence. He draws parallels to autonomous vehicle perception, planning, and control systems, breaking down how EliseAI structures transcription layers, language model processing, and text-to-speech pipelines to maintain speed without sacrificing intelligence.

Key Points

Cascaded Architecture for Voice Agents

  • Explanation: Voice agents require a structured pipeline separating perception, planning, and control layers, analogous to robotics.
  • Evidence: Described through transcription, LLM reasoning, and TTS generation steps.
  • Practical implication: Allows modular optimization of speed and accuracy at each pipeline stage.

Streaming Speculative Transcriber

  • Explanation: Combining fast streaming transcription with accurate batch transcription yields both low latency and correct entity recognition.
  • Evidence: Using Flux on top of Scribe V2 with phonetic matching.
  • Practical implication: Prevents transcription errors on names and medical data while maintaining rapid response times.

Background Tool Injection

  • Explanation: Offloading tool calls to background agents prevents blocking the main dialogue loop.
  • Evidence: Background tool calling for database lookups while user is speaking.
  • Practical implication: Reduces round-trip inference overhead in low-parameter language models.

Audio Prefix Caching

  • Explanation: Caching common response prefixes and playing pre-rendered or cached audio segments hides TTS generation latency.
  • Evidence: Cartesia TTS integration caching 'You said your name is' sequences.
  • Practical implication: Delivers human-like conversational responsiveness without awkward pauses.

Core insights

5
[M]Mechanismhigh noveltymoderate evidence

Transcription is treated as a speculative execution problem: a fast streaming transcriber emits early tokens to keep the dialogue loop moving, while a slower, higher-context batch transcriber runs behind it as a corrective layer and can cancel or overwrite the early transcript (with phonetic matching used for entity precision).

Why it matters

It decouples time-to-first-signal from final correctness, letting an agent begin reasoning before the audio is fully understood while still recovering hard entities like names, dates of birth, and insurance details. This is the transcription analogue of speculative decoding and it changes where 'truth' lives in the pipeline.

Generalization

Any streaming perception stage feeding a latency-sensitive agent can be split into a cheap provisional channel and an expensive authoritative channel, provided the downstream consumer supports retraction/revision of already-consumed context.

[A]Architecturehigh noveltymoderate evidence

Tool calls are moved off the critical path: background agents execute tool calls and push results into the main agent's context asynchronously, instead of the primary agent blocking on a tool round trip mid-turn.

Why it matters

In a voice loop, each synchronous tool round trip is a silence the user hears. Making tool results an asynchronous context injection rather than a blocking call changes the main agent's contract from 'call and wait' to 'read what has arrived', which is what makes small/fast models viable on the hot path.

Generalization

Separate the agent that decides what to say from the agent that decides what to know; treat tool execution as a background producer writing into shared context rather than a function call in the reasoning loop.

Source video ↗
[M]Mechanismhigh noveltymoderate evidence

Audio prefix caching matches the model's generated text against previously generated audio so that already-rendered segments can be replayed immediately, hiding TTS generation latency for predictable openings while dynamic entity data is still resolving.

Why it matters

It converts a generation-latency problem into a lookup problem for the most common case, and it explicitly decouples 'start speaking' from 'have all the data'. Perceived latency, not measured latency, becomes the optimization target.

Generalization

In any generative output channel with high-frequency boilerplate (speech, templated responses, UI fragments), cache-and-replay the stable prefix and only generate the variable suffix; schedule the stable prefix to play before the variable suffix is known.

[O]Mental Modelmedium noveltyweak evidence

The architectural decomposition of a voice agent maps onto autonomous-driving perception / planning / control, with each layer independently optimizable for its own speed-accuracy trade-off.

Why it matters

It justifies putting a hard boundary between transcription, reasoning plus tool access, and speech synthesis, so a latency fix in one layer does not force a redesign of the others. It also suggests importing robotics-style budget allocation per stage.

For real-time agentic systems, choose boundaries along sense / decide / act rather than along vendor or model boundaries; latency budgets then attach to stages, not to models.

Article ideas

3

Your Agent's Context Is Now Mutable, and Your Runtime Isn't Ready

Speculative transcription and async tool injection both push provisional information into an agent's working context, so the hard engineering problem in realtime agents is no longer perception quality but reconciliation: versioned context entries, retraction events, and explicit commit points. Teams that adopt the fast-path patterns without retraction semantics will ship agents that confidently state wrong names and dates.

Angle

Take the two latency patterns the talk treats as wins, and show that both smuggle in the same unaddressed requirement — a context store that supports revision — then sketch the primitive set (revision events, staleness timestamps, deferred entity commitment).

Source video ↗

Stop Shrinking the Model, Start Overlapping the Hops

The intelligence-versus-latency trade-off in realtime agents is usually framed as a model-selection problem, but when p95 latency is dominated by the number of sequential round trips rather than per-hop compute, architectural concurrency buys more responsiveness than model choice. Async tool execution, speculative perception, and cached output are three instances of the same move: overlap work instead of compressing it.

Angle

Argue the reframing, then demand the measurement the framing implies — a latency attribution breakdown per hop — and show how teams can instrument it before choosing a model tier.

Source video ↗

Perceived Latency Is the Only Latency: Cache the Boilerplate, Generate the Variable

Audio prefix caching works because it decouples 'start speaking' from 'have all the data', turning a generation problem into a lookup for the most common case. Any high-frequency generative output channel — speech, templated responses, UI fragments — should be split into a stable replayed prefix and a variable generated suffix, with the prefix scheduled to play before the suffix is known. The cost is that phrasing becomes partly constrained by what is cacheable.

Angle

Generalize the audio pattern into a design rule for generative output, and be explicit about the coherence risk when entity data contradicts the cached premise mid-utterance.

Retractable Context Store

gatehouse

Gating commitment on phonetically ambiguous entities until the corrective transcriber confirms reduces entity-level capture errors by at least 50% while adding less than 150ms to p95 turn latency.

Proof of concept

Instrument a context store with versioned entries, revision events, and per-entity commit points; run 200 scripted calls containing hard names, dates of birth, and insurance identifiers through a layered fast-plus-batch transcription path with and without deferred commitment.

Measurement

Entity-level accuracy on names/dates/identifiers, contradiction rate (agent states a value that is later revised), p95 turn latency, and the share of turns where the corrective pass fired.

Architectural implications

3

Transcripts become provisional and revisable rather than a single append-only log.

Before

One transcriber produces a transcript that the LLM consumes as ground truth.

After

A fast provisional transcript is consumed immediately and a slower corrective pass can invalidate earlier tokens and rewrite context.

Consequence

The agent runtime needs a reconciliation mechanism (revision events, retraction semantics, or deferred commitment on entities) — otherwise the agent acts confidently on a wrong name or date. This is the main unaddressed engineering burden introduced by the pattern.

Source video ↗

Tool execution moves out of the reasoning loop into background producers writing into shared context.

Before

The main agent calls a tool, blocks, receives the result, then continues its turn.

After

Background agents run lookups concurrently with the user speaking and inject results into the main agent's context opportunistically.

Consequence

Context becomes a mutable, time-stamped store with staleness and ordering concerns; the main agent must reason about what it currently knows versus what is still pending, which is a new class of prompt- and state-management work.

Source video ↗

A caching layer is interposed between text generation and speech synthesis.

Before

LLM text streams directly into the TTS engine, and the user waits for audio generation.

After

Text is matched against a cache of previously rendered audio; stable prefixes play from cache while variable suffixes generate.

Consequence

Cache keying, hit-rate observability, and coherence between cached and fresh audio become production concerns; response phrasing becomes partly constrained by what is cacheable.

Tradeoffs and failure modes

3

Speculative multi-layer transcription

Benefit

Low time-to-first-transcript plus high final accuracy on phonetically difficult entities.

Cost or risk

Two transcribers running concurrently raise per-call cost, and already-consumed incorrect tokens must be cancelled or corrected downstream — the summary does not describe how that cancellation propagates to the LLM context.

Source video ↗

Audio prefix caching

Benefit

Suppresses redundant generation and removes perceived TTS latency on common openings.

Cost or risk

Only helps for predictable phrasing; correctness depends on the cached prefix matching the eventual full response, so entity-driven branching can force a mid-utterance divergence or discard the cached segment's premise.

Source video ↗

Async background tool injection

Benefit

Removes synchronous tool latency from the dialogue loop and reduces inference round trips.

Cost or risk

The main agent may commit to an utterance before a background result arrives, producing answers inconsistent with data that lands milliseconds later; the summary gives no ordering or staleness guarantees.
