Summary

Overview

  • Speaker: Pamela Fox
  • Channel: AI Engineer
  • Main topic: Comparing frontier LLMs (GPT-5.5, Kimi K2.6, DeepSeek-V4 Flash, and Mistral Large 3) across single-prompt calls, RAG, tool calling, agent loops, and evaluations.
  • Purpose: To demonstrate how frontier LLMs behave differently across common AI engineering tasks and to provide a reproducible workshop framework for evaluating and optimizing model swaps. Pamela Fox leads a hands-on workshop guiding AI engineers through model swapping across multiple frontier LLMs. Using Microsoft Foundry and Python, the workshop explores how models differ in reasoning, tool calling capacity, RAG grounding, multimodal image inputs, and agent loops. Attendees examine the practical trade-offs of switching models and evaluate them systematically using programmatic string comparisons, LLM-as-a-judge approaches, and assertion frameworks.

Key Points

Model Swapping Requires Systematic Evals

  • Explanation: Simply swapping model names in code without rigorous evaluation leads to silent failures and broken application workflows.
  • Evidence: Workshop comparisons showed different models failing at math, RAG grounding, and tool call sequencing under identical prompts.
  • Practical implication: Engineers must build comprehensive evaluation suites before deploying multi-model or swappable LLM architectures.

Smaller Models Hallucinate More in RAG Scenarios

  • Explanation: When provided with context that lacks answers to a user query, smaller models frequently invent answers based on internal weights rather than citing missing data.
  • Evidence: DeepSeek and Mistral models sometimes answered carpenter bee questions with honey bee details absent from context, whereas GPT-5.5 correctly stated no source was provided.
  • Practical implication: Strict prompt engineering and guardrails are necessary when using smaller or open-weight models for retrieval tasks.

Tool Calling Efficiency Varies Significantly

  • Explanation: Some models execute multi-step tool calls in parallel within a single turn, while others make multiple sequential calls, increasing latency and cost.
  • Evidence: GPT-5.5 completed calculator and travel planning tasks in fewer turns compared to other tested models.
  • Practical implication: Model choice directly impacts API cost and execution speed in agentic workflows.

Automated Prompt Optimization with DSPy

  • Explanation: Instead of manually tweaking prompts for different models, frameworks like DSPy use optimizers to automatically discover optimal prompts based on evaluation metrics.
  • Evidence: Using DSPy and GEPA to generate acrostic poem prompts that satisfy complex programmatic constraints.
  • Practical implication: Saves engineering time and improves model portability across different LLM backends.

Frameworks, Models & Processes

ASSERT Framework

  • How it works: Generates scenario-specific test cases and evaluation judges from a developer-defined spec, running models against target behaviors and scoring outputs across dimensions like budget adherence and constraint satisfaction.
  • Components:
    • Behavior categories
    • Test sets
    • Scenario generators
    • LLM-as-a-judge evaluation targets
  • When to use: When evaluating complex, multi-turn agent applications in production before model swaps.

DSPy (Declarative Self-improving Python)

  • How it works: Expresses tasks as structured signatures rather than raw prompts, using optimizers to automatically tune prompts and weights against programmatic constraints and metrics.
  • Components:
    • Signatures
    • Predictors
    • Metrics
    • Optimizers (GEPA)
  • When to use: When building modular LLM applications that need to optimize prompts across different models automatically.

Core insights

[O]Mental Modelmedium noveltyweak evidence

Model swapping is framed as an availability/portability requirement — the ability to route around a cut-off or degraded model provider — rather than a cost-optimization nicety, which makes the model a swappable dependency that must be validated like any other dependency upgrade.

Why it matters

If model identity is treated as a runtime configuration rather than a compile-time assumption, the engineering budget shifts from prompt tuning to regression harnesses that gate each swap.

Generalization

Any system whose core capability is supplied by an external, single-vendor model should be designed with a substitution path and a validation gate, mirroring how teams treat database or cloud-provider portability.

[E]Empirical Resultmedium noveltymoderate evidence

Abstention under incomplete retrieval context is a model-level capability, not a prompt-level instruction: when the retrieved context does not contain the answer, smaller models fall back to parametric knowledge and fabricate, while stronger models explicitly report the gap.

Why it matters

RAG grounding failures therefore cannot be fixed by adding 'only answer from context' to the prompt; the guardrail must live outside the model or the model choice must be constrained by a grounding-specific eval.

Generalization

Faithfulness constraints should be treated as a per-model measured property, with abstention rate as a first-class benchmark dimension separate from answer quality.

[!]Failure Modehigh noveltymoderate evidence

Tool-call failure is not primarily about selecting the wrong tool but about argument-level hallucination — models inventing plausible-but-unrequested fields (e.g., inserting themselves as an attendee) — which requires schema validation and argument sanitization outside the model rather than trust in schema conformance.

Why it matters

Agent runtimes that forward model-generated arguments directly into side-effecting APIs inherit correctness and security risk from a per-model behavior that varies silently across swaps.

Generalization

Treat tool arguments as untrusted input: validate, constrain, and reject at the execution boundary, since schema-conformant generation is not guaranteed by schema declaration.

[~]Tradeoffmedium noveltymoderate evidence

Parallel tool-calling competence changes agent loop structure, not just latency: some models reach the goal in a single parallel turn while others require multiple sequential tool calls, producing large variance in turn count, cost, and intermediate state exposure under an identical prompt.

Why it matters

Loop designs, budgets, and max-turn limits calibrated against one model will silently under- or over-provision when the model is swapped; turn count becomes a measurable per-model efficiency metric.

Generalization

Agent runtimes should measure turns-to-completion and parallel-call ratio as model-specific performance characteristics alongside accuracy, and set budgets from data rather than fixed defaults.

Source video ↗
[A]Architecturehigh noveltymoderate evidence

Automated prompt optimization inverts prompt portability: instead of a hand-written prompt that travels across models, prompts become compiled artifacts generated per model against a metric and test set, so a model swap becomes a recompilation rather than a drop-in replacement.

Why it matters

This reframes prompt engineering as a build step with a compiler, a dataset, and a metric — which means the eval set and optimizer configuration are production assets, and unoptimized fallback prompts become a degraded-mode requirement.

Generalization

Where output constraints are complex and model-conditional, declarative program specs plus an optimizer scale better than manual prompt iteration, at the cost of losing a single prompt that works everywhere.

Source video ↗
[P]Practicemedium noveltymoderate evidence

The judge is itself a model: LLM-as-a-judge grading requires calibration against human labels and explicit rubrics, so the evaluation stack has the same swap-sensitivity problem as the system under test.

Why it matters

An uncalibrated judge can mask or manufacture regressions during a model swap; teams need a validated judge (or a mix of deterministic string checks plus judged checks) before trusting eval deltas.

Generalization

Evaluation infrastructure should be versioned and periodically re-validated against human ground truth, exactly like the system it evaluates.

[!]Failure Modehigh noveltyweak evidence

Input language is a reliability variable, not merely an i18n concern: prompting in a non-English language (e.g., Spanish) can cause a model that otherwise succeeds to hallucinate or fail the same multimodal task.

Why it matters

Multilingual applications can regress on a model swap even when English-language evals are green, meaning test stratification must include input language as a dimension.

Generalization

Eval suites should stratify by incidental input properties (language, encoding format, image quality) that are orthogonal to the task but known to shift model behavior.

Deep dives

5

Runtime detection of tool-argument hallucination

Research question

What is the cheapest reliable runtime signal that a model has fabricated tool arguments (e.g., invented fields, self-inserted values) before those arguments reach a side-effecting API?

Why

Argument-level hallucination is described as an observed, silent behavior that varies across models, so the guardrail must live at the execution boundary; without a detection mechanism, a model swap can turn a schema-conformant call into a bad write or a security-relevant side effect.

Source video ↗

Abstention rate as a first-class benchmark dimension

Research question

Does abstention under incomplete retrieval context correlate with model size, or with training/post-training recipe independent of size, and can it be enforced outside the model rather than by prompt instruction?

Why

If abstention is a model-level capability rather than a prompt-level instruction, then 'only answer from context' cannot be the guardrail; faithfulness must be measured per model and stratified separately from answer quality, or RAG grounding regressions will slip through a swap.

Source video ↗

Turns-to-completion and parallel-call ratio as model-specific metrics

Research question

What is the distribution of turns-to-completion and total token cost per model on the same agent task holding the harness fixed, and are these properties stable across model versions?

Why

If parallel tool-calling competence changes loop structure rather than only latency, then max-turn limits and cost budgets calibrated against one model are silently wrong after a swap; the metric must be measured per model and re-measured per version.

Eval suite sizing and stratification for swap gating

Research question

How small can a stratified eval suite be while still catching grounding and tool-argument regressions introduced by a model swap, and which stratification dimensions (task type, input language, context-completeness) buy the most detection rate per test case?

Why

Evals are described as time-intensive and costly, which pushes teams toward small suites; without data on detection rate per suite size, the merge gate that makes model swapping safe is calibrated by guesswork.

Research question

If optimized prompts are model-conditional build artifacts rather than portable text, then every swap becomes a recompile-and-verify step, and an unoptimized fallback prompt becomes a required degraded-mode asset rather than an afterthought.

Article ideas

4

Your RAG Prompt Cannot Save a Model That Won't Abstain

Grounding failures in RAG are a model-level capability gap, not a prompt-engineering gap: adding 'only answer from context' does not stop weaker models from substituting parametric knowledge, so faithfulness must be enforced by model selection plus an external guardrail and measured as a separate abstention dimension in every swap gate.

Angle

Contrast the prompt-instruction assumption against the workshop's observed behavior and derive the eval dimension and guardrail placement that follows.

Source video ↗

Tool Arguments Are Untrusted Input

The dangerous failure in agent tool calling is not wrong-tool selection but invented arguments, and since schema declaration does not guarantee schema-conformant generation, agent runtimes must validate and sanitize model-produced arguments at the execution boundary exactly as they would treat external user input.

Angle

Reframe the trust boundary: move trust from the tool schema in the prompt to runtime enforcement before side effects, and treat swap-induced argument changes as caught validation failures rather than silent bad writes.

Source video ↗

Model Swaps Are Dependency Upgrades, So Gate Them Like One

Because model swapping is driven by provider availability rather than cost tuning, the model is a swappable dependency; changing the model name is equivalent to a dependency upgrade and must ship as a PR with a per-candidate scorecard, making the eval set and test corpus the most valuable maintained asset in the repository.

Angle

Use the availability framing to argue that prompt tuning budget should be redirected into regression harnesses, with turn count, abstention rate, and argument-error rate as scorecard rows.

Source video ↗

The Judge Is Also Being Swapped

LLM-as-a-judge makes the evaluation stack inherit the same swap-sensitivity as the system under test, so an uncalibrated judge can manufacture or mask regressions; eval infrastructure must be versioned, rubric-explicit, and periodically re-validated against human labels before any swap delta is trusted.

Angle

Apply the model-swap logic reflexively to the grader, and recommend mixing deterministic string checks with judged checks to bound judge-induced error.

Source video ↗

Project ideas

4

Argument Sentinel

gatehouse

Strict argument validation and sanitization at the execution boundary reduces side-effecting bad writes from model-generated tool arguments to zero while preserving task success rate, and argument-error rate varies measurably across models under an identical tool schema.

Proof of concept

A fixed tool-calling harness with one side-effecting tool (e.g., booking with an attendee list). Run identical prompts across the workshop's candidate models with and without a validator that rejects unexpected/extra fields and enum violations before execution. Log every rejection.

Measurement

Bad writes reaching the sink per model (target: zero with validator), rejection rate per model, and task success rate delta between validator-on and validator-off arms.

Source video ↗

Abstention Gate

beyond-evals

Injecting context-incomplete queries with known-missing answers into a RAG suite produces an abstention rate that separates models more sharply than answer-quality scores, and that rate is not improvable by prompt instruction alone on weaker models.

Proof of concept

A small RAG corpus with documented gaps (e.g., carpenter-bee documentation only). Query it with questions whose answers are absent. Compare three arms: baseline prompt, 'answer only from context' prompt, and an external abstention check that flags unsupported answers. Run across all candidate models.

Measurement

Fabrication rate on context-missing queries per model per arm, and drop in fabrication rate attributable to prompt instruction versus external check.

Source video ↗

Turn Budget Profiler

movement-lab

Turns-to-completion and parallel-call ratio on an identical agent task differ enough across models that a fixed max-turn and cost budget calibrated on one model either truncates or over-provisions on another, and these metrics are stable enough within a version to set budgets from data.

Proof of concept

One multi-step tool task, one fixed harness, all four candidate models. Instrument turn count, parallel-call count, total tokens, and completion success. Repeat runs to estimate per-model variance and derive a budget per model.

Measurement

Distribution of turns-to-completion, parallel-call ratio, token cost, and completed-vs-truncated rate at a fixed max-turn limit per model.

Source video ↗

Swap Regression Detector

beyond-evals

A stratified eval suite significantly smaller than a full benchmark can detect swap-induced grounding, tool-argument, and turn-efficiency regressions at a measurable detection rate, and detection rate per test case is highest for context-completeness and argument-shape stratification rather than task-type alone.

Proof of concept

Build a seeded regression corpus where each item has a known correct behavior. Simulate swaps across the candidate models, incrementally grow the suite by strata, and measure how many known swap-induced regressions are caught at each suite size.

Measurement

Regressions detected per suite size, detection rate per stratum, and cost per detected regression.

Before

Tradeoffs and failure modes

5

Model swap flexibility vs. regression risk

Benefit

Routing around a degraded or unavailable provider and picking the best model per task.

Cost or risk

Swapping a model name without rigorous evaluation produces silent failures in math, grounding, and tool sequencing that existing tests may not catch.

Source video ↗

Eval rigor vs. eval velocity

Benefit

Curated test cases and calibrated judges catch drift and make swap decisions defensible.

Cost or risk

Evals are time-intensive and expensive to run, which pushes teams toward small suites that may not stratify enough to catch language- or grounding-specific regressions.

Source video ↗

Parallel vs. sequential tool calling

Benefit

Single-turn parallel tool calls complete multi-step tasks faster and with fewer round trips.

Cost or risk

Models that decompose into many sequential calls inflate turn count, latency, and cost, and expose more intermediate state under the same prompt.

Source video ↗

Automated prompt optimization vs. prompt portability

Benefit

Optimizers find constraint-satisfying prompts without manual trial and error.

Cost or risk

Optimized prompts are tuned to a specific model and metric, so a later swap requires reoptimization and revalidation rather than a simple drop-in.

Source video ↗

Cheap LLM judging vs. judge trust

Benefit

LLM-as-a-judge scales qualitative grading where string comparison cannot.

Cost or risk

Judges need human calibration and robust rubrics; an uncalibrated judge can misreport quality and hide swap-induced regressions.
