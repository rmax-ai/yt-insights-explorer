Summary

Overview

  • Speaker: Mikyo King
  • Channel: AI Engineer
  • Main topic: Code Mode: Why AI agents should write and execute code instead of relying purely on traditional tool calling
  • Purpose: To convince AI engineers to transition from traditional multi-turn tool calling to code mode architectures by providing agents with sandboxes and evaluating them effectively using platforms like Arize Phoenix. Mikyo King from Arize AI explores 'code mode', an architectural paradigm where LLM agents are given a programming environment and sandbox to search, compose, and execute tools dynamically rather than receiving a massive static catalog of tool definitions. The talk compares traditional tool calling with code mode, highlighting benefits such as progressive disclosure, composability, token efficiency, and emergent behavior, while also analyzing operational tradeoffs like sandboxing security, resource limits, network egress, and debugging complexity.

Topic Map

The Evolution of Software and Coding Agents

  • Explanation: Software engineering has historically been divided into software for software engineers versus non-engineers. Coding agents blur this boundary by dynamically writing software to solve tasks.
  • Key claims:
    • Software can be segmented into software for engineers and non-engineers.
    • Code mode dissolves the boundary between user interfaces and software by allowing coding agents to build software dynamically.
  • Examples:
    • Extracting invoices from an email inbox via a programmer writing a script versus a non-technical user being restricted by software UI boundaries.
  • Terminology:
    • code mode
    • coding agent
    • software development
  • Why it matters: Foundation models are trained on SWE benchmarks, so aligning agent architecture with code generation enables models to solve problems natively.

The Too Many Tools Problem

  • Explanation: Traditional tool-calling agents suffer from context bloat, token inefficiency, multi-turn latency, and context rot when given large catalogs of tools.
  • Key claims:
    • Giving an agent a huge catalog of tools leads to context window bloat and context rot.
    • Tool outputs that contain junk or require pagination cause multi-turn inefficiencies and increased cost.
  • Examples:
    • Calling CRM, meetings, email, calendar, docs, and tasks APIs sequentially until the context window fills up.
  • Terminology:
    • context window
    • context rot
    • tool definitions
    • tool calling
  • Why it matters: Context bloat increases latency, token cost, and error rates in agentic workflows.

Code Mode Architecture

  • Explanation: Instead of pre-loading tool definitions into the prompt, code mode gives the model the ability to search and execute tools inside a secure sandbox environment using programming constructs.
  • Key claims:
    • Models program the tools inside a sandbox instead of making single API tool calls per turn.
    • Models can execute multiple tools in one turn, use loops and conditionals, and return only necessary data back to the context window.
  • Examples:
    • Writing a Python script combining find_meeting, get_transcript, find_deal, and attach in a single sandbox execution.
  • Terminology:
    • sandbox
    • progressive disclosure
    • composability
    • emergent behavior
  • Why it matters: Code mode dramatically reduces turns, context window usage, latency, and token costs.

Why Code Mode Works

  • Explanation: Code mode leverages progressive disclosure of tools, composability of sub-agents and operations, high token efficiency, and emergent behavior (writing custom tools on the fly).
  • Key claims:
    • Progressive disclosure means models pick and choose only needed tool definitions.
    • Composability allows chaining tool calls sequentially or in parallel.
    • Emergent behavior enables agents to write custom helper functions like redact_pii() to solve complex tasks safely.
  • Examples:
    • Writing a Python function def redact_pii(t): to remove personally identifiable information before passing it to context.
  • Terminology:
    • progressive disclosure
    • composability
    • token efficiency
    • emergent behavior
  • Why it matters: It unlocks advanced reasoning workflows and prevents sensitive data leaks into the context window.

Code Mode in Practice: PXI and Browser Use

  • Explanation: Arize implements code mode in PXI (Phoenix Server) using bash, python execution environments, SQL execution for traces, and browser web workers.
  • Key claims:
    • PXI exposes bash, python execution, and SQLite queries to let agents query traces and manipulate data sets.
    • Web workers with two-way data binding allow agents to drive real browser UI and perform complex UI interactions.
  • Examples:
    • Using executeSQL to query spans in Phoenix or running search_browser_actions in a web worker.
  • Terminology:
    • PXI
    • Phoenix
    • web worker
    • executeSQL
  • Why it matters: Demonstrates practical, production-ready applications of code mode in observability platforms.

Tradeoffs and Open Problems

  • Explanation: Code mode introduces challenges related to resource limits, network egress, secret management, permissions, operational complexity, durability, and determinism.
  • Key claims:
    • LLM-generated code running in sandboxes requires strict CPU, memory, and network egress limits.
    • Secret management and over-broad permissions are critical security concerns.
    • Determinism, handling large binary/image payloads, and smaller model capabilities remain open research problems.
  • Examples:
    • A sandbox running out of memory or an LLM trying to leak API keys or make unauthorized outbound network calls.
  • Terminology:
    • resource limits
    • network egress
    • sandbox
    • durability
    • determinism
  • Why it matters: Engineers must design robust security and guardrails when letting LLMs write and execute arbitrary code.

Evaluating Code Mode with Arize Phoenix

  • Explanation: Arize Phoenix uses the Harbor framework to run agents through trial permutations, verify outputs using programmatic verifiers, and track success metrics across benchmarks.
  • Key claims:
    • Running multi-trial evaluations in isolated sandbox environments eliminates flake and indeterminate behaviors.
    • Code mode reduced token usage by 43% and cost by 31% while maintaining reward and latency in benchmarks.
  • Examples:
    • Comparing pre-code mode vs. post-code mode pass rates across pagedown-root-cause and max-llm-calls tests.
  • Terminology:
    • Phoenix
    • Harbor framework
    • evaluations
    • verifiers
  • Why it matters: Rigorous evaluation allows developers to analyze trace trajectories and tune agent instructions effectively.

Key Points

Context bloat in traditional tool calling

  • Explanation: Providing large catalogs of tools causes context window exhaustion, high costs, and increased latency.
  • Evidence: Comparison graphs showing traditional tool calling consuming 89% context and $0.89 vs code mode consuming 2% context and $0.02.
  • Practical implication: Switching to code mode keeps context clean by returning only necessary execution results.

Emergent behavior and custom tool creation

  • Explanation: Agents can write custom helper functions on the fly to handle tasks that lack pre-built tools.
  • Evidence: Example of an agent writing def redact_pii(t): to sanitize transcripts before passing them to the model.
  • Practical implication: Agents become more flexible and autonomous without needing developers to pre-define every possible tool.

Operational complexity and security risks

  • Explanation: Executing LLM-generated code requires careful sandboxing to manage CPU, memory, network egress, and secrets.
  • Evidence: Discussion on injected READMEs, network egress to malicious domains, and over-broad permission creep.
  • Practical implication: Engineers must implement strict guardrails and isolation layers around agent execution environments.

Frameworks, Models & Processes

Code Mode Architecture

  • How it works: The model generates a programming script containing tool calls and logic inside a secure sandbox, executes it, and returns only the final required output to the context window.
  • Components:
    • LLM model
    • Sandbox environment
    • Tool search interface
    • Execution runtime
  • When to use: When building complex agents with numerous tools, high token costs, and multi-turn latency issues.

Harbor Evaluation Framework

  • How it works: Runs agent tasks across multiple trials in isolated sandboxes with network access turned off, using programmatic verifiers to assign binary scores (0 or 1).
  • Components:
    • Task definition
    • Trial sandbox environment
    • Agent under test
    • Phoenix Verifier
  • When to use: When evaluating agent reliability, regression testing, and tuning agent instructions.

Core insights

[A]Architecturehigh noveltystrong evidence

Code mode relocates tool orchestration from the host's turn loop into LLM-authored code executing inside a sandbox: instead of one API call per turn, the model writes a program that calls several tools with loops and conditionals and returns only the distilled result to the context window.

Why it matters

This changes where the control flow of an agent lives. Turn-by-turn orchestration by the harness becomes in-sandbox program control flow, so intermediate tool outputs never enter the prompt — the primary driver of the reported token and cost reductions.

Generalization

Whenever an agent's bottleneck is the number of sequential tool round-trips rather than reasoning quality, moving orchestration into executable code converts N prompt round-trips into one program execution.

[M]Mechanismmedium noveltymoderate evidence

Progressive disclosure turns tool selection into a retrieval problem: the model discovers and pulls only the tool definitions it needs at runtime instead of receiving a full static catalog in the prompt.

Why it matters

Tool catalog size stops being a fixed context tax. Context budget becomes a function of the task rather than the size of the integration surface, which is the difference between supporting 10 and 1,000 tools in one agent.

Generalization

Any capability inventory too large to fit (tools, APIs, docs, schemas) should be exposed as searchable/queryable at runtime rather than pre-loaded — the same argument as retrieval over full-corpus prompting, applied to capabilities rather than knowledge.

Tool-catalog scaling and retrieval-based capability disclosure

Research question

At what tool-catalog size does tool-call selection accuracy measurably degrade with static prompt-loaded definitions, and does runtime tool search (progressive disclosure inside a sandbox) hold accuracy flat as the catalog grows from 10 to 1,000+ tools?

Why

If the degradation curve has a knee, teams get a concrete threshold for when to stop adding tools to a prompt and start building a searchable capability registry — and tool-search quality becomes a new single point of failure that needs its own evaluation.

Source video ↗

Cost attribution between intermediate-result elimination and other levers

Research question

What fraction of code mode's reported 43% token and 31% cost reduction is attributable specifically to keeping intermediate tool outputs out of the context window, versus prompt shortening, fewer model calls, or changed retry behavior?

Why

If intermediate-result elimination is the dominant lever, then optimization effort should go to data shaping at the runtime boundary (aggregation, filtering, handles) rather than to model selection or prompt compression — a different engineering roadmap entirely.

Source video ↗

Least-privilege capability scoping for LLM-written code

Research question

Can per-task capability tokens with network egress allowlists and scoped secret injection preserve code mode's composability while blocking API-key exfiltration and unauthorized outbound calls, and how often does agent-written code actually require privilege escalation?

Why

The security perimeter moves from the tool schema to the runtime, so the permissions model becomes core architecture rather than a deployment detail. Escalation frequency is the key number: if it is near zero, tight default-deny is viable; if not, the composability benefit collapses under approval friction.

Source video ↗

Determinism and durability of sandbox execution

Research question

Does record/replay of sandbox executions plus checkpointing of sandbox state produce high-fidelity reproduction of code-mode agent runs, and what residual nondeterminism remains after replay?

Why

Emergent helper functions and agent-authored control flow make runs hard to reason about; without replay fidelity, incident review and regression testing of code-mode agents degrade into re-running and hoping. This is a prerequisite for production use of self-written logic.

Evaluation reproducibility via sandbox-per-trial

Research question

How much of agent benchmark variance is removed by per-trial sandbox isolation plus programmatic verifiers, and does the residual variance differ by task type?

Why

Agent evaluation quality is bounded by environment reproducibility; if isolation removes most variance, pre/post architectural comparisons become feasible at small sample sizes instead of requiring huge, expensive trial counts.

Article ideas

4

Your Agent's Bottleneck Is the Round Trip, Not the Model

For multi-API agent workloads the dominant cost lever is eliminating intermediate results from the context window, not model selection or prompt shortening; code mode wins because it converts N sequential prompt round-trips into one program execution that returns only distilled output.

Angle

Decompose an agent's cost into turn count, per-turn context size, and retries, then show that shrinking per-turn context buys far less than cutting turns — with the 89%-to-2% context and $0.89-to-$0.02 comparison as the worked example.

Source video ↗

Stop Preloading Tools: Capability Discovery Is Just Retrieval

A static tool catalog in the system prompt is a context tax proportional to integration surface; tool definitions should be treated like a corpus and retrieved at runtime, which is the same argument that killed full-corpus prompting applied to capabilities instead of knowledge.

Angle

Frame progressive disclosure as retrieval-over-capabilities, then examine the consequence the framing is usually used to hide: tool-search quality becomes a new single point of failure and therefore a new thing that must be evaluated.

Source video ↗

The Sandbox Is the New Tool Schema

Handing an agent a general execution environment shifts the security perimeter from typed tool schemas to the runtime, so CPU/memory ceilings, egress control, scoped secrets, and least-privilege capability grants become architecture decided before the agent is useful — not deployment details bolted on after.

Angle

Argue that input validation at the tool boundary no longer covers the blast radius once the model writes arbitrary code, and that safety work migrates from schema design to capability isolation, using API-key exfiltration and unauthorized outbound calls as the threat model.

Source video ↗

Redaction Belongs in Code, Not in the Prompt

Putting a code-execution layer between raw data sources and the model context turns data governance from soft prompt guidance into enforceable, reviewable code, because an agent can strip fields before they ever reach the context window.

Angle

Contrast 'instruct the model to be careful with PII' with agent-authored helper functions that transform payloads at the runtime boundary, and be honest that voluntary-redaction frequency is an unmeasured claim rather than a demonstrated behavior.

Project ideas

4

Catalog Scaling Curve

beyond-evals

Tool-selection accuracy degrades past a measurable catalog-size knee under static prompt-loaded definitions, while code mode with runtime tool search holds accuracy flat and keeps context cost constant as the catalog grows by an order of magnitude.

Proof of concept

Build one agent over a synthetic integration surface (CRM, meetings, email, calendar, docs, tasks) expanded in controlled steps from 10 to 1,000 tools; run both the static-catalog tool-calling configuration and a sandbox code-mode configuration with tool search, using isolated per-trial environments and programmatic verifiers on a fixed task suite.

Measurement

Plot task success rate, prompt tokens, and tool-selection error versus catalog size for both configurations; report the catalog size at which static tool calling drops a statistically significant margin below code mode, and the variance of each point across trials.

Source video ↗

Egress Sentinel

gatehouse

Default-deny network egress with a per-task allowlist and scoped, short-lived secret injection blocks API-key exfiltration and unauthorized outbound calls from LLM-written sandbox code while causing privilege-escalation requests in under 5% of tasks.

Proof of concept

Instrument a code-mode sandbox with capability tokens per task, an egress allowlist proxy, and secrets injected as narrow-scope handles rather than raw strings; run a task suite plus adversarial prompts designed to induce key leakage and outbound calls, logging every escalation request the agent's code makes.

Measurement

Exfiltration success rate (target zero across adversarial trials), task success delta versus an unrestricted sandbox, and the percentage of tasks requiring an escalation request, broken down by task type.

Source video ↗

Sandbox Replay

new

Recording tool calls, tool responses, and filesystem state at each sandbox execution boundary and replaying them reproduces agent task outcomes with high fidelity, leaving only model sampling as residual nondeterminism.

Proof of concept

Implement record/replay around a code-mode runtime: capture ordered tool I/O, environment state checkpoints, and the model's generated programs; replay recorded runs with sampling pinned and compare final task outcomes and intermediate program outputs to the originals.

Measurement

Outcome agreement rate between recorded and replayed runs, per-step divergence location for the runs that disagree, and the fraction of divergence attributable to re-invoked tools versus regenerated code.

Source video ↗

Cost Attribution Ablation

new

At least 70% of code mode's token and cost savings comes from keeping intermediate tool outputs out of the context window, not from smaller prompts or fewer model calls.

Proof of concept

Take one code-mode workload and create ablated variants: (a) baseline tool calling, (b) code mode with tool outputs deliberately echoed back into context, (c) code mode returning only distilled results; hold the task set, model, and retry budget constant across all three.

Measurement

Per-task token count, cost, latency, and reward for each variant, reported as the share of total savings attributable to intermediate-result elimination, with retry counts logged to confirm the comparison is not an artifact of differing retry budgets.

Architectural implications

4

Control flow for multi-step tool use moves from the host agent loop into model-authored code inside the sandbox.

Before

Host-owned loop: one tool call per turn, sequential round-trips with the orchestrator making branching decisions between turns.

After

Sandbox-owned loop: the model writes a script combining tools such as find_meeting, get_transcript, find_deal, and attach in a single execution.

Consequence

Fewer turns and tokens, but the orchestrator loses per-step visibility — observability must move to trace trajectory and execution-level inspection rather than turn-by-turn logs.

Source video ↗

The full tool catalog is no longer a prompt artifact; it becomes a searchable runtime resource.

Before

All tool definitions pre-loaded into the system prompt, consuming context proportional to integration count.

After

Tool definitions retrieved on demand via search from within the sandbox (progressive disclosure).

Consequence

Agents can be wired to far larger integration surfaces at constant context cost, but tool-search quality becomes a new single point of failure and a new thing to evaluate.

Source video ↗

Data shaping and redaction shift from prompt instructions to executed code.

Before

Raw API responses flow into the context window; the model is instructed to handle sensitive fields carefully.

After

The agent writes helper functions such as redact_pii() that strip fields before anything reaches context.

Consequence

Enforceable, testable data governance at the runtime boundary; the safety property is reviewable code rather than emergent model compliance.

Source video ↗

Browser/UI automation is driven from inside a code runtime rather than one action per model turn.

Before

One browser action per tool call, each action costing a full model round-trip.

After

Web workers with two-way data binding let the agent drive real browser UI and perform complex UI interactions from within one execution.

Consequence

Long UI interaction sequences become feasible and cheap, moving browser agents closer to scripted automation with model reasoning at the level of intent.

5

Context efficiency vs. security blast radius

Benefit

Returns only necessary execution results, cutting context usage from 89% to 2% in the illustrative case.

Cost or risk

Arbitrary LLM-generated code runs in the environment, so CPU, memory, and egress must be capped and secrets protected against exfiltration.

Composability and emergent behavior vs. determinism

Benefit

Agents can chain tools sequentially or in parallel and invent helper functions like redact_pii() on the fly.

Cost or risk

Determinism remains an open problem; self-invented logic makes runs harder to reproduce and reason about.

Rich payload handling

Benefit

Code can aggregate, transform, and conditionally process tool output before returning it.

Cost or risk

Large binary and image payloads remain an open problem in this paradigm.

General-purpose sandbox vs. least-privilege permissions

Benefit

A single bash/python/SQL execution surface covers many agent tasks and reduces integration work.

Cost or risk

Over-broad permissions accumulate because one runtime serves many actions; secret scope and durability are additional unresolved burdens.

Code mode vs. small-model feasibility

Benefit

Benefits rely on the model's ability to write correct multi-step programs.

Cost or risk
