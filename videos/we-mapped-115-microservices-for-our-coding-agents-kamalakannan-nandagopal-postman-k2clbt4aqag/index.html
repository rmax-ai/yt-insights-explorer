Summary

Overview

  • Speaker: Kamalakannan Nandagopal
  • Channel: AI Engineer
  • Main topic: Beyond Code Generation: API Context for Agentic Engineering
  • Purpose: Explain how API Context Graphs solve the limitations of coding agents in complex distributed microservice architectures and present evaluation results comparing generic coding agents against API-context-aware agents. Kamalakannan Nandagopal, Staff Engineer at Postman, discusses how taking coding agents beyond code generation requires providing comprehensive API context. Postman mapped its 115+ microservices and 4,000+ endpoints into an API Context Graph grounded in hard truth (code and production telemetry). Evaluating coding agents (like Claude and Postman's AI agent) on tasks such as API discovery, API design/redesign, and impact assessment demonstrates that providing an API Context Graph dramatically improves agent evaluation scores while reducing token overhead.

Key Points

Production systems are complex and distributed

  • Explanation: Enterprise applications consist of multiple microservices across multiple environments, multiple application frontends, and hundreds of code repositories.
  • Evidence: Postman's internal architecture spans over 115 microservices and 4,200+ REST API endpoints.
  • Practical implication: Coding agents operating only within a single repository lack the global view required for reliable multi-service changes.

APIs serve as the natural context layer

  • Explanation: In microservice architectures, domains and models define system boundaries, and API calls define workflows and user journeys.
  • Evidence: Complex architectures are broken down by domain and model, with each microservice owning specific responsibilities defined by its APIs.
  • Practical implication: Mapping APIs provides the necessary context layer for coding agents to reason about system-wide interactions.

Grounding context in hard truth prevents hallucination

  • Explanation: Every data point in the API Context Graph must tie directly to code implementation or production telemetry.
  • Evidence: Pure LLM-maintained documentation degrades exponentially over time without human curation.
  • Practical implication: Ensures agents do not rely on stale or hallucinated documentation.

75% of pull requests involve APIs

  • Explanation: The vast majority of engineering changes either modify API surface areas or integrate new APIs.
  • Evidence: Retrospective analysis of PRs across Postman's top 10 repositories.
  • Practical implication: API context is critical for the vast majority of real-world coding tasks.

Frameworks, Models & Processes

API Context Graph Construction

  • How it works: Catalogs production microservices and endpoints, maps call graphs, data dependencies, and client consumption to build an LLM-indexed graph grounded in code and telemetry.
  • Components:
    • Microservice cataloging
    • Endpoint implementation mapping
    • Inter-service call mapping
    • Data persistence tracking (caches/databases)
    • Frontend and CLI interaction tracking
    • LLM indexing with hard-truth grounding
  • When to use: When scaling coding agents across distributed microservice architectures.

Examples & Case Studies

A developer added a new property to a task API input schema, but two weeks later, 15 downstream services were affected because input shapes weren't clear.

  • Illustrates: The difficulty of API design and redesign without comprehensive consumer context.
  • Lesson: Analyzing all shapes of input and consumer usage via an API Context Graph prevents integration failures and loss of developer trust.

An evaluation of impact assessment on a PR that changed an endpoint failed because new consumers were added to production between the eval creation and execution.

  • Illustrates: The critical need to keep context graphs up to date with production reality.
  • Lesson: Delays in syncing context graphs with ground truth lead to incorrect data and broken trust.

Actionable Takeaways

  • Immediate:
    • Catalog all production microservices and API endpoints as a foundation for agent context.
    • Ground all agent context in code and production telemetry rather than static documentation.
  • Strategic:
    • Use API Context Graphs to enable coding agents to perform system-wide impact assessments and API design.
    • Catch architectural problems, dependency cycles, and technical debt earlier in the development lifecycle.
  • Questions to investigate:
    • How can agent memory be effectively shared across broader engineering teams rather than individual users?
    • How can business semantic layers be seamlessly integrated into technical API context graphs?

Consumer-aware blast radius prediction for interface changes

Research question

What is the minimum set of graph edges — input shapes, consumer usage, call relationships, persistence — needed to predict the downstream blast radius of an interface change before merge, and how much precision is lost as edges are dropped?

Why

Latent cross-service breakage is the failure mode single-repo agents structurally cannot see; identifying the minimal sufficient edge set tells you exactly what the context graph must extract and keep fresh, and what can be omitted.

Source video ↗

Context graph freshness, drift detection and accuracy decay

Research question

How quickly does agent task accuracy decay as the API Context Graph falls behind live code and production telemetry, and can drift be detected before that accuracy degradation becomes observable?

Why

Grounding in code and telemetry only holds if the graph stays current; without drift detection the pipeline silently reintroduces the staleness problem it was built to eliminate, and teams lose the trust that makes the graph usable.

Isolating topology signal from context compression in the token savings

Research question

Why

If the gain disappears at matched budgets, the investment is a retrieval-efficiency play; if it persists, the value is genuinely in the graph structure — two different architectures with different cost models.

4

Stop Writing Docs for Your Coding Agent — Generate a Topology Graph Instead

The choice between prose documentation and extracted context is not a quality difference but a decay-rate difference: LLM-maintained docs rot without human curation while code-and-telemetry-derived graphs stay synchronized, so teams should replace documentation programs with extraction pipelines and freshness SLAs rather than better prompting.

Angle

Frames agent context as a maintained data product with a decay curve, and argues doc rot is an architectural bug, not a discipline problem.

Source video ↗

75% of Your PRs Are API Changes. Your Agent Only Sees One Repo.

Change-history analysis should determine the scope of an agent's context layer: if the dominant real-world change type is cross-service API surface, single-repo code search is structurally the wrong retrieval scope no matter how good the model is.

Angle

Instrument-first argument — measure your own PR taxonomy before choosing a context architecture.

Source video ↗

The Two-Week Bug: Why Agents That Pass Review Break Production

Impact-assessment failures in distributed systems are latent and cross-service rather than immediate compile errors, so coding-agent evaluation must include delayed blast-radius checks; pass rates on compile-and-test are systematically blind to the change class that causes the most damage.

Angle

Forensics of a single schema change that propagated to 15 services, used to argue for a new eval dimension.

Source video ↗

Tools Aren't the Bottleneck; Unshared Context Is

Adding skills, MCP servers, and per-user agent memory does not fix agent failure in distributed systems, because each mechanism inherits whatever context it receives and fragments across users; the leverage point is a shared, team-level system context substrate, not a longer tool list.

Angle

Critique of tool-count-driven agent roadmaps, with a substitution argument for shared context infrastructure.

Project ideas

4

Blast Radius Gate

gatehouse

A graph-derived consumer list predicts the large majority (>=90%) of services that actually break after an interface change, and gating merges on that list measurably reduces cross-service incidents.

Proof of concept

Build consumer/input-shape/call edges for a multi-service repo set; replay historical schema changes, compare the graph-predicted impacted-consumer list against the post-hoc incident list; then run the gate on live PRs and observe incidents.

Measurement

Precision and recall of predicted impacted services versus observed breakage per change; cross-service incident count and mean time-to-detection before versus after the gate.

Source video ↗

StaleGraph Benchmark

beyond-evals

Agent accuracy on API discovery and impact-assessment tasks degrades monotonically with graph staleness, crossing a usability threshold within a small number of commits or weeks of code change.

Proof of concept

Build an API context graph over a multi-service repository, snapshot it, then advance the code forward while freezing the graph; run an identical task suite at each graph-age offset against a live code-search baseline.

Measurement

Score delta per graph-age step, and the commit count or elapsed time at which graph-augmented accuracy falls below the code-search baseline.

Source video ↗

Unknown Consumer Probe

gatehouse

Graphs grounded only in deployed code and existing telemetry systematically omit newly added consumers, producing false-negative impact assessments, and a hybrid grounding strategy restores detection of those consumers.

Proof of concept

Introduce a new consumer service against a test API, then query a graph-augmented agent for the impacted-consumer list under three grounding configurations: static code only, telemetry only, and hybrid.

Measurement

False-negative rate for the newly introduced consumer and for other consumers absent from telemetry history, per grounding configuration.

Source video ↗

Token-Matched Context A/B

beyond-evals

At equal token budgets, API Context Graph context still outperforms code-search context, showing the accuracy gain comes from topology structure rather than from simply transmitting less text.

Proof of concept

Run the same discovery, design/redesign and impact-assessment task suite under three arms: graph context, code search capped to the same token budget, and uncapped code search; plot score against token spend.

Measurement

Task score at matched token budget and the slope of score-per-token curves across arms.

Architectural implications

3

Agent context is sourced from an indexed graph built from code and telemetry rather than from maintained documentation.

Before

Agent context came from human-written docs, skills, and per-user memory.

After

Agent context is a generated, LLM-indexed graph grounded in code and production telemetry.

Consequence

Context pipelines must ingest code and telemetry continuously; documentation maintenance burden is replaced by graph extraction and freshness guarantees.

Before

After

The agent queries a shared API Context Graph spanning 115+ microservices and thousands of endpoints.

Consequence

Multi-service changes become tractable, but the graph becomes critical infrastructure that must be maintained and indexed.

Tradeoffs and failure modes

3

Grounding vs maintenance overhead

Benefit

Grounding in code and production telemetry prevents stale or hallucinated context.

Cost or risk

It shifts maintenance from human docs to continuous code/telemetry extraction and indexing, which must be kept in sync as the system changes.

Source video ↗

Shared context vs per-user agent memory

Benefit

A centralized graph provides shared, standard context across teams.

Cost or risk

Per-user agent memory currently lacks standard sharing, so team-level knowledge stays fragmented.

Source video ↗

Structured graph context vs code search

Benefit

API Context Graph improves scores while saving tokens.

Cost or risk

Requires building and maintaining a graph index; value depends on tasks being API/topology-centric.
