Summary

Overview

  • Speaker: Lauren Tan
  • Channel: AI Engineer
  • Main topic: Building trust and velocity in AI-assisted coding and agentic software engineering
  • Purpose: To demonstrate how software engineers can establish robust foundations, verification pipelines, and architectural constraints to trust AI agents and achieve unprecedented development velocity. Lauren Tan (poteto) explores how software engineering has evolved with AI agents, moving from low-trust human-verified loops to high-trust autonomous loops. Drawing on experience shipping thousands of PRs at SpaceXSI, she introduces the 'potato pyramid' framework—prioritizing codebase design, static analysis, verification, prose, and human review—to turn AI-generated 'slop' into high-quality code. She demonstrates how enforcing strict lints, directory structures, and verification artifacts allows teams to scale velocity without sacrificing code quality.

Key Points

The meta of software engineering has shifted

  • Explanation: Software engineering is no longer about writing code slowly; it is about maintaining and improving code quality while massively increasing productivity through AI agents.
  • Evidence: Shipping 3,000+ PRs to production per month with stable or decreasing revert rates.
  • Practical implication: Engineers must build systems and guardrails rather than manually reviewing every line of code.

Code is the primary memory and input for agents

  • Explanation: Because agents generate output based on input code, messy codebases result in agentic slop spreading rapidly.
  • Evidence: Workarounds and anti-patterns get copied by subsequent agent runs.
  • Practical implication: Invest in codebase cleanliness, lint rules, and architectural guardrails before giving agents autonomy.

Comments and quick fixes are liabilities

  • Explanation: Agents love using imperative timers and writing unsolicited markdown explanations to justify hacks, leading to perf degradation.
  • Evidence: Cursor plugins reducing thousands of unnecessary timers and comments by enforcing strict lints.
  • Practical implication: Ban comments and temporary hacks; require agents to fix root causes.

Verification is the highest-leverage investment

  • Explanation: Moving from human review of raw code to verification artifacts (videos, screenshots, statecharts, formal proofs) scales trust.
  • Evidence: 70% of daily token spend going into verification patches rather than raw creation.
  • Practical implication: Invest heavily in runtime and formal verification tooling for agents.

Frameworks, Models & Processes

The Potato Pyramid

  • How it works: An inverse pyramid guiding where to allocate trust and engineering effort when building environments for AI agents.
  • Components:
    • codebase (good API design, architecture, refactoring)
    • static analysis (linters, type systems, compilers)
    • verification (runtime and formal verification)
    • prose (rules, skills, agent.md)

  • When to use: When setting up or refactoring an agentic software development environment.

Dune Client Framework

  • How it works: An Electron app framework designed with strict architectural constraints and lint rules tailored for agentic coding.
  • Components:
    • one folder per feature
    • strict import bans between threads
    • no comments in code
    • restricted API usage (banning useEffect)
  • When to use: When building desktop applications with AI coding agents.

Core insights

[O]Mental Modelmedium noveltymoderate evidence

The codebase itself is the dominant input to agent behavior — 'code is memory' — so any anti-pattern, workaround, or duplicated hack left in the tree gets replicated by every subsequent agent run, compounding like weeds. Quality of agent output is therefore a function of prior repository hygiene, not of the prompt.

Why it matters

It relocates the primary lever for agent reliability from prompting/context windows to repository curation. Cleanup of bad patterns becomes a precondition for autonomy rather than periodic maintenance, and every merged shortcut is a future multiplier of the shortcut.

Generalization

For any generative system conditioned on an in-domain corpus (RAG over internal docs, few-shot from repo code, retrieval over past tickets), the corpus is a latent policy: contamination propagates multiplicatively with usage volume, so corpus hygiene is a first-class reliability control.

[M]Mechanismhigh noveltymoderate evidence

API 'nuance' is the concrete failure surface for agents: constructs with implicit semantics (e.g., useEffect-style effect ordering) are the ones agents misuse, so the fix is to delete the expressive surface rather than to instruct around it. Banning such constructs in product code and replacing them with unambiguous framework APIs converts a class of judgment errors into compile/lint-time impossibility.

Why it matters

It gives a tractable criterion for API design under agent authorship: minimize constructs whose correct use requires unstated context. It also makes agent capability a property of the API surface, not of model quality — you can raise agent reliability without changing models.

Generalization

Wherever a consumer (human or model) lacks ambient context, expressiveness that requires ambient context should be removed. Applies to tool schemas, DSLs, and internal SDKs exposed to agents: prefer few, explicit, checkable operations over general primitives.

[P]Practicehigh noveltymoderate evidence

The review boundary is moving from raw diffs to verification artifacts (screenshots, snapshots, statecharts, formal proofs), with human reviewers evaluating evidence instead of lines. Reported spend pattern: ~70% of daily token spend goes to verification patches rather than creation.

Why it matters

It redefines the human's role as an evidence auditor and redefines the agent harness deliverable as proof-of-behavior, not code. It also implies budget allocation shifts: generation is cheap, verification is the dominant cost center, so tooling investment should follow that ratio.

Generalization

As generation cost falls relative to validation cost, the bottleneck artifact in any AI pipeline becomes the evidence bundle. Systems should be designed to emit machine-checkable evidence alongside output (traces, diffs of state, property test results) rather than requiring downstream inspection of the output itself.

[O]Mental Modelmedium noveltymoderate evidence

The 'potato pyramid' inverts where engineering effort belongs: deterministic layers (codebase design, architecture/refactoring, static analysis, type systems, compilers) form the base; verification sits above them; prose (rules, skills, agent.md) is near the top; human review is smallest. Prompt-level instructions are the weakest and least durable control.

Why it matters

It provides an explicit priority ordering for investment, and it directly contradicts the common default of iterating on prompts/instructions when agents misbehave. It says: if an instruction is load-bearing, mechanize it into the type system or a lint instead.

Generalization

Control mechanisms should be ranked by determinism and enforcement strength — compile-time > static analysis > runtime check > written instruction. Any rule that matters repeatedly should be escalated down the stack until it fails the build.

Source video ↗
[A]Architecturemedium noveltymoderate evidence

Directory structure plus dependency-graph analysis can categorically eliminate whole bug classes (e.g., renderer/main import bans in Electron), rather than catching individual instances. Structural boundaries become the enforcement unit, not behavioral tests.

Why it matters

It frames architecture as a security/correctness boundary that a model cannot reason its way past. Bans on cross-boundary imports are cheap to check, have no false negatives for the targeted class, and require no semantic understanding of agent intent.

Generalization

In agent-authored codebases, the cheapest reliable guardrails are graph-level invariants over module boundaries (allowed edges, allowed layers), because they're decidable, fast, and independent of what the model 'meant'.

[!]Failure Modehigh noveltyweak evidence

Agents use prose as an escape hatch: they write comments and markdown justifications for hacks and use imperative timers, which degrades performance. Banning ~99% of comments and enforcing lints against such patterns removes the justification channel and forces root-cause fixes — reportedly eliminating thousands of unnecessary timers and comments.

Why it matters

It identifies a specific, observable pathology (self-justifying artifact generation) and a blunt countermeasure. It also predicts an operational signal: rising comment volume and ad-hoc timing primitives are leading indicators of agent-generated debt.

Generalization

Generative agents will produce plausible rationalizations that make defective output harder to reject; when an output channel exists only for justification, removing the channel improves outcomes more than policing its contents.

Source video ↗
[M]Mechanismhigh noveltymoderate evidence

Verification is being built as agent-facing tooling rather than human-facing tooling: CLI-accessible runtime probes (app aria-accessible-name, app snapshot, app screenshot), feature maps, statechart-based UI property testing (Bombadil), and formal methods (TLA+ for model checking, Lean for proving algorithms and virtualization libraries).

Why it matters

It implies agents need first-class, scriptable observability of running systems — not just tests — to close their own loop. Property-based/statechart testing is the natural fit because agent output is stochastic; model checking and proofs cover concurrency and algorithmic invariants that tests sample poorly.

Generalization

Agent harnesses should expose the running system's state through narrow, idempotent CLI verbs plus property-based oracles, so the agent can self-verify without a human decoding logs. Formal methods become viable where the agent bears the proof-writing cost.

Propagation Bench

beyond-evals

A seeded anti-pattern replicates at a measurably higher rate in each successive agent run over the same repository, and introducing a build-failing lint against it reduces the replication rate to near zero without reducing task throughput.

Proof of concept

Build a synthetic repository with 5 seeded anti-patterns (duplicated logic, ad-hoc timer, workaround shim, dead abstraction, copy-pasted helper). Run N sequential agent tasks per arm — baseline vs lint-banned — and auto-detect replication of each seeded pattern in resulting diffs.

Measurement

Replications per seeded pattern per run generation; growth curve shape (linear vs multiplicative); delta between lint and no-lint arms; task completion rate and wall-clock cost held constant across arms.

Source video ↗

Evidence Gate

gatehouse

Requiring a machine-checkable verification artifact (snapshot, screenshot, replayable trace, or invariant check) on every agent-authored PR reduces escaped-defect rate at constant PR volume compared with diff-only review, but only for defect classes the artifact set covers.

Proof of concept

A PR gate plus reviewer UI: the bot refuses merge without an attached evidence bundle and renders the artifact for audit rather than the raw diff. Backfill against a historical PR sample to estimate what the gate would have caught.

Measurement

Escaped-defect rate and time-to-detection before/after; reviewer minutes per PR; fraction of artifact bundles that fail to cover the claimed behavior change (coverage gap rate).

Source video ↗

Rule Yield Ledger

gatehouse

Defects prevented per lint rule decays with rule count while exception annotations grow superlinearly past a threshold, so beyond that point additional rules cost more in maintenance and coordination than the defect classes they remove.

Proof of concept

Instrument a repository's lint configuration and PR history: for each rule, count blocked violations that would plausibly have shipped, plus inline exception annotations and false-positive suppressions. Plot yield and cost against rule index over time.

Measurement

Defects prevented per rule; maintenance hours and exception-annotation count per rule; false-positive rate; identification of the rule count at which exception annotations begin growing superlinearly.

Architectural implications

4

The review artifact changes from a diff to an evidence bundle (screenshot, snapshot, statechart, proof).

Before

Human reviewers read line-by-line diffs and infer runtime behavior mentally.

After

Agents attach verification artifacts; reviewers audit whether the evidence covers the claimed behavior.

Consequence

The harness must produce evidence as a build output, which pushes observability/screenshot tooling into the agent toolchain and makes 'no artifact, no merge' a policy gate.

Source video ↗

Enforcement responsibility migrates from written instructions to compiler/lint/dependency-graph layers.

Before

Rules live in prompts, agent.md, and reviewer memory; violations are caught socially.

After

Rules are encoded as API bans, import bans, and graph invariants that fail the build.

Consequence

Agent configuration files shrink; the type system and lint config become the real alignment spec, and rule changes become code-reviewed infrastructure changes with tests.

Source video ↗

Repository structure becomes a control surface with correctness semantics.

Before

Directory layout is a convention for human navigation.

After

Directory layering encodes allowed dependency edges, mechanically preventing entire failure classes.

Consequence

Refactoring and boundary design become reliability work with measurable payoff, and new directories require an explicit edge policy, raising the cost of ad-hoc structure.

Source video ↗

Agents require the running application to be instrumented and scriptable.

Before

Verification is a human looking at the app or reading test output.

After

The app exposes narrow CLI verbs (snapshot, screenshot, accessible-name) that agents invoke to close their own loop.

Consequence

Applications need an agent-facing control/observation API distinct from the end-user UI, with its own stability and security considerations (what an autonomous agent is allowed to invoke).

Tradeoffs and failure modes

4

Banning comments to remove the justification escape hatch

Benefit

Eliminates agents' ability to argue a hack into acceptance, and reportedly removed thousands of unnecessary comments and timers.

Cost or risk

Removes the channel for durable rationale ('why', invariants, non-obvious constraints), so intent must be re-encoded in names, types, and structure — or it is lost and re-litigated by future agent runs.

Source video ↗

Deep upfront investment in design and static analysis before granting autonomy

Benefit

Enables high-volume autonomy: shipping 3,000+ PRs per month with stable or decreasing revert rates.

Cost or risk

The investment is front-loaded and yields nothing until the pyramid base exists; it also presumes a codebase amenable to refactoring and strong static tooling, which is not universal.

Source video ↗

Replacing code review with verification-artifact review

Benefit

Shifts review from expensive manual line-reading to fast, checkable evidence, which is what makes high PR volume tractable.

Cost or risk

Trust is transferred to the coverage completeness of the artifacts; behavior not captured by the artifact set can be invisibly wrong, and artifacts are proxies rather than proofs of correctness.

Source video ↗

Categorical structural bans (e.g., renderer/main import bans, useEffect ban)

Benefit

Eliminates entire bug classes with a decidable check that does not depend on interpreting agent intent.

Cost or risk

Banned constructs may be the right tool in edge cases; the ban and its documented exceptions become their own maintenance surface and a coordination point every new use must negotiate.
