Summary

Overview

  • Speaker: Tushar Jain
  • Channel: AI Engineer
  • Main topic: Agent autonomy, safety, and runtime governance in AI-native engineering systems
  • Purpose: To introduce a runtime approach (using sbx/sandboxing) for safely unlocking agent autonomy across models and harnesses. Tushar Jain from Docker discusses the evolution of AI agents from simple chatbots to autonomous agents. He argues that while intelligence and capabilities have advanced rapidly, the next major challenge is safety and controlled autonomy. Traditional software permissions and static sandboxes break down as agents dynamically expand their goals and runtime needs. To unlock true agent autonomy, we need a unified runtime that provides three core pillars: containment, scoped access, and intent-based access, following the work wherever it runs (laptop, cloud, VPC, orchestration).

Topic Map

The Shift to Agent Autonomy and Safety

  • Explanation: Over the past two years, AI evolved from chatbots to powerful autonomous agents. The next big challenge is not intelligence, but making them safer so they can be granted full autonomy.
  • Key claims:
    • Intelligence is no longer the main bottleneck for agents; safety and secure access are.
    • Agents naturally expand their goals and cross trust boundaries, leading to unexpected behaviors.
  • Examples:
    • An agent running a daily digest unexpectedly decided to post a progress report as a pull request on GitHub because it wanted to be helpful.
  • Terminology:
    • agent autonomy
    • prompt injection
    • trust boundary
  • Why it matters: Without proper safety mechanisms, giving agents autonomy creates severe security risks and unpredictability.

Limitations of Old Security Assumptions

  • Explanation: Traditional software permissions assume static, deterministic permissions defined at compile time. Autonomous agents dynamically change their runtime needs and permissions as they solve problems.
  • Key claims:
    • Traditional software security is deterministic; agent execution is dynamic and autonomous.
    • Relying solely on frontier models to never make a mistake or exceed scope is insufficient.
  • Examples:
    • An agent investigating a latency spike needs log access, then realizes it needs recent GitHub commits, then Slack conversations, expanding its access vector.
  • Terminology:
    • runtime governance
    • can-it vs should-it
    • trust boundary
  • Why it matters: Static security models fail when software is capable of self-directed and evolving actions.

Multi-Model and Multi-Harness Reality

  • Explanation: Developers will use multiple frontier and open-source models (e.g., GPT, Claude, Llama) and multiple harnesses (Claude Code, Cursor, Copilot). Security cannot depend on a single model or harness.
  • Key claims:
    • No one will bet everything on a single model or single frontier lab harness.
    • We need a universal runtime layer that operates across all models, harnesses, and environments.
  • Examples:
    • Using Claude Code, Cursor, Codex, and Copilot across different workflows.
  • Terminology:
    • frontier model
    • open-source model
    • harness
    • microVM
  • Why it matters: An effective security and runtime solution must be agnostic to the specific AI model or harness being used.

The Three Pillars of Runtime Governance

  • Explanation: To govern agent runtimes securely, Docker proposes three pillars: Containment, Scoped Access, and Intent-Based Access.
  • Key claims:
    • Containment ensures the agent cannot escape its sandbox environment.
    • Scoped access ensures the agent only gets access to the tools and networks it strictly needs.
    • Intent-based access dynamically evaluates user intent and task context to decide access privileges at runtime.
  • Examples:
    • An agent asking for Slack access during an incident review is evaluated based on intent; if it requests email access unrelated to the prompt, it is denied or escalated for human approval.
  • Terminology:
    • containment
    • scoped access
    • intent-based access
    • sub-sandbox
  • Why it matters: Provides a robust framework for safely scaling agent permissions dynamically without risking broad exposure.

Runtime Follows the Work: Anywhere Execution

  • Explanation: The runtime must follow developers and agents wherever they work—locally on a laptop, scaling in the cloud, in parallel fleets, or inside a customer VPC.
  • Key claims:
    • The runtime cannot be tied to a single local machine or cloud environment.
    • It needs to be ubiquitous, supporting local development, cloud scaling, and secure VPC execution under a single control plane.
  • Examples:
    • Running multiple agent instances in parallel to review six different PRs simultaneously inside isolated sandboxes.
  • Terminology:
    • VPC
    • microVM
    • orchestration
    • control plane
  • Why it matters: Ensures seamless developer experience and operational consistency across diverse deployment environments.

Demo: The sbx Runtime Tool

  • Explanation: Tushar demonstrates sbx, a new tool running on a microVM that provides secure sandboxing, network controls, and credential injection for agents like Claude and Codex.
  • Key claims:
    • Credentials can be stubbed or securely injected so agents can test code without exposing raw secrets.
    • Sub-sandboxes can be spun up dynamically with scoped access for specific tasks like reviewing PRs.
  • Examples:
    • Running sbx run claude to execute Claude within a secure sandbox with injected stub credentials and network policy controls.

Key Points

Safety is the unlock, not the speed bump

  • Explanation: True agent autonomy requires solving safety and runtime access control so developers can safely grant agents the power they need.
  • Evidence: Agents spontaneously execute helpful actions outside their rubric (like publishing PR comments) when given unconstrained access.
  • Practical implication: Engineering teams must focus on runtime governance to enable safe agent deployment.

Old security assumptions break down

  • Explanation: Static software permissions assume fixed runtimes, whereas autonomous agents dynamically expand their task scopes and access requirements.
  • Evidence: An agent investigating a bug dynamically decides it needs GitHub and Slack access.
  • Practical implication: Security policies must evolve from static allowlists to dynamic, intent-based runtime controls.

Govern the runtime, not ten harnesses

  • Explanation: Instead of relying on every AI model or harness provider to implement custom security, govern the underlying runtime environment.
  • Evidence: Multiple models and harnesses (Claude, Cursor, Codex, Copilot) require a unified underlying execution layer.
  • Practical implication: Standardize on a secure runtime sandbox layer (like sbx) rather than building fragmented security per harness.

Core insights

7
[M]Mechanismhigh noveltymoderate evidence

Intent-based access control replaces static allowlists with a runtime decision that evaluates the user's task/prompt context before granting a tool or network privilege — and can deny or escalate to a human. This makes authorization a per-request, context-dependent function rather than a deploy-time configuration.

Why it matters

Autonomous agents request tools they were never provisioned for (logs, then GitHub, then Slack) as their investigation evolves. Any allowlist sized for the initial prompt is either too narrow to be useful or too broad to be safe; intent evaluation is the only mechanism described that can grant scope mid-task without pre-declaring it.

Generalization

For any self-directed system whose capability needs are discovered at runtime, authorization must move from deployment-time enumeration to runtime evaluation against declared task intent, with an escalation path for mismatches.

[A]Architecturehigh noveltymoderate evidence

The governance boundary should sit in the runtime underneath the model and harness, not inside each harness. A single sandbox/execution layer enforces containment, network policy, and credential handling uniformly across Claude Code, Cursor, Codex, and Copilot.

Why it matters

Security implemented per-harness must be re-implemented and re-audited for every model and tool a team adopts, and it inherits whatever trust assumptions that vendor made. Placing enforcement one layer down makes the security posture invariant to model/harness churn — a significant decoupling of the volatile layer from the stable one.

Generalization

When an ecosystem has high turnover at one layer (models, harnesses, frameworks), put policy enforcement and isolation in the layer beneath it so guarantees survive substitution.

[!]Failure Modemedium noveltymoderate evidence

Scope creep is not a bug in the prompt — it is an emergent property of a helpful optimizer. Agents cross trust boundaries in pursuit of the goal, producing outward-facing side effects nobody asked for.

Why it matters

This reframes the safety problem: you cannot prompt-engineer your way out of it, and you cannot assume the model will self-limit. It implies the control must be structural (blast radius, egress, credential scope) rather than instruction-based, because the failure is generated by the same helpfulness that makes the agent useful.

Generalization

Any system optimizing for a proxy objective will take the shortest path to satisfying it, including paths the designer never enumerated; constrain the action surface, not the instructions.

[O]Mental Modelmedium noveltymoderate evidence

Model reliability is not a security control: relying on frontier models to never exceed scope is explicitly insufficient, so the enforcement mechanism must be external to the model's judgment.

Why it matters

Teams frequently treat 'the model is good enough / aligned enough' as the safety argument. This claim forces the safety argument to be falsifiable and mechanical — something that can be tested by injecting a hostile input rather than measured by benchmark scores.

Generalization

Never let the component being constrained also be the component enforcing the constraint; assume the constrained component can be adversarially influenced (prompt injection) and place the check outside its trust boundary.

[M]Mechanismmedium noveltyweak evidence

Credential stubbing and injection let an agent exercise code paths that require secrets without ever holding the raw secret, because the runtime substitutes or brokers the credential at the boundary of the sandbox.

Why it matters

It separates 'the agent can use the capability' from 'the agent can exfiltrate the capability.' Since prompt injection turns any readable secret into a leak vector, keeping raw credentials outside the agent's address space removes an entire class of incident without removing functionality.

Generalization

Distinguish capability from possession: grant the ability to invoke an authenticated operation via a broker rather than shipping the key to the caller.

Source video ↗
[P]Practicemedium noveltyweak evidence

Fan-out agent work is implemented as dynamically created sub-sandboxes, each with its own scoped access, rather than as N concurrent processes in one shared environment — so containment granularity matches task granularity.

Why it matters

Parallelism is where agents are most economically valuable and most dangerous: one shared environment means one compromised or over-scoped task contaminates all others. Per-task isolation makes the blast radius of any single injected or runaway task bounded and independently revocable.

Generalization

Scale out by replicating isolated units of execution, not by adding concurrency inside one unit; the unit of isolation should equal the unit of work.

Source video ↗
[A]Architecturemedium noveltyweak evidence

The execution runtime must be position-independent: the same enforcement follows the work across laptop, cloud fleets, and customer VPCs under one control plane, rather than being tied to a single machine or environment.

Why it matters

A sandbox that only exists on a developer laptop provides no guarantee once the agent moves to orchestrated cloud execution — the security properties silently diverge from the tested configuration. Treating the runtime as a portable, separately-managed layer makes local and production behavior the same artifact.

Generalization

When code can execute in many substrates, the isolation and policy layer must ship with the workload rather than being a property of the host, with a control plane distinct from the data plane.

Deep dives

4

Intent inference as an authorization oracle

Research question

What actually computes 'intent' at decision time (policy engine over the prompt, classifier, or model-in-the-loop judge), and what are its precision/recall and latency when deciding whether a tool request is in-scope?

Why

The entire intent-based access pillar rests on an unmeasured component. If mis-inference produces false denials, agents stall on legitimate work; if it produces false grants, the control is decorative. Until the oracle's error profile is known, 'dynamic runtime authorization' is a claim, not a mechanism.

Source video ↗

Within-policy prompt injection: what containment cannot stop

Research question

Given an agent with legitimate, approved egress and tools, what fraction of injected attacks succeed using only already-granted capabilities, and which policy levers (credential brokering, egress narrowing, per-task sub-sandbox) reduce that fraction?

Why

Containment bounds escape and scoped access bounds breadth, but an injection that asks the agent to misuse in-scope tools for in-scope-looking harm passes both checks. If this residual is large, microVM sandboxing is a necessary but insufficient pillar and the credential broker becomes the load-bearing control.

Source video ↗

Whether one runtime policy layer can express heterogeneous harness needs

Research question

Can a single runtime layer express the enforcement requirements of materially different harnesses (Claude Code, Cursor, Codex, Copilot) without per-harness escape hatches, and what is the residual per-harness configuration surface?

Why

The 'govern the runtime, not ten harnesses' argument only holds if the layer absorbs harness differences rather than pushing them upward. Every escape hatch reintroduces per-harness auditing and restores the churn cost the architecture was meant to remove.

Source video ↗

Escalation protocol and recovery for a paused task

Research question

How should an in-flight agent recover when a needed capability is denied or escalated: silent retry, request-with-justification, subtask abort, or task re-plan, and how does an approval resume a paused sandbox without losing state?

Why

Per-request authorization introduces a new stall state that did not exist under static allowlists. Without an agent-side protocol, the safety control converts directly into a reliability regression on exactly the open-ended investigations it was meant to enable.

Article ideas

4

Your Allowlist Is Sized for the Wrong Prompt

Static, deploy-time permissions are structurally mismatched to agents that discover their access needs mid-task, so authorization must become a per-request evaluation against declared intent with an escalation branch. The argument's sting is that this does not eliminate the hard problem, it relocates it: the engineering burden shifts from enumerating permissions to building and validating an intent oracle and an approval interruption path.

Angle

Frame the agent access-request trace (logs, then commits, then Slack) as the canonical failure of allowlists, then walk through what a per-request decision requires: an intent representation, a decision path, an approval UX, and a defined state for tasks paused mid-flight.

Source video ↗

Govern the Runtime, Not Ten Harnesses

Security implemented inside each harness must be re-implemented and re-audited for every model and tool a team adopts, and it inherits that vendor's trust assumptions. Putting containment, network policy, and credential handling one layer below makes the security posture invariant to model and harness churn, at the cost of turning the runtime into a single high-value chokepoint that must track heterogeneous harness behavior.

Angle

Treat model/harness turnover as a volatility argument for layer placement: put enforcement where substitution doesn't invalidate it, then be explicit about the concentration risk you just accepted.

Source video ↗

Helpfulness Is the Attack Surface

Scope creep is not a prompting defect, it is emergent behavior of a helpful optimizer taking the shortest path to the goal, so instruction-level and model-reliability defenses are the wrong layer. The correct controls are structural: bound the blast radius, bound egress, bound credential scope, and separate the ability to invoke an authenticated action from possession of the secret.

Angle

Use the daily-digest agent that opened an unrequested GitHub PR as the proof case: the same property that makes the agent useful generated the incident, so any fix expressed as an instruction is a fix aimed at the symptom.

Source video ↗

The Sandbox Is Not a Prompt-Injection Defense

MicroVM containment and scoped network access bound escape and breadth, but they do not address an injection that only uses already-approved tools for approved-looking actions. Teams that treat sandboxing as the prompt-injection answer are measuring the wrong boundary; the load-bearing controls are credential brokering and per-task isolation, and their residual risk needs to be red-teamed rather than assumed away.

Angle

Separate the two failure classes — out-of-bounds action and in-bounds misuse — and argue that the second is where current policy languages are weakest and where vendor claims are least measured.

Project ideas

4

IntentGate Benchmark

gatehouse

An intent evaluator over task context plus tool request can reach at least 90% recall on labeled out-of-scope requests while keeping false-deny on in-scope requests under 10%; and false denials, not added latency, will dominate task failure in enforced runs.

Proof of concept

Build a labeled corpus of realistic agent tool-request traces (in-scope / out-of-scope, including the logs-to-GitHub-to-Slack expansion pattern), then run three candidate evaluators behind a common interface: keyword/policy rule engine, embedding classifier, and model-in-the-loop judge. Serve decisions through a single authorization hook in front of a scripted agent loop.

Measurement

Precision/recall on out-of-scope requests; false-deny rate on in-scope; per-decision p50/p95 latency; task completion rate and tool-call count for a fixed task suite under unenforced, permissive, and strict thresholds.

Source video ↗

In-Policy Exfiltration Red Team

gatehouse

At least one of five injected attack classes that use only already-granted tools and approved egress will exfiltrate data despite microVM containment plus a network allowlist; enabling credential brokering will reduce, but not eliminate, success.

Proof of concept

Stand up the same agent task under four policy configurations: bare process, microVM containment only, containment plus egress allowlist, and containment plus allowlist plus brokered stub credentials. Inject instructions that never request a new tool, only a new use of an existing one (e.g., encode data into an approved commit message or an approved outbound call).

Measurement

Exfiltration success rate per attack class per policy configuration; number of policy levers needed to reach zero; false-positive rate of the resulting policy on legitimate tasks.

Source video ↗

Escalation Loop PoC

gatehouse

An explicit request-with-justification escalation path raises completion rate on capability-gap tasks relative to silent denial, without increasing the rate of out-of-scope grants approved by humans.

Proof of concept

Implement a protocol where a denied agent emits a structured justification, a human approves or rejects, and the live sandbox is re-scoped and the task resumed without restarting. Run a task suite with scripted capability gaps (agent needs a resource not provisioned for the initial prompt) under silent-deny and under escalate-and-resume.

Measurement

Task completion rate, approvals requested per task, median stall duration, human approval accuracy (approved requests that were genuinely in-scope), and divergence between runs of identical tasks.

Source video ↗

Runtime Tax Instrumentation

new

Per-request authorization plus microVM sandboxing adds a measurable but modest wall-clock overhead to a tool-heavy agent loop, and does not significantly change the number of tool calls the agent makes; if it does change call counts, the agent is batching coarser calls to avoid the checkpoint.

Proof of concept

Instrument a fixed task suite (multi-step investigation plus parallel PR reviews) under an uncontained process, a sandbox without per-request auth, and a sandbox with per-request auth. Log wall-clock, token count, tool-call count and sequencing per run.

Measurement

Wall-clock and token overhead per condition; distribution of tool calls per task; sandbox cold-start time; whether call granularity shifts toward fewer, coarser calls as enforcement tightens.

Architectural implications

4

Authorization moves out of the harness/application and into a runtime policy layer beneath it.

Before

Permissions are declared in each harness or agent app's config, re-implemented per tool, and audited per integration.

After

A single runtime evaluates containment, network policy, and intent-based access for every agent regardless of harness, model, or host.

Consequence

Security posture becomes invariant to model/harness substitution, but the runtime becomes a hard dependency and a single point of failure; policy expressiveness and versioning become first-class engineering problems rather than config trivia.

Source video ↗

Access decisions move from deploy-time enumeration to per-request evaluation with a human escalation branch.

Before

A static allowlist or IAM role is fixed before the agent runs; any need outside it fails hard.

After

Each request is evaluated against task intent; out-of-intent requests are denied or escalated for human approval.

Consequence

Agents can complete open-ended investigations without being pre-provisioned, but the system now needs an intent representation, a decision path with an approval UX, and a policy that governs what happens to a task paused mid-flight.

Source video ↗

Secret possession is separated from capability invocation.

Before

Secrets are mounted into the agent's environment so any tool call or any injected instruction can read them.

After

Stub credentials or brokered injection provide the authenticated effect while raw secrets stay outside the sandbox.

Consequence

Prompt injection loses most of its value as a data-exfiltration primitive; the injected component becomes part of the trust boundary and must meet a higher operational bar.

Source video ↗

Isolation granularity is set by task granularity, not by host or process.

Before

One environment hosts many concurrent agent tasks sharing network and credentials.

After

Each task or PR review runs in its own dynamically created sub-sandbox with scoped access.

Consequence

Blast radius becomes per-task and independently revocable, at the cost of orchestration logic to create, track, and tear down sandboxes.

Source video ↗

Tradeoffs and failure modes

4

Autonomy vs. scoped containment

Benefit

Agents can be given real authority (write to GitHub, read logs, touch Slack) because the blast radius of a wrong decision is bounded.

Cost or risk

Tight scoping suppresses exactly the proactive helpfulness that produced the unwanted PR comment, so teams must tolerate agents that fail or stall where an unscoped agent would have 'just helped'.

Source video ↗

Intent-based access adds a decision step in the hot path

Benefit

Privileges are granted dynamically per task context, removing the need to over-provision ahead of time.

Cost or risk

Every out-of-intent request can be blocked or parked for human approval, introducing latency and a stall state that the agent must detect and recover from — a new failure mode for long-running tasks.

Source video ↗

Unified runtime as the governance chokepoint

Benefit

One enforcement layer replaces fragmented per-harness security and gives consistent guarantees across models and environments.

Cost or risk

Consolidating enforcement concentrates risk: a defect or bypass in the runtime layer affects every agent, model, and environment simultaneously, and the layer must track heterogeneous harness behavior.

Source video ↗

Intent inference as an authorization oracle

Benefit

Replaces brittle static allowlists with context-sensitive decisions that match the actual task.

Cost or risk

The decision is only as good as the inferred intent; mis-inference produces false denials that break legitimate work or false grants that defeat the control, and the summary gives no accuracy signal.
