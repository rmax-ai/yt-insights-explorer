Overview

  • Main topic: Building and running multi-player AI-native war rooms for legacy code modernization at GEICO using FleetKit.
  • Purpose: To share GEICO's practical experiment and framework (FleetKit and multi-player AI-native war rooms) for modernizing legacy codebases with AI agents while keeping human engineers focused on major work. Ford Prior from GEICO discusses how their claims engineering group tackled modernizing millions of lines of legacy code using an AI-native multi-player war room setup called FleetKit. With a budget of $1,000 in AI tokens and one day, they successfully mapped legacy domains, proposed agent-callable APIs, and shipped changes to UAT, proving that breaking free of the outer loop via multi-player AI war rooms can drastically accelerate software delivery.

Core insights

[O]Mental Modelmedium noveltymoderate evidence

The binding constraint on delivery is the outer loop (system context, ownership, dependencies, intent, review, deploy), not coding speed — and agent fleets must be aimed at that outer loop rather than at the inner-loop edit cycle where genAI already produced gains.

Why it matters

It relocates where an agentic system's value budget should be spent: on context acquisition, ownership mapping, and review/deploy coordination, not on code generation throughput. A team optimizing token spend on autocomplete-level tasks is optimizing the already-fast part.

Generalization

For any agentic software system, measure where wall-clock time actually goes end-to-end before choosing which stage to automate; the highest-leverage agent work is usually in the unglamorous coordination stages.

[A]Architecturehigh noveltymoderate evidence

FleetKit encodes the multi-agent orchestration in a markdown-based rule/protocol layer plus MCP servers, with an explicit phase split: leader agents do research, a human-in-the-loop queue gates approval, then builder agents execute. The orchestration policy lives in reviewable text artifacts, not in bespoke framework code.

Why it matters

Rules-as-markdown makes agent behavior diffable, reviewable, and editable by the humans who own the domain, while MCP servers keep tool access as a separate, reusable substrate. It decouples policy (who may do what, in what order) from capability (what tools exist).

Generalization

Separate agent policy/process definition (versioned natural-language rule packs) from agent capability (tool servers) so process changes don't require redeploying orchestration code and domain experts can review the policy directly.

[M]Mechanismmedium noveltymoderate evidence

Human approval is modeled as a first-class queueing primitive positioned between the research phase and the build phase, rather than as a review step after generation.

Why it matters

Placing the gate before expensive build work changes the cost profile: humans reject bad plans before tokens are spent executing them, and the queue becomes an observable, loadable runtime component with its own latency and backlog characteristics.

Generalization

In long-running agent workflows, insert human gates at the cheapest irreversible-decision boundary (plan approval) rather than at output review, and treat the gate as a queue with measurable throughput.

[P]Practicemedium noveltymoderate evidence

The war room is a joint human-agent role decomposition, not just an agent topology: decision-makers, drivers, and SMEs are assigned alongside agent fleets across channels, design studios, repos, and the agent automation suite.

Why it matters

Most multi-agent designs specify only agent roles and leave the human attentional structure implicit, which produces undefined handoffs. Making human roles explicit turns the system into a schedulable organization where human attention is the scarce resource being allocated.

Generalization

Design multi-agent systems by co-specifying human roles and agent roles with explicit handoff artifacts and channels; the human attention budget is the real constraint to optimize around.

Human-in-the-loop approval queues as the real throughput ceiling in agent fleets

Research question

When a human approval gate is placed between research and build phases, does the approval queue's latency and rejection rate dominate end-to-end wall-clock time compared to agent execution time, and how does gate placement (pre-build plan approval vs. post-build output review) change total token cost per accepted change?

Why

The architecture makes human attention a runtime component with its own backlog. If the gate is the bottleneck, then investing in faster agents or cheaper models yields diminishing returns, and the engineering budget should shift to gate ergonomics, batch approval, and rejection-feedback loops. Without queue instrumentation, teams will misattribute slowness to models.

Prose-as-policy: markdown rule packs vs. compiled orchestration code

Research question

Do agent behaviors specified as versioned markdown rule packs achieve equal or better task consistency and defect rate than equivalent behaviors encoded in orchestration framework code, and how often do models misinterpret prose rules in ways that produce silent policy violations?

Why

Moving orchestration policy into natural-language artifacts buys human reviewability and no-deploy iteration but trades away compile-time guarantees. Quantifying the misinterpretation rate turns a philosophical tradeoff into a measurable engineering parameter, and determines whether rule packs need conformance tests or a linting layer.

Per-task-class model routing economics for legacy code work

Research question

Across pipeline stages (domain mapping, API proposal, code modification, plan synthesis), does a cheaper model tier match a flagship tier on cost-per-successful-outcome, and is the winning tier stable across codebases and task shapes or specific to the reported benchmark harness?

Why

A single global model choice is the default failure mode. If the cheap tier wins on bulk legacy reading and modification but loses on planning or API synthesis, then routing tables rather than model upgrades are the savings lever. The result reported is internally benchmarked and needs external replication to be trusted.

Article ideas

4

Your Agents Are Fast; Your Org Is Slow: Aim Agent Fleets at the Outer Loop

GenAI already collapsed inner-loop coding time, so additional agent capacity spent on generation is near-worthless; the measurable leverage is in outer-loop stages — context acquisition, ownership mapping, dependency discovery, intent capture, and review/deploy coordination. Teams should instrument end-to-end lead time first and then point their agent fleet at whichever outer-loop stage owns the largest share, and should expect human approval queues, not models, to be the residual bottleneck.

Angle

Reframe the familiar 'AI coding productivity' narrative as a budget-allocation problem: show the 75/25 engineer-bandwidth split, argue that automating the already-fast stage is optimizing the wrong variable, and give a procedure for locating the outer-loop stage worth automating.

Source video ↗

Put the Human Gate Before the Build, Not After the Diff

Human review placed after generation is the most expensive possible place for a human to say no. Positioning approval as a queued stage between research/planning and execution means rejections cost a plan instead of a build, but it converts machine parallelism into human serialization — so the approval queue becomes the system's actual throughput ceiling and must be treated as an instrumented service with time-to-approval, rejection rate, and invalidated-work metrics.

Angle

Architecture-with-economics: compare gate-before-build vs. review-after-generation cost profiles, and argue the gate should be designed as a loadable queue with measurable throughput rather than as an informal review habit.

Source video ↗

Rules in Markdown, Capability in Servers: Separating Agent Policy From Agent Tooling

Encoding multi-agent process — who may act, in what order, with what handoffs — as versioned markdown rule packs rather than orchestration framework code lets domain SMEs review and amend agent behavior directly and lets process change without a deploy; MCP servers keep tool capability a separate reusable substrate. The price is that interpretability replaces compile-time guarantees, so rule packs need conformance tests and violation telemetry to be trustworthy at scale.

Angle

A concrete decomposition pattern with its failure modes: policy layer (diffable prose), capability layer (tool servers), and the missing third layer — enforcement verification — that determines whether prose-as-policy is safe.

Source video ↗

Amplification, Not Repair: What Agent Fleets Actually Do to a Team

Agent fleets multiply whatever process quality already exists, so adopting them on a team with unresolved ownership, dependency, and intent ambiguity accelerates existing dysfunction rather than fixing it. The corollary is that the deliverable of a first war-room run should be judged on whether it produced durable shared understanding — a domain map, a proposed API boundary, named owners — and not on diff volume shipped.

Angle

Contrarian adoption argument: use the amplification claim as a diagnostic, propose a pre-flight process-health check before standing up an agent fleet, and redefine 'success' for a first mission around artifacts that reduce outer-loop ambiguity.

Project ideas

4

GateBench: Measuring the Human Gate, Not the Agent

gatehouse

In a leader/builder agent pipeline, end-to-end wall-clock time is dominated by human approval-queue latency and rejection-driven rework rather than by agent execution or token throughput; moving the gate from post-build review to pre-build plan approval reduces total token cost per accepted change by a measurable margin at equal or better change quality.

Proof of concept

Build a two-variant harness over a small legacy repo: variant A runs research → build → human review on generated diffs; variant B runs research → human plan approval → build. Instrument both with time-to-approval, rejection rate, tokens spent per rejected plan, tokens spent per accepted change, and builder work invalidated per rejection.

Measurement

Tokens per accepted change, wall-clock breakdown by stage (agent vs. human queue), approval rejection rate, and fraction of build work discarded per rejection, across both variants on identical missions.

Source video ↗

RulePack Conformance Harness

beyond-evals

Markdown rule packs drive agent behavior with a measurable and bounded misinterpretation rate, and a lightweight conformance-test layer (canonical mission scenarios with expected policy outcomes) detects prose-policy violations that ad-hoc prompting would silently miss.

Proof of concept

Author a small rule pack (phase split, tool permissions, handoff artifacts), then run a suite of scenario probes that should trigger specific policy decisions. Compare violation rate against an equivalent ad-hoc prompt baseline on the same scenarios, and diff behavior after an edit to a single rule to see whether changes are local or produce cascading drift.

Measurement

Policy-violation rate per scenario suite, run-to-run behavioral variance, and blast radius (number of scenarios changing outcome) per single-rule edit, for rule-pack vs. ad-hoc-prompt conditions.

Source video ↗

TierRouter: Per-Stage Model Routing on Cost per Successful Outcome

beyond-evals

The cost-optimal model tier differs by pipeline stage — a cheaper tier matches a flagship on legacy code reading and bulk modification while the flagship retains an edge on domain mapping and API-surface synthesis — so a static per-stage routing table beats uniform flagship use on cost per successful outcome at no quality loss.

Proof of concept

Assemble a graded task set spanning four stages (code comprehension, bulk modification, domain mapping, API proposal) with field-match success criteria per stage. Run each stage under both tiers, log cost per request, and fit a small router that dispatches each stage to its cheapest non-inferior tier.

Measurement

Cost per successful outcome by stage and tier; quality delta per stage with confidence intervals on field-match success and downstream reviewer acceptance; total mission cost under routed vs. uniform-flagship deployment.

Source video ↗

MapScore: Grading Agent-Produced Domain Maps

new

Agent-produced legacy domain maps and proposed agent-callable API surfaces can be graded against SME-authored ground truth on coverage and correctness, and map quality score predicts downstream build success (approval rate of migration plans, defect escape rate) better than map size or detail does.

Proof of concept

Take one bounded legacy domain, have SMEs author a reference map (entry points, data dependencies, ownership boundaries, callable operations). Produce agent maps under several prompting/rule-pack conditions, score them differentially against the reference, then run builder agents on each map and track plan approval and defects to UAT.

Measurement

Coverage and correctness score versus SME ground truth; correlation between map score and downstream plan-approval rate, builder rework, and defect escape rate to UAT.

Architectural implications

4

Orchestration policy is expressed as markdown rules and protocols in a repository rather than as framework code.

Before

Agent workflows hard-coded in an orchestration framework, editable only by engineers who own the code.

After

Versioned, diffable natural-language rule packs that domain owners and SMEs can read and amend, paired with MCP servers for capability.

Consequence

Faster process iteration and better human review of agent behavior, at the cost of relying on the model to faithfully interpret prose rules — interpretability replaces compile-time guarantees.

Source video ↗

Human-in-the-loop approval is a queued stage in the pipeline between research and build.

Before

Human review happens at the end, on generated output or pull request.

After

Human approval gates the plan produced by research/leader agents before builder agents spend tokens.

Consequence

Cheaper rejection and a measurable human-attention bottleneck; the queue's throughput becomes the system's real throughput ceiling.

Source video ↗

Deliverables are agent-produced planning artifacts (domain maps, proposed agent-callable APIs) rather than only code diffs.

Before

Modernization produces code changes reviewed as patches.

After

Modernization produces a mapped domain and a proposed agent-callable API surface, green-lit by product and tech before execution.

Consequence

The API surface becomes the stable boundary agents operate against, which in turn makes legacy systems addressable by future agents — the mapping output is itself infrastructure.

Source video ↗

Model tier is selected per task class based on measured cost per successful outcome.

Before

A single frontier model used uniformly across all agent stages.

After

Task-class routing where cheaper tiers handle legacy code reading/modification and expensive tiers are reserved where they empirically add value.

Consequence

Requires maintaining an internal benchmark harness per task class; token cost becomes a tunable engineering parameter rather than a fixed budget line.

Tradeoffs and failure modes

5

Agent amplification of existing team dysfunction

Benefit

Structured agent fleets can multiply output of a well-run team dramatically under time and token constraints.

Cost or risk

The same machinery amplifies a poorly-run team's existing problems; process debt is not fixed by adding agents and may be accelerated.

Source video ↗

Human-in-the-loop gates as throughput limiters

Benefit

Gates catch bad plans before build-phase token spend and before irreversible changes.

Cost or risk

Every gate converts machine parallelism into human serialization; approval queues can become the dominant latency term in the pipeline.

Source video ↗

Cheaper-model parity on legacy code

Benefit

Large token savings on bulk legacy code modification work with no measured quality loss.

Cost or risk

The parity result is a vendor/product-specific benchmark on cost per request versus field match success rate; it may not transfer to other codebases, languages, or task shapes.

Source video ↗

Prompt cache economics at scale

Benefit

Fleet-style agents replay large rule packs and context repeatedly, which cache-friendly prompt structure can make affordable.

Cost or risk

Token cost behavior under sustained multi-agent fleet usage is unresolved by the team itself; the $1,000 one-day figure may not extrapolate to continuous operation.

Constrained-scope validation

Cost or risk

Success on one bounded domain in one day may not predict multi-team, multi-domain programs where dependency and ownership conflict dominate the outer loop.
