Overview

  • Purpose: To educate developers on designing richer, multimodal voice agent experiences beyond simple speech-to-speech chatbots. Charlie Guo from OpenAI's developer experience team explores the misconception that voice agents must exclusively talk back. He outlines three useful modes of voice interaction (speech-to-speech, speech-to-action, event-to-speech), explains why native audio models outperform traditional chained transcription pipelines in latency and preservation of nuance (tone, cadence, emotion), and introduces GPT-Realtime-2 with advanced reasoning and tool-calling capabilities.

Core insights

6
[O]Mental Modelmedium noveltymoderate evidence

Decouple the response channel from the input modality: a voice agent's reply does not have to be speech. The summary defines three composable modes — speech→speech, speech→action, and event→speech — which lets audio input drive tool calls, computer use, or outbound notifications instead of conversational turn-taking.

Why it matters

Most voice-agent stacks implicitly bind 'voice in' to 'voice out', which forces a TTS turn and a latency budget onto every interaction, including ones where an action (fill a field, click, call an API) is the correct response. Naming the three modes gives engineers an explicit design axis for what the agent emits.

Generalization

For any interface agent, separate the input channel, the reasoning step, and the output channel; output can be speech, UI mutation, tool invocation, or an async event. The same decoupling applies to text agents emitting UI events rather than chat messages.

Source video ↗
[A]Architecturemedium noveltymoderate evidence

Native audio models collapse the STT → LLM → TTS chain into a single streaming model, and the argument for doing so is not only latency: transcription is a lossy intermediate representation that discards tone, cadence, emotion, interruptions, and background noise before the reasoning model ever sees the input.

Why it matters

In a chained design the text transcript is the architectural bottleneck — every downstream component (intent detection, tool selection, policy) operates on a representation that has already thrown away the signal needed to distinguish an angry user from a joking one, or a genuine interruption from backchannel noise. That argues for placing paralinguistic understanding inside the model boundary rather than in a pre-processing stage.

Generalization

Whenever a pipeline serializes rich input into a lossy intermediate format (text, JSON summary, embedding) before the reasoning model, audit what decision-relevant signal is destroyed at that boundary. Latency and fidelity can fail together for the same reason: the compression step.

Source video ↗
[M]Mechanismhigh noveltymoderate evidence

Preambles are a latency-masking mechanism coupled to tool calling: the model speaks a short conversational filler while parallel tool calls execute, so perceived responsiveness is decoupled from actual tool round-trip time.

Why it matters

Tool-calling latency is the hardest constraint in realtime agents — you cannot stream tokens while waiting on an external API. Preambles turn dead air into an explicit, model-generated status signal, which is a UX-layer fix rather than an infrastructure one, and it composes with parallel tool calls to hide the slowest call behind the fastest acknowledgment.

Generalization

Any interactive agent with slow side effects needs an explicit 'acknowledge-and-narrate' channel that runs concurrently with tool execution; the same pattern applies to long-running code agents narrating progress and to UI agents showing optimistic state.

Source video ↗
[~]Tradeoffhigh noveltyweak evidence

Reasoning-before-speaking becomes an explicit tunable dial in realtime audio (reasoning levels), creating a direct budget trade between deliberation quality and conversational latency.

Why it matters

Text agents can hide multi-second reasoning behind a spinner or stream; a voice agent that goes silent for seconds reads as broken and invites barge-in. Exposing reasoning level per turn — cheap for chit-chat, expensive for a multi-tool booking — is a control surface that text-only stacks do not need and that production voice systems must schedule explicitly.

Generalization

Latency budgets are modality-specific; the same model needs a per-turn compute budget policy when the output medium is synchronous and human-paced (voice, live UI) versus asynchronous (chat, email, background jobs).

Source video ↗
[P]Practicemedium noveltyweak evidence

Audio should be treated as an intelligence layer over existing software surface (APIs, React hooks) rather than as a standalone voice-agent application.

Why it matters

This reframes the integration boundary: the voice model is a controller over an app's existing action surface, not a parallel conversational product. It means the tool/action schema the app already exposes becomes the primary interface contract for the voice layer, and the agent can be added to shipped software without a separate conversation store or UI paradigm.

Generalization

Attach new modalities (voice, vision, gesture) as control layers over an existing typed action surface; reuse the action schema rather than inventing a modality-specific one.

Source video ↗
[E]Empirical Resultmedium noveltymoderate evidence

Reported latency figures show an order-of-magnitude shift across generations — 2.8s (GPT-3.5 Voice Mode), 5.4s (GPT-4 Voice Mode), 320ms (GPT-4o AVM) — and the chained GPT-4 pipeline was slower than its predecessor despite a stronger model.

Why it matters

The regression from 2.8s to 5.4s suggests chained architectures scale latency with model quality: a better reasoning model adds serial time to every hop. Native audio removes the hop count entirely, which is why the quality/latency curve inverts. This is the concrete case for native audio as a latency strategy, not just a fidelity strategy.

Generalization

In multi-stage systems, per-stage quality improvements compound into latency regressions along the critical path; latency optimization should target hop count and serialization, not per-stage speed.

Architectural implications

4

Native audio replaces a three-model chain with one streaming model, eliminating the text transcript as the system's central data structure.

Before

ASR service → text transcript → LLM with tool schema → text → TTS service, with three network hops and three failure domains on the critical path.

After

A single realtime audio model that consumes audio, reasons, calls tools in parallel, and emits audio directly.

Consequence

Fewer serialization points and lower latency, but the auditable text artifact disappears from the default path — observability, logging, and evaluation must be re-architected around audio/turn level rather than transcript level.

Source video ↗

Response mode becomes a routing decision rather than a fixed property of the application.

Before

A 'voice agent' is defined by its modality: it speaks back by design.

After

The agent selects among speech, action, and event emission per turn, sometimes within a single workflow.

Consequence

The agent needs an explicit output-routing policy and a shared action schema spanning speech output, tool calls, and proactive notifications; mixing modes moves orchestration responsibility into the model's tool surface.

Source video ↗

Tool latency moves onto the conversation's critical path, so acknowledgment must be generated concurrently with execution.

Before

Tool calls are awaited and the result is returned as text in the next assistant turn.

After

Parallel tool calling plus model-generated preambles that cover the wait.

Consequence

Tool-call design must budget for narration; slow tools need per-tool preamble guidance and timeout policy, and the agent's perceived behavior depends on tool latency tails rather than averages.

Source video ↗

Speech-to-action grants the model execution authority over application state.

Before

A voice bot could only produce wrong answers, which the user could hear and correct.

After

The model fills forms, drives creative tools, and performs computer use on the user's behalf.

Consequence

Guardrails shift from content filtering to action authorization and confirmation; irreversible actions need explicit confirmation turns, and the security model must answer who approved the first unintended execution.

Tradeoffs and failure modes

5

Lossy transcription vs. native audio

Benefit

Native audio keeps tone, cadence, emotion, interruption, and noise cues and cuts latency by removing chained hops.

Cost or risk

Designs that depend on a text intermediate (searchable logs, keyword policy filters, text-based evals) lose their default substrate.

Source video ↗

Reasoning before speaking

Benefit

The model can deliberate and plan tool use instead of reflexively responding.

Cost or risk

Silence during deliberation reads as failure in a synchronous audio channel and invites barge-in; reasoning budget must be traded against conversational latency.

Source video ↗

Speech-to-action execution authority

Benefit

Voice becomes a fast input for form filling, creative tools, and computer use — tasks where typing dominates the user's time.

Cost or risk

An execution surface driven by ambiguous, noisy speech input; the summary gives no mechanism for confirmation or authorization, only that guardrails are an open problem.

Basing the fidelity argument on the 55/38/7 communication statistic
