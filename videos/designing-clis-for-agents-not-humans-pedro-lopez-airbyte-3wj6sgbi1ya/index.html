Summary

Overview

  • Speaker: Pedro Lopez
  • Channel: AI Engineer
  • Main topic: Building and designing Model Context Protocol (MCP) servers and CLIs specifically optimized for AI agents rather than human users.
  • Purpose: To share architectural best practices, design patterns, and lessons learned when building agent-facing interfaces (MCP servers and CLIs) for data infrastructure platforms like Airbyte. Pedro Lopez from Airbyte discusses how Airbyte evolved into the data and action layer for AI agents, detailing their experience in building the Airbyte Agent MCP Server and CLI. The talk outlines three main interface capabilities (manage, connect, ask & act), compares MCP and CLI interfaces, explains Airbyte's architectural design decisions (thin unified interfaces over core platform APIs), and shares four key design lessons for MCP (keep tool counts small, use OAuth, avoid elicitation due to poor client support) and four key design lessons for CLIs (JSON in JSON out, consistency is key, skills ship with the tool, auth must be headless).

Agent Interfaces: SDK, UI, MCP, and CLI

Designing MCP for Agents: Lessons Learned

  • Explanation: Discusses architectural and design lessons learned when building the Airbyte Agent MCP server, focusing on tool count minimization, OAuth authentication, and the limitations of elicitation.
  • Key claims:
    • Keep tool counts small using progressive discovery (e.g., separate describe_connector and execute tools rather than exposing individual tools for every connector entity).
    • OAuth is the required authentication standard because users expect long-lived headless sessions similar to mobile apps.
    • Elicitation (URL-mode or form-mode) is problematic due to inconsistent support across MCP clients.
  • Examples:
    • Connecting to Acme service or Anthropic custom connector via OAuth.
  • Terminology:
    • MCP
    • Progressive discovery
    • OAuth
    • Elicitation
    • describe_connector
    • execute
  • Why it matters: Provides concrete architectural guidelines for developers building MCP servers for AI agents.

Designing CLIs for Agents: Lessons Learned

  • Explanation: Explores how to design CLIs specifically for agent invocation rather than human usage, emphasizing JSON I/O, strict naming consistency, bundled skills, and headless authentication.
  • Key claims:
    • Design CLIs with JSON in and JSON out as the primary interface to allow programmatic construction and leverage Unix piping/jq for large responses.
    • Consistency is key: follow predictable naming patterns (noun-verb order like connectors list, connectors create) to prevent agent errors.
    • Skills must ship with the tool via markdown files to enable agent discovery and effective usage without bloating context.
    • Auth must be headless (environment variables or config files with API keys) because CLI agents cannot wait for interactive human prompts.
  • Examples:
    • Running airbyte-agent connectors execute --json ... and piping output to jq.
    • Using a SKILL.md reference file to teach Claude how to use the CLI.
  • Terminology:
    • CLI
    • JSON in, JSON out
    • Piping
    • jq
    • Skills
    • Headless auth
    • SKILL.md
  • Why it matters: Highlights that human-centric CLI design principles (like interactive prompts and human-readable flags) break when agents invoke terminals.

Key Points

Thin unified interface architecture

  • Explanation: MCP and CLI are presented as thin presentation layers sitting on top of shared platform APIs rather than re-implementations of business logic.
  • Evidence: Platform changes frequently (over 10 times a day), so interfaces rely on OpenAPI specs as a single source of truth.
  • Practical implication: Reduces maintenance overhead when underlying platform APIs undergo frequent deployments.

Keep tool counts small via progressive discovery

  • Explanation: Exposing every possible action as a separate MCP tool overwhelms agent context and degrades performance.
  • Evidence: Airbyte consolidated connector interactions into two core tools: describe_connector and execute.
  • Practical implication: Improves agent reliability by letting agents dynamically query schemas only when needed.

CLIs for agents require JSON I/O and strict consistency

  • Explanation: Human-friendly flags and interactive prompts fail when agents invoke commands programmatically.
  • Evidence: All commands accept JSON payloads and output JSON, enabling seamless integration with Unix pipes and jq.
  • Practical implication: Agents can reliably parse responses and handle complex multi-step data cross-referencing operations.

Compressed Summary

  • Airbyte built MCP servers and CLIs to act as data and action layers for AI agents.
  • MCP is ideal for non-technical users and quick prototyping with ChatGPT and Claude.
  • CLI is better for technical users, longer-running tasks, and large response handling via JSON and jq.
  • Key MCP lessons: keep tool counts small, use OAuth, avoid elicitation due to client inconsistencies.
  • Key CLI lessons: JSON in JSON out, noun-verb consistency, bundle SKILL.md documentation, ensure headless auth.

[A]Architecturemedium noveltymoderate evidence

Collapse many per-entity tools into a two-tool discover-then-execute pattern (describe_connector + execute) instead of one MCP tool per connector entity.

Why it matters

Exposing every possible action as a separate tool overwhelms the agent's context and degrades tool-selection reliability; progressive discovery lets the agent fetch schemas only when needed.

Generalization

Any agent-facing API surface with a large or growing action space should expose a stable, small set of meta-tools plus a runtime discovery mechanism rather than enumerating every operation statically.

Elicitation (URL-mode or form-mode) should be avoided in MCP servers because client support is inconsistent across MCP clients.

Why it matters

Designing a bidirectional interaction that depends on client-side elicitation support creates portability failures — the same server behaves differently or breaks across hosts like ChatGPT and Claude.

Generalization

Agent-facing protocols should not depend on optional interactive round-trips whose support varies across runtimes; push required interactions out-of-band rather than into the protocol hop.

Why it matters

Generalization

Architectural implications

3

MCP and CLI are layered as thin presentation interfaces over shared platform APIs rather than duplicating business logic.

Before

Each agent-facing interface (MCP, CLI) re-implements platform logic and drifts from the source of truth.

After

Interfaces derive from OpenAPI specs and only present/translate, leaving logic in the platform core.

Consequence

Maintenance cost stays flat even as the platform deploys 10+ times per day.

Source video ↗

Tool surface size is treated as a first-class design constraint rather than a natural consequence of the API's breadth.

Before

Expose one tool per entity/action; the agent sees the full API surface.

After

Expose a fixed small set of meta-tools plus runtime schema discovery.

Consequence

Agent context stays bounded and tool selection becomes more reliable as the integration grows.

Human-oriented CLI affordances (interactive prompts, human-readable flags) are treated as liabilities for agent consumers.

Before

Design CLIs for human ergonomics and reuse them for agents.

After

Design a separate JSON-in/JSON-out, headless, grammar-consistent surface for machine invocation.

Consequence

Agent-facing tooling diverges from human CLIs, requiring separate design standards and skills documentation.

Cost or risk
