[A]Architecturemedium noveltymoderate evidence

Wafer-scale integration co-locates SRAM with compute across an entire wafer, attacking the memory-bandwidth wall architecturally rather than through interconnect or cluster-level scaling.

Why it matters

Memory bandwidth, not FLOPs, is usually the binding constraint for inference and pre-training throughput; solving it at the package/wafer level changes the cost curve for serving large models and alters how models get partitioned across hardware.

Generalization

When a bottleneck is data movement rather than arithmetic, the highest-leverage fix is co-locating storage with compute at a larger physical granularity, not optimizing the arithmetic path.

[A]Architecturehigh noveltymoderate evidence

Agent orchestration is migrating from application-level chains to an OS-like runtime: a standalone desktop app that schedules and runs multiple agents in parallel.

Why it matters

If orchestration lives in a runtime rather than in library code, responsibilities shift for scheduling, process isolation, resource contention, permission scoping, and observability — the same concerns an OS owns for threads. Agent authors then target a supervisor API instead of building their own loop management.

Generalization

As agents become long-running and concurrent, the coordination layer accretes OS-like properties (scheduler, isolation, quotas, capabilities) and should not be reimplemented per application.

[~]Tradeoffmedium noveltymoderate evidence

A fast tier (4x output token speed) is positioned as a distinct frontier release rather than a degraded small model, making output speed a first-class capability axis alongside quality.

Why it matters

In multi-step agent loops, wall-clock latency compounds multiplicatively across steps, so output token throughput can dominate end-to-end task time; that makes model routing by step-type (speed tier for tool-calling and intermediate reasoning, slow tier for final synthesis) a concrete design decision rather than a cost hack.

Generalization

For iterative agent workloads, per-token latency and throughput should be evaluated per-step, not per-request, because they compound across a trajectory.

[O]Mental Modelhigh noveltymoderate evidence

Agents are shifting from request-response to persistent background monitoring: an agent that continuously scans the web for matching listings rather than answering a single query.

Why it matters

Persistence changes the engineering surface entirely — termination conditions, budget ceilings, deduplication of already-seen results, state persistence across restarts, and per-agent-hour cost accounting all become required, and the dominant failure mode becomes unbounded spend or duplicate notification rather than a wrong answer.

Generalization

Any agent that runs without a user-initiated trigger needs an explicit lifecycle contract (start, budget, dedupe key, stop) before it needs better reasoning.

Routing by speed-tier vs capability-tier inside multi-step agent loops

Research question

In a multi-step tool-using agent loop, does output-token throughput or per-step reasoning quality dominate end-to-end wall clock and task success, and does the optimum routing split vary by step type (tool call, intermediate reasoning, final synthesis)?

Why

A 4x output-token speed advantage compounds across steps, so a single-request benchmark cannot tell you whether fast tiers are a cost hack or a genuine capability tier. Getting the routing boundary wrong either inflates latency budgets or degrades hard-reasoning steps silently.

Source video ↗

Lifecycle contracts for always-on monitoring agents

Research question

What minimal lifecycle contract — explicit start, hard token/dollar budget, semantic dedupe key, stop condition, and restart-safe state — is sufficient to keep a persistent background agent both economically bounded and non-redundant?

Why

Persistence inverts the failure mode: the dominant risk becomes unbounded spend and duplicate notification rather than a wrong answer, and unit economics shift from per-request to per-agent-hour. Without a contract, a monitoring agent degrades into an untracked subscription.

Source video ↗

Serving placement under wafer-scale memory locality

Research question

When SRAM is co-located with compute across a wafer rather than streamed from off-package memory, do cluster-oriented partitioning, batching, and parallelism strategies still hold, or does optimal placement change shape entirely?

Why

If the binding constraint moves off the interconnect, serving stacks tuned for multi-GPU topologies will be misconfigured for wafer-scale hardware, and throughput-per-dollar assumptions baked into agent fan-out budgets become stale.

Agent orchestration as an OS-shaped runtime

Research question

Which responsibilities — scheduling, preemption, process isolation, permission scoping, quota enforcement, cross-agent observability — must a parallel-agent runtime own so that individual agent authors stop reimplementing them?

Why

Once agents run concurrently and long-lived, contention and permission bugs become platform bugs. Defining the supervisor API boundary determines whether agent code can assume isolation or must defend against sibling agents.

Transaction semantics for cross-merchant agentic commerce

Research question

Article ideas

4

Your Agent Loop Doesn't Have a Latency Problem, It Has N of Them

Per-request latency benchmarks are the wrong unit for agentic systems: because wall-clock time compounds across steps, output-token throughput and step count jointly determine task time, which makes step-type routing a first-class architectural decision rather than a cost optimization.

Angle

Reframe the 4x speed claim from a model spec into an agent-level accounting exercise: show how step count, per-step token throughput, and retry rate multiply, and why measuring at the trajectory level changes which model you pick for which step.

Source video ↗

The Missing Contract: Why Always-On Agents Fail on Economics Before They Fail on Reasoning

Persistent background agents need a lifecycle contract — budget ceiling, dedupe key, stop condition, restart-safe state — as a precondition for deployment; without it, the failure mode is not a wrong answer but an unbounded bill and a duplicate notification stream.

Angle

Treat the 24/7 agent as an operations problem, not a capability problem: enumerate the four contract fields, show what breaks when each is missing, and argue cost accounting should be per-agent-hour rather than per-request.

Source video ↗

Agents Are Becoming Operating Systems, and That Should Worry Framework Authors

When orchestration moves from library code into a standalone runtime that schedules parallel agents, the hard problems migrate to scheduler design, isolation, quotas, and capabilities — meaning the durable value accrues to the runtime layer and app-level agent frameworks risk becoming thin clients.

Angle

Compare the responsibility shift to how threads forced OS-level scheduling; argue that agent authors should target a supervisor API and design for preemption and concurrent side effects from day one.

Source video ↗

The Agent That Has to Be Right About Three Different Stores

Cross-merchant agentic commerce is a distributed-systems reliability problem disguised as a reasoning problem: because the agent absorbs schema normalization, delegation, and partial failure, idempotency and audit design must live in the agent layer rather than be assumed from tools that share no contract.

Angle

Walk a single cart across merchants with divergent schemas and auth, and show where duplicate charges, orphaned orders, and unreconcilable state appear when transaction semantics are left implicit.

Project ideas

4

Agent Lifeline

new

Persistent monitoring agents with an enforced lifecycle contract (hard dollar budget, semantic dedupe key, explicit stop condition, checkpointed state) achieve cost-per-useful-notification at least 5x lower than the same agent with only a token cap and no dedupe, without reducing recall of genuinely new results.

Proof of concept

A background apartment/listing monitor built on a supervisor wrapper that enforces a per-run budget, persists seen-item embeddings as a dedupe index, and emits only novel matches; run identical workloads with contract fields toggled off one at a time.

Measurement

Cost per unique useful notification, duplicate-notification rate, recall of newly appearing items, and spend overshoot versus configured budget, across a multi-day continuous run per configuration.

Source video ↗

StepTier

beyond-evals

In multi-step tool-using loops, routing intermediate tool-calling and reasoning steps to a 4x-faster output tier while reserving a slower capability tier for final synthesis reduces end-to-end wall clock by more than 40% with no measurable drop in task success, and the optimal split is stable within a task class.

Proof of concept

A router that instruments each step of a fixed benchmark loop (tool call, reflection, final answer), dispatches by step type to fast vs capability tiers, and logs steps-to-completion, wall clock, tokens, and dollars per successful task.

Measurement

Task success rate, steps-to-completion, p50/p95 wall clock, and cost per successful task for fast-only, capability-only, and step-routed configurations on identical agent tasks.

Source video ↗

Provenance Gate

gatehouse

A mandatory provenance-check ingestion gate (SynthID/C2PA signature validation) inserted before generated media enters an agent's context reduces false acceptance of synthetic content as captured evidence, at a false-reject cost low enough to keep as a default pipeline stage.

Proof of concept

An ingestion filter that inspects provenance metadata on a mixed corpus of captured and generated media, quarantines or flags unverifiable items, and blocks flagged content from being reused as agent context or presented as fact.

Measurement

False-accept rate (synthetic content treated as authentic), false-reject rate on authentic media, added ingestion latency, and downstream change in agent answer accuracy on questions that depend on media authenticity.

Source video ↗

Idempotent Cart

new

Assigning agent-layer idempotency keys and per-merchant compensation steps to every side-effecting commerce action reduces duplicate charges and orphaned orders under injected downstream failures to near zero, even when merchant backends share no contract.

Proof of concept

A simulated multi-merchant cart (three divergent product schemas and auth flows) driven by an agent that writes an intent record with an idempotency key before each action and reconciles partial failures with merchant-specific compensation.

Measurement

Duplicate charge count, orphaned-order count, and percentage of runs reaching a consistent final cart state under injected faults (auth expiry, timeout, mid-checkout schema drift).

Architectural implications

4

Agent orchestration is delivered as a standalone runtime that schedules parallel agents, rather than as a framework embedded in each application.

Before

Agents are implemented as app-level chains with hand-rolled concurrency and retry logic inside a single process or service.

After

A supervisor/runtime process owns scheduling, parallelism, isolation, and lifecycle for many agents, with apps targeting its interface.

Consequence

Scheduling, resource contention, permission scoping, and cross-agent observability become platform concerns; agent authors must design for preemption and concurrent side effects.

Source video ↗

Memory locality is moved to the wafer scale, co-locating SRAM with compute instead of streaming from off-package memory.

Before

Throughput scales by adding GPUs and moving weights/activations across interconnect and off-package HBM.

After

Capacity and bandwidth are integrated across a giant chip surface, reducing data movement per operation.

Consequence

Model partitioning, batching, and parallelism strategies tuned for multi-GPU cluster topologies do not transfer; serving stacks need architecture-specific placement decisions.

Source video ↗

Agents act directly on consumer-facing surfaces across many merchants with no unified contract.

Before

Integration is per-merchant via published APIs and negotiated partnerships, with the application owning all schema mapping.

After

A general agent drives heterogeneous backends in the background and normalizes results itself.

Consequence

Idempotency, delegation/consent, audit trails, and partial-failure reconciliation must be built into the agent layer rather than delegated to a shared protocol.

Source video ↗

Content generation and content verification are converging into the same product surface.

Before

Authenticity is assumed at capture time and provenance is a downstream media-operations concern.

After

Generated media carries embedded signals (SynthID/C2PA) that consumers and pipelines are expected to check.

Consequence

Ingestion and retrieval pipelines for agents need an explicit verification gate before generated content is trusted or reused as context.

Tradeoffs and failure modes

5

Speed-tier vs capability-tier model routing

Benefit

4x output token speed reduces compounding wall-clock latency across multi-step agent trajectories and lowers cost per step.

Cost or risk

A speed-optimized frontier tier may underperform on long-horizon planning or hard reasoning, so routing decisions must be validated per task class rather than globally.

Source video ↗

Always-on persistent agents

Benefit

Continuous background monitoring surfaces opportunities a user would never think to query for.

Cost or risk

No natural termination point means unbounded token spend, duplicate results, and unclear unit economics; cost accounting shifts from per-request to per-agent-hour.

Source video ↗

Agent as universal integrator across merchants

Benefit

One agent can transact across disparate retailers without each needing to expose a shared API.

Cost or risk

Every downstream merchant becomes a failure domain; schema drift, auth expiry, and partially completed transactions produce inconsistent state.

Source video ↗

Human review of the final 20% of agent-generated code

Benefit

Keeps humans on judgment-heavy work while agents handle volume and whole-codebase context.

Cost or risk

Reviewers become the throughput bottleneck, and the 20% figure is unmeasured — reviewer fatigue may silently degrade the only real quality gate.

Source video ↗

Wafer-scale compute as an alternative to GPU clusters

Benefit

Integrated SRAM across a giant chip surface removes the off-package memory bottleneck that constrains GPU-based training and inference.

Cost or risk

A single enormous die concentrates yield and defect risk and creates deep dependency on one fabrication partner (TSMC) and one vendor.
