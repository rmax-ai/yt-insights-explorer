Overview

  • Speaker: Ajay Prakash
  • Channel: AI Engineer
  • Main topic: Context engineering and playbooks for coding agents at LinkedIn
  • Purpose: To explain LinkedIn's methodology of context engineering, playbooks, MCP integration, and meta-tools for making coding agents reliable and trustworthy in enterprise development. Ajay Prakash from LinkedIn discusses how LinkedIn uses Context Engineering and their 'CAPT' system (Contextual Agent Playbooks and Tools) to improve the performance of coding agents. By moving beyond open-source codebases and injecting structured procedural memory, playbooks, and meta-tools via Model Context Protocol (MCP), LinkedIn scaled agent usage to over 8,000 daily users across engineering and product teams without fine-tuning LLMs.

Topic Map

The On-Call Problem and the Limitation of Coding Agents

  • Explanation: Illustrates an on-call scenario where an engineer hands an error log to an LLM coding agent, highlighting how unassisted agents lack enterprise-specific context and fail without explicit instructions.
  • Key claims:
    • LLM coding agents trained on open-source repos lack context on enterprise internal frameworks, codebases, and systems.
    • Unassisted coding agents hallucinate or get stuck when dealing with company-specific internal architecture.
  • Examples:
    • An on-call engineer debugging an error spike by giving the alert link to Claude Code or GitHub Copilot.
  • Terminology:
    • Coding agents

  • Why it matters: Shows why standard off-the-shelf coding assistants fail to solve real-world enterprise engineering problems without tailored context.

LinkedIn's Engineering Stack and Context Gaps

  • Explanation: Outlines LinkedIn's massive internal infrastructure (thousands of repos, microservices, internal frameworks, custom data platforms, experimentation, and config management) and the three main context gaps.
  • Key claims:
    • LinkedIn has over 1,000 repositories, microservices, and internal frameworks at every layer.
    • The three context gaps are tribal knowledge (scattered across docs, wikis, Slack), context overload (too many tools and token window limits), and no durable memory.
  • Examples:
    • Scattered documentation in wikis and Slack conversations that become outdated or duplicated.
  • Terminology:

Key Points

Vibe coding does not work in large enterprises

  • Explanation: Relying purely on LLMs trained on open-source repositories leads to hallucinations and dead ends when applied to enterprise-specific internal frameworks.
  • Evidence: Engineers trying unassisted coding agents experienced frequent hallucinations and had to manually prompt agents step-by-step.
  • Practical implication: Enterprises must invest in context engineering rather than expecting raw LLMs to understand proprietary stacks.

Playbooks provide procedural memory

  • Explanation: Playbooks package instructions, concepts, steps, best practices, and troubleshooting tips for specific engineering tasks.
  • Evidence: Airflow DAG authoring playbook includes specific concepts, steps, and gotchas like timezone-naive datetimes.
  • Practical implication: Store standard operating procedures as markdown playbooks that agents can discover and invoke.

Meta-tools solve context overload

  • Explanation: Directly exposing thousands of tools to an LLM clogs the context window and causes context compaction failure. Meta-tools allow dynamic tool discovery.
  • Evidence: Using search, get_schema, and execute instead of passing all 1,300+ tools simultaneously.
  • Practical implication: Implement a two-tier discovery pattern (search and schema fetching) when scaling agent toolsets.

Frameworks, Models & Processes

CAPT (Contextual Agent Playbooks and Tools)

  • How it works: Combines local MCP servers with structured playbooks (procedural memory) and meta-tools for dynamic discovery and execution.
  • Components:
    • Local MCP server
    • Central and local playbooks
    • Meta-tools (search, get_schema, execute)
    • Self-improving feedback flywheel
  • When to use: When deploying coding agents across an enterprise with proprietary internal codebases, tools, and workflows.

Playbook Self-Improving Flywheel

  • How it works: Engineers run a playbook, notice outdated info, ask the agent to update it, agent edits the playbook and opens a PR, which a human approves.
  • Components:
    • Run playbook
    • Notice outdated info
    • Agent updates playbook
    • Open PR
    • Human approval
  • When to use: To maintain up-to-date tribal knowledge and procedural documentation for AI agents.

Actionable Takeaways

  • Immediate:
    • Adopt Model Context Protocol (MCP) for structuring agent tool access.
    • Package internal workflows into self-contained, composable markdown playbooks.
    • Implement meta-tools (search and schema fetching) to prevent context overload.
  • Strategic:
    • Treat quality and reliability of generated code as a first-class requirement from day one.
    • Build the right infrastructure (internal MCP servers, auto-updates, auth) to support agents across your enterprise.
    • Design self-improving feedback loops so agents and engineers keep playbooks updated via pull requests.

Core insights

[M]Mechanismhigh noveltystrong evidence

Scaling tool access is solved by a two-tier discovery layer rather than a flat tool list: expose only three meta-tools (search, get_schema, execute) and let the agent resolve the concrete tool at runtime. LinkedIn uses this to reach 1,300+ tools without degrading context performance.

Why it matters

It decouples the size of the tool catalog from the size of the context window, turning tool registration into a retrieval problem instead of a prompt-budget problem. Directly registering tools hits a hard ceiling where context compaction stops working.

Generalization

Any agent whose tool surface exceeds a few dozen entries should expose a discovery/schema/execute indirection layer; the tool registry becomes an indexable store, not a prompt section.

[A]Architecturehigh noveltystrong evidence

Playbooks are procedural memory packaged as self-contained, composable, discoverable artifacts (markdown SOPs with concepts, steps, best practices, and gotchas) delivered alongside tools — not embedded in the model or in a monolithic system prompt.

Why it matters

It puts the non-obvious enterprise knowledge (e.g., timezone-naive datetimes in Airflow DAGs) where the agent can fetch it on demand, and where humans can review and edit it, instead of relying on the model to infer it or on prompt-stuffing.

Generalization

Separate declarative capability (tools/MCP) from procedural capability (playbooks) as distinct layers with distinct ownership and update cadence; procedural knowledge is data, not weights and not prompt text.

Deep dives

Meta-tool discovery vs flat tool exposure: where the crossover is

Research question

At what tool-catalog size and retrieval precision does a search/get_schema/execute indirection layer beat a curated top-k flat tool list on task success, token cost, and wall-clock round trips?

Why

The claim that thousands of tools stay performant under meta-tools is asserted without a comparative measurement; without a crossover point, teams cannot decide when to graduate from a flat list to a discovery layer, and the extra resolve step may cost more than it saves below some catalog size.

Source video ↗

Instrumenting playbook quality, staleness, and decay

Research question

Can per-playbook invocation telemetry (completion rate, retry count, human-correction rate, escalation-to-manual-prompting) predict which playbooks have gone stale before users abandon them?

Why

An 8,000-user, 600-playbook fleet with hourly distribution has no described evaluation harness; staleness is the dominant failure mode of a text-artifact capability layer, and it is invisible unless invocation traces are instrumented per playbook.

Source video ↗

Governance of agent-authored edits to shared procedural memory

Research question

Does a PR-style review gate on playbook diffs suppress legitimate in-run corrections or effectively catch instruction drift, and what approval latency is tolerable before the self-improvement flywheel stalls?

Why

The flywheel has the agent editing the instructions that govern it; without review, a bad edit to a central playbook silently degrades every consumer, and with heavy review the correction loop loses its main advantage over a normal docs process.

Source video ↗

Context artifacts as a fleet-distributed supply chain

Research question

What canary, rollback, and audit semantics are required before an hourly auto-updated context bundle is safe to ship to an entire engineering fleet, and how small must the blast radius be per cycle?

Why

Treating playbooks and tool schemas as a deployed binary buys freshness and consistency but converts a content bug into a fleet-wide outage on a one-hour fuse; the rollout controls, not the authoring, become the binding engineering constraint.

Source video ↗

Mis-selection under federated central and repo-local playbooks

Research question

In a multi-repo environment with overlapping playbook names and near-duplicate procedures, what is the agent's mis-selection rate between central and repo-local playbooks, and does the recovery behavior differ from a missing-playbook failure?

Why

Federating context along repo ownership scales authoring to the org chart but creates a discovery conflict problem; a wrongly-scoped playbook applies the wrong procedure confidently, which is worse than finding nothing.

Article ideas

3

Your Tool Catalog Is a Retrieval Index, Not a Prompt Section

Once an agent's tool surface exceeds a few dozen entries, registering tools in the prompt is a category error; the registry must become an indexable store queried through meta-tools, which moves the engineering investment from prompt budget to tagging, schema quality, and retrieval precision.

Angle

Frame the ceiling of flat tool registration as a context-compaction failure rather than a model failure, then argue that tool-overload is merely traded for discovery-overload unless tags and schemas are curated as a first-class artifact.

Source video ↗

Zero Fine-Tuning Is a Supply Chain Problem, Not a Prompt-Writing Problem

Substituting context artifacts for weight updates only works if those artifacts are shipped like software; the moment capability lives in an hourly-updated bundle reaching thousands of laptops, versioning, canary, rollback, and staleness detection become the real work, and authoring quality becomes the cheap part.

Angle

Contrast the wiki model of internal knowledge with the deployed-binary model, and argue that a bad playbook push is an outage with a one-hour fuse, not a docs typo.

Source video ↗

Separate Declarative From Procedural Capability: Playbooks as Data, Not Weights and Not Prompt Text

Tools and playbooks are two layers with different owners and different update cadences; collapsing procedural knowledge into a monolithic system prompt or into fine-tuning destroys the reviewability and hot-swap properties that make enterprise agent capability maintainable.

Angle

Argue that procedural knowledge belongs in discoverable, composable markdown artifacts precisely because humans must be able to review and edit the same bytes the agent reads at run time.

Project ideas

4

MetaToolBench

beyond-evals

At catalog sizes above roughly 200 tools, a three-meta-tool discovery layer (search, get_schema, execute) preserves tool-selection accuracy within 5% of an oracle flat list, while a static top-k flat list of the same size loses more than 20% accuracy on tasks whose correct tool is not in the top-k.

Proof of concept

Build a synthetic tool catalog of 20/100/500/1300 tools with paired tasks, run three agent configurations (all tools in prompt, top-k flat, meta-tool discovery), and instrument selection accuracy, tokens, and round trips.

Measurement

Tool-selection accuracy, task success rate, input tokens per task, number of resolve round trips, and the catalog size at which each configuration crosses a degradation threshold.

Source video ↗

Playbook Drift Gate

gatehouse

A PR-style review gate on agent-authored playbook diffs, combined with per-playbook invocation traces, catches injected instruction drift in more than 80% of cases while rejecting fewer than 10% of legitimate corrections.

Proof of concept

Instrument a small playbook corpus so every invocation logs completion, retries, and human corrections; inject known-stale and known-corrupting edits, then run them through a human-or-model review gate and compare detection against acceptance.

Measurement

Drift detection rate, false-rejection rate on legitimate edits, median approval latency, and correlation between trace-derived staleness signals and confirmed-outdated playbooks.

Source video ↗

ContextFleet

new

An hourly-synced context bundle without canary staging produces fleet-wide degradation from a single bad playbook push, whereas a staged rollout with a held-back cohort and one-command rollback confines the impact to under 10% of clients within the first update cycle.

Proof of concept

Ship playbooks and tool schemas through a versioned client with cohort staging, health signals from invocation traces, and rollback; inject a deliberately broken playbook and measure propagation and recovery under staged versus unmanaged rollout.

Measurement

Fraction of clients affected before detection, time-to-rollback, share of users on stale context, and recovery time to pre-push success rate.

Source video ↗

Playbook Scope Resolver

movement-lab

When central and repo-local playbooks overlap in name or procedure, an explicit scope-resolution step reduces agent mis-selection versus naive keyword discovery, cutting confident-wrong-procedure application without increasing not-found rates.

Proof of concept

Construct a multi-repo fixture with near-duplicate playbook names across central and local tiers, then compare naive keyword discovery against a resolver that ranks by repo context and ownership before invocation.

Measurement

Mis-selection rate, not-found rate, recovery attempts after a wrong-procedure run, and task success on tasks whose correct answer depends on repo-local gotchas.

Architectural implications

4

Tool exposure moves from static registration to runtime resolution.

Before

Every tool schema is injected into the agent's context up front, or the tool list is manually pruned per task.

After

A small fixed set of meta-tools (search, get_schema, execute) resolves concrete tools on demand.

Consequence

The tool catalog can grow independently of the model's context budget; tooling must now invest in indexing, tagging, and schema quality, and the agent gains an extra resolve step in its loop.

Source video ↗

Agent capability lives in retrievable, hot-updatable artifacts rather than in weights.

Before

New internal-framework capability requires fine-tuning, retraining, or a new model.

After

Capability is shipped as playbooks/tools with an hourly update channel.

Consequence

Iteration is measured in hours; the engineering problem shifts to authoring quality, versioning, and regression-testing of context artifacts.

Source video ↗

Ownership of agent context is federated to repo/service owners.

Before

A central team owns the prompt/context and becomes the bottleneck for every workflow.

After

Central tier for cross-cutting workflows plus repo-local playbooks owned by the teams that own the code.

Consequence

Context scales with the org chart, but requires conventions for composition, discovery, and conflict resolution between central and local playbooks.

Source video ↗

Context delivery becomes an endpoint software distribution problem.

Before

Each developer configures their own MCP servers, versions, and prompt setup.

After

A pre-installed, auto-updated client on every machine serves central and local playbooks.

Consequence

Requires supply-chain hygiene (rollout controls, rollback, audit) and introduces a shared failure domain — a bad push reaches the whole fleet on the next update cycle.

Tradeoffs and failure modes

5

Meta-tool indirection vs flat tool exposure

Benefit

Scales to 1,300+ tools without exhausting the context window or triggering compaction failure.

Cost or risk

Adds discovery round trips and a new failure mode: the agent searches with the wrong keywords/tags and never finds the right tool or playbook.

Source video ↗

Self-improving playbooks (in-band edits)

Benefit

Playbooks stay current because the engineer who hits stale instructions fixes them during the run.

Cost or risk

The agent is editing the very instructions that govern it; without review gates this risks instruction drift and silent degradation across all consumers of a central playbook.

Source video ↗

Hourly auto-update of the local MCP server

Benefit

All 8,000+ users get the same fresh context without manual sync.

Cost or risk

Large synchronized blast radius on a short cycle; a bad playbook or tool schema propagates fleet-wide within an hour.

Source video ↗

Catalog growth (600 playbooks, 1,300 tools)

Benefit

Broad coverage across engineering and non-engineering workflows.

Cost or risk

Tool-overload is traded for discovery/selection overload; correctness depends on retrieval precision and on curated tags rather than on the agent's ability to scan everything.

Source video ↗

Zero fine-tuning as the strategy

Benefit

No training pipeline; capability is updated by editing text artifacts.

Cost or risk

Relies entirely on the base model's ability to follow retrieved procedure in a proprietary stack; failures are attributed to context rather than model, and quality is bounded by how well the underlying model generalizes.
