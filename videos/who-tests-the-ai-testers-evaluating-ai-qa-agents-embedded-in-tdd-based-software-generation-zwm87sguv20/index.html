Summary

Overview

  • Speaker: Lilia Urmazova
  • Channel: PyData
  • Main topic: Evaluating AI QA agents using TDD-based software generation and testing approaches (Big-Bang, Sandbox Target, and Mutation Testing)
  • Purpose: To establish rigorous evaluation methodologies and metrics for AI QA agents that test code generated by developer AI agents. Lilia Urmazova presents a comprehensive evaluation framework for AI QA agents operating within Test-Driven Development (TDD) workflows. She contrasts classical QA with agentic workflows, outlines three distinct pipeline approaches (Big-Bang Monolithic, Sandbox Target, and Mutation Testing), compares their pros and cons via a comparative matrix, and proposes merged architectures utilizing stability metrics like Verification Recovery Rate (VRR).

Key Points

AI QA Agent Target Shift

  • Explanation: AI QA agents evaluate raw codebase artifacts produced by developer agents rather than interacting with live running applications.
  • Evidence: Contrasting human QA targets (live running apps, organic failures) with AI agent targets (codebase artifacts, injected flaws).
  • Practical implication: Testing frameworks must focus on static code artifacts and controlled fault injection rather than UI/runtime environments.

Trade-offs in Evaluation Approaches

  • Explanation: Each evaluation approach (Big-Bang, Sandbox, Mutation) trades off setup complexity, cost, bias, and variability.
  • Evidence: Big-Bang is cheap and easy to set up but suffers from LLM-as-a-judge subjectivity; Sandbox provides known bugs but lacks variability; Mutation offers high variability at high compilation cost.
  • Practical implication: Teams should choose or merge approaches depending on their specific budget and precision requirements.

Verification Recovery Rate (VRR)

  • Explanation: VRR quantifies an agent's self-healing capabilities by comparing pass rates on fixed code against baseline code.
  • Evidence: VRR formula equals Pass Rate fixed divided by Pass Rate initial.
  • Practical implication: Provides a normalized 0.0 to 1.0 score for system stability and agent recovery efficacy.

Frameworks, Models & Processes

Sandbox Target Approach

  • How it works: An initial clean codebase is replicated into a broken sandbox with hand-coded human bugs, and the QA agent is tasked with locating and patching them against a known manifest list.
  • Components:
    • Initial Codebase
    • Broken Sandbox
    • QA Agents Run
    • Static Manifest List
  • When to use: When you need low evaluation cost and deterministic tracking of specific known business logic bugs.

Mutation Testing Approach

  • How it works: An initial clean codebase is passed to a mutation library that injects randomized semantic faults at runtime, and QA agents must detect and isolate them across runs.
  • Components:
    • Initial Codebase
    • Mutated Code / Mutation Library
    • QA Agents Run
    • Efficacy Metrics (Killed vs. Survived)
  • When to use: When you want high variability and want to avoid maintaining static broken codebases or developer loops.

[A]Architecturehigh noveltymoderate evidence

Replace the LLM-as-judge oracle with seeded ground truth: the evaluator owns a manifest of injected faults and scores the QA agent on whether it located/patched each one, rather than asking a model to opine on test quality.

Why it matters

Moves agent evaluation from subjective grading to deterministic, auditable pass/fail per injected fault, which is what you need for regression tracking across model or prompt changes.

Generalization

Whenever an evaluator agent is graded on open-ended artifacts, move the oracle out of the model and into a versioned fault/label manifest that the harness controls.

[M]Mechanismmedium noveltymoderate evidence

Mutation testing is used as a variability engine for agent evaluation: faults are generated semantically per run rather than hand-authored, so you get fresh, non-memorizable tasks without a developer loop, and scoring becomes killed-vs-survived mutant accounting borrowed from classical mutation analysis.

Why it matters

Static benchmark tasks leak into training data and get overfit; per-run mutation makes the evaluation distribution non-stationary, which is closer to how reliability degrades in production.

Generalization

For any agent whose task is inspect-and-repair, generate the defects programmatically at eval time instead of curating a fixed defect set.

Gives a single comparable scalar for 'did the agent restore the system to working order', rather than raw pass counts that are not comparable across codebases or fault sets.

[O]Mental Modelmedium noveltymoderate evidence

The target of QA has shifted from a running application to a codebase artifact produced by a developer agent, so the eval harness must be built around static artifacts and controlled fault injection rather than UI or runtime environments.

Why it matters

Teams porting classical QA tooling (browser drivers, environment provisioning, E2E suites) into agent evaluations are solving the wrong problem; the expensive, non-obvious infrastructure is fault injection plus artifact-level test execution.

Generalization

Before building eval infrastructure, identify what the artifact under test actually is (live system vs. source tree); the harness boundary follows the artifact, not the product domain.

[A]Architecturemedium noveltyweak evidence

Sandbox and mutation approaches are proposed as a merged architecture rather than competing options: sandbox faults target structural business logic (whole checks omitted), mutations target local semantic swaps, and each covers what the other misses.

Why it matters

Signals a layered evaluation stack where fault granularity is the design axis, not a single benchmark suite; a single method leaves a blind spot in either breadth or depth.

Generalization

Agent evals should be layered by fault granularity: coarse structural defects for breadth/coverage, fine local perturbations for robustness of reasoning.

Deep dives

5

Baseline-relative recovery metrics (VRR) as a comparable stability scalar

Research question

Does normalizing repair success as pass_rate(repaired)/pass_rate(baseline) actually produce comparable, ungameable scores across heterogeneous fault sets and harnesses, or does variance in baseline pass rate dominate the ratio?

Why

If VRR is comparable, teams get one scalar to track self-healing across codebases and harness versions; if not, it silently rewards weak baselines and produces false regression signals. This is the measurement foundation for any agent-repair claim.

Source video ↗

Layered fault granularity as an eval design axis

Research question

Does a merged harness (coarse structural faults from a sandbox + fine local semantic mutations) discriminate between strong and weak QA agents better than either approach alone, and what is the marginal signal per additional fault layer?

Why

If the two layers are complementary rather than redundant, eval suites should be designed as a fault-granularity stack instead of a single benchmark; if redundant, teams are paying double compile cost for one signal.

Source video ↗

Unit economics of execution-grounded agent evals

Research question

What is the measured compile-and-test cycle cost per evaluation run for mutation-based scoring, and how much does it drop with incremental builds, test selection, and mutant batching?

Why

The binding constraint on eval scale is sandbox compute, not model cost. Harness design decisions (caching, incremental execution, parallelism) are the real levers, and without cost-per-eval numbers mutation cannot be a default loop.

Source video ↗

Reproducibility of per-run randomized fault generation

Research question

Can seeded mutant generation with recorded mutant IDs and operator types make randomized evaluation fully replayable without collapsing back to a fixed distribution?

Why

Variability is the point of mutation, but unreplayable runs make regressions indistinguishable from sampling noise, which breaks the ability to diff agent versions. Seeded generation is the minimal mechanism that reconciles both.

Source video ↗

Language-agnostic fault generation without mature mutation libraries

Research question

Do AST-level LLM-generated mutations serve as an adequate substitute for library-based mutation operators in ecosystems lacking mature mutation tooling, and do they produce faults of comparable detectability?

Why

The evaluation approach currently inherits the coverage limits of existing mutation libraries, which is a portability cliff for most language ecosystems. If LLM-generated AST mutations work, the harness generalizes; if they produce trivially detectable faults, it doesn't.

Article ideas

4

Stop Asking a Model to Grade Your QA Agent

Any agent evaluation that uses an LLM-as-judge oracle is an unfalsifiable measurement: the only defensible oracle for inspect-and-repair agents is an execution-grounded fault manifest where each injected defect has a deterministic located/patched verdict. Cheap setup is not a reason to accept a biased, runtime-less oracle.

Angle

Argue that the LLM-as-judge shortcut in agent QA evaluation is a category error, then show the oracle-replacement path: versioned fault manifests as first-class assets, pass/fail per fault, and diffable scores across agent versions.

Source video ↗

Your Agent Eval Is a Build System Problem

For execution-grounded agent evaluations, the dominant cost is compile-and-execute cycles inside sandboxes, not tokens. Teams that model eval cost as model spend will under-provision sandbox compute and design the wrong harness; the real levers are incremental builds, test selection, mutant batching, and parallelism.

Angle

Reframe agent-eval unit economics around cycles-per-run, walk through which harness architectural choices actually move that number, and argue that eval infrastructure should be staffed as build/CI engineering.

Source video ↗

Recovery Rate Is Not a Score Until It Survives a Bad Baseline

VRR-style normalized recovery metrics are only useful if they hold ordering and variance stable across differing baseline pass rates; otherwise a weak baseline inflates the ratio and the metric rewards fragile code. Publishing baseline-relative agent metrics without demonstrating cross-environment comparability is measurement theater.

Angle

Take one repair metric (VRR) and stress-test its normalization claim: what breaks it, how to report confidence alongside the scalar, and what a robustness check should look like before the number goes on a dashboard.

Source video ↗

The Artifact Under Test Decides Your Eval Harness

When the thing under test shifts from a running application to a source-tree artifact produced by another agent, porting classical QA infrastructure (browser drivers, environment provisioning, E2E suites) solves the wrong problem. The harness boundary follows the artifact, and building fault injection plus artifact-level test execution is where the non-obvious cost lives.

Angle

Contrast classical QA tooling assumptions with agentic QA requirements, then map which existing investments transfer and which are sunk.

Project ideas

4

Baseline-Stress VRR

beyond-evals

VRR loses cross-harness comparability when baseline pass rates fall below a threshold or when fault difficulty variance is high, so the same agent can move from VRR 0.9 to 0.6 purely by changing the baseline's health rather than its repair ability.

Proof of concept

Build one small service with a fixed set of seeded faults; run a single QA agent under two harness variants (sandbox-style hand-authored faults, mutation-style generated faults) and under intentionally weakened and strengthened baselines. Compute VRR for every (harness, baseline health) cell and test whether agent rankings are preserved.

Measurement

Rank correlation of agent orderings across harness/baseline cells; variance of VRR attributable to baseline health versus agent identity; number of configurations where a strictly worse agent outscores a better one under VRR.

Source video ↗

Seeded Mutant Replay Harness

gatehouse

Seeded, recorded mutant generation yields near-zero score variance across identical replays while retaining high task-level variability across different seeds, so regression diffs between agent versions become distinguishable from sampling noise.

Proof of concept

Implement generator with explicit seed, a structured mutant record (mutant id, operator type, source location, status), and full run replay from the record. Run the same QA agent 20 times on the same seed and 20 times on different seeds.

Measurement

Within-seed score variance vs. across-seed score variance; replay fidelity (identical mutant set and identical per-mutant verdicts); minimum detectable agent-version score delta at fixed eval budget.

Source video ↗

Compile-Cost Budgeter

movement-lab

Incremental builds plus test selection and mutant batching reduce per-evaluation compile/execute cost by an order of magnitude at unchanged mutant-kill discrimination, which is the difference between mutation scoring being a nightly job and a default per-commit loop.

Proof of concept

Wrap a mutation run over a mid-sized Python repo with three cost strategies (naive full rebuild, incremental build, incremental build + scoped test selection + batched mutants) and measure cost per scored mutant and discrimination between a strong and a deliberately degraded QA agent.

Measurement

Wall-clock and CPU-seconds per evaluation run per strategy; cost per confirmed mutant kill; area under the discrimination curve for strong vs. degraded agent; any loss in detection sensitivity introduced by test selection.

Source video ↗

Layered Fault Ladder

new

A two-layer harness (coarse structural business-logic omissions plus fine local semantic swaps) separates strong from weak QA agents with a larger effect size than either layer alone, because the layers surface different failure modes rather than redundant ones.

Proof of concept

Assemble a coarse-fault suite (whole checks omitted, e.g. missing coupon verification) and a fine-mutation suite over the same baseline; run three QA agents of varying capability against coarse-only, fine-only, and merged suites.

Measurement

Effect size (score gap between strong and weak agents) per suite configuration; correlation of per-agent scores across layers (to test redundancy); marginal discrimination gained per added fault layer per unit compile cost.

Architectural implications

3

The oracle moves from a model to a fault manifest plus pass/fail execution.

Before

An LLM-as-a-judge reviews the QA agent's output and assigns a quality score.

After

A versioned manifest of injected faults and a regression suite determines exactly which faults the agent found and fixed.

Consequence

Scores become reproducible and diffable across agent versions; the harness must own and maintain fault fixtures as first-class assets.

Source video ↗

The QA agent's tool surface includes repair, not just detection.

Before

QA agent reports bugs; humans or a separate developer agent change code.

After

QA agent is tasked with locating and patching faults inside the sandbox against a known target list.

Consequence

The agent needs file-edit plus test-execution loop tooling, and the eval measures end-to-end recovery, coupling QA and dev-agent responsibilities.

Source video ↗

The system under test becomes a mutable branch rather than a fixed environment.

Before

One clean codebase replica, same for every evaluation run.

After

A clean baseline plus per-run generated mutants, with mutant identity/operator/status tracked in a structured model.

Consequence

Evaluation state must be modeled as data (e.g. a Pydantic MutantModel with mutant IDs, operator types, statuses) so results aggregate and replay; harness needs provenance per run.

Tradeoffs and failure modes

4

LLM-as-judge (Big-Bang) evaluation

Benefit

Low setup cost: no fault authoring, no ground-truth manifest, quick to stand up.

Cost or risk

High judge bias and zero runtime verification, so scores can be systematically wrong with no execution evidence.

Source video ↗

Sandbox Target with hand-authored bugs

Benefit

Deterministic tracking of specific known business logic defects and cheap evaluation once authored.

Cost or risk

Low variability: a fixed manifest is a fixed distribution, prone to memorization and not representative of unseen failure modes.

Source video ↗

Mutation-based fault generation

Benefit

High variability and no developer loop to maintain broken codebases.

Cost or risk

High compilation/execution cost; also depends on mutation library maturity, which is a real gap outside Python.

Source video ↗

Using VRR as a cross-environment normalizer

Benefit

A single 0.0-1.0 scalar for recovery that can be compared across sandboxes and mutated builds.

Cost or risk

The normalization claim is asserted, not demonstrated; if baseline pass rates vary wildly, the ratio may not be comparable and could be gamed by a weak baseline.
