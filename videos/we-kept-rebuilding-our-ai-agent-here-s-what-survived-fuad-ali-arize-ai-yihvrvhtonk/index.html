Overview

  • Speaker: Fuad Ali
  • Channel: AI Engineer
  • Main topic: Lessons learned from two years of building and shipping a production AI agent (Alyx at Arize AI)
  • Purpose: Provide architectural insights, practical takeaways, and lessons learned on building production-grade AI agents. Fuad Ali, product manager at Arize AI, shares lessons from two years of shipping and rebuilding their in-product agent, Alyx. The talk covers the evolution of the agent architecture from a router to tool-calling loops to a unified agent with on-demand skill loading and memory. Key themes include the importance of harness code over agent frameworks, handling planning and todo lists in the harness rather than the model, and using production traces as test cases.

Decision 2: What Ends a Turn

  • Explanation: Handling turn completion and stopping rules in the harness rather than relying solely on model prompt adherence.

Key Points

Harness code over agent frameworks

  • Explanation: Building custom harness code for loops, planning, stopping rules, and memory provides maximum control and learning opportunities.
  • Evidence: Arize does not use an agent framework; the loop, plan, stopping rule, and memory are all custom.
  • Practical implication: Engineers should retain control over core orchestration logic rather than relying on black-box frameworks.

Treat huge results like files and grep them

  • Explanation: Passing massive JSON blobs into context windows destroys performance; truncate and let agents query selectively.
  • Evidence: JSON blobs >10MB truncated to previews with IDs, allowing agents to query full data via JQ.
  • Practical implication: Saves context window capacity and reduces latency/cost.

Production sessions as test cases

  • Explanation: Real production user traces provide the best ground-truth regression tests for agent changes.
  • Evidence: Replaying production sessions turn-by-turn to evaluate against today's code.
  • Practical implication: Build test suites directly from live usage data and user interactions.

Examples & Case Studies

  • Lesson: Monitor qualitative metrics like latency and identical tool call counts, not just error status codes.

Deep dives

5

Harness-enforced turn termination versus model-inferred completion

Research question

How much of multi-step agent reliability (task completion rate, premature-stop rate, hang rate) is attributable to code-enforced termination protocols (gated finish calls, iteration limits, force-finish) versus prompt-based done-ness conventions, across model versions?

Why

If termination is truly a constraint problem rather than a capability problem, teams are wasting effort tuning prompts and chasing model upgrades for what is a small amount of harness code. Quantifying the delta tells engineers where to spend their reliability budget and how much model portability they can buy.

Source video ↗

Bookkeeping-in-code: the action-budget competition between meta-tools and the task

Research question

Does exposing meta-tasks (todo lists, self-critique, memory writes) as model-callable tools measurably cannibalize the model's action budget, and does relocating that bookkeeping into harness state reduce iterations and improve completion on multi-step tasks?

Why

This generalizes far beyond todo lists to every 'agentic' tool that looks useful in a schema. A measured answer gives a design rule for tool surfaces: which behaviors belong in the tool schema and which belong in code, with iteration count and completion as the observable cost.

Source video ↗

The bounded text memory ceiling: where always-in-context memory stops beating retrieval

Research question

At what memory size and staleness rate does a bounded per-user markdown memory file stop outperforming vector retrieval or knowledge graphs on task success and stale-fact errors?

Why

The reported result contradicts the default build-retrieval-first instinct, but a single 8,000-character data point does not tell you when the crossover happens. Without a crossover curve, teams cannot know whether their memory needs justify infrastructure or a text file plus an eviction policy.

Source video ↗

Reference-plus-query tool IO and its retrieval failure modes

Research question

When tool results are truncated to previews with IDs and the agent must fetch full data via a query surface (e.g. JQ), what fraction of tasks fail because the agent never issues the follow-up query or queries the wrong path?

Why

Truncation is presented purely as a context-budget win, but it converts a data-availability guarantee into an agent behavior that can silently fail. Measuring the hidden failure rate determines how much preview fidelity and query affordance the harness must provide.

Source video ↗

Replayable sessions as a regression substrate under non-determinism

Research question

How stable and predictive are turn-by-turn replayed production sessions as a regression suite, and what stubbing/scoring design minimizes flake rate while still catching real regressions?

Why

If replay is ground truth, evaluation becomes a trace-fidelity engineering problem rather than a dataset-authoring problem. Flake rate and sensitivity to model upgrades determine whether replay can gate deployments or only inform them.

Article ideas

4

Your Agent Doesn't Need a Better Model, It Needs a Stop Condition

Most production agent failures attributed to model weakness are actually missing control-flow constraints: when planning lives in a model-callable tool and turn completion is inferred from output shape, the agent will loop, stall, or stop early regardless of which model you swap in. The engineering leverage is in the harness, not the model.

Angle

Take the concrete pathologies (20+ iterations maintaining a todo list, plaintext step announcements breaking done-detection) and show that each is a code constraint problem with a code fix; argue that framework abstractions hiding the loop block exactly this work.

Source video ↗

Stop Building Retrieval Before You've Earned It

For user-scoped long-term memory at modest scale, a bounded, human-readable, always-in-context text file can beat vector retrieval and knowledge graphs on both quality and operability; retrieval complexity should be justified by measured failure rather than assumed by default.

Angle

Contrast build cost and debuggability: retrieval pipelines add opaque failure modes, while a capped markdown file makes the real design question an explicit eviction/summarization policy you can inspect and test.

Source video ↗

Fewer Agents, More Loading: Capability Scaling Without Delegation

Decomposing an agent into specialist sub-agents multiplies prompt-token overhead and coordination surface without proportional capability gain; loading skills and tools on demand into one agent is a competing scaling axis whose new critical path is skill-selection quality.

Angle

Trace the architecture's own migration from ten specialists per page to one agent loading skills, and reframe the multi-agent debate around token cost and selection accuracy rather than agent count.

Source video ↗

Observability Is a Test Suite You're Not Using

Production traces are a test-generation substrate: if sessions are designed to be replayable, real usage distributions define your regression set and close the eval-to-production gap better than synthetic agent tests.

Angle

Frame trace fidelity as an evaluation prerequisite, then address the hard part — replaying non-deterministic agents stably enough to gate deployments.

Project ideas

4

Termination Gauntlet

gatehouse

Replacing output-shape-inferred completion with a harness-gated finish protocol (finish rejected while plan items are open, plus iteration limits and force-finish) reduces premature-stop and hang rates on multi-step tasks by a large margin, and this gain transfers across at least three model families with no prompt changes.

Proof of concept

Build a minimal agent harness with two modes — (A) done inferred from text-without-tool-call, (B) explicit finish call gated by harness plan state — and run both against the same set of 20 multi-step tasks with mid-run model swaps.

Measurement

Task completion rate, premature-stop rate, hang/timeout rate, and mean iterations per task for each mode and each model, reported as a cross-over table; a gain that does not transfer across models falsifies the portability claim.

Source video ↗

Meta-Tool Tax Ablation

movement-lab

Exposing planning as a model-callable todo tool increases total iterations and reduces task success relative to harness-owned plan state, and the tax grows with the number of meta-tools exposed in the schema.

Proof of concept

Implement three plan representations on identical tasks: (A) todo tool, (B) plan state injected as messages, (C) system-injected plan summary plus harness completion check. Instrument every iteration by tool called.

Measurement

Iterations spent on bookkeeping versus task tools, total iterations, and task success rate per condition; a flat or inverted result across conditions falsifies the action-budget-competition account.

Source video ↗

Memory Crossover Curve

new

A bounded always-in-context markdown memory beats vector retrieval and graph memory up to a threshold memory size and staleness rate, beyond which retrieval wins; the crossover is measurable and predictable from user-scoped fact count.

Proof of concept

Build a synthetic per-user session stream with controllable fact count and staleness, and run four memory backends — 2k/8k/32k-char markdown, vector retrieval, knowledge graph — on identical session-level tasks.

Measurement

Task success and stale-fact error rate as a function of fact count per user, plotted per backend, to locate the crossover; a monotonic retrieval win at all sizes falsifies the bounded-file claim.

Source video ↗

Preview-Then-Query Harness

beyond-evals

Truncating large tool payloads to previews with IDs plus an agent-driven query surface (JQ/grep) cuts context tokens and latency on large-payload tasks without reducing task success — provided the harness detects and retries agents that never issue the follow-up query.

Proof of concept

Implement a tool-IO layer with three modes — full payload, truncated preview plus JQ query tool, truncated preview plus JQ query tool and a harness nudge on unqueried IDs — over 10MB-scale JSON trace data.

Measurement

Context tokens per task, latency, task success, and the rate of silent retrieval failure (truncated ID never queried); a success drop that the nudge does not recover falsifies the reference-plus-query pattern at this payload scale.

Architectural implications

5

Ownership of the plan moved from the model to the harness.

Before

Plan/todo list exposed as a model-callable tool; the model decides when to create and update plan items.

After

Plan state held in harness state and surfaced in messages; harness enforces completion checks against open items.

Consequence

Eliminates planning-loop pathologies and makes task completion a code-checkable predicate rather than a model judgment.

Source video ↗

Termination logic moved from prompt convention to code constraint.

Before

Turn ends when the model emits text with no tool call, with done-ness reinforced via prompting.

After

Explicit finish call gated by harness; finish is rejected while plan items remain open, backed by iteration limits and force-finish.

Consequence

Stable multi-step execution across model versions whose plaintext conventions differ, at the cost of harness complexity.

Source video ↗

Capability scaling moved from agent decomposition to on-demand skill/tool loading.

Before

Many specialist sub-agents, each with its own prompt and tool surface, selected per page/context.

After

One agent that loads skills and tools on demand.

Consequence

Lower prompt-token overhead and fewer coordination surfaces; skill-selection quality becomes the new critical path.

Long-term memory moved from retrieval infrastructure to a bounded text artifact.

Before

Vector retrieval and knowledge graphs for user memory.

After

A per-user markdown file capped at 8,000 characters, updated by a background job with checkpointing.

Consequence

Memory becomes inspectable and cheap to debug; the cap makes eviction/summarization policy the main design question.

Tradeoffs and failure modes

5

Custom harness vs agent framework

Benefit

Full control over loop, plan, stopping rule, and memory; the ability to place constraints in code.

Cost or risk

All orchestration, streaming, and telemetry behavior must be built and debugged in-house; framework conveniences and ecosystem features are forgone.

Source video ↗

Truncated tool results

Benefit

Avoids context window bloat and reduces cost/latency on large structured payloads.

Cost or risk

The agent must issue follow-up queries to see data; a missing or wrong query path hides information it may have needed.

Source video ↗

Capped markdown memory

Benefit

Simple, inspectable, and reportedly better than knowledge graphs and vector retrieval at this scale.

Cost or risk

An 8,000-character ceiling forces information loss; behavior under larger memory requirements is untested.

Source video ↗

Fast-and-good-enough default model vs newest model

Benefit

Lower latency/cost as the default choice.

Cost or risk

Capability regressions on hard steps; the tradeoff is asserted rather than quantified in the summary.

Source video ↗

Silent failure via streaming telemetry

Benefit

Streaming tool calls are the responsive path for long agent runs.

Cost or risk

Telemetry returning zero completion tokens on streamed tool calls made the agent appear hung — failure mode invisible without trace-level inspection.
