Summary

Overview

  • Speaker: Karan Vaidya
  • Channel: AI Engineer
  • Main topic: Bridging AI agents from code-based tasks to knowledge work across various SaaS platforms
  • Purpose: To explain the gap between coding agents and knowledge work agents and introduce infrastructural primitives required to make knowledge work agents reliable, safe, and trustworthy. Karan Vaidya, CTO and co-founder of Composio, explores why AI agents have advanced rapidly in software engineering compared to general knowledge work. He analyzes the core primitives present in coding environments—centralization, history, context, verification, governance, and reversibility—and presents Composio's infrastructure built to bring these primitives to knowledge work agents.

Key Points

Coding agents succeeded due to existing infrastructure

  • Explanation: Git, monorepos, linters, compilers, and CI/CD pipelines provided a ready-made ecosystem of guardrails for coding agents.
  • Evidence: Growth of coding agents from autocomplete to autonomous coders over 3 years.
  • Practical implication: To make knowledge work agents work, we must build similar infrastructural primitives.

Knowledge work lacks centralization and memory

  • Explanation: Data in knowledge work is scattered across Salesforce, Notion, Gmail, Slack, and Zendesk with no single source of truth.
  • Evidence: Deals scattered across five separate platforms with independent logins.
  • Practical implication: Agents need a centralized hub to access all connected applications and account histories.

Verification and sandboxing prevent disaster

  • Explanation: Unlike code compilers that catch errors before building, knowledge work tools execute immediately without testing.
  • Evidence: Mass outreach email disaster where valid emails reached real people inappropriately.
  • Practical implication: Agents must test actions in sandboxes and check drafts against style guides before execution.

Core insights

6
[O]Mental Modelmedium noveltymoderate evidence

Coding agents advanced not because of a superior model but because the surrounding infrastructure already supplied agent-grade primitives (version history, compilation/tests as pre-execution verification, code owners/branch rules as governance, revert as reversibility). Knowledge work lacks all six, so agents 'work blind' regardless of model quality.

Why it matters

Reframes the agent reliability problem from a model-capability problem to an environment-primitive problem, which changes what an engineer should build and where to spend effort: harness and control-plane work, not prompt work.

Generalization

Agent capability in any domain is bounded by the domain's pre-existing verification, history, and reversibility substrate; where that substrate is missing, it must be engineered rather than waited for.

[M]Mechanismhigh noveltymoderate evidence

Knowledge-work tools have no compiler-equivalent gate: every tool call mutates real state immediately. The proposed mechanism is a synthesized verification stage — mock/sandbox the real-world tool, execute the action there, and check the draft against style guides and policies before issuing the real API call.

Why it matters

Gives a concrete pre-flight verification pattern for side-effecting tool calls, the single biggest reliability gap between coding agents (dry-run/compile/test) and productivity agents.

Generalization

Any agent with irreversible external side effects needs a shadow-execution layer that reproduces the call's semantics without touching production, plus automated acceptance checks, before the real call is allowed.

Source video ↗
[~]Tradeoffhigh noveltymoderate evidence

Reversibility is architecturally asymmetric across domains: code has revert, sent email does not. Where undo is impossible, the architecture must shift the control point earlier — from post-hoc rollback to pre-execution approval pathways and sandboxing.

Why it matters

Determines whether an agent platform needs an undo log, an approval queue, or both, and where latency and human-in-the-loop cost are incurred.

Generalization

Design recovery mechanisms per action class: reversible actions get automatic rollback/compensation logs; irreversible actions get blocking approval gates, since no rollback can be retrofitted.

Source video ↗
[A]Architecturemedium noveltyweak evidence

Governance is proposed as two distinct layers with different properties: deterministic guardrails/access control (machine-checkable, enforced) and natural-language policies (expressive, human-authored). The NL layer expresses intent; the deterministic layer enforces it.

Why it matters

Splits policy expression from policy enforcement, which is the boundary that makes enterprise agent deployment auditable; conflating the two produces either unenforceable prose or brittle hand-coded rules.

Generalization

Agent policy systems need a declarative intent layer compiled down to deterministic enforcement points at the tool-call boundary, analogous to IaC or policy-as-code.

Source video ↗
[M]Mechanismmedium noveltyweak evidence

Memory for knowledge-work agents is framed as an event log of the agent's own past actions and organizational workflow, not a vector store of documents — i.e., history of executed operations serves as both recall context and audit trail.

Why it matters

Suggests the durable memory primitive is a write-ahead/event-sourced action log at the tool layer, which simultaneously provides observability, replay, and context for future runs.

Generalization

Action logs and context stores should be the same substrate when agents must both remember and be audited; separating them duplicates state and desynchronizes recall from reality.

[E]Empirical Resultmedium noveltyweak evidence

Tool-call volume is heavily concentrated: roughly half of all agent tool calls occur in software engineering, while finance, marketing, support, and sales trail far behind.

Why it matters

Quantifies the domain disparity and supports treating knowledge-work agent infrastructure as an under-built, early market rather than a solved layer.

Generalization

Distribution of agent tool-call traffic is a usable proxy for where agent infrastructure is mature versus where primitives are still missing.

Deep dives

5

Shadow-execution verification for side-effecting SaaS tool calls

Research question

Can a mock/sandbox execution layer placed between agent and production API catch bad actions as reliably as compilers and tests catch bad code, and how does mock fidelity decay over time?

Why

Verification is the single biggest structural gap between coding agents (compile/dry-run/test) and knowledge-work agents; without a pre-flight gate every tool call is a production mutation. The value hinges on whether mocked SaaS semantics can stay faithful enough to make pre-flight failures predictive rather than theater.

Source video ↗

Reversibility taxonomy and compensation semantics per action class

Research question

What is a workable classification of agent actions by reversibility, and what containment mechanism (undo log, approval gate, staged batching, recall window) should each class receive?

Why

Reversibility is asymmetric across domains — code has revert, a sent email does not — so the architecture must choose between post-hoc rollback and pre-execution blocking. Getting the class map wrong either wastes human review on reversible actions or leaves irreversible ones unguarded.

Source video ↗

Compiling natural-language policy into deterministic tool-call enforcement

Research question

Can an NL policy layer be compiled down to deterministic guardrails at the tool-call boundary with measurable enforcement coverage and acceptable false-block rates across a large heterogeneous SaaS catalog?

Why

The two-layer governance proposal (deterministic guardrails plus NL policies) is only useful if intent in prose actually lands as machine-checkable enforcement; otherwise it is either unenforceable documentation or brittle hand-coded rules that fail at thousands-of-tools scale.

Source video ↗

Event-sourced action logs as unified memory, audit, and replay substrate

Research question

Does deriving agent recall context from the same event log that provides audit and replay outperform a separate document-retrieval memory store on multi-step knowledge-work tasks?

Why

If action history and context are the same substrate, recall cannot desynchronize from reality and replay/debugging come free; if they are split, state is duplicated and agents recall documents rather than what actually happened. This is testable and determines a core data-model decision.

Source video ↗

Isolating the primitive deficit from model capability in agent performance

Research question

On matched tasks across domains, how much of the coding-versus-knowledge-work agent performance gap is attributable to the six primitives versus model capability and task difficulty?

Why

The central causal claim — that missing primitives, not model weakness, explain knowledge-work agent failure — is asserted with illustrative evidence and no ablation. Without an isolation experiment, engineers cannot know whether to invest in harness infrastructure or wait for the next model.

Article ideas

4

Your Agent Isn't Dumb, Your Domain Has No Compiler

Knowledge-work agents underperform coding agents primarily because their environments lack pre-execution verification, history, and reversibility — not because models are weaker — so the highest-leverage engineering investment is a shadow-execution and governance control plane, not better prompting.

Angle

Reframe agent reliability from a model-capability problem to an environment-primitive problem, using the six primitives as a diagnostic checklist any team can run against its own domain.

Source video ↗

Nothing Has a Revert Button: Designing for Irreversible Agent Actions

Because undo semantics cannot be retrofitted onto sent emails or external API writes, agent platforms must classify actions by reversibility and shift the control point upstream — routing irreversible classes through approval gates and staged execution rather than a generic undo handler.

Angle

A design-patterns piece organized around an action-reversibility taxonomy, exposing the latency and human-review costs each gate introduces.

Source video ↗

Policy You Can't Enforce Is Just Documentation

Enterprise agent governance only works when natural-language policy intent is compiled down to deterministic enforcement points at the tool-call boundary; conflating prose policy with access control produces either unenforceable intent or brittle hand-coded rules that break at SaaS-catalog scale.

Angle

Contrast the two governance layers by their failure modes, arguing for a policy-as-code compilation step analogous to IaC.

Project ideas

4

Mock-Fidelity Harness

gatehouse

A sandbox that replays each SaaS tool against a recorded production contract will catch a measurably higher fraction of bad agent actions than schema-only validation, and its catch rate degrades predictably as mock/production divergence grows.

Proof of concept

Wrap 5 common SaaS APIs (Gmail send, Slack post, Notion write, Zendesk ticket, Salesforce update) behind an interception layer; for each, run 100 agent-generated actions through (a) no gate, (b) schema-only validation, (c) mock execution. Score each action as would-fail-in-production or acceptable using human labels, then inject drift into the mocks and re-measure.

Measurement

Precision/recall of pre-execution failure detection per gating strategy; catch-rate delta between fresh and drifted mocks; added latency per tool call.

Source video ↗

Reversibility Router

gatehouse

Routing agent actions through class-specific gates (auto-rollback for reversible, blocking approval for irreversible) preserves task completion rate while eliminating irreversible-harm incidents that a uniform approval policy would also block but at much higher review cost.

Proof of concept

Build an action-classification layer over a small agent that drafts and sends outreach email, posts to Slack, and updates CRM records; implement three modes — blanket approval, reversibility-routed, and no gate — and run identical task suites in each, with a simulated spam-disaster scenario.

Measurement

Irreversible-harm incidents per 100 runs; human review minutes consumed per completed task; task completion rate and end-to-end latency per mode.

Source video ↗

Policy Compiler Bench

gatehouse

A declarative NL policy layer compiled to tool-call guardrails over a normalized permission schema can achieve high enforcement coverage on a large SaaS catalog with a false-block rate low enough to be usable, and outperforms hand-coded rules on coverage.

Proof of concept

Normalize permissions for 50 tool actions, author 30 organizational policies in prose, compile each to guardrail predicates, then replay a labeled set of allowed/forbidden agent tool calls and compare the compiled layer against hand-coded rules and against an LLM-judge policy check.

Measurement

Enforcement coverage (forbidden calls blocked), false-block rate on allowed calls, inter-policy conflict count, and authoring time per policy across the three approaches.

Source video ↗

Action-Log Memory Ablation

beyond-evals

Agents whose recall context is assembled from an event log of their own executed tool actions complete multi-step knowledge-work tasks more reliably than agents using a document-retrieval memory store, with the advantage growing with task length.

Proof of concept

Implement a small cross-app workflow agent (read Slack thread, draft reply, update Notion, send email) with two interchangeable memory backends: event-sourced action log versus vector store over documents. Run matched task suites at 3, 5, and 10 steps, then test replay-based debugging on failures.

Measurement

Task success rate by backend and task length; contradictory-action rate; time-to-diagnose injected failures via replay; context tokens consumed per step.

Architectural implications

4

Knowledge work is fragmented across Salesforce, Notion, Gmail, Slack, and Zendesk with independent logins and no single source of truth, whereas coding starts from a monorepo.

Before

Each agent integration is a standalone connector with its own auth, schema, and no shared view of the user's account state.

After

A centralized toolkit layer owns app connections and logins and exposes a single surface plus shared account history to the agent.

Consequence

Authentication, rate limiting, and cross-app context move out of the agent and into an infrastructure tier, making the agent prompt-independent of integration details.

Source video ↗

Verification currently happens after the real action, because productivity APIs have no compile step.

Before

Agent emits the tool call; the SaaS API executes it; errors and inappropriate sends surface to end users.

After

A sandbox/mock execution stage plus draft checking sits between the agent and the real API, gating the production call.

Consequence

Adds a mandatory middleware hop and a second execution path to maintain, but converts silent side effects into catchable pre-execution failures.

Source video ↗

Irreversible actions have no rollback primitive equivalent to git revert.

Before

Reversibility is assumed to be a generic property handled by an undo function.

After

Actions are classified by reversibility, and irreversible classes are routed through approval pathways rather than undo handlers.

Consequence

Human-in-the-loop cost and latency become an explicit function of action class, not a blanket policy.

Source video ↗

Agent memory today is often a separate retrieval store detached from what the agent actually did.

Before

Context is assembled from documents and embeddings; executed actions are logged elsewhere or not at all.

After

An event log of agent actions feeds both observability and future context assembly.

Consequence

Audit, replay, and recall derive from one source, simplifying debugging of multi-step workflows.

Source video ↗

Tradeoffs and failure modes

4

Sandbox-before-execute verification

Benefit

Catches bad or inappropriate actions before they reach real users and external systems.

Cost or risk

Doubles execution paths and requires faithfully mocking each SaaS API; a mock that diverges from production semantics yields false confidence.

Source video ↗

Approval pathways for irreversible actions

Benefit

Prevents unrecoverable harm where no undo exists.

Cost or risk

Serializes work behind human review, reintroducing latency and a review bottleneck precisely on the highest-value actions.

Source video ↗

Natural-language governance policies

Benefit

Expresses organizational intent without hand-coding every rule.

Cost or risk

Policy in prose is not deterministically enforceable unless compiled to guardrails; ambiguity at scale across thousands of SaaS tools is unresolved.

Source video ↗

Missing verification, history, and governance in outreach agents

Benefit

Agent autonomously personalizes and sends outreach at scale.

Cost or risk

Without pre-flight sandboxing or governance walls, valid addresses receive spam and the failure becomes public, converting a tooling bug into reputational damage.
