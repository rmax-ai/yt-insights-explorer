In this hands-on workshop presented at AI Engineer New York by Sonar, Taylor Luttrell-Williams and Killian Carlsen-Phelan introduce Gitar, Sonar's AI code verification agent. They discuss the challenges of AI-generated code creating review bottlenecks and production incidents, and demonstrate how Gitar automates end-to-end verification, CI diagnosis, and autonomous fixes for pull requests.

Key Points

AI Code Generation Outpaces Human Review

  • Explanation: AI coding agents increase the volume of code written, leading to overloaded review queues and higher production failure rates.
  • Evidence: More code changes generated by AI equals more reviews, more CI failures, and more incidents.
  • Practical implication: Teams need automated verification agents to keep pace with AI-generated code.

Gitar Focuses on High Signal-to-Noise Ratio

  • Explanation: To avoid token waste and developer fatigue, Gitar is tuned for high signal-to-noise, minimizing false positives and autonomous errors.
  • Evidence: Every false positive consumes tokens and risks unintended changes.
  • Practical implication: High precision reduces review burden and token expenses.

Combining Static Analysis with Context and Intent

  • Explanation: Static analysis tools like SonarQube catch syntax and security bugs, but AI verification agents like Gitar infer intent and business logic.
  • Evidence: Static tools cannot infer business intent from titles and descriptions alone; both layers are needed.
  • Practical implication: Layering static analysis and agentic verification ensures complete code correctness.

Core insights

6
[A]Architecturemedium noveltymoderate evidence

Verification is being factored out as an independent agent that is decoupled from the agent that writes the code, rather than being a step inside the generation loop or a human reviewer's job.

Why it matters

It creates a clean trust boundary: the generating agent's self-assessment is not the gate; a separate system with its own context, rules, and merge authority decides. This makes review automatable and auditable independent of which coding agent produced the diff.

Generalization

Any pipeline where a generative agent produces artifacts with side effects eventually needs a separately owned verifier with independent context and its own pass/fail authority, not in-loop self-critique.

[A]Architecturemedium noveltymoderate evidence

Deterministic static analysis and agentic inference occupy different detection layers: static tooling catches syntax and security defects, while an LLM-based verifier infers intent and cross-workflow business invariants. Neither layer substitutes for the other.

Why it matters

It reframes the build-vs-buy question away from 'replace the linter with an agent' toward a layered stack where the cheap deterministic layer filters and the expensive inference layer handles semantics — which also bounds token cost.

Generalization

For any property you want to enforce on artifacts, split checks into deterministic validators (fast, cheap, exact) and semantic inference (slow, costly, approximate), and route only the residue to the expensive layer.

Source video ↗
[M]Mechanismmedium noveltyweak evidence

The defect class that survives human and static review is the cross-entity invariant — e.g., a PR that enables ticket transfer but leaves cancel-original-order unable to invalidate the transferred ticket. These are whole-workflow properties, not line-level defects.

Why it matters

It gives a concrete target for what an AI verifier should be evaluated on: multi-step state transitions across entities, which requires the verifier to hold a workflow model rather than only the diff.

Generalization

Validation of agent output should include whole-system invariants spanning multiple operations, because per-hunk review structurally cannot observe them.

Source video ↗
[~]Tradeoffmedium noveltymoderate evidence

False positives are treated as a direct cost vector, not just an annoyance: each one burns tokens and can trigger an unintended autonomous edit. Precision therefore bounds both spend and blast radius in an auto-fixing agent.

Why it matters

For agents with write access, recall-oriented tuning is dangerous — a wrong finding becomes a wrong commit. This inverts the usual 'catch everything' review heuristic.

Generalization

For any agent with mutation rights, optimize precision before recall and gate autonomy on confidence, because the cost function of a false positive is an applied change rather than a dismissed alert.

Source video ↗
[M]Mechanismmedium noveltymoderate evidence

CI remediation requires a classification step before action: distinguishing genuine breakages from infrastructure noise, then looping fix→rerun until checks pass.

Why it matters

Naively reacting to every red build causes an agent to 'fix' code in response to flaky infra, corrupting a green codebase. A triage classifier between signal and noise is a required component, not a nicety.

Generalization

Any agent that acts on monitoring signals needs a signal-quality classifier upstream; otherwise it optimizes against noise and produces confident, harmful edits.

Source video ↗
[P]Practicemedium noveltymoderate evidence

Business logic is supplied to the verifier as configuration artifacts — review directories, rules, and knowledge — rather than being expected to emerge from reading code.

Why it matters

It makes review behavior an explicit, versioned, reviewable input. That is the difference between a verifier you can reason about and one whose judgments shift with each model change.

Generalization

Agent behavior should be driven by inspectable, version-controlled policy artifacts (rules, knowledge bases, scoped directories), not only by implicit model priors.

Deep dives

5

Precision-first calibration for write-capable verification agents

Research question

On a labeled set of real pull-request defects, what is the precision/recall frontier of an LLM verifier at each autonomy tier (comment-only, propose-fix, auto-merge), and how many false positives must be tolerated per true positive at each tier before the error cost (tokens + applied wrong edits) exceeds the cost of a missed defect?

Why

Once the verifier has merge authority, a false positive stops being a dismissed alert and becomes an applied commit. This inverts the standard recall-oriented review heuristic and makes the confidence threshold a load-bearing design parameter rather than a tuning knob.

Source video ↗

Benchmarking cross-entity invariant detection

Research question

Can a verification agent detect whole-workflow invariants (transfer enables a state transition that the cancel path does not invalidate) at a rate materially above static-analysis-only and diff-only review baselines, and does that rate degrade as repository size and history depth grow?

Why

This names the concrete defect class the system exists to catch and gives a falsifiable target. If the verifier's advantage over static rules on this class is small, the inference layer's cost is not justified.

Source video ↗

Signal-quality triage upstream of autonomous remediation

Research question

What classification accuracy separates genuine breakage from infrastructure-only failure on historical build logs, and what is the downstream damage rate of each misclassification direction (spurious code edits vs ignored real regressions) in an agent that acts on red builds?

Why

An agent that treats CI as a boolean will confidently edit green code in response to flake. The triage classifier has its own error modes that must be measured before autonomy is granted, because one direction silently corrupts the codebase and the other silently ships regressions.

Source video ↗

Encoded policy artifacts as the verifier's specification

Research question

How much does detection of business-rule violations improve when rules are supplied as explicit versioned configuration (review directories, rule sets, knowledge artifacts) versus relying on model priors over the diff, and do rules reduce false positives as well as lift true positives?

Why

If encoded rules are the real driver of accuracy, then review quality is a configuration-management problem with a diffable, reviewable surface — and gaps in rules become silent policy holes rather than model weaknesses.

Source video ↗

Termination and divergence bounds on autonomous fix loops

Research question

Across multi-iteration fix→rerun remediation cycles, how do iteration count, net diff growth, and revert rate interact, and is there an iteration budget beyond which self-repair degrades code quality rather than improving it?

Why

'Iterate until CI passes' is an unbounded objective with a proxy metric. Instrumenting convergence is the only way to know whether the loop repairs or churns, and to set a defensible rollback condition.

Article ideas

4

Your Verifier Cannot Be Your Generator

Review must be a separately owned system with its own context and its own merge authority, because a generating agent's self-assessment is a structurally insufficient gate: it shares the blind spots that produced the defect, and it cannot authoritatively decide to stop itself.

Angle

Argue the trust-boundary case for out-of-loop verification using the cross-entity invariant failure — a bug that is invisible to per-hunk review and to the agent that wrote the hunk — then derive what the verifier must own (context ingestion, rules, pass/fail authority) that an in-loop critic cannot.

Source video ↗

When the Reviewer Can Commit, Optimize Precision

Agents with write access invert the economics of review: a false positive becomes an applied edit, so recall-first tuning is actively harmful and autonomy level must be gated on calibrated confidence rather than uniform.

Angle

Reframe the review metrics debate around the cost function — tokens burned plus unintended code changes — and show why 'catch everything' is a safe heuristic only for read-only reviewers.

Source video ↗

The Bug That Survives Every Review: Cross-Entity Invariants

Per-diff review, human or automated, structurally cannot observe whole-workflow properties; the durable defect class is state that must be invalidated across entities, and catching it requires the verifier to hold a workflow model rather than a patch.

Angle

Use the ticket-transfer / order-cancel gap as the canonical example and generalize it to any multi-step state machine, then argue that 'more hunks reviewed' is the wrong scaling axis.

Source video ↗

A Red Build Is Not a Boolean

Autonomous remediation agents need a signal-quality classifier upstream of action, because CI output is an ambiguous measurement of code correctness mixed with infrastructure variance — and an agent that edits code in response to flake will confidently corrupt a green codebase.

Angle

Draw the structural parallel to alerting pipelines and show that the missing component in most agent loops is triage, not repair capability.

Project ideas

4

Invariant Oracle

beyond-evals

An LLM verifier with repository-level workflow context detects cross-entity invariant violations in pull requests at a materially higher rate than static-analysis-only and diff-only-review baselines, and the gap persists but narrows as repository size increases.

Proof of concept

Curate 60–100 real merged PRs from 5 mid-size Python/TypeScript repos with known downstream regressions or invariant breaks (transfer/cancel, refund/ledger, soft-delete/orphan, permission-revoke). Score every PR four ways under identical prompts: static rules only, diff-only LLM review, verifier with workflow-context retrieval, and human review. Blind-label each finding against the known defect.

Measurement

Per-arm precision, recall, and defect-escape rate on the invariant class specifically; retrieval recall (fraction of known invariants surfaced in the assembled context); and the same metrics stratified by repository size to expose the degradation curve.

Source video ↗

Autonomy Gate Ladder

gatehouse

For a verifier with write access, a calibrated-confidence gate that escalates between comment-only, propose-fix, and auto-merge tiers achieves lower total cost (tokens + wrong applied edits) per true defect than either a single recall-first threshold or a single precision-first threshold.

Proof of concept

Build a gating wrapper that takes verifier findings plus a confidence score and routes each to one of three autonomy tiers under a configurable threshold policy. Replay the same PR corpus through several threshold policies and tally the applied-edit cost of each false positive against the token cost of each miss.

Measurement

Cost per true positive under each policy (dollars: tokens + engineer-minutes to revert wrong edits); false-positive-to-true-positive ratio per tier; and threshold stability across repeated runs of the same PR set.

Source video ↗

Flake-or-Break

gatehouse

A triage classifier trained on historical build logs and rerun outcomes separates infrastructure noise from genuine breakage accurately enough that an agent gating on it produces fewer spurious code edits than an agent reacting to every red build, without increasing escaped regressions.

Proof of concept

Assemble historical CI failures with ground truth from rerun-without-changes outcomes (green on rerun = noise) and post-merge incident linkage (real breakage). Train a small classifier over log signatures, affected-test identity, and flakiness history. Wire it in front of an automated remediation agent on a sandbox repo and compare edit behavior against the ungated baseline.

Measurement

Triage AUC and per-class precision/recall; spurious-edit rate; escaped-regression rate; and the fraction of agent iterations eliminated by suppressing noise-triggered runs.

Source video ↗

Fix-Loop Divergence Meter

new

Autonomous fix→rerun loops exhibit a detectable convergence signature (shrinking diff, stable test-set delta) that diverges measurably before quality degradation, so a simple iteration-budget rule can cut remediation cost without increasing revert rate.

Proof of concept

Instrument a self-repair loop to record per-iteration diff size, files touched, tests transitioned (fail→pass and pass→fail), and token spend, across a set of injected-defect tasks. Plot the trajectories and identify iterations after which net progress is negative, then test a budget rule that terminates at that point.

Measurement

Iteration count and token spend per successful fix; net diff growth per iteration; pass→fail test transitions (churn proxy); revert rate and post-merge defect rate under the budget rule versus unbounded looping.

Architectural implications

3

Merge authority is delegated to the verification agent, ending the loop at merge rather than at a report.

Before

Agent produces a PR; a human must read the findings, decide, and press merge.

After

Agent reviews, fixes, triages CI, and drives the change to merge under configured branch rules and status checks.

Consequence

The bottleneck moves from human attention to verifier precision and rule quality; a false positive now has merge-path consequences, so precision and gating policy become the critical design surface.

Source video ↗

Verification context is decoupled from generation context and assembled independently.

Before

The reviewer (human or model) sees only the diff and PR description.

After

The verifier ingests repository context, workflow knowledge, and encoded business rules, and infers intent.

Consequence

Context assembly becomes an owned subsystem with its own ingestion cost and staleness risk; the verifier's recall depends on how well enterprise codebases can be ingested.

Source video ↗

CI results are treated as an ambiguous signal requiring interpretation rather than a boolean gate.

Before

Red build = broken code; the pipeline halts.

After

Red build is classified into real breakage vs infrastructure noise before any remediation is attempted.

Consequence

Adds a triage layer with its own error modes; misclassification in either direction yields either spurious code edits or ignored real regressions.

Source video ↗

Tradeoffs and failure modes

4

Autonomous fix loops gated on CI passing

Benefit

Removes manual review-and-repair cycles and runs unattended to merge.

Cost or risk

Test-passing is a proxy for correctness; an agent can satisfy CI while missing business invariants, and unbounded iteration carries token cost.

Source video ↗

High precision over high recall

Benefit

Reduces developer fatigue, token spend, and the chance of unwanted edits.

Cost or risk

Suppressing low-confidence findings systematically leaks the rare-but-real business-logic bug the system exists to catch.

Source video ↗

Speed of generation vs capacity to verify

Benefit

AI agents raise code throughput substantially.

Cost or risk

Review queues and unverified changes grow in lockstep, converting velocity gains into production incidents.

Source video ↗

Automated pass/fail gating on PRs

Benefit

Enables consistent, scalable enforcement without human latency.

Cost or risk

Enforcement quality is only as good as the encoded rules; gaps in rules become silent policy holes that pass every gate.
