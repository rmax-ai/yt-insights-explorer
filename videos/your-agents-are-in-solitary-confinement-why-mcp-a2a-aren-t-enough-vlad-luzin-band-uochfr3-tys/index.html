Overview

  • Speaker: Vlad Luzin
  • Channel: AI Engineer
  • Main topic: Multi-Agent Communication and Collaboration Infrastructure
  • Purpose: To explain the technical challenges of multi-agent distributed systems and introduce Band's multi-agent collaboration layer and Jam as solutions. Vlad Luzin, co-founder and CTO at Band, explores the limitations of current multi-agent coordination approaches such as MCP and A2A. He argues that autonomous AI agents currently exist in 'digital solitary confinement'—isolated in different frameworks, languages, and environments without native communication, discovery, queuing, or governance. He introduces Band's multi-agent collaboration layer and the desktop app Jam, which solve routing, context overload, cost attribution, and multi-agent/multi-human collaboration.

[O]Mental Modelhigh noveltymoderate evidence

MCP and A2A solve only the protocol handshake, not the infrastructure around it: MCP is stateless tool calling and A2A is client/server requiring hand-built bi-directional setup, with no native discovery, queuing, persistence, or stateful session continuity. The speaker reframes remote agent interconnection as a distributed systems problem rather than a tool-call problem.

Why it matters

If you design multi-agent systems on top of MCP/A2A alone, you implicitly own retries, ordering, discovery, session persistence, and identity yourself — but likely without recognizing it, so these concerns end up scattered ad hoc through agent code instead of being a designed layer.

Generalization

Any time an abstraction is described only in terms of message format, ask what transport, continuity, and governance guarantees it does not provide; those missing guarantees are the real engineering surface.

[A]Architecturemedium noveltymoderate evidence

The proposed collaboration layer decomposes into four separable responsibility tiers: transport (real-time delivery, ordering, retries) / continuity (persistence, hydration, runtime binding) / conversation (rooms, participants, routing) / governance (identity, audit, tenancy). This is a concrete allocation of responsibilities that most agent stacks currently conflate into a single 'agent loop'.

Why it matters

Gives a checklist for auditing where each concern lives in your system and a seam structure that lets you swap agent frameworks or transports independently of conversation and audit semantics.

Generalization

Layering a stateful multi-actor system as transport / continuity / conversation / governance is reusable across agent frameworks, and mirrors how messaging and distributed middleware evolved before it.

[M]Mechanismmedium noveltymoderate evidence

The 'continuity' concept — persistence, hydration, and runtime binding as a first-class layer — implies agent processes are ephemeral and must be re-bound to durable conversation state on restart. Agent lifetime and conversation lifetime are different things and must be decoupled.

Why it matters

Most frameworks keep session state in-process, so a crash, redeploy, or scale-to-zero loses the conversation thread and any in-flight task. Naming hydration/runtime binding as a layer forces an explicit persistence boundary.

Generalization

For any long-running autonomous actor, externalize conversation/task state and treat the process as a disposable runtime that binds to it, rather than treating the process as the source of truth.

Deep dives

4

Continuity as a substitutable layer: hydration and runtime binding across heterogeneous agent frameworks

Research question

Can Codex-, LangGraph-, and Claude-Code-style runtimes be adapted behind a single continuity interface such that a mid-task process kill, redeploy, or scale-to-zero followed by hydration restores equivalent task state, with no framework-specific state leaking into the conversation layer?

Why

Every framework today treats the process as the source of truth for session state. If continuity is a real layer, it must be swappable and framework-agnostic, which is the precondition for horizontal scaling, crash recovery, and testing multi-agent topologies instead of hand-building them. If it is not swappable, 'continuity layer' is product framing rather than architecture, and every integration is still an O(n^2) adapter.

Source video ↗

Does a central collaboration broker preserve the delivery guarantees it claims to add?

Research question

Under partial failures, does routing agent-to-agent traffic through a shared broker produce fewer ordering violations and lost messages than point-to-point adapters, or does it reintroduce duplicate deliveries on retry and add a p95 hop latency penalty that exceeds the reliability gain?

Why

The entire case for a collaboration layer rests on it owning transport semantics (real-time delivery, ordering, retries) better than hand-rolled adapters. That is a measurable claim, not an architectural one, and it is untested in the source material. A broker that silently duplicates on retry is worse than a bespoke handler because the failure is now invisible to the agent author.

Source video ↗

Discovery placement: protocol extension versus proprietary registry

Research question

Is agent discovery better solved as a protocol concern (well-known endpoint plus capability manifest, extensible within A2A) or as a registry-broker concern, when compared on cold-start lookup latency, staleness of capability advertisements, and revocation of a compromised agent?

Why

The speaker asserts protocols lack native discovery and offers a product registry as the answer without arguing that discovery belongs outside the protocol. If discovery is cheap to standardize, the central layer loses one of its four pillars and the coupling decision becomes much less defensible; if revocation and staleness are genuinely hard, that difficulty is the moat and should be documented as such.

Source video ↗

Per-agent identity as the primary key for security and cost attribution in shared rooms

Research question

What is the minimum identity and telemetry schema (agent principal, delegating human, task, turn) that simultaneously supports scoped delegation for cross-tenant agent rooms and answers 'which agent and which developer spent these tokens on this task' without retrofitting?

Why

The source positions governance (identity, audit, tenancy) and cost attribution as two separate problems, but they share a primary key. Getting that key wrong makes both unsolvable later, because agents are multiplexed across users and rooms by then. It also determines whether a shared room is an impersonation and prompt-injection surface with no attributable actor.

Article ideas

4

Your Protocol Specifies the Envelope, Not the Infrastructure

MCP and A2A are message-format agreements, and teams that adopt them believing they have solved agent interconnection have quietly signed up to own discovery, queuing, session persistence, identity, and retry semantics themselves — usually without naming those concerns, so they surface as scattered patches inside agent code rather than as a designed layer.

Angle

Read the protocols for what they do not guarantee: enumerate the four missing properties (discovery, queues, persistence, stateful sessions), then show where each one reappears as ad hoc code in a typical agent repo. Argue that the correct response is to name the missing guarantees before choosing any product.

Source video ↗

The Human Is the Message Bus

In today's agentic workflows the developer has become the router, discovery service, and context serializer between parallel stateful sessions, and that manual relay — not the agents' intelligence — is where latency, token cost, and error injection concentrate; the first thing worth automating away is the human seam, which is an undeclared API that should be designed.

Angle

Treat 'loop engineering' as an anti-pattern with a measurable cost: count the copy-paste events, tokens re-serialized, and wall-clock time lost per multi-session task, then show what the seam looks like when it is an actual interface.

Source video ↗

Continuity Is a Layer, Not a Variable

Agent process lifetime and conversation lifetime are different things, and systems that keep session state in-process have silently fused them; naming continuity (persistence, hydration, runtime binding) as a first-class layer forces the persistence boundary to be explicit and turns agent runtimes into disposable, replaceable workers.

Angle

Contrast an in-memory agent that loses its thread on redeploy with an externalized-state agent that binds on start; then argue that every framework adapter must satisfy a serialization contract, which is the real cost of the design and the part vendors omit.

Source video ↗

Instrument Identity Before You Instrument Cost

Cost and effort attribution in multi-agent swarms is an infrastructure problem that must be solved at design time, because the primary key for attributing tokens is agent identity, and once agents are multiplexed across users and rooms that key cannot be reconstructed — making cost optimization and human-versus-AI contribution accounting permanently guesswork.

Angle

Show why per-request telemetry is insufficient and per-agent identity-scoped telemetry is the minimum; demonstrate the retrofitting failure mode where a single shared credential destroys attribution for every past run.

Hydration Conformance Suite

beyond-evals

At most two of three mainstream agent frameworks (Codex-, LangGraph-, Claude-Code-style) can restore full task state after a forced mid-conversation process kill when adapted to the same continuity interface, and the failures are attributable to framework-specific in-process state rather than to the persistence store.

Proof of concept

Define a minimal continuity contract (persist conversation + in-flight task, hydrate on start, bind runtime). Wrap three frameworks behind it. Drive each through a multi-step task, kill the process at step 3, restart, and diff reconstructed task state against a ground-truth transcript.

Measurement

Pass rate per framework over N restart trials; count of state fields lost per failure; time-to-resume after hydration; number of framework-specific shims required to satisfy the contract.

Broker Under Duress

new

A central collaboration broker reduces lost messages versus point-to-point adapters under partial failure, but at the cost of a p95 hop latency increase large enough that synchronous agent-to-agent request/response patterns regress, while duplicate deliveries on retry remain nonzero unless adapters implement idempotency themselves.

Proof of concept

Build an identical three-agent topology twice — direct adapters versus broker — and inject faults: dropped connections, restarts during in-flight tasks, downstream timeouts. Log every message with a monotonic id and compare delivery sets.

Measurement

Ordering violations per 10k messages, duplicate deliveries on retry, lost-message rate under injected faults, p95 and p99 hop latency with and without the broker.

Source video ↗

Human Relay Accounting

movement-lab

Human-mediated context transfer between parallel agent sessions accounts for a measurable double-digit fraction of wall-clock time and of total token spend in multi-session coding tasks, and eliminating the human relay reduces both more than improving the underlying agents does.

Proof of concept

Instrument a multi-session workflow: log every manual copy-paste/context re-injection event with its token size and elapsed time. Then replace the human relay with a scripted registration plus message-passing path and re-run the same task set.

Measurement

Minutes of human relay per task, tokens re-serialized per relay event, total tokens per completed task, error/retry count, before versus after the automated path.

Source video ↗

Attribution Key Enforcement

gatehouse

Systems that mint a per-agent identity principal (with delegating-human binding) before the first message retain full cost attribution across multiplexing, whereas systems starting from a shared credential cannot recover per-developer attribution for any historical run, only from the retrofit date forward.

Proof of concept

Stand up two agent rooms on the same broker: one with per-agent principals plus delegation tokens, one with a shared credential. Replay an identical workload, then attempt to answer 'tokens spent per agent and per developer per task' for both.

Measurement

Percentage of historical runs attributable to an agent and a human; percentage attributable to a task; number of runs with ambiguous or colliding identity; audit-query latency.

Architectural implications

3

Agent interconnection today is done with per-pair handlers, REST endpoints, and hand-rolled adapters; the speaker argues this is the wrong layer to own.

Before

Each agent integration is a bespoke API handler or client/server pair, with discovery, retry, and session state written per connection.

After

A shared collaboration layer owns transport, continuity, conversation rooms, and governance; agents register into it and address each other by identity.

Consequence

Integration cost collapses from O(n^2) point-to-point adapters to O(n) registrations, but you inherit a new central dependency whose availability and latency you must reason about.

Local agent onboarding is shown as programmatic: spin up Codex and LangGraph agents from the terminal and register them, instead of walking through platform-specific setup.

Before

Onboarding an agent means multi-step manual configuration per platform, with each channel requiring its own setup documentation.

After

Agents self-register via a programmatic call and become discoverable to other agents and humans immediately.

Consequence

Agent deployment becomes scriptable and reproducible (CI-able), which is a prerequisite for testing multi-agent topologies rather than hand-building them.

Session state ownership moves out of the agent process and into a continuity layer that hydrates and binds runtimes.

Before

An agent process holds conversation state in memory; restart or scale event loses the thread.

After

Durable conversation state is external; the runtime binds to it on start, so agent processes become replaceable workers.

Consequence

Enables horizontal scaling and crash recovery for conversational agents, but introduces a serialization/deserialization contract that every framework adapter must satisfy.

Tradeoffs and failure modes

3

Adopting a centralized agent collaboration layer

Benefit

Solves routing, discovery, continuity, retries, identity, and audit in one place rather than per integration, across heterogeneous frameworks.

Cost or risk

Introduces a central component in the path of all agent traffic — a single point of failure and a vendor/coupling decision that is expensive to reverse; also a natural collection point for all agent message content, raising tenancy and confidentiality questions.

Source video ↗

Stateless tool-calling simplicity vs. stateful agent coordination

Benefit

MCP's stateless call model is simple, composable, and trivially cacheable/retryable for tool invocation.

Cost or risk

The same statelessness is exactly wrong for agent-to-agent coordination, where continuity of conversation and in-flight task state are the requirement; teams using MCP as the coordination substrate will discover this late.

Source video ↗

Fully autonomous AI-to-AI communication

Benefit

Removes human intermediaries and lets agents negotiate and assign work across frameworks and organizations, reducing turnaround latency.

Cost or risk

Autonomy without an audit/identity layer means actions are hard to attribute and govern; the same summary that predicts AI-to-AI dominance argues governance (identity, audit, tenancy) must be a dedicated layer to compensate.
