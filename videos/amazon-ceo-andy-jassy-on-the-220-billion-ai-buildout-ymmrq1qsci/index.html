[M]Mechanismmedium noveltymoderate evidence

Inference cost is treated as the binding economic constraint on enterprise AI adoption, and it is being attacked at the silicon layer (Trainium, Graviton) rather than only at the model layer, with claims of 30-40% better price-performance on custom silicon.

Why it matters

If unit inference cost falls materially by moving the workload onto specialized hardware, then hardware/placement selection becomes an architectural decision with the same status as model selection. Agent runtimes that assume a single default accelerator or a single provider abstraction forfeit that margin.

Generalization

For any cost-sensitive AI system, the dominant lever may be workload-to-hardware matching (batch size, precision, accelerator family) rather than prompt or model tuning; abstraction layers should expose accelerator class as a first-class, selectable property.

[O]Mental Modelhigh noveltystrong evidence

Capacity commitments have wildly asymmetric lead times: data centers must be committed roughly two years before servers are deployed, while servers and networking need only months. Capacity is therefore locked in on forecast, before the shape of demand is known.

Why it matters

Anyone building agents on top of rented compute faces a provider whose supply is fixed years ahead. That makes capacity a rationed resource rather than an elastic one, which pushes prioritization, queueing, and workload shaping into the application layer.

Generalization

When a dependency has multi-year supply lead times, design the system to make demand elastic: tiered service levels, deferrable batch work, model routing to cheaper hardware, and explicit admission control, instead of assuming on-demand abundance.

[>]Predictionmedium noveltymoderate evidence

Demand is not merely high but already contracted forward: capacity is described as sold out through 2027 while demand for 2028 is already visible, and $220B of capex in one year still leaves demand unserved.

Why it matters

For engineers, the gating resource for shipping AI features may be allocated capacity rather than model quality or engineering talent. That changes planning: secure quota early, and design for degraded or cheaper execution paths when premium capacity is unavailable.

Generalization

In a supply-constrained AI market, forward-contracted demand means spot/on-demand access degrades first; systems should be built with graceful fallback across model tiers and hardware classes rather than assuming peak capacity.

[A]Architecturemedium noveltyweak evidence

Agentic capability is framed as a property that must be designed into enterprise software, not layered on top of it — existing applications will need to be rewritten to be 'agentically capable'.

Why it matters

This challenges the common wrapper strategy of exposing legacy systems through a thin tool/API layer and letting an external agent orchestrate them. If the claim holds, interfaces, state, permissions, and error semantics inside the application must be agent-native, which relocates responsibility from the orchestration layer into the application itself.

Generalization

Where agent-friendliness is a first-class requirement, retrofitted APIs leak non-agent-safe semantics (ambiguous errors, human-oriented workflows, coarse permissions); the abstraction boundary should move inside the application.

[E]Empirical Resultlow noveltymoderate evidence

The growth rate of generative AI demand is claimed to be orders of magnitude steeper than early cloud adoption — a $25B AI run rate within three years of the wave's start versus a much slower cloud ramp.

Why it matters

Compressed demand ramps shorten the window in which architectural decisions can be deferred. Practices that were reasonable when platforms matured over a decade — waiting for standards, prototyping slowly — are mispriced when the underlying capacity and cost curves move this fast.

Generalization

Architectures should be chosen for expected near-term change in cost and capability curves, favoring replaceable components over long-lived stable ones.

[P]Practicemedium noveltymoderate evidence

The fulfillment-network history is presented as a template: build massively ahead of demand (doubling 25 years of infrastructure in ~18 months), absorb short-term cost pain, then recover economics through regionalization that lowered cost-to-serve while improving speed.

Why it matters

It describes a two-phase operating pattern — over-provision for headroom first, then re-optimize topology for cost and latency — rather than trying to optimize during the ramp. Applied to AI infrastructure, this argues for pre-building capacity and only later regionalizing/consolidating for cost.

Generalization

Under uncertain, fast-ramping demand, sequence capacity and efficiency work rather than doing them concurrently; delaying the optimization phase is a deliberate hedge, not a failure.

Agent-Native vs Wrapper Benchmark

beyond-evals

For a fixed workflow, an application with native idempotency, permission, and error semantics achieves higher agent task success and fewer unsafe or ambiguous actions than a thin API wrapper over the same legacy logic.

Proof of concept

Implement a small approval or ticketing workflow twice: once as a legacy API wrapper and once as an agent-native application; run the same agent tasks against both.

Measurement

Task success rate, recovery rate after errors, unsafe action count, and tool calls per successful task.

Rationed Capacity Scheduler

new

Under a fixed forward-committed capacity budget, priority queueing with deferrable batch work attains higher interactive latency SLO attainment than FIFO or unbounded on-demand admission.

Proof of concept

Simulate agent workload classes against a fixed token or accelerator budget; implement admission control, priority queues, and tiered routing.

Measurement

Interactive SLO attainment, throughput, tail latency, and batch-job starvation rate.

Source video ↗

Accelerator-Aware Router

movement-lab

Routing each workload to an accelerator class based on batch size and utilization lowers cost per token versus a single-default accelerator deployment while staying within latency SLO.

Proof of concept

Benchmark identical inference workloads across accelerator classes at varying batch sizes and utilization levels, then build a router that selects accelerator class per workload.

Measurement

Cost per token at p50 and p95 latency, SLO violation rate, and utilization.
