Summary

Overview

  • Speaker: Suraj Gupta
  • Channel: AI Engineer
  • Main topic: Self-improving agent software factories using skills, persistent memory, and model routing
  • Purpose: To provide software engineers with concrete, implementable frameworks for building self-improving agent software factories that optimize their skills, memory, and model usage without constant human intervention. Suraj Gupta, AI Engineering Lead at Warp, discusses how to transition from building individual software engineering AI products to building self-improving software factories. He breaks down self-improvement into three concrete pillars for agent factories over time: skills (procedural memory via inner/outer agent loops), persistent memory (fact stores scoped to agents updated via background extraction), and model routing (optimizing Pareto efficiency across models like Opus, GLM, and Haiku using custom rules and eval sidecars).

Key Points

The shift from coding agents to software factories

  • Explanation: Software engineering is evolving from building standalone coding agents to constructing and maintaining self-improving software factories.
  • Evidence: Warp's transition from a terminal agent tool to a cloud agent platform.
  • Practical implication: Engineers need to design feedback loops and automation pipelines around their agents rather than treating them as static scripts.

Outer loops for skill improvement

  • Explanation: An inner-loop agent executes tasks using a skill file, while an outer-loop agent monitors performance, analyzes feedback, and updates the skill file.
  • Evidence: GitHub issue triage skill updates tracked through Git pull requests.
  • Practical implication: Agent capability can be version-controlled and human-reviewed via standard Git workflows.

Automatic extraction of persistent memory

  • Explanation: Agents extract facts and lessons from session outputs automatically so future sessions can leverage past learnings.
  • Evidence: Sentry error-handling memory store usage demonstrated in Warp Cloud Agent platform.
  • Practical implication: Agents become faster and more accurate over time without requiring manual context re-injection.

Configurable model routing

  • Explanation: Routing tasks to different LLMs based on task classification rules optimizes cost and performance.
  • Evidence: YAML configuration defining model preferences for database migrations versus documentation tasks.
  • Practical implication: Teams can prevent runaway API costs while maximizing task success rates.

Core insights

[A]Architecturehigh noveltymoderate evidence

Self-improvement is split into two distinct loops: an inner loop that executes tasks using existing skills, and an outer loop that observes inner-loop runs and mutates the agent's skills, memory, and configuration. The outer loop is a separate agent doing meta-work on the artifact (a SKILL.md file), not the executing agent reflecting on itself.

Why it matters

It places improvement responsibility in a separate agent/process rather than in-context self-critique, which makes the improvement step asynchronous, inspectable, and versionable. Builders must decide what the outer loop can mutate (skills, memory) versus what stays fixed.

Generalization

Any agent system can be decomposed into an execution plane and an improvement plane, where the improvement plane consumes execution telemetry as its input dataset.

[P]Practicehigh noveltymoderate evidence

Skill improvements are delivered as Git pull requests against the skill definition file, so agent capability changes flow through the same review, versioning, and rollback machinery as normal code.

Why it matters

This converts an autonomous, potentially degrading self-modification into a reviewable change with a diff, an author, and an audit trail. It also identifies who owns the review bottleneck as the factory scales.

Generalization

Treat agent behavioral artifacts (prompts, skill files, routing rules) as reviewed source code rather than runtime state, and gate autonomous writes behind the same workflow.

Source video ↗
[M]Mechanismmedium noveltymoderate evidence

Persistent memory is not written by the executing agent during its run; a separate background extraction process reads completed inner-loop sessions and distills facts, learnings, and outcomes into fact stores scoped to a specific agent.

Why it matters

Decoupling memory writes from execution avoids spending in-run tokens and context on memory upkeep and keeps the memory store curated rather than an append-only session log. Scoping the store to an agent is a deliberate boundary decision that limits cross-contamination of facts.

Generalization

Memory should be an asynchronous ETL pipeline over agent session traces, with an explicit scope key (agent, repo, service) and a versioning story, rather than an in-loop write.

Source video ↗
[O]Mental Modelmedium noveltymoderate evidence

Procedural memory (how to do a task, held in a skill file) and declarative memory (facts about past incidents, held in a fact store) are treated as two separate subsystems with separate update loops and separate review processes.

Why it matters

Conflating them leads to a single blob store that is neither a good procedure nor a good knowledge base. Separating them lets you apply code review to procedures and eviction/versioning policy to facts.

Generalization

Split agent long-term state along the procedural/declarative axis, because the correct update and validation mechanism differs for each.

Source video ↗
[M]Mechanismmedium noveltymoderate evidence

Model selection is pushed out of the agent and into a declarative rule-based router keyed on task class, with an eval sidecar providing the quality signal; the design goal is a Pareto frontier over cost and quality rather than a single best model.

Why it matters

Routing decisions become configuration that can be changed without touching agent code, and the eval sidecar implies routing decisions are validated against measured task success rather than intuition.

Generalization

Treat per-subtask model choice as a policy layer with its own config and evaluation harness, not as a hardcoded constant inside each agent.

Source video ↗
[~]Tradeofflow noveltyweak evidence

Uneven task difficulty within a factory makes uniform premium-model usage economically unviable; routing is a cost-forcing function rather than a pure optimization.

Why it matters

It reframes model choice as a budget constraint that shapes architecture: which subtasks get decomposed and routed cheaply versus kept on frontier models.

Generalization

Any high-volume agent pipeline will need a cost-tiering layer, and the tiering boundaries should follow task classes with measurable failure tolerance.

Deep dives

5

Outer-loop convergence and skill quality drift over successive self-modification cycles

Research question

Does an outer-loop agent that proposes SKILL.md diffs converge to higher task success over N cycles, or does skill quality oscillate/regress as merged PRs accumulate?

Why

The entire 'self-improving factory' premise rests on an unmeasured assumption that the improvement loop is net-positive over time. If it is not, the correct architecture is a bounded loop with periodic skill reset rather than an open-ended one, which changes how builders budget review effort and version skill files.

Source video ↗

How the eval sidecar actually closes the loop on routing rules

Research question

Is the eval sidecar an offline harness that derives YAML routing thresholds, or an online scorer that can trigger rerouting mid-traffic — and which produces a better cost/quality frontier?

Why

'Eval sidecar' is named but never mechanized. Whether routing policy is set offline or adjusted online determines whether routing is a config artifact or a control system, which changes the failure modes (stale rules vs. thrashing) and what telemetry must be retained.

Source video ↗

Fact-store scope granularity, conflict resolution, and stale-fact contamination

Research question

What scope key (agent, repo, service, task class) maximizes retrieval precision while minimizing cross-contamination and superseded-fact steering of future runs?

Why

Scoping memory to an agent is stated as a boundary decision but no policy is given for overlap, conflict, or eviction. Since wrong facts silently degrade future runs, this is the highest-leverage unaddressed correctness risk in the persistent-memory pillar.

Source video ↗

Human review as the throughput limiter of a self-improving factory

Research question

At what PR volume does human review of outer-loop skill updates become the binding constraint, and what is reviewer time per skill PR?

Why

The outer loop is automated but its gate is human. If review time per PR is constant, factory scale is capped by reviewer headcount — a concrete capacity ceiling that determines whether the review gate can survive scale or must be partially automated.

Source video ↗

Cost-tiering boundaries as an architectural constraint on task decomposition

Research question

At what task volume and model price differential does rule-based routing produce material cost reduction, and do routed cheap models stay on the cost/quality frontier on real distributions?

Why

If routing does not actually reduce cost per unit work, the whole tiering layer is overhead. The answer also shapes decomposition: tasks must be split at boundaries with measurable failure tolerance for cheap models, which is an architecture decision, not just a config one.

Project ideas

Skill Drift Bench

beyond-evals

Running an outer-loop skill-updating agent for N successive update cycles on a fixed task distribution produces a measurable net improvement that plateaus or regresses after a finite number of cycles, rather than improving monotonically.

Proof of concept

Implement a triage agent with a SKILL.md, an outer-loop agent that proposes skill diffs from recorded runs and feedback, and an automated merge path; replay a fixed frozen task distribution after each cycle and record task success rate and diff size per iteration.

Measurement

Task success rate and failure-class breakdown per cycle over N=20 cycles, plus the cycle index at which success rate stops improving or declines; regression detection via a held-out task slice never seen by the outer loop.

Source video ↗

Scoped Fact Store with Conflict Resolution on Write

movement-lab

A fact store with explicit scope keys and conflict resolution on write yields higher retrieval precision and lower stale-fact contamination over time than an append-only session log scoped to the same agent.

Proof of concept

Build a background extraction process over completed agent sessions that writes facts into a store keyed by (agent, repo, service) with supersession rules; run both this store and an append-only baseline against a repeated-failure workload.

Measurement

Retrieval precision on a labeled fact set, contamination rate (retrieved facts that are superseded or wrong), tokens and latency per repeated failure class versus a no-store baseline, tracked over successive weeks of accumulation.

Source video ↗

Eval-Sidecar Router with Derived YAML Thresholds

gatehouse

Routing thresholds derived automatically from an eval harness that scores task-class outcomes per model achieve a non-dominated cost/quality frontier versus static human-authored rules, and misrouting is detectable as a distinct failure class at request time.

Proof of concept

Instrument a router with declarative YAML task-class rules, run an eval sidecar that scores per-class outcomes for each candidate model, auto-derive thresholds, and log every routing decision with the rule that fired for auditability.

Measurement

Cost per successful task and success rate versus static routing across at least three task classes, plus false-downgrade rate (tasks sent to an underpowered model) and the fraction of routing decisions attributable to a single rule.

Source video ↗

Review-Load Ceiling Calculator

new

Human review time per skill PR is roughly constant, so factory scale (agent count times update frequency) is bounded by reviewer headcount, and the binding constraint arrives before agent-side compute does.

Proof of concept

Instrument a pipeline where the outer loop opens skill PRs at controlled rates; measure reviewer minutes per PR, acceptance rate, and the rate at which the PR queue grows without bound at fixed reviewer capacity.

Measurement

Reviewer minutes per PR distribution, PR acceptance rate, queue depth over time at fixed reviewer count, and the agent-update rate at which queue depth grows monotonically.

Architectural implications

3

Skill definitions become versioned artifacts rather than static prompts embedded in an agent.

Before

Skill prompts are static and go stale as human feedback and agent runs accumulate.

After

Skill definitions live in a file that an outer-loop agent proposes diffs against, merged via pull request.

Consequence

Agent behavior becomes diffable, reviewable, and rollback-able, and the review step becomes a scaling bottleneck and a place for degradation to be caught.

Source video ↗

Memory becomes background-extracted state rather than in-run context accumulation.

Before

Agents re-gather context for recurring issues, wasting tokens and time.

After

An extraction process writes scoped facts into a store that future runs read from.

Consequence

Requires memory versioning, scoping policy, and eviction strategy, since stale or wrong facts will silently steer future runs.

Source video ↗

Model choice is externalized from the agent into a router with declarative rules.

Before

An agent or team picks one model, typically the most capable, for all tasks.

After

Task classes are mapped to models via YAML rules, with an eval sidecar providing quality signal.

Consequence

Routing configuration becomes a first-class artifact requiring its own evaluation and monitoring; misrouting is now a new class of production failure.
