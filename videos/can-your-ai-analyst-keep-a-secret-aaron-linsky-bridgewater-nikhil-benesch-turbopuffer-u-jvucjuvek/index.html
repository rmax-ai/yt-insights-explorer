Summary

Overview

  • Speaker: Aaron Linsky and Nikhil Benesch
  • Channel: AI Engineer
  • Main topic: Building secure and scalable AI agents and vector search systems with fine-grained permissions
  • Purpose: To explain how Bridgewater and turbopuffer collaborate to solve the hard systems problem of isolation-native vector search at 100M+ scale. Aaron Linsky (Bridgewater) and Nikhil Benesch (turbopuffer) discuss the engineering challenges of building an AI analyst that respects private organizational permissions and document access controls at scale. They examine the limitations of naive vector search strategies like post-filtering and pre-filtering, and present a native filtering approach implemented in turbopuffer that achieves high performance across hundreds of millions of documents.

Key Points

Object Storage Economics for Vector Search

  • Explanation: Turbopuffer builds directly on object storage (S3, GCS, Azure Blob), keeping data cold by default and pulling into cache only when queried.
  • Evidence: Scale to terabytes of data at a fraction of the cost of traditional memory or SSD-heavy systems.
  • Practical implication: Drastically reduces infrastructure costs while maintaining competitive search performance.

The Failure of Post-Filtering and Pre-Filtering

  • Explanation: Post-filtering cuts off relevant results after vector search, leading to poor recall. Pre-filtering scans millions of filtered docs sequentially, causing high latency.
  • Evidence: 100M docs scanning in memory takes 5 seconds, far above the 100ms target latency.
  • Practical implication: Engineering teams must adopt index-aware filter evaluation (native filtering) to scale secure search.

Core insights

6
[~]Tradeoffmedium noveltystrong evidence

Naive permission handling in vector retrieval fails in two opposite directions: post-filtering (retrieve top-k then drop unauthorized docs) destroys recall because nearest neighbors in vector space rarely match the caller's permission set, while pre-filtering (filter first, then scan) destroys latency because it degrades to a sequential scan over millions of permitted documents.

Why it matters

This is the central systems constraint for any retrieval layer sitting over private, access-controlled corpora — you cannot fix permissions at the application layer after the index returns results.

Generalization

Whenever a retrieval primitive must respect a predicate that is uncorrelated with the similarity metric, neither pre- nor post-filtering is acceptable; the predicate must be evaluated inside the index search plan.

'Native filtering' — combining vector clustering with attribute indexes (viewers, groups) so that filter evaluation is index-aware and happens inside the search plan — reconciles the recall/latency dilemma rather than trading one for the other.

It reframes permissions from a post-hoc security check into an index-level concern, which changes where the access-control boundary lives in the retrieval stack.

Generalization

Isolation constraints (tenancy, ACLs, row-level security) should be compiled into the index structure itself, not bolted on as a query-time wrapper.

Deep dives

5

Post-filter recall collapse under heterogeneous ACLs

Research question

For a corpus with skewed, heterogeneous document ACLs, what recall does top-k post-filtering achieve relative to an exhaustive permission-filtered ground-truth search, as a function of k, ACL sparsity, and embedding dimensionality?

Why

The talk's central claim is that post-filtering 'destroys recall,' but this is asserted rather than measured. If recall collapse is steep (e.g., near-zero context at realistic ACL sparsity), then any agent built on top-k-then-filter is silently answering from empty context, and the failure is invisible to latency dashboards and to the security team alike. A recall curve turns a design intuition into an engineering constraint with a threshold.

Source video ↗

Permission revocation latency as a retrieval SLO

Research question

When group membership is indexed as a first-class filter attribute, what is the worst-case window between a revocation in the identity system and its enforcement in query results, and how does that window scale with group fan-out and index update batching?

Why

Encoding permissions as filters moves authorization into the index, which means revocation is no longer an instantaneous auth-service decision — it becomes a propagation problem with staleness. Without a defined revocation SLO, 'inherit enterprise permissions natively' is a claim about steady state that says nothing about the window in which a revoked user can still retrieve. This is the failure mode most likely to turn an architectural win into a security incident.

Source video ↗

Group expansion cost inside index-aware filter evaluation

Research question

How does p95 query latency degrade with group nesting depth and fan-out when a viewer predicate must be expanded transitively at query time inside the index search plan rather than resolved in an auth service?

Why

The talk describes attribute indexes on viewers and groups but never addresses transitive membership. If filter evaluation requires recursively expanding nested groups, the predicate stops being a cheap index lookup and starts being a join. Whether this stays inside the ~100ms budget determines whether permission-as-filter is viable for real enterprise directory structures or only for flat groups.

Cache-hit-rate threshold for object-storage retrieval economics

Research question

At what cache hit rate and query-distribution skew does an object-storage-backed vector index stop being cheaper than a disk/RAM-resident one, given a fixed ~100ms p95 target?

Why

The 10x cost claim is the economic justification for keeping a 100M+ document private corpus agent-accessible at all, but it is stated as an architecture-level comparison with no workload characterization. If the advantage evaporates below some hit rate, then cost feasibility — not latency — becomes the binding constraint on which corpora agents may touch, and that threshold should be known before procurement.

The permission-aware retrieval scale cliff

Research question

At what document count and ACL cardinality does a naive application-layer permission approach cross an interactive latency threshold, and is the transition a smooth degradation or a cliff?

Why

The distinction matters for how teams de-risk. A smooth degradation is caught by load testing; a cliff means small-corpus prototypes — which is how nearly all agent demos are built — give false confidence specifically about the security architecture, not just about performance. Locating the knee tells you the minimum corpus size at which any permission-aware retrieval design must be validated.

Article ideas

4

Your Permission Filter Is Not a Security Control — It's Where Your Recall Goes to Die

Post-filtering vector results by ACL is widely treated as the safe default because it keeps permissions out of the index and out of the hot path. It is neither safe nor default-worthy: it silently returns empty or partial context, so the agent's failure mode is a confident answer built from nothing rather than an error. Pre-filtering is the mirror image — correct recall, unusable latency. The only position that survives is compiling the authorization predicate into the index search plan, which means the security boundary and the retrieval boundary must be the same line of code.

Angle

Take the two naive strategies seriously on their own terms, show each fails asymmetrically (one on recall, one on latency), and argue that asymmetry is why teams ship the wrong one — post-filtering's failure is invisible in latency and error-rate dashboards.

Source video ↗

Predicate Pushdown Is the Whole Story: What Vector Search Is Relearning from 1990s Query Planners

The pre-filter versus post-filter debate is not a new vector-search problem; it is the classic predicate-pushdown problem, and it has a known resolution. The novelty is not the technique but the stake: in a relational planner, a bad filter strategy costs latency, whereas in an AI analyst it costs confidentiality. Once you reframe isolation constraints as predicates that must be evaluated inside the search plan, multi-tenancy, row-level security, and clearance levels become the same engineering problem with the same answer.

Angle

Draw the direct analogy to database query planners, then argue the stakes are asymmetric — the database punishes you with slowness, the agent punishes you with disclosure — so the tolerance for the naive plan is far lower than teams importing database intuitions expect.

Source video ↗

Two Orders of Magnitude Means the Architecture Is Wrong, Not Slow

Most retrieval architecture decisions get made by intuition and defended by benchmarking, when a five-minute napkin calculation would have settled them. A 100M-document sequential scan lands at seconds against a 100ms target; that gap is structural, not a tuning opportunity, and no amount of caching or hardware fixes a plan that is three orders of magnitude off. Teams should adopt an explicit gate: compute the naive plan's cost before building, and if the gap exceeds roughly two orders of magnitude, stop optimizing and change the architecture.

Angle

Make the arithmetic the argument. Walk the 100M-scan-versus-100ms-target gap, then generalize it into a pre-implementation decision rule and show where it would have saved the cost of a failed prototype.

Source video ↗

Your Demo Has Ten Thousand Documents and Your Problem Has a Hundred Million

Agent prototypes validated on small corpora produce false confidence that is qualitatively different from ordinary performance optimism — it is confidence in the security architecture. At 10k documents the naive permission approach works, so the access-control design gets marked settled and frozen before load characteristics are known. Because the failure arrives as a cliff rather than a slope, the design must be validated at plausible production cardinality before it is considered decided, not after.

Angle

Argue that the security design, not the performance profile, is what small-corpus prototyping misleads you about — and that the review gate for permission architecture should include a cardinality test.

Project ideas

4

Filter-Strategy Recall Curve

beyond-evals

For corpora with realistic ACL sparsity (most documents visible to a small fraction of users), top-k post-filtering yields recall below 0.3 of permission-filtered ground truth at k=20, and recall falls monotonically as ACL sparsity increases — meaning the strategy fails on correctness, not just on speed.

Proof of concept

Generate a 1M-document synthetic corpus with Zipf-distributed per-user visibility. Run three retrieval plans against exhaustive permission-filtered ground truth: (a) top-k then filter, (b) filter then scan, (c) filter as an index predicate. Sweep k in {5, 20, 100} and ACL sparsity across two orders of magnitude.

Measurement

Recall@k against the exhaustive-filtered ground truth, plus p95 latency, reported as recall-vs-sparsity curves per strategy. Success criterion: demonstrate a readable crossover point at which post-filtering becomes unusable as context.

Source video ↗

Revocation Staleness Testbed

gatehouse

With permissions expressed as index-side filter attributes, the revocation-to-enforcement window is bounded by index update batching rather than by the auth system, producing a measurable staleness window that grows with group fan-out — and it exceeds a 60-second revocation SLO once a user belongs to more than a threshold number of groups.

Proof of concept

Stand up a permission-as-filter index over ~1M documents, drive membership churn from a mock identity system at varying rates (joins/leaves per second, fan-out 10/100/1000), and continuously probe retrieval as a revoked user to detect when access actually stops.

Measurement

Distribution of revocation-to-enforcement lag (p50/p95/max) versus churn rate and group fan-out; identify the fan-out and churn thresholds at which the lag crosses the SLO.

Source video ↗

Predicate Pushdown Gate

new

A pre-implementation cost model taking only corpus cardinality, predicate selectivity, and storage tier predicts within 2x whether a candidate retrieval design misses a 100ms p95 target — making it a sufficient screening gate to reject naive plans before any code is written.

Proof of concept

Build a small estimator that computes expected work for pre-filter scan, post-filter top-k, and index-aware filtering across storage tiers (RAM/SSD/object storage). Backtest against measured latency from a prototype over 1M/10M/100M-document corpora and three selectivity levels.

Measurement

Predicted-versus-measured latency error (log-scale) per strategy and corpus size; count of architectures correctly rejected by the gate. Success criterion: no false negatives on the three strategies at any tested cardinality.

Source video ↗

Cache Crossover Model

movement-lab

The object-storage cost advantage is not a fixed multiple but a function of cache hit rate, and there exists a measurable hit-rate floor (expected well under 50%) below which disk-resident retrieval becomes cheaper at equal p95 — meaning cost feasibility for agent-accessible corpora depends on query skew, not corpus size.

Proof of concept

Model total cost per query for object-storage-first (cold by default, cache on read) versus disk/RAM-resident index across cache hit rates 0–95%, query volumes spanning three orders of magnitude, and a 100M-document corpus. Validate the model's latency assumptions against a small instrumented prototype with an artificially throttled cache.

Measurement

Cost per query and p95 latency as joint functions of hit rate and query volume; report the crossover hit rate at which the cost multiple falls to 1x and compare against the claimed 10x.

Architectural implications

3

Authorization moves from an application-layer check into the index search plan.

Before

Retrieve top-k vectors, then filter results by the caller's document permissions in application code.

After

Pass permission predicates into the vector query, where the engine evaluates them index-aware alongside clustering.

Consequence

The agent runtime can no longer retrieve documents it is not allowed to see, eliminating a whole class of retrieve-then-leak failures.

Source video ↗

Storage tier becomes the primary cost lever for retrieval infrastructure.

Before

Index held in RAM or on SSD for predictable latency, with cost scaling with corpus size.

After

Index lives on object storage, cold by default, with query-time cache warming.

Consequence

Cost scales with working-set/cache size rather than total corpus size, changing which corpora are economically feasible to keep agent-accessible.

Source video ↗

Permission models become part of the data schema, not just the auth service.

Before

ACLs live in an identity/authorization system separate from the document index.

After

Viewers and groups are indexed as first-class attributes alongside vectors.

Consequence

Group-membership churn now becomes an indexing/write-amplification problem rather than only an auth-service problem.

Tradeoffs and failure modes

4

Post-filtering for permission enforcement

Benefit

Trivial to implement on top of any vector database; keeps permissions out of the index.

Cost or risk

Severe recall loss: the top-k nearest neighbors may contain almost no documents the caller is permitted to see, so the agent silently answers from an incomplete or empty context.

Source video ↗

Pre-filtering for permission enforcement

Benefit

Correct recall — every scanned document is permitted.

Cost or risk

Latency collapses to that of a sequential scan over the permitted subset; at 100M documents this is seconds, far beyond interactive targets.

Source video ↗

Object-storage-backed vector index

Benefit

Order-of-magnitude lower cost and the ability to hold hundreds of millions of vectors online.

Cost or risk

Cold-by-default data means query latency depends on cache state; predictable p95 requires cache warming and careful partition/cache design.

Source video ↗

Native filtering coupling index structure to the permission model

Benefit

120ms p95 over 450M vectors while respecting fine-grained permissions.

Cost or risk

Permission changes (group joins/leaves) may require index updates, so access-control churn translates into write load and possible staleness windows.
