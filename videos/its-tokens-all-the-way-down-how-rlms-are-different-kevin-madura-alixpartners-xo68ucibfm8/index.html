Kevin Madura from AlixPartners explains Recursive Language Models (RLMs), comparing them to traditional RAG, tool-calling, and agents. RLMs treat context as an object to manipulate symbolically within a REPL environment, enabling recursive decomposition and overcoming traditional context window decay.

What is an RLM?

Key Points

Context is part of the environment

  • Explanation: Instead of passing strings back and forth, the LLM interacts with variables in a REPL.
  • Evidence: Intermediate results live in script variables rather than clogging the context window.
  • Practical implication: Reduces token bloat and allows handling millions of tokens efficiently.

Deterministic shell vs. probabilistic core

  • Explanation: The orchestrator uses a deterministic shell to execute code while the probabilistic model decides what tasks to delegate.
  • Evidence: Diagram showing deterministic shell wrapping the probabilistic core.
  • Practical implication: Provides structure and reliability to complex multi-step reasoning.

Frameworks, Models & Processes

Recursive Language Model (RLM)

  • How it works: Treats context as an object in a REPL environment, allowing the model to write code, peek, grep, chunk, and recursively call sub-LMs.
  • Components:
    • Deterministic shell (REPL)
    • Probabilistic core (LLM)
    • Sub-LMs
    • Script variables
  • When to use: Very large or dense inputs/outputs, tasks amenable to decomposition, and long-horizon sessions.

Core insights

[A]Architecturehigh noveltystrong evidence

RLMs reframe context from a payload passed between calls into a live object that the model manipulates symbolically inside a REPL; intermediate results persist in script variables rather than occupying the context window.

Why it matters

If intermediate state lives in variables instead of prompt tokens, the effective working set is no longer bounded by the context window, which changes how large-input pipelines are designed and what can be attempted at all.

Generalization

Any agent harness can be restructured so that bulky intermediate artifacts live in an execution environment and only references/summaries cross the model boundary.

[M]Mechanismmedium noveltymoderate evidence

The RLM pattern separates a deterministic execution shell (REPL) from a probabilistic core (LLM); the shell guarantees execution semantics while the model only decides what to write and what to delegate.

Why it matters

This is a concrete reliability boundary: deterministic code handles control flow and data movement (observable, replayable, testable), while the model is confined to the decision of what sub-task to invoke.

Generalization

Agent reliability improves when the nondeterministic component is wrapped by a deterministic runtime that owns execution, state, and error handling.

Source video ↗
[M]Mechanismhigh noveltymoderate evidence

Recursion, not retrieval, is the proposed remedy for context degradation: sub-tasks are delegated to sub-LMs as functions, so the parent never needs to hold the full corpus.

Why it matters

Contrasts directly with RAG/tool-calling, which the summary claims still accumulate context rot as the window fills; the decomposition happens at runtime and is decided by the model rather than pre-chunked at index time.

Generalization

For compositional tasks over dense inputs, runtime recursive decomposition can substitute for retrieval-time chunking, at the price of latency and repeated model calls.

Source video ↗
[~]Tradeoffmedium noveltymoderate evidence

The stated selection criterion is orthogonal to task complexity: use RLM when input does not fit or work is compositional and latency can be traded for reliability; skip when latency is critical, context is small, or the base model is a weak coder.

Why it matters

This makes base-model code-generation quality a hard prerequisite for the architecture, not an implementation detail — a weak coder cannot drive a REPL-based harness regardless of context size.

Generalization

Architectures that put code generation on the critical path inherit the base model's coding reliability as a system-level failure mode.

Treating context as a manipulable object in a REPL rather than a token payload eliminates context rot and unlocks arbitrarily long inputs, but it shifts the system failure mode from prompt engineering to code-generation reliability—making base-model coding ability a hard architectural prerequisite.

Architectural implications

2

Context handling responsibility moves from the application layer into the execution environment.

Before

Application code assembles strings, chunks documents, and manages what fits into the prompt window.

After

The model writes code against a context object living in a REPL; the application supplies runtime primitives (peek, grep, chunk, sub-LM call).

Consequence

Context-window engineering stops being the main design surface; harness APIs and sub-LM call interfaces become the new critical path, and token bloat is bounded by variable scope instead of prompt size.

Source video ↗

Delegation decisions shift from developer-authored control flow to model-authored code.

Before

Engineers predefine the pipeline: retrieve, then summarize, then answer.

After

The model decides at runtime which sub-tasks to delegate to sub-LMs inside the REPL.

Consequence

Observability must capture executed code and sub-call trees, since the control flow is no longer statically known; debugging moves from prompt inspection to trace replay.

Tradeoffs and failure modes

4

Latency versus reliability

Benefit

Recursive decomposition preserves accuracy on long or dense inputs that would otherwise degrade.

Cost or risk

Multiple sequential sub-LM calls add latency, making the pattern unsuitable for latency-critical paths.

Source video ↗

Dependence on base-model coding ability

Benefit

The REPL lets the model decompose, peek, and manipulate data flexibly.

Cost or risk

The architecture fails if the base model cannot write reliable code, since every orchestration step is expressed as code.

Source video ↗

Context rot / the dumb zone

Benefit

Keeping context as an environment variable avoids saturating the window.

Cost or risk

Conventional RAG, agents, and tool-calling degrade as the window fills, with reported performance loss after roughly 40% usage.

Recursion overhead cost
