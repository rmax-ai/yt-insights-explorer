Overview

  • Speaker: Harrison Chase
  • Channel: LangChain
  • Main topic: Building AI agents that improve over time through model, harness, and context dimensions
  • Purpose: To provide a comprehensive framework and practical tooling advice for building and continuously improving AI agents. Harrison Chase, co-founder and CEO of LangChain, discusses the future of building AI agents that improve over time at Interrupt26 London. He breaks down agents into three core components (Model, Harness, and Context) and explains how to improve each dimension over time using techniques like supervised fine-tuning, reinforcement learning, traces, evaluation, and simulation environments.

How Agents Improve Over Time

Key Points

Three Core Parts of an Agent

  • Explanation: An agent is composed of a Model (reasoning engine), a Harness (system wrapper for control, persistence, and tools), and Context (markdown, text, and knowledge).
  • Evidence: Architectural diagrams shown during the keynote presentation.
  • Practical implication: Developers must separate model selection from harness architecture and context management when debugging or upgrading agents.

Evals are the New PRD

  • Explanation: Product Requirements Documents (PRDs) for traditional software are replaced in AI systems by evaluation suites that define expected agent behavior and boundaries.
  • Evidence: Discussion on defining positive and negative criteria, expected outputs, and simulation environments.
  • Practical implication: Product managers and developers must invest heavily in writing comprehensive evaluation datasets rather than static feature specs.

Traces Represent a New Data Type

  • Explanation: Agent traces (runs, threads, trajectories) capture semantic failures and complex interactions that traditional server logs miss.
  • Evidence: Introduction of SmithDB designed specifically for querying and analyzing agent traces and trajectories.
  • Practical implication: Engineering teams need specialized database and tracing infrastructure to store and query agent execution history.

Frameworks, Models & Processes

Agent Improvement Flywheel

  • How it works: Run agent -> Get feedback (human or judge) -> See what happened (trace) -> Add eval data point -> Suggest/apply changes to model, harness, or context.
  • Components:
    • Run agent
    • Get feedback
    • Trace analysis
    • Eval data point creation
    • Agent updates (model, harness, context)
  • When to use: When designing automated or human-in-the-loop systems to continuously optimize production AI agents.

Examples & Case Studies

  • Illustrates: Automated context improvement based on trace analysis.

Actionable Takeaways

  • Immediate:
    • Adopt tracing tools to record exact inputs, outputs, and tool call sequences.
    • Start building domain-specific evaluation datasets (evals) as your primary product specifications.
  • Strategic:
    • Treat agent harnesses and context as living code and data that should be iteratively optimized using trace feedback loops.
    • Move from manual fine-tuning toward automated improvement loops combining SFT and Reinforcement Learning.
  • Questions to investigate:
    • How can we build universal judges for correctness without heavy manual domain expertise?
    • What simulation environments are required to safely test agents that perform write operations on production databases?

Claims Worth Verifying

  • Supervised fine-tuning is best for simpler tasks like classification, extraction, and summarization. (technical practice)
  • There are no managed enterprise offerings for Reinforcement Learning that match those available for Supervised Fine-Tuning. (market observation)

Core insights

6
[O]Mental Modelmedium noveltystrong evidence

An agent should be decomposed into three independently improvable layers — Model (weights), Harness (code/tools/prompts around the model), and Context (text/knowledge/memory) — and improvement effort should be routed to the layer whose update mechanism fits the failure. The harness and context layers are code-and-text artifacts, so they can be changed and shipped without touching weights.

Why it matters

It turns 'make the agent better' into a routing decision with distinct change cadences, review processes, and rollback semantics: weight updates are slow/offline, harness changes are normal software PRs, context changes are data edits. Teams that blur these layers cannot attribute regressions to a cause.

Generalization

Applies to any LLM system: separate the pretrained reasoning engine, the orchestration code, and the retrieved/curated text so each can be versioned, evaluated, and rolled back independently.

[~]Tradeoffmedium noveltymoderate evidence

The improvement loop is an ordered escalation ladder by cost: context text is the cheapest and easiest surface to update, harness logic/code is next, and model weights (SFT/RL) are the most expensive. Context lives at the user or organization level, so fixes are just text edits rather than retraining or redeployment.

Why it matters

Gives an engineering default: exhaust context and harness fixes from traces before spending on fine-tuning. It also implies production systems should capture context at per-user/per-org granularity so corrections can be targeted rather than global.

Generalization

Most agent failures are addressable by editing knowledge or orchestration rather than retraining; the cost ordering should drive the order in which you attempt fixes.

[>]Predictionmedium noveltymoderate evidence

Improvement loops have three automation levels — manual (engineer-driven), human-in-the-loop (background process proposes changes, human approves), and fully automated — and current production tooling sits at the middle rung, where background jobs mine traces and suggest context or harness fixes for approval.

Why it matters

Defines the concrete product surface to build now: a background reviewer over traces that emits reviewable diffs to context/harness, not an autonomous self-modifying agent. The human-approval gate is the safety boundary that makes automation acceptable before evals are comprehensive.

Generalization

Self-improving systems should be built as proposal generators plus approval gates, progressively widening automation as eval coverage grows.

[A]Architecturemedium noveltymoderate evidence

Evals replace the PRD as the specification artifact for agentic systems: they define what 'good' looks like positively and negatively, and they double as the guardrail that makes automated self-modification safe. Their hard cost is not writing assertions but constructing realistic inputs and simulation environments.

Why it matters

Shifts where requirements live and who owns them — from a static document to an executable dataset plus environment. It also explains why self-improving agents stall: without a simulation environment you cannot generate the diverse inputs needed to detect regressions from proposed context/harness changes.

Generalization

Any system whose behavior is probabilistic needs an executable spec; the bottleneck is environment fidelity, not assertion authoring.

[A]Architecturemedium noveltymoderate evidence

Agent traces are a distinct data type — runs, threads, trajectories capturing exact inputs, outputs, and sequences — that generic application logs do not represent, and they warrant purpose-built storage with ingestion, query, and semantic filtering rather than reuse of an existing observability backend.

Why it matters

Determines whether trace analysis can be automated at all: mining traces for failure patterns requires semantic filtering over trajectories, which is a different query model from log search or span metrics. It also implies trajectory-level retention and schema design decisions early, since they become the training/eval corpus later.

Generalization

New data types create new infrastructure categories; trajectory data needs semantic, not just temporal, indexing.

[M]Mechanismmedium noveltyweak evidence

Red teaming can be derived from production traces by algorithmically generating semantically similar queries to the ones that previously produced errors, turning each observed failure into a family of probe inputs.

Why it matters

Converts trace data into an adversarial eval generator without hand-authoring cases, and directly attacks the 'realistic inputs' bottleneck in eval construction. It is directly testable: perturb known-failure queries and measure failure rate as a function of semantic distance.

Generalization

Failure-driven input synthesis (mutate near known failures) is a cheaper eval-generation strategy than broad synthetic coverage.

Deep dives

5

Escalation ladder: routing a failure to context, harness, or weights

Research question

Given a recurring production failure cluster, what trace-derived features predict whether a context edit, a harness change, or a weight update will resolve it at lowest cost and lowest regression risk?

Why

The pass-1 ladder asserts a cost ordering but supplies no decision rule. Without one, teams will over-invest in fine-tuning for problems that are text bugs, or paper over orchestration defects with prompt padding. A feature-level rule (e.g. failure occurs only for org-specific entity names => context; failure occurs only when tool-call ordering matters => harness; failure persists across all orgs and all prompt phrasings => weights) is directly testable on trace corpora.

Source video ↗

Approval-gated self-modification: what a background context updater must pass

Research question

What gate configuration (diff granularity, per-change regression suite, blast-radius scope) minimizes false-accepts of automated context edits while preserving most of the automation benefit?

Why

The human-in-the-loop rung is named as the current product surface, but no threshold, diff-review, or rollback policy is specified. The gate design is the actual engineering artifact separating a self-improving agent from an unverified drift generator, and the false-accept rate is measurable as eval coverage grows.

Source video ↗

Environment fidelity as the binding constraint on eval and RL quality

Research question

How does eval signal-to-noise and RL reward validity change as a function of simulation-environment fidelity, and do trace-replayed environments outperform synthetic ones at equal budget?

Why

Simulation environments are named as the hard part of eval construction and implicitly as the prerequisite for RL rollouts, yet no fidelity criterion or cost figure is given. This reframes the roadmap bottleneck: investment moves out of prose specs and into environment construction, which should be measured rather than assumed.

Source video ↗

Trajectory data as a distinct storage and query model

Research question

Which query patterns over agent trajectories (semantic filtering, failure-cluster retrieval, trajectory diffing) cannot be served by existing observability stores, and at what trace volume does the gap become prohibitive?

Why

If trace mining for failure patterns requires semantic rather than temporal indexing, then reuse of a log/metrics backend blocks automated improvement at the root. The consequence is concrete: retention and trajectory-schema decisions made early become the training and eval corpus later, so they are expensive to reverse.

Source video ↗

Failure-seeded input mutation as an eval generator

Research question

At equal query budget, does mutating queries near known failures discover more distinct failure classes than broad uninformed sampling, and does discovery rate decay with semantic distance?

Why

This is the cheapest proposed attack on the realistic-inputs bottleneck and the only pass-1 mechanism with a clean falsification test. If mutation only yields variants of seeded failures, it cannot substitute for coverage, and eval construction remains the critical path.

Article ideas

4

Stop Retraining: The Agent Improvement Ladder Is a Cost-Ordering Problem

Most agent failures are text and code bugs wearing a model-capability costume; teams should be forced to exhaust context edits, then harness changes, before touching weights, because each rung has a different change cadence and rollback semantic that determines whether you can attribute a regression.

Angle

Reframes 'our agent is bad' as a routing decision with an explicit decision rule and a per-layer release process, using the three-layer decomposition as the routing table rather than as a taxonomy.

Source video ↗

Self-Improving Agents Ship as Approval Workflows, Not Autonomy

The deployable version of a self-improving agent today is a background trace reviewer that emits reviewable diffs to context and harness behind a human gate; the human is not a temporary crutch but the safety boundary that substitutes for eval coverage you do not yet have.

Angle

Argues the product surface is proposal generation plus approval, and that 'autonomous' is a later widening of a gate, not a different architecture.

Source video ↗

Evals Are the New PRD, Which Means Your Roadmap Is Now an Environment

Promoting evals to the specification artifact is correct but incomplete: the real cost is not assertions, it is realistic inputs and simulation environments, so the roadmap's critical path silently moves from prose specs to environment construction and dataset curation.

Angle

Follows the 'evals as PRD' claim to its uncomfortable consequence: teams that adopt the slogan without budgeting environment fidelity get guardrails that pass and agents that fail.

Your Observability Stack Cannot Query a Trajectory

Traces are a new data type with a semantic query model, not a log stream with extra fields, and reusing a general-purpose observability backend quietly caps how far agent improvement can be automated.

Project ideas

4

Layer Router

new

A classifier over trace-derived features can predict which remediation layer (context, harness, weights) resolves a failure cluster at lowest cost, and will beat an always-fine-tune baseline on cost-per-resolved-failure without increasing regression rate.

Proof of concept

Ingest a trace corpus with labeled failure clusters and the intervention that actually fixed each (context edit / harness PR / fine-tune). Train a small classifier on features such as cross-org recurrence, entity-specificity, tool-call ordering sensitivity, and prompt-phrasing invariance. Compare against baselines of always-context, always-harness, always-fine-tune.

Measurement

Cost per resolved failure cluster and post-fix regression rate on a held-out eval suite, per arm; router accuracy against the historically chosen layer.

Source video ↗

Context Diff Gate

gatehouse

Approval-gated background context edits, each carrying a per-change regression suite and a bounded blast radius (user vs org scope), achieve a false-accept rate low enough to justify removing per-edit human review for low-blast-radius diffs.

Proof of concept

Background job mines traces for context gaps and emits candidate diffs partitioned by scope (single user, single org, global). Each diff runs a targeted eval slice before reaching a reviewer. Log accept/reject decisions and post-merge regressions.

Measurement

False-accept rate (accepted edits that later regress) versus eval-slice coverage, split by blast radius; reviewer minutes saved per accepted fix.

Source video ↗

Failure Seeder

beyond-evals

Mutating queries near previously observed failures discovers more distinct failure classes per query than broad uninformed sampling, but discovery decays with semantic distance and rarely finds failure classes disjoint from the seeds.

Proof of concept

Collect failed queries from traces, generate semantic neighbors at controlled distances, run them against the agent, and cluster resulting failures. Run a broad-sampling control at equal query budget.

Measurement

Distinct failure classes discovered per 1k queries, for mutation vs control; fraction of discovered classes that are novel rather than variants of the seed.

Source video ↗

Fidelity Dial

beyond-evals

Eval signal-to-noise and RL reward validity scale with simulation-environment fidelity, and trace-replayed environments yield higher per-dollar eval sensitivity than synthetic environments.

Proof of concept

Build one task with three environment tiers (synthetic fixtures, partially recorded state, full trace replay). Run an identical eval suite and a short RL rollout on each tier and correlate scores with human judgment and with live production outcomes.

Measurement

Correlation between tier scores and human/production judgments; regression-detection sensitivity per unit of environment-construction cost.

Architectural implications

4

Agent improvement is modeled as a closed flywheel spanning run, feedback, trace, eval datapoint, and change application across three layers.

Before

Improvement treated as ad-hoc prompt tweaking driven by anecdote and spot checks.

After

An explicit pipeline where every production trace is a candidate eval datapoint and every accepted eval becomes a regression test for model, harness, or context changes.

Consequence

Requires shared identifiers linking traces to eval cases and to the specific layer changed, so regressions can be attributed to a model, harness, or context diff.

Source video ↗

Responsibility boundaries move: model selection is decoupled from harness architecture and context management.

Before

Debugging an agent meant swapping models or rewriting prompts as a single undifferentiated activity.

After

Model choice, harness logic/tools, and context content are diagnosed and upgraded separately, each with its own owner and release path.

Consequence

Teams need three distinct versioning and rollback mechanisms and, ideally, the ability to swap the underlying model without rewriting harness code.

Source video ↗

Context becomes a continuously curated layer rather than a static retrieval store.

Before

Context was a fixed corpus, index, or prompt assembled at build time.

After

Context is reviewed in the background against real interactions and updated per user or organization, as in Hex's unified context layer.

Consequence

Context store needs per-user/per-org partitioning, change history, and a review/approval interface; unmanaged automated edits become a silent regression source.

Source video ↗

Evaluation shifts from a QA phase to a specification artifact co-owned by product and engineering.

Before

A PRD described features; correctness was checked late by humans.

After

A comprehensive evaluation dataset plus simulation environment is the definition of correct behavior, written up front.

Consequence

Roadmap artifacts change shape; investment moves from prose specs into environment and dataset construction, which becomes the critical path.

Tradeoffs and failure modes

4

SFT vs RL for weight-level improvement

Benefit

SFT is straightforward: filter good traces and train, sufficient for simpler tasks like classification or extraction. RL runs rollouts scored in real time and has a higher ceiling for complex agents.

Cost or risk

RL is much harder to operate — it requires task environments, rollout infrastructure, and reliable real-time scoring — and SFT caps out on complex behavior.

Source video ↗

Automated context/harness self-modification

Benefit

Background review of traces can find context gaps and propose fixes without engineer time, letting agents improve with use.

Cost or risk

Proposed changes can silently degrade behavior; the only defense is eval coverage, which the speaker notes is hard to build because it needs realistic inputs and simulation environments.

Source video ↗

Specialized trace infrastructure vs general observability

Benefit

Purpose-built storage enables semantic filtering and trajectory-level querying required to mine agent failures automatically.

Cost or risk

A new database and tracing stack is additional operational surface and duplication alongside existing logging and metrics systems.

Source video ↗

Evals as the new PRD

Benefit

Executable specifications define good and bad behavior and act as guardrails for automated changes.

Cost or risk

Requires heavy upfront and ongoing investment in realistic inputs and environment construction, displacing conventional feature documentation without guaranteeing coverage.
