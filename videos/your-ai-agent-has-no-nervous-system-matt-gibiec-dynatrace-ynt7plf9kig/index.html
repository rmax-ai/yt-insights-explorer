Summary

Overview

  • Speaker: Matt Gibiec
  • Channel: AI Engineer
  • Main topic: AI agents lack operational context and observability, creating reliability and scaling challenges in production.
  • Purpose: To explain why AI agents fail or loop without production context, and to introduce Bluebox by Dynatrace as a solution for providing observability, context, and nervous-system capabilities to AI coding agents. Matt Gibiec, Regional Director of Solutions Engineering for AI-Native at Dynatrace, discusses the challenges developers, team leads, and heads of engineering face when deploying AI agents without observability, context, or runtime data. He introduces Bluebox by Dynatrace as an AI observability and context-provisioning tool designed to provide agents with production runtime context, automated service discovery, and evidence-based PR plans.

Topic Map

The Problem of AI Agents Operating Without Context

  • Explanation: AI agents are utilized to replace human tasks requiring reasoning, but they lack input, context, and a nervous system to understand their environment, leading to infinite loops and hallucinations.
  • Key claims:
    • AI agents operate at speed, but without sight.
    • Agents are only as good as the data available to make reasoning decisions.
    • Missing context and permissions lead to hallucinations and inefficient automated processes.
  • Examples:
    • An AI agent like Claude getting stuck in a loop repeating the same action and consuming tokens without producing desired results.
  • Terminology:
    • AI agent
    • hallucinations
    • reasoning
    • context
  • Why it matters: Without proper context, AI agents make decisions without understanding their consequences, wasting engineering resources and failing to deliver business value.

Challenges in AI-First Engineering Across Roles

  • Explanation: Different roles in engineering face distinct struggles when adopting AI agents, from developers dealing with runaway loops to heads of engineering wondering about ROI and code quality.
  • Key claims:
    • Developers struggle with why agents get stuck or fail to verify code independently.
    • Team leads struggle with PR deployments, stability, operational issues, and team focus.
    • Heads of engineering question if coding agents build the right things and deliver app value.
  • Examples:
    • Developers asking why an agent is stuck in a loop or cannot verify code on its own.
  • Terminology:

  • Why it matters: Organizations lack established instructions and metrics for measuring the value and success of AI agents.

The Autonomy Ladder and Staying in Control

  • Explanation: AI automation requires an autonomy ladder ranging from observation to fully autonomous PR generation, allowing teams to maintain control.
  • Key claims:
    • Autonomy ladder allows teams to decide how far agents run without input.
    • Levels range from L1 (observe only), L2 (suggest fix), L3 (open PR), to L4 (autonomous PR).

Key Points

AI agents lack a nervous system

  • Explanation: Agents execute tasks rapidly but lack real-time feedback from running software in development and production.
  • Evidence: Quotation from CTO Bernd Greifeneder: 'They operate at speed, but without sight.'
  • Practical implication: Engineering teams must provide continuous runtime context and observability to AI agents.

Context is King

  • Explanation: Context serves as the connective tissue that drives all automated processes and decision-making for AI agents.
  • Evidence: Without service dependency mapping and production data, agents make short-sighted decisions.
  • Practical implication: Agents need access to dependency graphs, historical loads, and application metrics before executing changes.

Local success does not equal production success

  • Explanation: Code tested successfully in local environments can break downstream services when merged into main branches.
  • Evidence: Merging code that passes local tests but breaks three other microservices.
  • Practical implication: Production context must be bridged into local testing and AI agent workflows.

[A]Architecturemedium noveltystrong evidence

A graduated autonomy ladder (L1 observe-only, L2 suggest-fix, L3 open-PR, L4 autonomous-PR) treats trust in an agent as a per-capability setting rather than a binary deploy decision, letting teams accumulate L1 observation context before granting higher-level execution rights.

Why it matters

It places an explicit control boundary in the agent workflow where responsibility shifts from agent to human, and lets context-accumulation precede autonomy—so the same agent stack serves advisory and autonomous modes without redesign.

Generalization

For any code-modifying or action-taking agent, autonomy should be a tunable level with graduated intervention points, not a global on/off switch; lower levels double as data-collection phases for higher ones.

Your Agent Doesn't Need a Better Model; It Needs a Nervous System

The dominant bottleneck in production coding agents is not reasoning capability but missing runtime feedback from the software they modify; instrumenting the environment reduces loops, hallucinations, and downstream breakage more effectively than model tuning.

Angle

Argue against model-centric agent improvement and for runtime-context engineering as the primary lever.

Source video ↗

Autonomy Is a Ladder, Not a Switch

Treating autonomy as a per-capability graduated setting—observe, suggest, open PR, autonomous PR—lets teams accumulate context at lower levels before granting execution rights, preventing the trust erosion caused by premature full autonomy.

Angle

Use the L1-L4 control ladder to argue that agent trust should be accumulated, not deployed.

Source video ↗

Local Tests Are a Lie for Distributed Systems

AI coding agents that rely on local test success as a correctness signal will merge changes that break downstream services; production dependency topology and load context must be pre-merge inputs to the agent, not post-incident diagnostics.

ContextBridge

movement-lab

Feeding a live OpenTelemetry service topology and dependency graph into a coding agent before it generates a PR reduces downstream production breakage per merged change compared with a local-tests-only baseline.

Proof of concept

Instrument a small microservice repository with OpenTelemetry, build a dependency/topology graph, expose it as an agent-readable pre-merge artifact to a coding agent (e.g., Claude/Cursor), and run a fixed set of feature changes.

Measurement

Downstream service breakage rate per merged PR, agent loop token cost, and reviewer-reported confidence versus a control group without topology context.

gatehouse

A graduated L1-L4 autonomy gate with explicit control boundaries reduces code-quality degradation and reviewer trust erosion compared with full autonomous PR generation.

Proof of concept

Implement an agent workflow that can run at observe-only, suggest-fix, open-PR, and autonomous-PR levels on the same repository, with per-level approval gates and context-accumulation logging.

Measurement

Merged-change quality regressions, review burden (time per PR), token cost per merged change, and reviewer trust survey across matched L1-L4 runs.

Architectural implications

3

Observability is repositioned from post-deploy monitoring to a pre-merge input consumed by the agent.

Before

Telemetry primarily serves humans debugging production after deployment.

After

Telemetry is fed into the coding agent's context window before changes are proposed/merged.

Consequence

The context/telemetry layer becomes a dependency of the development loop, requiring low-latency, machine-readable topology and dependency data.

Source video ↗

Agent control points are placed as graduated autonomy levels rather than a single human-approval gate.

Before

An agent either runs autonomously or is stopped for human review.

After

An explicit ladder (observe/suggest/PR/autonomous) governs how much the agent executes unreviewed.

Consequence

Workflow and PR tooling must support partial-autonomy handoffs and produce machine-generated PR artifacts as a first-class output.

Source video ↗

Instrumentation standard (OpenTelemetry) is reused as the agent context abstraction.

Before

Context for agents is assembled ad hoc from prompts, files, and tool outputs.

After

Context is assembled from live instrumented topology and runtime data.

Consequence

Context quality becomes coupled to instrumentation coverage; uninstrumented services are blind spots for the agent.

Tradeoffs and failure modes

3

Autonomy vs. trust erosion

Benefit

Higher autonomy levels (L3/L4) let agents ship fixes with less human effort.

Cost or risk

Fully autonomous agents 'create a messy environment and erode trust in engineering output,' so moving up the ladder too fast can degrade code quality and confidence.

Source video ↗

Context richness vs. loop/token cost

Benefit

Runtime context reduces hallucination and short-sighted decisions.

Cost or risk

Absent context, agents loop and consume tokens without results, making missing context a direct cost driver.

Source video ↗

Local test success vs. production correctness

Benefit

Local development iteration is fast and self-contained.

Cost or risk

Relying on local success masks downstream breakage—passing local tests can still break three production microservices.
