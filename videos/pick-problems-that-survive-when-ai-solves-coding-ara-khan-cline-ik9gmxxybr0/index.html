Frameworks, Models & Processes

Two-Level Learning Loop (Inner and Outer Loop)

  • How it works: An inner rollout agent interacts with the environment within each task to get feedback, while an outer meta-agent observes across tasks, diagnoses failures, and improves the evaluation harness or prompt configuration.

Core insights

[E]Empirical Resulthigh noveltystrong evidence

An agent's measured capability is partly an artifact of its harness, and that harness gap can be closed by a *different, stronger* agent rather than by retraining the model — GPT-5.6 Sol optimized the harness while Kimi K3 executed tasks, moving Terminal-Bench 2.1 from 77.5% to 88.8% in a 17-hour autonomous loop.

Why it matters

It decouples 'model capability' from 'system capability' in a measurable way and shows a concrete mechanism (cross-model meta-optimization) for extracting latent performance from a fixed base model without touching weights. An ~11-point benchmark delta is larger than many model-version upgrades and is obtained by editing prompts, tools, and runtime handling.

Generalization

When you have a verifiable score, the fastest capability gain is often not a better model but a better outer loop editing the harness — and the optimizer agent should be the strongest model you can afford, decoupled from the cheap executor.

[A]Architecturehigh noveltymoderate evidence

The RSI loop decomposes into two distinct agents with different scopes: an inner rollout agent that interacts with the environment per task, and an outer meta-agent that observes *across* tasks, diagnoses failure patterns, and edits the harness (prompts, tools, skills).

Why it matters

This is a clean architectural boundary: per-episode execution vs cross-episode diagnosis. The meta-agent requires a pooled failure signal (aggregate across rollouts), which is why it can fix systematic issues like rate-limit handling and worker liveness that no single rollout can perceive. It also implies the harness must be a first-class, machine-editable artifact rather than inline config.

Generalization

Any agent system with a repeatable task distribution should separate execution from meta-level harness editing, and should expose prompts/tools/skills as an editable surface with a measurable objective.

[!]Failure Modemedium noveltystrong evidence

A large share of the harness gains came from mundane runtime plumbing, not reasoning improvements: retry-with-backoff for rate limits, loop detection that checks whether output actually changed (to avoid false loop alarms), and keeping workers alive on premature process exits.

Why it matters

Benchmark and production scores are silently degraded by infra-level failure modes — throttling, spurious loop breakers, dead workers. Naive loop detection is actively harmful because it terminates legitimate progress; the fix is a semantic check (did output change?) rather than a repetition counter. These are cheap, high-leverage fixes that an agent can discover and apply.

Generalization

Before attributing low scores to model reasoning, audit the runtime: rate-limit backoff, liveness/restart semantics, and progress-aware termination conditions. Robustness plumbing is capability.

[O]Mental Modelmedium noveltymoderate evidence

The improvement surface is the entire stack — pre-training, post-training, inference, evals, and physical world interaction — and gains at the inference layer feed back into the loop's cost: models rewriting production kernels in Triton and Gluon cut serving cost 20% and raised token-generation efficiency >15%, making further self-improvement cheaper.

Why it matters

RSI is not a single recursion but a set of coupled loops whose outputs compound: cheaper inference lowers the price of the very optimization loops that produce more efficiency. That is a positive feedback structure an engineer can deliberately target by choosing which layer to optimize first.

Generalization

Prioritize optimizing whichever layer reduces the cost of running the optimization loop itself (inference/serving), because that multiplies the throughput of every other loop.

[O]Mental Modelmedium noveltymoderate evidence

Verifiability is the gate on self-improvement: the loops that work are those with an automatable, checkable signal (benchmark scores, kernel cost/throughput, physical-world outcomes), and project selection should prioritize problems that retain such a signal.

Why it matters

It converts 'will AI solve this?' into a design question: can I make progress measurable? Work with a tight verification loop is automatable and therefore accelerates; work without one stays human-bound. This reframes harness construction as the primary engineering deliverable.

Generalization

For any task you intend to automate or defend, first ask whether a machine-checkable objective exists; if not, either build one or expect the task to remain manual while verifiable neighbors get commoditized.

Cross-model harness transfer and the harness/model capability boundary

Research question

Does a harness optimized by a stronger meta-agent on one base model transfer to other base models and to held-out task suites, and what fraction of the score delta is harness-recoverable versus a hard base-model ceiling?

Why

The reported 77.5% to 88.8% gain is large enough to rival a model upgrade, but it is only meaningful as engineering knowledge if the edits generalize beyond the model and benchmark used to discover them. Quantifying transfer and saturation determines whether harness optimization is a general capability lever or a benchmark-overfitting procedure.

Source video ↗

Two-level agent architecture: rollout agent versus cross-episode meta-agent

Research question

At equal compute, does a two-level loop with an inner rollout agent and an outer cross-task meta-agent outperform a single in-episode self-correcting agent, and what pooled failure signal is necessary for the meta-agent to diagnose systematic issues?

Why

This boundary determines whether self-improvement is an architectural property or just in-episode retry behavior. If the meta-agent needs aggregate failure data across rollouts to fix rate-limit handling, worker liveness, and prompt/tool configuration, then harnesses must be designed as machine-editable artifacts with cross-episode telemetry.

Source video ↗

Runtime robustness as a measured capability surface

Research question

Which runtime failure modes—rate limiting, premature process exits, false loop alarms—dominate measured agent scores, and can semantic progress checks replace naive repetition counters without truncating legitimate long-running trajectories?

Why

If double-digit benchmark gains come from retry/backoff, liveness supervision, and progress-aware termination, then score regressions may be misdiagnosed as model reasoning failures. This turns runtime plumbing into a first-class evaluation variable and implies benchmark scores are non-comparable unless harness versions are pinned.

Verifiability, held-out generalization, and project selection

Research question

How do you build machine-checkable objectives for agent work that do not overfit the optimization suite, and how should project selection change when verifiability determines both automatable progress and defensibility?

Why

Verifiability is presented as the gate on self-improvement and as a career-selection criterion. The unresolved risk is that the same tight loop that enables optimization also enables benchmark overfitting unless optimization-set gains are compared against held-out gains.

Budget ordering across the coupled improvement stack

Research question

Under a fixed total budget, does optimizing inference/serving efficiency first produce a higher final benchmark score than optimizing the harness first, because cheaper rollouts increase the number of optimization iterations?

Why

The stack is described as coupled loops whose outputs compound: cheaper inference lowers the cost of running the very loops that produce further improvements. A prioritization rule would tell teams which layer to optimize first rather than treating all layers as equally improvable.

The Harness Is the Model: Why Capability Gains Live Outside the Weights

Measured agent capability is a joint product of base model and harness, and a stronger optimizer agent can extract large benchmark gains without retraining; therefore evals and procurement must pin harness versions and separate model attribution from harness attribution.

Angle

Use the 77.5% to 88.8% Terminal-Bench delta as the concrete case, then argue that leaderboard and product claims are under-specified unless they publish the harness, runtime policy, and optimizer model.

Source video ↗

Your Agent's Reasoning Failure Is Probably a Runtime Failure

Long-run agent scores are silently degraded by rate limiting, false loop detection, and dead workers, and fixing this plumbing is cheaper and higher-leverage than further prompt or reasoning tweaks.

Angle

Walk through the three mundane fixes—retry with backoff, output-change checks for loop alarms, and worker liveness—and argue that robustness plumbing belongs inside the measured capability boundary.

Source video ↗

Two Agents, One Loop: Execution and Meta-Diagnosis Must Be Separated

Per-episode self-correction cannot see pooled failure patterns; a cross-episode meta-agent that edits prompts, tools, and skills is the architecture that turns many rollouts into systematic improvement.

Angle

Contrast a single in-episode self-correcting agent with an inner rollout plus outer meta-agent loop, using the harness-editing example to show why the optimizer needs aggregate failure signals.

The durable project criterion is not task difficulty but a machine-checkable progress signal plus a duration shorter than the relevant capability timescale; verifiability both automates progress and defends work from commoditization.

Angle

Project ideas

4

Harness Transfer Matrix

beyond-evals

Harness edits discovered by a stronger meta-agent on base model A transfer to models B and C with at least half of the original score gain on held-out tasks; if transfer is near zero, the gains are benchmark-specific overfit rather than general harness engineering.

Proof of concept

Run baseline and optimized harnesses across several base models on an optimization suite and a held-out suite, logging per-model score deltas, runtime policies, and the exact harness edits applied.

Measurement

Transfer ratio = delta on held-out model / delta on optimization model, held-out gap per optimization iteration, run-to-run variance, and compute cost per point gained.

Source video ↗

Two-Level Loop Ablation

new

At equal token and compute budget, an inner rollout plus outer meta-agent loop outperforms a single in-episode self-correcting agent on task suites with shared failure modes, but shows no advantage on suites where failures are independent per task.

Proof of concept

Implement both loops on a benchmark with injected shared faults such as throttling and worker exits; toggle pooled cross-episode feedback versus per-episode self-correction only.

Measurement

Score per million tokens, final score at fixed budget, failure-mode clustering across rollouts, and ablation of pooled versus per-task feedback.

Source video ↗

Runtime Fault Injector and Liveness Guard

gatehouse

Injected runtime faults—rate limits, premature process exits, and output-stable long runs—account for more than 10 benchmark points, and progress-aware loop detection recovers most of that loss without falsely terminating legitimate long trajectories.

Proof of concept

Build a wrapper that injects each fault class and toggles retry with backoff, worker restart semantics, and semantic progress checks versus naive repetition counters.

Measurement

Score delta with and without each guard, false termination rate on known-good long runs, recovered points per fault class, and added wall-clock/token overhead.

Source video ↗

Inference-First Compounding Budget

new

Under a fixed total compute budget, spending first on inference or serving cost reduction yields a higher final benchmark score than spending the same budget first on harness edits, because cheaper rollouts increase the number of optimization iterations.

Proof of concept

Compare two budget-allocation orders on a small agent optimization task: inference-cost-first versus harness-edit-first, holding total spend constant.

Measurement

Final score per dollar, number of completed rollouts, cost per rollout, and final score at matched total spend.

Architectural implications

3

The meta-agent edits prompts, tools, and skills as a versioned, machine-writable harness surface.

Before

Harness configuration (prompts, tool wrappers, timeouts, retry policy) is hand-tuned by engineers and treated as static glue around a model.

After

Harness becomes a first-class artifact with an objective function and a dedicated optimizer agent that rewrites it across episodes.

Consequence

Teams need harness versioning, diff review, and rollback for an artifact that changes itself; evaluation must distinguish model regression from harness regression.

Source video ↗

Optimizer and executor are separate agents with separate roles.

Before

One agent, one model, does both the task and any self-correction within the episode.

After

A strong model runs the outer diagnosis/editing loop while a cheaper or different model runs rollouts at scale.

Consequence

Cost model changes: expensive tokens concentrate in cross-episode analysis, cheap tokens in high-volume rollouts; the system becomes model-heterogeneous by design.

Source video ↗

Runtime robustness (backoff, liveness, termination) is inside the measured boundary.

Before

Reliability plumbing is considered orthogonal to model evaluation; failures are attributed to the model.

After

The harness owns retry semantics, progress-aware termination, and worker supervision as part of the capability surface.

Consequence

Benchmark numbers become non-comparable across harness versions unless the harness is pinned and published alongside the score.

Tradeoffs and failure modes

4

Loop detection

Benefit

Terminates genuinely stuck agents, saving tokens and wall-clock time.

Cost or risk

Naive repetition counters trigger false loop alarms on legitimate long-running work, silently truncating successful trajectories.

Source video ↗

Rate-limit handling

Benefit

Retry with backoff keeps long autonomous runs alive through throttling.

Cost or risk

Without backoff, throttling converts into failed tasks and the resulting score is misread as a model capability limit.

Source video ↗

Score attribution across model and harness

Benefit

Harness optimization yields large score gains (77.5% to 88.8%) at low cost.

Cost or risk

Gains attributed to 'the model' may actually be harness fixes, so leaderboard comparisons across systems conflate model capability with harness engineering.

Source video ↗

Long autonomous optimization runs

Benefit

A 17-hour unattended loop produced double-digit benchmark improvement without human intervention.

Cost or risk

Unattended loops require worker liveness and process supervision, otherwise premature process exits silently waste the run.
