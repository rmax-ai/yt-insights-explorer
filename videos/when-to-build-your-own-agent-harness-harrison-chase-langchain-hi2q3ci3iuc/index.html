Summary

Overview

  • Speaker: Harrison Chase
  • Channel: Sequoia Capital
  • Main topic: Agent harnesses, evals, observability, and continuous improvement loops for LLM agents
  • Purpose: To provide technical guidance on building, evaluating, and improving agent harnesses and continuous learning systems for AI applications. Harrison Chase, co-founder and CEO of LangChain, discusses the core anatomy of LLM agents—breaking them down into models, context, and harnesses. He covers when to build custom agent harnesses versus using off-the-shelf options, the importance of evals and observability (benchmarking with tools like Harbor), and the creation of a continuous learning data flywheel using tools like LangSmith Engine.

Topic Map

Parts of an Agent

  • Explanation: An agent consists of three core components: a model, context, and a harness that orchestrates them.
  • Key claims:
    • To own your intelligence, you must own all three parts: model, context, and harness.
    • Model ownership involves open weights and the ability to switch models.
    • Context ownership includes episodic, semantic, and procedural memory.
  • Examples:
    • Switching models to avoid lock-in and use the best model available.
    • Using RAG and chat history as semantic and episodic context.
  • Terminology:
    • harness
    • model
    • context
    • open weights
    • RAG
  • Why it matters: Understanding the components of an agent is essential for owning and customizing AI intelligence effectively.

How to Own Your Harness

  • Explanation: A harness gets the model the right context at the right time for a given task, orchestrating fixed and dynamic context.
  • Key claims:
    • Agents need environments, data connections, long-run context management, parallelization, human-in-the-loop, and self-improvement.
    • The base agent loop is an LLM calling tools in a loop until a task completes.
    • Customizing harnesses can be done via middleware (hooks and plugins) or custom cognitive architectures.
  • Examples:
    • LangChain as a base minimal harness vs. DeepAgents as a customizable harness.
    • Adding summarization, sandbox environments, and sub-agents as middleware.
  • Terminology:
    • middleware
    • hooks
    • plugins
    • sandboxes
    • sub-agents
    • context offloading
  • Why it matters: Harness engineering allows developers to adapt general models into specialized, reliable agents for domain-specific tasks.

Evals and Observability

  • Explanation: Every mission-critical agent needs benchmarks to define what 'good' looks like and catch regressions.
  • Key claims:
    • Private evals define quality inside an organization.
    • Harbor is becoming an industry-standard open source eval runner.
    • Observability into LLM inputs, outputs, and message trajectories is critical for debugging agent failures.
  • Examples:
    • Frontier-bench and Terminal-bench as coding agent benchmarks.
    • LangSmith trace views showing tool calls, latencies, and token costs.
  • Terminology:
    • evals
    • observability
    • Harbor
    • frontier-bench
    • trajectories
    • traces
  • Why it matters: Without proper evals and observability, debugging agents and preventing regressions is nearly impossible.

Data Flywheel and Continuous Improvement

  • Explanation: Building a continuous learning loop requires collecting traces, mining data, curating evals, and running experiments.
  • Key claims:
    • A continuous learning loop acts as a hill-climbing machine to compound AI investment value.
    • Feedback is crucial for the flywheel, coming from UX design and synthetic feedback (online evals).
    • LangSmith Engine automates trace data analysis to create issue boards and suggest prompt or harness fixes.
  • Examples:
    • Using fine-tuned SLMs as judges to reduce evaluation costs.
    • LangSmith Engine automatically grouping agent failure traces and proposing prompt modifications.
  • Terminology:
    • data flywheel
    • synthetic feedback
    • online evals
    • SLM judges

    • issue board
  • Why it matters: Automating the feedback and iteration loop enables agents to improve continuously over time with minimal manual overhead.

Key Points

Anatomy of an Agent

  • Explanation: Agents are composed of three parts: a model, context, and a harness.
  • Evidence: Diagrams showing harness wrapping model and context.
  • Practical implication: Developers should control all three layers to avoid vendor lock-in and maximize agent performance.

When to Build vs. Use Off-the-Shelf Harnesses

  • Explanation: Off-the-shelf harnesses work well for in-distribution tasks, while custom harnesses are needed for out-of-distribution tasks.
  • Evidence: Discussion of Codex/Claude Code vs. specialized domain harnesses like legal AI.
  • Practical implication: Start with general off-the-shelf harnesses and customize or build proprietary ones as domain specificity increases.

The Importance of Observability

  • Explanation: Most agent failures stem from poor context fed to the LLM rather than model incompetence.
  • Evidence: Analysis of LLM call errors and trace trajectories.
  • Practical implication: Implement detailed trace logging and trajectory inspection to effectively debug agent behaviors.

Frameworks, Models & Processes

Recipe for Continuously Improving Agents

  • How it works: A four-step iterative process to upgrade agent performance using production data.
  • Components:
    • Build a v1 agent and start running it
    • Collect lots of traces
    • Curate the trace data via data mining
    • Run experiments on your data
  • When to use: When deploying production LLM agents that need to improve over time based on real usage.

Examples & Case Studies

Comparing Codex, Claude Code, and DeepAgents on coding benchmarks using Harbor.

  • Illustrates: How different agent harnesses and models perform across standardized tasks.
  • Lesson: Benchmarking allows developers to quantitatively evaluate trade-offs between different models and harness architectures.

The harness — not the model — is the engineering surface: it is defined as the component that gets the model the right context at the right time, orchestrating fixed versus dynamic context. This reframes agent quality as a context-assembly and orchestration problem, with the model as a swappable dependency.

Why it matters

It tells engineers where to invest effort and where to enforce abstraction boundaries: context assembly, orchestration, and loop control rather than model selection.

Generalization

Any LLM application can be decomposed into model + context + orchestration layer; the orchestration layer is the durable, portable asset and the one that absorbs domain specificity.

Research question

Why

It decides where the reliability budget goes: context plumbing and retrieval, or model upgrades. If context defects dominate, trace-level observability becomes day-one runtime infrastructure instead of monitoring.

Ownership benchmark: proprietary harness versus frontier off-the-shelf harness

Research question

Why

The ownership argument is presented as a principle, not an empirical result. Without a counterfactual benchmark, the build-your-own decision is unmade and organizations will fork architectures they did not need to fork.

Crossover threshold from middleware extension to custom cognitive architecture

Research question

At what measured task-distribution distance does a middleware-extended off-the-shelf harness degrade relative to a custom cognitive architecture, and what is the cost of the later migration?

Why

Without a criterion or cost model for the crossover, teams either over-build custom loops early or hit a middleware ceiling late and pay migration twice.

Fidelity–cost frontier of distilled SLM judges on agent trajectories

Research question

Why

Online evals only work continuously if judging is cheap; if the cheap judge mis-scores exactly the out-of-distribution cases the flywheel must catch, the cost win is a silent reliability regression.

Article ideas

4

The Harness Is the Product — The Model Is a Swappable Dependency

Agent quality is decided in context assembly and orchestration, not model selection; teams that treat the model as the architecture will keep buying upgrades to fix defects that live upstream of the model.

Angle

Reframe agent engineering from model choice to context-getting: the harness is the layer that owns fixed versus dynamic context, environments, loop control, and extension points.

Source video ↗

You Don't Own Your Intelligence If You Only Own the Model

Model switchability is a hollow guarantee unless the memory substrate and harness are in-house; ownership is a three-layer property, and partial ownership is vendor lock-in with extra steps.

Angle

Walk the lock-in failure mode: swapping an API endpoint while episodic, semantic, and procedural memory remain framework internals means the institutional knowledge stays with the vendor.

Source video ↗

Middleware Until It Breaks: A Migration Rule for Agent Architecture

Extension points are the correct default and a full architectural fork should be triggered by a measured shift in task distribution, not by ambition, so the engineering question is the crossover criterion rather than the aesthetic of a custom loop.

Angle

Give the decision rule with its missing measurement: define in-distribution versus out-of-distribution signals, name the middleware ceiling symptoms, and price the late migration.

Source video ↗

Traces Are the Asset, Dashboards Are the Cost

Observability only compounds when traces feed a mine, curate, experiment, deploy loop; standalone trace viewers are expensive logging that documents failures without reducing them.

Angle

Argue the trace store is the durable, reusable artifact and eval runners plus issue boards are the machinery that turns it into hill-climbing progress.

Project ideas

4

Crossover Bench

beyond-evals

A middleware-extended off-the-shelf harness matches a custom cognitive architecture on in-distribution tool-use tasks and degrades measurably past a reproducible out-of-distribution perturbation threshold.

Proof of concept

Implement the same domain task suite twice — a base harness with middleware (summarization, sandbox, sub-agents) and a custom loop — and sweep task perturbations from in-distribution to out-of-distribution on a shared eval runner.

Measurement

Quality per engineering-hour and per token as a function of distribution distance, plus the perturbation level at which the middleware harness falls below the custom architecture.

Source video ↗

Context Autopsy

gatehouse

A large majority of traced agent failures can be attributed automatically to context-assembly defects rather than model capability, and resolving the attributed context defect eliminates the failure without a model change.

Proof of concept

Instrument a deployed agent to capture full LLM inputs, message trajectories, tool calls, and latencies; build a classifier that labels each failure as context-defect or model-capability; apply targeted context fixes and re-run the same traces.

Measurement

Share of failures attributed to context defects, resolution rate after context-only fixes, and regression rate on existing private evals.

Source video ↗

Judge Divergence Ledger

beyond-evals

Distilled SLM judges agree with frontier-model judges on in-distribution traces but diverge systematically on out-of-distribution traces — exactly the region the improvement flywheel must detect.

Proof of concept

Fine-tune an SLM judge on agent trajectory labels and evaluate it against a frontier judge over held-out traces bucketed by distribution distance and failure type.

Measurement

Agreement and directional error by bucket, and the trace volume at which the SLM cost advantage exceeds the measured fidelity gap.

Source video ↗

Fix Proposal Survival Rate

new

Most machine-proposed prompt or harness fixes derived from grouped failure traces do not survive evaluation without degrading existing evals, and the survival rate is predictable from issue-cluster features.

Proof of concept

Build a pipeline that clusters failure traces into an issue board, proposes prompt or harness modifications, applies each proposal to a shadow harness, and runs the full eval suite plus private evals before acceptance.

Measurement

Fraction of proposals passing all evals, regression rate per accepted proposal, and correlation between survival and issue-cluster features such as cluster size.

Source video ↗

Architectural implications

4

The harness becomes an explicit, named layer boundary between model and context rather than implicit glue code inside an application.

Before

Prompt strings, retrieval calls, and tool loops scattered through application code with the model treated as the architecture.

After

A harness component owns context assembly, loop control, environments, and extension points, with the model as a replaceable dependency.

Consequence

Enables model switching and middleware-based extension without rewriting domain logic, but requires investing in context plumbing up front.

Source video ↗

Evaluation becomes transportable infrastructure via a standard runner (Harbor), making harness/model comparisons a routine benchmark operation.

Before

Per-team, bespoke eval scripts that are not comparable across harnesses or models.

After

Shared open-source eval runners where custom and off-the-shelf harnesses are measured on the same tasks.

Consequence

Harness choices become empirically comparable and regressions detectable, but pushes teams toward standard task suites that may not reflect private domain quality.

Source video ↗

Debugging interfaces shift from model-output inspection toward trajectory-level context inspection.

Before

Tuning prompts and upgrading models in response to bad answers.

After

Inspecting full LLM inputs, outputs, and message trajectories to locate context defects.

Consequence

Observability tooling (trace views with tool calls, latencies, token costs) becomes a first-class runtime dependency rather than a monitoring afterthought.

Source video ↗

The improvement loop is closed by automation that reads traces and emits proposed changes to prompts and harnesses.

Before

Humans read traces, cluster failures by hand, and write fixes.

After

Systems mine traces, group failures into an issue board, and propose prompt or harness modifications for review.

Consequence

Human effort concentrates on validating and reviewing proposed fixes, introducing a new review bottleneck and a need to measure auto-proposed changes.

Tradeoffs and failure modes

4

Middleware extension versus custom cognitive architecture

Benefit

Middleware (hooks and plugins) delivers summarization, sandboxes, and sub-agents without rebuilding the loop, keeping harness code minimal.

Cost or risk

Extension points can hit a ceiling on out-of-distribution tasks, forcing a later, more expensive migration to a fully custom architecture.

Source video ↗

Open weights and model switchability as a lock-in defense

Benefit

Owning the model layer avoids vendor lock-in and lets teams use the best available model per task.

Cost or risk

Switching models is only safe if context and harness are also owned; otherwise institutional memory and orchestration logic stay trapped with the vendor.

Source video ↗

Automated trace mining and fix proposal

Benefit

Grouping failure traces and proposing prompt or harness fixes removes manual triage from the improvement loop.

Cost or risk

Machine-proposed modifications arrive without stated validation, creating risk of unverified changes flowing toward production and a new review burden.

Source video ↗

Synthetic feedback and SLM judges

Benefit

Fine-tuned small-model judges reduce evaluation costs and enable online evals at production frequency.

Cost or risk

Judge quality is not established in the summary; a distilled judge can systematically mis-score exactly the out-of-distribution cases the flywheel is meant to catch.
