  • Main topic: Building memory-aware agent harnesses for anti-money laundering applications using Oracle AI Database.
  • Purpose: To provide an educational workshop on designing, structuring, and implementing memory-aware agent harnesses for financial fraud detection and anti-money laundering workflows. Nacho Martinez presents a workshop on building memory-aware agent harnesses from the ground up using an Oracle AI Database. He explains the concept of the Agent Stack, the anatomy of AI agents, and how agent harnesses bridge the gap between autonomous reasoning models and reliable production applications. He discusses memory layers, context engineering, toolboxes, skill distillation, and hybrid search methods.

Key Points

Most agent problems are harness problems

  • Explanation: When an agent fails, developers often blame the frontier model, but modifying the harness scaffolding usually yields better performance gains.
  • Evidence: Observed in various agent deployments where changing prompts, memory, or tooling fixes failures.
  • Practical implication: Focus engineering efforts on building robust harnesses rather than fine-tuning underlying models.

Filesystems vs Databases for Agent Storage

  • Explanation: While files are easy for unstructured blobs, multi-agent writes require database-level ACID compliance to prevent race conditions.
  • Evidence: Worktree pattern failure modes when multiple agents edit the same markdown file concurrently.
  • Practical implication: Use relational and vector databases for robust multi-agent memory persistence.

Context Window Limitations

  • Explanation: Larger context windows do not guarantee better results due to attention degradation and token costs.
  • Evidence: Academic studies on attention matrix accuracy over longer input lengths.
  • Practical implication: Employ summarization, compaction, and selective retrieval to keep context windows compact and relevant.

Core insights

6
[A]Architecturemedium noveltymoderate evidence

Agent memory should be treated as an ACID transactional store, not a filesystem of markdown blobs. The failure mode is concrete: multiple agents writing to the same file via a worktree pattern produce consistency conflicts and lost updates, because files lack ACID guarantees. Databases supply ACID, vector search, ranking, and security as primitives, so memory, retrieval, and access control collapse into one component rather than being bolted together.

Why it matters

It relocates the memory abstraction boundary from an app-level file convention to a database contract, which changes how concurrency, durability, and permissions are enforced in any multi-agent system.

Generalization

Any agent system with concurrent writers needs transactional semantics on its shared state; file-based memory is only safe for single-writer, append-only, blob-shaped artifacts.

[M]Mechanismhigh noveltymoderate evidence

The toolbox pattern decouples tool inventory size from context size: tools are registered through a write path as vector embeddings, and on every user turn a read path performs cosine top-k retrieval plus an LLM selector, injecting only the relevant tools into the prompt. This is what allows an agent to hold hundreds of tools without blowing the token budget.

Why it matters

It removes the system-prompt-as-tool-registry constraint and turns tool selection into a retrieval problem with its own write/read lifecycle and its own failure surface (retrieval recall).

Generalization

Any large, dynamic capability surface exposed to an LLM — tools, skills, procedures, API endpoints — should be indexed and retrieved per turn rather than enumerated statically.

[O]Mental Modelmedium noveltyweak evidence

Failure attribution defaults to the model when the leverage is actually in the harness (prompts, memory, tooling, scaffolding). Changing the harness reportedly yields larger gains than switching or fine-tuning frontier models, which reframes harness engineering as the primary optimization surface.

Why it matters

It redirects engineering budget away from fine-tuning and model-shopping toward the parts of the stack a team actually controls and can iterate on quickly.

Generalization

In layered systems, the layer with the most local change velocity absorbs most of the performance optimization work — here, the data/harness layer rather than the model layer.

[~]Tradeoffmedium noveltymoderate evidence

Context rot means expanding the context window is not a scaling answer: attention quality degrades as input length grows, so accuracy declines even when the tokens fit. The harness must actively maintain a dense, relevant window via summarization, compaction, and selective retrieval.

Why it matters

It makes context a managed resource with an eviction/compression policy rather than an unbounded buffer, which directly affects accuracy, token cost, and long-horizon task reliability.

Generalization

Long-running agents need a context maintenance policy analogous to a cache replacement policy: what to summarize, when to compact, and what to retrieve back in.

Why it matters

It gives a concrete layering (Application, Data, Model, Infrastructure, Compute) that tells an engineer where to invest to change agent behavior without touching the model.

Generalization

When the model is a commodity, differentiating behavior comes from the state and retrieval substrate beneath the reasoning loop.

[O]Mental Modelmedium noveltymoderate evidence

Agent memory is not a single store but a taxonomy with distinct schemas and lifecycles: short-term working memory, plus long-term episodic (past conversations, tool logs), procedural (workflows, skills), and semantic (personas, entities) memory.

Why it matters

Each memory class has different write frequency, retention, and retrieval patterns, so collapsing them into one vector bucket loses the structure needed for correct retrieval and for skill reuse.

Generalization

Separate memory by access pattern and lifetime, not by convenience; procedural memory in particular is the substrate for skill distillation and reuse.

Project ideas

4

Harness Ablation Bench

beyond-evals

Holding the model fixed, harness-only changes (prompt, memory, tooling, scaffolding) produce a larger task-success delta than upgrading to a stronger frontier model on the same agent benchmark.

Proof of concept

Build a benchmark runner that executes the same agent tasks across a matrix of harness configurations and two model tiers; log success, token cost, and failure category per run.

Measurement

Task success rate delta, cost per success, latency; compare best harness-only configuration against model-upgrade configuration.

Source video ↗

Toolbox Recall Auditor

beyond-evals

Vector top-k tool retrieval plus an LLM selector misses the ground-truth tool at a measurable rate that increases with tool-library size, and semantic-only retrieval does not recover the miss.

Proof of concept

Create synthetic tool libraries of 50, 200, and 500 tools with labeled query-to-tool mappings; for each query measure whether the correct tool appears in top-k and whether the selector chooses it.

Measurement

Recall@k, selector pick rate conditional on presence, end-to-end task success, and miss rate by library size.

Source video ↗

Transactional Memory Load Harness

gatehouse

An ACID database memory substrate eliminates lost updates from concurrent agent writers while keeping p99 per-turn latency within an acceptable bound versus a shared-file worktree baseline.

Proof of concept

Run N concurrent agent loops that write episodic logs and read shared state against a worktree file store and against a transactional database with vector search; inject overlapping writes.

Measurement

Lost updates and conflicts, p99 turn latency, write contention, retrieval latency, and recovery correctness.

Source video ↗

Skill Distillation Reuse Validator

new

Procedures distilled from successful episodic traces into procedural memory improve reuse task success over re-deriving from scratch, and replay validation filters harmful skills before reuse.

Proof of concept

Extract candidate skills from successful traces, store them as retrievable procedural memory, validate by replaying on held-out tasks, then compare retrieval plus reuse against a no-skill baseline.

Measurement

Reuse success rate, validation false-positive rate, token and latency savings, and regression rate on held-out tasks.
