Summary

Overview

  • Speaker: Brandon Waselnuk
  • Channel: AI Engineer
  • Main topic: Context engineering for AI coding agents and teams
  • Purpose: To educate AI engineers on why AI agents fail due to lack of organizational context and how to build or adopt a context engine that integrates data sources, resolves conflicts, and optimizes tokens. Brandon Waselnuk from Unblocked discusses context engineering for AI agents and how providing correct enterprise context solves the problem of AI models blindly agreeing with users ('You're absolutely right!'). He breaks down the AI maturity curve from tab complete to autonomous agent teams, outlines the failures of curated-context traps and MCP plateaus, details the six core requirements for a real context engine, and presents real-world impact metrics.

Key Points

The gap is not intelligence, it's context

  • Explanation: Models are increasingly intelligent (like Mythos or future models), but fail when they lack specific company and team context.
  • Evidence: Quoting Andrej Karpathy: 'The gap is not intelligence. It's context.'
  • Practical implication: Engineering effort should focus on context engineering rather than waiting solely for smarter base models.

Access to information does not equal understanding

  • Explanation: Giving agents access to all repositories and documents via naive RAG or MCP does not mean they understand organizational priorities, permissions, or temporal relevance.
  • Evidence: Comparison of underwater iceberg of code that compiles vs. hidden tribal knowledge like feature flag rollouts.
  • Practical implication: Context engines must resolve conflicts, apply recency signals, and respect governance.

Token and Time Efficiency via Context Hydration

  • Explanation: Hydrating prompts with pre-filtered, relevant context eliminates wasteful search loops and reduces token consumption.
  • Evidence: Cloudbeds benchmark: 2 hours 33 minutes down to 25 minutes; 20.9M tokens down to 10.8M tokens.
  • Practical implication: Context engineering directly lowers API costs and accelerates developer velocity.

Core insights

6
[A]Architecturehigh noveltymoderate evidence

A production context engine is defined by six co-equal requirements — unified system context across code/docs/Slack/conversations/incidents, targeted retrieval, conflict resolution, personalized relevance, token optimization, and permission enforcement — rather than retrieval quality alone.

Why it matters

Most teams build a retrieval layer (RAG or MCP) and treat conflict resolution, personalization, and permissions as afterthoughts. Naming them as first-class requirements changes what components must be built and where the boundary between 'tool' and 'engine' sits.

Generalization

Any agent operating over multi-source enterprise data needs conflict resolution, recency, per-user relevance, and ACL enforcement as distinct subsystems, not as prompt instructions.

[!]Failure Modehigh noveltymoderate evidence

'Satisfaction of search bias' is a concrete agent failure mode: when retrieval is exposed as raw MCP tools, the agent stops at the first plausible piece of information rather than continuing to search for the authoritative source.

Why it matters

This reframes MCP as a local maximum. If the agent decides when to stop searching, reliability is bounded by the agent's own stopping heuristic; pre-filtering and ranking must move into the engine.

Generalization

Giving an agent unconstrained search tools pushes stopping-criteria decisions into the model, where first-match heuristics dominate over coverage or authority.

Source video ↗
[!]Failure Modemedium noveltymoderate evidence

Hand-curated context repositories (markdown files in a virtual filesystem) rot faster than they can be maintained, becoming stale tribal knowledge that directly contradicts live sources such as Slack.

Why it matters

This challenges the common 'just write a CLAUDE.md / rules file' practice. Static curated context creates a floor of correctness that decays over time and introduces contradictions the agent has no mechanism to detect.

Generalization

Manually curated context is a perishable asset; any context source without an ingestion/refresh pipeline should be treated as degrading infrastructure.

Source video ↗
[O]Mental Modelmedium noveltymoderate evidence

The cost of bad context compounds monotonically along the autonomy curve: tab complete surfaces errors early, agent IDEs create doom loops, parallel agents create 'review tax' on senior engineers, and fully autonomous background agents produce silent failures where code compiles but breaks production.

Why it matters

It gives a staged maturity model where each increment of autonomy raises the required context quality rather than just changing tooling. Teams scaling autonomy without context investment shift cost from authoring to review and then to incident response.

Generalization

Reliability requirements for context scale super-linearly with agent autonomy; a context investment that is adequate for human-in-the-loop is insufficient for unsupervised agents.

Source video ↗
[E]Empirical Resultmedium noveltymoderate evidence

Token optimization via pre-hydrated context improves answer quality and cuts token usage simultaneously — the reported benchmark moved a task from 2h33m to 25m and tokens from 20.9M to 10.8M.

Why it matters

Directly contradicts the 'give the model more context / bigger window' intuition: more retrieved material means answers buried in noise, more search loops, and higher cost. This is a measurable, testable cost/quality lever.

Generalization

Pre-filtering and ranking context before it reaches the model can reduce cost and improve quality in the same intervention, because irrelevant context is actively harmful, not merely wasteful.

Why

Architectural implications

3

Context provenance and governance move out of the repository and into a dedicated ingestion/service layer.

Before

Team context lives in hand-maintained markdown, docs, and tribal knowledge spread across repos and chat.

After

A context engine ingests code, docs, Slack, conversations, and incident management, and serves resolved, permission-filtered context on demand.

Consequence

Context becomes stateful infrastructure with ACLs, freshness guarantees, and schema/versioning concerns rather than prompt-time text.

Source video ↗

Retrieval responsibility shifts from the agent's tool-calling loop into the engine.

Before

Agent decides when to call MCP/vector search and when to stop (leading to satisfaction of search bias).

After

Engine pre-filters, ranks, resolves conflicts, and hydrates a targeted context payload for the agent.

Consequence

Agent design simplifies to reasoning over given context, while reliability depends on engine ranking quality — a different, more testable component boundary.

Source video ↗

Permission enforcement becomes an agent-runtime concern, not just an application concern.

Before

Agents retrieve broadly and rely on the user's own access as an implicit filter.

After

The engine enforces per-user permission and personalized relevance before context is assembled.

Consequence

Context assembly must be user-scoped and auditable, adding identity/ACL coupling to every retrieval path.

Source video ↗

Tradeoffs and failure modes

4

Broad retrieval via MCP tool access

Benefit

Agents get access to information across many systems without building a bespoke ingestion pipeline.

Cost or risk

Satisfaction of search bias leads agents to stop at the first result, producing shallow answers, extra search loops, and token waste; access is mistaken for understanding.

Source video ↗

Hand-curated context repositories

Benefit

Cheap, fast to create, and immediately usable as agent context or rule files.

Cost or risk

They rot faster than they can be updated, producing stale tribal knowledge that conflicts with live sources like recent Slack threads.

Source video ↗

Aggressive context hydration and token optimization

Benefit

Large reductions in wall-clock time (2h33m to 25m) and tokens (48% fewer), with better answer quality because signal is not buried.

Cost or risk

Requires standing up and maintaining a multi-source engine with conflict resolution and permission enforcement, which is materially more engineering and governance work than a prompt file.

Source video ↗

Increasing agent autonomy (parallel/background agents)

Benefit

Higher throughput and less human-in-the-loop effort per task.

Cost or risk

Bad context converts into review tax on senior engineers and then into silent failures where compilable code violates unstated requirements such as feature-flag rollouts.
