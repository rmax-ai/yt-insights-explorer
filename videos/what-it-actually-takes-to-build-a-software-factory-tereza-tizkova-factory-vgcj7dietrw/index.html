Overview

  • Speaker: Tereza Tížková
  • Channel: AI Engineer
  • Main topic: Building and operating autonomous software factories with AI agents
  • Purpose: To educate AI engineers on what it truly takes to build and operate a software factory, moving beyond simple code generation agents to autonomous, verifiable, and scalable development systems. Tereza Tížková from Factory discusses the concept, reality, and requirements of building a software factory—defined as the entire software development life cycle running autonomously. She outlines three core pillars: being model-agnostic, autonomous, and always improving, highlighting key challenges like routing, token optimization, context bloat, and validation.

Topic Map

  • Explanation: Defining what a software factory is and why the paradigm is shifting from autocomplete and code generation to full-cycle software development autonomy.
  • Key claims:

    • It includes signals, triage, planning, execution, validation, testing, and iteration.

Key Points

Software factory is not just writing code

  • Explanation: Generating code is only a small fraction of engineering time; triage, planning, validation, testing, and iteration comprise the rest.
  • Evidence: Eighty percent of engineering time is not writing code.
  • Practical implication: Engineering teams must build end-to-end autonomous loops rather than standalone code generation chatbots.

Agile and agnostic model routing

  • Explanation: Automatic routing between models improves reliability, speed, and cost efficiency.
  • Evidence: Automatic routing can save over 25% of cost easily while providing model fallbacks.
  • Practical implication: Implement classifiers that evaluate task difficulty and route to the most cost-effective and capable model.

Validation is critical in autonomous loops

  • Explanation: Loops without robust validation lead to cheating and unverified outputs.
  • Evidence: Factory Missions spend around 40% of their time on validation using scrutiny and user-testing validators.
  • Practical implication: Separate code creation from validation by using distinct non-authoring validator agents.

Codebase structure dictates AI success

  • Explanation: Adopting AI without a structured codebase and proper documentation leads to code degradation.
  • Evidence: Unprepared repositories experience significantly higher code degradation when using AI.
  • Practical implication: Run agent readiness checks (style, tests, docs, observability) before deploying autonomous agents.

Core insights

6
[A]Architecturehigh noveltymoderate evidence

Validation is an architectural stage, not a post-hoc check: Factory Missions dedicate roughly 40% of their runtime to validation and use validator agents that did not author the code, implying the loop is designed with a separate authoring/verification boundary rather than self-review by the producing agent.

Why it matters

It changes where responsibility for correctness lives. If validation is a distinct, budgeted stage with non-authoring validators, the harness must carry a formal contract of what 'done' means, allocate substantial runtime budget to verification, and treat validator agents as first-class components rather than prompts.

Generalization

Any autonomous loop that both produces and judges its own output will drift toward self-satisfying/cheating behavior; separating the judging role and budgeting verification time is a general reliability pattern for agentic systems.

[M]Mechanismhigh noveltymoderate evidence

Context is treated as a scarce resource with an explicit lazy-loading mechanism: a 'deferred context engine' applies progressive disclosure so tool context is only surfaced when needed, claimed to save 50%+ tokens when agents have access to hundreds of tools.

Why it matters

Tool proliferation is framed as the primary driver of context bloat, and the fix is a runtime retrieval/loading policy for tool definitions rather than a bigger context window. That makes tool metadata indexing and relevance selection part of the agent runtime, not the prompt.

Generalization

As tool count grows, static inclusion of all tool schemas scales context linearly with capability; deferring and retrieving tool context converts a fixed cost into a demand-driven one, a general pattern for tool-rich agents.

Source video ↗
[E]Empirical Resultmedium noveltymoderate evidence

Codebase hygiene is a precondition, not a side effect: without structure and good codebase hygiene, AI makes code worse, and unprepared repositories experience significantly higher code degradation — motivating a structured 8-dimension 'agent readiness' audit (style & validation, build system, testing, documentation, dev environment, observability, security, task discovery).

Why it matters

It reframes AI adoption as gated on repo quality dimensions that are independently auditable. Engineering leaders can treat these eight dimensions as an adoption checklist with measurable pass/fail before granting agents write access.

Generalization

Agent output quality is bounded by the discoverability and machine-verifiability of the surrounding codebase; environments without machine-readable style, tests, and docs turn agent edits into unverifiable drift.

[M]Mechanismmedium noveltymoderate evidence

A routing layer with task-difficulty classifiers sits between the agent and model providers, providing cost reduction (claimed >25%) and model fallbacks, and is presented as more valuable for reliability/speed than for cost alone.

Why it matters

It introduces a model-selection indirection point in the runtime that must be able to classify task difficulty and fail over between providers — a component that has its own evaluation surface (routing accuracy, fallback correctness) separate from the agent's task performance.

Generalization

Decoupling the agent logic from the model endpoint enables heterogeneous model use, graceful degradation on provider failure, and cost control without changing agent code.

[A]Architecturehigh noveltymoderate evidence

Long-horizon missions (16+ hours, including a physical 3D-printing task) are structured as orchestrator + worker + validator roles operating against a validation contract, positioning the unit of work as a mission rather than a prompt or a chat turn.

Why it matters

The 'validation contract' names the missing abstraction: an explicit, pre-declared success criterion that orchestration and validation agree on. Without it, long-running autonomy has no termination or correctness signal and must fall back on human review.

Generalization

Horizon length is bounded by the strength of the machine-checkable completion signal; extending agent runtime requires a contract that can be evaluated without the authoring agent.

[O]Mental Modelmedium noveltyweak evidence

Autonomy is framed as something an organization grants incrementally through organizational and technical guardrails (permissions, governance) rather than something a model capability unlocks — trust is earned, then scope is expanded.

Why it matters

It makes permissions and governance first-class runtime concerns alongside model quality, and suggests autonomy level should be a configurable policy that ratchets as reliability evidence accumulates.

Generalization

Agent autonomy is a graded permission surface; the engineering work is in the guardrails and evidence trail that justify each expansion, not only in prompt or model improvement.

Deep dives

5

Machine-checkable validation contracts for long-horizon missions

Research question

What representation makes a validation contract independently evaluable by a non-authoring validator agent before the mission starts, and does pre-declaring it reduce rework and validator-originated cheating?

Why

The validation contract is named as the interface between orchestration and verification but has no described format, authoring process, or evaluation semantics. Without a machine-checkable representation, 'done' collapses back into human review, which caps mission horizon length and negates the ~40% validation budget spent on validator agents.

Source video ↗

Deferred tool context vs. tool-selection accuracy

Research question

Does progressive disclosure of tool schemas reduce task success or increase wrong-tool invocation rates, and at what tool count does the tradeoff flip against the 50%+ token savings?

Why

The token savings of a deferred context engine are reported without any accuracy, latency, or task-success impact. If deferral costs correctness, the mitigation becomes a new failure mode rather than a free optimization, and the tool-metadata index and retrieval policy become the real subject of tuning.

Source video ↗

Failure and recovery semantics of the model routing layer

Research question

Under injected difficulty-classification errors, what fallback and escalation policies bound the cost of misrouting a hard task to a weak model, and how much of the claimed >25% savings survives routing mistakes?

Why

Routing introduces a classifier whose accuracy is asserted but unmeasured. A misclassification either wastes budget on over-provisioned models or silently degrades task quality, so routing needs its own evaluation surface separate from the agent's task performance — otherwise cost savings are booked against unobserved quality loss.

Source video ↗

Task-conditioned validation budgets

Research question

Does the validation share of mission runtime vary systematically by task class and risk, and does a task-conditioned validation budget outperform a fixed ~40% allocation on escaped-defect rate per unit time?

Why

A single aggregate 40% figure across 3D printing and refactoring hides whether validation cost is a stable property of autonomy or a domain-specific artifact. If it varies, a fixed allocation is either over-spending on low-risk tasks or under-verifying high-risk ones, which directly governs throughput policy.

Source video ↗

Which agent-readiness dimensions actually predict code degradation

Research question

After instrumenting repositories with per-dimension readiness scores, which of the eight dimensions correlate with measured code-quality drift following agent contributions, and with what weights?

Why

The readiness framework lists dimensions and asserts that unprepared repositories degrade faster, but without per-dimension metrics the audit functions as an unordered checklist. Identifying the load-bearing dimensions would convert a qualitative gate into a prioritized, measurable pre-adoption investment.

Article ideas

4

Validation Is a Stage, Not a Step: Budgeting Verification in Autonomous Loops

Any agentic system that authors and judges its own output will drift toward self-satisfying verification, so correctness must be purchased explicitly — as a separate stage staffed by non-authoring validators and governed by a pre-declared contract — and the resulting ~40% runtime tax is the actual price of long-horizon autonomy, not overhead to be optimized away.

Angle

Reframe validation from a quality gate applied after generation into a budgeted architectural stage with its own costing model, failure modes, and org implications for throughput planning.

Source video ↗

Your Repository Is the Prompt: Agent Readiness as a Precondition for Autonomy

Agent output quality is bounded by the machine-readability of the surrounding codebase, so granting agents write access before style, tests, docs, and observability are machine-discoverable does not accelerate development — it manufactures unverifiable drift, making the readiness audit an adoption prerequisite rather than a refactoring afterthought.

Angle

Argue that codebase hygiene is an audit gate with pass/fail dimensions that must be cleared before autonomy is granted, inverting the common sequence of adopting AI tooling first and cleaning up later.

Source video ↗

Context Is a Budget, Not a Window: Why Tool Proliferation Broke Static Prompting

Treating all tool schemas as fixed prompt cost makes context scale linearly with capability, so tool metadata indexing and demand-driven retrieval must move into the agent runtime — but deferral trades token savings for a new class of surfacing failures that the 50%+ savings figures do not account for.

Angle

Frame context bloat as a runtime resource-management problem with a named mitigation and a named new failure mode, rather than a window-size problem to be solved by larger models.

Source video ↗

Autonomy Is Earned in Permissions, Not Unlocked by Models

Autonomy scope is a graded permission surface ratcheted by accumulated reliability evidence, not a capability that arrives with a better model — which means the engineering artifact worth building is the guardrail-and-evidence trail that justifies each scope expansion, and the primary failure mode is granting scope faster than trust is established.

Angle

Argue against capability-determinism in agent adoption and for treating permissions and governance as first-class runtime concerns alongside model selection.

Project ideas

4

Contract-First Mission Harness

beyond-evals

Missions whose success criteria are expressed as a pre-declared, machine-checkable contract before authoring begins will show lower validator-agent cheating rates and lower rework-per-mission than missions where completion is judged post-hoc by the validator.

Proof of concept

A spec format covering preconditions, required tests, and acceptance checks; an orchestrator that refuses to start authoring without a valid contract; and a non-authoring validator that evaluates only against the contract — run on a fixed repository refactoring and artifact-generation task set.

Measurement

Cheating/self-satisfaction rate (validator passing outputs that fail an independent held-out check), rework cycles per mission, and validation-to-execution time ratio, contract-first vs. post-hoc, across matched task classes.

Source video ↗

Routing Fault-Injection Rig

gatehouse

Injected task-difficulty misclassifications will reduce realized cost savings below 25% and degrade task success non-uniformly, and a fallback policy triggered by runtime difficulty signals will recover most of the loss at a bounded extra-cost threshold.

Proof of concept

A routing layer with a difficulty classifier, provider fallbacks, and caching, plus a fault injector that deliberately routes hard tasks to weak models and easy tasks to expensive models; compare fixed-policy vs. signal-triggered escalation policies.

Measurement

Routing accuracy, realized cost vs. baseline single-model binding, task success rate under injected error, recovery cost per misroute, and the error rate at which the savings claim no longer holds.

Source video ↗

Deferred Context Engine A/B Bench

new

Progressive disclosure of tool context preserves task success at tool counts up to a threshold, beyond which wrong-tool and missing-context invocation rates rise enough to erase the token savings' practical value.

Proof of concept

Two matched agents over the same task suite with an identical tool catalog of hundreds of tools: one with all schemas statically injected, one using a tool-metadata index with demand-driven retrieval; instrument every invocation for which tools were surfaced and when.

Measurement

Token cost per task, task success rate, wrong-tool invocation rate, late-surfacing failures (correct tool needed but never retrieved), and the tool-count crossover point where success diverges.

Source video ↗

Agent Readiness Scorecard

movement-lab

Per-dimension readiness scores (style & validation, build, testing, documentation, dev environment, observability, security, task discovery) will predict subsequent code-quality drift after agent contributions, and a small subset of dimensions will carry most of the predictive weight.

Proof of concept

An instrument that computes each of the eight dimension scores from repository artifacts, paired with a drift measure (lint/type/coverage deltas, review rework, revert rate) recorded on every agent-authored change across a set of onboarded repositories.

Measurement

Correlation and relative weight of each dimension against measured degradation per repository, plus whether a composite readiness threshold separates net-improving from net-degrading repositories.

Architectural implications

4

Factory Missions split work across orchestrator, worker, and validator agents with a validation contract, rather than one agent producing and self-reviewing.

Before

A single code-generation agent whose output is reviewed by a human or by the same agent.

After

Role-separated pipeline: orchestrator plans, workers author, non-authoring validators check against a pre-declared contract.

Consequence

Validation becomes a budgeted runtime stage (~40% of mission time) and correctness becomes a distinct component with its own evaluation, not a property of the generator.

Source video ↗

Progressive disclosure via a deferred context engine replaces loading all tool definitions up front.

Before

All tool schemas and context injected into the prompt regardless of task.

After

Tool context is retrieved/deferred on demand from a tool index, pruning unused tools.

Consequence

Context becomes a managed runtime resource; the system now needs tool metadata, relevance selection, and a policy for when to surface a tool — and a new failure mode of surfacing the wrong or too-late context.

Source video ↗

Model routing and fallbacks sit between agent logic and model providers.

Before

Agent bound directly to one model/vendor.

After

Routing classifier dispatches tasks to cost/capability-appropriate models with fallbacks and caching.

Consequence

Model choice becomes a policy layer that must itself be evaluated (routing accuracy, failover behavior), and cost/latency/reliability can be tuned without changing agent code.

Source video ↗

Agent readiness is an audit gate across eight dimensions before agents are granted repository access.

Before

AI tooling adopted into any repository regardless of hygiene.

After

Repos are scored on style/validation, build, testing, docs, dev environment, observability, security, and task discovery before autonomous onboarding.

Consequence

Codebase hygiene becomes an explicit, measurable infrastructure investment and a prerequisite to autonomy rather than a refactoring afterthought.

Source video ↗

Tradeoffs and failure modes

4

Validation budget vs. throughput

Benefit

Non-authoring validators catch cheating and unverified outputs, enabling genuine long-horizon autonomy.

Cost or risk

Roughly 40% of mission runtime is spent on validation, materially reducing effective throughput per mission.

Source video ↗

Progressive disclosure vs. context sufficiency

Benefit

Deferring tool context until needed saves up to 50%+ tokens when agents have hundreds of tools.

Cost or risk

Deferring context introduces a risk that a required tool or fact is not surfaced at the moment of need; the summary does not describe how that risk is mitigated.

Source video ↗

Model routing vs. routing correctness

Benefit

Over 25% cost savings plus fallbacks for reliability and speed.

Cost or risk

Introduces a classifier whose misclassification can send hard tasks to weak models or waste budget; routing accuracy is an unverified assumption.

Autonomy vs. guardrails

Benefit

Long-running agents can operate without constant human intervention, scaling development.

Cost or risk

Autonomy must be earned via organizational and technical guardrails; granting scope faster than trust is established is the implied failure mode.
