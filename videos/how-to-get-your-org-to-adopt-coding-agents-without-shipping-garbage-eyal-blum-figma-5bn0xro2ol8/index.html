Summary

Overview

  • Speaker: Eyal Blum
  • Channel: AI Engineer
  • Main topic: Internal organizational adoption of coding agents at Figma while maintaining high code quality and developer satisfaction.
  • Purpose: To provide engineering leadership with actionable frameworks, strategies, and lessons learned on how to successfully scale coding agent adoption across an organization while maintaining high quality standards and developer morale. Eyal Blum, a software engineer at Figma, shares the internal journey of adopting coding agents into engineering workflows without compromising code quality. He outlines the three-act journey of AI adoption—the honeymoon phase, the crash, and mastering the real skill of AI usage. The talk addresses friction points like reduced developer agency, burnout among top engineers, and communication inflation, offering actionable lessons on verification, planning over prompting, treating feedback from skeptics as a roadmap, and attention-aware communication.

Topic Map

The Three-Act AI Adoption Journey

  • Explanation: Organizations go through three phases when adopting coding agents: the honeymoon phase where simple tasks work 10x faster; the crash where complex workflows fail, bugs slip through, and trust breaks down; and the real skill phase where proper planning and verification amplify human judgment.
  • Key claims:
    • Simple tasks work 10x faster in the honeymoon phase.
    • Complex workflows fail and erode trust during the crash phase.
    • Real skill involves proper planning, verification, and correct guardrails.
  • Examples:
    • Trying to apply simple prompting practices to bigger problems resulting in bad code and bugs.
  • Terminology:
    • Honeymoon phase
    • The crash
    • Real skill
  • Why it matters: Understanding this trajectory helps organizations anticipate burnout and resistance, guiding teams past the initial crash into mature AI usage.

Organizational Friction Points

  • Explanation: AI adoption creates distinct friction points: uneven adoption across teams, reduced developer agency, burden on top engineers acting as gatekeepers, and ineffective communication caused by AI-generated noise.
  • Key claims:
    • Adoption is uneven across different engineering teams.
    • Engineers experience reduced job satisfaction when stuck in prompt-and-react cycles.
    • Top engineers absorb disproportionate burnout acting as gatekeepers for bad AI code.
    • Design docs, Slack messages, and emails increase in volume without a corresponding increase in clarity.
  • Examples:
    • Top engineers holding all context and getting burnt out by blocking bad AI PRs.
  • Terminology:
    • Developer agency
    • Gatekeepers
    • Uneven adoption
  • Why it matters: Recognizing these friction points is essential for engineering leaders to design interventions that protect team morale and code quality.

Lessons Learned at Figma: Verification and Planning

  • Explanation: To succeed, organizations must invest in verification, shift-left validation, test-driven development (TDD), and rigorous planning before prompting agents.
  • Key claims:
    • Investing in verification is the highest-value thing an organization can do.
    • Left-shifting validation moves verification earlier in the workflow and down the testing pyramid.
    • TDD with agents leads to significantly better results because goals are defined before code is written.
  • Examples:
    • Using test-driven development where the agent is told to write code from red to green.
  • Terminology:
    • Shift-left validation
    • Test-driven development (TDD)
    • Verification pyramid
    • Deterministic analysis
  • Why it matters: Shifting from unstructured prompting to structured planning and verification unlocks massive productivity gains without shipping garbage.

Culture and Communication in the Age of AI

  • Explanation: Attention is a scarce resource in the age of AI. Organizations must build new communication cultures that clearly distinguish AI-generated content from human-authored content and meet engineers where they are already working.
  • Key claims:
    • Human attention is a scarce resource when AI generates abundant artifacts.
    • Marking AI versus human-generated content helps calibrate reading time and skepticism.
    • Meeting engineers where they are working (e.g., tagging agents in Slack) reduces friction.
  • Examples:
    • Adding human-written summaries at the top of PR descriptions followed by AI-generated details.
  • Terminology:
    • Attention-aware communication
    • Source clarity
    • Comms culture
  • Why it matters: Establishing clear communication protocols prevents communication fatigue and restores trust across engineering teams.

Key Points

Invest in Verification

  • Explanation: Empower agents with ways to validate their own work and shift validation left in the development lifecycle.
  • Evidence: Playwright MCP and automated test suites allow agents to explore and verify code independently.
  • Practical implication: Reduces human review overhead and catches bugs before code reaches production.

Plan Before You Prompt

  • Explanation: Putting engineers back in the driver's seat by writing detailed implementation plans before invoking agents prevents agent drift.
  • Evidence: Spending a week on a detailed plan yielded 5x speedups in implementation and review cycles.
  • Practical implication: Transforms AI usage from chaotic prompting to structured software engineering.

Treat Skeptics' Feedback as a Roadmap

  • Explanation: Skeptical engineers highlight real tool failures and lack of validation; their feedback is the blueprint for improving AI safety.
  • Evidence: Skeptics get upset when AI code lacks validation, pointing directly to gaps in guardrails.
  • Practical implication: Brings resistant engineers along the journey and hardens internal AI workflows.

Attention-Aware Communication

  • Explanation: Clearly delineate human intent from AI generation in PRs, Slack, and docs to respect scarce human attention.
  • Evidence: PR descriptions starting with human-written intent followed by AI details reduce misunderstandings and friction.
  • Practical implication: Improves signal-to-noise ratio in internal communication channels.

Frameworks, Models & Processes

The Three-Act AI Adoption Journey

  • How it works: Describes the psychological and operational stages organizations experience when adopting AI tools.
  • Components:
    • Act 1: The Honeymoon (simple tasks 10x faster)
    • Act 2: The Crash (complex work fails, bugs slip, trust breaks)
    • Act 3: The Real Skill (proper planning, verification, and human judgment)
  • When to use: When diagnosing team sentiment and planning organizational AI rollout strategies.

Verification Pyramid

  • How it works: Structures code verification from automated deterministic checks up to human review.
  • Components:
    • Deterministic Analysis (linting, compiler, unit tests)
    • Agent Review (agent validation against criteria)
    • Human Review (architecture, functionality, high-level decisions)
  • When to use: When establishing CI/CD pipelines and guardrails for coding agents.

Plan-Over-Prompt Framework

  • How it works: Shifts effort from interactive trial-and-error prompting to upfront architectural planning.
  • Components:
    • Start with the 'Why' (executive summary)
    • Break it down into small, independently verifiable parts
    • Ensure each part has a validation gate
  • When to use: Before delegating complex coding tasks to autonomous agents.

[A]Architecturemedium noveltymoderate evidence

Verification should be structured as a tiered pyramid with distinct owners: deterministic analysis (linting, compiler, unit tests) first, then agent self-review against explicit criteria, then human review reserved for architecture, functionality, and high-level decisions. The speaker frames verification investment as the single highest-leverage organizational action — i.e., the bottleneck to agent productivity is validation capacity, not generation capacity.

Why it matters

It reframes the agent harness as primarily a validation pipeline: work should be routed upward through cheap deterministic gates before it ever consumes human attention. Teams that instead scale generation without scaling verification create a review bottleneck downstream.

Generalization

Any system where an agent produces artifacts faster than humans can audit them needs an explicit ordered verification ladder with cost-weighted routing from cheap automated checks to expensive human judgment.

[M]Mechanismmedium noveltymoderate evidence

Giving the agent executable feedback surfaces (Playwright MCP, automated test suites) so it can explore and validate its own work is presented as a concrete mechanism for closing the loop inside the agent runtime, rather than deferring all feedback to human reviewers.

Why it matters

The agent's reliability depends on having tools that return ground-truth signals about its own output. Handing the agent a browser-driving MCP server and a runnable test suite converts verification from a human post-process into an in-loop, machine-checkable step.

Generalization

Agent harness design should prioritize equipping agents with the same executable oracles a human engineer would use (test runners, linters, browser automation, type checkers) so correctness signal is available at generation time rather than review time.

Architectural implications

4

Verification moves from a terminal human review stage into the agent's own execution loop via deterministic checks and self-review.

Before

Agent generates code; the first correctness signal comes from a human reviewer at the end of the pipeline.

After

Agent runs linting, compiler, unit tests, and its own criteria-based review before handing off; humans review architecture and functionality only.

Consequence

Human review capacity is preserved by design, and the gatekeeper burnout pattern is mitigated; verification tooling becomes the critical path for adoption velocity.

Source video ↗

The test suite becomes the primary interface for specifying agent work rather than only a regression net.

Before

Tests exist to catch regressions after code is written by a human.

After

Tests are authored first as the goal contract; the agent is driven from red to green against them.

Consequence

Investment in test infrastructure and coverage becomes a prerequisite for safe agent delegation, and spec plus acceptance criteria collapse into one artifact.

Source video ↗

Generated artifacts need an explicit human-intent layer at their head so readers can separate intent from elaboration.

Before

PR descriptions, docs, and messages are assumed to be human-authored and read uniformly.

After

Artifacts start with a short human-written summary/intent followed by AI-generated detail, with AI content marked.

Consequence

Readers calibrate reading time and skepticism per section; provenance labeling becomes a required property of communication pipelines.
