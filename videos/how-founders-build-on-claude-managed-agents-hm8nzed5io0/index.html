Overview

  • Speaker: Lance Martin, Sahaj Garg, Mihir Garimella, Todd Olson
  • Channel: Claude
  • Main topic: Building and scaling AI agents using Claude Managed Agents, covering features like briefs, outcomes, memory architectures, and cost optimization.
  • Purpose: To share real-world founder experiences and technical insights on building, evaluating, and scaling AI agents using Claude Managed Agents. In this roundtable discussion, founders and Anthropic engineers explore how they build products on Claude Managed Agents. They discuss the entire journey of meetings and sales workflows, highlighting features like pre-meeting briefs, post-meeting task automation, cross-account aggregation, memory architectures (per-account vs. global org-wide memory), sandboxing source code, attribution of outcomes, and cost-vs-control trade-offs when scaling agent fleets.

Frameworks, Models & Processes

Outcome-Based Rubric Evaluation

  • How it works: Define clear evaluation rubrics for agent tasks, allowing the agent to iterate until the rubric is satisfied, backed by an independent verification agent.
  • Components:
    • Rubric definition
    • Iterative agent execution
    • Independent verification agent
    • Attribution checks
  • When to use: When building customer-facing features where accuracy and grounded context are critical to prevent user confusion.

Hierarchical Agent Memory

  • How it works: Maintain continuous, persistent memory at the individual account level while feeding insights upward into a global cross-account memory layer for aggregation.
  • Components:
    • Per-account persistent agent
    • Org-wide memory store
    • Cross-account aggregation layer
  • When to use: When scaling AI agents across complex enterprise accounts with hierarchical management structures.

[M]Mechanismhigh noveltymoderate evidence

Outcomes are implemented as rubrics that a separate, independent verifier agent scores iteratively until satisfied, rather than having the generating agent self-assess its own output.

Why it matters

Splits generation and verification into distinct agent roles with an explicit acceptance criterion, which is a concrete architectural pattern for reliability rather than a vague 'add evaluation' recommendation; it implies a cost/latency budget for a second agent pass on every task.

Generalization

Any agentic pipeline with externally-visible output can be made more trustworthy by moving acceptance criteria into an explicit rubric evaluated by a non-generating judge loop.

Deep dives

4

Statistical independence of verifier agents

Research question

When the generating agent and the verifier agent come from the same model family, what fraction of injected entity-level errors does the verifier actually catch, and how much does that catch rate improve with a heterogeneous verifier or a deterministic entity-resolution check?

Why

The whole reliability claim of the outcomes/rubrics pattern rests on the verifier being independent in the statistical sense, not just architecturally separate. If same-family verification correlates with generation failure modes, teams pay a per-task inference pass and still ship misattributed context to users. This is measurable before any product bet is made.

Source video ↗

Rubric lifecycle: authoring, versioning, and drift

Research question

Can outcome rubrics be derived from failure examples and maintained as regression suites, and what is the detection lead time (and false-alarm rate) when rubric pass-rates drift as an underlying workflow changes?

Why

Rubrics are named as the acceptance mechanism but the summary gives no authoring or upkeep process. Without a lifecycle, rubrics decay into stale gates that either pass bad output or block good output, and the verification layer becomes a cost with no reliability benefit.

Source video ↗

Memory scope precedence and conflict reconciliation

Research question

When per-account memory and organization-wide memory disagree on the same fact, which scope wins under a stated rule, and how much does downstream answer accuracy degrade compared with a single-store baseline?

Why

Two-tier memory is presented as hierarchical without stating precedence or write-conflict rules. Multi-tenant agent fleets will write contradictory facts into both scopes; without an explicit resolution rule the aggregation layer silently becomes the source of truth for individual accounts, which is the exact failure that makes cross-account roll-ups untrustworthy.

Source video ↗

Per-agent cost attribution as the input to routing and the build-vs-buy crossover

Research question

At what request volume does routing a task class from real-time frontier inference to lighter batch processing become net beneficial after accounting for measured quality loss, and can per-agent/per-account cost attribution predict that crossover before it is hit?

Why

Cost optimization is framed as a trade-off but the summary names no metric or threshold, and the managed-versus-custom-harness decision is likewise framed as cost- and control-dependent. A per-task cost ledger tied to account and agent is the prerequisite for turning both decisions from arguments into instruments.

Article ideas

3

Your Independent Verifier Is Not Independent

Architectural separation of generator and verifier is not statistical independence: when both share a model family they share failure modes, so verification only buys a gate, not a second opinion. Reliability has to be bought by changing the verifier's evidence and tools (deterministic entity resolution, different retrieval scope), not just its role label.

Angle

Take the outcomes/rubrics pattern at face value, then attack its weakest implicit assumption with injected-error experiments rather than opinion, and end with a concrete recipe for constructing a genuinely decorrelated check.

Source video ↗

Entities, Not Hallucinations, Are What Break Human-Facing Agents

For agents that pre-load human decision context, the dominant risk is misattribution of entities rather than generic hallucination, so the quality bar is per-entity correctness verified before delivery. A brief that pulls the wrong person's profile is not a weaker brief, it is an actively destructive one, and it demands a different verification step than plausibility checks.

Angle

Reframe agent evaluation for pre-meeting briefs around attribution accuracy as a first-class metric, with entity-resolution checks as the specific gate preceding delivery.

Source video ↗

Buy the Harness, Then Instrument the Crossover

Harness engineering is deferrable infrastructure, and the managed default is correct until cost and control constraints dominate. But the crossover point is a measurement, not an opinion: teams should adopt managed runtimes for time-to-value while simultaneously building per-task, per-account cost attribution so the exit decision is triggered by data.

Angle

Counterweight to premature platform building, paired with the instrumentation that must exist from day one to keep the managed decision revisitable.

Project ideas

4

Verifier Decorrelation Bench

beyond-evals

On injected entity-misattribution errors, a same-family verifier agent driven by an outcome rubric catches materially fewer errors than a heterogeneous verifier or a deterministic entity-resolution check, at comparable cost per verified task.

Proof of concept

Build a brief-generation pipeline with three verification configurations (same-family rubric verifier, cross-family verifier, deterministic entity-resolution check) and inject labeled misattribution and plausibility errors into a fixed brief set.

Measurement

Error catch rate and false-positive rate per configuration, plus inference cost and added latency per verified task; the hypothesis fails if same-family catch rate is within noise of the heterogeneous verifier at lower cost.

Source video ↗

Sandbox Capability Boundary Harness

gatehouse

A minimal sandbox policy (explicit repository read-scope plus a tool allowlist) reduces attempted out-of-scope tool calls and unauthorized file reads without reducing the rate of agent-proposed fixes that humans accept.

Proof of concept

Run a telemetry-to-codebase agent against the same set of application-state snapshots under a permissive and a restricted sandbox policy, logging every tool invocation and file path touched.

Measurement

Accepted-fix rate per policy, count of attempted out-of-scope tool calls and out-of-repository reads, and review time per accepted fix.

Source video ↗

Two-Tier Memory Conflict Injector

movement-lab

A two-tier memory store with an explicit scope-precedence rule yields higher multi-account answer accuracy than a single shared memory store once contradictory facts are injected between account-level and org-wide scopes.

Proof of concept

Stand up account-scoped and org-scoped memory behind a set of multi-account query tasks, inject conflicting facts (pricing, ownership, entitlements) at both scopes, and compare a precedence-rule store against a flat store.

Measurement

Downstream answer accuracy on conflict and no-conflict task subsets, plus the rate of silent cross-account contamination in roll-up answers.

Source video ↗

Per-Agent Cost Ledger and Routing Policy

new

Routing task classes by required intelligence and latency class, using a per-agent and per-account cost ledger, reduces total fleet inference spend without exceeding a defined quality-loss budget on interactive paths.

Proof of concept

Instrument tasks with a cost ledger keyed to agent, account, and task class, then shadow-route a subset of non-interactive tasks from frontier inference to lighter batch processing and compare outcomes against the rubric pass rate.

Measurement

Total and per-task cost by class, rubric pass rate before and after routing, interactive-path latency, and the request volume at which the routed configuration turns net positive.

Architectural implications

4

Verification is externalized from the generating agent into an independent verifier agent bound to a rubric.

Before

The agent assumes its own output is correct; quality control lives in prompts or post-hoc human review.

After

A second agent scores the output against explicit outcomes and triggers re-iteration until criteria are satisfied.

Consequence

Adds a per-task inference pass and a rubric artifact to maintain, but creates a machine-checkable gate before output reaches the user.

Source video ↗

Memory is split into per-account persistent state and organization-wide aggregation rather than one shared store.

Before

A single memory store serves all agents and accounts with no scope distinction.

After

Account agents carry perpetual local context; a separate aggregation layer produces cross-account views.

Consequence

Multi-tenant workflows become tractable without heavy upfront configuration, but scope-boundary and write-conflict rules become necessary.

Source video ↗

Agents bridge runtime application analytics and static source code inside a sandbox.

Before

Telemetry analysis and code maintenance are separate, human-mediated activities.

After

A sandboxed agent compares state snapshots to codebase versions and emits insights and fixes.

Consequence

Tool exposure and repository read scope become security-critical design parameters, not implementation details.

The harness itself becomes a buy-versus-build decision rather than a given.

Before

After

Managed runtimes absorb edge cases and shorten time-to-first-working-feature to days.

Consequence

Control and cost, not capability, become the reasons to eventually own the harness; the crossover point needs to be measured, not assumed.
