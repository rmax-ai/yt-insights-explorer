Summary

Overview

  • Speaker: Ash Prabaker and Andrew Wilson
  • Channel: AI Engineer
  • Main topic: Building and maintaining long-running AI agents using Claude models and custom agent harnesses
  • Purpose: To educate AI engineers on the architectural patterns, harnesses, and model evolutions required to successfully run coding and development agents autonomously for extended periods (5 to 30+ hours). Ash Prabaker and Andrew Wilson from Anthropic's Applied AI team discuss the evolution of Claude models and agent harnesses over a year, focusing on how to build agents that can run for hours without losing coherence, planning, or quality. They examine the three reasons agents lose the plot—context degradation, planning failures, and poor self-verification—and present practical fixes including model capability improvements, harness design patterns like the generator-evaluator loop (inspired by GANs), sprint contracts, and file system sharing.

Key Points

Self-evaluation is a trap

  • Explanation: LLMs cannot reliably evaluate their own work objectively due to sycophancy and bias toward finishing tasks.
  • Evidence: Out of the box, Claude identifies legitimate issues but talks itself into approving flawed work anyway.
  • Practical implication: Always separate the builder from the judge by using an independent adversarial evaluator agent.

Compaction doesn't cure coherence drift

  • Explanation: Summarizing or compacting long session contexts leads to loss of detail and drifting off task.
  • Evidence: Long-running sessions degrade in coherence as context windows fill up.
  • Practical implication: Use structured handoffs, fresh context windows per session, and filesystem artifacts for state persistence.

Make subjective quality gradable

  • Explanation: Quality metrics like design taste and originality can be evaluated deterministically if broken down into explicit rubrics.
  • Evidence: Using a 4-criteria rubric (design, originality, craft, functionality) paired with Playwright navigation successfully prevented purple-gradient slop.
  • Practical implication: Write detailed rubrics for your evaluator agent rather than relying on vague prompts.

Read the traces

  • Explanation: Debugging long-running agents requires analyzing step-by-step logs rather than guessing at prompt failures.
  • Evidence: The primary debugging loop is reading evaluator logs, finding where judgment diverged, and updating prompts.
  • Practical implication: Build tooling to inspect agent transcripts and trace execution history.

Harnesses are on a diet as models improve

  • Explanation: As base models become more capable and context-aware, complex scaffolding can be removed.
  • Evidence: Moving from Opus 4.5 to 4.6 dropped context resets between sessions, sprint decomposition, and per-sprint evaluator cadence in favor of continuous builds.
  • Practical implication: Continuously re-evaluate your harness architecture as newer, smarter models are released.

Frameworks, Models & Processes

Generator-Evaluator Loop

  • How it works: A generator model builds an artifact, and an independent evaluator model tests and grades it against explicit criteria, feeding actionable critique back into the loop.
  • Components:
    • Generator (builds the thing)
    • Evaluator (grades the thing using tools like Playwright and rubrics)
    • Feedback channel (critique and refinement)
  • When to use: When building multi-hour autonomous coding or creative agents where self-verification is critical.

Three-Agent Full Stack Architecture

  • How it works: Splits tasks across three distinct agents—Planner, Generator, and Evaluator—coordinating via local files on disk with zero shared context.
  • Components:
    • Planner (breaks 1-line prompt into spec and sprint milestones)
    • Generator (executes one sprint at a time)
    • Evaluator (tests against contract via Playwright and rubric)
    • Filesystem (shared state via spec.md, app/git, findings.md)
  • When to use: For building complex, full-stack software applications autonomously over several hours.

Examples & Case Studies

Building a retro game maker and a browser Digital Audio Workstation (DAW) using solo agents vs. full multi-agent harnesses.

  • Illustrates: Solo agents failed at play mode and sprite interaction after 20 minutes, whereas the 3-agent harness successfully built fully featured, tested apps over 6 hours.
  • Lesson: Complex multi-hour tasks require structured planning, sprint contracts, and adversarial evaluation.

Actionable Takeaways

  • Immediate:
    • Use separate adversarial evaluator agents instead of letting models grade their own work.
    • Rely on filesystem state (spec.md, progress.md) instead of infinite context windows for long tasks.
    • Break subjective quality into explicit rubrics for automated evaluation tools like Playwright.
  • Strategic:
    • Harness design co-evolves with base model capabilities; be ready to strip out scaffolding as models improve.
    • Granular contract criteria (e.g., 27 specific criteria per sprint) prevent vague agent outputs.
    • Treat prompt engineering for agents like writing rigorous software specifications.
  • Questions to investigate:
    • How to scale multi-agent team communication without excessive API costs?
    • What are the optimal compaction strategies for long-running sessions in non-coding domains?
    • How to train models natively to be self-critical without requiring heavy external harnesses?

Claims Worth Verifying

  • Tuning a standalone evaluator to be skeptical is tractable, but making a generator self-critical is not. (empirical observation)
  • Models exhibit context anxiety and rush to finish tasks as they approach the end of their context window. (behavioral observation)

  • Self-evaluation in LLM agents fails due to sycophancy; adversarial evaluators are required.
  • Context rot requires structured filesystem handoffs and fresh sessions rather than pure compaction.
  • A three-agent architecture (Planner, Generator, Evaluator) successfully powers multi-hour autonomous software development.
  • As base models improve with native context awareness and reasoning, harness scaffolding shrinks and simplifies.
  • Keywords: ai agents, harness design, evaluator loop, context management, anthropic claude

[A]Architecturehigh noveltystrong evidence

Separating the builder from the judge is an architectural requirement, not a prompting trick: an independent adversarial evaluator agent can be tuned to be skeptical and harsh, whereas a generator cannot reliably be made self-critical. Self-evaluation fails because the model identifies real issues and then talks itself into approving the work anyway.

Why it matters

It relocates verification responsibility out of the generation context into a separately tunable agent, which changes how you allocate context, prompts, and compute in any agentic build pipeline.

Generalization

Any system where an LLM both produces and grades its own output (code review, document drafting, data labeling) should split the roles, because the failure is in role collision rather than in model capability.

Architectural implications

4

Verification is moved out of the generating context into a dedicated adversarial evaluator agent with its own tooling and rubrics.

Before

A single agent generates output and self-reviews it in the same context window.

After

A separate evaluator agent navigates the artifact (e.g., Playwright), scores against an explicit rubric, and returns structured critique to the generator.

Consequence

Verification becomes independently tunable and auditable, but introduces additional inference cost and a new tuning burden (making the evaluator appropriately harsh).

Source video ↗

Coordination substrate shifts from the shared context window to concrete files on disk.

Before

Multiple roles share one accumulating context and implicit conversational state.

After

Planner, Generator, and Evaluator run with zero shared context and exchange specs, sprint contracts, and state via files.

Consequence

Context rot is avoided and every inter-agent agreement becomes a durable artifact, but the harness now needs file schemas, contract negotiation steps, and tooling to inspect the resulting state.

Source video ↗

Harness layers are treated as removable rather than permanent.

Before

Orchestration scaffolding accumulates over time to compensate for model weaknesses.

After

Scaffolding is deleted when a model upgrade absorbs the capability (e.g., context resets and sprint decomposition dropped between Opus 4.5 and 4.6).

Consequence

Harness architecture must be re-validated on every model upgrade, adding a recurring migration cost but preventing stale complexity from degrading performance.

Source video ↗

Task decomposition is delegated to a Planner agent instead of being fixed in the harness.

Before

The harness hard-codes sprint structure and planning steps in its control flow.

After

A Planner converts a one-line prompt into a high-level spec and sprint workflow that downstream agents follow.

Consequence

Planning becomes prompt- and model-mediated (and therefore improvable with model upgrades) rather than an invariant of the orchestration code.

Tradeoffs and failure modes

5

Self-evaluation

Benefit

Avoids the cost and complexity of a second agent and keeps the feedback loop fast.

Cost or risk

The generator acknowledges legitimate problems but approves flawed work anyway, shipping defects it already identified.

Context compaction for long sessions

Benefit

Keeps sessions within the context window and reduces token cost per step.

Cost or risk

Detail is lost and the agent drifts off task; coherence degrades as the window fills.

Harness scaffolding depth

Benefit

Compensates for model weaknesses and enables longer autonomous runs on earlier model generations.

Cost or risk

Becomes unnecessary overhead once models improve, requiring deliberate removal and re-validation on model upgrades.

Benefit
