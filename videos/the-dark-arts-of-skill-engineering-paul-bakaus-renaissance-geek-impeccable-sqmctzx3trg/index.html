Overview

  • Speaker: Paul Bakaus
  • Channel: AI Engineer
  • Main topic: Skill engineering and building advanced harness systems for LLMs
  • Purpose: To share practical knowledge, design patterns, and lessons learned on scaling AI agent skills beyond simple prompting into robust harness engineering. Paul Bakaus presents 'The Dark Arts of Skill Engineering', exploring lessons learned from building 'Impeccable', a large enterprise application and skill. He contrasts basic prompting with 'harness engineering', detailing nine dark arts techniques such as blind sub-agent critiques, divergence enforcement, model routing, memory, interactive loops, compiler harnesses, and designing for the weakest model.

Key Points

Prompting < Harness Engineering

  • Explanation: Simple prompts result in generic outputs (e.g., purple gradients, Inter font), whereas harness engineering structures constraints and agent behaviors.
  • Evidence: Analyzing the limitations of 55 lines of named bans in frontend-design prompts.
  • Practical implication: Engineers should wrap prompts in programmatic harnesses, linters, and multi-agent loops.

The Median is the Model's Gravity

  • Explanation: No amount of artisan prompt prose can overcome a model's latent space biases towards common choices.
  • Evidence: Tailwind's default theme defaults and historical web design trends.
  • Practical implication: You must use architectural mechanisms like anti-attractors to force divergence.

Blind Sub-Agents for Critique

  • Explanation: Asking an LLM to review its own work results in high self-ratings; spawning two blind sub-agents produces balanced critiques.
  • Evidence: Comparison of single-model code review vs. decoupled design director and deterministic detector sub-agents.
  • Practical implication: Implement adversarial sub-agent workflows for code review, design audits, and security checks.

Frameworks, Models & Processes

The Two Blind Sub-Agents Critique Pattern

  • How it works: Spawns two blind sub-agents (e.g. design director and deterministic detector) that evaluate work independently before the main thread synthesizes their findings.
  • Components:
    • Sub-agent A (Design Director: hierarchy, slop, heuristics)
    • Sub-agent B (Detector: browser evidence, deterministic)
    • Main thread synthesis
  • When to use: Code reviews, design reviews, security audits, and ranking outputs.

The Reactive Loop (Live Browser Integration)

  • How it works: A tiny server injects a picker into a dev page; dragging a knob sends server-side events back to the running agent thread.
  • Components:
    • Tiny server injecting picker
    • Node live-poll MJS
    • Server-side event listener
    • Agent auto-wake on exit
  • When to use: Visual tweaking, interactive debugging, and iterative refinement of UI elements.

Core insights

6
[M]Mechanismmedium noveltymoderate evidence

Self-critique by the same model/thread yields inflated ratings; the fix is architectural, not prompt-level: spawn two *blind* sub-agents with different evaluation roles (a heuristic 'design director' and a deterministic, browser-evidence 'detector'), then have the main thread synthesize their independent findings.

Why it matters

It relocates review responsibility out of the authoring thread into decoupled evaluator agents, which is directly reusable for code review, security audits, and output ranking — and explains why 'review your own work' loops underperform.

Generalization

Any agentic pipeline where a single model both produces and grades output can be improved by separating generation from evaluation across independent, information-isolated evaluators with heterogeneous criteria.

[O]Mental Modelhigh noveltymoderate evidence

Latent-space bias toward the 'median' output cannot be fixed with better prompt prose (even 55 lines of named bans fails); divergence must be induced mechanically, e.g. random anti-attractor seeds that push generation out of default clusters, followed by sub-agent ranking of many candidates.

Why it matters

It reframes a class of output-quality problems (generic designs, default palettes, repeated tailwind-style defaults) as a sampling/distribution problem rather than an instruction-following problem, which changes what you build.

Generalization

When a model's modal output is undesirable, generate a wider candidate distribution with randomized seeds/constraints and select post hoc, instead of trying to negate the mode in natural language.

Source video ↗
[A]Architecturemedium noveltymoderate evidence

Guardrails should be passive and mechanically enforced in the harness (write-gate hooks and linters that reject bad output before files hit disk) rather than expressed as instructions the model must remember to obey or commands users forget to run.

Why it matters

This is a boundary decision: constraints move from the probabilistic prompt layer to deterministic, non-compressible gates, improving reliability and eliminating a class of silent failures caused by context compression or model forgetfulness.

Generalization

Any rule that must hold with high probability should be enforced by a deterministic hook at the artifact boundary, not by prompt text that can be compressed away or ignored.

Source video ↗
[!]Failure Modemedium noveltyweak evidence

Sub-agent spawning is not a portable capability: models differ in permission models (e.g. Codex refused to spawn sub-agents when first prompted), so skills that depend on multi-agent workflows must explicitly instruct the model to stop and ask the user when it lacks the permission.

Why it matters

A skill built and validated against one harness can silently degrade on another; this forces explicit capability negotiation into skill design rather than assuming a uniform tool surface.

Generalization

Multi-agent or tool-dependent agent designs need runtime capability detection and a defined degradation path, because provider permission surfaces are heterogeneous.

Source video ↗
[M]Mechanismhigh noveltymoderate evidence

A reactive loop turns the running agent thread into a long-lived process woken by external UI events: a small server injects a control (a picker/knob) into the dev page, drags are sent as server-side events back to the agent thread, and the agent auto-wakes on exit.

Why it matters

It treats the human as an event source into a persistent agent session, enabling visual/interactive steering without restarting or re-prompting the agent — a concrete alternative to turn-based chat control.

Generalization

Agent runtimes can expose interruptible, resumable sessions bound to external event streams (UI, telemetry, CI), making the agent a reactive daemon rather than a request/response function.

Source video ↗
[P]Practicemedium noveltymoderate evidence

Divergence is produced by generate-many-then-rank: sample a large candidate set from a random seed (e.g. 100 shades) and use a sub-agent to rank them, rather than asking for a single best answer.

Why it matters

It is a cheap, testable recipe for escaping default choices that composes with the anti-attractor idea and with sub-agent evaluation, and it is directly measurable (diversity and preference metrics).

Generalization

For any generative task with a strong modal attractor, oversample with randomized conditioning and select with an evaluator model rather than trusting a single greedy generation.

Project ideas

3

Blind Critic Bench

beyond-evals

Blind multi-agent critique with two independent evaluator roles reduces self-evaluation bias compared to same-model self-review, as measured by increased correlation with human expert ratings.

Proof of concept

Build a pipeline that takes generated artifacts (e.g., UI designs), runs three conditions: self-review, single blind sub-agent, and two blind sub-agents with distinct criteria (heuristic vs evidence-based); collect ratings and compare against human expert scores.

Measurement

Bias (mean difference between model rating and human rating), rank correlation with human ratings, and cost/latency per condition.

Source video ↗

Anti-Attractor Sampler

movement-lab

Random anti-attractor seeds followed by sub-agent ranking produce a wider and more preferred distribution of outputs than prompt-level bans, without increasing cost per accepted artifact.

Proof of concept

For a design generation task, compare two conditions: (A) prompt with a 55-line ban list, (B) generate 100 candidates with random anti-attractor seeds and rank with a sub-agent; measure diversity and human preference.

Measurement

Diversity metrics (e.g., embedding entropy, unique color palettes, layout clusters) and win rate in pairwise human comparisons against baseline.

Source video ↗

Write-Gate Compliance Harness

gatehouse

Deterministic write-gate hooks achieve higher rule compliance (e.g., style, formatting) than prompt-based instructions across multiple sessions, especially when context compression occurs.

Proof of concept

Implement a linter that blocks file writes on violations in a coding agent, and compare with a prompt that instructs the model to avoid those violations; run 50 coding sessions each and count violations.

Measurement

Compliance rate (violations per 100 writes), false positive rate, and developer override frequency.

Architectural implications

3

Evaluation is split out of the producing agent into independent blind sub-agents with distinct, non-overlapping evaluation criteria.

Before

The generating agent also reviews and reports on its own output.

After

Generation, heuristic critique, and deterministic evidence collection are separate roles, with the main thread only synthesizing.

Consequence

Review quality becomes an orchestration concern; you can swap, add, or version evaluators independently, but you inherit multi-agent latency and permission dependencies.

Source video ↗

Constraint enforcement is moved below the prompt layer into deterministic hooks at the artifact boundary.

Before

Rules live as long prose ban-lists inside the prompt.

After

Linters and write-gates validate and block output before it is persisted.

Consequence

Rules become non-compressible and consistently applied, but every new rule adds harness code to maintain and can conflict with model autonomy.

Source video ↗

Skills are authored as portable artifacts compiled to multiple harnesses and validated against the weakest model in the fleet.

Before

A skill is tuned and assumed to work against the strongest available model/harness.

After

Capability differences (e.g. sub-agent permissions) are designed for up front, with explicit stop-and-ask paths.

Consequence

Skill engineering becomes a compatibility/matrix problem, trading peak capability on strong models for uniform behavior across a heterogeneous fleet.

Tradeoffs and failure modes

5

Multi-agent critique loops

Benefit

Blind, role-separated sub-agents yield balanced critiques instead of inflated self-review scores.

Cost or risk

Added latency, cost, and orchestration complexity; benefit magnitude and cost profile are not quantified in the summary.

Divergence via seeded oversampling

Benefit

Escapes the model's latent-space median rather than replicating default choices.

Cost or risk

Generating and ranking large candidate sets (e.g. 100 options) multiplies generation and evaluation cost per artifact.

Sub-agent permission heterogeneity

Benefit

Adversarial/multi-agent workflows improve output quality where sub-agents are permitted.

Cost or risk

Skills silently fail or behave differently on harnesses whose permission models disallow spawning sub-agents.

Passive guardrails over explicit commands

Benefit

Rules apply automatically and cannot be forgotten or compressed away.

Cost or risk

Deterministic gates reduce agent flexibility and require harness-level maintenance; stricter hooks may reject legitimate novel output.
