Summary

Overview

  • Speaker: Nina Žižakić & Eleonora Drykina
  • Channel: AI Engineer
  • Main topic: Unremarkable RAG in Production for Financial Rulebooks
  • Purpose: Explain technical decisions, architecture, and production lessons in building a RAG system for a financial institution dealing with 270 rulebooks, 6,000 PDF pages, and 3,000 tables. Nina Žižakić and Eleonora Drykina share real-world production insights on building a Retrieval-Augmented Generation (RAG) system for a major Belgian financial institution's payment rulebooks. They walk through technical decisions including indexing, table processing as CSV, hybrid dense and BM25 search with reciprocal rank fusion, agentic retrieval with multiple tools, streaming responses with Pydantic object handling, and evaluation strategies.

Core insights

6
[M]Mechanismmedium noveltymoderate evidence

Treating tables as a first-class, separately-parsed artifact (rows serialized as CSV text) rather than letting a generic page-level chunker ingest them prevents cross-row field misalignment in retrieved fee/rate data.

Why it matters

Generic character-window chunking silently corrupts tabular semantics: a fee type spanning multiple rows gets mapped to the wrong columns, producing plausible but wrong answers that are hard to catch downstream. A dedicated table pipeline is an architectural boundary, not a preprocessing nicety.

Generalization

Any RAG over documents with dense structured regions (financial tables, spec matrices, compliance schedules) needs region-type-specific extraction paths and a rule that a structured region is never split across chunks.

[E]Empirical Resultlow noveltymoderate evidence

Hybrid dense + BM25 retrieval combined via reciprocal rank fusion raised hit rate from 92% to 97% over dense-only in a corpus dominated by exact codes, identifiers and message names.

Why it matters

It quantifies a concrete 5-point gap and attributes it to a specific failure mode of dense retrieval — exact token lookups (device type codes, message names). That makes the hybrid decision an evidence-backed default rather than a preference.

Generalization

For domains with symbolic vocabularies (codes, IDs, SKUs, error strings, legal citations), dense-only retrieval has a measurably irreducible miss rate; sparse+fusion should be the baseline and dense-only must be justified.

Source video ↗
[A]Architecturemedium noveltymoderate evidence

Retrieval is exposed to the model as four distinct tools with different cost/granularity (search chunks, fetch sections, fetch a full rulebook, enumerate available rulebooks), and the agent is expected to sequence them (search first, then escalate to section retrieval).

Why it matters

This reframes retrieval granularity as a runtime decision rather than an index-time constant. The agent can escalate context size only when the cheaper search is insufficient, which is how cross-reference-heavy corpora (~2,000 cross-references) get resolved without stuffing everything into the prompt.

Generalization

Expose your retrieval index at multiple zoom levels as separate tools with explicit escalation policy; let the agent pay for more context only on demand. This is a zoomable-retrieval abstraction that generalizes to code search, legal, and internal docs.

Source video ↗
[~]Tradeoffmedium noveltymoderate evidence

Streaming structured output is impossible at the object level: a Pydantic response object cannot be partially streamed, so the answer is decomposed into token-streamed markdown text plus source cards attached at the end.

Why it matters

It is a concrete constraint of typed/schema-validated outputs versus perceived latency, and it dictates a UI contract: the schema-bearing part (citations, provenance) arrives after the natural-language part. Ignoring this produces either unvalidated JSON streaming or a long dead-air wait.

Generalization

When output schemas must be validated, split the response into a streamable unstructured channel and a terminal structured channel; design the client to render partial text and reconcile structured attachments on completion.

Source video ↗
[P]Practicelow noveltymoderate evidence

Chunk metadata is enriched with structural path information — document name, page numbers, section hierarchy — plus LLM-generated per-chunk summaries, so citations and section-aware retrieval are derived from indexing-time structure rather than reconstructed at query time.

Why it matters

Section hierarchy as metadata is what makes the 'retrieve sections' tool and grounded citations possible; the LLM-generated summary field adds a retrieval surface that isn't a verbatim substring of the page.

Generalization

Index both the raw content and a machine-generated synopsis per chunk, and carry the document's structural path as filterable metadata — this is what enables zoom-level retrieval and verifiable citation.

[E]Empirical Resultmedium noveltymoderate evidence

Published latency for this agentic retrieval loop is a median of ~38 seconds per answer, which the speakers explicitly reframe as a research task rather than a chat reply.

Why it matters

Multi-step tool-using retrieval has a latency profile an order of magnitude worse than single-shot RAG; that number should drive product framing, streaming strategy and UX expectations, and it makes latency a first-class optimization target.

Generalization

Agentic retrieval latency scales roughly with number of tool turns; plan for tens of seconds and design progressive disclosure (streamed reasoning/text) instead of pretending it's a chat completion.

Deep dives

Latency decomposition of agentic multi-step retrieval

Research question

Where does the 38-second median answer time actually go — planner/model turns, number of tool calls, vector-DB query time, or context-size-driven generation cost — and what fraction is recoverable without losing answer quality?

Why

If most of the 38s is per-turn model latency multiplied by tool turns, the optimization lever is escalation policy, not the vector DB. Without a per-stage breakdown, teams will optimize the wrong component and mis-set UX expectations for research-style answers.

Source video ↗

Escalation policy and tool-call budgets for zoomable retrieval

Research question

Does a hard tool-call budget or cost-weighted tool selection beat prompt-level 'tool discipline' instructions on quality-per-second when an agent has search-chunks, fetch-section, fetch-full-document and list-corpus tools available?

Why

'Tool discipline' is asserted as the thing that makes agentic retrieval beat single-shot RAG, but no policy mechanism is described. Escalation to full-rulebook retrieval is the most expensive and least precise action, so making that decision a guarded runtime policy rather than a prompt hope is the difference between a 38s research task and an unbounded one.

Source video ↗

Retrieval hit rate versus end-to-end grounded-answer accuracy

Research question

Does the 92%→97% reciprocal-rank-fusion hit-rate gain survive translation into final answer correctness and citation accuracy, or does the ~5-point retrieval gain collapse at the answer level?

Why

A retrieval metric that does not predict answer quality will cause teams to ship hybrid search and then misattribute remaining errors to the model. The reporting gap is the cheapest place to catch this: pair the retrieval numbers with end-to-end grounded-answer accuracy on the same query set.

Source video ↗

Ablating chunk-enrichment mechanisms (CSV tables vs section path vs LLM summaries)

Research question

Which enrichment actually buys retrieval and answer accuracy: whole-table CSV serialization, section-hierarchy metadata, LLM-generated per-chunk summaries, or the section-aware chunk boundary itself?

Why

All four are bundled as one 'good ingestion' story, so a team adopting the approach cannot tell which expensive step to keep. LLM-generated summaries in particular add a full generation pass over every chunk; if the gain is concentrated in table handling and section paths, the summary pass is pure cost.

Source video ↗

Streaming contracts for schema-validated agent output

Research question

Can incremental/partial JSON parsing with progressive schema validation restore perceived responsiveness for typed responses, or is the two-channel split (streamed prose, terminal structured payload) forced?

Why

The claim treats non-streamable Pydantic objects as a hard constraint, which turns into a permanent product experience: users read prose with no provenance until the very end. If partial validation works, the citation UI can render progressively and the two-channel contract becomes an implementation choice rather than an architecture.

Article ideas

4

Your Chunker Is Lying About Your Tables

In document RAG, table handling is an architectural boundary rather than a preprocessing detail: any pipeline that lets a character-window chunker touch a structured region produces fluent, well-cited, wrong numeric answers, so the retrieval index must carry region-type-specific extraction paths with a hard rule that a table is never split.

Angle

Show the concrete failure mode — a fee type spanning multiple rows getting mapped to the wrong columns — then argue that the fix is pipeline topology (dual ingestion paths, CSV row serialization) and that no amount of retrieval tuning recovers from corrupted chunk content.

Source video ↗

Retrieval Hit Rate Is Not an Answer Metric

Hybrid dense+BM25 fusion with reciprocal rank fusion gets cited as a 92%→97% win, but retrieval hit rate is a proxy that can move independently of end-to-end grounded-answer correctness and citation accuracy; hybrid search should be adopted as the baseline by default for symbolic corpora, and the remaining gap should be measured at the answer level before anyone claims a quality improvement.

Angle

Push back on the universally-quoted 5-point number: argue for paired reporting (retrieval hit rate alongside answer accuracy on the same query set) and show why domains full of codes, identifiers and message names make dense-only retrieval structurally unfixable.

Source video ↗

38 Seconds Is a Design Decision, Not a Bug

Multi-step agentic retrieval turns a chat completion into a small research task, and the honest response is to redesign the product contract around that latency — streaming the reasoning and prose, attaching provenance at completion — instead of pretending the system is a chat reply and hiding dead air behind a spinner.

Angle

Treat latency as a first-class product surface: frame the 38s median as a signal that agentic retrieval's cost scales with tool turns, and argue that progressive disclosure and a text-then-source-cards UI contract are the only defensible UX once you accept multi-turn retrieval.

Source video ↗

Stop Building One retrieve(query, k) Endpoint

Exposing retrieval at multiple zoom levels — chunk search, section fetch, full-document fetch, corpus enumeration — as separate tools moves retrieval granularity from an index-time constant to a runtime decision, which is the only way cross-reference-heavy corpora get resolved without stuffing everything into the prompt; the cost is that retrieval policy leaves your code and enters a nondeterministic agent loop, so escalation must be budgeted.

Angle

Reframe retrieval design as an API-surface question: four tools with different cost and granularity plus an explicit escalation policy, then confront the discipline problem the talk leaves open.

Source video ↗

Project ideas

4

Escalation Budget Harness

gatehouse

A hard tool-call budget with cost-weighted tool selection (chunks < sections < full document) matches or beats prompt-instructed 'tool discipline' on grounded-answer accuracy while reducing median latency by at least 30%.

Proof of concept

Wrap four retrieval tools behind an enforcement layer that counts turns, applies per-tool cost weights and blocks full-document escalation until section retrieval returns below a relevance threshold; run the same query set with three configurations: prompt-only discipline, hard budget, and cost-weighted selection.

Measurement

p50/p90 latency, tool-calls-per-query distribution, escalation rate to full-rulebook retrieval, grounded-answer accuracy and citation accuracy against a fixed labelled query set.

Source video ↗

Retrieval-to-Answer Fidelity Evaluator

beyond-evals

Reciprocal rank fusion's 92%→97% retrieval hit-rate gain translates into a smaller-than-5-point end-to-end answer accuracy gain, and the residual errors are dominated by table-dependent queries rather than by retrieval misses.

Proof of concept

Build a paired evaluation harness that scores dense-only, BM25-only and RRF-fused retrieval on identical queries, then scores grounded-answer correctness and citation accuracy on the same retrieved contexts, slicing results by whether the answer requires a table lookup.

Measurement

Delta in retrieval hit rate versus delta in answer accuracy and citation accuracy for dense-only vs hybrid, reported per query slice, with confidence intervals over the query set.

Source video ↗

Table-Invariant Ingestion Benchmark

movement-lab

Naive page-level character-window chunking measurably degrades accuracy on table-dependent queries, and whole-table CSV serialization with a no-split guarantee restores a double-digit accuracy margin — while LLM-generated per-chunk summaries add little beyond section-path metadata.

Proof of concept

Take a small set of rulebook PDFs with multi-row fee tables, ingest them through four pipelines (naive chunking, section-aware chunking, section-aware + CSV tables, section-aware + CSV tables + per-chunk LLM summaries), and query them with an evaluation set targeted at cross-row field mappings.

Measurement

Answer accuracy on table-dependent versus prose-only questions per pipeline, cross-row field-mapping error rate, indexing cost per pipeline, and the marginal accuracy contribution of each enrichment field.

Source video ↗

Two-Channel Streaming Contract

new

A client that renders streamed prose immediately and reconciles validated source cards on completion reduces perceived latency substantially versus waiting for a validated response object, without any loss of citation integrity.

Proof of concept

Implement an event-sequence response contract (markdown delta events, then a terminal Pydantic payload with source cards) behind FastAPI, and a reference client that renders deltas and attaches citations on completion; include a partial-JSON experimental variant that attempts progressive schema validation for comparison.

Measurement

Time-to-first-token, time-to-first-citation, time-to-complete-answer, perceived-latency proxy from user interaction timing, and rate of invalid or misattributed source cards across the two variants.

Architectural implications

3

Retrieval granularity is exposed as multiple callable tools rather than one top-k endpoint.

Before

A single retrieve(query, k) function feeding a fixed context window.

After

Four tools spanning chunks, sections, full documents and corpus enumeration, with the agent choosing escalation.

Consequence

Retrieval policy moves from code into the agent loop, increasing latency and nondeterminism but enabling multi-hop resolution of cross-references.

Source video ↗

Structured and unstructured outputs travel on different channels.

Before

App expects a single JSON/Pydantic response rendered on completion.

After

UI renders streamed markdown incrementally and appends validated source cards when the object finalizes.

Consequence

Client must handle an intermediate state with prose but no citations; the schema contract becomes an event sequence, not a single payload.

Source video ↗

Table and text ingestion are separate pipelines in the offline index.

Before

One chunker over extracted PDF text.

After

Regex/section-aware text chunks (≤2,000 chars) plus a dedicated CSV-serialized table path, both embedded densely and BM25.

Consequence

Indexing complexity rises but retrieval correctness for numeric/relational content stops depending on chunk boundary luck.

Tradeoffs and failure modes

4

Agentic multi-step retrieval vs latency

Benefit

Higher answer quality on questions requiring multi-step reasoning across rulebook cross-references, with explicit citations.

Cost or risk

Median 38 seconds per answer; agents may over-call tools or escalate to full-rulebook retrieval unnecessarily.

Source video ↗

Typed structured output vs streaming UX

Benefit

Validated Pydantic objects guarantee well-formed citations and provenance metadata.

Cost or risk

No partial object streaming; users wait with no structured feedback unless prose is streamed separately.

Source video ↗

Chunk size and table integrity

Benefit

2,000-character section-aware chunks keep retrieval units coherent and section-aligned.

Cost or risk

Tables must be excluded from that split logic, or multi-row fee mappings get corrupted; two divergent chunking regimes must be maintained and evaluated.

LLM-judge based evaluation

Benefit

Enables scalable automated scoring of grounded answers against rulebook content.

Cost or risk

Judge rubric calibration introduces evaluation noise that can mask real regressions.
