Summary

Overview

  • Speaker: Ryan Cooke
  • Channel: AI Engineer
  • Main topic: Building autonomous AI software engineering factories and moving beyond basic output metrics
  • Purpose: To critique the industry-standard 'software factory' model based purely on code output and present WorkOS's approach to encoding product engineering culture and institutional knowledge into autonomous agent systems. Ryan Cooke from WorkOS argues that typical AI software factories focusing solely on sandbox, model, and repo setups with output metrics like PR counts and lines of code fail to deliver true organizational leverage. Instead, engineering teams must encode their actual culture, product engineering processes (such as Hilltop documents, dependency chains, and review loops), and institutional knowledge into executable agent workflows using Model Context Protocol (MCP) gateways and contextual engines.

Topic Map

The Standard Playbook vs. Output vs. Outcomes

  • Explanation: Examining industry standards where companies set up sandboxes, models, repos, and PR generation, and why measuring output metrics (PRs/week, lines of code, PR velocity) obscures true value compared to outcome metrics.
  • Key claims:
    • Most industry benchmarks focus on output metrics like lines of code or PR count.
    • Output metrics can disguise whether AI systems are actually driving business outcomes.
    • More code and faster generation is not the same as more value and faster delivery.
  • Examples:
    • Ramp (>50% merged PRs from AI)
    • Spotify (1,500+ AI-generated PRs merged)
    • Stripe (1K+ merged PRs per week)
  • Terminology:
    • output metrics
    • outcome metrics
    • sandbox
    • model router
    • pull request
  • Why it matters: Optimizing for output metrics leads organizations to measure the wrong variable while failing to accelerate feature delivery time or engineer leverage.

What WorkOS Built: TARS and Horizon

  • Explanation: Introducing TARS (the product interface interacting via Slack, Linear, GitHub, and web UI) and Horizon (infrastructure orchestration running warm-pooled sandboxes and event loops).
  • Key claims:
    • Infrastructure is only half the story; agents must participate in the actual engineering process.
    • TARS handles user interactions, operational instructions, and open PRs.
    • Horizon orchestrates webhooks, sandboxes, and event loops between Linear and repo.
  • Examples:
    • TARS integration with Slack, Linear, and GitHub
    • Horizon cloudflare workers and warm-pooled sandboxes
  • Terminology:

  • Why it matters: Demonstrates how combining product engineering processes with robust infrastructure enables agents to handle end-to-end tasks autonomously.

The Blueprint and The PM Agent

  • Explanation: Encoding WorkOS's product engineering culture—featuring Hilltop documents, small teams, dependency chains, and review-first loops—into the PM agent lifecycle.
  • Key claims:
    • Hilltop documents capture narrative specifications before writing code.

    • Autonomous agents can execute work through every stage of the lifecycle without constant human shepherding.

Key Points

Measure outcomes, not just output

  • Explanation: Focusing on lines of code or PR counts obscures whether software factories are improving feature delivery time, defect rate, or engineer leverage.
  • Evidence: Industry metrics from Ramp, Spotify, and Stripe show high production rates, but production rate does not equal value delivered.
  • Practical implication: Engineering leaders should invest in systems that accelerate actual feature delivery and system compounding over time.

Infrastructure plus engineering culture

  • Explanation: Sandboxes, models, and repos are necessary but incomplete conditions for a software factory.
  • Evidence: Building on Cloudflare and open-source models without cultural process integration resulted in indistinguishable developer output.
  • Practical implication: Teams must encode their specific planning rituals, such as Hilltop docs and review loops, into agent workflows.

The Context Engine as cultural encoding

  • Explanation: An internal MCP gateway provides tool descriptions, guidelines, and semantic database queries that orient coding agents.
  • Evidence: Connecting Snowflake semantic tables and Slack query capabilities allowed agents and developers to query customer data directly.
  • Practical implication: Investing in an internal MCP gateway yields incredible leverage across multiple internal tools and developer workflows.

Actionable Takeaways

  • Immediate:
    • Audit your software factory metrics to ensure you are measuring outcome over output.
    • Build or adopt an internal MCP gateway to provide standardized tool shapes and context to coding agents.
  • Strategic:
    • Encode institutional knowledge and planning processes (like PRDs and review loops) into executable agent workflows.
    • Move from rented sandbox infrastructure to owning your session and memory infrastructure layers.
  • Questions to investigate:
    • How do you handle authorization and security governance when autonomous agents have broad system access?
    • How do you prevent agents from overestimating project scope and generating excessive unnecessary code?

Architectural implications

3

Memory and context ownership is being moved out of individual agent harnesses into a shared, identity-keyed context service.

Before

Memory and context live inside each agent harness or tool integration, scoped to that runtime.

After

Memory is served by an internal MCP gateway/context engine and scoped per-user, per-team, and company-wide.

Consequence

Agents become interchangeable consumers of context; the durable asset is the context service, and agent harnesses become more commoditized.

Source video ↗

Project initialization is delegated to an agent that operates on a narrative specification artifact before any code is written.

Before

A human turns a brief into a spec, issues, tickets, and dependency chains.

After

The PM agent generates Linear projects, Hilltop document drafts, decision logs, open questions, and tickets from a brief Slack description.

Consequence

The spec document becomes an executable input rather than a human-only artifact, making spec quality the gating factor for downstream agent work.

Source video ↗

Runtime orchestration (warm-pooled sandboxes, webhook handling, event loops) is separated from the product-facing agent surface.

Before

A single agent service handles both user interaction and execution infrastructure.

After

A product interface (TARS) and a separate orchestration layer (Horizon) with pooled sandboxes and event loops.

Consequence

Sandbox lifecycle, concurrency, and cost can be tuned as infrastructure concerns without touching the interaction surface, but introduces a coordination boundary between the two planes.

Tradeoffs and failure modes

4

Output-metric optimization

Benefit

Easy to instrument and benchmark across organizations (PR counts, lines of code, PR velocity).

Cost or risk

Optimizing production volume can obscure whether feature delivery time, defect rate, or engineer leverage improved at all.

Source video ↗

Review-first loop as autonomy boundary

Benefit

Human review milestones keep the agent aligned with organizational standards and preserve accountability.

Cost or risk

Human review gates reinsert a human latency and attention dependency into a pipeline otherwise marketed as autonomous, limiting end-to-end autonomy.

Source video ↗

Custom internal MCP gateway investment

Benefit

Standardized tool shapes and contextual querying yield leverage across multiple internal tools and developer workflows.

Cost or risk

A bespoke gateway couples every agent to one organization's internal semantics and requires ongoing maintenance of tool descriptions and semantic tables.

Source video ↗

Warm-pooled sandboxes

Benefit

Pre-provisioned sandboxes reduce the latency of starting agent work on repository tasks.

Cost or risk

Maintaining a warm pool implies idle compute cost and management of a pool lifecycle alongside the event-driven orchestration.
