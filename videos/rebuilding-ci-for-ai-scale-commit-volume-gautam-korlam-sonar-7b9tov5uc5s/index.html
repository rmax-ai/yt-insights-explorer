Summary

Overview

  • Speaker: Gautam Korlam
  • Channel: AI Engineer
  • Main topic: Rebuilding CI infrastructure and software factories to handle AI-scale commit volume and autonomous coding agents
  • Purpose: To explain the bottlenecks introduced by AI coding agents in monorepos and software factories, and to propose architectural and policy solutions to make CI and code review scale effectively. Gautam Korlam, co-founder and CTO of Gitar (part of Sonar) and former Uber engineer, discusses the challenges of adapting continuous integration (CI) and merge infrastructure for AI-scale commit volumes. Autonomous coding agents generate significantly more pull requests (PRs) than humans, leading to severe bottlenecks in traditional CI and review pipelines built for human speed. To keep software factories fast and compliant, engineering teams must make CI faster, move checks left, automate review processes, and enforce governance via plain-English policy rules rather than manual approvals.

Core insights

6
[!]Failure Modemedium noveltymoderate evidence

Per-PR green CI is not evidence of trunk safety. When two branches (e.g., an engineer and an agent) each modify the same function independently, both pass CI in isolation and the build breaks only at merge — so the merge queue, not the PR check, is where real correctness is enforced. The implied fix is for the queue to test likely futures speculatively/in parallel rather than serially replaying each PR against trunk head.

Why it matters

It relocates the correctness boundary: teams that scale agent PR volume while trusting per-PR CI will see trunk instability grow superlinearly with concurrency, and the symptom (build broken on main) appears far from the cause (independent valid changes).

Generalization

Any system where agents mutate shared state in parallel and validate only against a snapshot will pass local validation and fail on composition; validation must be performed against projected post-merge state, not current state.

[A]Architecturehigh noveltymoderate evidence

Audit compliance cannot be derived from CI state because CI state is ephemeral. Pipeline status is a mutable, expiring artifact; a durable per-merge record (test reports, reviewer identity, policy override reasons) must be written to a store with a different lifecycle than the CI system.

Why it matters

It forces an explicit architectural boundary: audit ledger is a first-class durable subsystem, not a view over CI logs. Without it, compliance claims about historical merges become unverifiable once logs age out or tests are re-run against changed code.

Generalization

Agent-generated changes need append-only provenance records decoupled from the execution system that produced them, because execution artifacts are retention-bounded while accountability is not.

[O]Mental Modelmedium noveltymoderate evidence

Bottlenecks migrate rather than disappear. Speeding up build and test does not increase throughput if review is the slowest station; the observed consequence of fast CI plus high PR volume is review queue saturation and rubber-stamping, i.e., approval becomes a throughput artifact rather than a judgment.

Why it matters

It reframes optimization as whole-pipeline station balancing: any investment that improves only one stage can increase risk by pushing more volume into an under-provisioned human gate.

Generalization

Throughput of an agent pipeline equals its slowest station; optimizing upstream stages without matching downstream capacity converts a latency problem into a quality/oversight problem.

[P]Practicemedium noveltymoderate evidence

Governance for routine agent changes should be encoded as written policy that auto-approves and emits an audit record, rather than as discretionary human approval. The human gate is replaced by an executable rule plus evidence, reserving human attention for exceptions.

Why it matters

It makes approval scalable and reviewable: a rule can be inspected, versioned, and audited, whereas a rubber-stamped human approval carries neither consistency nor a defensible rationale.

Generalization

As change volume exceeds human review bandwidth, approval authority must be delegated to versioned, inspectable policy that produces machine-checkable evidence for each decision.

Source video ↗
[A]Architecturemedium noveltyweak evidence

Agents require a distinct identity and permission boundary from the humans who own the change: an agent must not be able to approve its own work. This is separation of duties applied to autonomous actors, and it implies the code-review agent and the code-authoring agent cannot be the same trust principal.

Why it matters

Without author/reviewer principal separation, an agentic review layer provides no assurance — it can be trivially satisfied by the same system that produced the defect, and the audit record would show a meaningless approval.

Generalization

Autonomous systems need enforced non-self-approval and role separation at the identity layer, not as a prompt convention, or automated review collapses into self-attestation.

Source video ↗
[P]Practicelow noveltymoderate evidence

CI latency is an economic variable, not just a UX one: the cost of a failed run is a "repair lap" whose total cost scales with pipeline duration multiplied by agent concurrency. Build output caching and compilation sharding reduce that multiplier.

Why it matters

It gives a concrete lever and a way to price CI investment: with agents generating parallel work, the same build-time reduction saves proportionally more engineer/agent time than under human-paced workloads.

Generalization

When the number of concurrent automated producers rises, per-run latency becomes a multiplicative cost term, shifting optimization priority from average latency to incremental/reuse-based build strategies.

Cost-bounded speculative merge queues

Research question

Under a synthetic stream of concurrent agent-authored PRs, what scheduling policy for speculative post-merge futures (fan-out width, batched rebase, invalidation-on-trunk-move) minimizes trunk-break rate per 100 merges subject to a fixed test-minute budget?

Why

Serial rebase-and-test against trunk head is the mechanism that makes per-PR green CI non-predictive of trunk safety; if speculation cost cannot be bounded, high-concurrency agent PR streams either break trunk or exhaust CI compute. This is the single architectural decision that determines whether agent volume is absorbable.

Minimum durable per-merge evidence manifest

Research question

What is the smallest per-merge record schema (commit identity, test report digests, approver principal, governing policy version, override reasons) that lets an auditor reconstruct test outcome, approver identity, and override rationale after all CI logs have expired?

Why

If audit is read off pipeline status and logs, every compliance claim degrades silently as retention windows roll over — and merge throughput improvements make this worse by producing more history faster. The schema is the contract that makes the whole governance model defensible.

Enforcing non-self-approval at the principal layer

Research question

Can a capability model in which authoring and reviewing agents hold disjoint, change-scoped tokens reject 100% of self-approval attempts deterministically, without serializing the author→review→merge workflow beyond a fixed latency budget?

Why

Automated first-pass review only produces assurance if the reviewer cannot be the author. If separation lives in prompt convention rather than identity enforcement, the audit record shows an approval that means nothing — a worse failure than no review, because it looks compliant.

Flake rate as a function of agent-driven parallelism

Research question

Does test flake rate grow with parallel execution width and simultaneous agent-triggered workflows, and does a quarantine policy outperform an override-with-durable-record policy on both trunk-break rate and audit reconstructability?

Why

Overrides and genuine passes are indistinguishable in pipeline status, so under agent-scale concurrency flaky tests become either a throughput tax or an audit blind spot. The choice between quarantine and recorded override is a concrete policy decision teams must make now.

Station balancing: where the bottleneck migrates

Research question

Why

Optimizing only the build stage increases risk by pushing more volume into an under-provisioned human gate; knowing the saturation point is a prerequisite for deciding when to replace human approval with policy rather than adding reviewers.

Article ideas

4

Your Green CI Is Evidence About a Branch, Not About Trunk

Per-PR CI validates a change against a snapshot that will never exist again; at agent concurrency, correctness must be enforced at composition time by a queue that tests projected post-merge states, or trunk stability degrades faster than PR volume grows.

Angle

Take the concrete two-agents-modifying-the-same-function case, walk through why both PRs are legitimately green, then argue that the merge queue — not the PR check — is the real correctness boundary and should be designed as a speculative-execution system with invalidation semantics.

Source video ↗

CI Logs Are a Cache, Not a Ledger

Pipeline status is mutable, retention-bounded execution state; compliance obligations are not retention-bounded, so any audit answered from CI logs is a claim with an expiry date, and the merge path must write durable per-merge records as a mandatory step rather than a best-effort side effect.

Angle

Argue the architectural boundary explicitly: audit ledger as a first-class append-only subsystem with its own lifecycle, evidence manifest per merge, and the new failure mode introduced when record-writing is allowed to fail silently.

Source video ↗

Making CI Fast Is How You Get Rubber-Stamped Reviews

Throughput equals the slowest station, so shaving build time without provisioning the review gate converts a latency problem into an oversight problem: volume accumulates at the human gate and approval degrades from judgment into a queue-clearing ritual.

Angle

Frame optimization as whole-pipeline station balancing, then prescribe the only scalable answer for routine changes — versioned written policy that auto-approves defined change classes and emits an audit record, reserving human attention for exceptions.

Source video ↗

An Agent That Reviews Its Own Work Has Reviewed Nothing

Automated first-pass review only produces assurance when the reviewer is a different trust principal from the author; separation of duties must be enforced at the identity layer with disjoint capabilities, because a prompt convention produces audit records that certify nothing.

Angle

Contrast a rubber-stamped approval, a same-agent self-approval, and an enforced author/reviewer principal split, showing what the audit record can and cannot prove in each case.

Project ideas

4

Futures Queue

new

For a fixed test-minute budget, testing K projected post-merge futures in parallel reduces trunk breaks per 100 merges by a materially larger margin than serial rebase-and-test, and the break-rate reduction survives invalidation churn from trunk moving underneath speculative runs.

Proof of concept

Replay a recorded or synthetic high-concurrency PR stream (with deliberately intersecting edits to shared functions) through three queue strategies: serial rebase, batched/official batching, and speculative fan-out with cancellation-on-invalidation. Instrument trunk-break events and total test-minutes per strategy.

Measurement

Trunk breaks per 100 merges, p95 queue latency per PR, total test-minutes consumed, and the fraction of speculative runs invalidated before completion — reported as a Pareto curve of break-rate versus test-minutes across K.

Source video ↗

Merge Ledger

gatehouse

A minimal per-merge evidence manifest (commit SHA, test-report digests, approver principal ID, policy version, override reason) is sufficient for an auditor to reconstruct test outcome, approver identity, and override rationale after all CI logs are deleted, with no loss of answerable compliance questions relative to the pre-deletion state.

Proof of concept

Build a merge-path hook that writes an append-only manifest per merge into a store with an independent, longer retention policy; simulate log expiry by deleting the CI backend, then run a fixed questionnaire of compliance queries against the surviving manifest only.

Measurement

Percentage of compliance questions answerable post-expiry from manifests alone, versus the CI-log baseline; rate of merges where manifest write fails and the merge still proceeds.

Source video ↗

Two-Key

gatehouse

A capability model with disjoint, change-scoped author and reviewer tokens rejects 100% of self-approval attempts deterministically, while adding a bounded latency overhead versus an unpoliced author→review→merge flow.

Proof of concept

Implement a policy engine issuing author and review capabilities scoped to a single change, route automated review through a distinct principal, and run an adversarial suite of self-approval attempts (same agent, delegated token, replayed token, impersonation) plus a benign workflow benchmark.

Measurement

Block rate on adversarial self-approval attempts (target 100%), false-positive rate on legitimate cross-principal approvals, and median added end-to-end latency per change.

Flake Under Load

beyond-evals

Test flake rate increases measurably as parallel execution width and simultaneous agent-triggered workflows increase, and a quarantine policy reduces trunk breaks relative to override-with-record at the cost of lower short-term merge throughput.

Proof of concept

Run an identical suite matrix at increasing concurrency levels under simulated agent load; split failures into deterministic and nondeterministic classes; compare quarantine-first versus recorded-override policy on the same failure stream.

Measurement

Flake rate as a function of execution width, trunk-break rate per policy, merges per hour per policy, and audit reconstructability score for each override event.

Architectural implications

4

Compliance and audit are currently read off CI pipeline status and logs.

Before

Pipeline status and CI logs act as the de facto source of truth for what was tested and who approved.

After

A separate append-only audit record store per merge captures test reports, reviewer identity, policy and override reasons, independent of CI log retention.

Consequence

Audits remain answerable after log expiry, but the merge path now must write durable evidence as a mandatory step — a new failure mode if writing records is best-effort.

Source video ↗

Merge correctness is validated per-PR against trunk head.

Before

Submit queue serially rebases and re-tests one candidate change at a time against the current trunk.

After

Queue speculatively tests a set of likely post-merge futures in parallel.

Consequence

Higher compute and scheduling complexity in exchange for fewer trunk breaks; queue design becomes a speculative-execution problem with cancellation and invalidation semantics.

Source video ↗

Checks are positioned late, at the queue.

Before

Expensive regression and compliance checks run after a change is submitted, blocking the merge.

After

Checks move left into earlier pipeline stages so breaking changes are caught before entering the queue.

Consequence

Queue latency and contention drop, but developers absorb feedback earlier and earlier-stage checks must run against incompletely assembled state.

Source video ↗

Human approval is the gate for routine changes.

Before

A person approves dependency bumps and similar routine changes, with rationale implicit.

After

A written policy auto-approves defined classes of change and emits an audit record.

Consequence

Approval throughput decouples from headcount, but the policy corpus becomes critical infrastructure requiring versioning and review itself.

Tradeoffs and failure modes

5

Fast CI vs. durable evidence

Benefit

Caching and sharding shorten pipeline time and reduce the cost of repair laps.

Cost or risk

Accelerating CI does not by itself preserve provenance; execution artifacts expire while accountability obligations persist, so a fast pipeline can still be unauditable.

Source video ↗

Automated first-pass review vs. meaningful oversight

Benefit

Using agents for first-pass review clears the review queue and keeps pace with agent PR volume.

Cost or risk

An approval produced by an automated reviewer that is not strictly separated from the authoring agent is self-attestation, and automating approval does not by itself create genuine scrutiny.

Source video ↗

Throughput push vs. approval quality

Benefit

Removing upstream bottlenecks moves more changes toward merge.

Cost or risk

Volume accumulates at the review gate and degrades into rubber-stamping, where approval is granted to keep queues moving rather than because the change was assessed.

Source video ↗

Flaky-test overrides vs. audit integrity

Benefit

Overriding a known flaky test unblocks a PR without reworking the test suite.

Cost or risk

An override and a clean pass are indistinguishable in pipeline status, so the record must capture that an override occurred and why; otherwise the audit cannot tell a waived failure from a genuine success.

Source video ↗

Parallel speculative merge testing vs. compute cost

Benefit

Testing likely futures in parallel prevents composition failures from reaching trunk.

Cost or risk

Parallel speculation multiplies test executions and must handle invalidation when the projected trunk changes underneath a speculative run.
